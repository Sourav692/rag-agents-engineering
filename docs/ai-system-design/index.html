Distributed systems for AI

Every AI system is still a distributed system. The model is one more remote dependency: slow, expensive, rate-limited and sometimes wrong. The classic toolkit carries most of the load.

module
0
time
2 wk
lessons
5
progress
not started

by the end you can

  1. Write SLOs and an error budget for a service with an AI dependency
  2. Apply timeouts, backoff with jitter, bulkheads and circuit breakers
  3. Model capacity and cost before choosing components

lessons

  1. 0.1

    Requests, queues and back-pressure

    • Synchronous vs asynchronous paths; when a queue absorbs bursts
    • Back-pressure and load shedding so overload stays local
    • Streams for long-running or fan-out work
  2. 0.2

    Caching and consistency

    • Cache layers: client, edge, application, model-side
    • Invalidation, TTLs and stale reads
    • Consistency choices for user state and indexes
  3. 0.3

    SLOs and error budgets

    • SLIs that users feel: latency percentiles, availability, quality
    • Error budget = 100% minus the SLO
    • Separate SLOs per user journey, not one global number
  4. 0.4

    Resilience patterns

    • Timeouts on every remote call
    • Capped exponential backoff with jitter
    • Bulkheads and circuit breakers around throttled dependencies
  5. 0.5

    Capacity and cost modelling

    • Back-of-envelope sizing: requests, payloads, concurrency
    • Cost drivers per request, per user, per month
    • Headroom and peak-to-average ratios

expert test

Inference and serving

For foundation-model systems, the serving layer sets cost, latency and capacity. The concepts form a chain: hardware physics, metrics, memory, scheduling, topology, routing.

module
2
time
3 wk
lessons
6
progress
not started

by the end you can

  1. Explain prefill vs decode and what bounds each
  2. Design SLOs on TTFT, TPOT and goodput
  3. Size a deployment: GPUs, parallelism, batch and KV budget

lessons

  1. 2.1

    Prefill, decode and the metrics

    • Prefill is compute-bound; decode is memory-bandwidth-bound
    • TTFT, TPOT/ITL, end-to-end latency, goodput
    • Output length dominates latency
  2. 2.2

    KV cache and batching

    • PagedAttention: KV memory in pages
    • Continuous (iteration-level) batching
    • Chunked prefill to protect decode latency
  3. 2.3

    Reusing work

    • Prefix caching cuts prefill only
    • RadixAttention for multi-call programs
    • Tiered KV storage: GPU, CPU, SSD, remote
  4. 2.4

    Topology

    • Disaggregated prefill and decode pools
    • Tensor, pipeline and expert parallelism
    • Multi-tenant LoRA adapters on one base model
  5. 2.5

    Making it faster and smaller

    • Speculative decoding helps at low load only
    • FP8 and INT4 quantisation; hardware support
    • Distillation as a serving decision
  6. 2.6

    Routing and scaling

    • KV-cache-aware routing through an inference gateway
    • Scale on queue or batch size, not GPU utilisation
    • Cold starts and warm pools

course/syllabus/module 6

Reliability: retries, idempotency and fallbacks

Model calls fail often and in new ways: overload errors, partial streams, malformed output, tool calls with side effects. Retrying blindly duplicates actions and amplifies outages.

module
6
time
1 wk
lessons
6
progress
not started

by the end you can

  1. Design retries that never repeat a side effect
  2. Bound retry amplification with budgets and circuit breakers
  3. Fail over across models and providers with known behaviour

lessons

  1. 6.1

    Idempotent side effects

    • Idempotency keys on every side-effecting tool
    • Replay the stored result; reject a reused key with new parameters
    • Workflow run ID plus activity ID as the key
  2. 6.2

    Retry budgets

    • Retry at one layer only, just above the failure
    • Cap retries per request and per client
    • Retry budgets as a share of active requests
  3. 6.3

    Overload and fallback

    • 429 and 529: honour Retry-After
    • Circuit breakers on throttled backends
    • Fallback models need their own evals and a degraded mode
  4. 6.4

    Partial streams

    • A 200 can still fail mid-stream
    • Once tokens reach the user, the call is committed
    • Discard, resume or surface: pick a policy
  5. 6.5

    Output repair

    • Structured outputs vs JSON mode
    • Bounded validate-and-repair loops
    • Keep repair retries apart from transport retries
  6. 6.6

    Durable retries

    • Activities run at least once
    • Retry policies with backoff in the workflow engine
    • Timeouts per step, not only per run

design exercise

expert test

lessons

  1. 9.1

    Delegation vs impersonation

    • OAuth token exchange (RFC 8693)

  2. 9.2

    • MCP on OAuth 2.1 with PKCE

    • Sync lag when permissions change

    • Prompt-cache timing leaks across users
    • Per-tenant caches, indexes and memory
    • Log who asked, which agent, which scope, what changed
