M21 Framework fluency with LlamaIndex

M21 rebuilds pipelines you already know from the LangChain modules in LlamaIndex: a plain vector RAG, hybrid fusion, reranking and an enrichment window. The ideas are the same; the class names and several defaults change. The M21 notebooks build on four ideas: the Node as the unit LlamaIndex indexes, the QueryEngine that wraps retrieval and answering, the postprocessors that edit the retrieved list in between, and the sentence window that retrieves one sentence and sends its neighbours.

Open the lab

The notebooks run on a 33-page climate-change PDF and a 100-row customer CSV. These pages and the lab use the Larkspur Cloud handbook from M10 to M12, loaded as two Documents: the refunds section from M12 and a short exports section. Three golden questions carry the module: Can I get a refund on an annual plan after 45 days?, How long does a refund take to appear? and Can I export my data after I cancel my plan? The first one is the hard case. Its best-matching sentence is the 30-day full-refund rule, and the answer sits in the sentence after it.

TL;DR

  • A LlamaIndex Node is a chunk with an id, metadata and links to its source Document and its neighbours. chunk_size counts tokens, and the metadata string counts against it: on the notebook’s PDF the page label and file path take 38 of the 200 tokens.
  • index.as_query_engine() builds a retriever, a list of node postprocessors and a response synthesizer, and returns the answer with its source_nodes. Check the defaults: similarity_top_k is 2, and QueryFusionRetriever makes 4 queries (3 of them written by the LLM) unless you set num_queries=1.
  • Postprocessors run in list order on the retrieved nodes. On the handbook, retrieving 10 sentences and letting the ms-marco-MiniLM-L-6-v2 cross-encoder keep 2 brings in the prorated-refund rule that plain top-2 retrieval misses.
  • A sentence window embeds one sentence and sends up to window_size sentences on each side. In the lab the retrieval scores are identical for every window size; only the text the LLM reads changes, from 142 characters for the bare sentence to 621 at the notebook’s window_size=3.
  • The notebooks pass a FAISS store to IngestionPipeline without an embedding step, so FAISS stays empty and VectorStoreIndex(nodes) builds a second, in-memory index. Read what each object actually holds before trusting a port.

M10 to M20 built every technique in LangChain. The ideas are framework-independent, and rebuilding them in LlamaIndex is the test: if a port behaves differently, either the framework does something different or the idea was only half understood.

LlamaIndex has two text objects where LangChain has one. A Document is what a reader loads: the directory reader turns 01a’s climate-change PDF into 33 Documents, one per page, and a paged CSV reader turns 01b’s 100-row customer file into 100 Documents, one per row. A Node is what the index stores: a piece of a Document with its own id, text, metadata, an optional embedding, and relationships. Every node the sentence splitter produces carries three relationships: its source Document, the previous node and the next node. The neighbour links let a query engine fetch the text around a hit later (lesson 21.4).

The concepts map onto the LangChain pieces from M10 to M18:

Same numbers, different chunks

Two differences change the chunks you get from the same settings.

Chunk size counts tokens. 01a sets a chunk size of 200 with 50 of overlap and says so in a comment: LangChain’s splitter measures characters by default, LlamaIndex’s measures tokens. 200 tokens is several times longer than 200 characters, so a “200” ported from a LangChain notebook is not the same split. We call this the unit swap.

Metadata counts against the chunk and goes into the embedding. The sentence splitter builds the metadata string a node will carry, measures it in tokens and subtracts it from the chunk size before splitting. The PDF reader attaches seven fields (page label, file name, path, type, size and two dates) and excludes all but the page label and file path from the embedding and LLM text:

Setting Value on 01a’s PDF
Chunk size 200 tokens
Metadata kept in the embedded text (page label, file path) 38 tokens
Room left for text 162 tokens
Largest of the 123 nodes 158 tokens of text

Table 2: Metadata eats the chunk (measured on the checkout used for this page).

The absolute file path is part of every vector. Exclude fields from the embedding and LLM text on the Documents, before splitting, when they should be stored but not embedded.

Splitting never crosses a Document boundary. Notebook 02a uses the splitter’s defaults, 1,024 tokens with 200 overlap, and every PDF page fits in one chunk. The 33 pages become exactly 33 nodes. The page, not the chunk size, decides what a chunk is. On the Larkspur handbook the two sections load as two Documents; lesson 21.4 splits them into one node per sentence, 13 for refunds and 4 for exports.

QueryEngine

A query engine turns a question into an answer in three stages. index.as_query_engine(similarity_top_k=2) returns one, and each query runs:

Figure 3: A query engine’s three stages.

  • The retriever embeds the question and returns the nearest nodes with their scores. The default is 2.
  • The postprocessors run in list order. 01a passes none; lessons 21.3 and 21.4 add a reranker and a window replacement here.
  • The synthesizer puts the nodes’ text into a prompt for the configured LLM. The default mode, compact, packs the nodes into as few prompts as the context window allows, then refines the answer across them.

The response holds the answer and the source nodes it was built from, with their scores. 01a’s evaluation reads both: the answer goes to correctness and faithfulness metrics, the source texts become the retrieval context for DeepEval’s contextual relevancy metric. Logging the source nodes on every production query gives the same view without an evaluation run.

The CSV variant

01b reads each CSV row as one Document whose text is one “column: value” line per field: index, customer id, first name, last name, company and so on. It skips splitting, embeds each row, and asks which company does sheryl Baxter work for? with two results. The answer is in row 1 (Rasmussen Group), and the row’s own text names her, so one retrieved row is enough.

A question about many rows, such as how many customers are in Chile?, gets the same two rows, and no prompt can count the other 98. That is lesson 19.4’s sample average again: row-per-Document RAG answers lookups, and counts, sums and filters belong to a query over the table.

In practice: porting Larkspur’s pipeline

  1. Convert the chunk size: Larkspur’s 300-character split is about 75 tokens at a rough four characters per token, not 300; measure it with the splitter’s own tokeniser.
  2. Exclude file paths from embedded and LLM metadata before splitting.
  3. Embed in the pipeline and count vectors in the store afterwards.
  4. Log source nodes for every answer, as lesson 19.2 kept its context.

Key Takeaways

  • A Document is what a reader loads; a Node is what the index stores, with an id, metadata and neighbour links. Splitting never crosses a Document boundary.
  • The sentence splitter counts tokens, not characters (the unit swap), and subtracts embedded metadata from the chunk size: 38 tokens of page label and path leave 162 of 200 for text.
  • A query engine retrieves, postprocesses and synthesises; log its source nodes. Put the embedding model in the ingestion pipeline, or the vector store you passed stays empty.

Check yourself

1. A teammate ports a LangChain pipeline with chunk size 200 to LlamaIndex and keeps the number. What changes?

The unit. LangChain’s splitter counts characters by default and LlamaIndex’s counts tokens, so 200 tokens is several times longer than 200 characters. LlamaIndex also subtracts embedded metadata from the chunk: on 01a’s PDF, 38 tokens of page label and file path leave at most 162 tokens of text.

2. After 01a's ingestion runs, the FAISS index holds 0 vectors, yet queries return answers. How?

The pipeline has no embedding step and only adds already-embedded nodes to its store, so FAISS stays empty without an error. The vector store index then embeds the nodes again into the default in-memory store, and that is what the notebook queries. Embed in the pipeline and build the index with FAISS as its storage.

3. The CSV variant answers which company Sheryl Baxter works for. Why would it fail when asked how many customers are in Chile?

The first is a lookup: one row names her and holds the answer, and two retrieved rows include it. The second needs every row, and retrieval returns two, so no prompt can count the other 98. Counts, sums and filters belong to a query over the table, as in lesson 19.4.

Three of the defaults change what a port does:

  • The number of queries defaults to 4. The retriever keeps your question and asks the configured LLM to write 3 more, then runs every query on every retriever: with two retrievers, 8 retrievals and one LLM call per question. 02a sets it to 1, which turns query generation off. M17 covers what the extra queries buy.
  • The final cut defaults to 2. 02a does not set it. Two retrievers with two hits each still return two nodes.
  • The mode defaults to simple. The four modes, as the installed llama-index-core 0.14.25 implements them:
Mode Scaling inside each list How lists combine
Relative score Min-max: best 1, worst 0 Times weight, summed per node
Distance-based score Min-max between mean ± 3 standard deviations Times weight, summed per node
Reciprocal rerank 1 / (60 + rank), rank from 0 Summed per node; weights ignored
Simple None Highest raw score per node

Table 2: The four fusion modes.

Weights are divided by their sum: 0.6 and 0.4 stay as they are, and 3 and 2 become the same thing. Scores in the two score modes are also divided by the number of queries.

Only simple keeps the answer, and for the wrong reason: it compares a BM25 score with a cosine similarity, and BM25 scores run higher. We call that scale collision. Three behaviours explain the rest of the table:

  • With two hits per list, the distance-based mode ignores the gap. Two scores have a mean halfway between them and a standard deviation of half their difference, so mean ± 3 standard deviations always maps the better one to 2/3 and the worse to 1/3. In a check with fixed scores, dropping the vector runner-up from 0.80 to 0.10 left every fused score unchanged. The weights then decide the order: 0.6 × 1/3 = 0.2 for the vector runner-up beats 0.4 × 1/3 = 0.1333 for the BM25 runner-up. Flip the weights to 0.4 and 0.6 and the prorated rule takes second place at 0.2.
  • Relative score with two hits sends every runner-up to 0. Both second places score 0 here, and the cut falls between equal scores.
  • Reciprocal rerank drops the weights. The constant is 60 and ranks start at 0. A node first in one list scores 1/60. M16’s ensemble multiplies each term by its weight and counts ranks from 1, so the two “RRF” scores are not interchangeable.

Pitfall: same name, different formula. 02a’s note says reciprocal rerank is unsuitable “since there is no normalization”. Rank fusion never looks at the scores, and their scales cannot hurt it; the mode where scales collide is simple, the default. M16’s fusion lesson works through score and rank fusion in general; in LlamaIndex the same mode names carry different constants.

The BM25 side differs from LangChain’s too. LlamaIndex’s BM25 retriever uses an English stemmer, English stop words and a word pattern of two or more characters, so “refund” in the question matches “refunds” in the prorated rule. LangChain’s splits on whitespace and would not match them: lesson 16.2’s token mismatch, already fixed here.

Score direction

Every fusion mode assumes a higher score is better. 02a’s vector retriever comes from the default in-memory store, which returns cosine similarity. The assumption holds. Wire the notebook’s FAISS store in properly (lesson 21.1) and it stops holding: a flat L2 index returns squared L2 distances as the score, where lower is better.

The same three handbook sentences, retrieved for the 45-day question through two FAISS indexes:

Sentence Inner-product index score L2 index score
30-day full-refund rule 0.6922 0.6155
Monthly plans are not refundable 0.5373 0.9254
Prorated rule 0.5267 0.9465

Table 4: One ranking, two score directions.

The order is the same; the scale runs the other way. On unit-length vectors the squared distance is 2 minus twice the cosine (2 - 2 × 0.6922 = 0.6156). Feed the L2 list to relative score and the nearest sentence scales to 0 while the farthest gets the full weight. We call this the flipped score, the fusion cousin of lesson 16.1’s flipped threshold.

Relative score’s min-max on each column of Table 4 shows the flip:

In practice: Larkspur’s hybrid port

  1. Set every argument: number of queries, final similarity_top_k, mode and weights; never rely on the defaults.
  2. Retrieve deeper than 2 per list: min-max modes need more than two points to scale.
  3. Use reciprocal rerank when the lists’ scales differ, knowing it ignores weights.
  4. Use an inner-product index on normalised vectors for FAISS, and print each retriever’s raw scores once before trusting the fused list.

Fusion decides which nodes come back. Lesson 21.3 reorders and trims them before the model reads them.

Limits of this evidence

  • One question, a local model. Tables 3 and 4 use the handbook split into sentences and all-MiniLM-L6-v2; 02a’s OpenAI model scores differently, and other questions can rank the modes in another order.
  • Two hits per list is the worst case for the two score modes. With deeper lists, min-max and the mean ± 3 standard deviations rule keep more of each list’s spread.
  • One release. The mode formulas and defaults are those of llama-index-core 0.14.25; the switcher’s scaled values are hand arithmetic on Table 4, checked against that release’s formula.

Key Takeaways

  • Check the defaults before porting: four queries add an LLM call and multiply retrievals, a final cut of 2 trims the fused list, and the default simple mode compares raw scores across retrievers (scale collision).
  • With two hits per list the score modes flatten the gap and the weights decide the order; reciprocal rerank ignores the weights and counts ranks from 0. On the 45-day question three of four modes drop the answer.
  • Every fusion mode assumes higher is better. Use inner product on normalised vectors rather than L2 distance (the flipped score), and print each retriever’s raw scores once.

1. A port of M16's hybrid retriever to LlamaIndex sets only the retrievers and weights. What does it do differently from the original?

It generates 3 extra queries with an LLM and runs all four on both retrievers, 8 retrievals per question; it cuts the fused list to 2; and it uses the simple mode, which takes the highest raw score per node and so compares BM25 scores with cosine similarities.

Lesson 21.2 fused two retrievers and, on the 45-day question, cut the answering sentence in three modes out of four. M18 handled that with a second stage. In LlamaIndex the second stage has a fixed slot.

A node postprocessor takes the retrieved list of scored nodes and the question, and returns a list. It can reorder the nodes, drop some, replace their scores or rewrite their text. A query engine runs its postprocessors in list order, after the retriever and before the synthesizer; outside an engine, one can be run by hand on a list of nodes, as 03a does for its comparison.

The cell that sets up the example also carries a port bug. It builds each Document with LangChain’s keyword for the text. LlamaIndex accepts the unknown keyword and creates a Document whose text is empty. The comparison function rebuilds the list with LlamaIndex’s own keyword, so the comparison still works, but the first list is five empty Documents, and nothing warns. We call this the silent keyword.

Order in the list

Postprocessors see whatever the one before them produced. With lesson 21.4’s window replacement in the same list, the order decides what the reranker judges:

Order The reranker scores Trade-off
Reranker, then window The single sentence that was embedded Short inputs, fast; judges the sentence without its context
Window, then reranker The whole window More context per pair; longer inputs, slower

Table 4: Two orders for a reranker and a window.

Follow the 45-day question through each order, with 10 sentences retrieved and the cross-encoder keeping 2:

Choose the order of the two postprocessors and see what the cross-encoder judges and what the model reads.

Reranker, then window

  • The cross-encoder scores 10 single sentences and keeps the 30-day rule and the prorated rule (Table 2).
  • The window postprocessor then swaps each kept sentence for its neighbours.
  • The model reads two windows built around the right sentences.

Window, then reranker

  • The window postprocessor first turns all 10 sentences into windows of up to seven sentences.
  • The cross-encoder scores 10 long passages, and neighbouring hits share most of their text.
  • Inputs are several times longer, and the scores in Table 2 no longer apply.

Decide which text the reranker should judge, and write the list in that order.

In practice: reranking Larkspur’s sentences

  1. Retrieve 10 sentences, rerank, keep 3, passing the model and the cut explicitly.
  2. Cut by count, not at a score of zero.
  3. Window after reranking for the handbook: the cross-encoder judges sentences and the model reads windows.
  4. Assert Documents have text after building them, to catch the silent keyword.

Key Takeaways

  • Node postprocessors run in list order between the retriever and the synthesizer, and can reorder, drop, rescore or rewrite nodes. Retrieve wide and let a reranker keep the top few.
  • The LLM reranker can silently return fewer nodes with tied integer scores; the cross-encoder reranker defaults to a different model and a cut of 2 (the default swap), so always pass both.
  • Cross-encoder scores are logits that only rank: the Larkspur answer scores -2.1011 and still ranks 2nd. Calibrate any cut-off on the golden set, or cut by count.

Check yourself

1. A port of 03a's cross-encoder reranker drops the model and cut arguments. What changes?

The default swap: the reranker falls back to cross-encoder/stsb-distilroberta-base instead of the ms-marco model, and keeps 2 nodes instead of 5. Both the scoring and the number of nodes the synthesizer reads change, without an error. Always pass both arguments.

2. After reranking the 45-day question, the prorated rule scores -2.1011. Should a filter drop nodes below zero?

No. The ms-marco cross-encoder returns a logit that only ranks: the prorated rule is 2nd and is the sentence that answers the question. A cut at zero would drop the answer. Cut by count, or set any threshold from the golden set for this exact model.

3. A query engine runs a cross-encoder reranker and a window replacement. What decides their order?

Which text the reranker should judge. Reranker first scores the single embedded sentence, with short, fast inputs; window first scores the whole window, with more context and longer inputs. Each postprocessor sees what the previous one produced, so the list order is the decision.

Sentence window

Lesson 21.4: Sentence-window retrieval. Notebooks: 04a_context_enrichment_window_with_llamaindex.ipynb

What you’ll learn

  • Explain how a sentence window embeds one sentence and sends its neighbours to the model.
  • Trace three Larkspur questions through window sizes 0 to 3, and find each one’s minimum.
  • Diagnose a window that cannot fix a retrieval miss, and two windows that send the same sentences.
  • Count what stored windows cost in metadata.

Lesson 21.3 ended with a reranker that judges single sentences. Single sentences match a question precisely and answer it badly: the 45-day question retrieves the 30-day rule, and the prorated rule that answers it is the next sentence.

Small chunks match a question precisely and large chunks answer it completely (M12). A sentence window does both: it embeds single sentences and, once one is retrieved, sends the model the sentences around it. LlamaIndex builds it from two pieces, a node parser at indexing time and a postprocessor at query time:

Figure 1: Sentence-window retrieval. The window travels as metadata until the postprocessor puts it in the text.

The two pieces do this:

Piece When What it does
Sentence-window node parser Indexing Splits each Document into sentences with NLTK’s Punkt tokenizer, one node per sentence; stores the sentences from i - window_size to i + window_size as a window field, and the sentence itself as a second field (04a renames it original sentence); excludes both from the embedding and LLM text
Metadata replacement postprocessor After retrieval Sets each node’s text to its window field; a node without one keeps its text

Table 1: The two pieces of a sentence window.

The window size defaults to 3, seven sentences in all, as 04a’s comment says, and must be greater than 0. A window never crosses into another Document. The notebook’s remark that “metadata replacement” sounds off-topic comes from this design: the neighbours travel as metadata until the postprocessor puts them in the text.

On the Larkspur handbook the parser makes 17 nodes: 13 sentences in the refunds section and 4 in exports. The first sentence of each section carries the section title with it, because Punkt does not split at a blank line.

Four behaviours follow:

  • The window changes what the model reads, never what is retrieved. Every sentence scores the same at every window size, because the window is excluded from the embedding. Tuning the window size cannot fix a retrieval miss.
  • Each question needs a different window. The 45-day question needs 1, the refund-timing sentence answers alone, and the export question needs the “Settings, then Data” sentence two places back. One global size over-sends for some questions and under-sends for others.
  • The Document boundary caps the window. The exports section has four sentences. Every window from 2 up sends the same 272 characters. That limit helps when sections are independent and hurts when the answer spans two of them.
  • Two hits can send the same sentences twice. At 2 retrieved, the refund-timing question gets its sentence and the 30-day rule two places before it. At window 3 their windows share 5 sentences, and the model reads 1,241 characters to cover 9 distinct sentences. We call this window overlap, as in lesson 18.5; merge overlapping windows before synthesis.

What stored windows cost

The window is stored, not computed at query time. Each node holds its window and a copy of its sentence in metadata:

Window size Metadata on the handbook’s 17 nodes Sentence text Ratio
1 5,249 characters 1,380 characters 3.8
3 (default) 9,313 characters 1,380 characters 6.75
5 12,342 characters 1,380 characters 8.9

Table 3: Stored window metadata against sentence text (the module’s lab).

We call this the stored window: at the default size, the handbook’s metadata is 6.75 times its text, held in the docstore or the vector store’s payload for every node.

The alternative computes the window at query time instead of storing it:

Figure 2: A query-time window, as in M18. Nothing extra is stored; each query pays for the lookup.

Key distinction: M18’s enrichment windows do the same job with character chunks and a neighbour lookup at query time. LlamaIndex moves the work to indexing time and the unit to the sentence, and pays in storage instead of lookups.

04a compares the sentence window against a sentence-splitter index at its 1,024-token default, both retrieving one node. Both of 04a’s pipelines are handed the same FAISS store, which stays empty for the reason in 21.1; each index builds its own in-memory store.

In practice: windows on the Larkspur handbook

  1. Window size 2 covers all three golden questions at one retrieved sentence (Table 2).
  2. Keep sections as separate Documents, so a refunds window never pulls in export sentences.
  3. Merge overlapping windows whenever more than one sentence is retrieved.
  4. Budget the metadata: 6.75 times the text at the default size, for every node.

Limits of this evidence

  • The lab’s model, not the notebook’s. Every number comes from the module’s lab with all-MiniLM-L6-v2; 04a’s text-embedding-3-small can retrieve a different sentence for the same question.
  • Seventeen sentences. Three questions over a short handbook show the behaviours; they do not size a window for a larger corpus. Choose it on your own golden set.
  • Punkt decides the units. A sentence tokenizer that keeps a section title on the first sentence, or splits an abbreviation, changes every window.

Key Takeaways

  • A sentence window embeds single sentences and swaps in the surrounding sentences after retrieval. The window changes what the model reads, never what is retrieved.
  • Each question needs a different window (1, 0 and 2 for the three Larkspur questions), a Document boundary caps how far a window reaches, and overlapping windows send the same sentences twice.
  • Windows are stored in metadata on every node (the stored window): at the default size of 3, the handbook’s metadata is 6.75 times its sentence text.

Check yourself

1. The 45-day question retrieves the 30-day rule at every window size. Can a larger window fix a retrieval miss?

No. The window is excluded from the embedding, so every sentence scores the same at every window size, and the same sentence is retrieved. The window only changes what the model reads. Here a window of 1 is enough, because the prorated rule that answers the question is the next sentence.

2. For the export question, windows of 2, 3 and 5 all send 272 characters. Why?

The exports section has only four sentences and is its own Document, and a window never crosses a Document boundary. From a window of 2 up, the window already covers the whole section, so larger sizes add nothing.

3. At two retrieved sentences and window 3, the refund-timing question sends 1,241 characters covering 9 distinct sentences. What is wrong, and what is the fix?

Window overlap: the two retrieved sentences sit two places apart, so their seven-sentence windows share 5 sentences, and the model reads them twice. Merge overlapping windows from the same Document into one passage before synthesis.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. You port Larkspur’s hybrid retriever to LlamaIndex: a FAISS IndexFlatL2 vector store and BM25, fused with QueryFusionRetriever(mode="relative_score"). The fused top result is now the least relevant handbook passage. What happened?

What a strong answer covers:

  • Prints each retriever’s raw scores before fusion. With IndexFlatL2, LlamaIndex’s FAISS store returns squared L2 distances as score, so lower is better
  • relative_score min-max scales each list with higher meaning better, so the nearest chunk gets 0 and the farthest gets the full weight
  • Fixes the direction at the source: IndexFlatIP on normalised vectors (cosine similarity), or a retriever wrapper that flips distances
  • Adds a golden-set check that compares fused results with each retriever alone, so a scale or direction bug shows up as a regression

2. The refund assistant answers “Can I get a refund after 45 days?” with “No, only within 30 days.” The handbook prorates refunds after day 30. Do you raise window_size, raise similarity_top_k, or add a reranker?

What a strong answer covers:

  • Checks the retrieved sentence first: it is the 30-day rule, and the prorated rule is the next sentence, ranked third
  • A window of 1 sends both rules in 284 characters; similarity_top_k=2 adds “Monthly plans are not refundable” instead
  • A cross-encoder over the top 10 also brings the prorated rule into the top 2, at the cost of a model call per candidate
  • Weighs storage too: at window_size=3 the handbook’s window metadata is 6.75 times its text, held on every node

3. The M21 lab asks you to port the Part VI hybrid-plus-rerank pipeline to LlamaIndex and confirm the metrics match. They do not. How do you find out why?

What a strong answer covers:

  • Compares retrieved node ids per golden question before comparing answer scores, so retrieval and generation differences separate
  • Lists the default changes: chunk_size in tokens against LangChain’s characters, metadata counted in the chunk budget and embedded with the text, and similarity_top_k=2
  • Checks BM25 tokenisation: LlamaIndex’s BM25Retriever stems and drops English stop words, LangChain’s splits on whitespace
  • Checks fusion: LlamaIndex’s reciprocal_rerank ignores retriever_weights, while EnsembleRetriever applies weights to RRF

4. LLMRerank(top_n=5) sometimes returns one node, and on a few questions none. The answers that follow are thin or refuse. What is going on, and what do you change?

What a strong answer covers:

  • The default prompt tells the LLM to leave out documents that are not relevant, so the output can be shorter than top_n
  • Nodes the LLM omits are dropped, and the parser skips lines it cannot read without raising, so a reply in another format drops its whole batch of up to 10
  • Logs the raw reranker reply and the count in and out per query, and alerts on empty results
  • Falls back to the retrieval order when the reranker returns too few nodes, or uses a cross-encoder, which always scores every candidate

5. A refactor removed num_queries=1 from the fusion retriever. Retrieval quality looks the same on the golden set, but latency and the LLM bill went up. Why?

What a strong answer covers:

  • QueryFusionRetriever defaults to num_queries=4: one LLM call writes 3 extra queries, and each query runs on every retriever
  • With two retrievers that is 8 retrievals and one generation call before the answer step starts
  • Treats default parameters as part of the pipeline’s config: pin them explicitly and diff them in code review
  • Measures per-stage latency and token use in traces, not only end-to-end quality, so a cost regression shows even when accuracy holds

Key Takeaways

  • Map the concepts first: Document and Node, retriever, postprocessor, QueryEngine. Then read the defaults, because they differ from LangChain’s.
  • Check what each component holds after the pipeline runs: vectors in the store, metadata in the embedding text, and the score direction of every retriever.
  • Put reranking, filtering and window replacement in node_postprocessors, in the order you want them applied.
  • Retrieve small, send big: a sentence window keeps the retrieval scores of a sentence and gives the model the paragraph around it. Size the window per question type and watch overlap when k is above 1.
