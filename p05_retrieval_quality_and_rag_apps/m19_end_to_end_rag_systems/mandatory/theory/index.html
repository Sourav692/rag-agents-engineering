M19 End-to-end RAG systems

A RAG pipeline returns an answer. A RAG system returns an answer a user can check: the chunks it came from, the sentences that support it, and a refusal when the evidence is missing or the question needs something other than retrieval. The M19 notebooks build on four ideas: grounding the answer in retrieved context, a schema for citations, how a table row becomes a retrievable record, and running the pipeline on your own hardware.

Open the lab

The running example is the Larkspur Cloud handbook from M10 to M12 (refunds, exports, outages) plus its server catalogue: ten server sizes with vCPUs, memory, a monthly price and a one-line description. The golden questions are Can I get a refund on my annual plan? for citations, and four questions on the catalogue for structured data: the average monthly price, the servers under $50, the ls-cpu-8 server, and a server for a memory-hungry database.

TL;DR

  • Grounded generation has three parts: evidence retrieved for this question, an instruction to use only that evidence, and permission to say “I don’t know”. Lesson 19.1’s chain has all three but formats the metadata away, so its answers cannot be checked.
  • RunnablePassthrough.assign keeps the retrieved chunks in the output with one retrieval. A second call fills a QuotedCitations schema (id, source, title, page, quotes); check every quote against its chunk in code, because the notebook’s highlighter fails silently on a paraphrase.
  • An LLM explanation per retrieved chunk costs k extra calls and, asked why a chunk is relevant, explains even a wrong one. Show scores to engineers and grade relevance with a yes or no.
  • Put a record’s description in page_content and its ids, numbers and dates in metadata. In the lab, embedding every column shrinks the lead of the right rows from 0.115 to 0.0004, and What is the average monthly price? answered from the top 4 rows gives $36.25 where the table says $102.50.
  • The local pipeline embeds with bge-base-en-v1.5 and searches FAISS on your machine, but generates through the Hugging Face Inference API. Fully local means HuggingFacePipeline as well.

Mental model

Each box adds something a reader can verify. The router keeps questions that need the whole table away from top-k retrieval; the metadata carried from retrieval to the answer is what makes a citation point somewhere; the quote check is the one step that runs as code, not as a model call.

Grounded generation

Lesson 19.1: Environment setup and a complete RAG system. Notebooks: 01a_setup.ipynb, 01b_build_a_simple_rag_system.ipynb, 01c_simple_rag_pdf.ipynb (optional)

What you’ll learn

Lessons M16 to M18 made retrieval find more, rank better and fit the budget. M19 turns a retrieval pipeline into a system someone can rely on, and starts by building one end to end.

A Larkspur customer asks Does Larkspur offer a free tier? The handbook says nothing about one. A chain that retrieves five chunks and asks the model to “answer the question” gets a fluent reply anyway, drawn from what the model knows about other hosting providers. The answer reads as policy, and it is invented.

Grounded generation means the answer comes from evidence the system retrieved for this question, and the model is told to use nothing else. The rest of this page builds that system in two halves: an index built once, and a chain that runs per question.

Building the index once

Notebook 01b indexes two kinds of source into one store. Figure 1 shows the offline half: everything that happens before the first question arrives.

Persisting matters for the second half. The notebook reopens the store from disk with the same collection name and the same embedding model. A question asked tomorrow therefore lands in the same 1,536-dimension space as today’s chunks.

The chain that answers

The chain itself is three steps:

Figure 2: The 01b chain. The retrieved chunks become plain text inside the prompt.

Grounding rests on three things, and 01b’s prompt has all three:

Part 01b’s wording What it prevents
Evidence for this question The five retrieved chunks The model answering from the whole of its training
A limit “Answer the following question using only the following pieces of retrieved context” Blending in outside knowledge
A way out “If the answer is not in the context, do not make up answers, just say that you don’t know” A forced answer when the evidence is missing

Table 2: The three parts of a grounded prompt.

The third part is the one most often left out. Without a permitted refusal, a model asked about something the context lacks answers from what it learned in training. We call that an ungrounded fill: the free-tier answer above.

Whether a given model complies is a property you test. Put questions with no answer in the golden set and count the refusals. The instruction does not guarantee compliance either: a model can still blend in outside knowledge or misread a chunk, and M29 and M32 add a second call that grades the answer against its evidence.

What this chain throws away

01b’s formatting step joins the chunks’ text and nothing else. The title, id and source in metadata never reach the model, and the chain returns only the model’s message. The answer may be grounded, but nobody can check it: there is no list of chunks, and no way to say which one a sentence came from. We call this formatted-away sources.

A setup trap

01b embeds the string “Hello, world!” with the batch method meant for a list of documents, and gets back 13 vectors. A Python string is iterable, so each of its 13 characters is embedded on its own. The single-query method, or a one-item list, gives one 1,536-dimension vector.

Pitfall: character embedding. The same mistake inside an indexing loop embeds characters and stores them without an error. Check that the number of vectors equals the number of chunks after every indexing run.

The optional 01c notebook builds the same pipeline on FAISS from one climate-change PDF, with 1,000-character chunks, 200 of overlap and k = 2, and reconstructs the index matrix to show its shape: one row per chunk, 1,536 columns. The 33-page PDF splits into 97 chunks and the matrix is 97 by 1,536; that row count is the vectors-equal-chunks check in practice.

In practice: a grounded Larkspur assistant

  1. Use all three parts of Table 2 in the prompt, including the way out.
  2. Add unanswerable golden questions (free tier, GPU servers) and track the refusal rate.
  3. Count vectors against chunks after indexing.
  4. Keep the chunks in the output, which lesson 19.2 shows how to do in one retrieval.

Limits

  • The notebook’s sample questions run against Wikipedia articles and papers, not the Larkspur handbook. The Larkspur answers on this page are illustrative expectations, not recorded outputs.
  • A refusal instruction lowers the rate of ungrounded fills; it does not remove them. Only a measured refusal rate on unanswerable questions says how a given model behaves.
  • The 97-chunk count was recomputed offline from the PDF with the notebook’s splitter settings. The embedding dimension comes from the model’s documentation and the notebook’s printed comments, not from a fresh API call.

Key Takeaways

  • Grounding needs three things in the prompt: evidence retrieved for this question, an instruction to use only that evidence, and permission to say “I don’t know”. Without the last, the model fills gaps from training (an ungrounded fill).
  • The instruction does not guarantee compliance. Put questions with no answer in the golden set and count the refusals.
  • A chain that formats only the chunk text and returns only the answer cannot be checked (formatted-away sources). Keep the chunks and their metadata if anyone needs to verify a sentence.

Check yourself

1. A Larkspur assistant answers "Does Larkspur offer a free tier?" with a confident description of one. Which part of a grounded prompt is missing?

Most likely the way out: permission to say “I don’t know” when the answer is not in the context. Without it, a model whose evidence lacks the answer fills the gap from training. Add it, then test with unanswerable golden questions and count the refusals, because the instruction alone does not guarantee compliance.

2. The 01b chain's answers are grounded, but a reviewer cannot tell which chunk any sentence came from. Why?

The formatting step joins only the chunks’ text, so titles, ids and sources never reach the model, and the chain returns only the model’s message. There is no list of chunks to check against. Keeping the retrieved chunks in the output, as lesson 19.2 does, makes the answer checkable.

3. Embedding "Hello, world!" returns 13 vectors. What went wrong, and why is it dangerous in an indexing loop?

The batch method expects a list of strings, and a Python string is iterable, so each of its 13 characters was embedded separately. In an indexing loop the same mistake stores character vectors without an error. Use the single-query method or a one-item list, and check that vectors equal chunks after indexing.

Returning the sources

What you’ll learn

  • Design a citation schema whose quotes a machine can check.
  • Diagnose three things the schema does not guarantee: support, per-claim links and verbatim quotes.

Lesson 19.1’s chain answered from five chunks and then threw them away. A Larkspur agent reading Yes, annual plans are refundable within 30 days has no way to see which handbook passage said so, or whether one did.

Both M19.2 notebooks first run the M15 contextual retrieval notebook (M15.5). That run builds the index the citations depend on, and writes four metadata fields on every chunk:

Shown as stored, a 0-based page tells a reader “page 0”, or sends them to the page before the right one. Add 1 when you display it. We call this the off-by-one page.

Sources at the answer level

Notebook 02a keeps the retrieved documents in the chain’s output instead of formatting them away. The retriever’s result and the question go into a dictionary, and a pass-through step runs the answer chain on that dictionary and adds the answer beside them. Figure 1 shows the shape.

Figure 1: The 02a chain. The answer chain reads the same five documents that the output keeps.

The output holds three things: the five context documents, the question, and the response. The retriever runs once. The chunks the user sees are therefore the chunks the model read.

This is source attribution at the answer level: the reader gets a list of five sources and has to find the supporting sentence in each.

Citation schema

Notebook 02b asks for more: which chunk supports the answer, and the exact sentences. A citation schema is a structured output the model fills, one record per supporting chunk:

What the schema does not guarantee

Three gaps remain, each with a name:

  • Citation after the fact. The second call looks for support for text that already exists. It shows the answer can be justified from the chunks, not that the model used them. A claim with no support may get a loose citation or none, and nothing marks which.
  • The flat list. The schema is a list per answer. Nothing ties a citation to the sentence of the answer it supports. For true per-claim citations, add a claim field (the answer sentence) or have the answer call emit numbered markers that the citations reference.
  • The paraphrased quote. The schema asks for exact sentences; the model can still paraphrase or merge two. 02b’s display code highlights each quoted sentence in its chunk with a pattern match. A paraphrase highlights nothing and raises nothing, and a citation whose id matches no retrieved chunk comes back with no context. Both fail silently.

So check every citation in code before showing it: look the chunk up by id, normalise whitespace in both texts, and test whether the quote is a substring of the chunk. Here are four planted citations against the refund chunk:

Planted quote Check result Why
The verbatim sentence Pass It is a substring of the chunk
The same sentence broken across two lines Pass Whitespace is normalised before comparing
“Annual plans are fully refundable for 30 days.” Fail A paraphrase, and it drops the 100 GB condition
Any quote under an id that was not retrieved Fail No chunk to check against

Table 4: Planted citations against the quote check.

Drop or flag the citations that fail, and track the failure rate as a production metric. A rising rate means the prompt, the model or the chunk text changed.

Pitfall: a citation prompt that sees a Python object. 02b’s citation chain passes the list of retrieved documents straight into its prompt. The model reads the documents’ programming representation, metadata and all, rather than the formatted text the answer chain saw. Format the chunks the same way for both calls.

In practice: cited answers for Larkspur

  1. Keep the context in the output, one retrieval, as 02a does.
  2. Ask for the five-field schema, plus a claim field so each citation names the answer sentence it supports.
  3. Check every quote in code; show only citations that pass, and display pages from 1.
  4. Alert on the failure rate, per model and prompt version.

Citations show which chunk supports an answer. Lesson 19.3 asks a related question about retrieval itself: why a chunk was retrieved at all.

Limits

  • The refund citation and the four planted quotes are illustrative. The notebooks’ own runs use Wikipedia and paper questions, and ship without outputs.
  • A passing substring check proves the quote exists in the chunk. It does not prove the quote supports the claim, or that the answer states the rule completely.
  • 02b’s display code also matches on page: a citation with the right id but a wrong page gets no context either. The quote check on this page is an addition; the notebook only highlights.

Key Takeaways

  • Keep the retrieved documents in the chain’s output, so the retriever runs once and the sources shown are the chunks the model read; display PDF pages from 1, not 0.
  • A citation schema with id, page and verbatim quotes makes citations checkable. It is still a flat list per answer, written after the fact, so add a claim field for per-claim citations.
  • The model can paraphrase a quote or cite an id that was never retrieved. Verify every quote against its chunk in code, drop failures, and track the failure rate.

Check yourself

1. Why does keeping the retrieved documents in the chain's output, rather than retrieving again for display, matter?

The retriever runs once, so the chunks shown to the user are exactly the chunks the model read. Retrieving again for display could return different chunks, and the user would check the answer against evidence the model never saw.

2. A citation for the refund question quotes "Annual plans are fully refundable for 30 days." What does the quote check do, and why is this citation dangerous?

The check fails it, because the text is not a substring of the refund-window chunk. It is a paraphrase that also drops the 100 GB condition, so showing it would put an incomplete rule behind a citation that looks authoritative. Drop or flag it, and count it in the failure rate.

3. The citation schema returns a list of records for the whole answer. What can it not tell you, and how would you change it?

Which sentence of the answer each citation supports, and whether the model actually used the cited chunk, since citations are found after the answer is written. Add a claim field holding the answer sentence, or have the answer call emit numbered markers that the citations reference.

Explaining a retrieved chunk

Lesson 19.3: Explainable retrieval. Notebooks: 03a_explainable_retrieval.ipynb

What you’ll learn

  • Trace an explainable retriever: one search, then one explanation call per chunk.
  • Diagnose an explanation that rationalises a ranking error.
  • Separate explaining a chunk to a user from debugging a ranking.
  • Redesign the explainer as a relevance grader.

Lesson 19.2 linked each answer to the chunks that support it. A user can still ask the step before that: why did the system pick these chunks at all?

Notebook 03a answers with an explainable retriever. It wraps a FAISS index with k = 5 and, for every chunk it returns, makes one more LLM call that writes a paragraph on why the chunk fits the query. The output is a list of pairs: the chunk’s content and its explanation.

Figure 1: One retrieval, then one explanation call per chunk.

Each explanation call receives two things: the query and one chunk’s text. It does not receive the similarity score, the chunk’s rank or the other chunks. Three properties of this design decide where it is useful.

It costs one call per chunk

The loop calls the explanation chain k times, one after another. At k = 5 a single search becomes five model calls before any answer is written:

Explained chunks Explanation calls With the answer call
All 5 retrieved 5 6
Only the 2 the answer cites 2 3
Only the one a user expands 1, on demand 1 + 1

Table 1: Calls per question for three explanation policies.

Run the calls as one batch to cut the wait, or explain only what a reader will look at.

It explains the text, not the ranking

The prompt says “Explain why this context is relevant to the query”. The model never sees the similarity score or the other chunks, and it is not offered “this chunk is not relevant” as an answer.

On the Larkspur handbook that matters. In the M10 TF-IDF index, What happens if my server goes down? ranks the reboot chunk first, on the shared word “server” (M10.2). Asked why reboot is relevant, with no way to say it is not, the model’s likely reply is a reason:

Retrieved chunk Why it ranked first Likely explanation (Illustrative)
reboot: “You can reboot a server from the console…” Shares “server” with the question (TF-IDF 0.416) “Rebooting is one way to recover a server that has gone down.”

Table 2: An explanation for a ranking error (illustrative reply).

That reads as an explanation and is a rationalisation of a ranking error. We call it the rationalised miss. The chunk was ranked by similarity between two vectors; the paragraph is the model’s reading of the query and the chunk side by side, written after the fact.

Table 3 shows what the ranking actually did for that question. Scores were recomputed with scikit-learn’s TF-IDF and English stop words over the twelve M10 chunks, which reproduces the M10 lab.

Rank Chunk TF-IDF score Evidence for the question
1 reboot 0.416 No
2 sizing 0.389 No
3 export 0.217 No
tied at 0 sla, incidents 0.000 Yes

Table 3: The real ranking for the outage question. Both evidence chunks score zero.

The score log tells an engineer the problem is vocabulary: “goes down” never meets “outage”. The explanation for reboot hides it.

Key distinction: an explanation can guide a user and mislead an engineer. To debug retrieval, print the scores and the rank of the chunk you expected, never the explanation.

Ask a question that can say no

A version that helps both readers changes the question:

03a asks Ask instead
Why is this context relevant? Is this context relevant to the query? Answer yes or no, then quote the sentence that decides it.
One free-text paragraph A structured result: relevant or not, a verbatim evidence quote, and the retriever’s score
Every retrieved chunk Only the chunks the answer used, or the ones a user expands

Table 4: From explainer to relevance grader.

The yes-or-no form is a relevance grader. Figure 2 shows where it sits: the same retrieval, but each call returns a verdict that a filter can act on.

Figure 2: The relevance grader. A verdict of “no” removes the chunk and leaves a trace an engineer can read.

On the reboot chunk it can return “no”, with the score beside it, which is the signal the explainer could never give. M28 uses it to filter chunks and rewrite the query, and M32.1 adds a hallucination check and source highlighting on top.

Two notes on running 03a today. Its retriever call uses a method that the current LangChain core no longer has, so it raises an attribute error; the current call is the retriever’s standard invoke. And the demo indexes three sentences with k = 5; FAISS returns all three, so each query gets three explanations, including two for texts about photosynthesis and global warming when the question is why the sky is blue. That is forced top-k (lesson 16.1) again, now with a paragraph defending each forced pick.

In practice: explanations for Larkspur agents

  1. Explain on demand: a support agent clicks a source to see why it is there; no call is spent otherwise.
  2. Grade, then explain: ask the yes-or-no question first, and show the verbatim evidence quote as the explanation.
  3. Show the score beside every explanation, so a weak match is visible as weak.
  4. Debug with ranks, logged per query, never with explanation text.

Lesson 19.4 leaves free text: Larkspur’s server catalogue is a table, and a table row needs its own representation before it can be retrieved.

Limits

  • The explanation and grader replies on this page are illustrative. 03a ships without outputs, and its demo corpus is three science sentences, not the handbook.
  • The TF-IDF scores come from the M10 index. 03a ranks with OpenAI embeddings, which would score the outage question differently; the point about explanations not seeing scores holds for either.
  • A grader is also a model call. It can be wrong in both directions, so its verdicts need the same golden-set measurement as any other judge.
  • The missing retriever method was checked against the installed langchain-core 1.7.0.

Key Takeaways

  • An explainable retriever adds one LLM call per chunk. Batch the calls, or explain only the chunks the answer cites or a user expands.
  • A prompt that asks why a chunk is relevant gets a reason even for a ranking error (the rationalised miss). The paragraph explains the text, not the ranking, so debug retrieval with scores and ranks.
  • Ask a yes-or-no relevance question with a verbatim quote and the retriever’s score instead. That turns the explainer into a relevance grader that can say no.

Check yourself

1. The explainable retriever runs with k = 5. How many LLM calls does one question cost before the answer, and how would you reduce them?

Five, one explanation per retrieved chunk, made one after another. Batch them to cut the wait, and explain only the chunks the answer cites, or only the one a user expands, to cut the count.

2. For "What happens if my server goes down?", the explainer says the reboot chunk is relevant because rebooting recovers a server. Why should an engineer distrust this?

It is a rationalised miss. TF-IDF ranked reboot first only because it shares the word “server”, and the prompt asked why the chunk is relevant with no option to say it is not. The paragraph describes the text after the fact; the score and the rank of the expected chunks show what actually happened.

3. How do you change the explainer so it can flag the reboot chunk as a bad retrieval?

Ask a yes-or-no question instead: is this context relevant, then quote the sentence that decides it. Return a structured result with the verdict, the verbatim evidence and the retriever’s score. That relevance grader can answer “no” for reboot, which the “why is this relevant” prompt never could.

Record representation

Lesson 19.4: RAG over structured data: CSV and JSON. Notebooks: 04a_structured_data_rag.ipynb, 04b_simple_csv_rag.ipynb (optional), 04c_json_rag.ipynb (optional)

What you’ll learn

  • Choose which fields of a table row to embed and which to keep as metadata.
  • Flatten a nested JSON record without losing what you need to filter on.
  • Diagnose four question types that retrieval answers fluently and wrongly.
  • Route a question about a table to search, a filter, a lookup or a query engine.

Lessons 19.1 to 19.3 worked on prose: handbook paragraphs and PDF pages. Larkspur also has a server catalogue, a table of ten sizes with vCPUs, memory, a monthly price and a one-line description. Ask What is the average monthly price of a Larkspur server? and a RAG chain retrieves four rows and averages those, confidently and wrongly.

A table row is a set of typed fields; an embedding model takes one string. Something has to turn the row into text, and that choice, the record representation, decides what the index can find. Notebook 04a shows three ways to write the same row. For the ls-mem-4 row:

Two details make the split work. 04a casts every number to an integer before it goes into metadata, because a range filter compares numbers and a CSV loader returns strings (M11.3). And the context sent to the model adds the metadata back after each description, so the model can quote a price it could not search on.

The rule is a default. “Built in 1962” carries meaning a buyer might search for, in a way “295000” does not. Judge each field by whether its value has meaning or only magnitude.

Nested JSON

JSON adds depth. A support ticket in 04a has a nested customer object, a list of tags and a list of messages. Its conversion makes two separate decisions:

  • Meaning goes to the embedded text: the subject and the conversation, one “sender: body” line per message.
  • Filters go to flat metadata: the customer’s tier becomes a top-level customer-tier field, because Chroma rejects nested objects in metadata.

Lists are the hard case. 04a joins the tags into one string, “export,performance,timeout”, and an equality filter on that string matches only the whole string in that order. Check what your store accepts before flattening: the Chroma version installed in this course (1.5.9) stores a list value as metadata, and its contains operator matches list membership. In a scratch test it returned the record whose tags were the list export and performance, and not the one holding the single string “export,timeout”.

Where the store has no list type, the options are a boolean field per tag, or a relational table for tags with only ids in the vector store. When filtering is that relational, the vector store is the wrong primary home for the data.

The optional notebooks show the two ends. 04b loads a customer CSV with every column in the text and asks which company does Sheryl Baxter work for?, an exact lookup by name. 04c uses JSON path expressions to pick the fields of each Nobel Prize record (year, category, laureate names) that become text before embedding.

Each of these comes back as a fluent, specific answer. We call this the sample average: an answer computed over the rows retrieval happened to return, presented as a fact about the whole table. 04a’s comparison names the difference between the two approaches: query generation fails loudly (a bad query raises an error or returns nothing), and retrieval fails quietly (it answers from whatever it retrieved).

Routing a table question

So route by the kind of question, not the kind of data:

Figure 2: Route a table question by what it needs.

04a builds each branch in its simplest form:

  • Router: one prompt classifies a question as aggregate, lookup or semantic, and the system refuses the first two instead of answering from a sample.
  • Self-query: a structured-output call turns Which properties cost less than $400,000? into a semantic part and, when extraction works, a maximum price of 400,000, which becomes a store filter. The notebook’s filter uses less-than-or-equal, which lets a listing at exactly $400,000 through; “less than” needs strictly-less-than. The full version is M17’s self-querying lesson.
  • Query generation: the model writes one line of pandas over the schema, and the notebook evaluates it.

Pitfall: evaluating model-written code. That last branch runs code the model wrote with full interpreter access, and a data field can carry a prompt injection. In production, generate SQL against a read-only connection with a timeout, or run a sandboxed executor.

In practice: Larkspur’s server catalogue

  1. Embed descriptions only; keep name, vCPUs, memory and price as typed metadata.
  2. Route averages and rankings to SQL over the catalogue, read-only.
  3. Route “ls-cpu-8” to a get by id, and price limits to a self-query filter with the right operator.
  4. Send semantic search only the descriptive questions, such as a server for a memory-hungry database.

Key Takeaways

  • Embed fields whose values carry meaning, and put identifiers, numbers and dates in metadata, cast to their real types. Embedding every column dilutes the vector (field dilution).
  • Retrieval reads a sample of k rows. Aggregation, numeric comparison, exact lookup and ranking need every row, a filter or an id, and retrieval fails on them quietly: the catalogue’s average comes back as $36.25 instead of $102.50.
  • Route by the kind of question: a query engine for aggregates, get-by-id for lookups, self-query filters for ranges, semantic search for the rest. Never evaluate model-written code without a sandbox.

Check yourself

1. Why does embedding every column of the catalogue make the memory-hungry database question harder to answer?

Field dilution: each row’s string now carries names and numbers, which pull every row towards every other. With descriptions only, ls-mem-4 and ls-mem-2 lead the third row by 0.115; with every column, ls-mem-2 beats the general-purpose ls-small by 0.0004.

2. A RAG chain answers the catalogue's average monthly price as $36.25. What happened, and what should answer it instead?

The sample average: retrieval returned four rows at k = 4 and the model averaged those. The true average over all ten rows is $102.50, and ls-gpu-1 at $480 ranks last for this question, so only the whole table gets it right. Route aggregation questions to a query engine over the full table.

3. A teammate wants to answer "Tell me about ls-cpu-8." by embedding every column so the name is in the text. What do you suggest?

A get by id. Embedding every column does make ls-cpu-8 win, but only by 0.050, which is a ranking, not a lookup; with descriptions only, the sibling ls-cpu-4 wins. A question that names one record by its id should fetch that record directly.

Local inference

Lessons 19.1 to 19.4 called a hosted embedding model and a hosted chat model. Some Larkspur customers sign contracts that say support tickets and the handbook may not leave their network. For them, every model call is a question of where the data goes.

What local costs

Keeping everything local trades the API bill for three costs:

  • Hardware and latency. A 7B model generating on your own CPU or GPU replaces a network call. Measure tokens per second on the target machine before promising a latency.
  • One embedding model on both sides. The query must be embedded by the model that embedded the chunks. Switching from OpenAI’s 1,536-dimension vectors to bge’s 768 means re-embedding the whole corpus, not only new documents.
  • Loading a saved index runs pickle. FAISS’s loader needs an explicit dangerous-deserialisation flag because the docstore is saved as a pickle file, and loading a pickle can run code. Load only index files your own pipeline wrote.

Pitfall: a borrowed index file. A FAISS index downloaded from a shared drive or a model hub is code as well as data. Rebuild it from source documents, or load only files your pipeline wrote and stored where only it can write.

Two reuse bugs

Two smaller things to change when you reuse 05a’s code:

Code in 05a What it does Fix
A parallel step that runs the RAG chain and the retriever side by side, to return answer and sources Double retrieval: retrieves twice, once inside the chain and once for the sources; a counting retriever in a scratch test was called two times Retrieve once and reuse the result, as lesson 19.2’s pass-through pattern does
The answer helper keeps only the text after the last “Answer:” Strips a prompt echoed back with the completion; the installed endpoint client already returns only new text, so the split guards against nothing and cuts any answer that itself contains “Answer:” Drop the split, or set “return only new text” explicitly when moving to a local pipeline

Table 3: Two reuse bugs in 05a.

On a fixed FAISS index the two retrievals return the same list, and the double retrieval only costs an extra search. On an index that updates between the calls, the sources shown could differ from the context the model read.

05a’s fallback evaluation counts expected keywords in each answer, such as “carbon dioxide” and “methane”. Substring matching rewards any answer that mentions the words, right or wrong. Treat it as a smoke test, and use the golden-set metrics from M10 for decisions.

In practice: an offline Larkspur deployment

  1. Audit every component with Table 2: embeddings, index, reranker (M18), generator, and any grader.
  2. Generate in-process on hardware sized from a measured tokens-per-second figure.
  3. Re-embed the whole handbook with the local embedding model, and evaluate it on the golden set before switching.
  4. Write and load the index yourself, never from a shared location.

  • Changing embedding models means re-embedding the whole corpus. Measure tokens per second on the target hardware before promising a latency.

Check yourself

1. 05a embeds and indexes on your machine. Does a Larkspur customer's data stay on their network?

No. The generator runs through the Hugging Face Inference API, so every prompt, with the three retrieved chunks inside it, leaves the machine. Only indexing is local. Swapping the endpoint client for a local pipeline that loads the weights makes generation local too.

2. Moving Larkspur's pipeline from OpenAI embeddings to bge-base-en-v1.5, can you embed only new documents with the new model?

No. The query must be embedded by the same model that embedded the chunks, and the two models produce vectors of different sizes (1,536 against 768) in different spaces. Re-embed the whole corpus, and re-run the golden set before switching.

3. Why does loading a saved FAISS index need a dangerous-deserialisation flag, and what rule follows?

The index’s docstore is saved as a pickle, and loading a pickle can run arbitrary code. Load only index files your own pipeline wrote and stored where only it can write; rebuild anything else from the source documents.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. A Larkspur customer forwards a support answer about annual-plan refunds. Its citation quotes “Annual plans are fully refundable for 30 days” and points to page 0 of the handbook. Neither the sentence nor a page 0 exists. What happened, and what do you change?

What a strong answer covers:

  • Two separate faults: the quote is a paraphrase the model wrote, and the page is the PDF loader’s 0-based number shown without adding 1
  • Logs the request: the retrieved chunk ids, the answer, the raw QuotedCitations, to confirm the cited id was among the retrieved chunks
  • Adds a code check before display: each quote, whitespace-normalised, must appear in the chunk with that id; failures are dropped or flagged, never shown as citations
  • Tracks the quote-failure rate per day and alerts on a jump, which signals a model, prompt or chunking change

2. The team wants to cut latency by asking for the answer and its citations in one structured call instead of two. What do you gain and lose?

What a strong answer covers:

  • Gains one round trip and the tokens of sending the context twice
  • In one call the model writes claims and their support together, which can tie each citation to a claim; in two calls citations are a post-hoc search for support
  • Either way the quote check in code stays, since neither design makes quotes verbatim
  • Decides on the golden set: citation precision, unsupported-claim rate and latency for both designs, not on intuition

3. After the citation feature ships, how do you know whether answers are better supported than before, and how do you keep watching it?

What a strong answer covers:

  • Offline: on the golden set, citation precision (cited chunk supports the claim), citation recall (claims with a citation) and the quote-match rate
  • Online: share of answers with at least one verified citation, share of “I don’t know” answers, and quote-failure rate
  • Samples traffic for an LLM or human judge of whether each claim is supported by its quote
  • Watches refusals on questions the handbook does answer, since a stricter prompt can trade hallucinations for missed answers

4. Product adds the server catalogue to the index, and the assistant tells a customer the average Larkspur server costs about $36 a month. The real average is $102.50. Why, and what is the fix?

What a strong answer covers:

  • Retrieval read the top 4 of 10 rows, the ones whose descriptions resemble the question most; they average $36.25, and the $480 GPU server ranks last
  • No k fixes it below the whole table; aggregation, comparisons, id lookups and rankings need every row or an exact filter
  • Routes by question type: aggregates to SQL on a read-only connection, id lookups to a get by id, price limits to a metadata filter, descriptive questions to the vector store
  • Adds these four question kinds to the golden set, with the right answer computed from the table, so a regression shows up as a wrong number

5. A bank evaluating Larkspur’s assistant requires that no customer data leaves its network. The team says the system is local because it uses bge-base-en-v1.5 and FAISS. Is it, and what changes?

What a strong answer covers:

  • Checks every component: embeddings and FAISS run locally, but HuggingFaceEndpoint sends each prompt, retrieved chunks included, to the Hugging Face Inference API
  • Moves generation in-process with HuggingFacePipeline (or another self-hosted server inside the network) and removes the API token
  • Sizes the hardware: memory for a 7B model, tokens per second on the target machine against the latency requirement
  • Keeps the same embedding model for queries and documents, and loads saved FAISS indexes only from files the pipeline wrote, since load_local unpickles them

Key Takeaways

  • Carry metadata from the store to the answer. A chunk without its id, source and page in the output cannot be cited.
  • Treat citations as model output to verify: check each quote against the chunk it names, show the page counting from 1, and count the failures.
  • Route a question by what it needs. If it needs every row, a filter or one known record, send it to a query, a filter or a get by id, not to top-k retrieval.
  • Call a pipeline local only after checking each component, the generator above all.
