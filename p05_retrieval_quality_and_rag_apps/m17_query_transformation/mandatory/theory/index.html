M17 Query transformation and routing

Users ask short, vague or compound questions, and the retriever searches with exactly what they typed. M17 changes the query before retrieval: rewrite it, ask it several ways, ask a broader question, search with an invented answer, split it, or send it to the right place first. The M17 notebooks build on four ideas: why a question and its answer sit far apart, how to fuse rankings from several phrasings, how a hypothetical answer becomes a search key, and the two ways to route a question.

Open the lab

The running example is the Larkspur Cloud handbook from M10: twelve chunks on billing, refunds, outages, servers and data exports, and the same three golden questions. M10 left one of them unsolved. What happens if my server goes down? shares no word with the two chunks that answer it, so no value of k could retrieve them. M17 starts there.

TL;DR

  • Questions and documents differ in vocabulary (“server goes down” against “outage” and “availability”) and in shape (a nine-word question against a 400-token passage). Every technique here closes one of those gaps, or splits a question that has more than one need.
  • Multi-query and RAG-Fusion search with several LLM-written phrasings. In the lab, five variants per question lift mean recall@3 over the three golden questions from 0.50 to 0.83 with a flat union and to 1.00 with RRF.
  • RRF’s constant k is a real setting. At two chunks sent, k = 60 scores 0.67 and k = 1 scores 0.83, because a large k lets chunks that several variants rank low outvote a chunk two variants rank high.
  • HyDE embeds an LLM-written answer instead of the question. It costs one LLM call per query and can mislead on a private corpus the model knows nothing about. Decomposition costs five LLM calls and three retrievals where plain RAG costs one and one.
  • An LLM classifier routes by reasoning and pays a generation call per query; semantic routing compares embeddings with example questions and cannot say “none of these”. Guard it with a minimum score and a minimum margin, and hand unclear cases to the classifier.

Mental model

Everything in M17 happens before the first vector search or after the last one. The index from M11 to M16 stays as it is. A transformation multiplies the queries, so the stage after retrieval has to merge their results, and the merge decides which chunks survive the cut to the model.

M16 improved the retriever: two kinds of search, fused, filtered and de-duplicated. Every one of those techniques still searches with exactly what the user typed. M17 changes what is searched for.

A retriever compares the question with each chunk and returns the closest. That works when the two look alike, and a question rarely looks like its answer. In the M10 index, What happens if my server goes down? scores 0.000 against both chunks that answer it. Its top three are reboot (0.416), sizing (0.389) and export (0.217), all matched on the word “server”. No value of k fixes that: the evidence is not low in the ranking, it is absent from it.

Query–document asymmetry is the name for this mismatch. It has two parts:

  • Vocabulary: the user’s words are not the handbook’s words. The answering chunks say “outage”, “availability” and “incident” and never “down”.
  • Shape: a question is short and interrogative; a chunk is long, declarative and dense with terms. Notebook 05a pairs a nine-word question, What is LangSmith, and why do we need it?, with a 400-token passage that answers it. Even with a good embedding model, the question’s vector sits closer to other questions than to the passage.

Key Takeaways

  • A question rarely looks like its answer: it differs in vocabulary (the user’s words against the handbook’s) and in shape (short and interrogative against long and declarative).
  • Expansion sends an LLM-enriched query to the retriever and the original question to the answer prompt. It costs one LLM call per retrieval, and too many added terms dilute the query.
  • Match the transformation to the gap, and keep plain retrieval as an exit. Running one technique on all traffic (transform everything) adds cost where nothing is missing.

Vocabulary spread

The mechanism is vocabulary spread: each phrasing reaches for different words, and each set of words lands near different chunks. 02a illustrates it with three ways of asking about LangSmith. Two silent bugs

Both bugs below shipped in earlier versions of the notebooks, and neither raised an error.

The id-only merge. The original get_unique_union() in 02a de-duplicated by document id and returned the ids, not the documents. Every LangChain document has an id attribute. That branch always ran, and the answer prompt’s context held a list of bare identifiers. The model answered from memory, fluently, and the output looked like a working RAG chain. The fix keys the merge by the chunk’s text and returns the documents themselves; 02a then asserts that the context contains real passage text.

Junk variants. Parsing the LLM’s reply by splitting it on newlines assumes exactly three bare lines. Models add headers, numbering, blank lines and preambles such as “Here are three variations:”, and each of those becomes a query sent to the retriever. The failure is intermittent: the same chain returns clean lines on one run and markdown on the next. 02a binds a schema with structured output, so the reply is a list of exactly the phrasings. The optional notebooks 02b and 02c show the older approach, a regular expression that cleans the split text, and use the same pattern to generate five hypothetical answers for HyDE (lesson 17.5).

The two parsing approaches handle the same untidy reply very differently. The reply below is illustrative, written in the shape the bug describes:

In practice: multi-query on the Larkspur handbook

  1. Use it where the baseline misses. The refund and outage questions gain; the export question gains nothing.
  2. Parse with a schema and log every phrasing. A drifting or junk variant then shows up in traces.
  3. Assert the context is text, not ids, in a test that runs on every change.
  4. Cut by rank, not arrival. At two chunks the union drops incidents. Lesson 17.3 keeps the same variants and fixes the order.

RRF

Lesson 17.3: RAG-Fusion with Reciprocal Rank Fusion. Notebooks: 03a_rag_fusion.ipynb

What you’ll learn

  • Explain what Reciprocal Rank Fusion keeps that a flat union throws away.
  • Trace the Larkspur outage question through five variants and a fused list.
  • Predict when the constant k changes the order, and compute both orders by hand.
  • Diagnose agreement on a distractor, the failure fusion cannot see.

Lesson 17.2 merged three phrasings with a flat union and found the evidence for the outage question, then ranked it 5th by order of arrival. The union keeps every chunk once and throws away two signals: where each list ranked the chunk, and how many lists found it.

RAG-Fusion keeps both. It asks for five phrasings, because agreement means little across two or three rankings, and fuses the lists with Reciprocal Rank Fusion (RRF). Notebook 03a scores each chunk by adding 1 / (rank + k) for every variant that retrieved it, with rank counted from 0 and k = 60:

Figure 1: RAG-Fusion. The fusion step needs only ranks, a dictionary and a sort.

With k = 60, first place in one list adds 1/60, about 0.0167, and fourth place adds 1/63, about 0.0159. Being found by more variants therefore matters more than placing first in any one of them. RRF uses ranks and never similarity scores, because scores from different queries are not on the same scale.

M16’s fusion page covers the same formula with the more common convention that counts ranks from 1. There the lists come from BM25 and dense retrieval; here they come from five phrasings of one question.

reboot still comes first. Key distinction: fusion only reorders what the variants retrieved. It cannot add a chunk no variant found, and it cannot tell a relevant agreement from an irrelevant one. A reranker (M18) can.

What k controls

A small k makes rank position dominate: at k = 1, first place is worth 1 and fourth place 0.25. A large k flattens the curve until only the number of votes counts. 03a runs k at 1, 5, 60 and 1000 and notes that the order changes only when rank and agreement disagree.

In the refund question they do. Two variants rank refund-window 1st and 2nd (ranks 1 and 0); three variants rank retention low (ranks 3, 3 and 2). By hand:

retention 3, 3, 2 1/63 + 1/63 + 1/62 = 0.0479 1/4 + 1/4 + 1/3 = 0.83

Details that bite

  • Merge documents, not ids. RAG-Fusion inherits lesson 17.2’s id-only merge bug if it reuses that merge: key by chunk text, return documents, and assert the context holds passage text.
  • Junk variants vote. In a union a junk line only adds noise. In RAG-Fusion each junk query produces a ranked list that votes, so a header such as “Here are five queries:” can lift whichever chunk it matches. Parse with a schema.
  • Cost. One LLM call for the five variants, five retrievals run in parallel, and a fusion step that is a dictionary and a sort. The answer call makes it 2 LLM calls and 5 retrievals.

In practice: fusing Larkspur’s variants

  1. Five variants, fused, cut at 3 for questions the router sends here: mean recall 1.00 on the golden set.
  2. Tune k with the cut. If the product sends only 2 chunks, k = 1 scores 0.83 and k = 60 scores 0.67 on this set.
  3. Watch the distractor. Log each fused list with its votes; reboot winning the outage question shows the variants drifting.
  4. Add a reranker (M18) over the fused pool when distractors keep winning.

Lesson 17.4 changes the question in a different direction: instead of rewording it, it asks a broader one.

Limits

  • Hand-written variants on a small index. Every number on this page comes from the lab: five hand-written variants per golden question over the twelve M10 chunks, scored with TF-IDF. Notebook 03a generates its variants with a model, and they change on every run.
  • Three questions decide the k comparison. The 0.67 against 0.83 gap at two chunks comes from one question, refund, changing order. It shows that k can matter; it does not show which k suits another corpus.
  • Ranks count from 0. 03a and the lab give first place rank 0, so each vote is worth slightly more than on M16’s page, which counts from 1. Compare scores only within one convention.

3. RAG-Fusion raised recall on the golden set, but the outage question's top chunk is reboot instructions. What is happening, and what helps?

Agreement on a distractor: four of five variants matched reboot on “server” or “does”, and one variant drifted toward restarting a server. RRF counts those votes like any others. Check the variants for drift, cut at a depth that keeps both evidence chunks, and add a reranker over the fused pool.

The specificity trap

Lesson 17.4: Step-back prompting. Notebooks: 04a_step_back_prompting.ipynb

What you’ll learn

  • Explain why a specific question, especially one with a false premise, retrieves the wrong context.
  • Trace step-back retrieval: a broader question, two searches, one combined context.
  • Explain why two worked examples teach “make it broader” better than an instruction.
  • Choose between step-back and plain retrieval by question type and cost.

Lessons 17.2 and 17.3 reworded the question to reach the handbook’s vocabulary. Rewording keeps the question’s scope. Some questions fail because the scope itself is wrong.

Notebook 04a opens with Did Leonardo da Vinci invent the printing press? A retriever searches for exactly that and mostly finds pages about Gutenberg, movable type and 1440. None of them says what Leonardo did invent, which is the knowledge that settles the question. The question carries a false premise, and searching on its words retrieves documents about the premise rather than the answer.

We call this the specificity trap: the narrower and more assumption-laden the question, the more its words steer retrieval toward the assumption.

Larkspur has the same shape of question. A customer on a monthly plan asks Can I get a refund on my monthly plan? The handbook offers refunds on annual plans only, and the answer the customer needs is “no, but cancelling stops the next charge”. That second fact sits in the cancel chunk, which shares almost no words with the question.

Teaching abstraction by example

“Make this question more general” is hard to specify in prose. Too loose, and the model rewrites the question into something unrelated; too strict, and it barely changes anything. 04a teaches the move with two worked examples instead:

Input Output
Did the Beatles ever write a book? What types of creative works did the Beatles produce?
Was Albert Einstein a musician? What fields did Albert Einstein work in?

Table 2: The two few-shot examples in 04a.

Both show the same pattern: a yes-or-no question about one specific thing becomes an open question about the category it belongs to. The few-shot template expands into real message pairs (a user turn, then the model’s reply) before the real question, so the model imitates the pattern rather than interpreting an instruction.

The pattern can overshoot. We call that over-generalising: a step-back question so broad that it retrieves a vague overview instead of the background that matters. What does Larkspur offer? would be a step back from the refund question too, and it would retrieve almost anything.

In practice: step-back on Larkspur’s policy questions

  1. Route yes-or-no policy questions here, especially ones that name a plan, a period or an amount the policy might not cover.
  2. Write Larkspur few-shots: Can I pause my server for a month? becomes What can I change about a running server?

HyDE

Lesson 17.5: HyDE: embed a hypothetical answer. Notebooks: 05a_hyde.ipynb, 05b_hyde_walkthrough.ipynb (optional), 05c_hyde_rag_techniques.ipynb (optional)

What you’ll learn

  • Explain why an invented answer can retrieve better than the question it answers.
  • Trace a hypothetical answer through the index, and see a misleading one fail.
  • Explain which embedding calls run the LLM and which pass straight through.
  • Decide whether HyDE suits a private corpus, with a test rather than an assumption.

Lessons 17.2 to 17.4 changed the question’s words or its scope. The result was still a question: short, interrogative, unlike the passage that answers it. Lesson 17.1 called that the shape half of the query–document asymmetry.

HyDE (Hypothetical Document Embeddings, Gao et al., arXiv:2212.10496) attacks the shape. Instead of embedding the question, it asks an LLM to write an answer, embeds that answer, and searches with its vector. An invented answer is declarative, long and full of the vocabulary documentation uses, so it lands nearer the real passage than the question does:

Figure 1: HyDE. The invented answer is a search key; only real chunks come back.

The hypothetical answer may state wrong facts, and that does not matter. It is discarded after embedding, never reaches the user and never enters the context.

Two models, one index

HyDE always needs two models: an LLM to write and an embedding model to embed. The embedding model must be the one that built the index, or the vectors are not comparable. The index itself is built plainly. Documents are already answer-shaped, and indexing through an LLM would cost a generation per chunk.

LangChain packages the steps as a hypothetical document embedder, which behaves differently for the two methods every embedding model has:

Method Called when What it does
Embed documents Building the index Passes straight through to the base embedder; no LLM call
Embed query Every search Runs the LLM, then embeds the generated text

Table 2: The two embedding paths of the HyDE embedder.

Notebook 05a checks the first row: a document embedded through the HyDE wrapper matches its plain embedding. That pass-through makes the wrapper a drop-in. Hand it to a vector store as its embedding model, and indexing stays plain while every similarity search applies HyDE.

The wrapper ships with built-in prompt templates inherited from the datasets the paper used; the general one asks the model to “write a passage to answer the question”. 05a writes its own prompt instead, asking for an excerpt from technical documentation, so the hypothetical answer matches the genre of the indexed chunks.

Several hypothetical answers

The paper generates several hypothetical answers and averages their embeddings. No single invention then dominates the search vector. A jargon guess averaged with two good ones pulls the vector less.

Figure 2: HyDE with several hypothetical answers. One search, with a key no single guess controls.

LangChain’s current wrapper cannot do this: its chain returns one string, and its averaging step always averages exactly one vector. 05a generates three answers itself at temperature 0.8, embeds them and averages them, then checks how similar the three are to each other. A cosine similarity near 1.0 means the answers are near-identical, and the average bought nothing for three times the generation cost. The optional notebook 05b builds HyDE by hand, then with LangChain’s wrapper and a custom prompt; 05c asks for one hypothetical document sized to the index’s chunk length, so the search key and the chunks have the same shape.

Check yourself

1. The hypothetical answer HyDE writes may state wrong facts. Why does that not mislead the user?

It is only a search key. It is embedded, then discarded: it never reaches the user and never enters the context. The chunks that come back from the index are real, and the answer is built from them.

2. Two hypothetical answers to the outage question give recall at 2 of 1.00 and 0.00. What separates them?

Vocabulary. The good guess uses the handbook’s words (availability, outage, service credits, incident) and retrieves sla and incidents. The jargon guess describes failover and live migration, words the handbook never uses, and its “data loss” pulls the search to the export chunk.

3. You pass the HyDE embedder to a vector store to build the Larkspur index. Does indexing call the LLM, and what must the base embedder be?

No. Embedding documents passes straight through to the base embedder, so indexing stays plain; only query embedding runs the LLM. The base embedder must be the model that built the index, or the query and chunk vectors are not comparable.

Logical vs semantic routing

What you’ll learn

  • Compare an LLM classifier and an embedding-similarity router on cost, reach and failure.
  • Diagnose a classifier that silently returns no route, and one that always returns a route.
  • Read route scores and margins, and set the thresholds that send unclear questions onward.
  • Design Larkspur’s routes and test them on real scores.

Lessons 17.1 to 17.6 each fit one kind of question: decomposition for compound ones, HyDE for vague ones, step-back for premises, plain retrieval for direct lookups. Applying all of them to every question is the transform-everything habit from lesson 17.1. Something has to choose per question.

A router decides where a question goes before anything answers it: which prompt, which data source, which transformation. Notebooks 07a and 07b build the same four-way router twice, over personal finance, book reviews, health and fitness, and travel:

  • Logical routing: an LLM reads the question and chooses.
  • Semantic routing: the question is embedded and sent to the destination whose example questions it is closest to.

The LLM classifier

The first version of 07a asked for the category as free text and compared it with exact strings. The model answered “health & fitness” and “travel guides”, which match neither “Health & Fitness” nor “Travel Guide”: every branch fell through and the router returned nothing. The notebook still appeared to work. We call this the silent fall-through.

The fix binds a schema with structured output whose destination field is a fixed set of the four route names, so no other value can come back, plus a one-sentence reasoning field that makes each decision readable in traces:

Figure 1: The LLM classifier after the fix. Every question costs one LLM call, and only a listed name can come back.

A fixed set guarantees a valid route, not a sensible one. Asked What is the capital of France?, the classifier still picks one of the four. We call this the forced route. A production router needs:

  • An “other” destination: out-of-scope questions then have somewhere honest to go.
  • A regression set of questions with expected routes, because adding a route changes decisions on old questions.
  • A small model. Routing is classification; it rarely needs the model that writes answers.

Semantic routing

Each route is defined by a few example questions, three per route in 07b, embedded once at start-up. Per query the router embeds the question, takes each route’s highest similarity to its examples, and picks the highest route. The routing path never calls an LLM.

07b shows why the winner alone is not enough. With text-embedding-3-small, How can I travel on a budget? is one of the travel examples word for word and scores 1.0000, while personal finance still scores about 0.50 on “budget”. Are meal-prep books worth buying? wins by a margin of about 0.002, with every route near 0.28, and book reviews is not even in the top two despite the word “books”. The router returns both answers with the same confidence.

Two thresholds turn scores into a confidence check: a minimum top score (did anything match?) and a minimum margin over the runner-up (was the choice distinguishable?). 07b uses 0.35 and 0.02 and calls them illustrative. Questions that fail either go to the LLM classifier, which makes the two routers one system:

In practice: routing Larkspur’s questions

  1. Semantic router first, with Table 2’s routes and more examples per route drawn from real tickets.
  2. Tune the floor and the margin on logged questions with known routes; Table 3 suggests a lower floor and a higher margin for this model.
  3. Classifier fallback with an “other” route for anything that fails either check.
  4. Send cross-topic questions to both routes when the two top scores sit close, rather than forcing one.

  • Logical routing asks an LLM to choose; semantic routing picks the route whose examples are closest by embedding, about 100 times cheaper per query in 07a’s comparison.

Check yourself

1. Why does the fixed LLM classifier return its route through a fixed set of names, and what does that still not guarantee?

Free text broke the first version: “health & fitness” matched none of the exact strings, every branch fell through and the router returned nothing while appearing to work. A fixed set guarantees a valid route name, not a sensible one; asked the capital of France, it still picks one of the four, so it needs an “other” route.

2. "Will restarting my machine lose my files?" scores servers 0.473 and reliability 0.466. With thresholds of 0.35 and 0.02, where does it go, and why?

To the LLM classifier. Its top score passes the 0.35 floor, but its margin over the runner-up is 0.008, below 0.02, so the choice is not distinguishable. Without the margin check the semantic router would have returned servers with the same confidence as an exact match.

3. "Can I download my databases?" is clearly a data question, yet the router sends it to the classifier. What does that tell you about the thresholds?

Its top score, 0.325 for data, falls under the 0.35 floor borrowed from a different embedding model, even though its margin of 0.134 is large. The floor is too high for all-MiniLM-L6-v2 on these routes. Set the floor and the margin from logged questions scored by your own model.

Splitting the question

A self-querying retriever puts an LLM in front of the retriever. The LLM splits the question into two parts, and each goes to the tool that can evaluate it:

08a exercises each comparison the filter language offers: equality on a category, a numeric greater-than, a range built from two comparisons joined by AND, and set membership built with OR.

The schema is a prompt

The LLM cannot guess which fields exist. A list of attribute descriptions, one per field with a name, a type and a sentence, is written into the query-construction prompt. Two details carry weight:

  • The type permits comparisons. Declared as a float, rating allows greater-than; declared as a string, the model can only test equality.
  • The description is a prompt, not documentation. “The rating of the book (1-5 scale)” tells the model what values are plausible.

A field that is not described cannot be filtered on. A field that was never written at ingestion cannot be filtered on either, which is lesson 16.5’s point again: facets come from ingestion.

08a also lets the question set the result count. With the limit option on, “two books” becomes a limit of 2; without it, the phrase is silently ignored and the default k applies.

In practice: self-querying the Larkspur handbook

  1. Write facets at ingestion: plan name, memory, vCPUs and traffic on the plan sheets; section, version and date on policy chunks.
  2. Describe each field with a type and one sentence, numbers as numbers.
  3. Coerce and log every structured query, and alert on calls where a question with a number produced no filter.
  4. Route here only questions with a condition on a fact (Figure 3 in lesson 17.1); everything else keeps plain or transformed retrieval.

Check yourself

1. Why does similarity search put the 4 GB plan in the top 3 when a customer asks which plans have more than 8 GB of memory?

A vector encodes meaning and cannot perform a comparison. The three plan sheets read alike, so they score 0.599, 0.595 and 0.574, and the 4 GB plan ranks third whatever its memory. A metadata filter on memory greater than 8 is the tool that can evaluate the condition.

2. In the self-querying retriever, what happens to "a rating above 4.5" in "books with deep themes and a rating above 4.5"?

The LLM removes it from the semantic query, which becomes “deep themes”, and re-expresses it as a filter: rating greater than 4.5. The embeddings search on meaning, and the metadata index applies the comparison. The comparison works only because rating is declared as a number.

3. A self-querying retriever sometimes returns 4.3-rated books for "rated above 4.5", with no error in the logs. What is happening?

The dropped filter: on some runs the LLM produced no filter at all, and the retriever fell back to plain similarity search. In 08a this happened once in four runs. Log the structured query beside every result, and alert when a question with a number yields no filter.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. You ship RAG-Fusion for Larkspur’s support assistant. A customer asks “What happens if my server goes down?” and gets reboot instructions instead of the SLA credit policy. Recall on the golden set went up. What happened?

What a strong answer covers:

  • Prints the fused list with each chunk’s votes and ranks: the reboot chunk can win because four of five variants matched “server” or “does”, which is agreement on a distractor
  • Checks the variants themselves; a variant that drifts (“How do I restart a server…”) adds a vote for the wrong chunk
  • Looks at the cut: at three chunks both evidence chunks are in, at two only sla is, so the number of chunks sent matters as much as the fusion
  • Fixes with a reranker over the fused pool (M18), a lower k or fewer drifting variants, and adds the question to the golden set at the production cut

2. Your latency budget is 1.5 s and a plain retrieval takes 300 ms. Product wants multi-query, HyDE and decomposition “on every question”. What do you propose?

What a strong answer covers:

  • Counts the calls: multi-query adds one LLM call and N retrievals, HyDE one LLM call, decomposition five LLM calls and three retrievals where plain RAG has one and one
  • Routes first: send compound questions to decomposition, short or vague ones to variants or HyDE, and direct lookups straight to retrieval
  • Runs the per-variant retrievals and sub-questions in parallel (retriever.map(), .batch()), and uses a small model for rewriting
  • Measures each technique per question type against the M10 baseline and keeps only the ones that win where they are applied

3. How do you show that RAG-Fusion helped, rather than only cost more?

What a strong answer covers:

  • Compares against the plain pipeline on the same frozen golden set, at the cut the product really uses
  • Reports recall at that cut, answer quality, latency and LLM cost per question, and breaks results down by question type
  • Watches regressions on direct lookups: in the lab, RRF at k = 60 and two chunks drops the refund question from 1.00 (union) to 0.50
  • Logs the variants and fused lists in production so a bad variant or a distractor that keeps winning shows up in traces

4. Larkspur routes questions semantically to billing, data, reliability and servers. “Do I get a refund if an outage lasts a day?” goes to servers. How do you make the router safer?

What a strong answer covers:

  • Reads all route scores and the margin, not only the winner; a question that straddles billing and reliability will have close scores
  • Adds a minimum top score and a minimum margin, tuned on logged traffic, and sends anything below either to an LLM classifier or a default prompt
  • Gives the classifier an explicit “other” destination, because a Literal guarantees a valid route, not a sensible one
  • Adds exemplars for the cross-topic phrasings that fail, and keeps a regression set of query to expected route

5. A self-querying retriever turns “annual-plan refund rules updated after 2025” into a metadata filter. Some days it returns nothing, and the logs show no error. What do you check?

What a strong answer covers:

  • Logs the structured query each call produced, because the query constructor is an LLM and its output varies between runs
  • Looks for a filter value of the wrong type (“2025” as a string), which a store such as Chroma rejects for $gt, and coerces numeric values before they reach the store
  • Checks the metadata itself: an attribute that is not declared cannot be filtered, and “annual” against “Annual” breaks equality
  • Treats an empty result after a filter as a signal to retry without the filter or to ask the user, not as “nothing matched”

Key Takeaways

  • Print what the retriever saw before you change the prompt: the original query, every variant and every list. Fluent answers can come from an empty context, as the 02a notebook’s merge bug showed.
  • Match the transformation to the gap. Vocabulary gaps want variants or expansion, shape gaps want HyDE, compound questions want decomposition, facts the embedding cannot compare want a metadata filter.
  • RRF rewards agreement, and agreement on a distractor still counts. Tune k and the cut on your golden set instead of taking 60 on trust.
  • Route cheaply by similarity, check the margin, and pay for an LLM classifier only when the margin is small.
