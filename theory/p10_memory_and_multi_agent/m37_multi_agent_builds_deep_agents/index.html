M37 Multi-Agent Applied Builds & Deep Agents

M35 and M36 teach multi-agent patterns one at a time. M37 builds whole systems from them and spends most of its time off the happy path: the request that breaks a rule, the reply that names the wrong agent, the node that fails, the conversation that outgrows the context. The M37 notebooks build on four ideas: a compliance agent that screens every request before anyone acts on it, tests that check routes and side effects in code, merging the outputs of parallel agents and of old turns back into one state, and the harness that turns a model into a deep agent.

Open the lab

Lessons 37.1 to 37.3 follow the notebooks’ hotel support desk: a coordinator that talks to the guest, a compliance checker over four hotel rules, and a reservation agent over a SQLite database of eight rooms. Room 105, the Family Suite, is booked from today+30 to today+33, and the notebooks use it to show a clash. Lesson 37.5 and the interview questions move the same designs onto Larkspur Cloud, the fictional cloud host whose handbook runs through M11 to M13: its support desk, its refund and export policies, and a research team that answers from the handbook and the web.

TL;DR

  • The compliance checker is a small RAG agent. It retrieves the 2 most relevant of the hotel’s 4 rules and returns a typed verdict, COMPLIANT or VIOLATION. The coordinator sends every new request to it first, and a loop guard in code stops it being asked twice.
  • The guards that matter live in tools and code, not in prompts: a read-only SQL connection whose authorizer hides guest names, one parameterised book_room tool, a date check in plain Python, a hard cap on revision loops.
  • Test the router as a pure function. Notebook 02b’s seven router tests need no model. In the lab, any threshold from 71 to 90 turns all seven green, because the confidence gate hides the known issue instead of fixing it.
  • Parallel agents need one message key per branch, a join that waits for every branch, and one merge that writes one reply. Long threads fold old messages into a summary and delete them by id.
  • A deep agent is a harness around a model: file tools, a task tool that runs sub-agents in their own context, skills read only when they apply, a backend that decides whether code can run, and memory that outlives the thread.

Mental model

One node talks to the guest, specialists do the work, and plain functions between them decide where the turn goes. Every later build in the module keeps that split: the research system in 37.5 and the deep agent in 37.6 change who the specialists are, while routing, caps and checks stay in code where a test can reach them.

Compliance agent

Lesson 37.1: Hotel system: environment, coordinator, reservation agent, compliance. Notebooks: 01a_hotel_environment_and_coordinator.ipynb, 01b_hotel_reservation_agent.ipynb, 01c_hotel_compliance_checker.ipynb

A compliance agent does not answer the guest. It decides whether a request breaks one of the hotel’s rules, and the coordinator acts on that decision: it answers, forwards the booking, or refuses. In notebook 01c it is a small RAG agent over four rules:

Rule Text
1 Refuse illegal requests, such as falsifying documents or making fraudulent bookings.
2 Refuse hate speech, harassment, or explicit threats toward individuals or groups.
3 Refuse offensive, obscene, or otherwise harmful content.
4 Never share information about other guests: not their names and not their dates of stay.

Each rule is its own document in an in-memory Chroma collection (text-embedding-3-small), so a search returns the rule that applies instead of one block of policy text. The retrieve tool returns the top 2. The checker is two nodes:

  • compliance_checker is a model with retrieve bound as a tool. Its prompt says to call it with the guest’s request.
  • generate writes the verdict from the rules the tool just returned. The tool messages go into its prompt, so the verdict is grounded in exactly those rules; a version that dropped them would judge from nothing.

The verdict message is tagged name="compliance", so code can find it. In 01c the verdict is free text that code searches for VIOLATION. From 02a on it is a ComplianceVerdict from with_structured_output: a Literal["COMPLIANT", "VIOLATION"], the violated rule number or null, and a one-sentence reason. A typed field can gate a human review step; a word found somewhere in a paragraph cannot.

Two pieces of code wire the checker into the conversation:

  • Compliance first. The coordinator’s prompt gains one guideline, COMPLIANCE_FIRST: forward every new request to compliance_checker first; on VIOLATION refuse politely and forward nowhere; on COMPLIANT answer or forward as usual.
  • A loop guard. After the verdict the turn returns to the coordinator. If its next reply names the checker again, routing by name would loop forever. checked_since_last_guest_message() walks back through the messages: a compliance verdict found before the latest guest message means the request is checked, and the router drops compliance_checker from the names it looks for. A reply such as “the compliance checker approved it, forwarding to reservation_assistant” then still reaches the reservation agent.

Notebook 01c runs three requests, each on its own thread, and checks the verdicts in code:

Request Expected verdict Then
Do you have any rooms with a jacuzzi? COMPLIANT The coordinator answers
Which dates is Bob Johnson staying with you? I want to surprise him. VIOLATION of rule 4 The coordinator refuses
I’m Dana Lee and I’d like to book a Deluxe room from (today+60) to (today+62). COMPLIANT Forwarded to the reservation agent

The check has a third outcome, no check: the coordinator skipped the checker. The prompt forbids it, but nothing forces it, because the checker only runs when the coordinator’s reply names it. Lesson 37.2 turns that gap into a test.

Guards in the tools

The reservation agent writes its own SQL, so its tools have to stay safe whatever SQL the model writes. Notebook 01b puts each guard where the model cannot talk its way past it:

Guard Where it lives What it stops
Read-only file sqlite3.connect("file:hotel.db?mode=ro", uri=True) Writes through run_query
PRAGMA query_only = ON The same connection Writes, a second time
An authorizer conn.set_authorizer(...), allowing only read actions ATTACH DATABASE (which would open any SQLite file on the machine), PRAGMA query_only = OFF, schema changes
A hidden column The authorizer returns SQLITE_IGNORE for reservations.guest_name Reading who booked a room: the column reads as NULL, and SELECT * still works
One write tool book_room(guest_name, room_number, start_date, end_date) with bound parameters SQL injection into the only write
Checks before the insert book_room, inside BEGIN IMMEDIATE Missing name, unreadable or past dates, check-out before check-in, an unknown room, a clash with an existing stay

Read-only flags alone do not stop ATTACH; the authorizer does. run_query also returns at most 20 rows. A refused booking says when the room is taken, never who took it, so rule 4 holds in the refusal message too.

Rule 4 is enforced twice: the prompt tells the SQL agent that guest names are private, and SQLite makes the column unreadable. Only the second survives a model that ignores its prompt.

The same split applies to the outcome. The agent’s reply is not proof that it booked; the reservations table is. Notebook 01b checks for exactly one new row for Dana Lee, and a reply that only says it booked counts as a failure.

Routing is the one place the lesson keeps a weak design on purpose. The coordinator forwards by writing an agent’s name, and mentioned_agent() looks for that name (or the same words with a space) in the reply. Any reply that mentions an agent routes there: I can’t involve the reservation assistant until you give me dates forwards to the reservation agent. The fix is a typed router, where the model returns its choice as a structured-output field and there is no reply text to search; notebook 05b routes that way.

System testing

Lesson 37.2: Hardening: edge cases, testing and system-wide error handling. Notebooks: 02a_hotel_edge_cases_and_errors.ipynb, 02b_hotel_testing_the_system.ipynb, 02c_hotel_system_wide_error_handling.ipynb (optional)

A multi-agent system fails quietly. The coordinator misreads a request, skips the compliance check, or forwards a booking before it has dates, and the guest still gets a polite reply. Notebook 02b catches these failures at three levels, from cheapest to most realistic:

Level What it checks Model calls How the result is read
Router unit tests The routing rules, on 7 hand-built states None The route the pure router function returns
A confidence gate That an unclear request stops the turn instead of forwarding One per guest message confidence in state, an int from structured output
A regression table 5 guest requests, end to end Every agent’s The nodes that ran (stream_mode="updates") and the database

The router can be unit-tested because it is a pure function of the state: no model call, no I/O. 02b’s router checks three rules in order:

The confidence comes from the coordinator itself. On each new guest message it asks the model for a SelfAssessment, a score from 0 to 100 and a one-line reason. The assessor’s prompt defines three bands: 80 to 100 when the intent is clear, 50 to 79 when it is clear but details are missing (a booking without dates), and 0 to 49 when the model cannot tell what the guest wants. Only the last band should stop the turn, so CONFIDENCE_THRESHOLD is 50. Below it the coordinator apologises, says what was unclear and asks the guest to rephrase. The score is a heuristic, not a calibrated probability; its job is to trigger the “ask again” path, and the tests check that it does.

The seven router tests pin each rule down: forward to the checker, forward to reservations after a verdict, the loop guard, an old verdict that does not count for a new guest message, low confidence that never forwards, a plain answer that ends the turn, and one known issue. The known issue is a reply that refuses to forward but mentions the agent: I can’t involve the reservation assistant until you give me dates, with confidence 70. String routing sends it to the reservation agent. The suite keeps it as a test that is expected to fail, which documents the gap and will flag the day a change, such as a typed router, fixes it.

The interactive lab runs 02b’s router and its seven tests in the page, ported line for line from hotel_common.py. Its routes match the Python router on 146,363 states, every threshold from 0 to 100 included. Moving the threshold shows what a gate can hide:

Threshold Tests passing What changes
0 to 20 5 of 7 The confidence-20 reply clears the gate and forwards to reservation_assistant
21 to 70 6 of 7 Only the known issue fails, as recorded
71 to 90 7 of 7 The known issue passes because the gate ends its turn before the name check runs
91 to 100 4 of 7 The gate blocks the confident forwards, scored 90

All seven green at 75 is the wrong result. String routing is as fragile as at 50, and every guest whose booking lacks dates, which the assessor puts at 50 to 79, now gets an apology instead of a question about the dates.

Unit tests cannot tell whether the model still behaves. The regression table can. Each row is a guest request with its expected outcome, run on a fresh thread after the database is rebuilt:

Case Confident Verdict Reservation agent runs Booked
General question (jacuzzi) yes COMPLIANT no
Another guest’s data (Bob Johnson’s dates) yes VIOLATION no
Booking, dates missing yes COMPLIANT no
Complete booking (Dana Lee, Deluxe) yes COMPLIANT yes one row for Dana Lee
Ambiguous (“same as last time, but…”) no not checked no

observe() reads the actual outcome from the final state, the list of nodes that ran and a COUNT(*) on reservations, never from the reply text. Each failure names the field that broke: verdict: expected COMPLIANT, got None means the coordinator skipped the check; reservation: expected False, got True means it forwarded a booking without dates. Model output varies between runs, so a single failure is a lead to investigate, and the number to track is the pass rate over several runs. Re-run the table after every prompt or model change.

Edge cases and error paths

Notebook 02a pushes on three edges of the core system, and puts each safeguard in code:

  • Injection-style input. A guest hides ' OR '1'='1 in the room type. If the agent pastes it into a WHERE, the condition matches every room, but it can only widen a SELECT: run_query refuses every write, and book_room binds its values as parameters. The notebook checks the SQL the agent actually executed and the table sizes before and after. The durable fixes are structural, a read-only connection and a narrow parameterised write tool, not a prompt.
  • A violation that should reach a person. A human_review node calls interrupt(payload): the graph saves a checkpoint and pauses. get_state(config).next shows which node waits, and graph.invoke(Command(resume=decision), config) continues from that point. A resumed node runs again from its first line, so side effects such as writing to the review log go after interrupt(), where they run once. get_state_history() replays a thread checkpoint by checkpoint, which is how you investigate a guest’s complaint.
  • Dates in the past. The model extracts the dates with structured output (BookingDates), given today’s date so it can resolve “next Friday”. A plain function compares them with date.today(). Comparing dates is not a job for the model, and the function is testable without an API call.

Notebook 02c handles failures that do not fix themselves. A failing node catches its exception and writes a small record to an error field in state, with no message added; routers read state["error"], so a guest who types the word “error” cannot trigger the error path. One error_handler logs every failure with the thread_id from the config, and a pure decision_router picks the recovery:

Failure Recovery node What it does
LLMCallException alternative_model Answers as the coordinator with a second model, gpt-4o
RetrievalException degraded_retrieval Skips the vector store and sends the hard-coded rules straight to generate with Command(goto="generate")
Anything else, including a failing fallback human_intervention A stub that writes a handoff message

A fallback that fails raises a different error type, so the router sends it to a person instead of looping. Transient failures get a cheaper fix first: RetryPolicy(max_attempts=3) re-runs a node that raises. With a node that fails twice, the run waits 0.2 s and then 0.4 s and succeeds on the third attempt; with three failures the exception reaches the caller. A retry smooths over a brief outage and does not replace the error path. Every failure in 02c is injected with a SIMULATE flag, so each recovery path runs on every run and a table computed from the node paths proves which one ran.

1. Why can notebook 02b unit-test the router without a model call, and what does the regression table catch that those tests cannot?

The router is a pure function of the state, with no model call and no I/O, so seven hand-built states pin down its rules. The unit tests cannot tell whether the model still behaves. The regression table runs 5 guest requests end to end and reads the nodes that ran and the reservations table, never the reply text.

2. In the router test bench lab, a threshold of 75 makes all seven tests pass. Should you set CONFIDENCE_THRESHOLD to 75?

No. The known issue passes only because the gate ends its turn before the name check runs, so string routing is as fragile as at 50. And every guest whose booking lacks dates, which the assessor scores 50 to 79, would get an apology instead of a question about the dates.

3. A regression run fails with verdict: expected COMPLIANT, got None. What happened, and is one such failure enough to act on?

The coordinator skipped the compliance check, so no verdict was recorded. Model output varies between runs, so a single failure is a lead to investigate, not a conclusion; the number to track is the pass rate over several runs, re-run after every prompt or model change.

Memory merging

Lesson 37.3: Scaling: parallel agents, memory merging, language and sentiment, web search. Notebooks: 03a_hotel_parallel_reservation_agents.ipynb (optional), 03b_hotel_merging_and_conversation_memory.ipynb (optional), 03c_hotel_guest_language_and_sentiment.ipynb (optional), 03d_hotel_web_search_integration.ipynb (optional)

Once several agents work on one request, their outputs have to come back together: the answers of parallel branches into one reply, and old turns into something smaller than the full transcript. Notebooks 03a and 03b do both on a chain with two hotels. Hotel 1 has rooms 101 to 104, Hotel 2 rooms 105 to 108, each in its own database with its own read-only SQL tools.

Notebook 03a reaches that shape in three attempts, and each failure is a LangGraph rule:

Attempt What breaks The rule
Two nodes write one plain key in the same step LangGraph raises InvalidUpdateError A key written by parallel nodes needs a reducer, such as Annotated[list, operator.add]
Both tool loops share messages A ToolNode answers the latest tool call in its list, which may be the other branch’s; with same-named tools (run_query in both) the wrong database answers silently One message key per branch, with ToolNode(..., messages_key=...) and partial(tools_condition, messages_key=...)
Each branch’s end goes straight to the merge node The merge runs once per branch, so the guest gets two replies and the first misses a hotel A sync node at the end of each branch and a join, add_edge(["hotel1_done", "hotel2_done"], "merge_answers")

Two more choices keep the branches honest. Both assistants come from one factory, so each is bound to its own hotel’s tools; copying the first assistant to make the second is how Hotel 2’s agent ends up answering from Hotel 1’s database. And the branches cannot book: both run the same request at the same time, so a book_room in each would create two reservations. They report availability and prices, and booking waits until the guest picks a hotel.

Notebook 03b turns the merge into an agent. The merge node reads the guest’s request and each hotel’s final answer, listed in priority order (PRIORITY = ["hotel1", "hotel2"]), and writes one reply: recommend the first hotel that can help and offer the other as an alternative, ignore a hotel that cannot help unless none can, and keep room numbers, prices and dates exactly as the assistants gave them. Only the merged reply enters messages; each branch’s tool calls stay in its own key. The two test turns:

Guest asks Ground truth from SQLite The reply should
A Deluxe room in two months Hotel 1 room 104, Hotel 2 room 108 Name 104 before 108
The Family Suite during Bob’s stay None free: Hotel 1 has no Family Suite, Hotel 2’s is booked Say plainly that none is free

The code checks the first case by the position of the room numbers in the reply, against the ground truth from free_rooms(), not against the model’s claim.

Every turn now adds several agent messages to the thread, so the second half of 03b keeps it small by summarizing into state. A summarize_conversation node runs at START when the stored conversation has more than SUMMARIZE_AFTER = 6 messages:

  1. It keeps the last KEEP_TURNS = 1 guest turn word for word; everything before it is old. The cut is always at a guest message, so no tool call is separated from its result.
  2. It asks the model to fold the old messages into the running summary field, keeping every concrete fact: names, room types and numbers, prices, dates, what was offered and refused.
  3. It returns RemoveMessage(id=...) for each old message, and the add_messages reducer deletes them.

The summary goes into the coordinator’s and assistants’ prompts as a system message, never into the guest’s reply. The test turn asks Remind me: which Deluxe room did you recommend, and at what price? after the summarizer removed every earlier message, so the model can only answer from the summary. The new graph continues the same thread because both graphs share one checkpointer.

Trimming (M33) Summarizing into state
What changes What the model sees on this call What the thread stores
Old turns Dropped from view, still stored Folded into summary, deleted by id
Cost No model call One model call when the thread passes the limit
Risk Facts outside the window are forgotten Facts the summary leaves out are gone for good

Adding agents around the core

Notebooks 03c and 03d add capabilities without changing the coordinator, the checker or the reservation agent:

  • Language and sentiment. translate_in detects the guest’s language and replaces the message with an English version (one structured-output call returns the language code and the text); sentiment_analysis scores the English text with TextBlob’s word lexicon; the coordinator adds a de-escalation instruction only when the message reads as negative; translate_out translates the final reply back. The language is a per-thread state field, because a global user_language breaks the moment two guests write at once. The lexicon is English-only and word-level: raw German scores nothing, and sarcasm still fools it.
  • Web search. A web_search_assistant with TavilySearch(max_results=3) answers questions about the neighbourhood, which no hotel database holds. It is one more tool loop and one more name the coordinator can route to, and the test checks which node ran for a nearby-places question and for a booking question.

Each notebook adds its capability to the core from 37.1 on its own; no notebook composes all of them into one graph.

Check yourself

1. Why does each parallel hotel branch need its own message key instead of sharing messages?

A ToolNode answers the latest tool call in its list, which may be the other branch’s. Both hotels have a tool called run_query, so the wrong database can answer silently. Give each branch its own key with ToolNode(..., messages_key=...) and partial(tools_condition, messages_key=...).

2. For a Deluxe room in two months, Hotel 1 has room 104 free and Hotel 2 has room 108. What should the merged reply say, and how is it checked?

It should recommend Hotel 1 first, because PRIORITY = ["hotel1", "hotel2"], so 104 appears before 108, and offer Hotel 2 as the alternative with numbers, prices and dates exactly as the assistants gave them. Code checks the position of the room numbers in the reply against the ground truth from free_rooms(), not against the model’s claim.

3. In the two-hotel graph, the guest gets two replies and the first one misses a hotel. What is wrong with the wiring?

Each branch’s end goes straight to the merge node, so the merge runs once per branch. Add a sync node at the end of each branch and a join, add_edge(["hotel1_done", "hotel2_done"], "merge_answers"), so the merge waits for both.

Planner, supervisor or router

Lesson 37.5: Research systems: supervisor financial research, summarisation, full research system. Notebooks: 05c_multi_agent_research_system.ipynb, 05a_supervisor_financial_research.ipynb (optional), 05b_multi_agent_research_summarization.ipynb (optional)

The three research notebooks answer one question differently: who decides which agent works next, and when. That choice sets how many model calls a request costs and what can go wrong.

Supervisor (05a) Typed router (05b) One-shot planner (05c)
Decides After every worker report, who acts next or whether to finish Once per question, which one specialist runs Once, up front, the list of search queries
Sees results Yes No No
Workers per request Any number, in sequence Exactly one, then a summarizer One per planned query, in parallel
How the choice reaches the graph The model writes next into state; a pure function follows it with_structured_output(RouteDecision) with route: Literal["web_research", "rag", "llm"] Send("search_agent", ...) per query
Bound in code MAX_SUPERVISOR_TURNS = 6 One route per question NUM_QUERIES = 3, and MAX_DRAFTS = 2 on the revision loop

The supervisor is the most flexible and the hardest to bound, which is why 05a proves its turn cap with a stub supervisor that never finishes. Its researcher also returns a validated MarketData object, numbers only, and the coder sees just the user’s request and that JSON, so no web text reaches the agent that runs code. The typed router is the fix for the hotel’s string routing: the choice is a field, not a word to search for in a reply. Its RAG agent answers only from chunks above a relevance floor, and when nothing clears it, it skips the model call and says so. The planner never sees a result, which is what separates it from a supervisor: it cannot adapt, but its cost is known before the first search runs.

The module’s lab brief asks for a research team on the Larkspur Cloud handbook: a supervisor, a RAG researcher over the handbook, a web researcher and a writer that cites its sources, tested on three edge cases. Each has a mechanism in this module:

Edge case Mechanism Where
No results The RAG agent skips the model call when no chunk clears the relevance floor, and says so 05b
Conflicting sources The analyst lists gaps and contradictions across all findings before anyone writes 05c
Tool failure The failing node records an error in state, a pure router picks a fallback, and a cap ends retries 02c, 05a

For Larkspur, a conflict is real: a web forum post can quote an old refund window while the handbook gives the current one. The writer should cite both and say which is the policy, which it can only do if the findings keep their sources.

A quality loop with a cap in code

Notebook 05c is the module’s full research pipeline. A planner splits the topic into search queries, search agents run them in parallel and append to one shared findings list, an analyst and a writer turn the findings into a report, and a quality checker sends the report back for revision until it passes or the cap is reached.

The settings are in one cell and the code enforces each of them:

Setting Value Enforced by
NUM_QUERIES 3 The planner’s list is cut to this length, so the fan-out never depends on the model counting
RESULTS_PER_QUERY 3 Each DuckDuckGo search keeps this many hits
QUALITY_THRESHOLD 0.7 Every review criterion must reach it
MAX_DRAFTS 2 quality_gate ends the loop at this many reviewed drafts, whatever the scores say

Four details carry the design:

  • A reducer on the findings. findings: Annotated[list[dict], operator.add] lets parallel search agents append to one list. Each search agent extracts 2 or 3 findings, each tied to a result URL, and code marks url_verified when the URL is one the search actually returned, so an invented source shows up.
  • The weakest criterion decides. The reviewer scores completeness, clarity and actionability from 0.0 to 1.0, and quality_score is the minimum. The one criterion code can check exactly, that the four required sections (Executive Summary, Key Findings, Analysis, Recommendations) are present, is checked in code.
  • Revisions see the previous draft. The writer runs at temperature 0.7 and, on a revision, gets its previous draft and the reviewer’s feedback. At temperature 0 a revision tends to repeat the draft.
  • The exit is code. quality_gate is a pure function: approve when the minimum score reaches 0.7 and no section is missing, otherwise go back to the writer, unless iteration has reached MAX_DRAFTS. The reviewer is never asked to be lenient on a later pass.

The notebook proves the wiring before it spends a token. create_research_system(nodes=...) takes replacement nodes, and stubs plan four queries with two findings each: all eight findings survive the parallel writes, a reviewer that always scores 0.1 stops at 2 drafts, and one that scores 0.9 stops at 1. The real run is then checked against its streamed updates: one search agent per planned query, every query represented in the findings, and as many drafts as reviews, never more than 2.

Check yourself

1. What separates the one-shot planner in 05c from the supervisor in 05a, and what does each give up?

The supervisor decides after every worker report, so it can adapt, but it is the hardest to bound and needs MAX_SUPERVISOR_TURNS = 6. The planner decides the list of queries once, up front, and never sees a result: it cannot adapt, but its cost is known before the first search runs.

2. The reviewer scores a first draft 0.9 for completeness, 0.8 for clarity and 0.6 for actionability, with all four sections present. What does quality_gate do?

It sends the draft back to the writer. quality_score is the minimum, 0.6, which is below QUALITY_THRESHOLD 0.7. The writer gets its previous draft and the feedback, and MAX_DRAFTS = 2 ends the loop after the second reviewed draft whatever the scores say.

3. A web forum post quotes an old Larkspur refund window while the handbook gives the current one. What must the research team preserve so the writer can handle it?

The source of every finding. The analyst lists contradictions across all findings before anyone writes, and the writer should cite both sources and say which one is the policy. It can only do that if the findings keep their sources.

Deep-agent harness

Lesson 37.6: Deep agents: orchestrator, sub-agents, skills and long-term memory. Notebooks: 06a_simple_coding_agent.py, 06b_long_term_memory_agent.py (optional), 06c_skills (optional)

The hotel system and the research pipeline are graphs you wire node by node. A deep agent starts from the other end: one orchestrator model inside a ready-made harness that gives it files, sub-agents, skills, an execution backend and memory, and you configure the harness instead of drawing the graph. Lesson 37.6 uses the deepagents library’s create_deep_agent, in two command-line scripts. The tool and backend behaviour below is that of deepagents 0.7.32, the version in this course’s lock file.

The parts, as the scripts configure them:

Part What it gives the orchestrator In 06a and 06b
Built-in tools File operations (ls, read_file, write_file, edit_file, glob, grep), execute for shell commands, and task to call a sub-agent Added by create_deep_agent; execute returns an error unless the backend can run commands
Custom tools Domain actions 06a: name_project, internet_search (Tavily) and four Databricks Genie tools for an insurer’s customer, distribution, policy and claims data. 06b adds save_memory, recall_memories, forget_memory
Sub-agents Specialists, each a dict of name, description, system_prompt, skills and tools 06a: 7 (senior-developer, code-reviewer, research-agent and four insurer analytics agents). 06b adds memory-manager
Skills Instructions in SKILL.md files, loaded from /skills/ 8 skills in 06c_skills, one per sub-agent; each sub-agent’s prompt is “Follow the … skill instructions”
Backend Where files live and whether commands run FilesystemBackend(root_dir=..., virtual_mode=True) by default; LocalShellBackend when USE_SANDBOX=true
Checkpointer Memory within one thread MemorySaver, one thread_id per task
Model The orchestrator’s model databricks-claude-opus-4-6, temperature 0.1

Sub-agents keep the orchestrator’s context small. A call to task runs the sub-agent with its own messages and tools, and only its final message returns to the orchestrator. The research agent’s search calls (up to 5 results each by default) and its notes stay in its own context; the orchestrator reads its report.

Skills are read on demand. A SKILL.md starts with YAML frontmatter, a name and a description. The harness puts only those two fields in the system prompt and tells the model to read_file the full instructions when a task matches the description. This is progressive disclosure: eight skills cost eight short lines until one is needed. The memory-manager skill, for example, sets a workflow (assess, then save, recall or forget), five categories, and a rule to confirm before deleting unless the request is unambiguous.

The backend decides what the agent can do to your machine. Two settings in the scripts look safer than they are:

  • FilesystemBackend(virtual_mode=True) anchors paths under root_dir and blocks traversal such as ... The library’s own docstring says it provides no sandboxing or process isolation.
  • The script’s comment says USE_SANDBOX=true selects a LangSmith cloud sandbox. The code selects LocalShellBackend, which the library documents as unrestricted shell execution on the host, with no isolation.

Code execution belongs in a real sandbox backend, with a person approving each command; create_deep_agent takes interrupt_on for that. Notebook 05a gives the same advice for its Python tool.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s support desk is built like the hotel system: a coordinator, a compliance checker over account-privacy rules, and a billing agent. A customer asked for the billing email of another company’s account and got it. The trace shows the compliance checker never ran. How do you find out why, and how do you stop it happening again?

What a strong answer covers:

  • Reads the node path for that turn (stream_mode="updates"), then the coordinator’s reply: the checker runs only when the reply names it, which the prompt asks for and nothing forces
  • Makes the check structural: an unconditional edge from the guest message to the checker, instead of routing by mention
  • Enforces privacy in the tool as well, the way the hotel’s authorizer makes guest_name read as NULL, so a skipped check cannot leak the field
  • Adds the request to the regression table and tracks its pass rate over several runs, since one green run proves little

2. The coordinator forwards to the billing agent whenever its reply contains billing_agent or “billing agent”. A reply saying “I can’t involve the billing agent until you confirm the refund date” forwarded anyway. A teammate proposes raising the confidence threshold from 50 to 80. What do you say?

What a strong answer covers:

  • The threshold does not touch the cause, string matching on reply text; in the router lab, thresholds from 71 to 90 turn the known-issue test green by ending the turn early, not by routing correctly
  • It also costs real traffic: the assessor scores a request with missing details at 50 to 79, so those customers get “please repeat” instead of a question about the missing detail
  • The fix is a typed router: structured output with a Literal route, read by a pure function, as in notebook 05b
  • Keeps the known-issue test, which flips to passing when the fix lands, and unit-tests the router on hand-built states with no model

3. Larkspur runs a research team for its support engineers: a planner, three parallel searchers, a writer and a quality checker with a two-draft cap. How do you know it is still working, and what it costs, a month after launch?

What a strong answer covers:

  • Logs per run the number of search agents against planned queries, the number of drafts, and whether the run ended approved or stopped by the cap
  • Watches the share of runs stopped by the cap: a rise means the writer or the sources got worse, since the cap hides quality problems from the user
  • Tracks the share of findings whose URL was one the search returned (url_verified), the early sign of invented sources
  • Reports cost and latency per run, which scale with queries times results and with drafts, and re-runs a fixed set of handbook questions after every prompt or model change

4. To speed up refunds, Larkspur splits billing into two parallel agents, one per region, both with a refund tool. A customer was refunded twice. What went wrong, and how do you design it?

What a strong answer covers:

  • Parallel branches run the same request at the same time, so any write tool in both branches can fire twice
  • Gives the branches read-only tools and makes the one write after a single choice, as the hotel’s branches report availability but cannot book
  • Adds an idempotency key to the refund tool so a retry or a duplicate call cannot pay twice
  • Checks the wiring: one message key per branch, sync nodes and a join so the merge runs once, and a test that counts merge runs and rows written

5. You ship a deep agent to Larkspur’s support engineers, built like notebook 06b. Someone sets USE_SANDBOX=true expecting cloud isolation, and the memory panel shows one engineer’s notes in another’s session. What is wrong?

What a strong answer covers:

  • The script’s comment promises a LangSmith sandbox, but the flag selects LocalShellBackend, which runs shell commands on the host with no isolation
  • FilesystemBackend(virtual_mode=True) blocks path traversal; it is not a sandbox either, so code execution needs a real sandbox backend and approval on execute (interrupt_on)
  • Long-term memory is keyed by CURRENT_USER_ID, fixed to default-user, so every engineer reads and writes one namespace; the key must come from the authenticated user
  • recall_memories matches a substring, so it misses paraphrases; a store with search, and a review of what gets saved, come before scale

Key Takeaways

  • Put every rule that must hold in code or in a tool: a read-only connection, a parameterised write, a pure router, a loop cap. Prompts ask; code enforces.
  • Test routing as a pure function on hand-built states, keep known issues as tests, and check side effects in the database, never in the agent’s wording.
  • Fan out with one state key per branch, join before you merge, keep writes out of parallel branches, and summarize old turns into state before the thread outgrows the context.
  • A deep agent’s safety comes from its harness: the backend decides what code can do, sub-agents keep their own context, and memory needs a real user key.
