M35 Multi-Agent Architectures

One agent with every tool and every knowledge base has to pick among all of them on every step. Splitting it gives each agent a short prompt and a few tools, and adds a new problem: something has to decide which agent works next. The M35 notebooks build on four ideas: a supervisor that makes every routing decision, teams of supervisors nested as subgraphs, handoffs that let an agent pass the conversation on, and swarms that remember which agent holds it.

Open the lab

The running example is the Larkspur Cloud handbook from M11 to M13, split between three specialist RAG agents. The billing agent holds billing, cancellation, refunds and promotional credits; the operations agent holds the availability guarantee, incidents, server sizing and reboots; the data agent holds exports and retention. Three requests come back on every page and in the lab: How long does a refund take? (billing), My server went down last night. Do I get service credits? (operations, then billing) and Can I export my data after I cancel my plan? (data).

TL;DR

  • Split one agent when it has more tools or sources than one prompt can choose among well. A team makes more model calls (the 35.1 notebook’s specialist team costs roughly four times the monolith’s), so measure it against the single agent on the same requests.
  • The five LangGraph architectures share one primitive, Command(goto=..., update=...): a node writes to state and names the next node. They differ in who decides what runs next.
  • A supervisor decides every step and takes control back. On the outage request that costs 5 model calls, 3 of them routing, and buys one place to log, test and cap every decision.
  • A hierarchy nests compiled team graphs under a top supervisor. With three specialists it only adds overhead (7 calls for the same request); it pays off when one supervisor would face too many workers.
  • A handoff is a tool that returns Command(goto=..., graph=Command.PARENT). A swarm stores active_agent per thread, so a follow-up costs 1 call against 3 for the supervisor. Nothing ends a handoff loop except recursion_limit, whose default is 10,007 steps.

Mental model

Both graphs answer the outage request with the same two specialists. The supervisor decides before each specialist and once more to finish, so it spends 3 of its 5 model calls on routing. In the swarm, triage routes once and each agent hands the work on itself: 3 calls. Every architecture in this module sits somewhere between these two, and the choice is about who holds control after an agent finishes.

When one agent becomes a team

Lesson 35.1: Monolithic vs multi-agent; a crew from scratch. Notebooks: 01a_multi_agent_vs_monolithic_agent.ipynb, 01b_multiagent_pattern_from_scratch.ipynb (optional)

A monolithic agent is one ReAct loop with one system prompt and every tool. The 35.1 notebook gives such an agent a web search tool (TavilySearch, 3 results per search) and asks it for a market report with three sections: news and sentiment, a technical read of the price trend, and financial performance. Then it builds a team for the same request: a news analyst, a technical analyst and a financial analyst, each a ReAct agent with its own persona and the same search tool, and a report writer that merges their three sections.

Monolithic agent Specialist team
Prompts one, covering every domain one per specialist, each about one domain
Tool choice every tool, every step a few tools per agent
Model calls one ReAct loop three ReAct loops and a synthesis call; the notebook puts it at roughly four times the calls
Latency sequential the specialists run in parallel, so the slowest one sets the time
Failure you debug one long transcript which specialist went wrong, and whether the writer used its section

The team runs as fan-out and fan-in. START has an edge to all three analysts, and each analyst has an edge to the writer. LangGraph runs the three analysts in the same super-step and starts the writer only when all three have finished.

The notebook does not declare a winner from one run. It measures both reports in code (word count, markdown headings, whether each requested topic is covered) and asks a judge to score each report on its own, so the judge never knows which approach wrote it. One request on one company is one sample, and a gap of a point or two on the judge alone is noise.

For Larkspur the same question decides whether to split the support assistant. One agent with the whole handbook and every tool has to tell a refund question from an outage question on every step. Three agents (billing, operations, data) each search one part of the handbook, at the cost of a decision about which of them should answer. The rest of this module is about that decision.

A crew is a dependency graph

The optional notebook rebuilds the core of CrewAI without a framework, on the raw OpenAI SDK. An Agent has a role, a task and an expected output. agent_1 >> agent_2 (borrowed from Airflow) records that agent 2 needs agent 1’s output, and agent 2 receives that output in its context, labelled with the agent that produced it.

A Crew collects agents in a with block and runs them in topological order: an agent runs only after everything it depends on. A cycle has no topological order, so the crew raises an error before any model is called. [analyst_a, analyst_b] >> editor is fan-in: the editor waits for both and reads both outputs.

The last part of the notebook draws the same fan-in crew as a LangGraph StateGraph, with one add_edge per dependency. A crew is a fixed dependency graph. Everything in lesson 35.2 onward adds a node that chooses the next agent at run time.

Key Takeaways

  • A specialist team gives each agent one domain and a few tools, at roughly four times the model calls of one ReAct loop. Running the specialists in parallel keeps latency near the slowest one.
  • Compare a team with a single agent using code checks and a judge that does not know which approach wrote each report. A gap of a point or two on the judge from one request is noise.
  • A crew is a fixed dependency graph run in topological order, so a cycle fails before any model is called. Choosing the next agent at run time is what the later architectures add.

Five architectures, one primitive

Lesson 35.2: The five multi-agent architectures and agent communication. Notebooks: 02a_five_multi_agent_architectures.ipynb, 02b_agent_communication.ipynb (optional)

Every architecture in the 35.2 notebook is built from one return value. A node returns Command(goto="writer", update={...}): the update is written to state and the graph runs writer next. The node’s return annotation, such as Command[Literal["writer", "__end__"]], lists the nodes it may jump to, and LangGraph draws those as the graph’s edges. add_edge fixes a path when the graph is built; Command(goto=...) picks one at run time. Most real systems use both.

Architecture Who decides what runs next Fails when Reach for it when
Network each agent, for itself nothing guarantees the run ends agents need to negotiate
Supervisor one central node the supervisor becomes a bottleneck routing must be auditable
Tool-calling supervisor the model, by choosing tools the same input can route differently intent classification is the hard part
Hierarchical a coordinator over team coordinators step budgets grow and team internals are hidden the problem is shaped like an org chart
Custom workflow mostly the graph, with one dynamic branch the work is too open-ended for fixed paths the sequence is known in advance

The tool-calling supervisor needs no routing code. Each specialist is wrapped as a tool, and InjectedState hands it the graph’s state without the model having to pass it as an argument. The docstring is the routing rule, because it is the tool description the model reads. The notebook’s mixed query (“trouble with my bill and the app keeps crashing”) may call one specialist or two, and that variability is the trade.

Two points from the notebook carry through the rest of the module:

  • A router that writes nothing keeps the transcript readable. The supervisor in Part 2 decides without appending a message, so the transcript holds only the work.
  • Always pass recursion_limit. LangGraph counts super-steps, and its default limit is 10,007. The notebook passes 25 on every run, and a deliberately endless ping-pong between two nodes stops with GraphRecursionError in a fraction of a second. The hierarchy run needs twice that, because each team adds steps of its own.

For Larkspur, the choice comes down to a few questions in order:

The support assistant’s order is not known in advance (a question may need one specialist or two), so it starts at the second question, and the answer depends on whether conversations stay with one specialist across turns. A swarm is a network in which the handoffs are tools and the graph remembers who holds the conversation; lesson 35.5 builds one. Lesson 35.4 builds the supervisor and the hierarchy.

Agent communication

Choosing who runs next is half the design. The other half is what agents pass to each other while they run. The optional notebook builds three patterns.

Pattern State Each agent reads Trade-off
Message passing one messages list with the add_messages reducer the whole conversation so far simple and transparent; every agent re-reads and parses prose
Typed fields one field per stage (raw_data, analysis, confidence_score, recommendations) only the fields it needs structured output fills each field with a validated Pydantic object; the schema is rigid
Generator and critic running lists of drafts and critiques (operator.add) the last draft and the feedback on it iterates to a better draft; needs a cap

The generator and critic loop shows how to keep a model from ending its own loop. The critic does not return a yes or no. For each of three criteria it copies the sentence from the draft that meets it, or writes none. Code then checks that each quote really is in the draft and computes the verdict, and MAX_ITERATIONS = 3 ends the loop whether or not the critic approves.

The notebook marks one boundary. This loop is not a blackboard: its order is fixed (draft, critique, draft), and only the exit is decided at run time. A blackboard has a controller that picks which of several specialists acts next from what is on the shared board; M36 builds one.

Key Takeaways

  • Build every architecture from one primitive, a node returning Command(goto=..., update=...). add_edge fixes a path at build time, Command picks one at run time, and most systems use both.
  • Pick the architecture by who should decide what runs next. Use a custom workflow when the order is known, handoffs when the conversation should move with an agent, and a supervisor when routing must be auditable.
  • Always pass recursion_limit, since the default is 10,007 super-steps. In a generator and critic loop, have the critic quote evidence per criterion, compute the verdict in code and cap the iterations.

Human review in a supervisor loop

Lesson 35.3: Supervisor workflow with human review. Notebooks: 03a_supervisor_workflow_with_human_review.ipynb (optional)

The 35.3 notebook turns a short transfer rumour into a publishable news article. An article passes when it is about football transfers, names the player’s current club and market value, and runs to at least 100 words. A supervisor, the “news chef”, grades the article and routes it to the specialist that can fix the first failing check. A human reads the result before it is published.

Four design choices make the loop safe to run unattended up to the human step:

  • Grade in code what code can check. Topic, club and market value need judgement, so a model answers them with structured output. The word count is exact, so code does it and the model is never asked.
  • Route to the first failing check. After every specialist, control returns to the news chef, which grades the updated article again: market value first, then club, then length. An off-topic article ends the run at once.
  • Cap the passes. MAX_PASSES = 5. A grader that keeps answering “no” cannot keep the loop going past that.
  • Write the output in one place. Only a full pass copies the article into final_article, so the published text is always the version that passed, whether or not any specialist ran.

The workflow then becomes one node of an outer graph, followed by a node that publishes. Compiling the outer graph with a checkpointer and interrupt_after=["newsagent_node"] pauses every run after the article is written. The reviewer reads the state, changes it with update_state if needed, and resumes with invoke(None, ...). In the notebook the edited article, not the model’s, reaches the publishing call.

That interrupt is static: fixed at compile time, it pauses every run at the named node. A dynamic interrupt(payload) inside a node pauses only when the node decides to, and the run resumes with Command(resume=...). Larkspur needs the dynamic kind. A refund the billing agent proposes inside the 30-day window can go straight to the customer; one outside the window pauses for a person. The check that decides to pause compares dates in code, for the same reason the word count does.

Key Takeaways

  • Grade in code whatever code can check exactly, such as word count, and use a model with structured output only for checks that need judgement. Route to the first failing check and cap the passes.
  • Write the published output in one place, set only on a full pass, so the text that ships is always the version that passed.
  • A static interrupt_after pauses every run at a node; a dynamic interrupt(payload) pauses only when the node decides. Use the dynamic kind for a refund outside the 30-day window, and compare the dates in code.

Check yourself

1. Why does the news chef use a model to judge topic, club and market value, but leave the 100-word check to code?

Topic, club and market value need judgement, so a model answers them with structured output. The word count is exact, so code computes it and the model is never asked. A check that code can do exactly should never depend on a model’s answer.

2. An article names the player's current club but has no market value and only 80 words. Which specialists run, and in what order?

The news chef routes to the first failing check, in the order market value, club, length, so market_value_researcher runs first. Control returns to the chef, which grades again; the club passes, so word_count_rewriter runs next. MAX_PASSES = 5 caps the loop if a check keeps failing.

3. Larkspur wants a person to review only refunds proposed outside the 30-day window. Should it use a static interrupt_after or a dynamic interrupt?

A dynamic interrupt(payload) inside the node. A static interrupt_after is fixed at compile time and pauses every run, while the dynamic one pauses only when the node decides to, and the run resumes with Command(resume=...). The check that decides to pause compares the dates in code.

Supervisor

Lesson 35.4: Supervisors and hierarchical teams. Notebooks: 04a_supervisor_pattern.ipynb, 04b_hierarchical_agents.ipynb

A supervisor is a node that reads the work so far and picks the next specialist, or decides the task is done. Every specialist reports back to it. In the 35.4 notebook the supervisor is a model with structured output: RouteDecision holds next, a closed Literal["researcher", "writer", "critic", "FINISH"], and a one-line reasoning. A typed choice cannot name a node that does not exist, and the graph never parses prose to find out where to go.

The notebook splits deciding from routing:

  • The supervisor calls the model and writes the decision to state: next_agent, task_complete, and one entry in route_log. It never writes to messages, so the transcript holds only the work and the routing history sits in its own key.
  • Each specialist appends its output to messages and returns specialist_calls: 1. The operator.add reducer sums those, so the count never depends on reading message text.
  • route_to_agent is a pure function on the conditional edge. It reads specialist_calls first and sends the run to finalize once it reaches MAX_SPECIALIST_CALLS = 6, whatever the model chose. Only then does it follow task_complete and next_agent.

recursion_limit = 25 stays as the backstop, but it ends a run with an error; the counter ends it with a result. Part 9 of the notebook proves the cap with stubs: a supervisor that never says FINISH and a writer that returns numbered drafts without a model. The run stops at 6 specialist calls, and no model is called.

The supervisor’s price is one decision before each specialist and one more to finish. On Larkspur’s outage request (operations, then billing) that is 5 model calls, 3 of them routing, where a swarm needs 3. Each follow-up costs the supervisor 3 calls, because every turn starts at the supervisor again. The routing cost lab counts it call by call. In exchange, every routing decision is in one log with its reason, the routing rules are in one prompt you can test, and one counter caps the whole run.

Hierarchical teams

When one supervisor has too many workers to choose among well, group the workers into teams with a supervisor each, and put a coordinator over the team supervisors. In LangGraph each team is its own StateGraph, compiled on its own, and added to the parent graph with add_node like any function node. The parent never sees inside it.

After each department the run returns to the CEO, which can send the work on to a second department (research, then content) or finish. The notebook’s teams show that a team’s inside is its own choice: research fans out to two specialists and merges in a lead, content has its own supervisor, analysis is a fixed pipeline.

Four rules make the hierarchy compose:

  • One shared state contract. TeamState (messages and final_answer) is what the parent and every team speak, so a compiled team drops in as a node with no adapter code.
  • Extensions stay at their level. The CEO’s CEOState adds department, route_log and ceo_turns; the content team’s ContentState adds next_step and content_turns. Keys outside TeamState never cross the boundary.
  • Counters stay out of the shared contract. A team hands its whole final state back to the parent. A counter in TeamState with an adding reducer would be added a second time on the way up.
  • Cap every level. MAX_CEO_TURNS = 4 and MAX_CONTENT_TURNS = 4, each read by a pure routing function from its own counter.

Test each team on its own before you assemble the hierarchy; a team that misbehaves is much harder to diagnose once it is one node inside a larger graph. The cost is visibility and steps: the parent sees what a team appended, not why, and in lesson 35.2 the two-level run needs recursion_limit raised from 25 to 50.

Larkspur’s three specialists do not need a hierarchy. Put billing and data in an accounts team with its own lead and operations in a platform team, and the outage request costs 7 model calls, 5 of them routing, against 5 for a flat supervisor. A hierarchy starts to pay when the flat supervisor’s prompt has to describe so many specialists that its routing accuracy drops; measure that before adding the layer.

Key Takeaways

  • Give the supervisor a closed Literal of next nodes and keep its decisions out of messages. A pure routing function reads a specialist-call counter first, so the cap ends a run with a result, not an error.
  • A supervisor pays one routing call before each specialist and one to finish, 5 calls for the outage request against 3 for a swarm. In return, every decision sits in one log with its reason.
  • Compose hierarchies through one shared state contract, keep counters out of it and cap every level. Add a layer only after measuring that a flat supervisor’s routing accuracy has dropped.

Handoffs

Lesson 35.5: Handoffs and swarms. Notebooks: 05a_agent_handoffs.ipynb, 05b_multi_agent_swarm.ipynb

A router and a handoff both move a request between agents. They differ in who holds control afterwards.

Router or supervisor Handoff
Who picks the next agent the router, after every step the agent holding the conversation, by calling a tool
Where control goes after an agent back to the router, on a static edge nowhere: the agent finishes the turn or hands off
The next user message starts at the router the active agent, read from active_agent in state
What stops a loop the router’s own cap nothing built in; only recursion_limit

A structured-output classifier that sends each request to one specialist is still a router. A handoff needs the agent itself to choose, by calling a tool, and the graph to remember the choice.

A handoff tool is an ordinary @tool that returns a Command instead of a string. It runs inside the calling agent’s own graph, but the decision belongs to the parent graph that holds all the agents, so the Command is addressed there:

  • goto="billing" names the parent node to run next.
  • graph=Command.PARENT applies the Command in the closest parent graph, which ends the calling agent’s run.
  • update={...} writes the conversation plus a ToolMessage that answers the tool call, and sets active_agent.

InjectedState gives the tool the agent’s messages and InjectedToolCallId gives it the id of the call it answers, so the model fills in only one argument in the 35.5 notebook’s version: context, a note for the next agent so the customer is not asked again. The parent’s state is MessagesState plus active_agent. Its only routing of its own is at START: read active_agent and send the new message there, or to triage on a new thread.

With a checkpointer, active_agent outlives the turn. Here is one Larkspur thread through triage and the three specialists:

Turn 2 is the point of the checkpointer: triage does not run, because START read active_agent = billing from the saved thread. Turn 3 moves sideways, billing to operations, with no coordinator involved. Every move is one tool call, and each one rewrites active_agent.

Nothing in this graph forces a stop. If two agents each decide the other should answer, they pass the request back and forth until recursion_limit raises GraphRecursionError; each agent run is one super-step of the parent graph. The notebook proves both the routes and the guard with a scripted model (LangChain’s GenericFakeChatModel replaying fixed replies, tool calls included), so the mechanism is tested without an API call.

Swarm

A swarm is the same mechanism packaged by the langgraph-swarm library. create_handoff_tool builds the tool, create_swarm builds the parent graph with one node per agent and the START router, and SwarmState is MessagesState plus active_agent. default_active_agent names the agent a new thread starts at. Compile with a checkpointer and the swarm remembers, per thread_id, which agent holds each conversation.

The second notebook builds three agents over a music store: a general QA agent that does RAG over company documents, an NL2SQL agent over the Chinook catalogue, and an invoice agent. Each gets its own tools plus handoff tools to the other two. Two details carry over to any swarm:

  • The library tool carries no note. It takes no arguments, and its ToolMessage says only “Successfully transferred”. Whatever the next agent needs must already be in the conversation. The hand-built tool’s context argument exists to fix that.
  • Tools that run model-written queries must be safe whatever the model writes. The NL2SQL connection opens the file read-only, sets PRAGMA query_only = ON, and installs an authorizer that refuses writes, ATTACH and PRAGMA. The invoice tools bind the customer ID as a parameter and never paste it into the SQL.

A swarm spends routing once per thread. On the outage request, triage hands off to operations, operations answers its part and hands off to billing: 3 model calls, one of them routing, against 5 for a supervisor. After that, each follow-up goes straight to the active agent for 1 call, where the supervisor pays 3 and a hierarchy 5. The routing cost lab runs the same three Larkspur requests through all four architectures, with the follow-up turns on a slider.

Over a thread of the outage request and 3 follow-ups the lab counts 6 calls for the swarm, 14 for the supervisor and 22 for the hierarchy. The router (M30) spends 8 and still never asks billing about the credits. The swarm’s saving rests on the conversation staying with one specialist. When a follow-up changes topic, the active agent has to recognise that and hand off, and the routing quality now lives in every agent’s prompt instead of one supervisor’s.

Key Takeaways

  • A handoff tool returns Command(goto=..., graph=Command.PARENT) and sets active_agent. With a checkpointer, the next user message goes straight to the agent holding the conversation, with no router in between.
  • Nothing in a swarm forces a stop, so two agents can bounce a request until recursion_limit raises. Pass a note with each handoff, because the library tool carries none.
  • A swarm spends routing once per thread, 6 calls for the outage request and 3 follow-ups against 14 for a supervisor. The saving holds only while follow-ups stay on one specialist’s topic.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s support swarm sometimes takes a minute to fail. The trace shows billing and operations handing the same customer back and forth until LangGraph raises GraphRecursionError. What do you look at, and what do you change?

What a strong answer covers:

  • Reads the handoff ToolMessages and each agent’s prompt: both agents believe the other owns “outage credits”, so the ownership line is unclear
  • Fixes ownership in the agents’ prompts and handoff tool descriptions, and gives one of them the answer instead of another handoff
  • Sets recursion_limit explicitly on every run (25 in the notebooks), because the default of 10,007 steps is what made the failure take a minute
  • Adds a scripted-model test that replays the ping-pong and asserts the run ends with the error, so a prompt change cannot bring the loop back silently

2. The M30 router sends each question to one knowledge base. Customers ask “my server went down, do I get credits?” and get an answer about the outage with nothing about credits. Do you replace the router with a supervisor or a swarm?

What a strong answer covers:

  • Names the failure: a one-shot router picks one specialist, so a two-part request loses its second half
  • Supervisor: re-decides after each specialist, so it covers both halves; 5 calls for this request, with every decision in one log
  • Swarm: operations answers its part and hands off to billing; 3 calls, and follow-ups go straight to the active agent
  • Chooses by traffic shape: many multi-turn conversations with one specialist favour the swarm; audit or compliance needs favour the supervisor’s single decision log

3. Your lab brief says to compare routing accuracy and cost after replacing the router with a supervisor over three specialist RAG agents. How do you measure it?

What a strong answer covers:

  • Labels each golden question with the specialists it needs, in order, and scores the route the system took against that label
  • Logs routing outside the transcript (route_log, one entry per decision with its reason), so routing accuracy is read from state and not parsed from prose
  • Reports model calls, tokens and latency per request, split into routing calls and specialist calls, next to answer quality from the M11 baseline
  • Looks per question, not only at the mean: single-domain questions get more expensive under a supervisor while multi-part ones get correct

4. A swarm thread has active_agent = billing. Three days later the same customer writes “Can I export my data?” What happens, and what should happen?

What a strong answer covers:

  • The START router reads the saved active_agent, so billing receives a question it has no handbook section for
  • Billing needs a handoff tool to the data agent and a prompt that tells it to use it; otherwise it answers from nothing or asks the customer to repeat
  • The library handoff tool carries no note, so whatever data needs must already be in the messages; a hand-built tool can pass a context note
  • Considers expiring or resetting active_agent after a quiet period, so a new topic on an old thread starts at triage

5. Larkspur wants a human to approve any refund the billing agent offers outside the 30-day window before the customer sees it. Where does the pause go in a supervisor workflow?

What a strong answer covers:

  • Uses a checkpointer, because a paused run has to be saved and resumed by thread
  • Prefers a dynamic interrupt(payload) inside the billing node, so only out-of-window refunds pause; a static interrupt_after pauses every run
  • Lets the reviewer edit state (update_state) or resume with Command(resume=...), then sends the edited answer, not the model’s
  • Checks the window in code from the purchase date, so the decision to pause never rests on the model’s judgement

Key Takeaways

  • Split one agent only when its tools or sources are too many to choose among well, and measure the team against the single agent on the same requests.
  • Let the model choose the next agent, and let a pure function in code read that typed choice and a counter. The loop ends where the code says, whatever the model says.
  • A supervisor pays a routing call per specialist plus one to finish; a swarm pays one routing call per thread and then follows active_agent. Pick by whether conversations stay with one specialist and whether you need one decision log.
  • Pass recursion_limit on every run and add a counter cap to any graph that can cycle; test both with a stub or scripted model.
