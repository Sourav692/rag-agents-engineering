M36 Collaboration, Control & Parallel Agents

M35 put several agents behind a supervisor. This module changes how they work together: through a shared board, by arguing, by interviewing each other, and by running at the same time. The M36 notebooks build on four ideas: a blackboard that every agent reads and a controller that re-decides after each contribution, a debate judged by a third agent, STORM’s perspective interviews, and LangGraph’s superstep model for parallel branches.

Open the lab

The running example is the Larkspur Cloud handbook from M11 to M13. One compound support question carries the parallel lessons and the lab: “I’m cancelling my annual plan after this week’s outages. Can I get a full refund, how long will it take, can I still export my data, and do I get credits for the outages?” It splits into four sub-questions whose evidence is the handbook’s refund-window, refund-timing, export and retention, and SLA chunks. The blackboard lesson uses an outage escalation from the same handbook; debate and STORM use a decision and an article about it.

TL;DR

  • A blackboard is one shared list that every specialist reads and appends to. A controller re-reads it after every contribution and picks the next specialist, so it can skip a branch that a fixed pipeline always runs. Guard it with a typed decision and a call cap (the notebook stops at 6 specialist calls, with a recursion limit of 20 behind it).
  • Debate gives two agents opposite sides and a judge who reasons past both. It costs 2N + 1 calls for N rounds (7 at N = 3), so keep it for trade-offs; a factual question is better answered in one call.
  • STORM researches from several perspectives before it writes: personas, simulated interviews, one merged outline, one draft per section. Its cost is countable: 1 + P × (2T + 1) + 1 + S + 1 calls, 22 to 24 in the notebook.
  • LangGraph runs parallel branches in supersteps: every node of a step runs at once and the next step starts when the slowest one ends. In the lab, the four sub-questions take 5.7 s one at a time, 3.4 s in parallel, and 2.7 s once the outage rewrite moves inside its agent node.
  • Parallel branches need a join that waits (a list edge or defer=True) and a reducer on every key they share; without them the synthesizer answers from half the evidence, or the run raises InvalidUpdateError.

Mental model

The patterns differ in who decides what runs next and when that decision is made. A pipeline and STORM fix the order when you build the graph. A fan-out fixes the shape but lets the branches overlap in time. A blackboard leaves the order to a controller at run time, which buys flexibility and costs a model call per step. All four write to one shared state, so all four need the same guards: typed decisions, reducers on shared keys and a cap on the number of steps.

Blackboard

Lesson 36.1: Blackboard architectures. Notebooks: 01a_blackboard_intro.ipynb, 01b_blackboard_research_team.ipynb (optional)

A blackboard system coordinates specialists through one shared store, the blackboard. Specialists never call each other. Each one reads the board, does its own job and appends its result. A controller reads the whole board after every contribution and picks the next specialist, or FINISH. The design comes from the HEARSAY-II speech-recognition system (Erman et al., 1980). In HEARSAY-II the specialists watched the board for their own trigger conditions and a scheduler chose among them; in the notebooks the controller does all the watching.

The controller is the only part that decides order. The specialists stay narrow, and adding one means adding a node and a name the controller may choose; nothing else is rewired.

Where a fixed pipeline fails

Lesson 36.1’s notebook gives both designs one request with conditional logic: find the latest news, then run a technical analysis if the news is neutral or positive, or a financial analysis if it is negative. The pipeline news → technical → financial → writer runs both analyses on every request, because its edges cannot skip a node. The blackboard controller reads the news analyst’s post, then picks one branch. The notebook checks this in code from the list of specialists that ran, rather than asking another model whether the instruction was followed:

Check, computed from steps Sequential pipeline Blackboard
Followed the either/or Never: both branches run by construction Whatever this run’s controller chose
Correct branch for the sentiment Never: both branches run Checked against a sentiment label from the news post

The blackboard row can fail too, because the controller is an LLM. That is the reason the check is computed on every run instead of assumed.

On the Larkspur handbook the same shape is an outage escalation: a customer says their server went down twice this week; if the outages pushed availability below the 99.95% SLA, draft a service-credit reply, otherwise draft a reply that points to the status page and the root-cause report. An incident analyst posts what the incident log shows, the controller reads it and calls either the credits analyst or the status analyst, and a writer drafts from the board. A pipeline would pay for both analysts on every escalation.

Guards that keep a controller honest

A controller that re-decides at every step can also loop, stall or name a step that cannot run yet. The notebooks guard it at four points:

  • A typed decision. ControllerDecision.next_agent is a Literal of the specialist names plus FINISH, so the model can only name a real node. The node writes the decision to state, and a separate, pure routing function reads it.
  • A cap in code. The controller returns FINISH without calling the model once MAX_SPECIALIST_CALLS = 6 specialists have run. LangGraph’s recursion_limit = 20 is the backstop, and it ends the run with an error rather than a clean stop.
  • Preconditions checked in code. In the optional research-team notebook, precondition_problem() rejects impossible choices (fact-checking an empty board, finishing without a draft) and rule_based_next() substitutes the rule-based choice. Every override is printed and counted.
  • Structured contributions. Posts there are dicts with agent, type and content, so code can tell a finding from a fact-check from a draft, and can pair each finding with its own verdict.

Specialists that search must execute their tool. The notebook runs each one as a small create_agent loop; binding the tool with bind_tools() alone only lets the model request a search, and nothing runs it.

What it costs, and when it pays

Every specialist turn sits between two controller turns, so a run with k specialists makes up to k + 1 controller calls on top of the specialists’ own. Traces are harder to read than a pipeline’s because the path changes from run to run; in the research-team notebook a fact-check that flags a finding sends the controller back to the researcher, a loop-back no edge in the graph spells out.

Use a blackboard when the next step depends on what earlier steps found: diagnosis, triage, research with verification. When the order is known before the run starts, a pipeline or a fan-out (lesson 36.5) is cheaper and easier to test.

Key Takeaways

  • A blackboard coordinates specialists through one shared store, and only the controller decides order. It can pick one branch from what earlier posts found, where a fixed pipeline runs every branch by construction.
  • Guard the controller in code with a typed Literal choice, a specialist-call cap, precondition checks and structured posts. recursion_limit is only the backstop, because it ends the run with an error.
  • A run with k specialists makes up to k + 1 controller calls, and its path changes from run to run. When the order is known before the run, a pipeline or fan-out is cheaper and easier to test.

Debate

Lesson 36.2: Debate. Notebooks: 02a_debate.ipynb (optional)

In a debate two agents argue opposite sides of a question over several rounds, each reading the whole transcript and rebutting the other’s latest point, and a neutral judge writes the verdict. The blackboard agents cooperate on one artifact; debaters disagree on purpose, so the judge sees the strongest case for both sides before deciding.

Two research setups share the name. The notebook follows Liang et al.’s MAD (EMNLP 2024): fixed affirmative and negative sides, and a judge that reads the debate and extracts the answer. In Du et al.’s multiagent debate (2023) every agent gets the same prompt, answers on its own, then reads the others’ answers and revises until they converge: no assigned sides and no judge.

The control flow is a small round-robin graph. A round counter in state drives the conditional edge after advance_round, and because that routing function is plain Python, the notebook checks it without a model call: after rounds 1 and 2 it routes back to side A, after round 3 to the judge.

What makes a debate worth reading

  • Honest sides that engage. Each persona must argue its side without inventing facts, and after its opening turn must rebut the opponent’s strongest recent point before adding one or two of its own (120 words at most in the notebook). Without the rebuttal rule the debate turns into two parallel monologues and the judge has nothing to weigh.
  • A judge that reasons past the debate. The judge fills a Pydantic DebateVerdict: the strongest point from each side, the weak or overstated claims, a final recommendation and a confidence. Its prompt asks it not to name a winner, so the recommendation may be conditional (“start with a monolith, split out services when …”).
  • A baseline beside it. The notebook asks the same question in one call with a neutral prompt. A capable model often hedges on its own, so the debate does not always add anything.

Cost against value

Approach LLM calls What you get
Single call 1 One answer, often already balanced
Debate, N rounds 2N + 1 A transcript, the strongest point from each side, a judged recommendation
Debate, N = 3 (the notebook) 7 Six turns and one verdict

Debate earns its cost on questions with legitimate trade-offs and no single correct answer: architecture choices, build or buy, policy. The notebook’s question is whether a six-person team should start a new B2B SaaS product with microservices or a monolith. For a factual question with one correct answer, the single call is the better choice.

On the Larkspur handbook that line is easy to draw. “How long does a refund take?” has one answer, 5 to 10 business days, and belongs to retrieval. “Should the support assistant stop retrieving and put the whole handbook in a long-context prompt?” is a trade-off between cost per call, accuracy on facts buried mid-context and access control (M11’s fifth interview question); a debate transcript and its judged verdict are a useful input to that decision. When two retrieved chunks disagree, for example an old and a new refund policy, fix the index first with version metadata and a filter (M12) rather than asking two agents to argue about which one is current.

Known weaknesses: both debaters can miss a consideration neither persona was primed to raise, a weak persona makes the debate lopsided, and the judge is a single point of bias unless its prompt keeps it even-handed.

Key Takeaways

  • A debate runs two opposing sides over N rounds, each rebutting the other’s latest point, then a judge fills a structured verdict. It costs 2N + 1 calls, 7 at three rounds, against 1 for a single call.
  • Require each side to rebut before adding its own points, or the debate becomes two monologues. Ask the judge for the strongest point from each side and a recommendation rather than a winner.
  • Debate questions with real trade-offs, such as build or buy. Send factual questions like the refund time to retrieval, and fix disagreeing chunks in the index with version metadata.

STORM

Lesson 36.3: STORM: multi-perspective research and writing. Notebooks: 03a_storm.ipynb

STORM (Synthesis of Topic Outlines through Retrieval and Multi-perspective question asking; Shao et al., NAACL 2024, arXiv:2402.14207) writes a long article on a topic the writer knows little about. A single “write an article about X” prompt tends to give one generic angle. STORM researches first, from several perspectives, and writes only from what the research found:

  1. Perspective generation. One structured-output call proposes P distinct editor personas, each a different professional lens on the topic.
  2. Simulated interviews. For each persona, a persona-editor asks one focused question at a time and an expert answers, for T turns; both roles are the same model with different system prompts. A third call extracts the transcript’s facts into a typed list.
  3. Outline synthesis. An editor-in-chief call merges every persona’s facts into one ordered outline of 4 to 6 sections.
  4. Section drafting. A writer call drafts each section from the research notes; a last call writes the title.

Debate (lesson 36.2) uses opposing perspectives to decide. STORM uses complementary ones to research.

The facts list is the payload

Each stage consumes the previous stage’s typed object (PerspectiveList, ResearchFindings, ArticleOutline), produced with with_structured_output, so no stage parses free text. Only the extracted facts travel into the outline and the drafts; the transcripts stay for audit, so you can trace which question surfaced which fact. Two steps decide quality:

  • Persona design. Three reworded generalists produce redundant research. If the personas overlap, tighten the perspective prompt, for example by listing the disciplines to draw from.
  • Outline synthesis. This is where P research threads become one narrative. An outline with one section per persona is a concatenation, and the synthesis prompt needs to ask for a merged structure.

The notebook’s expert is the model playing a knowledgeable role, with no retrieval, so its “facts” are only as reliable as the model’s memory; that is the pattern’s main weakness. Swapping the expert’s plain call for a tool-using agent grounds it without changing any later stage. On the Larkspur handbook the expert would answer from a handbook retriever: for an article on what happens to an account when a customer cancels, a billing persona would surface the 30-day refund window and the 5 to 10 business days a refund takes, and a data persona the 30 days of retention before deletion, each fact traceable to its chunk.

Counting the calls

The cost is fixed by the parameters before the run starts: one call for the perspectives, 2T + 1 per interview (T questions, T answers, one extraction), one for the outline, one per section and one for the title.

calls = 1 + P × (2T + 1) + 1 + S + 1
Perspectives P Turns T Calls With S = 4 to 6 sections
3 2 18 + S 22 to 24 (the notebook)
3 3 24 + S 28 to 30
5 2 28 + S 32 to 34
5 3 38 + S 42 to 44

The notebook attaches a callback that counts every chat-model call, structured-output calls included, and compares the count with this arithmetic. Capping P (perspectives[:NUM_PERSPECTIVES]) and S (MAX_SECTIONS = 6) keeps the cost bounded when the model returns more than it was asked for.

Latency is a different number from cost. The interviews are independent of each other, but the notebook runs them in a Python for loop, so their waits add up. Dispatching one branch per persona with Send (lesson 36.5’s map-reduce) puts them in one superstep: the same calls, with the interview stage taking about as long as its slowest interview. The section drafts are independent in the same way.

Key Takeaways

  • STORM researches before it writes. P personas each run a T-turn interview, their extracted facts merge into one outline, and each section is drafted from what the research found.
  • Quality rests on distinct personas and an outline that merges the research threads. One section per persona is a concatenation, and an expert with no retrieval is only as reliable as the model’s memory.
  • Cost is fixed before the run at 1 + P × (2T + 1) + 1 + S + 1 calls, 22 to 24 in the notebook. Dispatch the interviews with Send so the stage takes about as long as the slowest interview.

Three kinds of controller

Lesson 36.4: Meta-controllers, ensembles and emergent systems. Notebooks: 04a_meta_controller.ipynb (optional), 04b_ensemble_parallel_exploration.ipynb (optional), 04c_cellular_automata.ipynb (optional)

A router, a meta-controller and a blackboard controller are all one structured-output call that picks from a fixed set. They differ in what they pick and how often:

Controller What it decides When Calls per request
Router Which specialist answers, inside one fixed graph Once, before any specialist runs 1
Meta-controller Which whole architecture runs: one call, a search agent, a planner or a debate Once, before any architecture runs 1
Blackboard controller (36.1) Which specialist acts next, given the whole board After every contribution, until done Up to one per specialist turn, plus one

A router differs from a handoff (M35) in who holds the decision: the router decides before any specialist runs, and the specialist cannot pass the request on; in a handoff the agent holding the conversation transfers it by calling a tool.

The meta-controller wraps each architecture as a plain callable, (query: str) -> str, so it never sees inside one. Its decision is a Strategy Enum, and a registry maps each member to its callable instead of a chain of ifs; a registry check catches a strategy with no callable. The notebook’s four strategies, mapped onto Larkspur support traffic:

Strategy Shape of request A Larkspur request of that shape
direct_answer Self-contained fact the model already knows “What is a vCPU?” (general knowledge, no handbook needed)
search_agent Live or external information “Is there an incident right now?” (only the live status page knows)
multi_step_planning Several bundled sub-questions The lab’s refund, timing, export and credits question
debate Trade-off with no single answer “Should we move from a monthly to an annual plan?”

The main weakness is that classification errors cascade. A misrouted request still gets an answer, from the wrong specialist or architecture, and nothing downstream notices. The notebook’s guard is a table of requests with the route each was written for, compared in code with the route each controller chose. That table is the regression test to run on every prompt or model change. One choice per request also cannot handle a mixture (“look up X, then debate whether it is a good idea”), and the classification call adds latency before any real work starts.

Ensembles: vote against verdict

An ensemble runs several independent agents on the same question at the same time, each with a different persona, and an aggregator combines their conclusions. The notebook’s committee has a bullish growth analyst, a cautious value analyst and a quantitative analyst, and a chief investment officer (CIO) who writes the recommendation.

The graph uses every piece of lesson 36.5. One edge from START to each analyst puts all three in one superstep. All three write the shared analyses key in that superstep, so it carries the operator.or_ reducer, which merges their one-entry dicts. A list edge from the three analysts makes the CIO wait for every report.

The analysts never see each other’s work, so none anchors on another. That independence is what an ensemble buys, and the notebook checks the parts that are easy to assume:

  • Overlap. Each analyst records its start and end time; the check passes when all three windows were open at once.
  • Vote against verdict. Each analyst ends its report with Recommendation: Buy|Hold|Sell, and the CIO’s recommendation is a Literal of the same three values, so code can set the majority vote beside the verdict. A CIO that departs from the majority is fine if its summary says why. A CIO that departs with no reason given is the failure to look for.

For Larkspur, the same shape fits an answer review: three graders read one drafted reply, one for faithfulness to the retrieved chunks, one for tone, one for policy, and an aggregator decides whether it ships. Each grader costs its own model calls, so the committee is priced like three agents, while its latency is set by the slowest grader.

Emergent systems

The cellular-automata notebook has no controller at all. Every cell of a warehouse grid is a small agent with one local rule: its distance to the packing station is 1 plus the smallest distance among its neighbours. Applied to every cell at once, tick after tick, the rule spreads a distance wave around the walls, and a carrier reaches the station by always stepping to the neighbour with the lowest value. The notebook checks the emergent paths against a global breadth-first search over the same grid, then walls off a cell next to the station and shows the path rerouting with no change to the code.

This is the far end of the control range in this module: no controller, only a local rule applied everywhere in synchronous ticks. It solves a global problem without a planner, at the cost of many cheap updates, and the notebook trusts the result only after the breadth-first check.

Key Takeaways

  • A router picks a specialist and a meta-controller picks a whole architecture, each once per request; a blackboard controller decides after every contribution. All three are one structured-output call over a fixed set.
  • A misrouted request still gets an answer, and nothing downstream notices. Keep a table of requests with their intended routes and compare it in code on every prompt or model change.
  • An ensemble runs independent agents in one superstep with a reducer on their shared key. Set the majority vote beside the aggregator’s verdict, and flag a departure from the majority that gives no reason.

A blackboard controller differs from both by deciding again after every contribution.

Map-reduce / async

Lesson 36.5: Parallel agents, async nodes and streaming. Notebooks: 05a_parallel_agents.ipynb, 05b_async_multi_agent_streaming.ipynb

An agent spends almost all of its time waiting: for a model, a search, a database. Three agents that each wait one second take 3 s one after another and about 1 s together, because the waits overlap; nothing runs faster. Notebook 05b measures exactly that with asyncio.sleep(1) standing in for a model call. The rest of this page is how LangGraph arranges the overlap and where it goes wrong.

The running example is the compound Larkspur question from the module page, split into four sub-questions. Three are answered directly; the outage one first rewrites “outages” into the handbook’s own words (availability, service credits), because TF-IDF missed that evidence in M11.

Supersteps

LangGraph runs a graph in supersteps. In each superstep it runs every node that the previous superstep triggered, waits for all of them, applies their state updates together, and only then works out what runs next. Several edges out of one node (a fan-out) put all their targets in the same superstep, so they run in parallel: async def nodes on the event loop, plain def nodes in a thread pool. Notebook 05a proves the layout with stub nodes and stream_mode="debug", which reports the superstep of every task: plan alone, then the three searchers together, then report once.

The barrier at the end of a superstep has a cost when branches have different lengths. In the graph above, rewrite finishes at 0.9 s, but credits cannot start until the whole superstep ends at 1.6 s, when export (the slowest, 1.2 s) finishes. The outage branch waits 0.7 s for work it does not depend on. Moving the rewrite inside the credits node keeps every branch one node long, and the answer lands at 2.7 s instead of 3.4 s.

The join

A join is a node with several incoming branches. With separate edges (add_edge("a", "join"), add_edge("b2", "join")) it runs once for every superstep in which one of its predecessors finished. Notebook 05a builds one unequal-branch graph three ways and counts the join’s runs:

Join style Join runs What happens
Separate edges 2 The first run sees only the short branch; the second sees both
List edge, add_edge(["a", "b2"], "join") 1 Waits until every listed node has finished
add_node("join", ..., defer=True) 1 Held back until the run has nothing else to do

In the lab’s graph the separate-edges synthesizer runs in superstep 3 with 3 of 4 sub-answers, writes a reply with nothing about outage credits, and runs again after credits. Use a list edge when you know the predecessors at build time. It waits for every node it names, so if a conditional edge skips one of them, the join never runs. defer=True waits for the run to go quiet instead, which also suits branches chosen at run time.

Reducers

Nodes of one superstep write their updates together when it ends. If two of them write the same key and the key has no reducer, LangGraph cannot choose a winner and raises InvalidUpdateError. A reducer in the state schema, Annotated[type, reducer], says how to combine the writes:

  • Annotated[list, operator.add] concatenates lists: every branch appends its sub-answer.
  • Annotated[int, operator.add] adds counters.
  • A dict merge (merge_dicts, or operator.or_) combines one-entry dicts into one dict keyed by branch.

The notebook runs the same two nodes against both schemas: the plain one raises, the reduced one keeps both writes. The combined list comes out in the same order on every run, whichever branch finished first, because LangGraph applies a superstep’s writes in a fixed order. A key that only one node per superstep writes needs no reducer.

Map-reduce with Send

Fixed edges cannot express a fan-out whose size is known only at run time: one branch per document, or one per sub-question when the decomposer (M18) returns three for one question and five for the next. A routing function that returns a list of Send objects can:

def fan_out(state):
    return [Send("answer_one", {"index": i, "question": q}) for i, q in enumerate(state["sub_questions"])]

graph.add_conditional_edges("plan", fan_out, ["answer_one"])
graph.add_edge("answer_one", "synth")

Each Send runs answer_one with its own private input, and all of them land in one superstep. An operator.add reducer collects the results; since branches can finish in any order, the reduce step sorts them by their tag before combining. Notebook 05a maps an LLM summary over three documents this way and counts one map branch per document.

Async nodes and what astream shows

Making nodes async def and calling await graph.ainvoke(...) changes nothing about which nodes are parallel: edges from one source do that. A chain of async nodes still runs in order. What async adds is overlap on one event loop, and astream lets you watch it:

stream_mode Emits Use it for
"updates" One event per node, as that node finishes Progress: “the refund branch is done”
"values" The full state: the input, then once per superstep Debugging the shared state
"messages" Model output token by token, tagged with the node Showing two agents writing at once

In 05b three agents wired to START and sleeping 1.0, 1.5 and 0.5 s report through updates at 0.5, 1.0 and 1.5 s, in finish order, and the whole team takes about 1.5 s against 3.0 s for the sum. values reports two snapshots, empty and full, because all three share one superstep.

In the lab, with the rewrite inside the agent node, the first sub-answer (refund_timing) streams through updates at 1.2 s, while values stays silent until the superstep ends at 1.9 s, when credits (1.5 s with its rewrite) finishes. The interactive lab runs this graph with stub latencies and draws every superstep. Its schedule matches LangGraph 1.2.18 running the same graph with asyncio.sleep at all 39 settings, to within 0.04 s:

Setting in the lab Answer lands Synthesizer runs Supersteps
One at a time, rewrite as its own node 5.7 s 1 7
In parallel, rewrite as its own node, separate edges 3.4 s 2 (the first saw 3 of 4) 4
In parallel, rewrite as its own node, list edge or defer=True 3.4 s 1 4

max_concurrency in the run config caps how many tasks run at once, which is how you stay under a provider’s rate limit. LangGraph starts a superstep’s tasks in node-name order, so under a cap the later names wait for a free slot. At a cap of 1 the parallel graph takes as long as the chain; with separate edges it takes longer, 6.5 s against 5.7 s, because the synthesizer still runs twice.

When parallelism buys nothing

  • A chain. If the writer needs the researcher’s output, it cannot start early. 05b’s three dependent one-second steps take about 3 s whether or not they are async.
  • A single agent. One agent waiting is one wait. Streaming can still show progress, but there is no time to win.
  • Fast local work. Arithmetic and string handling are work, not waiting; async adds overhead to them.

Whole runs can overlap too. asyncio.gather over three ainvoke calls runs three complete team runs in about the time of one (1.5 s against about 4.5 s), with no change to the graph. In a notebook, await directly; asyncio.run(...) fails inside a running event loop.

Key Takeaways

  • Parallel agents overlap their waits and run no faster: three one-second waits take about 1 s together against 3 s in sequence. A chain, a single agent or fast local work gains nothing.
  • LangGraph runs fan-out targets in one superstep and waits for all of them before the next. Keep branches the same length, and join with a list edge or defer=True so the join runs once with every input.
  • Give any key that several nodes write in one superstep a reducer, or LangGraph raises InvalidUpdateError. Use Send for fan-outs sized at run time, and max_concurrency to stay under rate limits.

Check yourself

1. Three agents that each wait one second finish in about one second together. Why, and what does making nodes async not change?

The waits overlap; nothing runs faster. Edges from one source put nodes in the same superstep, and that is what makes them parallel. Making nodes async def adds overlap on one event loop but does not change which nodes are parallel, so a chain of async nodes still runs in order.

2. In the lab, moving the rewrite inside the credits node brings the answer from 3.4 s to 2.7 s. Where does the saving come from?

As its own node, rewrite finishes at 0.9 s, but credits cannot start until the superstep ends at 1.6 s, when export finishes. The outage branch waits 0.7 s at the barrier for work it does not depend on. Inside one node, every branch is one node long and that wait disappears.

3. The synthesizer writes a reply with nothing about outage credits, then runs a second time. What causes this, and how do you fix it?

The join uses separate edges, so it runs once for every superstep in which a predecessor finished; its first run saw 3 of 4 sub-answers. Use a list edge, add_edge([...], "synth"), when the predecessors are known at build time, or defer=True when branches are chosen at run time. A list edge never runs if a conditional edge skips one of its named nodes.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s support assistant now answers each part of a compound question in a parallel branch. Since the change, some replies to “refund, export and outage credits” questions say nothing about credits, and the trace shows two synthesizer outputs for one request. What happened, and how do you fix it?

What a strong answer covers:

  • Reads the trace by superstep: the outage branch has one more node (a query rewrite) than the others, so it finishes a superstep later
  • With separate edges into the synthesizer, the join runs once per superstep in which a predecessor finished: first with three sub-answers, then again with four. The reply that went out was the first
  • Fixes the join with a list edge (add_edge([...], "synth")) or defer=True, or keeps every branch one node long by moving the rewrite inside the agent
  • Adds a deterministic test with stub nodes that counts synthesizer runs and the sub-answers each run saw, so the fix stays fixed

2. Escalations ask for one of two follow-ups depending on what the incident log shows: a service-credit reply if availability fell below the SLA, a status-page reply otherwise. Would you build this as a fixed pipeline, a router or a blackboard?

What a strong answer covers:

  • A fixed pipeline cannot skip a step, so it runs both follow-ups on every escalation and pays for both
  • A router decides once, before any specialist has run, so it cannot branch on what the incident analyst finds
  • A blackboard controller re-reads the board after each post and can choose the credit branch only after the incident finding lands; that is the behaviour the request needs
  • Guards it: a Literal decision so the controller can only name a real node, a call cap enforced in code, a recursion limit as a backstop, and a computed check of which branches ran

3. You parallelised the four sub-question agents. Median latency fell, but p95 barely moved and the provider started returning rate-limit errors. How do you measure what is going on, and what do you change?

What a strong answer covers:

  • Wall time is the sum, over supersteps, of the slowest task in each, so p95 follows the slowest branch’s tail; logs per-node latency from the updates stream to find it
  • Caps concurrency (max_concurrency in the run config) to stay under the rate limit and measures what it costs: in the lab a cap of 2 takes the answer from 2.7 s to 3.7 s
  • Tracks time to the first streamed sub-answer separately from time to the final answer, since that is what the user sees first
  • Re-runs the golden set from the M11 baseline to confirm the faster path did not change answer quality

4. One of the four branches times out on a provider call. What happens to the three sub-answers that finished, and how should the assistant reply?

What a strong answer covers:

  • A task error fails the whole superstep; the synthesizer never runs on that attempt
  • With a checkpointer, LangGraph keeps the writes of the tasks that succeeded in that superstep, so a resume re-runs only the failed one
  • Adds a retry policy to the flaky node, and decides whether a missing sub-answer should block the reply or become an explicit “could not check outage credits” line the synthesizer must state
  • Alerts on the per-branch failure rate, since one flaky dependency now takes down every compound question that touches it

5. A product manager wants every refund answer to go through a three-round debate “so the assistant considers both sides”. What do you say?

What a strong answer covers:

  • A three-round debate costs 7 calls instead of 1; the notebook’s own advice is that a factual question with one correct answer is better served by a single call
  • Refund policy is a fact in the handbook; if two retrieved chunks disagree (an old and a new policy), the fix is version metadata and filtering at retrieval, not an argument
  • Debate earns its cost on real trade-offs, such as whether to replace RAG with a long-context prompt, where the transcript and the judge’s strongest point from each side are the deliverable
  • Proposes a test: run debate and single-call answers on the golden set and compare correctness, faithfulness, cost and latency before deciding

Key Takeaways

  • Choose the collaboration pattern by who decides the next step and when: fixed at build time (pipeline, STORM), shaped but overlapping (fan-out), or decided at run time (blackboard).
  • Give every LLM controller a typed decision, a call cap enforced in code and a computed check of what actually ran.
  • Parallel branches cost as much as the slowest task in each superstep; keep branches the same length, join with a list edge or defer=True, and put a reducer on every shared key.
  • Debate and STORM multiply calls by design. Count them, run the cheap baseline beside them, and keep them for trade-offs and research where the trail is the product.
