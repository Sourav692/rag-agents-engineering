M33 Conversation memory and conversational RAG

A chat model keeps nothing between calls. What looks like memory is the application sending earlier messages back with each new one, and in RAG the retriever needs that history as much as the model does. The M33 notebooks build on four ideas: the message history, the summary that keeps a long history affordable, the history-aware retriever that rewrites a follow-up before searching, and the checkpointer and thread_id that give a LangGraph agent the same memory per user.

Follow-ups and the retriever
Open the lab

The running example is the Larkspur Cloud support assistant answering from the same twelve handbook chunks as the M11 lab. Customers ask a first question and then follow up: Can I get a refund on my annual plan? then How long until the money is back?, or How do I export my data? then How long do I have? The lab runs six of these three-turn chats.

TL;DR

  • The model is stateless. Turn N of a chat that keeps everything sends 2N − 1 messages, so six turns send 36 messages in total, and cost grows with every turn.
  • A session_id (LCEL) or thread_id (LangGraph) picks whose history is loaded. The same chain or graph serves every user; the id is the whole isolation story, so it must come from your server, never from the user.
  • Bounding a history is a choice between forgetting and paying: a window or a token trim drops early facts for free, and a running summary keeps them in compressed form for one extra LLM call per fold.
  • A follow-up such as How long do I have? names no subject, so the retriever searches for the wrong thing. In the lab at k = 1, sending the latest message finds the evidence on 6 of 12 follow-ups; a rewritten standalone question finds it on 10.
  • Appending earlier questions to the query recovers turn 2 (5 of 6) but drowns a change of topic on turn 3 (1 of 6 at k = 1). The rewrite costs an LLM call per follow-up and cannot fix a vocabulary mismatch.

Mental model

One history feeds two consumers. The rewrite step reads it so the retriever searches for the real subject; the answer step reads it so the model can refer back. After the answer, both messages go into the history, keyed by the session, and the next turn starts from there.

Message history

Lesson 33.1: Why LLMs forget; classic memory classes. Notebooks: 01a_why_llms_forget.ipynb, 01b_classic_memory_classes_and_chains.ipynb (optional)

A chat model call is a function of the messages sent in that call and nothing else. Tell the Larkspur assistant I’m on the annual Team plan, then ask Which plan am I on? in a second call, and the second call receives only the question. The notebook shows the same thing with a name: the stateless chain prompt | llm | parser cannot answer What’s my name?.

The fix is to send the earlier turns back. A message history is the ordered list of typed messages that make up the conversation so far:

Type Who wrote it Stored in the history?
SystemMessage You, the developer: instructions for the model Usually not; the prompt adds it on every call
HumanMessage The user Yes
AIMessage The model Yes

Each turn appends the user’s message, sends the whole list, and appends the reply:

The notebook’s hand-rolled loop is the whole idea in four lines: append the HumanMessage, llm.invoke(history), append the reply, return it. InMemoryChatMessageHistory gives the same list a standard interface (add_user_message, add_ai_message, messages, clear) that file, SQLite and Redis backends share, which is what lesson 33.2 relies on.

The price is that a history which keeps everything resends everything. Turn N sends 2N − 1 messages: 1, 3, 5, 7, 9 and 11 over six turns, 36 messages in total, where six independent calls would send 6. Token cost and latency grow with the length of the conversation, and a long enough chat no longer fits the context window. Lessons 33.3 and 33.6 bound that growth.

The classic memory classes

Before RunnableWithMessageHistory and LangGraph checkpointers, LangChain packaged memory as classes that a chain loaded before each call and saved after it. The optional notebook runs them through the load, invoke and save loop. Forgetting the save step is the classic bug: the chain runs, and the next turn has no history.

Class What the prompt receives Keeps early facts Extra LLM calls Where the idea lives now
ConversationBufferMemory Every message Yes None A message history (this lesson)
ConversationBufferWindowMemory The last k exchanges (2k messages) No None A window or trim_messages (33.3, 33.6)
ConversationSummaryMemory One running summary Yes, compressed One per turn Summary memory (33.3)
ConversationSummaryBufferMemory Summary plus recent turns Yes, compressed When over max_token_limit Summary memory (33.3)
VectorStoreRetrieverMemory The past exchanges most similar to the question Only if retrieved None Long-term memory (M34)

Check yourself

1. A customer gives their plan in one call and asks for it in the next. Why can a stateless chain not answer, and what fixes it?

A chat model call depends only on the messages sent in that call, so the second call receives the question and nothing else. A message history fixes it: append each HumanMessage and AIMessage to an ordered list and send the whole list on every turn, so the earlier turn travels with the new question.

2. A history that keeps everything runs a six-turn chat. How many messages does turn 6 send, and how many over all six turns?

Turn N sends 2N − 1 messages, so turn 6 sends 11, and the six turns send 1 + 3 + 5 + 7 + 9 + 11 = 36 messages. Six independent calls would send 6. Token cost and latency grow with the conversation, which is why lessons 33.3 and 33.6 bound the history.

3. A legacy chain using ConversationBufferMemory runs without errors, but every turn behaves as if the conversation just started. What is the likely bug?

The save step is missing from the load, invoke and save loop. The classic memory classes load the history before each call and save the exchange after it; skip the save and the next turn loads nothing. New code avoids the manual loop with the patterns in lessons 33.2 to 33.6.

One history per session

Lesson 33.2: RunnableWithMessageHistory, multi-user sessions and persistence. Notebooks: 02a_runnable_with_message_history.ipynb, 02b_multi_user_sessions_and_persistence.ipynb

RunnableWithMessageHistory does the load and save of lesson 33.1 around any runnable. You give it the chain and a factory, get_session_history(session_id), that returns the history for one conversation. Every call then carries the id in its config:

chain_with_history.invoke({"query": "Which plan am I on?"},
                          config={"configurable": {"session_id": "cust-4821"}})

Two keys tell the wrapper where things go when the chain takes a dict. input_messages_key names the input that holds the new message (it is saved after the call), and history_messages_key names the MessagesPlaceholder that receives the stored history. The model then receives the system message, the history at the placeholder and the new question, in that order. A chain that returns a dict, like the retrieval chain of lesson 33.4, also needs output_messages_key to say which output to save as the AI message.

The session_id is the only thing that separates one customer’s conversation from another’s. In the notebook, two users talk to the same chain with their turns interleaved, and each one’s Summarize what we discussed sees only their own messages; a new session_id starts empty. Any string works: a user id, a chat id, or both combined, so one customer can hold several separate chats. Because whoever supplies the id chooses which history loads, take it from the authenticated session on the server, never from text the user can edit.

Where the history lives

Only the factory changes when the store changes; the chain and the wrapper stay the same.

Backend Survives a restart Many users Typical use
InMemoryChatMessageHistory in a dict No Yes, one per key Tests and notebooks
FileChatMessageHistory Yes One JSON file per session Single-user CLI or desktop tools
SQLChatMessageHistory Yes Yes, one table keyed by session_id Web apps and services

The notebook proves the database does the remembering. Run 1 stores a user’s preferences through one chain and deletes the chain object; four rows sit in the message_store table. Run 2 builds a brand-new chain with no Python-side state, and it still answers What’s my name? from those rows. Pass the database URL by keyword, SQLChatMessageHistory(session_id=..., connection="sqlite:///x.db"): the second positional argument is table_name, so the positional form creates no connection and fails only when invoked.

SQLite is fine for one process. For a service with concurrent writers, use the same interface on Postgres or Redis. These classes come from langchain-community, and RunnableWithMessageHistory is deprecated in langchain-core; lesson 33.6 does the same job with a LangGraph checkpointer, which is where new code should go.

Check yourself

1. Two customers send interleaved turns to the same chain wrapped in RunnableWithMessageHistory. What keeps their conversations apart?

The session_id in each call’s config. The wrapper passes it to get_session_history(session_id), which returns that conversation’s history, loads it before the call and saves the new messages after it. A new session_id starts empty, so each customer’s summary sees only their own turns.

2. A notebook prototype keeps histories in a dict of InMemoryChatMessageHistory. It must now serve a web app and survive restarts. What do you change?

Only the factory: return SQLChatMessageHistory keyed by session_id, and the chain and wrapper stay the same. The in-memory store loses everything on restart. For a service with concurrent writers, use the same interface on Postgres or Redis rather than SQLite.

3. SQLChatMessageHistory(session_id, "sqlite:///x.db") builds without complaint but fails on the first invoke. What went wrong?

The second positional argument is table_name, not the connection, so this form creates no database connection and fails only when invoked. Pass the URL by keyword: SQLChatMessageHistory(session_id=..., connection="sqlite:///x.db").

Summary memory

Lesson 33.3: Trimming, windowing and summary memory. Notebooks: 03a_trimming_windowing_and_summary.ipynb

A history that keeps everything grows on every turn (lesson 33.1). The cheap ways to bound it, a window or a token trim, drop the oldest messages, and the oldest messages are often the ones that set the context: the customer’s plan, their region, the account the ticket is about. Summary memory compresses those messages instead of dropping them. The prompt carries a short running summary of the older turns, written by a second LLM call, plus the most recent messages word for word.

The notebook keeps the last MAX_RECENT = 4 messages verbatim. After each answer it appends the exchange; when the recent list passes four messages, the oldest exchange goes to a summariser chain with the current summary, and the updated summary replaces the old one in the system prompt.

Over five turns of a Larkspur billing ticket, the prompt never holds more than one summary, four recent messages and the question. From turn 3 on, every turn folds one exchange, so the summariser runs three times in five turns. On turn 5 the customer asks which plan they are on; they said so in turn 1, which by then survives only in the summary. A window of the last two exchanges would hold turns 3 and 4 and could not answer.

The summary costs something too. Each fold is an extra LLM call, so on a short chat summary memory is no cheaper than keeping everything. It is lossy: names and decisions survive, exact wording does not, and a summariser can drop a fact you needed. And the summary grows a little with every fold, so the prompt is bounded only as long as the summariser keeps it short. Lesson 33.6 builds the same idea as a LangGraph node, and create_agent agents get it ready-made as SummarizationMiddleware.

Trim, window or summarise

trim_messages cuts a list to a token budget on the way to the model. The notebook’s settings keep the newest messages that fit (strategy="last"), always keep the system message (include_system=True), never cut a message in half (allow_partial=False) and make the kept part start on a user message (start_on="human"), so it reads as a conversation. It runs locally; the model is only the token counter.

On the notebook’s eleven-message chat, which counts 80 tokens with gpt-4o-mini’s counter, a 45-token budget keeps five messages (36 tokens): the system message and the last two exchanges. Bob’s name and his vanilla ice cream are gone. Add a question and the trimmer keeps four of twelve messages, so neither What ice cream do I like? nor What math problem did I ask? can be answered from the conversation: whats 2 + 2 falls outside the budget too. Those counts come from running the notebook’s trimmer with langchain-openai 1.7.3; another counter gives other cuts.

A window does the same job in storage. The notebook’s WindowedChatHistory keeps only the last k = 2 exchanges, so after My name is Paulo, I live in Seattle, I work as an AI engineer and I have 2 cats, the question What do you remember about me? sees only the job and the cats.

Strategy What the model receives Keeps early facts Extra LLM calls Stored history
Keep everything Every message Yes None Grows forever
Trim by tokens (trim_messages) Newest messages within max_tokens No None Complete; only the prompt is cut
Window of k exchanges Last 2k messages No None Only the window
Running summary Summary plus recent messages Yes, compressed One per fold Summary plus recent

Wrap a trimming chain in RunnableWithMessageHistory and the store keeps the full history while the model sees the trimmed part. That split between what is stored and what is sent is the question lesson 33.6 asks of a LangGraph thread.

Check yourself

1. On turn 5 of the Larkspur billing ticket, the customer asks for the plan they gave in turn 1. Why can summary memory answer when a two-exchange window cannot?

A window drops the oldest messages, so it holds only turns 3 and 4 and the plan is gone. Summary memory folds old exchanges into a running summary instead of dropping them, and turn 1’s plan survives there. The model sees the summary, the last four messages and the question.

2. The notebook's eleven-message chat counts 80 tokens. With a 45-token trim_messages budget, what does the model keep, and can it say which ice cream Bob likes?

It keeps five messages (36 tokens): the system message and the last two exchanges. Bob’s name and his vanilla ice cream fall outside the budget, so it cannot answer. Those counts depend on the token counter; another counter gives other cuts.

3. A team adds summary memory to a support bot whose chats rarely pass three turns, hoping to cut cost. Is that a good choice?

No. Each fold is an extra LLM call, so on a short chat summary memory is no cheaper than keeping everything, and it is lossy: exact wording does not survive and a summariser can drop a fact you needed. Keep everything while the chat fits the budget.

History-aware retriever

Lesson 33.4: Conversational RAG with history-aware retrieval. Notebooks: 04a_conversational_rag_with_history.ipynb

Lessons 33.1 to 33.3 gave the history to the model. In RAG the retriever reads the question too, and it reads only the literal text. How long do I have? contains one useful term, “long”, and no Larkspur handbook chunk contains it: every chunk scores zero. The model would receive the history, so it knows the customer means their data after cancelling, but the chunks it receives were chosen for a question with no subject. The notebook shows the same failure on Lilian Weng’s agents post: after What is Self-Reflection?, the follow-up How do we achieve it? retrieves chunks about “it”.

A history-aware retriever adds one step before retrieval. An LLM reads the chat history and the latest question and writes a standalone question, one that makes sense without the history, and the retriever searches for that. The notebook’s prompt tells the LLM to reformulate the question if needed, return it unchanged otherwise, and not answer it.

create_history_aware_retriever(llm, retriever, prompt) builds exactly this branch, so turn 1 costs no rewrite call. create_retrieval_chain then joins it to a stuff-documents chain whose prompt also carries MessagesPlaceholder("chat_history"), so the answer step sees the conversation as well. Wrapped in RunnableWithMessageHistory with output_messages_key="answer", the chain loads and saves the history itself (lesson 33.2).

Two failure modes come with the rewrite. It is an LLM call on every follow-up, which adds latency and cost before retrieval can start. And it can be wrong: it can drop a constraint the customer gave, or carry an old topic into a new question.

Rewrite, append or neither

The interactive lab runs six three-turn Larkspur support chats against the twelve handbook chunks from the M11 lab, with the same TF-IDF (it matches scikit-learn’s TfidfVectorizer to within 5e-16 on all 648 scores). It compares three things the retriever can receive on turns 2 and 3: the latest message as typed, the earlier questions with the latest appended, and a standalone rewrite. The customer messages are hand-written and the rewrites are representative, written by hand rather than generated; the rankings are real.

Retriever receives Turn 2 hits, k = 1 Turn 3 hits, k = 1 Hit rate, k = 1 Hit rate, k = 2
The latest message 2 / 6 4 / 6 0.50 0.58
Earlier questions + latest 5 / 6 1 / 6 0.50 0.92
A rewritten question 5 / 6 5 / 6 0.83 0.92
  • The latest message misses the turns that point back. What do I get if you miss it?, How long do I have? and Can I get money back on it? score zero against every chunk, and Is that possible after I cancel? finds the cancel chunk instead of the export evidence. Follow-ups that name their own subject, such as Do my promo credits expire?, hit either way.
  • Appending fixes turn 2 and breaks turn 3. Turn 2 usually continues turn 1’s topic, so the extra words help. Turn 3 often changes topic, and two earlier questions outweigh one new one: at k = 1 the old topic takes the only slot in 5 of 6 chats. At k = 2 appending catches up, by spending a context slot on the old topic every time.
  • The rewrite wins at k = 1 and pays for it with 12 LLM calls, one per follow-up. Its two misses are worth reading. How long until the money is back? misses whatever the query says, because the evidence chunk says “Refunds” and “business days” and no phrasing of the question uses those words; a rewrite restores the subject, not the handbook’s vocabulary, which is M11’s representation problem and the reason for embeddings (M14). And What happens if I cancel my annual plan instead of getting a refund? is a rewrite that carried too much history: “refund” and “annual plan” pull the refund chunk above cancel at k = 1.

The lab is the module’s lab brief in miniature. On your own corpus, write the multi-turn conversations, label the evidence for each turn, and report hit rate on turns 2 and 3 separately from turn 1, with and without the rewrite. A single average over all turns hides the follow-ups, because first questions are usually standalone.

Check yourself

1. The model receives the chat history, yet the follow-up How long do I have? retrieves nothing useful. Why, and what does a history-aware retriever add?

The retriever reads only the literal question, and its one useful term, “long”, appears in no handbook chunk, so every chunk scores zero. A history-aware retriever first has an LLM rewrite the latest message as a standalone question from the history, and the retriever searches for that. On turn 1, with an empty history, it skips the rewrite.

2. In the lab at k = 1, appending earlier questions hits on 5 of 6 turn-2 messages but only 1 of 6 on turn 3. Why the collapse?

Turn 2 usually continues turn 1’s topic, so the extra words help. Turn 3 often changes topic, and two earlier questions outweigh one new one, so the old topic takes the only slot in 5 of 6 chats. At k = 2 appending catches up to 0.92, but only by spending a slot on the old topic every time.

3. With the rewrite, How long until the money is back? still misses its evidence. Would a better rewrite prompt fix it?

No. The evidence chunk says “Refunds” and “business days”, and no phrasing of the question uses those words. A rewrite restores the subject, not the handbook’s vocabulary; that is a representation problem, which embeddings (M14) address.

Checkpointer / thread_id

Lesson 33.6: LangGraph threads, checkpoints and memory optimisations. Notebooks: 06a_memory_and_conversational_agent.ipynb, 06b_memory_optimizations.ipynb

A LangGraph graph keeps the conversation in its state, typically a messages channel with the add_messages reducer, so each node returns only its new messages and the reducer appends them. Compile the graph with a checkpointer and LangGraph saves a snapshot of that state, a checkpoint, after every step. The thread_id in the config names the sequence of checkpoints a run reads and extends:

graph = builder.compile(checkpointer=InMemorySaver())
graph.invoke({"messages": "How long do I have?"},
             config={"configurable": {"thread_id": "cust-4821"}})

This replaces RunnableWithMessageHistory and session_id from lesson 33.2, and LangChain recommends it for new code. The same compiled graph serves every user; the id decides which history comes back. In the notebook, user001 asks Explain AI in 1 line and then Do the same for ML, which only makes sense because the first turn is replayed; user002 talks on another thread, and user001’s memory is untouched when the conversation switches back.

Checkpoints are snapshots of every step, not just of the end of a turn. A turn writes one for the input, one at the start of the run and one per node step: a one-node chat graph writes 3 per turn, and the notebook’s tool-calling agent about 5 (two model calls and a tool call). get_state(config) returns the latest; get_state_history(config) walks all of them newest first, which is what replay, forking and debugging use.

Checkpointer Survives a restart Use
InMemorySaver No Notebooks and tests
SqliteSaver Yes, a plain SQLite file with checkpoints and writes tables One process; a context manager, so compile inside the with block
PostgresSaver (langgraph-checkpoint-postgres) Yes Deployments with concurrent writers

Two rules from the notebook. Short-term describes scope, not lifetime: a thread on SqliteSaver or PostgresSaver stays on disk until you delete it, so it is customer data with retention rules like any other. And the thread_id must come from trusted server-side config, never from user text, because whoever picks the id reads that thread.

Delete or hide

A thread that keeps everything sends every earlier message on every turn. The notebook runs one six-turn support ticket through four graphs. Counted in messages (the token counts vary per run), the model receives:

Turn Sequential Sliding window Trim on read Summary
1 1 1 1 1
2 3 3 3 3
3 5 3 3 summary + 1
4 7 3 3 summary + 3
5 9 3 3 summary + 1
6 11 3 3 summary + 3
Stored after turn 6 12 4 12 summary + 4

These counts come from running the notebook’s four graphs with a stub model in place of gpt-4o-mini; the graph logic decides them, not the model. Turn 3 asks What is my favorite color?, given in turn 1. Sequential can answer, and so can the summary graph if its summariser kept the colour; sliding window and trim on read cannot, since both send only the last MAX_MESSAGES = 3 messages.

The two bounded strategies send the same prompt and differ in what they keep:

  • Sliding window deletes. A truncate node returns RemoveMessage(id=...) for every message older than the window, and the add_messages reducer removes them from the checkpointed state. They are gone for every later turn, for get_state() and for anyone auditing the ticket. The reducer is the mechanism: operator.add can only append, so a deleting window needs add_messages.
  • Trim on read hides. The model node calls trim_messages on a copy of the list and leaves state alone, so the thread still holds all 12 messages, turn 1’s colour included. Trimming the prompt never trims the checkpoint: with SqliteSaver the full thread is written to disk on every step.

The summary graph keeps a summary string next to a buffer of recent messages. Once the buffer reaches MESSAGE_THRESHOLD = 4, a node folds all but the newest message into the summary and removes them, so it folds every other turn (turns 3 and 5 here) and each fold is an extra LLM call. Because summary has no reducer, any value written to it replaces the old one: pass {"summary": ""} only on the first turn, or each turn wipes the memory you are building.

For agents built with create_agent, LangChain 1.x ships the summary strategy as SummarizationMiddleware. M34 adds the memory a thread cannot hold: facts about a customer that should carry over to their next conversation.

Check yourself

1. The sliding-window and trim-on-read graphs both send the model the last three messages. What differs between them, and when does it matter?

The sliding window deletes: a truncate node returns RemoveMessage ids and the add_messages reducer removes them from checkpointed state. Trim on read hides: it trims a copy for the model, and the thread still holds all 12 messages. Pick trim on read when you need the full thread for audit or replay.

2. How many checkpoints does a one-node chat graph write per turn, and why more than one?

Three: one for the input, one at the start of the run and one per node step. Checkpoints snapshot every step, not just the end of a turn, so the notebook’s tool-calling agent writes about 5. get_state_history(config) walks them newest first for replay, forking and debugging.

3. A summary graph runs its folds, yet each turn starts with an empty summary. What is the likely cause?

The app passes {"summary": ""} on every turn. The summary channel has no reducer, so any value written to it replaces the old one and wipes the memory being built. Pass the empty summary only on the first turn.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. After a refactor, Larkspur’s assistant answers first questions well, but follow-ups like “How long do I have?” now cite billing chunks. Nothing in the retriever changed. How do you find the cause?

What a strong answer covers:

  • Logs the query the retriever actually received on each turn, next to the user’s message, before reading any prompt
  • Checks that history reaches the rewrite step: the session id in the config, the history_messages_key matching the placeholder, and an empty chat_history (which makes create_history_aware_retriever skip the rewrite and search the raw text)
  • Replays a follow-up golden set and compares hit rate on turns 2 and 3 with the last good release
  • Adds those follow-ups to the regression suite so the next refactor is caught by a number, not a customer

2. The rewrite step adds an LLM call, and its latency, to every follow-up. A teammate wants to drop it and append the chat history to the query instead. What do you tell them?

What a strong answer covers:

  • Appending is free and does recover elliptical turns: in the lab, turn 2 hits 5 of 6 either way
  • It fails on topic changes, because earlier questions outweigh the new one: 1 of 6 turn-3 hits at k = 1, against 5 of 6 with a rewrite
  • A larger k hides the problem by spending context slots on the old topic, which costs tokens and adds distractors
  • Middle ground: skip the rewrite on turn 1 and when a cheap check says the question is already standalone, use a small fast model for the rewrite, and measure latency against hit rate

3. How do you know, week by week, whether conversational retrieval is getting better or worse in production?

What a strong answer covers:

  • Logs per turn: turn number, raw message, rewritten query, retrieved chunk ids and scores, session id
  • Tracks retrieval quality split by turn number, since first turns hide follow-up regressions in an overall average
  • Samples rewrites for an LLM judge or human check: is the rewrite faithful to the history, and does it drop or invent constraints
  • Re-runs a frozen set of multi-turn conversations on every prompt, model or index change, as the M33 lab brief describes

4. A product manager wants the conversation id in the URL so customers can share a chat with a colleague. What is the risk, and how would you build it?

What a strong answer covers:

  • The thread_id or session_id is the only thing separating one customer’s history from another’s; whoever can choose it can read that history
  • Derives the id on the server from the authenticated user (or checks ownership before loading), never from request text
  • Builds sharing as an explicit, read-only copy or an access grant, with an audit entry
  • Remembers that a persistent checkpointer keeps the thread until it is deleted, so retention and deletion rules apply to it like any customer data

5. Support tickets now run to 60 turns, and prompt cost per turn keeps climbing. Which memory strategy do you pick, and what do you check before shipping it?

What a strong answer covers:

  • Full history sends every earlier message on every turn, so cost per turn grows without limit
  • A window or trim on read flattens the prompt but loses early facts such as the plan or the region; a running summary keeps them for one extra call per fold
  • Prefers trim on read or a summary over deleting messages, so the full thread stays available for audit and replay
  • Tests recall of an early fact on a late turn, and watches the summary channel: with no reducer, writing summary again on a later turn overwrites the accumulated summary

Key Takeaways

  • Memory is the list of messages you resend. Decide on purpose which ones go back, because every one costs tokens on every later turn.
  • Key every history by a session or thread id that your server controls, and choose a store that survives a restart before real users arrive.
  • Rewrite follow-ups into standalone questions before retrieval, and measure hit rate on turns 2 and 3, not only on first questions.
  • Bound long threads by hiding or summarising old turns rather than deleting them, and test that an early fact still reaches the model late in the thread.
