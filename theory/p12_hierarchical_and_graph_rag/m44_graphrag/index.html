M44 GraphRAG Techniques

Graph retrieval changes which evidence reaches the answer model. A question can start at one entity, follow a relationship to another passage, or ask for themes across communities. The M44 notebooks build on four ideas: community detection, global and local search, graph expansion, and the indexing work those choices require.

Expansion and the evidence set
Open the lab

The running example is the fictional Larkspur Cloud handbook. “Which export mechanism remains available after cancellation?” needs a connection between policy and product pages. “What dependencies recur across cancellation, exports and outages?” asks for a corpus overview. These questions need different retrieval plans, even when they share an index.

TL;DR

  • Decide what a node and an edge mean before calling a system GraphRAG. A similar pair of chunks, an extracted factual relation and a community membership support different inferences.
  • Local search starts near entities; global search uses community reports to cover the corpus. Choose using the question’s required evidence.
  • Expansion increases the candidate set. In the lab’s cancellation fixture, degree 0 returns 2 relations; degree 1 returns 4. Neither count measures answer accuracy.
  • Carry source passages through extraction, traversal and generation. A citation marker alone does not establish that its claim follows from its source.
  • Compare indexing, updates and query work on the same question set before replacing the flat retrieval baseline.

Mental model

Both routes must return evidence that the answer can cite. The graph supplies candidate connections; the source passages establish what the handbook actually says. Community reports add a summary layer whose omissions need checking against those passages.

Chunk graphs and traversal

Lesson 44.1: Concept-graph traversal. Notebooks: 01a_graph_rag.ipynb

The first notebook represents each chunk as a node in an undirected NetworkX graph. It splits documents with chunk_size=1000 and chunk_overlap=200, extracts concepts with a structured LLM response and named entities with spaCy, then compares chunk embeddings. An edge exists when cosine similarity is strictly greater than 0.8. Shared concepts influence the edge weight after that threshold has passed.

For chunks A and B, the code weights an edge as 0.7 × cosine + 0.3 × shared_fraction. The denominator of shared_fraction is the smaller concept-set size, with zero when that size is zero. This weight combines two signals chosen by the notebook author. It has no calibrated meaning as a probability that either chunk proves the other.

A Larkspur cancellation chunk and export chunk could share a product name while describing different dates or account states. The similarity edge is a retrieval lead. Read the passages before turning that lead into a policy statement.

The query path retrieves k=5 chunks from FAISS, compresses them with LLMChainExtractor, then tries to map their text back to graph nodes. Compression can change the text, so equality against the original chunk is fragile. Stable chunk IDs and an explicit mapping between compressed spans and original passages remove that ambiguity.

The traversal uses a heap, inverse edge weights and a model-based completeness check. Its implementation also appends neighbours immediately when discovered. It should not be described as an unmodified shortest-path algorithm. The initial seed priority uses 1 / similarity_score on a value returned by similarity_search_with_score; verify the backend’s score convention and zero handling before using it as a relevance priority.

Budgets and stopping

The code sets max_context_length=4000, but the traversal does not enforce that attribute. A variable named as a budget supplies no protection until a branch checks it. Count the accumulated context with the answer model’s tokenizer and stop before exceeding an explicit budget. Cap visited nodes and completeness-check calls separately.

An LLM saying “complete” is a stopping heuristic. For the cancellation question, check that the context contains the cancellation condition, available export mechanism and applicable retention condition. If the graph has no path to one of those passages, report the missing evidence. Increasing context cannot create a relation absent from the index.

For each query, log seed IDs, selected edges, retrieved source spans, context size and stopping reason. Compare against flat retrieval on the same golden questions. A longer traversal can increase work while leaving the answer’s supporting evidence unchanged.

Key Takeaways

  • A chunk graph links chunks whose cosine similarity passes a threshold and weights edges by similarity and shared concepts. The weight is a retrieval lead, not a calibrated probability.
  • A variable named as a budget protects nothing until code checks it. Count context with the answer model’s tokenizer and cap visited nodes and completeness checks separately.
  • Treat the model’s “complete” verdict as a heuristic. Check the required evidence is present, and log seeds, edges, context size and stopping reason against flat retrieval.

Source attribution

Lesson 44.2: Local GraphRAG with source attribution. Notebooks: 02a_graph_rag_local_attribution.ipynb (optional)

The optional local notebook uses Ollama for extraction and generation, all-MiniLM-L6-v2 for entity embeddings, and a directed NetworkX graph for relationships. Its Entity and Relationship records store source_doc and source_sentence. Query-time vector search finds entity entry points, then breadth-first traversal follows outgoing edges up to max_hops.

For Larkspur, a graph path might connect Cancellation to Export, then Export to Snapshot. The path explains why retrieval reached the snapshot document. The cancellation policy still needs a passage stating the conditions under which that snapshot export remains available.

Keep two records for each generated claim: the route by which retrieval found evidence, and the exact passage used to support the claim. A traversable relation can be stale, incorrectly extracted or disconnected from the conditions in the original text. Inspecting the source is how a reviewer can reject that relation.

What the notebook verifies

The example prompt asks for [N] references. The code finds those markers with a regular expression and maps valid IDs back to source records. It assigns each resulting Citation a fixed confidence=0.9, and its claim field contains a reference label rather than the extracted answer claim. That value is an example constant, not a measured confidence estimate.

The context supplied to generation contains entity names and descriptions. The stored source sentence is attached afterwards through the source map. The code therefore demonstrates provenance storage and citation resolution; it does not check entailment between every answer claim and the quoted sentence. Add a claim-to-span review before treating an answer as verified.

The graph also uses a single source record per entity ID. Re-ingesting the same lowercased name can overwrite its description and source. A DiGraph allows one edge for a given ordered node pair, so distinct relation evidence between the same pair can overwrite as well. Preserve multiple source spans and relation types when they carry separate claims.

Local execution boundaries

The notebook falls back to empty extraction results if Ollama is unavailable. An empty graph from that branch does not establish that the documents contain no relationships. Report model availability and extraction failures separately from a legitimate zero-result retrieval.

When using several seeds, verify distance budgets per seed. A single shared visited set can let an earlier seed suppress a shorter path from a later seed. Store the best depth or run a true multi-source breadth-first traversal when the required semantics are “within this many hops of any seed”. Retain source access filters during traversal and again when constructing context.

Key Takeaways

  • Keep two records per claim: the graph route that found the evidence, and the exact passage that supports the claim. A traversable relation can be stale or wrongly extracted.
  • Resolving [N] markers to sources proves provenance storage, not entailment. A fixed confidence value is a constant; add a claim-to-span review before calling an answer verified.
  • Report extraction failures separately from legitimate empty results, and keep multiple source spans and relation types when one node or edge would overwrite them.

Community detection

Lesson 44.3: Microsoft GraphRAG: communities, global vs local search. Notebooks: 03a_microsoft_graphrag.ipynb

An entity graph can group related regions before a question arrives. Community detection derives groups from graph connectivity. A community report then summarises the extracted material in a group. The grouping and its generated report are separate artifacts: changing the summary prompt changes the report without changing the graph partition.

For Larkspur, cancellation and export relations may form one region, while outage recovery relations form another. These are illustrative groups, not results of running a community detector on the handbook. Review extracted edges and group membership before interpreting a report as a reliable account of a product area.

Microsoft GraphRAG’s indexing pipeline extracts graph information, detects communities, builds reports at multiple levels and embeds text. That pipeline supplies reusable artifacts for query time. Microsoft indexing overview.

Global vs local search

Local search combines entity-related graph material with source text. Use it for “Which export mechanism remains available after cancellation?”: the evidence centres on specific entities and their conditions. Check that the selected context includes the original policy spans. Microsoft local search.

Global search addresses questions spread across the corpus by using community reports. The standard approach processes report context into partial responses, then combines useful results. Use it for “What operational dependencies recur across the handbook?” and inspect which report regions contributed. A fluent answer can still omit a small community or repeat an extraction mistake. Indexing cost

Flat RAG pays to split, embed and store passages. A graph pipeline adds extraction, identity resolution and relation storage. Community retrieval adds detection and report generation. Changes to source material can require rebuilding derived records, including reports that depend on the changed entities.

Record each stage separately. Useful fields include model and prompt version, input and output tokens, call count, retries, elapsed time, stored artifact size and changed source IDs. At query time record report selections, expansion candidates, reranking calls and answer context. The notebook configures a 10000 maximum context token setting for global search; that configured value is neither a measured bill nor proof that every execution uses the whole allowance.

Use the module lab brief’s shared global and multi-hop question set to compare GraphRAG, RAPTOR and hybrid retrieval. Hold source versions, answer model and evaluation criteria constant. Report indexing and update work alongside retrieval and answer quality. Derive any amortised cost from measured indexing work, measured query work and the actual expected query volume; no break-even figure follows from the architecture alone.

Key Takeaways

  • A community comes from graph connectivity and its report is a generated summary of it. Review edges and membership before trusting a report about a product area.
  • Use local search for questions about specific entities and their conditions, and global search for themes spread across the corpus. Inspect which reports contributed.
  • Graph pipelines add extraction, identity resolution, community detection and report generation to indexing. Record each stage’s tokens, calls and time, and derive cost from measurements.

Graph expansion

Lesson 44.4: Graph expansion inside a vector database (Milvus). Notebooks: 04a_graphrag_with_milvus.ipynb (optional)

The Milvus notebook stores entity, relationship and passage embeddings in separate collections. Vector retrieval chooses initial entity and relationship IDs. Adjacency mappings connect those IDs back to candidate relations and then to the passages that mention them. The graph traversal in this design runs in application memory; Milvus supplies vector retrieval and stored records.

Let B be the entity-by-relation incidence matrix. B[e,r]=1 when entity e participates in relation r. Then B Bᵀ connects entities that share a relation, while Bᵀ B connects relations sharing an entity. The notebook uses powers of these matrices to expand the seed sets, takes nonzero entries, and merges the entity and relationship retrieval paths. Milvus Graph RAG tutorial.

Matrix products count walks. They do not certify that a relation supports the user’s question. Their diagonal entries also permit a walk to remain at the same entity, so increasing the degree can retain previously reached candidates. Direction and relation type require separate handling: an undirected incidence matrix does not preserve a predicate’s direction.

The interactive lab computes the entity-side candidate row of (B Bᵀ)^d B. Degree 0 shows direct incident relations and is a teaching baseline; the notebook’s configured target_degree starts at 1. The explicit fictional fixture has no embedding or LLM output. Choosing a seed stands in for the preceding vector search.

With Cancellation selected, degree 0 reaches the cancellation-to-export and cancellation-to-billing relations. Degree 1 also reaches the export-to-snapshot and billing-to-refund relations. Those are 4 candidate relations across 3 distinct source passages. At degree 2 the set has 6 relations across 4 passages; degree 3 has all 8 relations across 5 passages. The lab labels every relation with its source so that expansion has a visible evidence cost.

The additional billing branch is reachable and can still be irrelevant to an export question. Rerank relations using the question, then fetch and deduplicate their source passages. Preserve the retrieval route for debugging, but cite the actual passage used by the answer. Compare the candidate set before and after reranking against the golden evidence set.

Keeping expansion bounded

The notebook retrieves top_k=3 entity and relationship hits, merges expanded candidates, uses an LLM to select relations and limits final passages with final_top_k=2. Those parameters control different stages. Increasing the first value can enlarge work even when the final context limit stays fixed.

Bound expansion degree, candidate relation count and source-passage count before an expensive reranker runs. If a hub connects many unrelated policies, filter by product, relation type, version and access rights before following it. Record which budget stopped the expansion so a missing passage can be attributed to a specific stage.

Treat identity mapping as part of retrieval correctness. Different casing, aliases and repeated names can split one entity or merge different entities. The notebook’s IDs come from string lists; an operational index needs stable IDs and explicit updates to both vectors and adjacency mappings. A fresh vector record with stale adjacency can retrieve the right entity and still traverse the wrong policy graph.

Key Takeaways

  • Vector search picks seed entities and relations; powers of the incidence matrix expand them. Products count walks and do not show that a relation answers the question.
  • Each expansion degree adds candidate relations and source passages. Rerank relations against the question and bound degree, relation count and passages before an expensive reranker runs.
  • Use stable IDs and update vectors and adjacency mappings together. A fresh vector with stale adjacency can find the right entity and traverse the wrong policy.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s cancellation answer reaches an export node but misses the retention condition. Where do you look first?

What a strong answer covers:

  • Inspect the retrieved seed IDs, traversed relations and final passage IDs before editing the prompt.
  • Check whether the retention relation was extracted, linked and reachable in the allowed direction.
  • Separate an expansion cutoff from a reranking or context-budget omission.
  • Add the complete policy path to the golden question’s evidence set and check its sources.

2. Support asks for themes across the whole handbook, but the current retriever returns only cancellation neighbours. How would you change retrieval?

What a strong answer covers:

  • Route the overview question to community reports with explicit corpus coverage.
  • Check which communities and report levels contributed to the answer.
  • Compare the overview against source passages and a flat baseline on the same corpus.
  • Retain local retrieval for questions about a specific product or policy condition.

3. GraphRAG improves an offline answer score but indexing is too expensive after every handbook edit. What would you measure?

What a strong answer covers:

  • Record extraction, embedding and report-generation work separately from query work.
  • Measure update frequency and which reports depend on each changed source.
  • Include failed calls, retries and storage in the comparison.
  • Compare amortised work over the actual question volume without assuming an unmeasured break-even point.

4. Two documents use “Snapshot” for different products, and the assistant joins their policies. How do you contain the error?

What a strong answer covers:

  • Inspect entity identity, product scope and version fields before increasing traversal depth.
  • Split ambiguous entities and preserve the source record for each relation.
  • Filter candidate passages and graph edges by the caller’s product and access rights.
  • Test a question where the wrong merge would produce a plausible answer with a false policy condition.

5. Every answer has numbered citations, yet reviewers keep finding unsupported claims. What would a useful attribution check do?

What a strong answer covers:

  • Split the answer into claims and resolve each reference to an existing source span.
  • Check that the span supports the claim and preserves its conditions and date.
  • Audit relation evidence as well as the final node’s description.
  • Treat fixed confidence values and valid citation syntax as insufficient evidence of support.

Key Takeaways

  • Name the graph representation and retrieval route in each evaluation result.
  • Bound expansion before context construction and measure the candidate set it creates.
  • Preserve passage provenance through both graph and community retrieval.
  • Re-evaluate source coverage, update work and answer quality whenever extraction or routing changes.
