M42 Hierarchical & Memory-Augmented Retrieval

A passage index finds local evidence. A question about the whole handbook may need a representation assembled from several passages before retrieval begins. The M42 notebooks build on four ideas: abstraction levels, collapsed-tree retrieval, global memory and dual-level retrieval.

Open the lab

Larkspur Cloud’s handbook supplies the running example. A customer asks how cancellation affects data access; an operations lead asks how the handbook manages service continuity. Both questions connect policies that live in separate sections. Source passages still decide what the answer may claim.

TL;DR

  • RAPTOR adds summaries at several levels to the retrieval corpus. Preserve their links to the passages they summarise.
  • Collapsed-tree retrieval ranks leaves and summaries together. Tree traversal chooses a route through parent-child links; these are different retrieval algorithms.
  • MemoRAG uses corpus memory to draft retrieval clues. Verify those clues against retrieved evidence before answering.
  • LightRAG separates entity-focused retrieval from retrieval over thematic relationships, then assembles graph context and source passages.
  • The lab uses four authored source passages and three representative summaries. At a two-node budget, the continuity query reaches one source identifier with leaves only and four through summary ancestry. These are fixture retrieval counts, not algorithm benchmark results.

Mental model

Derived representations can make distributed evidence easier to find. They also introduce another place to lose an exception, merge unrelated entities or preserve a deleted policy. Keep source identifiers and versions through every transformation so a retrieved summary can lead back to its evidence.

Abstraction levels

Lesson 42.1: RAPTOR: clustering and recursive summarisation. Notebooks: 01a_raptor.ipynb

An original passage preserves local wording. A summary combines claims across passages, and a summary of summaries describes a broader theme. These representations answer different questions. For Larkspur, an export procedure answers where to click; a cancellation summary connects export, retention and billing; a handbook overview can describe continuity across cancellation and outages.

The RAPTOR notebook repeatedly calls embed_texts, clusters the embeddings with GaussianMixture, and passes each cluster’s text to summarize_texts. build_raptor_tree(texts, max_levels=3) limits the recursion. The cluster count is min(10, len(current_texts) // 2), and fit_predict assigns each item one cluster. That is a teaching simplification: the RAPTOR paper describes soft clustering and distinguishes tree traversal from collapsed-tree querying.

Store a node’s level, source identifiers, source versions and child identifiers alongside its text. A summary may be accurate overall while omitting the one exception a customer asks about. For a policy answer, follow the summary back to passages before quoting a condition or number.

The notebook’s leaf metadata starts with level, origin and parent_id, but no id. Its summary child_ids are built with meta.get('id'), so first-level child references are missing. Do not treat this metadata as verified provenance. A single input item also makes the cluster-count expression zero; handle empty and singleton inputs before fitting a mixture model in a production implementation.

Collapsed-tree retrieval

Collapsed-tree retrieval puts original passages and summary nodes in one searchable pool. Embed the question, score every eligible node, and select context within a budget. The chosen mix of levels can change with the question. A top-down traversal instead selects parents first, then searches their descendants; an early wrong branch can exclude a relevant leaf.

The notebook’s build_vectorstore collects all levels and creates a FAISS store, which makes mixed-level search possible. Its later hierarchical_retrieval helper loops over levels and appends an AND id: string to the query. Appending text to an embedding query does not enforce a metadata filter or a parent-child join. Inspect the selected node identifiers and check filtering behaviour before calling that helper a constrained tree traversal. LLMChainExtractor then compresses retrieved documents, adding another transformation whose output needs source checks.

The interactive lab isolates the effect of adding summary nodes. Its four fictional passages and three authored summaries use real TF-IDF cosine scoring, with one vocabulary fitted over the whole fixture for a controlled comparison. Leaf-only mode filters out summaries; collapsed mode searches all nodes. These summaries are labelled representative, and no clustering or LLM runs in the browser.

Record indexing calls separately from retrieval and generation calls. Test precise facts, cross-section comparisons, changed policies and questions that the corpus cannot answer.

Global memory

Lesson 42.2: MemoRAG: global memory and clue-guided retrieval. Notebooks: 02a_memorag.ipynb (optional)

Corpus memory gives the retriever a view of the document collection before it searches for passages. For “How does Larkspur protect continuity?”, memory can suggest export, retention, availability and incident reports as clues. The final answer still needs source passages that support each claim.

The MemoRAG paper uses a long-range memory model to form a compressed corpus representation and draft clues for retrieval. A clue can contain an incorrect detail. Its job is to locate evidence; the generator must check the retrieved material.

The optional notebook implements a smaller approximation. MemoryStore.memorize asks a chat model for JSON topic and details pairs, validates them with Pydantic, embeds the resulting text and stores it in FAISS. These are readable text records, not the model’s attention key/value tensors. The prompt says it mimics KV-cache memory creation; distinguish that analogy from an actual compressed model cache.

At query time, create_retrieval_queries searches up to ten memory records, requests clue spans and surrogate questions, removes short candidates, and appends the original question. process_query retrieves three passages per query and deduplicates passage text before generating an answer. Each additional clue can add retrieval work and context; deduplication alone does not enforce a token budget.

Stage What to inspect Failure to test
Memorise Topic/detail records and parse failures An exception lost during extraction
Find memory Retrieved records and their source versions Stale or irrelevant memory dominates
Generate clues Exact clue text beside the original query A plausible clue invents a product
Retrieve Source identifiers, ranks and deduplication Repeated clues crowd out another policy
Answer Support for each claim The generator repeats an unsupported clue

The notebook’s duplicate check uses similarity_search("") to obtain existing topics. A nearest-neighbour result is a subset, so this does not enumerate the whole store or establish uniqueness. Use an explicit topic registry or stable record identifiers when implementing updates. It also returns None when no memory exists, while process_query iterates the result; an empty-memory fallback should retrieve with the original question.

Treat memory as derived data with dependencies. When Larkspur changes retention rules, update the source index and regenerate memory entries derived from those passages. Shared memory must not expose restricted documents through its summaries or clues. Test deletions against both stored memory and generated answers.

The optional notebook loads a prebuilt FAISS memory store and uses paid model calls. Reading it establishes the implementation shape; it does not establish a measured advantage on the Larkspur questions. Report any comparison only after running both pipelines on the same question set and budget.

Dual-level retrieval

Lesson 42.3: LightRAG: low-level and high-level graph retrieval. Notebooks: 03a_light_rag.ipynb

LightRAG searches for specific entities and broader relationships through separate routes. For “How does cancellation affect export?”, the low-level route can locate Cancellation and Export. The high-level route can locate a relationship profile about data portability. The two routes contribute evidence to one answer.

The LightRAG paper describes graph indexing with entity and relationship profiles, dual-level retrieval and incremental integration of new material. High-level retrieval searches thematic relationships; it does not mean searching RAPTOR’s upper summary levels or Microsoft GraphRAG community reports.

Combine these results with their source passages, deduplicate them and apply a context budget before generation. An edge description can help locate a policy, but it cannot replace the policy’s qualifiers.

The notebook builds this mechanism directly with NetworkX, Pydantic extraction schemas and two FAISS indexes. It does not invoke the packaged LightRAG library. Its PDF splitter uses chunk_size=1200 and chunk_overlap=150, then keeps the first twenty chunks for the demonstration. That cap limits the evidence available to every later graph query.

GraphExtraction returns entities and relationships. Entity names are normalised with strip().lower(). Node descriptions are merged; relationship descriptions and keywords are merged by endpoint pair. The graph is an undirected nx.Graph, so it cannot preserve a directed, typed multi-edge domain model without changes. Capitalisation and whitespace normalisation also cannot resolve two products with the same name.

Route Vector search target Graph expansion Source handling in the notebook
Low level Entity profiles Direct neighbours of selected entities Adds passages recorded for the entity
High level Relation profiles Endpoint entities of selected relations Adds passages recorded for the relation

lightrag_retrieve defaults to four entity hits and four relation hits. Those are seed counts, not a bound on the final context: a high-degree entity can add many edges. The low-level expansion adds incident edges to selected_edges, but does not add all of those edges’ source chunk identifiers to relevant_chunks. The returned relationship block can therefore contain an assertion whose source passage is absent. Join source identifiers for every selected assertion and test that invariant before relying on the answer’s provenance.

For Larkspur, preserve separate product identifiers, relation direction where it carries meaning, and source versions. Restrict graph expansion to authorised evidence. If a policy is withdrawn, recompute merged profiles as well as removing the source passage, since old wording can survive inside a node description.

To evaluate the two routes, run entity-only, relation-only and combined retrieval on the same precise and cross-section questions. Inspect answer support, source coverage and context size. Record extraction failures and indexing cost separately; a graph with plausible labels can still omit the relationship the question needs.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s assistant says cancelled accounts lose data immediately, although the source passage describes a retention window. The retrieved summary omits that window. How do you debug it?

What a strong answer covers:

  • Trace the summary to the exact source version and inspect whether summarisation dropped the exception
  • Inspect both the summary rank and the source passage rank before changing the answering prompt
  • Retrieve source evidence for precise policy claims and flag unsupported summary assertions
  • Add the cancellation question to the golden set and rebuild affected summary ancestors

2. Operations asks for themes across the handbook, while support asks exact policy questions. Would you force both through top-down tree traversal?

What a strong answer covers:

  • Compare traversal with collapsed search on both question types under the same context budget
  • Check whether choosing one high-level parent excludes a needed leaf early
  • Retain precise passages when summaries lack the required condition or number
  • Report indexing work and per-query quality separately instead of assuming a tree is faster

3. A new memory-assisted retriever returns fluent clues about a service Larkspur no longer sells. What should you monitor?

What a strong answer covers:

  • Log memory version, generated clues, retrieved source identifiers and final citations
  • Measure evidence recall and answer support separately from clue fluency
  • Invalidate derived memory when its source documents change or are deleted
  • Compare against original-query retrieval and fall back when clues find no supported evidence

4. Larkspur has two products with the same short name. Entity extraction merges them and connects the wrong cancellation rule. How should the graph change?

What a strong answer covers:

  • Use stable identifiers and product context instead of case-normalised names alone
  • Keep relation direction, qualifiers and source identifiers when the domain requires them
  • Inspect extracted assertions against passages before accepting a merge
  • Rebuild affected profiles and test an ambiguous-name query after the correction

5. A private incident report is deleted, but a global handbook summary still mentions it. What must deletion remove?

What a strong answer covers:

  • Follow dependency links through summaries, memory entries, graph descriptions and vector indexes
  • Remove or regenerate derived text that contains the report’s information
  • Apply access controls before derived evidence is exposed, including shared summaries
  • Verify with a deletion regression query and inspect stored representations as well as the answer

Key Takeaways

  • Choose a representation for the information need and compare it against the flat baseline.
  • A summary’s source coverage does not prove that every source fact survived compression.
  • Distinguish a paper’s algorithm from the simplified implementation in its teaching notebook.
  • Measure retrieval, source support, update work and generation quality separately.
