M43 Knowledge Graphs with Neo4j

A knowledge graph represents named entities and their relationships explicitly. Cypher matches those relationships; vector retrieval helps find a starting entity when a question uses different words. The M43 notebooks build on four ideas: the property graph, pattern queries, translating questions into Cypher, and combining graph facts with text retrieval.

Candidates and graph constraints
Open the lab

The running example extends the fictional Larkspur Cloud handbook into plans, features, regions and supporting passages. The golden questions ask which plans support exports in the EU, which source establishes that capability, and what happens after a policy version changes. The notebooks use healthcare, historical and extraction examples; the Larkspur catalogue is a separate teaching fixture.

TL;DR

  • Model identity, edge direction and source provenance before querying the graph.
  • Bind the same plan variable across feature and region patterns when both constraints must hold.
  • The 43.3 notebook executes hand-written Cypher; automatic text-to-Cypher is an explained extension.
  • Vector candidates can fail exact relationship checks. In the lab, k=2 yields no eligible plans, k=3 yields one and k=5 yields both.
  • A stored source link helps only when retrieval carries its passage into the answer evidence.

Mental model

Extraction turns prose into candidate facts. Stable identities let those facts connect across documents, while retained passages let a reader inspect what supports them. Retrieval must carry both the matched relationship and its supporting text into the answer.

Nodes, edges, properties

Lesson 43.1: Graph fundamentals and Cypher. Notebooks: 01a_kg_simple.ipynb

A property graph stores entities as nodes, typed directed relationships between them, and attributes on either. Larkspur can represent a plan as (:Plan {id: "eu-team"}), an export capability as (:Feature {id: "export"}), and their connection as (:Plan)-[:SUPPORTS]->(:Feature). The plan’s display name is a property; its stable identifier determines which entity it is.

Direction encodes meaning. Plan SUPPORTS Feature permits a different question from Feature DEPENDS_ON Service. Choosing relationship types is part of modelling the handbook, before any retrieval algorithm runs. A graph answers only relationships you stored or can derive from them; an absent edge can mean missing extraction rather than a false claim.

The introductory notebook creates a Person and related subjects, prizes and countries with MERGE, then queries the named relationship types. Its small example teaches the same modelling decision: choose labels, identity properties and edge directions before asking a question. Keep Larkspur’s invented teaching fixture separate from the notebook’s example facts.

Cypher

Cypher binds variables to matching graph patterns. To ask which Larkspur plans support exports in the EU, bind the same p in both patterns:

MATCH (p:Plan)-[:SUPPORTS]->(:Feature {id: $feature}),
      (p)-[:AVAILABLE_IN]->(:Region {id: $region})
RETURN DISTINCT p.id AS plan
ORDER BY plan

Pass feature="export" and region="eu" as parameters. Reusing p requires one plan to satisfy both facts. Independent plan variables would admit unrelated matches. DISTINCT removes repeated result rows; it does not repair duplicate entity identities in storage.

The notebook uses GraphDatabase.driver, sessions, session.execute_write and session.run. Keep a driver open for its intended lifetime, consume query results while their session is open, and close it when finished. Some notebook helper functions close the shared driver in finally; running cells out of order can therefore require recreating it.

For diagnosis, inspect the returned paths and their source facts before asking a model to phrase the result. A fluent answer cannot supply a relationship the query failed to match.

Check yourself

1. Why are relationship types and directions modelling decisions, and what can it mean when an expected edge is absent?

Direction encodes meaning: Plan SUPPORTS Feature permits a different question from Feature DEPENDS_ON Service, so you choose types before any retrieval runs. A graph answers only relationships you stored or can derive from them. An absent edge can mean the extraction missed it, not that the claim is false.

2. The EU export query reuses one variable p in both patterns. What goes wrong if each pattern binds its own plan variable?

Reusing p requires one plan to satisfy both facts: it supports export and it is available in the EU. Independent variables admit unrelated matches, such as one plan with export and another plan in the EU region. DISTINCT only removes repeated rows; it does not repair duplicate entity identities.

3. A model-phrased answer says no plan supports export in the EU, and you expected one. What do you inspect before the wording?

The returned paths and their source facts. A fluent answer cannot supply a relationship the query failed to match, so check whether the pattern matched the stored labels, directions and identifiers before asking a model to phrase the result.

Identity before import

Lesson 43.2: From CSV to knowledge graph. Notebooks: 02a_healthcare_kg.ipynb

The healthcare notebook reads healthcare.csv with csv.DictReader, creates provider, patient, specialisation and location nodes, then links them with TREATS, SPECIALIZES_IN and LOCATED_AT. The Larkspur equivalent imports plans, features, regions and the source documents that assert their connections.

A repeated import should preserve identities when a description changes. The notebook merges a provider on both name and bio, and a patient on several attributes. If a bio changes, that entire property pattern no longer matches. Use a stable key for identity and update descriptive properties separately. Neo4j’s MERGE documentation explains full-pattern matching and uniqueness constraints.

CREATE CONSTRAINT plan_id IF NOT EXISTS
FOR (p:Plan) REQUIRE p.id IS UNIQUE;

In a separate import query:

MERGE (p:Plan {id: $plan_id})
SET p.name = $name, p.updated_at = $updated_at

These are a proposed Larkspur schema, rather than cells copied from the healthcare notebook. Include tenant or catalogue scope in the key when the identifier is only locally unique. Validate missing keys before writing; a display name alone rarely captures that scope.

Import checks

Cast numeric and date fields explicitly when the query needs their types. DictReader provides text, so storing an age without conversion leaves a string. Match the endpoint entities before merging their relationship, and report rows whose endpoints are missing.

Check imported entity keys, relationship counts and a few known paths against the input. Re-run a small fixture with the same rows and then with an edited description. The entity count should stay fixed while the description changes. Keep a source document identifier and version on extracted assertions so that deleting an obsolete handbook edition does not leave unsupported plan capabilities behind.

Check yourself

1. The healthcare notebook merges a provider on both name and bio. Why does that break repeated imports?

MERGE matches the whole property pattern, so when a bio changes the pattern no longer matches and the import creates a second provider. Merge on a stable key, such as MERGE (p:Plan {id: $plan_id}), back it with a uniqueness constraint, and update descriptive properties separately with SET.

2. A CSV row links a plan to a region that is not in the graph. What should the import do with it?

Match both endpoint entities before merging the relationship, and report the row whose endpoint is missing instead of creating a link to nothing. Rows without a valid key go to quarantine before any entity is merged.

3. Larkspur deletes an obsolete handbook edition, but some plans still show capabilities that only that edition asserted. What did the import leave out?

A source document identifier and version on each extracted assertion. With them, deleting the edition also removes the assertions it supported; without them, unsupported plan capabilities stay behind.

Text-to-Cypher

Lesson 43.3: Natural-language graph QA (text-to-Cypher). Notebooks: 03a_query_kg_with_langchain.ipynb

Text-to-Cypher translates a question into an executable graph query, runs it, and phrases the returned rows as an answer. The schema must tell the model which labels, relationship types and properties exist. Larkspur’s question about EU export plans needs both the SUPPORTS and AVAILABLE_IN patterns, bound to the same plan.

The lesson notebook is narrower than its curriculum title. It calls Neo4jGraph.query with hand-written Cypher for provider counts, specialisations, locations and patients. It does not instantiate a query-generation chain. Read those queries as expected answers for a later translation test. Their healthcare examples are data-query exercises, not medical guidance.

The LangChain Neo4j integration documents GraphCypherQAChain and schema refresh. This is the extension beyond the checked-in notebook. After a schema change, refresh the schema used for generation and re-run questions that exercise the changed labels and properties.

Debug the query before the answer

Save the question, generated Cypher, parameters, returned rows and final answer as separate trace fields. If the answer is wrong, first compare the generated pattern with the hand-written reference. A misspelled relationship, reversed direction, missing region condition or wrong property key can produce an empty or misleading result without a syntax error.

Test valid paraphrases, an unknown entity, ambiguous plan names, a question requiring multiple relationships and an empty-result case. Grade the rows as well as the answer. An empty result should say that no matching facts were found under this schema and data version; it cannot establish that a capability is impossible.

Generated queries need database-enforced read permissions and bounded execution. Use a read-only principal, query timeout and result limits; a prompt instruction alone does not restrict database authority. LangChain’s chain security note explains that an opt-in flag acknowledges risk rather than enforcing permissions.

Check yourself

1. Why must Text-to-Cypher generation see the graph schema, and when must that schema be refreshed?

The schema tells the model which labels, relationship types and properties exist, so it can write a pattern that matches, such as SUPPORTS and AVAILABLE_IN bound to one plan. After a schema change, refresh the schema used for generation and re-run the questions that exercise the changed labels and properties.

2. A generated query returns no EU export plans, though the hand-written query finds one. What kinds of mistake would you look for in the generated Cypher?

Compare its pattern with the reference: a misspelled relationship, a reversed direction, a missing region condition or a wrong property key. Each can produce an empty or misleading result without a syntax error. Save the question, Cypher, parameters, rows and answer as separate trace fields so you can see where it went wrong.

3. A team relies on a prompt that says generate read-only queries, plus the allow_dangerous_requests flag. Is the database protected?

No. A prompt instruction does not restrict database authority, and the opt-in flag acknowledges the risk rather than enforcing permissions. Use a read-only database principal, a query timeout and result limits.

Graph + vector hybrid

Lesson 43.4: Vector indexes on graph nodes. Notebooks: 04a_vector_indexing_and_embedding.ipynb

Vector search finds candidates whose text resembles the question. Graph matching checks explicit relationships. A Larkspur plan can rank highly for “export in the EU” while lacking the EU availability edge. Keep candidate selection and relationship validation visible as separate stages.

The vector notebook creates an index on HealthcareProvider.comprehensiveEmbedding, configured for 1536 dimensions and cosine similarity. It embeds bio using genai.vector.encode, stores the property with db.create.setNodeVectorProperty, and queries with top_k=3. Those dimensions belong to that notebook’s configuration, not to every embedding model. Query and stored vectors must use the same model and dimensionality.

The notebook’s db.index.vector.queryNodes is the historical procedure used in its cells. Current Neo4j vector-index documentation prefers SEARCH on recent releases and marks the procedure deprecated from 2026.04. Check the deployed database version before copying syntax. Inspect SHOW VECTOR INDEXES and wait for ONLINE before searching.

A post-filter can return fewer than k results. Raising k gives the graph more candidates to check, with more work per request. It still cannot fix a missing relationship, an unresolved entity or a candidate outside the retrieved set. Treat authorization as a separate constraint applied throughout retrieval, rather than an optional relevance filter.

Candidate budget and exact constraints

The interactive lab uses a deliberately small fictional catalogue. It computes exact cosine ranking from hand-placed two-dimensional teaching vectors, then follows SUPPORTS and AVAILABLE_IN edges. These are illustrative vectors and invented catalogue records for the exercise, not model embeddings or a benchmark of Neo4j’s approximate index.

At k=2, no retrieved candidate has both required paths. At k=3, one qualifies; at k=5, both eligible records qualify. The candidate ledger shows excluded records as well as survivors, so an empty answer has an inspectable cause. The displayed recall divides surviving eligible records by every eligible record in this complete toy catalogue. Production recall needs independently labelled questions and answers.

Move the candidate budget before changing the schema. Once all eligible records are found, extra candidates add validation work without adding an eligible answer on this fixture. Compare that curve with the exact Cypher match over the full graph. A graph-first query can be preferable when the required constraints are precise and indexed; vector-first retrieval helps when the starting description is approximate.

Check yourself

1. Why keep vector candidate selection and graph relationship checks as separate stages?

Vector search finds text that resembles the question, while graph matching checks explicit relationships. A Larkspur plan can rank highly for “export in the EU” and still lack the EU availability edge. Keeping both stages visible shows which records were excluded and why.

2. In the graph filter lab, how many candidates survive the graph checks at k = 2, 3 and 5, and what does raising k past that buy?

None at k=2, one at k=3, and both eligible records at k=5. Once every eligible record is found, extra candidates add validation work without adding an answer on this fixture. Raising k cannot fix a missing relationship or an unresolved entity.

3. You copy the notebook's db.index.vector.queryNodes call to a new Neo4j deployment. What should you check first?

The database version: current Neo4j documentation prefers SEARCH on recent releases and marks the procedure deprecated from 2026.04. Check SHOW VECTOR INDEXES and wait for ONLINE before searching, and make sure query and stored vectors use the same model and dimensionality.

Extraction produces candidate facts

Lesson 43.5: LLM entity and relationship extraction. Notebooks: 05a_entity_relationship_extraction.ipynb, 05b_create_kg_from_text.ipynb (optional)

The extraction notebook asks an LLM for entities and relationship tuples, parses the response using ast.literal_eval, aggregates entities, and draws the graph with NetworkX. This demonstrates extraction and visualisation. It does not establish that every emitted tuple is supported by the text, nor does it persist that graph to Neo4j.

For Larkspur, “EU Team supports exports” can produce a Plan, a Feature and a SUPPORTS assertion. “EU Team may support exports after approval” needs its condition preserved. Flattening both sentences into an unconditional edge changes the policy.

Keep the passage identifier, source version and extraction configuration alongside accepted assertions. Validate endpoint types and allowed relationship types before insertion. Resolve aliases using identifiers and context: “Team” and “EU Team” might be separate products. A string set, as used for deduplication in the notebook, removes exact duplicate names but cannot resolve those identities.

Preserve relations and conditions

The notebook’s parser expects literal Entities: and Relationships: sections. Extra model commentary can break parsing. Structured output can constrain the response shape, but a schema-valid tuple still needs a support check. Handle malformed output as a failed extraction and retain the input for review.

Its line-based chunker uses a word threshold and can overshoot it when one line is long. Test boundary cases before assuming that threshold is a hard maximum. The optional exercise explicitly separates entity recognition, coreference resolution and relationship extraction; inspect pronouns and aliases at chunk boundaries when evaluating those stages.

A directed graph with one edge per ordered node pair can also overwrite distinct relationship labels between the same entities. Use a representation that preserves each assertion when the domain allows several predicates, versions or sources for a pair. Evaluate entity resolution errors separately from relation extraction errors, then check the paths used by your question set. A graph that looks plausible in a visualisation can still answer the wrong question.

Check yourself

1. Why does the page treat every extracted tuple as a candidate fact rather than an edge ready for the graph?

The extraction does not establish that every emitted tuple is supported by the text. Each one needs a support check against its passage, endpoint and relationship type validation, and entity resolution before it is stored with its passage identifier and source version. Even a schema-valid tuple from structured output needs the support check.

2. The handbook says EU Team may support exports after approval. What must extraction keep, and what happens if it does not?

It must keep the condition. Flattening the sentence into an unconditional SUPPORTS edge makes it identical to “EU Team supports exports”, which changes the policy.

3. A plan and a feature have two different stored predicates, but the graph shows only one. What caused the loss?

A directed graph with one edge per ordered node pair overwrites distinct relationship labels between the same entities. Use a representation that preserves each assertion when the domain allows several predicates, versions or sources for one pair.

Assemble retrieval with source evidence

Lesson 43.6: End-to-end knowledge-graph RAG. Notebooks: 06a_roman_empire_graph_rag.ipynb

The end-to-end notebook loads Roman Empire pages, splits the first three documents with TokenTextSplitter(chunk_size=512, chunk_overlap=24), converts chunks with LLMGraphTransformer, and calls add_graph_documents(include_source=True, baseEntityLabel=True). These are notebook settings, rather than measured optimums. Larkspur substitutes versioned handbook passages while retaining links from extracted entities to the source text.

Its retrieval has two combinations. First, Neo4jVector.from_existing_graph(search_type="hybrid") combines keyword and vector search over Document text, as described in the Neo4jVector integration. Separately, structured_retriever extracts question entities, resolves them through a full-text index, and fetches incoming and outgoing relationships. The final retriever concatenates these graph facts with retrieved document text.

The graph branch uses a full-text query with fuzzy terms, a limit of two entity candidates, and a final limit of fifty relationship rows. These are explicit caps, not relevance guarantees. Log which identity matched and which rows were truncated. A highly connected entity can consume the neighbourhood budget before the needed relationship appears.

Check the evidence contract

include_source=True retains source connections during ingestion; the notebook’s structured retriever excludes MENTIONS edges and returns relation strings. Those strings alone do not give the answer model a per-claim passage citation. To make a verifiable answer, retrieve the supporting passage identifiers and text alongside each graph assertion and carry them into the prompt.

Test a local entity question, a relationship join, a paraphrase whose entity name differs, an unsupported claim, and a changed handbook version. Compare vector-only retrieval, graph-only retrieval and their combination on the same questions. Report retrieved evidence, answer correctness, unsupported claims, latency and indexing work separately. No notebook output establishes that the combined system wins on Larkspur.

The notebook also rewrites conversational follow-ups before retrieval. Record the rewritten question, since a wrong resolved pronoun can send both retrieval branches to the wrong entity. Keep the original user question available when judging the final answer.

Check yourself

1. The end-to-end notebook combines two kinds of retrieval. What does each one contribute to the context?

Neo4jVector with search_type="hybrid" combines keyword and vector search over Document text. structured_retriever extracts the question’s entities, resolves them through a full-text index and fetches their incoming and outgoing relationships. The final retriever concatenates the graph facts with the retrieved text.

2. A question about a highly connected entity misses the relationship it needs. Which caps in the graph branch could explain it?

The branch keeps at most two entity candidates and fifty relationship rows, and a highly connected entity can use up the neighbourhood budget before the needed relationship appears. These caps are not relevance guarantees, so log which identity matched and which rows were truncated.

3. Ingestion ran with include_source=True. Can the answer model cite a passage for each graph claim?

No. The structured retriever excludes MENTIONS edges and returns relation strings, which carry no per-claim citation. Retrieve the supporting passage identifiers and text alongside each graph assertion and carry them into the prompt.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s EU export plan disappears after a handbook update, although its passage still exists. How do you locate the failure?

What a strong answer covers:

  • Checks ingestion version, entity key and the required feature and region paths.
  • Separates a missing graph edge from a candidate that fell below the vector budget.
  • Reads the extraction input and supporting passage before changing the prompt.
  • Adds the updated plan and previous version to the fixed regression questions.

2. Product wants both a free-text search and exact regional availability. Would you retrieve vectors first or match the graph first?

What a strong answer covers:

  • Uses exact graph predicates when identity and constraints are known.
  • Uses semantic candidates for approximate descriptions and validates their graph relationships.
  • Measures eligible-answer recall against candidate budget, query latency and graph degree.
  • Applies authorization across every retrieval branch and checks all returned source passages.

3. The assistant returns a convincing answer from an empty Cypher result. What should monitoring record?

What a strong answer covers:

  • Logs original question, rewritten question, generated query, parameters and rows separately.
  • Grades query results against known paths as well as grading final answer support.
  • Tracks empty-result and truncation rates by question type and schema version.
  • Requires an explicit unsupported-answer response when the available facts cannot answer.

4. A CSV re-import doubles the number of plans after descriptions change. How do you repair the import design?

What a strong answer covers:

  • Inspects which mutable properties were included in the merge pattern.
  • Uses a stable scoped identifier with an appropriate uniqueness constraint.
  • Updates descriptions separately and resolves existing duplicates with source-aware review.
  • Tests repeated imports and edited descriptions on a fixture before loading the full catalogue.

5. A generated query asks for a plan relationship that is absent from the schema. Should the system retry until it finds an answer?

What a strong answer covers:

  • Checks whether the requested relation is representable and present in the current schema.
  • Bounds retries and query execution, with read-only database permissions.
  • Distinguishes a translation error from missing source data and ambiguous identity.
  • Returns the evidence limitation rather than inventing a relation to satisfy the request.

Key Takeaways

  • Choose stable entity identities and explicit relationship meanings before import.
  • Compare generated Cypher with a hand-written query and inspect rows before grading prose.
  • Separate semantic candidate selection from exact graph validation and measure both stages.
  • Retrieve source passages with graph assertions so each answer claim can be checked.
