M39 Building MCP Servers & Clients

M38 connects one client to one server. M39’s projects grow that into a client that holds several servers at once, a client written by hand against the SDK, and servers that answer over HTTP. The projects are runnable code in projects/, not notebooks. They build on four ideas: one client in front of several servers, the session each connection lives in, the older HTTP transport with a stream and a separate POST endpoint, and the newer one with a single endpoint.

Open the lab

The running example is the module’s lab brief applied to Larkspur Cloud, the fictional host whose handbook runs through M11 to M13: a support assistant with two MCP servers. handbook wraps a retriever over the handbook (search_handbook), and status stands in for web search over Larkspur’s status pages (search_status, canned results, no network). The golden questions are How long does a refund take?, which belongs to the handbook, and Is there an outage right now?, which belongs to the status pages. Every count on these pages was recorded by driving those two servers through the installed SDK: mcp 1.30.0 and langchain-mcp-adapters 0.3.2.

TL;DR

  • A multi-server client keeps one session per server and merges their tools into one list for the model. Tool names must be unique across servers; tool_name_prefix=True turns search into handbook_search.
  • A session is one initialize handshake followed by requests over the same transport until it closes. Over stdio a session is a server process.
  • MultiServerMCPClient.get_tools() opens a new session for every tool call. Over stdio, 8 calls start 10 server processes and send 38 JSON-RPC messages; one held session per server needs 2 processes and 14 messages.
  • SSE keeps a GET /sse stream open for every reply and answers each POST with 202 Accepted. Streamable HTTP answers each POST on /mcp itself and ties requests together with an mcp-session-id header.
  • stateless_http=True drops the session id, the server-to-client stream and the closing DELETE: 8 held calls cost 14 HTTP requests instead of 18, and the server keeps nothing between requests.

Mental model

The client is the only piece that knows there are two servers. The model sees one list of tools, and each call goes back down the session of the server that listed the tool. Everything in M39 is about the middle column: how many sessions there are, how long each one lives, and what carries its messages.

What comes back from a server

Lesson 39.1: Single-server MCP, with resources. Notebooks: 01_single_server_mcp, 02_single_server_mcp_with_resources

Both projects build one FastMCP weather server and a LangGraph client that talks to it over stdio. Project 01 gives the server a tool, get_weather, and a prompt, compare_weather_prompt. Project 02 swaps the prompt for a resource, file://delivery_log, which reads nine order lines from delivery_log.txt. Lesson 38.5 explains who chooses each kind; this page is about what each one returns, because the client has to handle every shape.

Recorded with SDK 1.30.0 against copies of the two servers, with no API key set:

Request What the client gets
tools/call get_weather {"location": "Dublin"} One text block holding {"error": "OpenWeatherMap API key is not configured on the server."}, with isError: false
prompts/get compare_weather_prompt One message, role: "user", the filled-in instructions; both arguments are required
resources/list One resource, listed as file://delivery_log/ with a trailing slash, MIME type text/plain
resources/read file://delivery_log One text block holding a JSON array of the nine lines

Three things in that table catch people out.

  • An error returned as data is a success. get_weather catches every failure and returns a dict with an error key, so the result carries isError: false and the model reads the message as weather data. A tool that raises is reported differently: a Larkspur search_handbook that raises ValueError("index not loaded") comes back with isError: true and the text Error executing tool search_handbook: index not loaded, and langchain-mcp-adapters turns that into a ToolMessage with status="error". Raise when the call failed; return data when it worked.
  • A list becomes one JSON string. The resource function returns list[str], and FastMCP serialises it as one text block, not one block per line. The client joins the text blocks it receives and pastes the result into a message, so the model sees a JSON array.
  • The return type decides the schema. get_weather is typed -> dict, and FastMCP lists it with no outputSchema, so the result has no structuredContent either. A typed return, such as a Pydantic model, gives the client a schema to check results against.

The project 03 copy of the server ships with OPENWEATHERMAP_API_KEY = "{{OPENWEATHERMAP_API_KEY}}". The guard only rejects an empty key or the literal YOUR_OPENWEATHERMAP_API_KEY, so the placeholder passes, the API answers 401, and the tool returns {"error": "Authentication failed…"}, again as a success.

The client decides what reaches the model, and the two projects do it differently:

A prompt’s text goes to the agent as if the user had typed it. A resource goes in wrapped as CONTEXT … TASK: <what you asked>, or with a request to acknowledge it and keep it in memory when you give no task; the MemorySaver checkpointer keeps it for the rest of the thread. Both servers read files and are started by relative path (python weather_server.py, Path("delivery_log.txt")), so the client only works when it is run from the project folder.

For Larkspur, the same rules give one decision per feature. search_handbook raises when the index is missing and returns chunk ids and text otherwise; the refund policy can be a resource a support engineer attaches by hand; and a prompt like M38’s answer_with_citations is something the engineer starts on purpose.

Multi-server

Lesson 39.2: Multi-server MCP. Notebooks: 03_multi_server_mcp

Project 03 puts the weather server next to a second one, a task server whose add_task and list_tasks tools keep a to-do list in tasks.txt. The client names both in one dict and hands it to MultiServerMCPClient from langchain-mcp-adapters:

server_configs = {
    "weather": {"command": "python", "args": ["weather_server.py"], "transport": "stdio"},
    "tasks":   {"command": "python", "args": ["task_server.py"],    "transport": "stdio"},
}
client = MultiServerMCPClient(server_configs)
all_tools = await client.get_tools()   # one flat list: get_weather, add_task, list_tasks

The keys, weather and tasks, are the client’s names for the servers. The model never sees them. It gets one list of tools, bound to the LLM with bind_tools, and a LangGraph ToolNode runs whichever one it picks. When the model calls add_task, the adapter sends the call to the server that listed it.

Three rules follow from the flat list.

  • Names must be unique across servers. ToolNode indexes tools in a dict by name (langgraph 1.2.18), so if two servers both offer search, the one loaded last answers every call and nothing warns you. MultiServerMCPClient(..., tool_name_prefix=True) renames each tool <server>_<tool>, which gives weather_get_weather and tasks_add_task here. Lesson 38.4 shows the same collision in a hand-written client.
  • Descriptions do the routing. The model chooses by name and description alone; server boundaries are invisible to it. For Larkspur, search_handbook says it searches the handbook’s policies and search_status says it searches live status pages, so Is there an outage right now? lands on the status server. If both said “search Larkspur information”, the model would have to guess.
  • Every tool costs tokens on every call. All definitions from all servers go to the model each turn, as M38 measures. Connect the servers an agent needs, not every server you have.

Project 02 under lesson 39.4 builds the same thing by hand: a config.json with an mcpServers block, one stdio_client and ClientSession per entry on an AsyncExitStack, and load_mcp_tools(session) for each. Its two servers run in Docker. The config.json entries start each one with docker run -i --rm …, where -i keeps standard input open so stdio works through the container, and the client starts a fresh container for every session. docker-compose up only needs to build the two images: the containers it also starts sit with their input open and are not the ones the client talks to. Replace the placeholder /ABSOLUTE/PATH/TO/… volume path in config.json with your own first; as shipped, it mounts a folder that does not exist.

The second server there is MCP’s reference fetch server: one fetch tool that returns a page as Markdown, 5,000 characters at a time by default, with a start_index for the next slice, and a robots.txt check before it fetches on the model’s behalf. It is the web-search half of the module’s lab brief.

When one server fails

get_tools() loads every server at once with asyncio.gather, so the first server that fails raises and no tools load at all. Recorded with a working handbook server and a status entry whose command does not exist:

  • await client.get_tools() raised FileNotFoundError for the status command, and returned nothing for the healthy handbook server.
  • await client.get_tools(server_name="handbook") returned search_handbook.

The hand-built client in project 02 wraps each server in its own try, prints Connection failed for <name>, and starts with the tools it got. Neither is right by default. A Larkspur assistant can answer refund questions with the status server down, so it should start degraded and say which tools are missing; an agent whose every task needs both servers should refuse to start. Load per server, record which ones failed, and put that list in the system prompt and the logs.

Failures during a call are a separate case. A tool that raises comes back as isError: true, and the adapter returns it to the model as a ToolMessage with status="error" so the agent can try something else. A dead process or a dropped connection is not a tool error: the adapter raises, and the agent run stops unless your code catches it.

Client sessions

Lesson 39.4: Your own client and a multi-server client. Notebooks: 01_build_your_own_server_client, 02_multi_server_client

Every client in these projects is built from the same three layers, each an async context manager:

transport = await stack.enter_async_context(stdio_client(params))   # or sse_client(url), streamable_http_client(url)
read, write = transport[0], transport[1]
session = await stack.enter_async_context(ClientSession(read, write))
await session.initialize()                                           # the handshake
tools = (await session.list_tools()).tools
result = await session.call_tool("execute_shell_command", {"cmd": "ls"})

The transport moves bytes: pipes to a child process, or HTTP. ClientSession speaks JSON-RPC over it. initialize() sends the client’s protocol version (2025-11-25 in SDK 1.30.0) and capabilities, reads the server’s, and sends the notifications/initialized notification. From then on the session carries requests until the AsyncExitStack closes, which closes the session and then the transport: a stdio server process exits, and a Streamable HTTP client sends DELETE.

A session is the unit of state in MCP. The protocol version, the capabilities and anything the server ties to the connection live for one session. Over stdio a session is also a process, because the client starts one server process per connection. That makes the question of how long a session lives the main design choice in a client.

Project 02 holds one session per server for the life of the agent, on one AsyncExitStack. MultiServerMCPClient.get_tools() in project 03 does not hold any. Its docstring says it plainly: “A new session will be created for each tool call”. Each tool call opens a session, initializes it, calls the tool and closes it. With SDK 1.30.0 a fresh session also sends tools/list after the call, because call_tool checks the result against the tool’s output schema and a new session has not listed its tools yet.

The interactive lab drives the two Larkspur servers through both clients over every transport and shows each recorded message. For 8 tool calls:

Transport Held sessions A session per call
stdio 2 processes, 14 messages 10 processes, 38 messages
SSE 14 messages, 16 HTTP requests 38 messages, 48 HTTP requests
Streamable HTTP 14 messages, 18 HTTP requests 38 messages, 58 HTTP requests
Streamable HTTP, stateless 14 messages, 14 HTTP requests 38 messages, 38 HTTP requests

Held sessions pay 6 messages once (an initialize, a notification and a tools/list per server) and then 1 per call. A session per call pays 4 per call. Over stdio the cost is also processes: 8 calls were answered by 8 different server processes, so a cache, a loaded index or a counter in server memory starts empty every time. Over HTTP the server process stays up, so its memory survives, but nothing tied to a session does.

To keep the convenience of MultiServerMCPClient and hold the session, open it yourself:

client = MultiServerMCPClient(connections)
async with client.session("handbook") as session:
    tools = await load_mcp_tools(session)        # calls reuse this session
    agent = create_agent(model, tools)
    ...

A session per call is the right choice in one case: a stateless server behind several replicas, where any request may land anywhere and holding a session buys nothing. Everywhere else, hold one session per server and reopen it when it drops.

A client written by hand

Project 01’s client.py connects Gemini to the terminal server without LangChain, which shows the work an adapter does for you. After the handshake it lists the server’s tools and turns each into a Gemini FunctionDeclaration: the MCP name, the description and the inputSchema with every title key removed. FastMCP’s schema for get_weather in lesson 39.1 shows what gets stripped: "title": "get_weatherArguments" on the object and "title": "Location" on the property.

Then each query runs one round:

That is one round, not a loop. If the second reply asks for another tool, the client does not run it and returns only the first part’s text. It also sends execution_result.content, a list of MCP content objects, as the function response, where a plain string or dict would be safer. langchain_mcp_client.py in the same project replaces all of it with two calls: load_mcp_tools(session) converts the tools and create_react_agent(llm, tools) runs the loop until the model stops asking for tools. In langgraph 1.2.18 create_react_agent is deprecated in favour of create_agent from langchain.agents, which M24 uses.

The terminal server these clients drive runs any shell command the model writes, with shell=True and the working directory set to ~/Desktop/github/langgraph-ai/mcp/01-build-your-own-server-client/workspace, a path from the author’s machine. Point it at a folder of your own before running it, and treat the tool as remote code execution: project 02’s copy runs it inside a container, which limits what a bad command can reach.

SSE

Lesson 39.5: Transports: SSE and streamable HTTP. Notebooks: 03_sse_transport_server_client, 04_streamable_http_client

Lesson 38.6 compares the two HTTP transports side by side. Project 03 builds the SSE one by hand, which shows how it works. The server is a Starlette app with two routes around the SDK’s SseServerTransport:

sse = SseServerTransport("/messages/")
routes = [
    Route("/sse", endpoint=handle_sse),             # GET: one long-lived stream per session
    Mount("/messages/", app=sse.handle_post_message),  # POST: every message the client sends
]

handle_sse hands the stream to the low-level server, mcp._mcp_server.run(...), which serves one session for as long as the GET stays open. FastMCP builds the same app for you with mcp.run(transport="sse") or mcp.sse_app().

The POST never carries an answer. Every request gets 202 Accepted, and its result arrives later as an event on the GET stream, matched by JSON-RPC id. Recorded with SDK 1.30.0 on the two Larkspur servers with held sessions, setup took 4 requests per server (the GET and three POSTs) and each tool call 1 more, so 8 calls made 16 HTTP requests. Nothing closes the session but the stream: when the GET ends, the server drops the session id. That puts the whole session on one long-lived connection, which a proxy that closes idle connections will cut.

The project’s code has five problems to fix before you copy it:

  • handle_sse returns None. The SDK’s own example in mcp/server/sse.py returns Response() after the stream ends and says why: without it, a client disconnect raises TypeError: 'NoneType' object is not callable.
  • No host checks. The app builds SseServerTransport with no security settings, so DNS-rebinding protection is off. FastMCP turns it on by itself when the host is 127.0.0.1 or localhost.
  • An open shell on every interface. It binds 0.0.0.0:8081 by default, and run_command runs any command with shell=True and no timeout.
  • A README that describes another server. It lists execute_shell_command with a command parameter and promises “command validation”; the code defines run_command and add_numbers and validates nothing.
  • Two workspaces. The Docker instructions mount the workspace at /workspace, while the code runs commands in /root/mcp/workspace.

Streamable HTTP

Project 04’s temperature server is a FastMCP server on one endpoint, /mcp:

mcp = FastMCP("Temperature Converter", host=host, port=port, stateless_http=True)
...
mcp.run(transport="streamable-http")

The comment beside stateless_http=True in the project says it enables the streamable HTTP protocol. It does not: transport="streamable-http" in run() picks the transport, and stateless_http, in the words of FastMCP’s settings, decides “if the server should create a new transport per request”. Stateful is the default. The two modes cost this, recorded on the Larkspur servers with held sessions:

Stateful (default) stateless_http=True
Setup, per server 4 requests: initialize (the reply sets mcp-session-id), the initialized notification (202), a GET for the server’s own stream, tools/list 3 requests: initialize, the notification, tools/list
Each tool call 1 POST, answered as an event stream 1 POST
Close, per server DELETE /mcp nothing
8 calls, 2 servers 18 requests 14 requests

Each POST gets its own answer in the response, as text/event-stream by default or JSON with json_response=True. The mcp-session-id header ties a stateful client’s requests together, and the server checks it on every request. Probed against a stateful Larkspur server in SDK 1.30.0:

  • A GET /mcp without text/event-stream in Accept gets 406 “Not Acceptable: Client must accept text/event-stream”. Project 04’s server_launcher.py uses exactly this as its health check, treating a 406 as “the server is up”.
  • A tools/list POST with no session id gets 400 “Bad Request: Missing session ID”.
  • A session id the server does not know, such as one from another replica or one that expired, gets 404 “Session not found”, and the client has to initialize again.

Stateful sessions expire after 1,800 seconds with no request in flight, and one server holds at most 10,000 at once; both are FastMCP settings (session_idle_timeout, max_sessions). Stateless mode has neither, and no server-to-client stream either, so the server can only speak in answer to a request.

Project 04’s client mixes transports behind one agent. config/servers.json lists the temperature server as "type": "http" with a URL and the terminal server as "type": "stdio" with a command, and Google ADK’s MCPToolset opens each with the matching connection parameters (StreamableHTTPServerParams, StdioConnectionParams). That is the module’s mental model in one file: the agent sees one tool list, and each tool goes back over its own server’s transport.

Choosing a transport

  • stdio for a server on the same machine that the client starts and owns: a desktop assistant’s file tools, a local retriever over the handbook. No network, no auth, and a process per session.
  • SSE only to reach a server that speaks nothing else, such as M38’s deployed research server. It needs two endpoints and one long-lived GET per session.
  • Streamable HTTP, stateful for a shared server that keeps something per client or sends messages between requests. With several replicas, route by mcp-session-id.
  • Streamable HTTP, stateless for tools that keep no per-client state and must scale out: Larkspur’s status search can run as many replicas as it needs, and any of them can answer any request.

Lesson 39.3’s Databricks server ends with mcp.run(). In SDK 1.30.0 run() defaults to transport="stdio", so as written the server reads its standard input instead of listening for HTTP. A server that a platform reaches by URL needs transport="streamable-http" and must listen on the host and port the platform expects.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s assistant moved from held sessions to MultiServerMCPClient.get_tools() to simplify the code. Since then the handbook server’s in-memory embedding cache never hits, and p95 latency has doubled. What happened?

What a strong answer covers:

  • get_tools() in langchain-mcp-adapters 0.3.2 opens a new session for each tool call, and over stdio each session is a new server process, so the cache dies with every call
  • Confirms it from the wire, not the code: count initialize requests and server process starts per tool call (one each, against zero with held sessions)
  • Fixes the client by holding sessions, async with client.session("handbook") and load_mcp_tools(session), or moves the server to HTTP, where the process outlives the session
  • Moves the cache out of process memory if it must survive restarts anyway, and adds a check on the setup cost per call to the latency dashboard

2. The status server runs as three replicas behind a load balancer, with stateful Streamable HTTP. Some tool calls fail with 404 “Session not found”. What is going on, and what do you change?

What a strong answer covers:

  • A stateful session lives in the memory of the replica that answered initialize; a request with that mcp-session-id routed to another replica gets 404, and the client must initialize again
  • Two fixes: sticky routing on the mcp-session-id header, or stateless_http=True so any replica can answer any request
  • Stateless costs: no server-to-client stream, so the server cannot push notifications between requests, and nothing per session survives; fine for a search tool that keeps no state
  • Also checks the idle timeout (1,800 seconds by default in SDK 1.30.0) and the 10,000-session cap, since both end sessions the client still believes in

3. How would you monitor the MCP layer of the assistant in production, separately from the model?

What a strong answer covers:

  • Logs per tool call: server name, transport, session id, latency split into session setup and the call itself
  • Tracks the ratio of initialize requests to tools/call requests; it should be near zero with held sessions, and a jump to one means a client started opening sessions per call
  • Counts HTTP status codes per server (202 on SSE, 404 for lost sessions, 406 from clients sending the wrong Accept header) with middleware like the lab’s recorder
  • Alerts when a server’s tools/list changes, because the model’s routing depends on the names and descriptions it lists

4. At startup the status server’s container fails to pull. With MultiServerMCPClient, the assistant does not start at all, though the handbook is fine. With the hand-built client from project 02, it starts with handbook tools only. Which behaviour do you want, and how do you get it?

What a strong answer covers:

  • get_tools() loads every server with asyncio.gather, so one failed server raises and no tools load; project 02 wraps each server in its own try and keeps going
  • Decides per server: a support assistant can answer handbook questions without status, so start degraded, but say so in the system prompt and in the UI
  • Loads servers one by one with get_tools(server_name=...) or per-server sessions, records which failed, and retries them in the background
  • Tests it: a golden question per server, run with each server down, checking the assistant says it cannot reach status instead of guessing

5. A teammate deploys the SSE project’s server on a VM to share it with the support team. It binds 0.0.0.0:8081 and offers run_command. What do you flag before it goes live?

What a strong answer covers:

  • Anyone who reaches the port can open a session and run any shell command: shell=True, no authentication, no timeout (the stdio version at least has 30 seconds)
  • The README promises command validation the code does not have, and the app is built by hand from SseServerTransport with no security settings, so DNS-rebinding protection is off
  • Replaces the shell with narrow tools (search_handbook, not run_command), binds to localhost behind an authenticating proxy, and runs the process in a container with a read-only file system
  • Moves to Streamable HTTP with FastMCP’s own app, so host and origin checks come with the server, and adds the server to the team’s security review like any other API

Key Takeaways

  • Give each server one session and hold it for the life of the agent. A session per call costs a handshake every time, and over stdio a process, and loses whatever the server kept in memory.
  • Merge tools from several servers into one list only after checking names: prefix them by server, and give each a description that says which questions it answers.
  • Pick the transport by where the server runs: stdio for a local subprocess, Streamable HTTP for anything shared, and stateless mode when replicas must answer any request.
  • Treat an MCP server that runs commands as a remote shell. Narrow tools, authentication and a sandbox come before the first deployment.
