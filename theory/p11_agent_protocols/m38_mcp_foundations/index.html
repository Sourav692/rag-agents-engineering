M38 MCP Foundations

M38 takes the tool-calling chatbot apart. The tool code and its schemas move into an MCP server, the chatbot keeps its loop and talks to the server through an MCP client, and from then on any client can reuse the server and the chatbot can plug in servers it did not write. The M38 notebooks build on four ideas: a server and a client that share one session, the three things a server can offer (tools, resources and prompts), the reference servers you add from a config file, and the transports that move a server off your machine.

The golden question is the M11 one, How long does a refund take? Every message, schema and status code quoted here was recorded from real runs with MCP Python SDK 1.30.0, the version in the course’s protocols dependency group.

TL;DR

  • An MCP server owns the tools; the chatbot keeps the loop. The client launches a stdio server as a subprocess, opens one session per server, sends initialize (protocol version 2025-11-25 in SDK 1.30.0), then tools/list and tools/call as the model asks.
  • FastMCP builds each tool definition from the Python function: the function name, the whole docstring as the description, and a JSON schema from the type hints. The Args: lines stay inside the description; no parameter gets a schema description of its own.
  • Tools are for the model to call. Resources and prompts are for the application and the user: the lesson 7 chatbot reads a resource when the user types @topic and fetches a prompt on /prompt.
  • Every connected server’s tools go to the model on every call. The notebook’s three servers send 17 definitions, about 2,527 tokens, and the filesystem server is 80% of that. Two filesystem servers send 14 names twice, and the chatbot routes all 14 to the second one.
  • Remote servers run on their own and the client connects by URL. Streamable HTTP uses one endpoint, /mcp, and an mcp-session-id header; the older SSE transport uses a stream at /sse plus POSTs to /messages/.

Mental model

The client and the server agree on a protocol version and capabilities once, then the client lists what the server offers. The model sees only the tool definitions; it never talks to the server. When it asks for a tool, the chatbot hands the call to the session that owns that tool, and the result goes back to the model as a tool result. Swap the server for another and the chatbot code does not change.

What moves out of the chatbot

Lesson 38.1: From a tool-calling chatbot to MCP. Notebooks: 01a_chatbot_example.ipynb, 01b_chatbot_example_openai_walkthrough.ipynb (optional)

Notebook 01a builds the chatbot the rest of the module takes apart. It has two tools, search_papers (query arXiv and save the results to papers_info.json under a topic folder) and extract_info (look a paper up by id in those files), and every tool needs three things written by hand in the chatbot:

  1. The function that does the work.
  2. A schema in the tools list: a name, a description and an input_schema that the model reads to decide when and how to call it.
  3. An entry in mapping_tool_function, so execute_tool can turn the name the model picked back into a Python call and the result into a string.

Around them sits the loop in process_query: send the question and the tools list to the model (claude-3-7-sonnet-20250219, max_tokens=2024), and while the reply contains a tool_use block, run the tool, append a tool_result with the same tool_use_id, and call the model again.

MCP keeps the loop and moves the rest. In notebook 03a the chatbot has no tools list and no mapping; both come from the server.

Piece 01a: inside the chatbot 03a: with MCP
Tool functions Defined in the notebook In research_server.py, behind @mcp.tool()
Tool schemas Written by hand in tools Fetched with session.list_tools()
Name to function mapping_tool_function and execute_tool session.call_tool(name, arguments=...)
The loop and the model process_query, chat_loop Unchanged, now methods of MCP_ChatBot

The split pays off as soon as a second chatbot, an IDE or an agent framework wants the same tools: each of them speaks MCP to the same server instead of copying three pieces per tool. For Larkspur Cloud, the M11 retriever becomes one server, larkspur-handbook, and every assistant the support team builds connects to it.

The optional notebook 01b runs the same chatbot on OpenAI. Only the wrapper changes: each schema sits inside {"type": "function", "function": {...}} with parameters in place of input_schema, and the arguments arrive as a JSON string the code parses with json.loads. The tools and the loop are the same, which is why the server in lesson 38.2 can serve either provider.

From a function to a tool definition

Lesson 38.2: Building an MCP server. Notebooks: 02a_creating_an_mcp_server.ipynb

A server that offers tools answers two requests: list the tools, and call one. The MCP Python SDK gives two ways to build it. The low-level Server makes you handle ListToolsRequest and CallToolRequest yourself. FastMCP, which notebook 02a uses, does it for you: create the server, decorate functions, run it.

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("research")

@mcp.tool()
def search_papers(topic: str, max_results: int = 5) -> List[str]:
    """
    Search for papers on arXiv based on a topic and store their information.
    ...
    """

if __name__ == "__main__":
    mcp.run(transport="stdio")

The notebook writes this file with %%writefile, so the cell saves the server instead of running it; the server starts later from a terminal or from a client. On stdio the server reads requests from its standard input and writes replies to its standard output, one JSON-RPC message per line.

FastMCP builds the definition from the function. Here is what SDK 1.30.0 sends for search_papers in reply to tools/list, recorded from the notebook’s server and printed as the dict the chatbot builds:

{
  "name": "search_papers",
  "description": "\n    Search for papers on arXiv based on a topic and store their information.\n    \n    Args:\n        topic: The topic to search for\n        max_results: Maximum number of results to retrieve (default: 5)\n        \n    Returns:\n        List of paper IDs found in the search\n    ",
  "input_schema": {
    "properties": {
      "topic": {"title": "Topic", "type": "string"},
      "max_results": {"default": 5, "title": "Max Results", "type": "integer"}
    },
    "required": ["topic"],
    "title": "search_papersArguments",
    "type": "object"
  }
}
Part of the definition Where FastMCP takes it from
name The function name
description The whole docstring, indentation and Args: block included
Property types and required The type hints; a parameter with a default is optional
default The Python default (max_results = 5)
Property descriptions Nothing: the Args: lines stay in the description

Compare it with the schema notebook 01a wrote by hand. That one gave each parameter a description (“The topic to search for”) and a one-line tool description. The generated pair is 989 characters of compact JSON against 611 for the hand-written pair, and the model reads the parameter help only as free text inside the description. When a parameter needs help or limits, put them in the type: with Annotated[int, Field(description="Number of chunks to return", ge=1, le=12)], SDK 1.30.0 adds description, minimum and maximum to that property.

FastMCP also infers an output schema from the return type. For the Larkspur search_handbook tool, which returns str, the definition carries "outputSchema": {"properties": {"result": {"title": "Result", "type": "string"}}, "required": ["result"], "title": "search_handbookOutput", "type": "object"}, and every call returns the text twice: once in content and once in structuredContent. The notebook’s chatbot passes only result.content to the model, so the copy costs bytes on the wire and nothing in the prompt.

Test a server before writing a client. The MCP Inspector launches it the way a client would, npx @modelcontextprotocol/inspector uv run research_server.py, and lets you list and call tools by hand. If a tool works in the Inspector and fails in the chatbot, look in the client first.

Check yourself

1. Where does FastMCP take each part of a tool definition from, and where do the docstring's parameter descriptions end up?

The name comes from the function name, the description from the whole docstring, the types and required from the type hints, and default from the Python default. Nothing fills the property descriptions: the Args: lines stay inside the tool description, so the model reads parameter help only as free text.

2. The Larkspur search tool needs a chunk count between 1 and 12 that the model can see in the schema. How do you declare it?

Put the help and the limits in the type: Annotated[int, Field(description="Number of chunks to return", ge=1, le=12)]. SDK 1.30.0 then adds description, minimum and maximum to that property. An Args: line in the docstring would only add free text to the tool description.

3. A tool works when you call it by hand in the MCP Inspector but fails inside your chatbot. Where do you look first?

In the client. The Inspector launches the server the way a client would and calls the tool directly, so a pass there shows the server and the tool work. Test the server in the Inspector before writing a client, so this split is available when something breaks.

MCP server / client

Lesson 38.3: Building an MCP client. Notebooks: 03a_creating_an_mcp_client.ipynb

MCP names three roles. The host is the application the user talks to, here the chatbot with its LLM. The client is the piece inside the host that holds one connection to one server. The server offers tools, resources and prompts. A host that uses three servers holds three clients, and the model never talks to any server directly: it sees definitions and asks for calls, and the host decides which client sends them.

Notebook 03a wraps the 38.1 loop in an MCP_ChatBot class and adds the client:

server_params = StdioServerParameters(command="uv", args=["run", "research_server.py"], env=None)

async with stdio_client(server_params) as (read, write):      # starts the server as a subprocess
    async with ClientSession(read, write) as session:          # one session, one server
        await session.initialize()
        response = await session.list_tools()
        self.available_tools = [{"name": t.name, "description": t.description,
                                 "input_schema": t.inputSchema} for t in response.tools]
        await self.chat_loop()                                 # calls session.call_tool(...)

With stdio the client owns the server’s life: stdio_client starts the process, and leaving the async with block ends the session and stops it. Nothing has to be running beforehand.

Here is the session the client opens against the Larkspur handbook server, recorded over stdio with SDK 1.30.0. Sizes are the compact JSON of each message.

Message Direction What it carries Size
initialize request client to server protocolVersion: "2025-11-25", the client’s capabilities (none) and clientInfo 152
initialize result server to client the agreed version, capabilities for tools, resources and prompts, serverInfo 276
notifications/initialized client to server no id and no reply: the session is open 54
tools/list request client to server nothing but the method 46
tools/list result server to client one definition, search_handbook, with input and output schemas 608
tools/call request client to server {"name": "search_handbook", "arguments": {"query": "How long does a refund take?"}} 135

Three details in that trace matter when you debug:

  • The handshake fixes what the session can do. The server declared tools, resources and prompts, each with listChanged: false, so this client will not be told if the tool list changes; it has to list again.
  • Requests and replies pair by id. The client numbers its requests 0, 1, 2 and the server echoes the id; the notification carries none because nothing answers it.
  • serverInfo.version was 1.30.0, the SDK version, because the server did not set one. Pass a version of your own if clients should be able to tell your releases apart.

The client also translates for the model. Notebook 03a’s live code runs on OpenAI and wraps each MCP definition as {"type": "function", "function": {"name": ..., "description": ..., "parameters": tool.inputSchema}}; the Anthropic version kept in comments uses input_schema: tool.inputSchema. Both read the same inputSchema, so one server serves either model. On the way back the Anthropic version passes result.content as the tool_result, and the OpenAI version passes result.content[0].text as the tool message.

Check yourself

1. A host uses three MCP servers. How many clients does it hold, and does the model ever talk to a server directly?

Three clients, each holding one connection to one server. The model never talks to a server: it sees definitions and asks for calls, and the host decides which client sends them.

2. In the recorded Larkspur session, the notifications/initialized message gets no reply. How do replies pair with requests, and why is this message different?

Requests and replies pair by id: the client numbers its requests 0, 1, 2 and the server echoes the id. notifications/initialized is a notification, so it carries no id and nothing answers it; it tells the server the session is open.

3. The server's tool list changes while a client is connected, and the client keeps offering the old list. What in the handshake explains this?

The server declared its capabilities with listChanged: false in the initialize result, so this client will not be told when the list changes. The handshake fixes what the session can do. The client has to call tools/list again to see the change.

Reference servers

Lesson 38.4: Connecting to reference servers. Notebooks: 04a_connecting_to_reference_servers.ipynb

The modelcontextprotocol/servers repository holds reference implementations you can run without writing a line of server code. Notebook 04a adds two of them to the research server: fetch reads a URL and returns it as Markdown, and filesystem reads and writes files under the folders you allow. The chatbot stops hard-coding its server and reads a config file instead:

{
  "mcpServers": {
    "filesystem": {"command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "."]},
    "research":   {"command": "uv",  "args": ["run", "research_server.py"]},
    "fetch":      {"command": "uvx", "args": ["mcp-server-fetch"]}
  }
}

npx and uvx download and start a published server in one step, so nothing is installed ahead of time. The last filesystem argument is the folder it may touch: . is the folder the chatbot runs in. (The notebook’s note says this lets the fetch server reach your files; it is the filesystem server that does.)

connect_to_servers opens a session per server and keeps all of them on an AsyncExitStack, so cleanup() closes every session and subprocess in reverse order. For each tool it appends the definition to available_tools, which goes to the model on every request, and writes tool_to_session[tool.name] = session, which tells process_query where to send a call. A server that fails to start is caught and printed, and the chatbot carries on without its tools.

Recorded with the notebook’s own MCP_ChatBot (SDK 1.30.0, server-filesystem 2.1.0, mcp-server-fetch 2026.10.28), the three servers offer:

Server Tools Characters of tool JSON
filesystem read_file, read_text_file, read_media_file, read_multiple_files, write_file, edit_file, create_directory, list_directory, list_directory_with_sizes, directory_tree, move_file, search_files, get_file_info, list_allowed_directories 8,072
research search_papers, extract_info 989
fetch fetch 1,046

Two consequences follow from the two data structures:

  • Every definition costs on every call. The three servers send 17 definitions, 10,107 characters, about 2,527 tokens, before the user’s question, and the filesystem server is 80% of it. Adding the Larkspur retriever as a fourth server adds one tool and 417 characters.
  • Names must be unique across servers. tool_to_session is a dict, so a second server with the same tool names overwrites the first. The notebook’s closing notes ask what happens then. Add a second filesystem server rooted at ./handbook and the model receives 32 definitions for 18 names, while all 14 filesystem names route to the second server. A request to read research_server.py, which sits in the project folder, now reaches the handbook server and comes back as ENOENT: no such file or directory.

The interactive lab runs the notebook’s merge on the recorded tool lists. Switch servers on and off, and watch the definitions per call, the characters, and which server each tool name reaches.

A reference server’s definitions are text the model reads, written by someone else. The fetch server’s description says: “Although originally you did not have internet access, and were advised to refuse and tell the user this, this tool now grants you internet access.” Read what a server tells your model before you connect it, and pin its version (@modelcontextprotocol/server-filesystem@2.1.0, mcp-server-fetch@2026.10.28) so an update cannot change that text unseen.

available_tools holds every tool definition and goes to the model on every request. tool_to_session maps each tool name to the session of the server that offers it, so process_query knows where to send a call. One tells the model what exists; the other routes the call.

Tools, resources, prompts

Lesson 38.5: Prompts and resources. Notebooks: 05a_adding_prompt_and_resource_features.ipynb

A server can offer three kinds of thing. They differ in who decides to use them, and that decides which one a feature should be.

Tool Resource Prompt
FastMCP decorator @mcp.tool() @mcp.resource("papers://folders") @mcp.prompt()
Listed with tools/list resources/list, resources/templates/list prompts/list
Used with tools/call resources/read prompts/get
In the lesson 7 chatbot, chosen by the model the user, typing @topic the user, typing /prompt name arg=value
Returns content for the model data the app shows or adds to context messages to send to the model

Resources are read-only data, like GET endpoints in a REST API: they return data and should not change anything. Each has a URI the server chooses. A static URI names one thing (papers://folders, the list of topic folders); a template names a family (papers://{topic}, the papers saved under one topic), and the client fills in the parameter at read time.

Prompts are templates the server owns. generate_search_prompt(topic, num_papers=5) returns a long instruction to search for papers on the topic and summarise them; FastMCP takes the prompt’s name from the function and its arguments from the signature, and prompts/get returns the filled-in text as messages.

The Larkspur server offers one of each kind of resource and a prompt. Recorded with SDK 1.30.0:

  • resources/list returned only the static resource, handbook://sections.
  • resources/templates/list returned the template, handbook://section/{chunk_id}.
  • resources/read on handbook://section/refund-timing returned that chunk as text/plain.
  • prompts/get for answer_with_citations with question = "How long does a refund take?" returned one message with role: "user" whose text asks the model to call search_handbook and cite chunk ids.

The lesson 7 chatbot routes user input before the model sees it:

/prompts only prints the list. A prompt fetched with /prompt goes to process_query like a typed question. A resource is printed for the user and never reaches the model in this chatbot; another host could add it to the context instead. Two details in the chatbot’s code are worth knowing before you copy it:

  • It lists only static resources. connect_to_server calls list_resources(), which does not return templates, so papers://{topic} never enters the routing table. get_resource works around it: for an unknown papers:// URI it uses any session that has a papers:// resource. With two servers using that scheme it picks the first.
  • One dict routes all three kinds. self.sessions maps tool names, prompt names and resource URIs to sessions, so a prompt named like another server’s tool overwrites the route, the same collision the lab in lesson 38.4 shows for tools.

For Larkspur the split is: search_handbook is a tool, because the model needs it mid-answer with a query it writes; the sections are resources, for a support console that lets an engineer attach a section; and answer_with_citations is a prompt the engineer starts on purpose.

Check yourself

1. What decides whether a server feature should be a tool, a resource or a prompt?

Who decides to use it. The model chooses a tool mid-answer through tools/call. The user chooses a resource, read-only data fetched with resources/read, and a prompt, a server-owned template fetched with prompts/get; in the lesson 7 chatbot that means typing @topic or /prompt name arg=value.

2. Why is search_handbook a tool on the Larkspur server, while the handbook sections are resources and answer_with_citations is a prompt?

The model needs search_handbook mid-answer with a query it writes, so it is a tool. The sections are data a support console lets an engineer attach (handbook://sections and the template handbook://section/{chunk_id}), so they are resources. answer_with_citations is something the engineer starts on purpose, so it is a prompt.

3. The lesson 7 chatbot never puts the papers topic template in its routing table. Why, and how does reading a topic still work?

connect_to_server calls list_resources(), which returns static resources but not templates, so papers://{topic} never enters the table. get_resource works around it: for an unknown papers:// URI it uses any session that has a papers:// resource. With two servers using that scheme, it picks the first.

Remote transport

Lesson 38.6: Remote servers and deployment. Notebooks: 06a_creating_and_deploying_remote_servers.ipynb

A stdio server is a subprocess: the client starts it, owns it, and talks over its standard input and output. A remote server is a process of its own, often on another machine, that must already be running when the client connects by URL. The tools, resources and prompts do not change; with FastMCP only the last line does:

mcp = FastMCP("research", port=8001)   # notebook 06a
...
mcp.run(transport="sse")               # or "streamable-http", or "stdio"

Notebook 06a deploys over SSE because, when the course was filmed, Streamable HTTP was still being built into the Python SDK; it adds notes for Streamable HTTP. SDK 1.30.0 ships both. Recorded against the Larkspur server running each way (initialize, list tools, one tools/call, close):

SSE Streamable HTTP Streamable HTTP, stateless_http=True
Endpoints GET /sse, then POST /messages/?session_id=… /mcp for everything /mcp
Reply to a request 202 Accepted; the answer arrives on the /sse stream 200 with the answer in the response (text/event-stream) 200 with the answer
Session id in the query string mcp-session-id header, set on the initialize reply none
Close close the stream DELETE /mcp nothing to close

After initialize, every request in the stateful run carried two headers: mcp-session-id (32 characters) and mcp-protocol-version: 2025-11-25. The session id is what lets a stateful server remember a client between requests; it is also why a stateful server behind several replicas needs sticky routing, while a stateless one can answer from any replica and cannot keep anything between calls.

Paths and names to get right in SDK 1.30.0:

  • Defaults. FastMCP listens on 127.0.0.1:8000, with SSE at /sse and /messages/ and Streamable HTTP at /mcp. The notebook’s port=8001 still works as a constructor argument.
  • The URL. The notebook says to append /mcp/. The server answers POST /mcp/ with 307 and a Location of /mcp; the 1.30.0 client follows a same-origin 307 for a POST, so either works, and /mcp saves the round trip.
  • The client function. The notebook imports streamablehttp_client. In 1.30.0 it is marked deprecated with “Use streamable_http_client instead.”; the new one takes the URL and an optional httpx.AsyncClient for headers and auth. sse_client(url) still takes the URL as the notebook passes it.

Deploying a remote server

The lesson 9 project ships a Dockerfile: python:3.11-slim, uv pip install --system ., EXPOSE 8001, then uv run research_server.py. Two things change once the server leaves your laptop.

The bind address depends on the SDK version. The project’s own uv.lock pins mcp 1.8.0, whose FastMCP default host is 0.0.0.0, reachable through the container’s mapped port. The course environment’s 1.30.0 defaults to 127.0.0.1, which only the container itself can reach. Set host="0.0.0.0" in the constructor and the server behaves the same under both.

The server’s files live where it runs. The research server keeps papers in a papers/ folder beside it. In notebook 06a’s hosted server that folder is empty, so the resources list no topics. On a fresh copy, recorded with 1.30.0, papers://folders returns “No topics found.” and extract_info fails with [Errno 2] No such file or directory: 'papers', because it lists the folder without checking that it exists. A remote server needs storage that outlives the container, and tools that handle an empty start.

Before anyone outside can reach the server, it needs what a stdio server never did: authentication, because anyone who can reach the URL can call the tools; TLS; and logs of which client called what. The 1.30.0 FastMCP constructor takes auth settings and a token_verifier for the first. Notebook 06a’s optional section deploys to Render, and its resources link Cloudflare’s guide to remote MCP servers.

Check yourself

1. Why does a stateful Streamable HTTP server behind several replicas need sticky routing, while a stateless one does not?

A stateful server remembers a client through the mcp-session-id header set on the initialize reply, so every request in that session must reach the replica that holds it. With stateless_http=True there is no session: any replica can answer, but the server cannot keep anything between calls.

2. The lesson 9 Dockerfile runs fine with mcp 1.8.0, but with SDK 1.30.0 nothing outside the container reaches it. What changed, and what is the fix?

The FastMCP default host. In 1.8.0 it is 0.0.0.0, reachable through the container’s mapped port; in 1.30.0 it is 127.0.0.1, which only the container itself can reach. Set host="0.0.0.0" in the constructor and the server behaves the same under both.

3. On a fresh deployment the folders resource says No topics found and extract_info fails with No such file or directory. What is wrong?

The research server keeps papers in a papers/ folder beside it, and a fresh copy has none; extract_info lists the folder without checking that it exists. A remote server needs storage that outlives the container, and tools that handle an empty start.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s support bot connects to a filesystem server rooted at the project folder. Someone adds a second filesystem server rooted at ./handbook. Now the bot says files it read yesterday “do not exist”. How do you find the cause?

What a strong answer covers:

  • Reads the startup log: both servers list the same 14 tool names, so the model gets 32 definitions for 18 names
  • Finds the router, tool_to_session[tool.name] = session, which keeps the last server for each name; every filesystem call now goes to ./handbook, which resolves research_server.py inside its own root and answers ENOENT
  • Fixes it by namespacing tool names per server (for example handbook__read_text_file) or by refusing to start on a duplicate name, rather than relying on config order
  • Adds a startup check that fails when two servers expose the same name, and logs which server each call went to

2. You are exposing the handbook to agents over MCP. A teammate wants every chunk as a tool, another wants them as resources, a third wants a prompt. How do you decide?

What a strong answer covers:

  • Asks who decides when the data is used: the model picks tools, the application or user picks resources, the user picks prompts
  • Makes search a tool (search_handbook), since the model needs to call it in the middle of an answer with a query it writes
  • Makes sections resources (handbook://section/{chunk_id}), read without side effects, for a UI that lets an engineer attach a section to the chat
  • Makes “answer with citations” a prompt, a reusable instruction the user starts with /prompt, and keeps tool count low because every tool definition is sent on every call

3. After connecting four MCP servers, Larkspur’s bot got slower and its bill went up, though most questions never call a tool. How do you measure where the cost went?

What a strong answer covers:

  • Measures the tool definitions sent per request: in the lab, the notebook’s three servers send about 2,527 tokens of tool JSON before the question starts, and the filesystem server is 80% of it
  • Logs per request the number of tool definitions, their size, and which tools were called, to find servers whose tools are never used
  • Drops or filters servers per route (a billing question does not need write_file), and checks the tool-choice rate on a fixed question set after each change
  • Watches for the hidden cost of duplicates: two filesystem servers raise the total to about 4,649 tokens and add nothing the model can use

4. You ship larkspur-handbook in a Docker container with transport="streamable-http" and port 8001 mapped. The container is healthy, but no client can connect. What do you check?

What a strong answer covers:

  • Checks the bind address: in SDK 1.30.0 FastMCP listens on 127.0.0.1 by default, which no one outside the container can reach; pass host="0.0.0.0" (the project’s own lock, mcp 1.8.0, defaulted to 0.0.0.0, so the same code behaves differently)
  • Checks the URL: Streamable HTTP lives at /mcp; /sse is the other transport, and /mcp/ answers with a 307 redirect to /mcp
  • Checks the session: a stateful server returns an mcp-session-id header that every later request must carry, so behind several replicas it needs sticky routing or stateless_http=True
  • Tests from outside with the MCP Inspector before blaming the client, and keeps an authenticated endpoint in mind before exposing it publicly

5. A security review flags the bot’s server_config.json: @modelcontextprotocol/server-filesystem with the argument ., run from the project folder. What is the risk, and what do you change?

What a strong answer covers:

  • The . makes the whole project folder readable and writable through read_text_file and write_file, and that folder holds the .env with the API keys the chatbot loads
  • Any text the model reads, including a fetched web page, can ask it to read that file; the fetch server’s own description already tells the model it now has internet access, so tool descriptions shape behaviour too
  • Narrows the root to a data folder, drops write tools the bot does not need, and keeps secrets out of any served folder
  • Reviews every third-party server’s tool descriptions before connecting it, and pins server versions in the config so an update cannot change them unseen

Key Takeaways

  • Put tools behind a server once and every client can use them; keep the loop, the model choice and the routing in the client.
  • Read the definitions FastMCP generates before shipping: the docstring is the description the model sees, and parameter help belongs in the type hints if the model needs it.
  • Count what each server costs on every request, and give every tool a name that is unique across all connected servers.
  • Choose the transport by where the server runs: stdio for a local subprocess, Streamable HTTP at /mcp for a shared service, with the bind address, session header and auth checked before deploy.
