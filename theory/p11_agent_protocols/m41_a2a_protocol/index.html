M41 A2A: Agent-to-Agent Protocol

MCP gives one agent a standard way to call tools. A2A gives agents a standard way to call each other over HTTP, whatever framework each one is built with. The M41 notebooks build on four ideas: the Agent Card a server publishes so callers can find it, the Task and Message objects that carry the work, agents from different frameworks talking only through that contract, and a system that uses MCP for tools and A2A between agents.

Open the lab

The running example is Larkspur Cloud, the fictional cloud host whose handbook runs through M11 to M13. Its handbook agent, the agentic RAG graph from M28 to M31, becomes a service: it publishes an Agent Card and answers over A2A, and the support desk agent, built in another framework, calls it. The lab asks every agent the M11 golden question Can I export my data after I cancel my plan? All protocol details on these pages come from the installed a2a-sdk 0.3.26 (the protocols uv group) or from the notebooks.

TL;DR

  • An Agent Card is a JSON document at /.well-known/agent-card.json: name, URL, version, capabilities such as streaming, and skills. The client reads it before sending anything. In 0.3.26 the notebooks’ path /.well-known/agent.json still answers, with a deprecation warning in the server log.
  • Work travels as JSON-RPC 2.0 over HTTP: message/send, message/stream, tasks/get, tasks/cancel. The reply is either a Message (a one-shot answer) or a Task with a state such as working or completed.
  • On the server, the only code you write is an AgentExecutor. The LangGraph graph, a plain LLM call or a Google ADK agent behind it is invisible to the caller.
  • A Task keeps its answer in status.message. In the lab, a client that reads result.parts the way notebook 41.3’s connector does forwards 1,492 characters of Python repr to the next agent instead of the 185-character answer.
  • MCP and A2A sit at different layers: the capstone’s host agent loads its tools over MCP (stdio) and delegates documents to the RAG agent over A2A (HTTP).

Mental model

The caller sees two things: a card and a stream of task events. Everything to the right of the A2A server, the executor and the graph, can be rewritten in another framework without the caller changing a line, as long as the card and the task events stay the same.

Agent Card

Lesson 41.1: A2A basics: Agent Cards, tasks, messages. Notebooks: 01a_a2a_protocol_basics.ipynb

An Agent Card is the JSON document an A2A server publishes about itself. A client that knows only a base URL fetches the card first, and everything else it needs comes from there: where to post requests, which skills the agent has, and whether it can stream.

In a2a-sdk 0.3.26, AgentCard has eight required fields:

Field What the client does with it
name, description, version Shows or logs which agent, and which release of it, answered
url Posts JSON-RPC requests here
capabilities Checks streaming before calling message/stream; the others are push_notifications, state_transition_history and extensions
skills Picks the agent for a job: each AgentSkill needs id, name, description and tags, and may add examples and its own input and output modes
default_input_modes, default_output_modes Learns which content types the agent accepts and returns

Two fields have defaults the notebooks never set: protocol_version is 0.3.0 and preferred_transport is JSONRPC. Authentication also lives on the card, in security_schemes and security, and an agent can keep some skills on an authenticated extended card (supports_authenticated_extended_card, served at /agent/authenticatedExtendedCard).

On the wire the fields are camelCase. This is the card the lab’s handbook agent serves, recorded from a live server:

{
  "capabilities": { "streaming": true },
  "defaultInputModes": ["text"],
  "defaultOutputModes": ["text"],
  "description": "Answers questions from the Larkspur Cloud handbook.",
  "name": "larkspur_handbook_agent",
  "preferredTransport": "JSONRPC",
  "protocolVersion": "0.3.0",
  "skills": [{
    "id": "handbook_qa", "name": "handbook_qa",
    "description": "Answers billing, export and outage questions from the Larkspur Cloud handbook.",
    "tags": ["rag", "handbook"],
    "examples": ["Can I export my data after I cancel my plan?", "How long does a refund take?"]
  }],
  "url": "http://localhost:10002/",
  "version": "1.0.0"
}

Where the card lives. The notebooks say /.well-known/agent.json. In 0.3.26 the SDK’s constant is AGENT_CARD_WELL_KNOWN_PATH = "/.well-known/agent-card.json", and A2ACardResolver fetches that path. A2AStarletteApplication serves both: the old path still returns the card and logs that it is deprecated and will be removed. Clients written against the new SDK never touch the old path, so the notebooks work unchanged.

The card is a contract. A skill description is all a calling agent’s model knows about the agent, the same way a tool description is all it knows about a tool (M31). Changing streaming, a skill id or the URL breaks callers that read the old card, so bump version when you do.

From discovery to reply

Notebook 41.1 runs one server and one client in the same process. The server is an echo agent: its AgentExecutor puts a single agent message on the event queue. The client goes through four steps, and each maps to one HTTP call or one decision:

Submitting means posting a JSON-RPC 2.0 request. The message has a role (user or agent), a client-chosen messageId and a list of parts, each a text, file or data part:

{
  "jsonrpc": "2.0", "id": "req-1", "method": "message/send",
  "params": { "message": {
    "kind": "message", "role": "user", "messageId": "id-1",
    "parts": [{ "kind": "text", "text": "Can I export my data after I cancel my plan?" }]
  } }
}

The echo agent answers with a Message: "kind": "message", "role": "agent", and the text in parts. The request context hands the executor a contextId, which groups related turns, and a taskId, and the executor copies both into its reply. It never created a task, though, so nothing was stored. In the lab, tasks/get on that id returns error -32001, Task not found. A Message is the whole answer; there is nothing to poll.

The server side of the notebook is three objects: an AgentExecutor with the agent logic, a DefaultRequestHandler that implements the JSON-RPC methods on top of it with an InMemoryTaskStore, and an A2AStarletteApplication that serves the card and the endpoint. The client side is A2ACardResolver and A2AClient. In 0.3.26, constructing A2AClient emits a DeprecationWarning that points to ClientFactory; the notebooks’ calls still work.

Check yourself

1. A client knows only an A2A agent's base URL. What does it fetch first, and what does it learn from it?

The Agent Card, which A2ACardResolver in 0.3.26 fetches from /.well-known/agent-card.json. The card tells it where to post requests (url), which skills the agent has, whether it can stream (capabilities), and which content types it accepts and returns.

2. The echo agent answers message/send with a Message. What happens if the client calls tasks/get with the taskId from that reply?

It gets error -32001, Task not found. The executor copied the contextId and taskId from the request context into its reply but never created a task, so nothing was stored. A Message is the whole answer; there is nothing to poll.

3. You rename the Larkspur handbook agent's skill id from handbook_qa to billing_qa. What else must change on the card, and why?

Bump version. The card is a contract: a calling agent’s model knows the agent only through what the card says, and changing streaming, a skill id or the URL breaks callers that read the old card.

Tasks & messages

Lesson 41.2: A LangGraph agent over A2A. Notebooks: 02a_langgraph_agent_over_a2a.ipynb

A2A has two reply shapes, and the executor decides which one a caller gets:

Reply When the executor produces it Where the answer is Can the client poll it?
Message ("kind": "message") It enqueues one agent message and nothing else, as the echo agent in 41.1 does result.parts No: tasks/get answers -32001, Task not found
Task ("kind": "task") It enqueues a Task, then status updates through a TaskUpdater, as notebook 41.2 does result.status.message, plus artifacts if the agent publishes any Yes, by its id, for as long as the task store keeps it

A Message suits a one-shot answer. A Task suits anything that takes time, can fail halfway, or needs another turn from the caller.

The lifecycle. TaskState in 0.3.26 has nine values. The SDK treats four as terminal (completed, failed, canceled, rejected): TaskUpdater marks their update final and refuses any update after one, and tasks/cancel on a terminal task answers -32002. Two are interrupted states, where the task waits for the caller: input-required and auth-required. The caller continues such a task by sending a message with the same taskId; a message aimed at a terminal task gets error -32602 (the task is in terminal state), so a follow-up question starts a new task in the same contextId.

The diagram shows the paths these pages use; auth-required behaves like input-required, and unknown is the ninth value. Notebook 41.2’s executor only ever walks submitted, working, then completed or failed.

The interactive lab replays exchanges recorded from three agents served by a2a-sdk 0.3.26, each asked Can I export my data after I cancel my plan? The handbook agent has notebook 41.2’s executor, with a stub that returns a fixed handbook answer where the notebook calls the LangGraph graph. Its four calls:

  • message/send returns a Task in state completed. history holds the user turn and the working update; the 185-character answer is in status.message.
  • message/stream returns three server-sent events: a task in submitted, a status-update to working with "final": false, and a status-update to completed with "final": true.
  • tasks/get returns the same Task that message/send returned.
  • tasks/cancel returns error -32002: the task cannot be canceled in state completed.

When the graph fails. Notebook 41.2’s executor catches the exception, sets the task to failed with the error text, and then re-raises. The lab’s third agent does the same with an index that is not loaded. A message/send caller gets JSON-RPC error -32603 whose message is the raw exception text, vector index not loaded, and no task id. A message/stream caller sees the task go to failed, and tasks/get with the streamed id returns the failed Task. An executor that sets failed and returns without re-raising gives the message/send caller a Task in state failed instead (checked against the same SDK), which the caller can handle like any other result, and the raw exception text stays out of a reply that may go to another team’s agent.

The executor seam

The A2A server never sees LangGraph. It calls one method, AgentExecutor.execute(context, event_queue), and serialises whatever the method puts on the queue. Notebook 41.2’s LangGraphAgentExecutor does five things:

  1. Reads the text with context.get_user_input().
  2. Creates a Task with new_task(context.message) if the request did not continue one, and enqueues it.
  3. Publishes working through a TaskUpdater, with a short agent message.
  4. Runs graph.invoke({"messages": [("user", text)]}) in asyncio.to_thread, since invoke blocks and the server’s event loop must stay free.
  5. Publishes completed with the last message’s content, or failed on an exception.

cancel() raises ServerError(error=UnsupportedOperationError()), which reaches the caller as error -32004. Notebook 41.3’s executors use await agent.ainvoke(...) instead of a thread; either keeps the loop free.

The card advertises two skills, calculator and lookup, one per tool of the ReAct agent, and streaming=True. Streaming here means task events: the graph’s invoke returns once, so a stream carries the three events in the lab and no partial tokens. To stream tokens, the executor would iterate the graph’s own stream and publish each chunk as an artifact update or a working message.

The notebook builds the graph with langgraph.prebuilt.create_react_agent. The installed langgraph 1.2.18 marks it deprecated in favour of langchain.agents.create_agent (M24); it still runs, and the executor would wrap either one the same way.

Check yourself

1. When should an A2A executor reply with a Task rather than a Message?

When the work takes time, can fail halfway, or needs another turn from the caller. A Task can be polled by its id for as long as the task store keeps it, and it moves through states; a Message suits a one-shot answer, and tasks/get on it answers -32001.

2. After the handbook agent's task reaches completed, the caller wants to ask a follow-up. Can it send the message with the same taskId?

No. completed is terminal, and a message aimed at a terminal task gets error -32602, so the follow-up starts a new task in the same contextId. Only a task in an interrupted state, input-required or auth-required, continues with the same taskId.

3. With the index not loaded, a message/send caller gets error -32603 carrying the raw exception text and no task id. What causes this, and what is better?

Notebook 41.2’s executor sets the task to failed and then re-raises, which turns the failure into a JSON-RPC error. Set failed and return without re-raising: the caller gets a Task in state failed, handles it like any other result, and the raw exception text stays out of a reply that may go to another team’s agent.

Cross-framework interop

Lesson 41.3: Cross-framework agent interop. Notebooks: 03a_cross_framework_agent_interop.ipynb

Notebook 41.3 serves two agents that share no code. The research agent is a LangGraph ReAct agent with one tool, lookup_facts, on port 10101. The writer agent is a single get_llm(temperature=0.7).invoke(...) call behind a copywriter prompt, with no graph and no tools, on port 10102. Each has its own AgentExecutor and its own Agent Card. An orchestrator reads a registry file listing the two base URLs, fetches both cards, sends a topic to the research agent (hop 1) and passes the research agent’s output to the writer agent (hop 2).

The two agents agree on four things: the card’s shape, the message/send method, the Message and Task objects, and the well-known card path. They differ in everything else (framework, prompt, tools, temperature), and the orchestrator imports none of it. Replace the writer’s single call with a CrewAI crew or a Google ADK agent, keep the card and the reply shape, and the orchestrator does not change.

On Larkspur Cloud the same layout is a support desk orchestrator, the handbook agent (the M28 to M31 agentic RAG graph, in LangGraph) as hop 1, and a reply drafter that turns the handbook answer into a customer email as hop 2. The drafter’s team can pick any framework.

Discovery from a registry. The registry holds URLs only. Capabilities come from each card at run time, so a new agent joins by adding one URL, and a changed skill shows up without an orchestrator release. The notebook picks cards by card.name. Picking by skill (id or tags) survives a rename and lets two agents offer the same skill. The registry itself is a trust list: only agents on it get your traffic.

Reading the reply

The orchestrator talks to both agents through an AgentConnector with one method, send_task(message, session_id). Its reading of the reply decides what hop 2 receives:

result = response.root.result
if hasattr(result, "parts"):          # a Message
    return "\n".join(part.root.text for part in result.parts if hasattr(part.root, "text"))
return str(result)                    # a Task object; fall back to its string representation

Both executors in the notebook enqueue a Task before their answer, so every reply is a Task, and a Task has no parts. The connector returns str(result), the Python repr of the whole Task, and the orchestrator forwards that to the writer. The interactive lab shows it with the handbook agent: the repr is 1,492 characters of context_id=…, history=[Message(…)] and TaskStatus(…), around a 185-character answer. Running the notebook’s own AgentConnector cell against the same server returns the same 1,492 characters. The writer, told to synthesise research notes, receives Pydantic field names as its notes.

Two more paths in the same connector:

  • An error reply. When the agent fails, response.root is a JSONRPCErrorResponse, which has no result. The AttributeError lands in the connector’s except, and send_task returns the string Error communicating with agent: 'JSONRPCErrorResponse' object has no attribute 'result', which the orchestrator passes to the writer as research notes.
  • The session. send_task takes a session_id and never sends it, so each hop gets a fresh contextId. To keep the two hops in one conversation, set context_id on the outgoing Message; the server then files the new task under that context.

A reader that checks for an error first and then branches on the reply’s kind fixes the first two:

root = response.root
if hasattr(root, "error"):
    raise RuntimeError(f"A2A error {root.error.code}: {root.error.message}")
result = root.result
message = result if result.kind == "message" else result.status.message
if result.kind == "task" and result.status.state != "completed":
    raise RuntimeError(f"task {result.id} ended in {result.status.state}")
return "\n".join(p.root.text for p in message.parts if p.root.kind == "text")

An agent that publishes its output as artifacts (TaskUpdater.add_artifact) puts it in result.artifacts instead; read those the same way.

Check yourself

1. What must the research and writer agents agree on for one orchestrator to call both, and what may differ?

Four things: the card’s shape, the message/send method, the Message and Task objects, and the well-known card path. Framework, prompt, tools and temperature may all differ, and the orchestrator imports none of them, so a CrewAI crew could replace the writer without an orchestrator change.

2. The writer agent receives 1,492 characters of field names and TaskStatus text instead of research notes. What went wrong in the connector?

Both executors enqueue a Task, and a Task has no parts, so AgentConnector falls through to str(result), the Python repr of the whole Task around a 185-character answer. Check for an error first, then branch on result.kind and read the text parts of result.status.message for a task.

3. Why pick agents from the registry by skill id or tags rather than by card name, as the notebook does?

Picking by skill survives a rename and lets two agents offer the same skill. The registry holds URLs only and capabilities come from each card at run time, so a new agent joins by adding one URL. The registry is also a trust list: only agents on it get your traffic.

MCP + A2A

Lesson 41.4: Capstone: agentic RAG with MCP and A2A. Notebooks: mcp_a2a_agentic_rag (project)

The capstone project runs two Google ADK agents, each behind its own A2A server, and gives both of them MCP tools. It runs in its own environment (its requirements.txt), with a Gemini model (gemini-2.0-flash-exp in model.py) and a Streamlit UI.

MCP A2A
Connects An agent to tools and data An agent to another agent
In the capstone mcp_config.json starts two servers as subprocesses over stdio: web_search (SerpAPI) and terminal (execute_command from an allow-list, list_files, read_file) The host reads agent_registry.json (one URL, http://localhost:10002), fetches the RAG agent’s card and delegates to it
The caller gets A tool result, which its own model reasons over An answer from an agent with its own model, tools and state
Lifetime One call A Task, with states, that can be polled, streamed or canceled

The host is an orchestrator, as in 41.3, with four function tools (_list_agents, _delegate_task, _smart_delegate_to_rag, _get_model_info) next to the MCP toolsets. It does not always ask its model where to send a question. _is_document_question checks the text for keywords such as resume, pdf, document or tell me about, and on a match the host calls the RAG agent directly. Keyword routing is fast and predictable, and it misroutes: tell me about today’s AWS outage goes to the document agent, though only the web can answer it.

The RAG agent splits a PDF into 500-token chunks (tiktoken cl100k_base) with 50 tokens of overlap, indexes them in a FAISS IndexFlatL2, and answers with multi-candidate retrieval: it adds Gaussian noise (standard deviation 0.01) to the query embedding three times, takes the top 5 chunks for each, answers all three candidate sets in parallel, and asks the model to pick the best answer. That is the agentic RAG of M28 to M32, now behind an A2A card instead of inside one graph.

On Larkspur Cloud, the host is the support desk, the RAG agent holds the handbook, and the MCP web search answers what the handbook cannot. A question like Can I export my data after I cancel my plan? goes over A2A to the handbook agent; Is the Frankfurt region down right now? goes to a tool over MCP.

What the capstone needs to run

The project’s A2A connector was written against an older a2a-sdk API, which notebook 41.3 also points out, and two of its paths fail without raising. Both are known bugs in the connector, listed here so the symptoms make sense:

  • The A2A hop. utilities/a2a/agent_connect.py builds A2AClient(base_url=self.agent_card.base_url, ...) and calls client.send_request(...). In a2a-sdk 0.3.26 AgentCard has no base_url, and A2AClient takes agent_card or url and has send_message but no send_request. Run against 0.3.26, send_task returns the string Error communicating with agent: 'AgentCard' object has no attribute 'base_url', and the host passes that string on as the RAG agent’s answer: to its model through _delegate_task, or, for a keyword-routed question, straight to the user. Notebook 41.3’s connector uses the current API; combine it with the reader from 41.3.
  • The RAG agent’s own web search. Besides the MCP tools ADK loads, rag_orchestrator.py has a WebSearchAgent that posts a JSON-RPC request with method search to http://localhost:8000 (or MCP_ENDPOINT). Nothing in the project listens there, and search is not an MCP method (MCP calls a tool with tools/call). When the decision prompt asks for a web search, the final prompt receives [WebSearchAgent] Failed to obtain web data. as its web context.

Two smaller points: pyproject.toml lists a2a-python where requirements.txt lists a2a-sdk>=0.3.0, and the web search server logs the first ten characters of SERPAPI_KEY at startup, so its log is not safe to share.

A smoke test that sends one golden question through the host and checks that the reply contains handbook text, not Error communicating, catches the first failure on the first run.

Check yourself

1. In the capstone, when does the host use MCP and when does it use A2A?

MCP connects it to tools and data: web_search and terminal, started over stdio, return a tool result that the host’s own model reasons over, and each use lasts one call. A2A connects it to another agent: the host reads agent_registry.json, fetches the RAG agent’s card and delegates, getting an answer from an agent with its own model, tools and state, tracked as a Task that can be polled, streamed or cancelled.

2. A user asks the host to tell me about today's AWS outage. Where does the question go, and is that right?

To the RAG agent. _is_document_question matches the keyword tell me about, so the host calls the document agent directly, though only the web can answer. Keyword routing is fast and predictable, and it misroutes.

3. Under a2a-sdk 0.3.26 every document question comes back as a reply starting Error communicating with agent. What is wrong, and what catches it early?

agent_connect.py builds A2AClient(base_url=self.agent_card.base_url, ...) and calls send_request, but AgentCard has no base_url and A2AClient has send_message, not send_request. send_task returns the error string and the host passes it on as the answer. A smoke test that sends one golden question and checks for handbook text, not Error communicating, catches it on the first run.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s support desk agent calls the handbook agent over A2A, then passes the reply to a writer agent. Customers start getting answers that quote context_id= and TaskStatus(. Nothing errored. Where do you look?

What a strong answer covers:

  • Logs the raw JSON-RPC response from the handbook agent and checks result.kind: the agent now returns a Task, where it used to return a Message
  • Finds the connector that reads result.parts and falls back to str(result) for a Task; the answer is in status.message (or in artifacts, if the agent publishes them)
  • Fixes the reader to branch on kind, and fails loudly on a kind it does not know rather than stringifying it
  • Adds a contract test that runs the client against both reply shapes, so a change on the server side is caught before customers see it

2. The platform team wants every Larkspur team to reach the handbook RAG system. One proposal is an MCP tool handbook_search; the other is an A2A agent larkspur_handbook_agent. Which do you ship?

What a strong answer covers:

  • An MCP tool returns chunks and leaves reasoning to the caller’s model; an A2A agent returns an answer from a system that owns retrieval, grading and rewriting
  • Callers that need citations, their own prompt or their own reranker are better served by the tool; callers that want an answer and a task they can poll are better served by the agent
  • A2A adds a task lifecycle, streaming and cancellation, and costs a second model loop per question
  • The two can coexist: the agent behind A2A, with its retriever exposed as an MCP tool for callers that want raw chunks

3. The handbook agent runs behind A2A in production. What do you measure, and what alerts you that it is degrading?

What a strong answer covers:

  • Counts tasks by final state (completed, failed, canceled, rejected) and JSON-RPC error codes per caller and per skill
  • Measures time to the first working update and time to completed, separately from the graph’s own latency
  • Watches tasks stuck in working and tasks lost on restart, since an InMemoryTaskStore keeps nothing across a deploy
  • Alerts when the Agent Card changes (version, skills, streaming) without a matching client release, and replays the golden questions through A2A after every deploy

4. Re-indexing the handbook takes 20 minutes, and the support desk triggers it through the handbook agent over message/send. Calls time out, and some re-index twice. How do you redesign the exchange?

What a strong answer covers:

  • Has the client send with configuration.blocking set to false, which returns the Task at once in submitted, then poll tasks/get or subscribe with message/stream, instead of holding one HTTP request open for 20 minutes
  • Uses push notifications (capabilities.push_notifications, tasks/pushNotificationConfig/set) when the client cannot hold a stream
  • Makes the trigger idempotent per handbook version, so a retried send does not start a second re-index
  • Persists tasks in a durable store and implements cancel(), since a cancel on a finished task answers -32002 and a lost task answers -32001

5. A partner company wants its booking agent to call Larkspur’s handbook agent. The Agent Card is public. What do you check before you open it up?

What a strong answer covers:

  • Declares authentication in the card (security_schemes, security) and keeps internal skills on the authenticated extended card (supports_authenticated_extended_card)
  • Treats every incoming message as untrusted input: the partner’s agent can carry prompt injection into the handbook agent’s model
  • Treats every reply from a remote agent as untrusted too, before it reaches a tool call or a customer
  • Rate-limits and logs per caller, and scopes the skills a partner sees to what its contract covers

Key Takeaways

  • Publish an Agent Card and let clients discover it; hard-code a base URL, never a list of skills.
  • Read replies by kind: a Message has parts, a Task has status.message and artifacts. Never forward str() of a protocol object.
  • Keep the A2A code in one AgentExecutor and keep the agent behind it framework-specific. That boundary is what lets you swap LangGraph for anything else.
  • Use MCP for tools and data, A2A for agents. A system needs both once one agent’s answer depends on another team’s agent.
