M03 Hugging Face models and Gradio demos

M02 called models that run on someone else’s servers. This module runs open models from the Hugging Face Hub on your own machine: the same kind of model that embeds chunks in M14 and reranks them in M19. The M03 notebooks build on four ideas: where a downloaded model lives and how to pin it, what a pipeline does between your string and its answer, why every limit and price is counted in tokens, and how to put a web page in front of a Python function.

Open the lab

The running example is the Larkspur Cloud support team, which uses the handbook from M11 to M14. They want three things from open models: a sentiment label on incoming tickets such as My refund took three weeks., a vector for every handbook answer so that Can I export my data after I cancel my plan? finds the right one, and a demo page the support lead can try without opening a notebook.

TL;DR

  • from_pretrained and pipeline download a model once into ~/.cache/huggingface/hub and read it from disk after that. The cache holds files by content hash under blobs/ and links them from snapshots/<commit>/, so a model is pinned by its commit, not by its name.
  • pipeline(task) runs three steps: the tokenizer turns text into ids, the model turns ids into numbers, and post-processing turns those numbers into a label and a score. Without model=, the task picks a default model, and the defaults change between transformers releases.
  • Models read tokens, not characters. On the handbook’s FAQ page GPT-2 counts 308 tokens and all-MiniLM-L6-v2 291, both near M11’s four characters per token. Rare words cost more: the notebook’s Preposterous, I’m flabbergasted! runs at 2.29 characters per MiniLM token.
  • Every model has a token limit, and text past it is cut without an error. all-MiniLM-L6-v2 reads 256 tokens; embed the whole FAQ page and the last 35 tokens, the support and promotional-credit answers, are not in the vector.
  • gr.Interface wraps one function in a form. gr.Blocks lays components out in rows, columns and tabs, and wires each event (click, change) to a function by naming its inputs and outputs.

Mental model

Only the first call touches the network; every later call reads the cache, and a running app loads the model once and keeps it in memory. The tokenizer and the model come from the same repo and must stay together, because the ids mean nothing to any other model. Gradio adds nothing to the model; it calls the same Python function on every click.

Hub & cache

Lesson 3.1: Hub setup, datasets and models. Notebooks: 01a_hf_setup.ipynb, 01b_hf_basics.ipynb

The Hugging Face Hub stores models, datasets and Spaces as git repositories named owner/name, such as sentence-transformers/all-MiniLM-L6-v2. Every change to a repo is a commit with a 40-character hash, and branch names such as main point to the latest one. Notebook 01a logs in with notebook_login(), which saves an access token; scripts and servers read the same token from the HF_TOKEN environment variable. Public models download without a token, but gated models need one, and anonymous requests get lower rate limits (the library prints a warning saying so).

The first from_pretrained or pipeline call for a repo downloads its files into a local cache. Every later call reads the files from disk. This is the entry for the embedding model M14 and M17 use, as it sits in a cache on disk:

~/.cache/huggingface/hub/models--sentence-transformers--all-MiniLM-L6-v2/
├── refs/main                       40 bytes: the commit hash 1110a243…
├── blobs/                          each file once, named by the hash of its content
│   ├── 53aa5117…                   90,868,376 bytes (the weights)
│   ├── cb202bfe…                   466,247 bytes (tokenizer.json)
│   └── …
├── snapshots/1110a243…/            the repo as it was at that commit
│   ├── model.safetensors  -> ../../blobs/53aa5117…
│   ├── tokenizer.json     -> ../../blobs/cb202bfe…
│   └── …                           every file is a symlink into blobs/
└── .no_exist/                      files the library asked for that the repo does not have

Three consequences follow from that layout:

  • A name is not a version. main moves when the owner pushes. Pass revision= with a commit hash to load the same weights in every environment, which is how transformers pins its own default models (lesson 3.2).
  • Revisions share files. Two snapshots of one repo point at the same blob when a file did not change, so a new commit downloads only what changed. Old revisions stay on disk until you remove them.
  • The cache is a folder you can move. HF_HOME (default ~/.cache/huggingface) or HF_HUB_CACHE (default $HF_HOME/hub) relocate it, for example to a volume shared by several containers; HF_HUB_OFFLINE=1 makes the library read only from it and never call the Hub.

To see what the cache holds, scan_cache_dir() in 01a returns an HFCacheInfo object with every repo, revision and size. The notebook also suggests huggingface-cli scan-cache; in huggingface_hub 1.16.1, the version this course locks, that command prints “huggingface-cli is deprecated and no longer works”. Use hf cache ls to list repos and sizes, hf cache rm to delete one, and hf cache prune to remove revisions no branch points to.

Datasets use the same Hub and their own cache. Notebook 01b calls load_dataset('rotten_tomatoes', cache_dir='rotten_tomatoes_data'); the relative cache_dir writes a data folder next to the notebook instead of into the shared cache. The dataset has three splits (8,530 training, 1,066 validation and 1,066 test reviews), and the notebook divides its correct predictions by a hard-coded 1066. Write len(test_df) instead, so the accuracy stays right if the split changes. The Hub now lists the dataset as cornell-movie-review-data/rotten_tomatoes; if the short name stops resolving, use the full id.

Key Takeaways

  • Hub repos are git repositories, and a branch such as main moves when the owner pushes. Pin revision= to a commit hash to load the same weights in every environment.
  • The cache stores each file once as a content-hashed blob and links snapshots to it, so a new commit downloads only what changed. Clear old revisions with hf cache prune.
  • Relocate the cache with HF_HOME or HF_HUB_CACHE and set HF_HUB_OFFLINE=1 on servers that must never call the Hub. Compute accuracy from len(test_df), never a hard-coded count.

Check yourself

1. Why does loading a model with revision main not guarantee the same weights in every environment?

A name is not a version. main is a branch that moves when the owner pushes, and refs/main holds whichever commit hash it points to now. Pass revision= with a commit hash to load the same weights everywhere, which is how transformers pins its own default models.

2. The owner of all-MiniLM-L6-v2 pushes a commit that changes only tokenizer.json. What does your next load of main download, and what stays on disk?

Only the new tokenizer.json. The new snapshot’s model.safetensors symlink points at the same 90,868,376-byte blob, because that file did not change. The old revision stays on disk until you remove it; hf cache prune removes revisions no branch points to.

3. Several containers share one model cache, and the servers must never call the Hub. Which settings do you use?

Point HF_HOME or HF_HUB_CACHE at the shared volume, and set HF_HUB_OFFLINE=1 so the library reads only from the cache. Pin each model with revision= and a commit hash so every container loads the same snapshot.

Pipelines

Lesson 3.2: Pipelines, tokenization and pretrained models. Notebooks: 02a_pipelines_for_nlp_tasks.ipynb, 02b_understanding_llms.ipynb, 02c_accessing_pretrained_models.ipynb (optional)

pipeline() from transformers loads a tokenizer and a model from one Hub repo and runs three steps on every call: pre-processing (the tokenizer turns text into token ids), the forward pass (the model turns ids into numbers) and post-processing (those numbers become a label, a span or generated text). Notebook 02a runs it for sentiment, named entities, question answering and translation; 01b uses it to label 1,066 movie reviews and computes accuracy against the dataset’s labels.

For a Larkspur ticket, My refund took three weeks., the sentiment pipeline’s tokenizer produces nine ids: [CLS] my ref ##und took three weeks . [SEP]. The model returns two logits, softmax turns them into probabilities, and the model’s config.json maps index 0 to NEGATIVE and 1 to POSITIVE. Each step can go wrong on its own. A ticket longer than the model’s 512 positions has to be truncated at the tokenizer, a model trained on movie reviews misreads billing language in the forward pass, and a two-label head cannot say “billing” or “outage” at all.

A task name picks a model for you. pipeline(task="text-classification") with no model= loads the task’s default, and transformers prints “No model was supplied, defaulted to … Using a pipeline without specifying a model name and revision in production is not recommended.” In transformers 5.17.0, the version this course locks, the defaults include:

Task Default model Pinned revision
text-classification (alias sentiment-analysis) distilbert/distilbert-base-uncased-finetuned-sst-2-english 714eb0f
token-classification (alias ner) dbmdz/bert-large-cased-finetuned-conll03-english 4c53496
text-generation HuggingFaceTB/SmolLM3-3B a07cc9a

The NER default is 1.33 GB of weights, five times the sentiment model’s 268 MB, which is why 02a warns before loading it. Pass model= (and revision= with a commit hash) to choose the model yourself: 02a loads ProsusAI/finbert for financial headlines, and the task comes from the repo’s metadata.

The task list changes between releases. The list printed at the top of 02a comes from an older transformers. Version 5.17.0 has no question-answering, translation, summarization, text2text-generation or conversational task, so the notebook’s pipeline('question-answering') and pipeline('translation_en_to_fr') cells fail in this course’s environment. Print transformers.pipelines.get_supported_tasks() to see what your installed version supports.

Two smaller points from the notebooks. save_pretrained(folder) writes the tokenizer, model and config into a folder that pipeline(model=folder) loads again; 02a saves the text-classification pipeline that way, not the NER one, and writes the folder next to the notebook. Notebook 02c shows the same text generation twice: once with AutoTokenizer and AutoModelForCausalLM and an explicit generate(), once as pipeline("text-generation", model="gpt2"). The pipeline is shorter; the explicit version lets you read the logits, which the next two sections need.

Tokenization

Models read tokens, pieces of text from a fixed vocabulary, each mapped to an integer id. Notebook 02b explains why the pieces are subwords: a character vocabulary is small but needs many tokens per sentence, a word vocabulary is large and still meets unknown words, and subwords keep common words whole while building rare ones from parts. Every model ships its own tokenizer, and the ids mean nothing to any other model. These are real outputs of the two tokenizers this module and M14 use, from AutoTokenizer in transformers 5.17.0:

Text GPT-2 (byte-level BPE, 50,257 tokens) all-MiniLM-L6-v2 (WordPiece, lower case, 30,522 tokens)
Larkspur Cloud L arks pur ␣Cloud [CLS] lark ##sp ##ur cloud [SEP]
Preposterous, I’m flabbergasted! Prep oster ous , ␣I 'm ␣fl ab berg asted ! [CLS] prep ##ost ##ero ##us , i ' m fl ##ab ##berg ##ast ##ed ! [SEP]
Can I export my data after I cancel my plan? 11 tokens, one per word plus ? 13 tokens, the same split plus [CLS] and [SEP]

The two schemes differ in ways that matter later. GPT-2 keeps case and attaches a leading space to the token after it (␣ above), so “fl” at the start of a text is id 2704 and ” fl” after a space is id 781; 02b’s markdown quotes the second. WordPiece lower-cases everything, marks a piece that continues a word with ##, and adds [CLS] and [SEP] around every input.

Prices and limits are counted in tokens, so the ratio of characters to tokens decides what a text costs. M11 estimated tokens as characters divided by four. On the handbook that holds: the refunds section is 1,111 characters and 246 GPT-2 tokens (4.52 characters per token), the FAQ page 1,415 characters and 308 tokens (4.59). It fails on rare words: Preposterous, I’m flabbergasted! runs at 2.91 characters per GPT-2 token and 2.29 per MiniLM token. Product names, codes and other languages move the ratio the same way, so count with the model’s own tokenizer before you budget.

Every model has a token limit, and the text past it is dropped without an error. GPT-2 has 1,024 positions. The MiniLM tokenizer reports 512, but sentence-transformers reads max_seq_length: 256 from the repo’s sentence_bert_config.json and cuts every input there, [CLS] and [SEP] included. The FAQ page is 291 MiniLM tokens, so its last 35 tokens, 183 characters holding the support response times and the promotional-credit rule, never reach the model. Embedding the whole page and embedding its first 1,231 characters give the same vector (cosine similarity 1.0000). How fast does support answer a ticket? then scores 0.229 against the page and 0.687 against the support answer on its own. This is the reason M13 sizes chunks and why the size must be measured in the embedding model’s tokens.

The interactive lab holds the real token ids for five Larkspur texts under both tokenizers and cuts them exactly as tokenizer(text, truncation=True, max_length=N) does; it matches the library at every limit from 8 to 320, 3,130 settings with 0 mismatches. Lower the limit on the refunds section to 128 and MiniLM keeps the text up to “less than 100 GB of out”, splitting the sentence M13’s golden question needs, while GPT-2’s cut falls one word earlier, before “GB”.

From logits to text

A causal language model such as GPT-2 predicts the next token. Notebook 02b feeds it I skip across the, four tokens, and gets logits of shape [1, 4, 50257]: one batch, one row per input token, one score per vocabulary entry. The last row scores every possible next token; argmax picks the most likely, and softmax turns the row into probabilities. generate() repeats that step, appending each new token to the input.

How the next token is picked is the decoding strategy, set by generate()’s arguments. The notebook’s settings:

  • Greedy (the default): the most likely token every time. Deterministic, and prone to repeating itself in long text.
  • Beam search, num_beams=5: keeps the five most likely sequences and returns the best whole one; repetition_penalty=1.2 lowers the score of tokens already used.
  • Sampling, do_sample=True: draws from the probabilities. temperature=0.4 sharpens them toward the top tokens, top_k=10 draws only from the ten most likely, and top_p=0.94 from the smallest set whose probabilities add up to 0.94. The notebook sets top_k=0 to switch the top-k filter off when it tests temperature and top-p alone.

Two details catch people out. max_new_tokens=20 counts only generated tokens, while max_length=40 counts the prompt too and leaves room for 36 new tokens after the 4-token prompt. And GPT-2 has no padding token; 02c passes pad_token_id=tokenizer.eos_token_id to silence the warning generate() gives about it. The code comment in 02b’s first tokenizer cell, tensor([[1026, 373, 257, 3223, 290, 6388, 88]]), is the encoding of It was a dark and stormy, not of the sentence in that cell.

Key Takeaways

  • A pipeline is tokenise, forward pass, post-process, and each step can fail on its own. Pass model= and revision= yourself, because the task default and the task list change between releases.
  • Count tokens with the model’s own tokenizer, since rare words and codes shift the ratio. Text past the limit is dropped without an error, so measure chunk sizes in the embedding model’s tokens.
  • generate() picks one next token at a time from the last row of logits. Greedy is deterministic but repeats; beam search and sampling with temperature, top_k and top_p change that.

Check yourself

1. Why is pipeline with only a task name a risk in production code?

It loads the task’s default model, chosen by the installed transformers version, and the library warns that a pipeline without a model name and revision is not recommended in production. In 5.17.0, text-classification loads distilbert/distilbert-base-uncased-finetuned-sst-2-english at 714eb0f. Pass model= and revision= with a commit hash to choose it yourself.

2. The FAQ page is 291 MiniLM tokens. Why does the support-speed question score 0.229 against the whole page but 0.687 against the support answer alone?

sentence-transformers cuts every input at max_seq_length: 256, so the page’s last 35 tokens, the 183 characters with the support response times, never reach the model. The whole page and its first 1,231 characters give the same vector, so the page’s embedding carries no trace of the answer. This is why M13 sizes chunks in the embedding model’s tokens.

3. A GPT-2 reply generated with default settings repeats itself in long text. Which generate arguments from the notebook change that?

The default is greedy decoding, which is deterministic and prone to repetition. Beam search with num_beams=5 and repetition_penalty=1.2 lowers the score of tokens already used. Sampling with do_sample=True draws from the probabilities instead, shaped by temperature, top_k and top_p.

Gradio Blocks

Lesson 3.5: Building demos with Gradio. Notebooks: 05a_gradio_introduction.ipynb, 05b_gradio_layout.ipynb (optional), 05c_gradio_interactions.ipynb (optional), 05d_gradio_image_ml_integration.ipynb (optional), 05e_gradio_text_ml_integration.ipynb (optional), 05f_gradio_modals_errors.ipynb (optional), 05g_gradio_styling_and_themes.ipynb (optional)

Gradio turns a Python function into a web page. The function stays ordinary Python; Gradio draws an input component for each argument, an output component for each return value, and calls the function when the user acts. launch() serves the page at http://localhost:7860, or the next free port above it.

Gradio has two ways to build that page:

  • gr.Interface(fn, inputs, outputs) builds a form around one function: the input components, a Submit button and the outputs. Notebook 05a wraps an adder, a text reverser, a greyscale filter and a classifier this way, and 05d sets live=True so the function reruns on every change instead of on Submit. Interface also adds a Flag button; in Gradio 6.31 flagged examples go to .gradio/flagged, not the flagged folder 05a names.
  • gr.Blocks() is a context manager in which you place components yourself, inside gr.Row(), gr.Column(scale=…), gr.Tab(), gr.Accordion() and gr.Group() (05b). Blocks adds no button and calls nothing by itself. You connect each event to a function (05c): button.click(fn, inputs, outputs) runs on a click, slider.change(...) on every change of value. One page can hold many components and many events, each with its own function.

The event names its inputs and outputs by component, and Gradio passes values between the browser and the function. This is the Larkspur ticket tagger as a Blocks app, with the ticket box and button in a wide column and the result beside them:

import gradio as gr
from transformers import pipeline

clf = pipeline("sentiment-analysis",
               model="distilbert/distilbert-base-uncased-finetuned-sst-2-english",
               revision="714eb0f")                       # loaded once, when the app starts

def tag(ticket):
    if not ticket.strip():
        raise gr.Error("Paste a ticket first.")          # stops here and shows the message
    r = clf(ticket)[0]
    return {r["label"]: r["score"]}                      # gr.Label shows a label with its confidence

with gr.Blocks() as demo:
    with gr.Row():
        with gr.Column(scale=2):
            ticket = gr.Textbox(label="Ticket", lines=4)
            go = gr.Button("Tag")
        with gr.Column(scale=1):
            label = gr.Label(label="Sentiment")
    go.click(fn=tag, inputs=ticket, outputs=label)

demo.launch()

Three habits from the notebooks carry over to every demo:

  • Load the model once, outside the function. 05e builds its sentiment pipeline at the top of the notebook and only calls it inside predict_sentiment. A pipeline built inside the event function would reload the weights on every click.
  • Fail with a message. raise gr.Error("…") stops the function and shows the message in the page; gr.Warning("…") shows a notice and lets the function finish (05f).
  • Style through launch() in Gradio 6. 05g passes theme= to gr.Interface and css= to gr.Blocks. Gradio 6.31, the version this course locks, still accepts both but warns “The parameters have been moved from the Blocks constructor to the launch() method in Gradio 6.0”; pass them as demo.launch(theme=…, css=…).

Notebook 05e’s last cell, gr.load("distilbert-base-uncased-finetuned-sst-2-english", src=…), runs the model on Hugging Face’s servers instead of locally. In the course copy its src points at a GitHub folder URL, which gr.load does not accept; the source notebook has src="models", which loads the model by its Hub name.

A demo is a tool for trying a model with people who do not run notebooks, such as the Larkspur support lead. It has no login, rate limit or monitoring unless you add them, so in production the model runs behind a service with those controls, and the demo stays a way to try it.

Key Takeaways

  • Use gr.Interface for a quick form around one function, and gr.Blocks when you need your own layout and many events, each wired to a function with calls such as button.click(fn, inputs, outputs).
  • Load the model once when the app starts, raise gr.Error to stop with a message, and pass theme= and css= to launch() in Gradio 6.
  • A demo has no login, rate limit or monitoring. Use it to let people try a model, and serve production traffic from a service with those controls.

Check yourself

1. What does gr.Blocks leave you to do that gr.Interface does for you?

gr.Interface builds a form around one function: input components, a Submit button, the outputs and a Flag button. gr.Blocks adds no button and calls nothing by itself: you place the components in rows, columns and tabs, and connect each event to a function, such as button.click(fn, inputs, outputs). In return one page can hold many components and events.

2. In the Larkspur ticket tagger, the support lead clicks Tag with an empty ticket box. What does the page show, and does the classifier run?

The page shows “Paste a ticket first.” and the classifier does not run. tag checks for an empty ticket first, and raise gr.Error(...) stops the function there and shows the message. gr.Warning would show a notice and let the function finish.

3. Every click in a colleague's Gradio demo reloads the model weights. Where did they build the pipeline, and where should it go?

Inside the event function, so each call builds the pipeline again. Build it once outside the function, when the app starts, as 05e and the ticket tagger do, and only call it inside the function.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur indexes each handbook page as one chunk with all-MiniLM-L6-v2. Support says “How fast does support answer a ticket?” never finds the FAQ page, though the answer is on it. What do you check?

What a strong answer covers:

  • Tokenizes the page with the model’s own tokenizer and compares the count with max_seq_length (256 here); the FAQ page is 291 tokens, so the support answer is past the cut
  • Proves it by embedding the page and its first 1,231 characters: the two vectors are identical (cosine 1.0000), so the tail never mattered
  • Fixes it at chunking time (M13), with chunk sizes counted in the embedding model’s tokens, not characters
  • Adds a check at indexing time that logs or rejects any chunk over the limit, since the library raises no error

2. A teammate’s service calls pipeline("sentiment-analysis") with no model argument to tag tickets. Is that ready to ship?

What a strong answer covers:

  • The task name picks a default model (distilbert-base-uncased-finetuned-sst-2-english in transformers 5.17.0) and the default can change in any release; text-generation now defaults to SmolLM3-3B, and the question-answering and translation tasks the notebook uses are gone in 5.x
  • Pins model= and revision= (a commit hash) so the same weights run in every environment
  • Checks the model fits the data: SST-2 is movie reviews with two labels, while tickets need categories such as billing or outage
  • Measures it on labelled tickets before trusting the score, as notebook 01b does with the 1,066 Rotten Tomatoes test reviews

3. Finance asks what the ticket tagger will cost and how slow it is. How do you estimate it before launch?

What a strong answer covers:

  • Counts tokens with the model’s own tokenizer on a sample of real tickets; characters divided by four is close on prose and off by almost half on names and odd words (2.29 characters per token on the notebook’s sentence)
  • Measures latency per batch on the target hardware, with the model loaded once, not per request
  • Separates the one-time costs (download, about 268 MB for the SST-2 model, and load) from the per-call cost
  • Tracks token counts and latency percentiles in production, because ticket length drifts

4. The tagger runs in containers on a cluster with no internet access. The first deploy fails at startup. Why, and how do you ship models there?

What a strong answer covers:

  • from_pretrained tries to download on a cache miss; with no network it fails, and every new pod would download again even with network
  • Builds the cache into the image or a mounted volume (HF_HOME or HF_HUB_CACHE), at a pinned revision
  • Sets HF_HUB_OFFLINE=1 so the library reads the cache and never calls the Hub
  • Watches disk use with hf cache ls and removes revisions no branch points to with hf cache prune; their blobs stay on disk until then

5. The support lead’s Gradio demo takes several seconds per click, though the model alone answers in a fraction of that. Where does the time go?

What a strong answer covers:

  • Looks for the model being loaded inside the event function; load the pipeline once at module level and call it in the function
  • Checks whether share=True routes traffic through a tunnel, and whether many users queue behind one worker
  • Times each step (tokenize, model, post-process, network) instead of guessing
  • Treats the demo as a demo: authentication, rate limits and monitoring belong to the real service, not to launch()

Key Takeaways

  • Pin every model by name and commit. A task default or a moving main branch changes your results without changing your code.
  • Count tokens with the model’s own tokenizer, and keep every input under its limit; truncation is silent.
  • A pipeline is tokenizer, model and post-processing. When its output is wrong, check each of the three before blaming the model.
  • Load models once and call them many times, in notebooks, services and Gradio demos alike.
