M30 Adaptive RAG and query routing

A plain RAG pipeline sends every question down the same path. An adaptive one decides first: which knowledge base to search, whether to search the web instead, whether a person should take over, and how much retrieval work the question deserves. The M30 notebooks build on four ideas: classifying the query into a closed set of labels, routing each label to its own knowledge base, escalating to a human, and choosing a retrieval strategy per query type.

Open the lab

The running example is the Larkspur Cloud support desk. The twelve handbook chunks from M11 are split into the three knowledge bases the 01a notebook routes between: billing (five chunks), technical (four) and general (three). The lab routes eighteen support tickets, each labelled with the knowledge base that holds its answer, such as Why was I billed twice this month? (billing) and How long do you keep my data after I cancel? (general).

TL;DR

  • A router is a classifier in front of retrieval. In the notebooks it is one LLM call with structured output that must return a label from a fixed set (Literal['Technical', 'Billing', 'General']), and the label becomes a metadata filter or a branch in a LangGraph graph.
  • A misroute hides the answer: the filter restricts retrieval to a knowledge base that does not hold it. In the lab, a router that always picks sends 15 of 18 tickets to the right knowledge base at one search each. A score floor of 0.42 removes all 3 misroutes, but 11 tickets then fall back to searching all three knowledge bases, 2.22 searches per ticket.
  • Escalation is checked before the category. A negative ticket goes to a person whatever it is about; the healthcare notebook adds a fourth sentiment, Distress, that goes to an on-call team.
  • Adaptive RAG routes between the vector store and the web, then checks twice: a document grader sends the question to the web when half or fewer chunks pass, and a hallucination grader sends an unsupported answer back for regeneration.
  • A strategy per query type spends LLM calls where the question needs them. In the 04a notebook a factual or contextual question costs up to 11 LLM calls and an analytical or opinion question 4.

Mental model

The router decides what retrieval is allowed to see. Each knowledge base then retrieves and the model answers from what came back. Grading and generation work only with what the chosen path returns, so a misroute surfaces as a confident wrong answer or an apology, never as an error.

Query classification

Lesson 30.1: Router agentic RAG over multiple knowledge bases. Notebooks: 01a_router_agentic_rag.ipynb, 01b_router_agentic_rag_modular.ipynb (optional)

A router is a classifier whose output decides where a question goes. In 01a, categorize_inquiry fills the route_category prompt from prompts.yaml and calls the LLM with with_structured_output(QueryCategory), where

class QueryCategory(BaseModel):
    categorized_topic: Literal['Technical', 'Billing', 'General']

The Literal closes the label set. The parsed output can only be one of three strings, so determine_route can compare against them with no defensive parsing. The prompt gives each label a one-line definition (“Billing queries will focus more on payment and purchase related aspects”). Those definitions are the router’s whole specification: a ticket that fits two of them gets whichever label the model leans toward that day.

Every notebook in M30 puts a classifier of this kind in front of something:

Notebook Labels Output field What the label decides
01a Technical, Billing, General Literal Which knowledge base filter to apply
01a Positive, Neutral, Negative Literal Escalate to a human or answer
02a Billing, Appointments, Records, Insurance Literal Which department’s documents to search
02a Positive, Neutral, Negative, Distress Literal Human support, on-call team or answer
03a vectordb, web_search Literal Vector store or web search
04a Factual, Analytical, Opinion, Contextual str Which retrieval strategy runs

The last row shows why the schema matters. The 04a classifier’s field is a plain str, and its result indexes a dictionary of four strategies. If the model writes factual or Factual query, the lookup raises a KeyError. With a Literal, the structured-output parser rejects the value instead.

01a classifies category and sentiment in two sequential LLM calls. One call with a two-field schema would halve the classification cost; two prompts are easier to evaluate and change separately. Either way, keep the labels you route on in the schema, never in free text you parse afterwards.

An LLM classifier is one of two ways to route. M18 calls it logical routing; the other, semantic routing, compares the question with example text for each route and takes the closest. The lab below uses the semantic kind with TF-IDF, because it runs in the browser and its scores can be checked exactly.

Multi-KB routing

01a builds one Chroma collection, knowledge_base, with cosine distance (collection_metadata={"hnsw:space": "cosine"}). Each document carries a category field in its metadata. The retriever returns at most three chunks scoring 0.2 or more (search_type="similarity_score_threshold", k=3, score_threshold=0.2). The knowledge bases are separate only through the filter: before retrieving, a response node sets search_kwargs["filter"] = {"category": category}. 02a notes the other design, one vector store per category.

Three details in 01a decide whether a route works:

  • The label and the stored value must match exactly. The classifier returns Technical; the metadata says technical. Chroma compares metadata values exactly, so each response node lowercases the label before filtering. The notebook runs the refund question with the filters general, General and technical to show the difference; the last is what a misroute retrieves.
  • A misroute is silent. Filtered to the wrong knowledge base, the retriever returns whatever clears 0.2 there, or nothing. With no chunks, the response prompt tells the model to reply “Apologies I was not able to answer your question”. Nothing in the graph records that the route was wrong.
  • The filter is written onto a shared retriever. retrieve_knowledge_base_content mutates kbase_search.search_kwargs, so two requests served at once can overwrite each other’s filter. Pass it per call instead: kbase_search.invoke(query, filter={"category": category}), which VectorStoreRetriever merges over its defaults.

The optional 01b notebook keeps the same graph and binds one generate_support_response to the three response nodes with functools.partial, so the three prompts become one response_generation template. Adding a fourth knowledge base then means a prompt entry, a node and a branch in determine_route.

The classifier in 01a must always answer, because its schema has no “unsure” label. A router that can abstain needs a confidence score and a rule for what happens below it:

The interactive lab runs this rule on eighteen Larkspur tickets. Each knowledge base is scored by its best chunk under TF-IDF (scikit-learn’s weighting, the same index as the M11 lab), and the ticket goes to the highest. A fallback searches all three knowledge bases, so it always includes the right one but costs three searches instead of one. Its numbers:

Floor Misrouted Fall back Reach the right KB Searches per ticket
0.00 3 0 15 of 18 1.00
0.01 2 1 16 of 18 1.11
0.30 2 4 16 of 18 1.44
0.42 0 11 18 of 18 2.22

The three misroutes fail for different reasons:

  • The dashboard keeps logging me out. shares no term with any chunk, so every knowledge base scores 0.000 and the always-route rule sends it to billing, the first in the list. Any floor above zero catches it, for 0.11 extra searches per ticket.
  • How long do you keep my data after I cancel? goes to technical at 0.320, because “data” matches the export chunk. The retention chunk says “cancelled”, not “cancel”, and scores 0.184. A floor of 0.32 catches it, but by then three correctly routed tickets also fall back.
  • My server went down for an hour. Will I be compensated? reduces to the single word “server” once stop words are removed (“down” is one of them), exactly like the correctly routed How do I restart a server that stopped responding?. Both score 0.416 for technical, so no floor can separate them. Catching it at 0.42 sends 8 correct tickets to the fallback with it.

A floor removes the misroutes that have no signal, cheaply. Confident misroutes need a better classifier (embeddings, an LLM, or several example tickets per route) and a labelled routing set to find them, since the router’s own score cannot.

Human-in-the-loop escalation

Lesson 30.2: Customer-facing routing with sentiment and human escalation. Notebooks: 02a_healthcare_router_agentic_rag.ipynb (optional)

Some tickets should not be answered by retrieval at all. An angry customer wants a person; a customer in an emergency needs one now. Both router notebooks handle this by classifying sentiment as well as topic and checking sentiment first.

In 01a, determine_route reads:

if support_state["query_sentiment"] == "Negative":
    return "escalate_to_human_agent"
elif support_state["query_category"] == "Technical":
    ...

The order is the policy. A negative billing ticket never reaches the billing knowledge base, however well the router would have classified it. 01a’s escalate_to_human_agent returns a fixed apology and notifies nobody; it marks where a real handoff goes.

The healthcare notebook, 02a, builds that handoff for a clinic’s support desk. It routes four departments (Billing, Appointments, Records, Insurance) and four sentiments, with a rule in the sentiment prompt that “Distress” applies “only when the customer is facing a health emergency”:

Three parts of the design carry over to any support desk:

  • Two escalation targets. Negative goes to the support queue; Distress goes to on-call doctors. For Larkspur the same split separates an unhappy customer (support) from a production server down right now (the on-call engineer). Each target gets its own form and its own message back to the customer.
  • Each label maps to a filter value. The classifier returns Records; the documents are stored under medical_records. generate_department_response holds an explicit mapping from label to filter value, which is safer than lowercasing and hoping the strings agree.
  • The handoff carries context. The form collects name, number and email into escalation_cust_info (or oncall_cust_info), and the escalation node writes them into the reply. A production handoff should also pass the query, both labels and anything already retrieved, so the person does not start from zero.

How the graph waits for the person

02a’s form node displays Jupyter widgets and then loops, polling UI events with a 0.3-second sleep, until the Submit button sets a flag. The node holds the graph open the whole time. That works in a notebook. In a service it ties up a worker per waiting customer, and a restart loses every form in progress.

Both notebooks already compile their graphs with a MemorySaver checkpointer and run each conversation under a thread_id. That is what LangGraph’s interrupt() needs (M10): the node calls interrupt(...) with the form it wants filled, the graph saves its state and returns, and a later call with Command(resume=form_values) on the same thread continues from that node. Nothing waits in memory, and with a persistent checkpointer the paused ticket survives a restart.

Choosing what triggers escalation

Sentiment is a proxy for “a person should handle this”. It misses a calm customer with an urgent problem and catches a sarcastic one with a simple question. Count both errors on labelled tickets before trusting it:

Error What it costs at Larkspur How to see it
Missed escalation A customer with a production outage gets a handbook answer Tickets reopened or escalated by the customer after an automated answer
Needless escalation An agent’s time on a question the handbook answers Escalated tickets an agent closes with a handbook link

Other triggers belong beside sentiment: a router that fell back to searching every knowledge base, an answer the hallucination grader rejected (lesson 30.3), or the same customer asking the same question twice.

Routing between the vector store and the web

Lesson 30.3: Adaptive RAG: vector store vs web, with hallucination grading. Notebooks: 03a_adaptive_rag_langgraph.ipynb

Adaptive-RAG (Jeong et al., NAACL 2024, arXiv:2403.14403) starts from the observation that a fixed pipeline does the same work for an easy question and a hard one. The paper routes by question complexity: no retrieval, one retrieval step or several, chosen by a small classifier trained for the job. The 03a notebook keeps the idea of deciding up front and routes by source instead: the vector store or the web.

The source classifier is one LLM call with a closed schema, datasource: Literal["vectordb", "web_search"]. Its system prompt lists what the vector store holds (chain-of-thought prompting, transformers and attention, DINO, diffusion models, parameter-efficient fine-tuning) and asks the model to choose vectordb when the question relates to any of them. That list is the router’s only knowledge of the index. Add documents on a new topic and the router keeps sending those questions to the web until someone edits the prompt. For Larkspur, the list would be the handbook’s sections: pricing, refunds, exports, outages and server sizing.

Each route rewrites the question for its own engine before searching. The vector-store rewriter makes it concise for semantic search; the web rewriter makes it a search-engine query.

Path Settings in 03a
Vector store Research-paper PDFs split at 4,000 characters with 300 overlap; Chroma with cosine distance; up to 5 chunks scoring 0.35 or more
Web Tavily with max_results=6, search_depth='advanced' and include_raw_content=True; pages with no content are dropped

Grading documents and answers

The graph checks its work twice, once on the evidence and once on the answer. M28 and M29 teach each check on its own; here they sit behind a router.

The document grader asks the LLM, once per retrieved chunk, whether the chunk is relevant (binary_score, yes or no). grade_documents keeps the chunks graded yes and computes the relevant fraction. The rule is relevance_frac <= 0.5, with RELEVANCE_THRESHOLD = 0.5:

Chunks retrieved Graded relevant Fraction Next step
5 3 0.60 Generate from the 3
4 2 0.50 Web search, keeping the 2
5 2 0.40 Web search, keeping the 2
0 0 none Web search

Exactly half counts as failure. On the web route, web_search appends the pages to the chunks that passed, so the answer can draw on both sources.

The hallucination grader reads the answer and the documents and returns binary_score and feedback. The score is inverted from what the name suggests: yes means the answer may contain unsupported or contradicting content. On yes, the graph returns to generate_answer, which adds the feedback to the RAG prompt and tries again. On no, the graph ends.

Nothing counts the retries. The regeneration edge has no limit, so a grader that keeps saying yes loops until LangGraph’s recursion limit stops the graph, and in the version this repo locks (langgraph 1.2.18) that limit is 10,007 steps by default. Each round costs two LLM calls. Add a counter to GraphState, stop after one or two retries, and return the best answer with a warning or escalate it (lesson 30.2).

The notebook tests the loop by uncommenting a hard-coded wrong answer in generate_answer. That line sits in the first-attempt branch only, so the retry, which takes the feedback branch, runs the real chain. The test exercises one rejection and one retry with feedback.

Counting the LLM calls per path from the graph, before any retry:

Path LLM calls Web searches
Vector store, grading passes Route, rewrite, up to 5 grades, generate, check: up to 9 0
Vector store, grading fails The same plus a web rewrite: up to 10 1
Web from the start Route, rewrite, generate, check: 4 1

A question the router sends to the vector store and the grader then rejects is the most expensive path. If many questions take it, the router’s topic list is wrong or the index is missing content, and both are cheaper to fix than to grade around.

Per-query strategy

Lesson 30.4: Strategy per query type. Notebooks: 04a_adaptive_retrieval_rag_techniques.ipynb

Lessons 30.1 to 30.3 route a question to a place: a knowledge base, a person, the web. The 04a notebook routes it to a method. A classifier labels the question Factual, Analytical, Opinion or Contextual, and each label runs a different retrieval strategy over the same index. The idea is to spend retrieval work where the question needs it: precision for a fact, coverage for an analysis, spread for an opinion, the user’s situation for a contextual question.

Type What the question wants How 04a retrieves LLM calls per question
Factual One verifiable fact Rewrites the query, retrieves 8 chunks, has the LLM score each from 1 to 10, keeps the top 4 Up to 11
Analytical An explanation that covers several aspects Generates 4 sub-questions, retrieves 2 chunks for each, has the LLM pick the 4 most diverse and relevant 4
Opinion Several viewpoints Has the LLM name 3 viewpoints, retrieves 2 chunks for each, has the LLM pick 3 representative ones 4
Contextual An answer for this user Rewrites the query with the user’s context, retrieves 8 chunks, scores each against query and context, keeps the top 4 Up to 11

The call counts include the classifier and the final answer. The factual and contextual strategies score chunks one LLM call at a time, so their cost grows with the number retrieved; the analytical and opinion strategies spend one call to plan the searches and one to select.

On the Larkspur handbook the four types look like this:

  • Factual: How long does a refund take? One chunk holds the answer; precision matters more than coverage.
  • Analytical: Should we move from monthly to annual billing? The answer needs the billing cycle, the refund window and cancellation, three chunks a single query may not reach together.
  • Opinion: Is the starter plan good enough for a small shop? A handbook states policies, not opinions, so a viewpoint search finds little; the honest answer lists the facts that bear on the choice.
  • Contextual: Which server size do I need? The answer depends on the customer’s peak memory use, which belongs in the context passed to the strategy.

The notebook’s code has four faults worth knowing before you reuse it:

  • The classifier’s label is free text. categories_options.category is a str, and AdaptiveRetriever looks it up in a dictionary of four strategies. Any other spelling raises a KeyError. A Literal field, as in lesson 30.1, closes the set.
  • The opinion strategy cannot finish. The selection call returns SelectedIndices, whose indices field is already a list of integers, and the code then calls .split() on it, which raises an AttributeError. Iterating over the list fixes it.
  • The user’s context never arrives. ContextualRetrievalStrategy.retrieve accepts user_context, but AdaptiveRetriever calls every strategy with the query alone, so the contextual path always runs with “No specific context provided”.
  • Each strategy builds its own index. All four inherit a constructor that splits the texts (800 characters, no overlap), embeds them and builds a FAISS index, so the corpus is embedded four times at start-up. One shared index serves all four.

The demo corpus is one sentence about the Earth. Every search returns that one chunk, so the four strategies cannot retrieve different evidence and the demo cannot show that the routing helps. To see it, run the four sample questions over a real corpus and compare each strategy against plain top-k retrieval on the same golden set, the way M11 sets a baseline.

The Adaptive-RAG paper behind lesson 30.3 routes on a different axis, question complexity: no retrieval, one step or several. The two combine. A complexity router decides how many rounds of retrieval to run; a type router decides what each round looks for.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s support assistant started answering “Apologies, I was not able to answer your question” to customers who ask how long their data is kept after they cancel. The retention chunk is in the general knowledge base. How do you find the fault?

What a strong answer covers:

  • Pulls the logged category for those tickets first: a ticket routed to technical or billing never searches the general knowledge base, whatever the retriever does
  • Checks that the label matches the stored metadata exactly (General against general), since a filter that matches nothing returns no chunks and triggers the apology
  • Replays retrieval with the correct filter to separate a routing failure from a retrieval failure (score below the 0.2 threshold, chunk missing from the index)
  • Adds the failing tickets to a labelled routing set, and adds a fallback that searches without the filter when the filtered search returns nothing

2. The team is splitting the handbook into billing, technical and general knowledge bases. One Chroma collection with a category filter, or one collection per department?

What a strong answer covers:

  • One collection with a filter (the 01a design) keeps one embedding model and one index to run, and a fallback is the same search with the filter removed
  • Separate collections let each department choose its own chunking, embedding model and re-indexing schedule, at the cost of a fan-out query for the fallback
  • A misroute costs the same in both designs, because both trust the label
  • Access control never rests on a classifier’s label: if some documents are restricted, enforce it with collections or filters derived from the user’s identity

3. The router has been live for a month. How do you know whether it is still routing well?

What a strong answer covers:

  • Keeps a labelled routing set (the lab’s eighteen tickets are a small version) and reports accuracy per category and a confusion matrix on every prompt or model change
  • Logs the label, its score or confidence, the fallback rate and the escalation rate per day, and watches the label mix: a launch can create a kind of question no knowledge base covers
  • Tracks downstream signals per route, such as empty retrievals and apology answers, since a silent misroute shows up there first
  • Samples routed tickets for human review, weighted toward low-confidence and fallback cases

4. A ticket reads: “I was charged twice and my server has been down all morning. This is ridiculous.” What should the router do?

What a strong answer covers:

  • Sentiment runs first in determine_route, so a negative reading sends it to a person; the handoff should carry both topics, the contact details and anything already retrieved
  • A single-label classifier must drop one of the two problems; a schema that allows several labels, or decomposition into sub-questions (M18), keeps both
  • An outage in progress may deserve the on-call path, the way the healthcare notebook separates Distress from Negative
  • Measures both error costs: a missed escalation loses a customer, and a needless one costs an agent’s time

5. The adaptive RAG graph from lesson 30.3 is much slower and costlier than the plain pipeline it replaced. Where do the calls go, and what do you cut?

What a strong answer covers:

  • Counts LLM calls per path from the graph: on the vector route, one for routing, one rewrite, one grade per retrieved chunk (up to five), one answer and one hallucination check, plus a rewrite and a web search when grading fails
  • Grades all chunks in one call, or skips grading when the top retrieval score is high
  • Puts a retry counter in the graph state: the regeneration loop has none, so only LangGraph’s recursion limit stops it, and that limit is 10,007 steps by default in the version this repo locks (langgraph 1.2.18)
  • Moves routing and grading to a smaller model, traces latency per node, and re-checks answer quality against the baseline after each cut

Key Takeaways

  • Give the router a closed label set in its output schema, and normalise the label before it becomes a filter.
  • Plan for the misroute. A score floor with an unfiltered fallback catches routes with no signal cheaply; confident misroutes only show up on a labelled routing set.
  • Check escalation before the category, and make the handoff a pause with saved state rather than a node that blocks while it waits.
  • Every grader loop needs a counter, and every query type should spend only the LLM calls its question needs.
