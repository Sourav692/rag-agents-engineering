M31 RAG as an agent tool

In M28 to M30 the graph decides when to retrieve: a grader, a router or a fixed edge sends every question down a path someone drew in advance. In M31 retrieval becomes one tool among several, and the model decides whether to call it and what query to send. The M31 notebooks build on four ideas: the agent deciding when to retrieve, the tool description as the only thing it knows about the retriever, managed platforms that run the whole RAG pipeline as a service, and the chat UI that puts an agent in front of users.

Tool descriptions and routing
Open the lab

The running example is the Larkspur Cloud support agent. It has two tools: handbook_search, a retriever over the handbook from M11 to M13, and web_search for everything outside Larkspur. The lab routes twenty mixed questions between them, ten about the handbook (How long does a refund take?, Can I export my data after I cancel my plan?), six for the web (What does Hetzner charge for a 4 GB server?) and four that need no tool at all (What is 15% of 240?).

TL;DR

  • As a tool, retrieval runs inside a loop: the agent node calls the model, the model may reply with a tool call, ToolNode runs the retriever, and the chunks go back to the model as a ToolMessage. The loop ends when the model replies without a tool call.
  • All the model knows about a tool is its name, its description and its argument schema. In the lab, where TF-IDF stands in for the model, two tools both described as “Search tool.” route 4 of 20 questions correctly, and only the four that needed no tool; specific descriptions route 15 of 20.
  • Tune descriptions like any retrieval setting: on a golden set, then on questions held out from it. Fitted to the lab’s twenty questions they route 19 of 20 and 4 of 5 held-out questions, and they cost 133 tokens on every model call instead of 84.
  • A managed RAG platform (Contextual AI in lesson 31.2) runs the datastore, parser, reranker and grounded generator behind one API. The agent can call the whole platform as a single tool, so swapping it in leaves the agent loop unchanged.
  • A chat UI adds sessions, settings and visible tool steps. State such as the index and the agent belongs to the user’s session, not to module globals.

Mental model

Retrieval sits inside the loop, so the model decides whether it runs, how often, and with which query. A question that never triggers a tool call is answered from the model’s weights, with no handbook text in front of it. The quality of the retriever matters only for questions the model sends to it.

Agent-decided retrieval

Lesson 31.1: RAG as a tool inside a LangGraph agent. Notebooks: 01a_rag_as_tool_in_agents.ipynb

The notebook builds two graphs over the same retriever: four short documents about a fictional cafe, embedded with text-embedding-3-small, stored in Chroma and searched with k = 2. These pages tell the same story with the Larkspur handbook.

The first graph lets the pipeline decide. A classifier node, topic_decision, asks the model a yes or no question with structured output (GradeQuestion.score), and a conditional edge sends the question either to retrieve and generate_answer or to a fixed off-topic reply. Every on-topic question is retrieved exactly once, with the user’s words as the query.

The second graph lets the model decide. create_retriever_tool wraps the retriever as retriever_tool, a second tool off_topic handles unrelated questions, and both are bound to the model with bind_tools. The graph has two nodes: agent calls the model, and ToolNode runs whatever tools it asked for. should_continue routes to tools while the last message has tool_calls, and to END when it has none. The edge from tools back to agent makes it a loop.

Both graphs spend two model calls on a handbook question: classify and generate in the first, tool call and answer in the second. They differ in who decides and what the retriever receives:

Pipeline decides Model decides
The retrieval decision topic_decision, then fixed edges the model, through tool_calls
What the decision reads the classifier’s system prompt each tool’s name, description and argument schema
Query sent to the retriever the user’s message, unchanged the query argument the model writes
Retrievals per question 0 or 1 0, 1 or more, because tools loops back to agent
Unrelated questions off_topic_response, a fixed message the off_topic tool, or a direct answer
Typical failure the classifier says no and the handbook is never searched the model answers from memory and never calls the tool

The model-decided graph handles what the fixed one cannot: small talk that needs no retrieval, a follow-up whose query must be rewritten from the conversation, and a second search when the first chunks miss. It pays for that with a decision you no longer control in code. A question about Larkspur’s refund window that the model answers without calling handbook_search gets an answer from its training data, with nothing to cite.

The tool’s output loses the sources. create_retriever_tool joins the retrieved page_content strings with a blank line (document_separator="\n\n") and drops the metadata, so the model sees the chunk text without the source field. To cite, pass a document_prompt that prints the source into each chunk, or response_format="content_and_artifact" to keep the Documents beside the text.

Tool descriptions

When the model picks a tool, it reads what bind_tools sends with every call: each tool’s name, its description and the JSON schema of its arguments. For the notebook’s retriever tool that is:

{"type": "function",
 "function": {"name": "retriever_tool",
              "description": "Information related to pricing, hours, or the founder of Cafe Lumiere.",
              "parameters": {"type": "object", "required": ["query"],
                             "properties": {"query": {"type": "string", "description": "query to look up in retriever"}}}}}

The description carries the scope that the first graph kept in its classifier prompt (“questions about Cafe Lumiere’s founder, menu pricing, or opening hours”). It now has to separate retriever_tool from every other tool the model can call, and the model never sees the documents behind it.

The interactive lab gives the Larkspur agent two tools, handbook_search and web_search, and routes twenty golden questions plus five held-out ones. Its router is a stand-in for the model: the M11 TF-IDF retriever, scoring each question against the two descriptions and picking the higher score, or no tool when neither shares a word with the question. Its scores match scikit-learn’s TfidfVectorizer to within 4.5e-16. The four presets:

Descriptions Golden set, of 20 Sent to the wrong tool Held out, of 5 Tokens per call
Names only: “Search tool.” for both 4 0 0 6
Vague: “Information related to Larkspur Cloud plans and pricing.” 5 0 0 20
Specific: the topics each tool covers 15 1 2 84
Tuned: Specific plus words taken from the golden questions 19 0 4 133
  • Names only routes nothing. The four questions it gets right are the small talk and arithmetic that needed no tool; all sixteen handbook and web questions are answered from memory.
  • Vague catches When are monthly plans billed? on the word “plans” and nothing else. Can I export my data after I cancel my plan? misses because the lab, like TF-IDF, treats “plan” and “plans” as different words.
  • Specific routes 15 of 20, with one question sent to the wrong tool: What does Hetzner charge for a 4 GB server? goes to handbook_search, because “server” appears only in the handbook description. A competitor’s price answered from Larkspur’s handbook is the worst miss in the set. Three handbook questions are right for the same thin reason: goes down, reboot and size match nothing, and “server” carries them.
  • Tuned names PostgreSQL, AWS, Hetzner, Docker and Ubuntu, words copied from the golden questions, and reaches 19 of 20. On the held-out five it reaches 4 of 5: What is the newest Node.js version? still gets no tool. It also sends 133 tokens with every model call, against 84.

A model reads meaning, so word forms such as “refund” and “refunds” matter far less to it than to the stand-in. A missing scope fails for a model too. If neither description says which tool owns other providers’ prices, the model has to guess, as the stand-in did with the Hetzner question. A description that works states four things:

  • What it searches, and whose data: “the Larkspur Cloud handbook” against “the public web”.
  • The topics, in the words users type: refunds, cancelling, data export, outages, server sizing.
  • Where it stops: Larkspur’s own prices and policies belong to handbook_search; other providers’ prices belong to web_search.
  • What it returns: handbook passages as plain text, so the model knows what it will get back and that it must quote it.

Every description is sent with every call, so each added word costs tokens on every turn of every conversation. Treat the descriptions as a retrieval setting: keep a routing golden set of questions with the tool each one should use, score each change against it and against held-out questions, and add the misses you find in production traces.

Key Takeaways

  • Retrieval as a tool lets the model skip it for small talk, rewrite the query and search again. The cost is a decision outside your code, and a model that answers from memory has nothing to cite.
  • create_retriever_tool drops chunk metadata, so the model sees text without sources. Add the source with a document_prompt, or keep the Documents with response_format="content_and_artifact".
  • Write each tool description to say what it searches, its topics in users’ words, where it stops and what it returns. Test changes on a routing golden set and held-out questions.

Check yourself

1. What does letting the model decide when to retrieve gain over a fixed classifier, and what does it give up?

It handles small talk with no retrieval, rewrites a follow-up into a better query, and searches again when the first chunks miss. It gives up a decision you control in code: a model that answers a refund question without calling handbook_search answers from its training data, with nothing to cite.

2. With the specific descriptions, the question about Hetzner's price for a 4 GB server goes to the handbook tool. Why, and what fixes it?

“server” appears only in the handbook description, and neither description says which tool owns other providers’ prices, so the router guessed. State where each tool stops: Larkspur’s own prices and policies belong to handbook_search, other providers’ prices to web_search.

3. The tuned descriptions route 19 of 20 golden questions because they copy words from those questions. What else must you check before trusting them?

The held-out questions, where they reach 4 of 5 and still give the Node.js question no tool, and the cost: 133 tokens on every model call against 84. Keep a routing golden set and held-out questions, score each description change against both, and add misses from production traces.

Managed RAG

Lesson 31.2: Managed RAG platforms: Contextual AI. Notebooks: 02a_agentic_rag_contextual_ai.ipynb (optional)

Lesson 31.1 assembles retrieval from parts you run yourself: an embedding model, a Chroma collection, a retriever and a prompt. A managed RAG platform runs those parts as a service. You upload documents to a datastore, create an agent over it, and send questions to one endpoint. The notebook does this with Contextual AI’s Python SDK (from contextual import ContextualAI) over four PDFs, two of them quarterly revenue slides.

The question goes to the agent, and the answer comes back with the retrieved passages that support it. LMUnit sits outside the query path: it scores answers offline. Each box is a component you would otherwise build in an earlier module:

Component Call in the notebook What it does Built by hand in
Datastore client.datastores.create(name=...), then client.datastores.documents.ingest(datastore_id, file=f) Parses, chunks and indexes each upload. A document reports status='processing' until it is completed. M12 to M15
Parser POST /parse with parse_mode="standard", enable_document_hierarchy=True, figure_caption_mode="concise" Turns a PDF into Markdown per page, with the section hierarchy as structure M12
Reranker client.rerank.create(query=..., instruction=..., documents=..., metadata=..., model="ctxl-rerank-en-v1-instruct") Reorders passages by relevance and by a plain-language instruction about sources and dates M19
Grounded language model POST /generate with knowledge=[...], avoid_commentary, temperature=0 Answers only from the passages it is given, or says it has no relevant information M32
Agent client.agents.create(datastore_ids=[...], system_prompt=...), then client.agents.query.create(agent_id=..., messages=[...]) Runs retrieval, reranking and generation in one request M20
LMUnit client.lmunit.create(query=..., response=..., unit_test=...) Scores one answer against one natural-language test, from 1 to 5 M11’s golden set

After every policy change the Larkspur index holds two versions of the same rule, and the instruction-following reranker is built for that case. The notebook’s example ranks three passages about GPU pricing, an internal sales portal page from January 2025, an analyst report from November 2023 and an unrelated spec sheet, under the instruction “Prioritize internal sales documents over market analysis reports. More recent documents should be weighted higher.” For Larkspur the instruction would read “Prefer the current handbook over archived handbook versions and community forum posts”, with each passage’s date and source passed in metadata. The notebook ships without saved outputs, so these pages quote no scores from it, and its claims about benchmark results are the vendor’s own.

The grounded model’s avoid_commentary flag decides whether the answer may add context beyond the passages. The notebook calls it once with the flag off and once with it on, then asks a quantum-computing question against renewable-energy passages to show the refusal path. For a support agent, the refusal path is the one to test first: a question the handbook does not answer should get “I don’t have that information”, not a plausible policy.

A managed platform fits behind the tool interface from lesson 31.1. Wrap the agent query in a tool, and the LangGraph agent calls it like any retriever:

@tool
def handbook_search(query: str) -> str:
    """Search the Larkspur Cloud handbook: plans, billing, refunds, cancelling,
    data export and retention, outages, server sizing, support tickets."""
    result = client.agents.query.create(
        agent_id=agent_id, messages=[{"role": "user", "content": query}])
    return result.message.content

The calls are the notebook’s; the tool and its description are the 31.1 pattern. The outer agent still decides when to search, and the platform decides how.

What you trade:

  • You run fewer parts. Parsing, chunking, reranking and grounded generation come configured, and the platform’s UI shows ingested documents and agent answers.
  • You control fewer settings. Chunk size, embedding model and k are the platform’s choices unless its configuration exposes them. Beyond its name and datastore, the notebook’s agent sets only system_prompt, suggested_queries and enable_multi_turn.
  • Your documents leave your infrastructure. Check data residency, access control on each datastore, and how a deleted document leaves the index.
  • You measure it the same way. Run the M11 golden set through the platform agent and compare the row with your own pipeline’s. A managed platform is one more change to test against the baseline.

Key Takeaways

  • A managed RAG platform runs parsing, chunking, reranking and grounded generation as a service behind one endpoint. Wrap its agent query in a tool, and your own agent still decides when to search.
  • You run fewer parts but control fewer settings, and your documents leave your infrastructure. Check data residency, access control on each datastore and how a deleted document leaves the index.
  • Run your golden set through the platform agent and compare it with your own pipeline. Include questions the handbook cannot answer, which should get a refusal rather than a plausible policy.

Check yourself

1. What do you trade when you replace your own retrieval pipeline with a managed RAG platform?

You run fewer parts, since parsing, chunking, reranking and grounded generation come configured. You control fewer settings, such as chunk size, the embedding model and k, and your documents leave your infrastructure, so check residency, access control and deletion. You measure it the same way, by running the M11 golden set through it.

2. After a Larkspur policy change, the index holds an old and a new version of the same rule. How would the instruction-following reranker handle it?

Pass each passage’s date and source in metadata and an instruction such as “Prefer the current handbook over archived handbook versions and community forum posts”. The reranker then orders passages by relevance and by that instruction, so the current rule ranks above the archived one.

3. Which behaviour of the grounded language model should a support agent test first?

The refusal path. A question the handbook does not answer should get “I don’t have that information”, not a plausible policy. The notebook tests it by asking a quantum-computing question against renewable-energy passages.

Chat UI

Lesson 31.3: Exercise: LlamaIndex Wikipedia agent with Chainlit. Notebooks: 03a_llamaindex_wikipedia_agent (optional)

The exercise builds the 31.1 pattern in LlamaIndex and puts it behind a chat window. A ReAct agent gets one tool, a QueryEngineTool over a vector index of Wikipedia pages, and Chainlit serves the conversation. The two scaffolds, chat_agent.py.txt and index_wikipages.py.txt, have # REPLACE THIS WITH YOUR CODE gaps to fill; copy each to its .py name first and install the llamaindex dependency group.

A chat UI is event-driven. Chainlit calls one function per event, and the scaffold fills three of them:

Event Scaffold function What it does
Chat opens on_chat_start Sends cl.ChatSettings with a Select for the model and an input for the pages to index
Settings saved setup_agent, under @cl.on_settings_update Turns the request into a page list, fetches and indexes the pages, builds the agent, then confirms in the chat
Message sent main, under @cl.on_message Runs the agent on the message and sends its reply back

index_wikipages.py turns a free-text request such as /get wikipages: paris, lagos, lao into a list of page titles with structured output: a Pydantic model, WikiPageList, filled by an LLM program. The folder’s README notes that llama-index-program-openai does not support llama-index-core 0.14; use FunctionCallingProgram or LLMTextCompletionProgram from llama_index.core.program instead.

Four things the UI changes about the agent:

  • Indexing happens while the user waits. The index is built when settings are saved, not offline as in M11. The scaffold answers with a confirmation message once it is ready; until then, questions have nothing to search.
  • State belongs to a session. The scaffold keeps index and agent in module globals. Chainlit serves every connected user from one Python process, so the second user to save settings replaces the first user’s index and agent. Store them per session with cl.user_session.set("agent", agent) and read them back with cl.user_session.get("agent"). Chainlit keeps a session for session_timeout seconds after the connection drops, 3600 in the scaffold’s config.toml.
  • The tool description can change per session. QueryEngineTool takes metadata=ToolMetadata(name=..., description=...). When each user indexes different pages, build the description from their settings (“Wikipedia articles on London, Barcelona and Paris”), so the agent knows what this session’s index holds. A fixed description such as “Wikipedia pages” says nothing about which ones.
  • Users can see the tool calls. Chainlit shows the agent’s intermediate steps in the chat. The scaffold’s config.toml was generated by Chainlit 0.7.0 and turns this on with hide_cot = false. Chainlit 2.x, which this course installs, reads its settings from .chainlit/config.toml and uses cot = "full", "tool_call" or "hidden" instead, with "full" as the default. For Larkspur’s support chat, a visible step per handbook_search call lets a support lead check the answer against what was retrieved.

The same three events host the Larkspur agent from lesson 31.1: build the agent per session in on_chat_start, run it in on_message, and stream its tool calls as steps.

Key Takeaways

  • Chainlit calls one function per event. Build the index and agent when settings are saved, run the agent on each message, and confirm in the chat once indexing finishes.
  • Keep the index and agent per session with cl.user_session, not in module globals, because one Python process serves every connected user.
  • Build the tool description from each session’s settings so the agent knows what its index holds. Show tool calls as steps, set with cot in Chainlit 2.x, so a reviewer can check answers against retrieval.

Check yourself

1. Why does keeping the index and agent in module globals break the Chainlit app as soon as two people use it?

Chainlit serves every connected user from one Python process, so the second user to save settings replaces the first user’s index and agent. Store them per session with cl.user_session.set("agent", agent) and read them back with cl.user_session.get("agent").

2. A user indexes the Wikipedia pages on London, Barcelona and Paris. What tool description should that session's agent get?

One built from the user’s settings, such as “Wikipedia articles on London, Barcelona and Paris”, passed through ToolMetadata on the QueryEngineTool. A fixed description such as “Wikipedia pages” tells the agent nothing about what this session’s index holds.

3. You keep the scaffold's setting that shows the agent's intermediate steps, but under the Chainlit version the course installs nothing changes. Why?

The scaffold’s config.toml was generated by Chainlit 0.7.0 and uses hide_cot = false. Chainlit 2.x reads .chainlit/config.toml and uses cot = "full", "tool_call" or "hidden" instead, with "full" as the default.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur adds a web_search tool to the support agent. A week later a customer asks “Can I get a refund on my annual plan?” and the agent quotes another provider’s refund policy. How do you find out what happened?

What a strong answer covers:

  • Opens the trace for that conversation and reads the model’s tool_calls: which tool it called, with which query, and what came back
  • If it called web_search: a routing failure. Compares the two descriptions for overlap (“refund”, “plans”, “pricing” in both, or in neither)
  • If it called handbook_search and still answered wrongly: a retrieval or generation failure, debugged as in M11 by printing the returned chunks
  • Rewrites the descriptions to state the boundary (“Larkspur’s own policies” against “other providers”), adds the question to a routing golden set, and re-runs it

2. The Larkspur support bot today always retrieves before it answers. A teammate wants to replace it with an agent that calls handbook_search only when it decides to. What do you gain, what do you risk, and how do you decide?

What a strong answer covers:

  • Gains: no retrieval for small talk or arithmetic, a query the model rewrites from the conversation, and a second call when the first chunks miss
  • Risks: the model answers a policy question from memory without calling the tool, or loops on tool calls and adds latency
  • Counts the cost per question from the graph: two model calls either way for a handbook question, more when the agent loops
  • Decides on the golden set: answer quality, the share of handbook questions that triggered the tool, and p95 latency, against the always-retrieve baseline

3. The agent is live. How do you monitor tool selection in production, before customers notice a wrong answer?

What a strong answer covers:

  • Logs every tool call with its name, the model-written query, the number of chunks returned and their top score
  • Tracks per-tool call rates and the share of answers given with no tool call; a jump after a prompt, model or description change is the alert
  • Samples conversations for an LLM judge or a reviewer to label the right tool, and grows the routing golden set from the misses
  • Re-runs the routing golden set and a held-out set on every change to a description, a tool list or the model

4. A customer asks “Is a 4 GB server cheaper at Larkspur or at Hetzner?” What should the agent do, and how can it go wrong?

What a strong answer covers:

  • The question needs both tools: handbook_search for Larkspur’s price and web_search for the competitor’s, then a comparison
  • Failure modes: only one tool is called and the other price is filled in from memory, or a web result about Larkspur outranks the handbook
  • Guards: descriptions that say which tool owns Larkspur’s own facts, answers that cite each figure’s source, and a refusal when one side is missing
  • Adds multi-tool questions to the routing golden set, scored on whether both tools were called

5. The platform team proposes replacing the hand-built handbook retriever with a managed RAG platform. What do you evaluate before you agree?

What a strong answer covers:

  • Runs the same golden set through both and compares answer quality, refusals on out-of-scope questions, and latency, as M11 does for any change
  • Checks what the platform does with the handbook’s tables and policy versions: its parser output, and whether reranker instructions can prefer the current policy
  • Reviews data residency, access control on the datastore, per-query cost, and what leaving the platform would take
  • Keeps the agent’s tool interface fixed (handbook_search(query)), so the swap is one tool’s implementation and the routing golden set still applies

Key Takeaways

  • An agent retrieves only when the model calls the tool. Measure how often it does on questions that need the handbook, and how often it does not.
  • Write each tool description for the model: what it searches, the topics in users’ words, and where it stops and the neighbouring tool starts. Keep it short, because it is sent on every call.
  • Tune descriptions against a routing golden set and score them on held-out questions too, as you would any retrieval setting.
  • A managed platform or a chat UI changes what sits behind or in front of the tool, not the loop. Keep the tool’s name, description and arguments stable across both.
