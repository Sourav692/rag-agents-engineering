M32 Reliability, Feedback Loops & Diversity

A RAG pipeline returns an answer whether or not the chunks behind it were relevant, whether or not the answer stays inside them, and whether or not the reader can check it. M32 adds a check for each of those, then lets user ratings reorder retrieval, then makes sure the chunks the model reads are not copies of each other. The M32 notebooks build on four ideas: catching an answer the retrieved chunks do not support, showing the exact passages an answer used, the difference between ratings users give and signals they leave, and choosing chunks that are relevant without repeating each other.

Open the lab

The running example is the Larkspur Cloud handbook from M11: the same twelve chunks and the same TF-IDF index as the M11 top-k lab. The golden set keeps M11’s three questions and adds two: Is there a credit if my server plan has an outage?, whose evidence ranks third, and Can I still use my server after I cancel the plan?, whose top answer carries an unrelated chunk along with the right one.

TL;DR

  • 01a wraps generation in two LLM graders: one answers yes or no for each retrieved chunk before generation, the other answers yes or no for whether the answer is grounded in the kept chunks. Both run llama-3.1-8b-instant on Groq at temperature 0 with structured output.
  • Source highlighting asks the model for verbatim segments of the chunks it used. Nothing in the parser enforces “verbatim”, so check every segment against its chunk in code.
  • 02a re-ranks with relevance_score *= average rating / 3, which keeps every chunk between 0.333 and 1.667. In the lab, 100 rated answers lift mean recall@2 on the golden set from 0.50 to 0.70, the order stops changing after event 8, and 40 of the 41 wrong answers go to two questions whose evidence the retriever never returns.
  • A thumbs-up or thumbs-down on the answer lands on every chunk in it. In the lab an unrelated chunk rides a good answer up to 1.667, and an evidence chunk is pushed down to 0.333 next to the distractor it was served with.
  • With the handbook stored five times, plain top-3 for the export question returns the export chunk three times. The notebook’s dartboard search returns export, retention, export at its default oversampling of 3, and export, retention, cancel at 4.

Mental model

The checks in the top row act on one answer and can only remove: a grader drops a chunk or rejects an answer, and neither can add the chunk that was missing. The loop in the bottom row acts across many answers and can only reorder the chunks retrieval already returns. A missing chunk is a retrieval problem in both rows, and the fixes for it sit in M14 to M19.

Relevance grading

Lesson 32.1: Reliable RAG: relevance checks, hallucination checks, source highlighting. Notebooks: 01a_reliable_rag.ipynb

01a indexes five posts from DeepLearning.AI’s The Batch on agentic design patterns. It splits them with RecursiveCharacterTextSplitter.from_tiktoken_encoder into 500-token chunks with no overlap, embeds them with OpenAI’s text-embedding-3-small into Chroma, and retrieves k = 4 chunks for a question about the kinds of agentic design pattern.

Before generation, a grader reads each retrieved chunk with the question and returns a structured verdict:

class GradeDocuments(BaseModel):
    binary_score: str = Field(description="Documents are relevant to the question, 'yes' or 'no'")

llm = ChatGroq(model="llama-3.1-8b-instant", temperature=0)
retrieval_grader = grade_prompt | llm.with_structured_output(GradeDocuments)

The prompt sets a low bar on purpose: a chunk is relevant if it shares keywords or meaning with the question, and “It does not need to be a stringent test. The goal is to filter out erroneous retrievals.” Chunks graded no are dropped, and only the kept ones go to the model. That is one grader call per chunk, four per question at k = 4.

On the Larkspur handbook, the M11 TF-IDF retriever answers How long does a refund take? with refund-window first and reboot second; reboot wins only because both texts contain “does”. A grader with this prompt should drop reboot. It cannot add refund-timing, the chunk that holds the answer, because that chunk was never retrieved. Grading removes noise and leaves recall where retrieval put it.

The notebook passes docs_to_use to generation without checking whether it is empty. If every chunk is graded no, the model receives no documents and answers anyway. Branch on the empty case: rewrite the query and retry a bounded number of times (M28), fall back to another source (M29), or say the handbook does not cover the question.

Hallucination detection

After generation, a second grader reads the kept chunks and the answer, and returns yes when the answer is “grounded in / supported by the set of facts”:

class GradeHallucinations(BaseModel):
    binary_score: str = Field(..., description="Answer is grounded in the facts, 'yes' or 'no'")

hallucination_grader = hallucination_prompt | llm.with_structured_output(GradeHallucinations)
hallucination_grader.invoke({"documents": format_docs(docs_to_use), "generation": generation})

Three things about this check decide how far to trust it:

  • It checks support, not usefulness. The question is not in the grader’s input. An answer can be fully grounded and still miss the question; Self-RAG (M29) adds a separate check for that.
  • It returns one verdict for the whole answer. One unsupported sentence fails the answer and the grader does not say which one. Per-claim checks, which split the answer into statements and verify each against a cited chunk, give the location as well as the verdict.
  • It is a model judgment. The same 8B model writes and grades here, so they can share blind spots. Before relying on it, label a sample of answers by hand and measure how often the grader agrees, for yes and no separately.

The generation prompt in 01a makes the grader’s job harder than it needs to be. It says “Answer the question based upon your knowledge”, which invites the model to add what it remembers. On the refund question, if only refund-window survives grading, any number of days in the answer is unsupported, because that chunk states the 30-day window and nothing about how long a refund takes. The grader should return no; a prompt that says “answer only from the documents, and say so when they do not cover the question” stops most of those answers before they are written.

The notebook prints the verdict and stops. In production, a no leads somewhere: regenerate with the stricter prompt, retry retrieval with a rewritten query, or answer that the handbook does not say and offer a person. Cap the retries; each one is another generation call and another grading call.

Source highlighting

The last step asks the model which parts of the kept chunks the answer used. A Pydantic schema and PydanticOutputParser define the output:

class HighlightDocuments(BaseModel):
    id: List[str]       # ids of the documents used
    title: List[str]
    source: List[str]
    segment: List[str]  # "direct segments from used documents that answers the question"

The prompt asks for segments that are “verbatim snippets from the documents, ensuring a word-for-word match”, and to leave out documents the answer did not use. For the Larkspur question Can I export my data after I cancel my plan?, a correct highlight returns two exact sentences:

Chunk Segment
export Export your data at any time from Settings, then Data.
retention After a plan is cancelled, its data is kept for 30 days and then permanently deleted.

The parser checks the JSON shape and nothing else. A model can paraphrase, merge two sentences or quote a chunk it was never given, and the output still parses. Check each segment in code before showing it:

for doc_id, segment in zip(result.id, result.segment):
    text = chunks_by_id[doc_id].page_content
    start = text.find(segment)          # -1 means the segment is not in the chunk

A segment that is found gives character offsets to highlight in the interface. A segment that is not found falls back to citing the whole chunk, and goes in a log, because a rising miss rate means the highlighting prompt or model has drifted. The four parallel lists have a trap of their own: zip stops at the shortest list, so a response with three ids and two segments silently loses a row. Compare the lengths before zipping.

Highlights serve the reader, who can check the answer against the handbook in one glance, and they serve the team. Logged segments show which chunks answers actually use, and a chunk that is retrieved often and never highlighted is a candidate for the grader to drop or for retrieval to stop returning.

Key Takeaways

  • Grade each retrieved chunk for relevance before generation, at one grader call per chunk. Grading drops noise but cannot add a chunk retrieval missed, so branch on the empty case instead of answering anyway.
  • The hallucination grader checks support, not usefulness, and returns one verdict for the whole answer. Measure its agreement with hand labels before trusting it, and route a no to a capped retry or an abstention.
  • A parser checks only the shape of highlighted segments. Confirm each one with text.find(segment), cite the whole chunk and log the miss when it is absent, and compare list lengths before zip.

The feedback re-ranker

Lesson 32.2: Retrieval with a user-feedback loop. Notebooks: 02a_retrieval_with_feedback_loop.ipynb

02a builds a RetrievalQA chain with gpt-4o over Understanding_Climate_Change.pdf and stores one feedback record per answer as a line of JSON:

{"query": ..., "response": ..., "relevance": 5, "quality": 5, "comments": ""}   # relevance and quality on a 1 to 5 scale

On the next query, adjust_relevance_scores re-weights the retrieved chunks. For each chunk and each stored record it asks gpt-4o whether the record is relevant to the current query and that chunk. It averages the relevance of the records judged relevant and multiplies the chunk’s score:

doc.metadata['relevance_score'] *= (avg_relevance / 3)  # Assuming a 1-5 scale, 3 is neutral
return sorted(docs, key=lambda x: x.metadata['relevance_score'], reverse=True)

Four properties of this rule decide what it can do:

  • Feedback sets the order on its own. encode_from_string in helper_functions.py gives every chunk relevance_score = 1.0, so after the multiplication the order depends on the ratings alone. Similarity only breaks ties, because Python’s sorted is stable and keeps the retriever’s order for equal scores.
  • The multiplier is bounded. It uses the average, so a chunk sits between 1/3 (every rating 1) and 5/3 (every rating 5). The first rating moves a chunk as far as it will go; later ratings only move the average.
  • It reorders the candidates and nothing else. The chunks come from retriever.invoke, which returns 4 by default. A chunk outside those 4 never receives a rating.
  • It costs one model call per pair. Every retrieved chunk is checked against every stored record, so 4 chunks and 1,000 records make 4,000 gpt-4o calls for one query.

The interactive lab runs this rule on the Larkspur handbook with the M11 TF-IDF retriever. Five golden questions take turns, 20 times each over 100 events. Each answer uses the top 2 of the 4 candidates, and the simulated user gives a 5 when every evidence chunk is in the answer and a 1 otherwise. The lab replaces the gpt-4o relevance call with a fixed rule: a record counts for a chunk when it was given on the same question and its answer used that chunk. Its port of the rule matches the Python function on all 202 settings it offers.

  • The credit question is fixed by one rating. Its candidates arrive as sizing, reboot, sla, export. At event 4 the answer uses sizing and reboot, the user gives a 1, and both drop to 0.333. sla and export move up at 1.000, the next answer contains the evidence, and the thumbs-up at event 9 lifts them to 1.667.
  • The loop stops learning early. No ranking changes after event 8 and no score changes after event 9. Events 10 to 100 add records and change nothing.
  • Feedback cannot reach a missing chunk. refund-timing scores 0 for the refund question, and sla and incidents score 0 for the outage question, so none of them is ever a candidate. Those two questions account for 40 of the 41 wrong answers. On the outage question, every candidate has an average of 1 by event 8, all sit at 0.333, and the order is the retriever’s again.

Three lines of the notebook’s code need fixing before the loop runs as described. The relevance check compares the model’s answer with lowercase 'yes' while the prompt asks for 'Yes' or 'No'; normalise with .strip().lower(). A FAISS store returns its stored Document objects, so *= on their metadata persists between calls and compounds: one rating of 5 gives 1.667 on the first query and 2.778 on the second. Copy the documents before adjusting them. And retriever.search_kwargs['docs'] = adjusted_docs has no effect: the FAISS retriever ignores a docs argument and searches the index again, so the re-ranked list has to be passed to the chain directly.

Implicit vs explicit feedback

Explicit feedback is a judgment the user states: a thumbs-up, a star rating, the 1 to 5 relevance and quality fields in 02a. Implicit feedback is inferred from what the user does next.

Explicit Implicit
Examples Thumbs up or down, a 1 to 5 rating, a comment Opening a cited source, copying the answer, asking the same question again in other words, opening a support ticket
Meaning Clear: the user said it Inferred: a rephrased question probably means the answer missed
Volume Only from users who choose to rate From every session
What it rates The whole answer Often one source, such as the one the user opened
Bias Raters choose themselves, so they may not be typical users Users click what is shown first, so top-ranked chunks collect more signal

The lab’s second setting shows why the granularity matters. Thumbs on the answer gives every chunk in the answer the same rating, as 02a does. Clicks on each source rates each chunk on its own: 5 for an evidence chunk the user opened, 1 for one they skipped. On Can I still use my server after I cancel the plan?, sizing is not evidence but sits in every good answer next to cancel. Rated through the answer, it rides along to 1.667; rated per source, it falls to 0.333. On the refund question the effect runs the other way: the answer is always incomplete, so thumbs on the answer push the evidence chunk refund-window down to 0.333 with the distractor, while per-source ratings lift it to 1.667.

The sharper signal does not change the lab’s totals. With either setting, mean recall@2 ends at 0.70 and 41 of 100 answers are wrong, because neither signal reaches a chunk the retriever does not return. Per-source ratings keep reshuffling non-evidence chunks for longer, and the order settles at event 15 instead of event 8.

In practice, use both. Implicit signals give volume and per-chunk detail, after correcting for position: compare clicks at the same rank, or occasionally shuffle the order of sources. Explicit ratings are fewer but mean what they say; every thumbs-down is a candidate for the golden set, so the next change to retrieval is measured on the questions that failed.

Folding good answers into the index

The second half of 02a uses feedback to change the index itself. fine_tune_index keeps records with relevance >= 4 and quality >= 4, joins each question and answer into one text, appends them to the original document text and re-encodes everything with encode_from_string (1,000-character chunks, 200 overlap) into a new FAISS store. The notebook calls it a periodic job, “daily or weekly”.

This adds chunks that are worded the way users ask, which helps future questions phrased like past ones. It has limits:

  • Only answers that were already good get in. In the lab, the refund and outage questions never earn a thumbs-up, so nothing about them would be added. The questions that most need new text get none.
  • Past answers become retrievable facts. When Larkspur changes a policy, the stored answers still quote the old one and compete with the corrected handbook. Tag each added chunk with its date and the handbook chunks it was answered from, and drop it when those change.
  • It rebuilds the whole index. Every run re-embeds the full corpus plus the feedback text; incremental upserts (M15) avoid that.

Key Takeaways

  • The feedback re-ranker multiplies each chunk’s score by its average rating over 3, so a chunk stays between 1/3 and 5/3 and ratings alone set the order. It costs one model call per chunk and stored record.
  • Feedback only reorders the candidates retrieval returns. In the lab, mean recall@2 rose from 0.50 to 0.70, but 40 of the 41 wrong answers came from chunks that were never candidates.
  • Combine implicit and explicit feedback. Implicit signals give volume and per-source detail once corrected for position; explicit ratings are fewer but mean what they say, and each thumbs-down is a golden-set candidate.

2. For the question about using a server after cancelling, how do thumbs on the answer and clicks on each source treat the sizing chunk?

sizing is not evidence but sits in every good answer next to cancel. Rated through the answer it rides along to 1.667; rated per source it falls to 0.333. Either way the lab’s totals stay at mean recall@2 0.70 and 41 wrong answers, because neither signal reaches a chunk the retriever does not return.

3. You plan to fold highly rated answers back into the index every week. What happens when Larkspur changes a policy, and how do you guard against it?

The stored answers still quote the old policy and compete with the corrected handbook as retrievable facts. Tag each added chunk with its date and the handbook chunks it was answered from, and drop it when those change.

Diversity-aware selection

Lesson 32.3: Dartboard RAG: relevance and diversity together. Notebooks: 03a_dartboard_rag.ipynb (optional)

When a knowledge base holds the same passage several times, top-k retrieval fills every slot with copies of the best match. 03a makes that happen on purpose: it loads Understanding_Climate_Change.pdf with documents = documents * 5, splits it into 1,000-character chunks with 200 overlap, and shows that the top 3 results for What is the main cause of climate change? are repetitions of one chunk.

Its fix comes from Better RAG using Relevant Information Gain (arXiv 2407.12101), the dartboard method. Picture the query as the centre of a dartboard and darts thrown around it. A set of chunks scores by how close its nearest member lies to where the darts land. A second copy of a chunk already in the set lies exactly where the first one does, so it adds nothing; a chunk that covers ground nearby adds the most.

greedy_dartsearch builds the set one chunk at a time from a candidate pool of num_results * oversampling_factor nearest chunks (3 by default):

  1. Turn distances (1 - cosine similarity) into log probabilities with a normal density of width SIGMA = 0.1, for query to chunk and for chunk to chunk.
  2. Pick the chunk most probable under the query.
  3. Treat every candidate as a place a dart can land, weighted by how close it is to the query (RELEVANCE_WEIGHT). For each remaining candidate, measure how close the set would come to each landing place if that candidate joined (DIVERSITY_WEIGHT), and sum over the landing places with logsumexp. Both weights are 1.0.
  4. Add the highest scorer and repeat until num_results are picked.

Running the notebook’s greedy_dartsearch, unchanged, on the twelve Larkspur chunks stored five times (60 chunks, TF-IDF vectors) shows both the gain and its limit. For Can I export my data after I cancel my plan?, whose evidence is export and retention, with num_results = 3:

oversampling_factor Pool Distinct chunks in pool Plain top-3 Dartboard top-3
1 3 1 export × 3 export, export, export
2 6 2 export × 3 export, retention, export
3 (default) 9 2 export × 3 export, retention, export
4 12 3 export × 3 export, retention, cancel

Plain top-3 has recall 0.50 on this question at every pool size. Dartboard reaches 1.00 once the pool holds retention, from an oversampling factor of 2. At the default of 3 its third pick is still a copy of export, because a pool of 9 drawn from five copies of each chunk holds only two distinct chunks. A selector can only choose among the candidates it is given: make the pool larger than the number of copies, or remove the copies at indexing time.

Dartboard and MMR (M17.4) solve the same problem the same greedy way and differ in the score. MMR subtracts a redundancy penalty with a linear λ; Dartboard adds log probabilities, so SIGMA sets how quickly closeness stops counting, and the two weights shift the balance between relevance and coverage. The notebook’s notes point out that the method needs only distances, so it works the same on dense, hybrid or cross-encoder scores.

Two details to know when running 03a. The first selection score is a placeholder of 1.0, not a computed score, so it cannot be compared with the scores after it. And the final cell calls get_context_with_dartboard(test_query, k=3), while the function’s parameter is num_results; Python raises a TypeError, and num_results=3 is the fix.

Key Takeaways

  • Top-k fills every slot with copies of the best match when the corpus holds duplicates. Dartboard selection scores a set by how close its nearest member lies to each landing place, so a copy adds nothing.
  • The selector only chooses among its num_results * oversampling_factor candidates. With five copies per chunk the default pool of 9 holds two distinct chunks, so enlarge the pool past the copy count or deduplicate at indexing.
  • Dartboard and MMR both select greedily and differ in the score. MMR subtracts a linear redundancy penalty, while dartboard adds log probabilities and needs only distances, so it works on dense, hybrid or cross-encoder scores.

Check yourself

1. Why does a second copy of a chunk already in the set add nothing to the dartboard score?

A set scores by how close its nearest member lies to where the darts land. The copy lies exactly where the first one does, so it brings no landing place any closer. A chunk that covers ground nearby adds the most.

2. With the Larkspur chunks stored five times and the default oversampling factor of 3, what does dartboard return for the export question, and why?

export, retention, export. Recall reaches 1.00 against 0.50 for plain top-3, but the pool of 9 drawn from five copies of each chunk holds only two distinct chunks, so the third pick is a copy. At a factor of 4 the pool holds three and the picks become export, retention, cancel.

3. Your retriever scores with a cross-encoder rather than embeddings. Can you still use dartboard selection, and how does it differ from MMR?

Yes: the method needs only distances, so it works the same on dense, hybrid or cross-encoder scores. Both pick greedily; MMR subtracts a redundancy penalty with a linear λ, while dartboard adds log probabilities, with SIGMA setting how quickly closeness stops counting.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. A Larkspur customer asks how long a refund takes. The assistant answers with a number of business days that differs from the handbook, and the hallucination grader marked the answer grounded. How do you work out what failed?

What a strong answer covers:

  • Pulls the trace: the retrieved chunks, the grader’s verdict on each, the kept set, the answer and the hallucination grader’s input
  • Checks retrieval first: on the M11 TF-IDF index refund-timing scores 0 for this question, so the kept set may hold only refund-window, which gives no duration at all
  • Checks the generation prompt: 01a tells the model to answer “based upon your knowledge”, which invites a remembered number; a grounded system says “only from the documents”
  • Treats the grader as a model with an error rate: labels a sample of answers by hand, measures how often the grader agrees, and adds this case to that set

2. Product wants a thumbs-up and thumbs-down on every answer, feeding a re-ranker like the one in 02a. What do you tell them it will and will not fix?

What a strong answer covers:

  • It reorders the candidates retrieval returns, so it fixes questions whose evidence is retrieved but ranked low (the lab’s credit question goes from recall@2 0.00 to 1.00 after one thumbs-down)
  • It cannot reach a chunk retrieval never returns: in the lab 40 of the 41 wrong answers in 100 events go to the refund and outage questions, and no rating changes that
  • A rating on the answer credits every chunk in it, so unrelated chunks ride along on good answers; per-source signals or a reranker trained on graded pairs are sharper
  • Ships it with a holdout: re-runs the golden set before and after, and watches per-question recall so one popular question cannot hide a regression elsewhere

3. The relevance grader and the hallucination grader have been live for a month. How do you know they are working, and what do you alert on?

What a strong answer covers:

  • Logs every verdict with the question, chunk ids and answer, so rates can be tracked per question type and per document
  • Watches the share of questions where every chunk is graded irrelevant, and the share of answers graded not grounded; a jump after an index or prompt change points at the change
  • Samples graded traffic for human labels each week and tracks the graders’ agreement with them, separately for “yes” and “no”, since a lenient grader fails in one direction
  • Counts the cost: 01a makes five grader calls per answer (one per chunk at k = 4, plus one grounding call) and a sixth for highlighting, and the latency they add belongs on the same dashboard

4. fine_tune_index has been folding highly rated question and answer pairs into the index every week. Larkspur then changes its refund rule. What goes wrong, and how do you guard against it?

What a strong answer covers:

  • Old answers that quote the old rule are now chunks in the index, and they match refund questions better than the handbook does because they were written as answers to those questions
  • The new handbook chunk competes with every highly rated answer that repeats the old rule
  • Tags every feedback-derived chunk with its source, date and the handbook chunks it was answered from, and removes it when any of those chunks changes
  • Keeps feedback chunks out of the citation path, or ranks them below primary documents, so the assistant never cites a past answer as policy

5. Larkspur ingests the handbook from the help centre, the PDF export and the internal wiki, so the export rule is stored three times. Top-3 retrieval returns it three times. Do you add Dartboard, MMR or deduplication?

What a strong answer covers:

  • Deduplicates at indexing time first: exact or near-duplicate chunks waste storage and every later step, and a content hash catches the exact copies
  • Uses Dartboard or MMR for the overlap that survives deduplication, such as two documents that state one rule in different words
  • Sizes the candidate pool to the duplication: in the dartboard run, a pool of 9 drawn from five copies of each chunk holds only two distinct chunks, so the third pick is a copy again
  • Measures on golden questions that need two or more distinct chunks, and checks that single-fact questions do not lose their second supporting chunk

Key Takeaways

  • Graders filter and verify; they never add evidence. When every chunk is graded irrelevant or the answer is not grounded, rewrite the query or abstain instead of answering anyway.
  • Check source highlights in code: every segment must be found in the chunk it claims to come from.
  • Feedback re-ranking moves only chunks that were shown. Read its result per question, and send questions it cannot fix to retrieval work.
  • Remove duplicate chunks at indexing time, then use a diversity-aware selector with a candidate pool larger than the number of copies.
