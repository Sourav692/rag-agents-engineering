M28 Grading and query rewriting

A plain RAG pipeline hands the model whatever the retriever returned. The smallest agentic step is to read what came back first, and to search again with a better query when it is wrong. The M28 notebooks build on four ideas: a grader that judges each retrieval, conditional edges that route on its verdict, a bound on how often the loop may retry, and a topic check that stops off-topic questions before retrieval.

Open the lab

The notebooks run on a research paper (lesson 28.1) and a fictional company’s support documents (lesson 28.3). These pages put the same graphs on the Larkspur Cloud handbook from M11: its twelve chunks, and five golden questions that each take a different path through the loop. Can I export my data after I cancel my plan? is answered on the first retrieval, How long does a refund take? after one rewrite, What happens if my server goes down? after two, Do you offer a student discount? has no answer in the handbook, and What’s the weather like today? is off topic.

TL;DR

  • A document grader is an LLM call with structured output that reads retrieved text next to the question and says whether it helps answer it. A conditional edge turns that verdict into the next node: generate, or rewrite and retrieve again.
  • A retriever returns k chunks for every query. In the lab, the student-discount question retrieves two chunks at 0.000, and a rewrite of it retrieves support at 0.503; neither says anything about discounts, and only the grader keeps them from the model.
  • A rewrite loop without a counter runs until the grader says yes or LangGraph stops it. At the default recursion limit of the pinned langgraph 1.2.18 (10,007 steps), a grader that always says no costs 3,336 retrievals.
  • Lesson 28.3’s graph allows 2 rewrites per question. On the five golden questions, that bound answers 3 at 31 LLM calls; a bound of 3 answers the same 3 at 34.
  • A topic check before retrieval costs one call per question and stops off-topic ones early: the weather question costs 1 call instead of 8, and gets an off-topic reply instead of “not found”.

Mental model

Every self-correcting design in Part IX is this loop with more branches. The grader decides whether the loop runs again, and the counter decides when it must stop. Without the grader the model answers from whatever came back; without the counter an unanswerable question never ends.

Conditional edges

Lesson 28.1: Retriever as a tool; grade then rewrite in LangGraph. Notebooks: 01a_simple_agentic_rag.ipynb

Notebook 01a turns a plain RAG chain into a graph that can look at its own retrieval. It starts by wrapping the vector store retriever as a tool:

retriever_tool = create_retriever_tool(
    retriever,
    "retrieve_info_from_papers",
    "Search and return information about a paper discussing usage of LLMs for human collaborative problem solving.",
)

The name and the description are all the model sees of the retriever. The agent node binds the tool with model.bind_tools(tools), so the model decides whether to call it and with what query. A Larkspur assistant describes its tool as a search over the Larkspur Cloud handbook, so the model can answer “hello” without calling it.

A LangGraph edge is either fixed or conditional. add_edge("rewrite", "agent") always goes the same way. add_conditional_edges(source, fn, path_map) calls fn on the state after source runs, and the value it returns picks the next node. 01a has two conditional edges:

After node Routing function Returns Goes to
agent tools_condition (from langgraph.prebuilt) "tools" if the last AI message has tool calls, otherwise END retrieve through the path map {"tools": "retrieve", END: END}, or the end
retrieve grade_documents Literal["generate", "rewrite"] The node with that name; no path map is needed when the function returns node names

The grader in 01a is the routing function itself, so it is not a node. It writes nothing to the state: after a run, the message history shows a rewrite but not the verdict that caused it, and the only record is the ---DECISION: DOCS NOT RELEVANT--- line the function prints. Lesson 28.3’s notebook splits the same job in two. assess_relevance is a node that writes retrieved_documents and should_generate to the state, and route_by_document_quality is a small routing function that reads them. That costs one extra step per retrieval and makes every decision visible in the state and in a checkpointer.

rewrite sends the new question back to agent, not straight to retrieve. The model reads the rewritten question as the last message and decides again whether to call the tool, and with what query. Nothing on this path counts the trips: the loop ends only when the grader says yes, which lesson 28.3 fixes with bounded retries.

Document grader

A document grader is one LLM call that reads retrieved text next to the question and says whether the text helps answer it. The call uses with_structured_output(<Pydantic model>), so the reply is a typed field the router can compare, not free text to parse. The two notebooks in this module grade differently:

01a: grade_documents 03a: assess_document_relevance
Place in the graph Routing function on the edge after retrieve Node, followed by a separate router
What it reads Everything the tool returned, as one message One chunk per call
Output schema binary_score: str, described as 'yes' or 'no' relevance: str (RELEVANT or IRRELEVANT) and reasoning: str
Decision score == "yes" relevance.strip().upper() == "RELEVANT"
What reaches the answer Every retrieved chunk, relevant or not Only the chunks that pass
Grader calls per retrieval 1 k (the notebook retrieves k = 2)

Grading the block is cheap, but one relevant chunk carries the irrelevant ones into the prompt with it. Grading each chunk costs k calls per retrieval and filters what the model reads.

The schema decides what the router can trust. binary_score is a plain str, and the comparison is exact, so a model that answers "Yes" sends a relevant retrieval to rewrite. 03a normalises with .strip().upper() before comparing, and its topic classifier goes further with Literal["RELEVANT", "IRRELEVANT"], which makes Pydantic reject any other value.

The prompt sets the bar. 01a grades a document relevant if it “contains keyword(s) or semantic meaning related to the user question”. 03a also accepts “context that helps understand the topic”. On the Larkspur handbook, How long does a refund take? retrieves refund-window first: it is about refunds, and it says an annual plan can get a full refund within 30 days. It does not say how long a refund takes. A grader that accepts “related” passes it, and the model answers from a chunk without the answer. A grader that asks “does this answer the question?” fails it and sends the query to rewrite, which in the lab finds refund-timing at 0.720.

The grader reads text because a similarity score cannot do its job. A retriever returns k chunks for every query, whatever they score. In the lab, Do you offer a student discount? shares no word with the handbook and still retrieves billing and cancel at 0.000. Its rewrite Student discount pricing for plans retrieves support at 0.503 and billing at 0.461, both above the 0.227 that refund-window scores for the refund question, and neither mentions a discount. No score threshold separates those cases; reading the chunk does.

Key Takeaways

  • Wrap the retriever as a tool whose name and description tell the model when to call it. A conditional edge after retrieval then sends the run to generate or rewrite on the grader’s verdict.
  • Make the grader a node that writes its verdict to state, with a small router that reads it, so every decision is visible. Type the verdict as a Literal rather than comparing free strings.
  • Ask the grader whether a chunk answers the question, not whether it is related. A similarity score cannot do this, because the retriever returns k chunks for every query whatever they score.

Topic guardrails

Lesson 28.3: Guardrails, query optimisation and a retry loop. Notebooks: 03a_advanced_rag_agent.ipynb

Notebook 03a builds an eight-node support agent. Before it retrieves anything, it asks whether the question belongs to the assistant at all:

generate_response, handle_off_topic and handle_no_results each end the turn. The two handlers reply with fixed text and make no LLM call.

validate_topic is one structured-output call. Its schema is TopicRelevance, with classification: Literal["RELEVANT", "IRRELEVANT"] and confidence: Literal["HIGH", "MEDIUM", "LOW"], and its system prompt lists what counts as on topic (the company’s services, pricing, support procedures, company information) and what does not (general technology questions, other companies, weather and news). route_by_topic sends RELEVANT to retrieval and anything else to handle_off_topic, which replies with a list of what the assistant can help with.

The check has to run before retrieval because the grader cannot tell “off topic” from “not in the handbook”. Both look like a retrieval where nothing passes, both spend the retry budget, and both end in the same no-results reply. The lab shows the difference on the Larkspur golden set with two rewrites allowed:

Question Topic check Grader Ends in LLM calls
Can I export my data after I cancel my plan? on topic 2 of 2 pass on the first retrieval answer 4
Do you offer a student discount? on topic 0 of 2 on each of 3 retrievals no-results reply 9
What’s the weather like today? off topic not reached off-topic reply 1
What’s the weather like today?, check off none 0 of 2 on each of 3 retrievals no-results reply 8

The guardrail and the grader catch different failures. The student-discount question is about pricing, so it passes the topic check; only the grader and the bound stop it.

The check costs one call on every question, on-topic ones included. Over the lab’s five questions it saves 3 calls at two rewrites (31 with the check, 34 without), breaks even at one rewrite (24 and 24) and costs 3 at zero rewrites (14 and 11). It pays when off-topic traffic times the cost of a full retry loop is more than one call per question. It also changes what the customer reads: “I can help with pricing, refunds and servers” instead of “I couldn’t find that in the handbook”.

Three details in 03a matter in production:

  • It classifies the enhanced query. enhance_user_query runs first and folds the conversation history into a standalone question. A follow-up such as What about annual plans? names nothing the classifier can place; after enhancement it carries the refund question it follows.
  • Confidence is computed and ignored. route_by_topic reads only classification, so a LOW-confidence RELEVANT goes to retrieval exactly like a HIGH one. Asking a clarifying question on low confidence needs a third branch in the router.
  • A false rejection is silent. An on-topic question classified IRRELEVANT never reaches retrieval, so no grader and no retrieval log sees it. Track the off-topic rate and sample those replies.

Bounded retries

Lesson 28.1’s graph has no counter. rewrite feeds agent, agent calls the retriever, and the loop ends only when the grader says yes. When the handbook has no answer, LangGraph’s recursion limit is the only stop. In the version this course pins (langgraph 1.2.18), the default recursion_limit is 10,007 steps. Run with stub nodes and a grader that always says no, the 01a graph made 3,336 retrievals and 10,007 LLM calls before it raised GraphRecursionError. With {"recursion_limit": 25} in the config it stopped after 8 retrievals and 25 LLM calls.

03a bounds the loop in the state:

  • optimization_attempts counts rewrites, and enhance_user_query resets it to 0 at the start of every turn, so the bound is per question, not per conversation.
  • route_by_document_quality checks in order: any chunk passed, go to generate_response; 2 rewrites used, go to handle_no_results; otherwise go to optimize_query. A turn therefore makes at most 3 retrievals.
  • optimize_search_query repeats the >= 2 check and returns the state unchanged, a guard in case another edge ever reaches it.

The bound also caps the cost. With 03a’s call pattern and k = 2, a question costs one call for the topic check, two grader calls per retrieval, one call per rewrite and one call for the answer if there is one. Answered on the first retrieval, that is 4. Never answered with two rewrites allowed, it is 1 + 6 + 2 = 9.

The interactive lab runs this loop on five Larkspur golden questions, with real TF-IDF retrieval over the M11 handbook chunks and the bound as its slider. Its totals for the golden set with the topic check on:

Rewrites allowed Answered No-results reply Off-topic reply Retrievals LLM calls
0 1 3 1 4 14
1 2 2 1 7 24
2 3 1 1 9 31
3 3 1 1 10 34

Each step up the bound reaches one more question until 2, where the outage question is answered on its second rewrite. Going to 3 answers nothing new: the extra retrieval and three calls all go to the student-discount question, which the handbook cannot answer at any bound. Questions without an answer always pay the full bound, 1 + 2(m + 1) + m calls for a bound of m, so the bound is set by how far the golden set’s answered count keeps rising, and no further.

Keep recursion_limit as a backstop even with a counter in the state. The counter bounds the loop you designed; the recursion limit bounds the one a later edit creates by accident.

Two rewrites, two jobs

03a rewrites the query in two places, for different reasons:

enhance_query optimize_query
Runs Once per turn, before the topic check After a retrieval where no chunk passed
Reads The conversation history and the new question The current query
Job Make a follow-up standalone Find words that retrieve better
On the first turn Passes the question through, no LLM call Same as any turn

Each optimize_query call rewrites the previous rewrite, since it reads enhanced_query and writes the result back to it. Two rounds can drift from what the customer asked. 01a rewrites messages[0], the original question, every time.

A rewrite helps only if it moves toward the documents’ words. In the lab, the outage question’s first rewrite, What happens when my server is unavailable?, swaps one everyday phrase for another. TF-IDF matches exact tokens, so it retrieves reboot at 0.416 and sizing at 0.389 again, the same as the original. The second rewrite uses the handbook’s vocabulary, “outage” and “availability”, and retrieves sla at 0.470 and incidents at 0.253. M18 covers rewriting before retrieval as a stage of its own, including HyDE and multi-query.

Key Takeaways

  • A topic check before retrieval costs one call per question and stops off-topic traffic from spending the retry budget. Track the off-topic rate, because a false rejection never reaches retrieval or its logs.
  • Bound rewrites with a per-question counter in the state and keep recursion_limit as a backstop. Without a counter, the default limit let a stub graph make 10,007 LLM calls.
  • Enhancement makes a follow-up standalone; optimisation looks for words that retrieve better. A rewrite helps only when it moves toward the documents’ vocabulary, and rewriting a rewrite can drift from the question.

Check yourself

1. Why does the topic check run before retrieval instead of leaving off-topic questions to the document grader?

The grader cannot tell “off topic” from “not in the handbook”: both look like a retrieval where nothing passes, both spend the retry budget and both end in the same no-results reply. In the lab the weather question costs 1 call with the check and 8 without.

2. With two rewrites allowed and two chunks per retrieval, how many LLM calls does a question the handbook cannot answer cost?

Nine: 1 for the topic check, 6 grader calls (2 per retrieval over 3 retrievals) and 2 rewrites, with no answer call. In general it is 1 + 2(m + 1) + m for a bound of m, because unanswerable questions always pay the full bound.

3. Raising the bound from two rewrites to three costs three more calls on the golden set. What does it buy?

Nothing: the answered count stays at 3. The extra retrieval and calls all go to the student-discount question, which the handbook cannot answer at any bound. Set the bound where the golden set’s answered count stops rising, and keep recursion_limit as a backstop.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. A week after the Larkspur handbook moved to a new document system, the support assistant’s LLM bill doubled while traffic stayed flat. Traces show most questions now making three retrievals. What happened, and what do you check first?

What a strong answer covers:

  • Reads the path log: the share of questions that use rewrites and end in the no-results reply rose, so retrieval or grading changed, not traffic
  • Re-runs the golden set and prints retrieved chunks for a failing question: if the right chunk is missing, the migration broke loading, chunking or the index; if it is present and graded no, the grader or its prompt changed
  • Explains why cost doubled: with a bound of 2 and k = 2, every failed question pays 9 calls instead of 4
  • Adds an alert on the no-results rate and rewrites per question, so the next regression shows up the same day

2. Your retriever moves to k = 8 for better recall. The grader currently reads all eight chunks as one block and answers yes or no. Do you switch to grading each chunk?

What a strong answer covers:

  • One block grade lets a single relevant chunk carry seven irrelevant ones into the prompt; per-chunk grading filters them out
  • Per-chunk grading costs k calls per retrieval, 8 instead of 1, and multiplies with every retry
  • Mitigations: run the grades in parallel, put the grader on a small fast model, or ask for a list of per-chunk verdicts in one structured-output call
  • Measures both on the golden set: answer faithfulness, tokens sent to the model, latency and cost per question

3. How do you know the grader is grading correctly in production?

What a strong answer covers:

  • Labels a sample of (question, chunk) pairs by hand and measures the grader’s precision and recall against them
  • Names both errors: a false yes sends a non-answer to the model (refund-window for “how long does a refund take?”); a false no burns a rewrite and can end in “not found” for a question the handbook answers
  • Logs the verdict and its reasoning field per chunk, since a grader on a routing edge leaves no trace in the state
  • Re-checks after every change to the grader’s model or prompt, and when a new document type enters the index

4. A customer asks about refunds, then sends “What about annual plans?” and gets the off-topic reply. What went wrong?

What a strong answer covers:

  • The topic check saw the follow-up alone; it should classify the enhanced query, after the history is folded in
  • Checks that the history was there: the conversation is checkpointed per thread_id, and a new thread starts empty
  • Uses the confidence field the classifier already returns: route low confidence to a clarifying question instead of a refusal
  • Adds follow-up questions to the golden set and tracks the off-topic rate, since a false rejection never reaches retrieval logs

5. A product manager asks to raise the retry bound from 2 to 5 “so more questions get answered”. How do you respond?

What a strong answer covers:

  • Plots answered questions against the bound on the golden set: in the lab, going from 2 to 3 answers nothing new and adds 3 calls
  • Points out who pays: questions with no answer in the handbook always use the full bound, 1 + 2(m + 1) + m calls at k = 2
  • Looks at the questions still unanswered: a rewrite cannot find content that is not indexed, so the fix is the handbook, or better rewriting toward its vocabulary
  • Keeps LangGraph’s recursion_limit as a backstop under the counter, since a later edit can add a loop the counter does not see

Key Takeaways

  • Grade retrieved text against the question before the model reads it. A similarity score measures shared words; only reading the chunk tells you whether it answers.
  • Put the verdict in the state and route on it with a conditional edge, so every path the graph takes can be logged and explained.
  • Bound every retry loop with a counter in the state that resets each turn, and set the bound where the golden set stops gaining answers.
  • Check the topic before retrieval when off-topic traffic is real, and watch the no-results rate it leaves behind: those questions are gaps in the handbook.
