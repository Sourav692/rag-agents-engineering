M29 Self-correcting RAG: CRAG and Self-RAG

A plain RAG pipeline generates from whatever the retriever returns. Corrective RAG (CRAG) grades the retrieved chunks first and finds other context when they fail. Self-RAG asks the model to judge each step, from whether to retrieve at all to whether its answer is supported and useful. The M29 notebooks build on four ideas: a retrieval evaluator, knowledge refinement, reflection tokens and a groundedness check.

What correction costs
Open the lab

The running example is the twelve-chunk Larkspur Cloud handbook from M11 and its three golden questions, plus two questions the handbook cannot answer: Does Larkspur offer GPU servers? and How much does the starter plan cost per month? The handbook is private, so a web search cannot answer for it. That makes it a fair stress test for a pipeline whose fallback is the web.

TL;DR

  • CRAG puts a retrieval evaluator between retrieval and generation. In notebook 01a it grades each chunk yes or no and searches the web when half or fewer pass; in 01b it scores each chunk from 0 to 1 and picks Correct (above 0.7), Incorrect (below 0.3) or Ambiguous.
  • Knowledge refinement cuts the context down to the parts that answer the question before generation. 01b does it with an LLM call that turns a document into bullet points.
  • Self-RAG makes four judgments, the reflection tokens of the paper: retrieve or not, is this chunk relevant, is the answer supported, is it useful. Notebook 02a asks an LLM for each one and caps the retry loops at max_iterations = 2.
  • The groundedness check is the hallucination guard, and in 02a it has two holes: it passes without a call when there are no documents, and its regenerate loop ignores the iteration cap.
  • Correction is paid in LLM calls. In the lab at k = 5, the baseline makes 1 call per question, CRAG 5.6 on average and Self-RAG 15.0, up to 20 on a question the handbook cannot answer.

Mental model

There are two places to catch a bad answer. CRAG checks the context before generation; Self-RAG also checks the answer after it. Each check is an LLM call, and each failed check sends the question round again, so the price of correction is set by how often the checks fail.

Retrieval evaluator

Lesson 29.1: Corrective RAG in LangGraph with web-search fallback. Notebooks: 01a_agentic_corrective_rag_langgraph.ipynb, 01b_crag_rag_techniques.ipynb (optional)

Corrective RAG (Yan et al., Corrective Retrieval Augmented Generation, 2024, arXiv:2401.15884) adds one component to the baseline: a retrieval evaluator that judges the retrieved documents before the model sees them. Its verdict picks what happens next. If retrieval looks right, generate from it; if it looks wrong, find other context; if it is unclear, use both. The paper trains a small model (T5-large) as the evaluator. Both M29 notebooks prompt an LLM instead.

That is the graph notebook 01a builds in LangGraph, with nodes retrieve, grade_documents, rewrite_query, web_search and generate_answer. The two notebooks build the evaluator differently:

01a, LangGraph 01b, plain functions (optional)
Retriever Chroma, k = 5, similarity_score_threshold 0.35 FAISS, k = 3
Evaluator output binary_score, yes or no per chunk (gpt-4o, temperature 0) relevance_score, 0 to 1 per chunk (gpt-4o-mini)
Decision Relevant fraction above 0.5: generate. At 0.5 or below, or nothing retrieved: rewrite and search the web Best score above 0.7: Correct, use that document. Below 0.3: Incorrect, search the web. Otherwise Ambiguous: refine the document and add web results
Web search Tavily, max_results=6, search_depth='advanced', full page text DuckDuckGo results, refined to bullet points
LLM calls one per retrieved chunk, plus a rewrite on the fallback, plus generation one per retrieved chunk, plus rewrite and refinement on the fallback, plus generation

Three behaviours follow from 01a’s rule, and the M29 lab shows each on the Larkspur handbook. Its grader is a stand-in that agrees with the golden labels, so these are routing effects, not grader mistakes.

  • The threshold is a fraction, so it moves with k. Every golden question has two evidence chunks. A perfect grader keeps two, and 2 of k is more than half only when k is 3 or less. On Can I export my data after I cancel my plan? CRAG answers in 4 calls at k = 3. At k = 5 it keeps both evidence chunks, still falls back, and spends 7 calls plus a web search.
  • It grades chunks, not answers. At k = 1 the export question retrieves only retention. One relevant chunk out of one passes the rule, and CRAG answers in 2 calls without the export chunk, which says how to export.
  • A correct verdict can trigger the wrong fix. For What happens if my server goes down? TF-IDF returns reboot, sizing and export, and the grader rightly rejects all three. CRAG then searches the web for a private handbook’s outage policy. The answer was in the corpus all along, under the words “outage” and “availability”; a rewrite and retry against the index (M18, M28) would have found it.

The web fallback suits a corpus of public facts that go stale, such as the research papers in 01a. For a private handbook, replace it or guard it: retry inside the index, then refuse.

Knowledge refinement

Retrieval returns whole chunks, and a chunk can mix the sentence that answers the question with sentences that do not. Knowledge refinement cuts the context down to the useful parts before generation. The CRAG paper does it with decompose-then-recompose: split each document into short strips, score every strip with the evaluator, drop the low scorers and join the rest.

Notebook 01b uses a simpler version. knowledge_refinement sends a document to the LLM with the prompt “Extract the key information from the following document in bullet points” and returns the bullets as a list. Where it runs depends on the action:

Action Best score Context sent to the generator
Correct above 0.7 the best retrieved document, as is
Incorrect below 0.3 refined bullets from the web results
Ambiguous 0.3 to 0.7 refined bullets from the best document, plus refined web results

Notebook 01a has no refinement step. It filters at chunk level, keeping only chunks graded yes, and passes the web pages in full (include_raw_content=True), so a fallback can put six whole pages into the prompt.

On the Larkspur export question at k = 3, the retriever returns retention, export and cancel. Chunk-level filtering keeps the first two whole. Strip-level refinement would go one step further. As an illustration (written by hand, not notebook output):

Strip Keep?
retention: After a plan is cancelled, its data is kept for 30 days and then permanently deleted. yes, it answers “after I cancel”
retention: Export it before that window closes. yes
export: Export your data at any time from Settings, then Data. yes, it says how
export: Exports include databases, object storage and server snapshots. borderline, it answers a different question
cancel: You can cancel any plan from the Billing page. no

Refinement costs one more LLM call per document it rewrites, and an LLM that rewrites evidence can also change it. Keep the original chunk id beside each bullet so the answer can still cite the source.

Reflection tokens

Lesson 29.2: Self-RAG: retrieve-or-not, relevance, groundedness, utility. Notebooks: 02a_self_rag_langgraph.ipynb, 02b_self_rag_rag_techniques.ipynb (optional)

Self-RAG (Asai et al., Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection, arXiv:2310.11511) trains one model to emit special tokens that judge its own pipeline. The paper calls them reflection tokens, and there are four kinds:

Token Question it answers Values in the paper 02a (LangGraph) 02b (optional)
Retrieve Do I need documents for this? yes, no, continue RetrieveDecision.need_retrieval: yes or no RetrievalResponse: Yes or No
ISREL Is this passage relevant? relevant, irrelevant RelevanceGrade.binary_score, per chunk RelevanceResponse: Relevant or Irrelevant
ISSUP Is the answer supported by the passage? fully, partially, no support GroundednessGrade.binary_score plus feedback SupportResponse: Fully supported, Partially supported or No support
ISUSE Is the answer useful for the question? a score from 1 to 5 UtilityGrade.binary_score plus feedback UtilityResponse: an integer from 1 to 5

In the paper the tokens are part of the model’s vocabulary and come out of the same decoding pass as the answer. Neither notebook trains a model. Each judgment is a separate LLM call with a structured-output schema, so “reflection token” here means “one more call that returns a label”.

Notebook 02a wires each judgment to its own conditional edge:

Two loops go back to retrieval (no relevant chunk, or an answer that misses the question) and one goes back to generation (an unsupported answer). max_iterations = 2 bounds the rewrite loops: after two rewrites, route_after_relevance_grading sends the question to generate even with no relevant chunk, and route_after_utility ends the run.

The first token is the one CRAG lacks. What is 9 plus 10? gets need_retrieval = 'no' in 02a and skips the vector store. Every Larkspur question is about the handbook, so on this corpus the Retrieve token saves nothing and costs one call.

The loops make the cost depend on the question. On How much does the starter plan cost per month? at k = 5, no chunk is ever relevant, and the M29 lab counts 20 LLM calls: 1 retrieve decision, 15 relevance grades over three passes, 2 rewrites, 1 generation and 1 utility grade. On the export question the same graph stops after one pass in 9 calls.

Groundedness check

The groundedness check is the hallucination guard. In 02a, grade_groundedness sends the context and the answer to a “strict fact-checker” prompt; the schema returns binary_score, yes only if every claim is supported, and a feedback string naming the unsupported claims. On a no, the router sends the run back to generate, and the feedback goes into the prompt as “a previous attempt at this answer was rejected for this reason”. Groundedness and utility are separate checks because they fail separately: an answer can be fully supported by the chunks and still miss the question.

Two details in 02a decide what the check catches.

With no documents it passes without running. If documents is empty, grade_groundedness returns "yes" and makes no call. That is exactly the out-of-corpus case: on the starter-plan question, Self-RAG exhausts its rewrites, generates with no context, and the check waves the answer through. The only guard left is the generation prompt’s line “If the context does not contain enough information to answer confidently, say so plainly”. Notebook 02b is weaker still. When no chunk is relevant it generates with the context “No relevant context found.” and a prompt that asks only to “generate a response”, so the model answers from memory; its own low-relevance test asks a climate-change corpus how did harry beat quirrell?

The cap does not bound the regenerate loop. route_after_groundedness writes state["iteration"] = iteration + 1 inside the routing function. LangGraph keeps only what nodes return, so that write is lost and the counter never moves. Run against the notebook’s own node and router code with a groundedness grader that always says no, the compiled graph (langgraph 1.2.18) regenerated until LangGraph raised GraphRecursionError: with recursion_limit = 200, that was 98 regenerations and 200 LLM calls. With the default config it ran to the limit that release reports, 10,007 steps. The fix is to count in a node: have generate return the new iteration when it is regenerating, or add a small regenerate node before it.

The paper’s three support levels are worth keeping when you build this yourself. 02b ranks candidate answers by “fully supported” first and utility second (max(responses, key=lambda x: (x[1] == 'fully supported', x[2]))), which a yes or no grade cannot do.

Cost per question

Lesson 29.3: Trade-offs: when correction is worth the extra calls

Every check in CRAG and Self-RAG is an LLM call, and every failed check sends the question round again. The calls are easy to count from the notebook graphs:

Pipeline LLM calls per question
Baseline 1: generate
CRAG (01a) one grade per retrieved chunk, plus 1 rewrite if it falls back, plus 1 generation; the web search is a tool call on top
Self-RAG (02a) 1 retrieve decision, one grade per retrieved chunk on every pass, 1 rewrite per extra pass, and per generation 1 call, 1 groundedness grade (skipped with no documents) and 1 utility grade

The interactive lab runs those graphs on the M11 handbook with TF-IDF retrieval and stand-in graders: relevance agrees with the golden labels, groundedness says yes, utility says yes only when every evidence chunk reached the generator, and a rewrite repeats the question. The last rule makes the Self-RAG figures a worst case, since a real rewrite can find the evidence and end the loop early. Its counts, checked against the notebooks’ own LangGraph code with the same stand-ins (50 runs, 0 mismatches):

Question Baseline CRAG, k = 3 Self-RAG, k = 3 CRAG, k = 5 Self-RAG, k = 5
Can I export my data after I cancel my plan? 1 4 7 7 + web 9
How long does a refund take? 1 4 + web 18 4 + web 18
What happens if my server goes down? 1 5 + web 14 5 + web 14
Does Larkspur offer GPU servers? (not in the handbook) 1 5 + web 14 5 + web 14
How much does the starter plan cost per month? (not in the handbook) 1 5 + web 14 7 + web 20
Mean 1.0 4.6 13.4 5.6 15.0

Three patterns hold across the table:

  • Correction costs most where it helps least. The two questions the handbook cannot answer are the expensive ones for Self-RAG, 14 to 20 calls, and they end with a generation that has no context to be grounded in. CRAG sends both to the web, which cannot see a private handbook.
  • Some misses no check can repair. On the refund question, refund-timing shares no term with “How long does a refund take?”, so it is never retrieved and never graded. Self-RAG’s utility check sees the gap and spends 18 calls on three passes that return the same chunks. The fix is upstream, in retrieval (M14, M17) or in a rewrite that changes the words (M18).
  • On an easy question the checks are overhead. At k = 3 the export question is answered from both evidence chunks by all three pipelines; CRAG pays 4 calls and Self-RAG 7 for the same context the baseline read in 1.

The notebooks also make the calls one after another. grade_documents and grade_relevance loop over the chunks in Python, so k grades add k round trips of latency. Batching them (doc_grader.batch(...)) cuts the wait, not the bill.

When correction pays

Correction earns its calls when a wrong answer costs more than the extra latency and tokens, and when the fix it reaches for can supply the missing evidence. A short chain of questions settles most cases:

For the Larkspur assistant that means:

  • Billing and refund questions are worth a check, because a wrong refund window turns into a support ticket. A relevance grade per chunk and one groundedness check on the answer add k + 1 calls.
  • The web fallback stays off. Every Larkspur fact lives in the handbook. A question the handbook cannot answer should get a refusal and a handoff to support, not a search.
  • Retrieval misses are fixed in retrieval. The outage question fails on wording; one rewrite against the index is cheaper than three Self-RAG passes or a web search.
  • Every loop gets a counter and a budget. max_iterations caps the rewrite loops in 02a; the regenerate loop needs a counter updated in a node (lesson 29.2), and a per-request limit on LLM calls catches the next loop nobody bounded.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s support assistant runs CRAG with a web fallback. A customer asks what happens when their server goes down, and the assistant quotes another provider’s availability guarantee. The handbook has the right answer. What went wrong, and what do you change?

What a strong answer covers:

  • Reads the trace first: which chunks came back, how each was graded, and whether the web branch fired. In the lab, TF-IDF retrieves reboot, sizing and export for this question, the grader correctly rejects all three, and CRAG goes to the web
  • Names the two faults: a retrieval miss on wording (“server goes down” against “outage” and “availability”), and a fallback that searches a source which cannot know a private handbook
  • Fixes retrieval inside the corpus first: a rewrite-and-retry against the index (M28), hybrid or embedding search (M17, M14)
  • Restricts the web branch to questions about public facts, or replaces it with a refusal that says the handbook does not cover the question

2. Product wants Self-RAG on every Larkspur question “to stop hallucinations”. The assistant already carries most of Larkspur’s support traffic. How do you decide?

What a strong answer covers:

  • Counts calls before arguing: in the lab at k = 5 Self-RAG averages 15.0 LLM calls per question against 1 for the baseline, and the easy export question still costs 9
  • Notes that 02a grades chunks one at a time in a loop, so calls add latency in series unless they are batched
  • Proposes tiering: the baseline with a cheap check for most traffic, the full loop for high-stakes intents such as billing and refunds
  • Measures on the golden set whether the extra calls change answers, and keeps the loop only where they do

3. CRAG has been live for a month. How do you tell whether the retrieval evaluator is helping or just adding cost?

What a strong answer covers:

  • Logs the route for every request: chunks graded, chunks kept, relevant fraction, web fallback yes or no
  • Tracks the web fallback rate by question type; a rate that jumps after an index change points at retrieval, not at the questions
  • Samples cases where the grader kept everything and cases where it kept nothing, and grades them by hand to measure the grader’s own precision and recall
  • Watches for the threshold coupling with k: in the lab the export question falls back to the web at k = 4 and k = 5 with both evidence chunks kept

4. Someone asks the Self-RAG assistant “How much does the starter plan cost per month?” The handbook lists no prices. The groundedness check passed, yet the answer contains a price. How?

What a strong answer covers:

  • Traces the loop: no chunk is relevant, so 02a rewrites and retrieves until the cap, then generates with no documents
  • Points at grade_groundedness: with no documents it returns “yes” without calling the grader, so the check never ran
  • Notes the only remaining guard is the generation prompt’s instruction to say so when the context is missing; 02b drops even that and answers from the model’s memory
  • Fixes it by routing “no relevant documents after the cap” to a fixed refusal, and by adding out-of-corpus questions to the golden set

5. A cost dashboard shows one Self-RAG request that made about 200 LLM calls before it failed with a recursion error. The iteration cap is 2. Where do you look?

What a strong answer covers:

  • Suspects a loop that does not move the counter, and reads the routers
  • Finds it in 02a’s route_after_groundedness, which writes state["iteration"] inside a routing function; LangGraph keeps only what nodes return, so the counter never moves and the regenerate loop runs until the recursion limit
  • Moves the increment into a node (for example, generate returns the new iteration when it regenerates) and adds a test with a grader that always says “no”
  • Sets an explicit recursion_limit and a per-request call budget as a second guard

Key Takeaways

  • Grade the context before you generate from it, and log the grade: the route a request took is the first thing to read when an answer is wrong.
  • Pick the fallback by where the answer can live. A web search cannot answer for a private handbook; rewrite and retry against your own index first, and refuse when the corpus has nothing.
  • A groundedness check guards only the cases it runs on. Make “no documents” a refusal, never an automatic pass.
  • Count LLM calls per question on your golden set before you ship a correction loop, and bound every loop with a counter that a node, not a router, updates.
