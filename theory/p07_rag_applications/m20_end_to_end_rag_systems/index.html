M20 End-to-end RAG systems

A RAG pipeline returns an answer. A RAG system returns an answer a user can check: the chunks it came from, the sentences that support it, and a refusal when the evidence is missing or the question needs something other than retrieval. The M20 notebooks build on four ideas: grounding the answer in retrieved context, a schema for citations, how a table row becomes a retrievable record, and running the pipeline on your own hardware.

Sample or population
Open the lab

The running example is the Larkspur Cloud handbook from M11 to M13 (refunds, exports, outages) plus its server catalogue: ten server sizes with vCPUs, memory, a monthly price and a one-line description. The golden questions are Can I get a refund on my annual plan? for citations, and four questions on the catalogue for structured data: the average monthly price, the servers under $50, the ls-cpu-8 server, and a server for a memory-hungry database.

TL;DR

  • Grounded generation has three parts: evidence retrieved for this question, an instruction to use only that evidence, and permission to say “I don’t know”. Lesson 20.1’s chain has all three but formats the metadata away, so its answers cannot be checked.
  • RunnablePassthrough.assign keeps the retrieved chunks in the output with one retrieval. A second call fills a QuotedCitations schema (id, source, title, page, quotes); check every quote against its chunk in code, because the notebook’s highlighter fails silently on a paraphrase.
  • An LLM explanation per retrieved chunk costs k extra calls and, asked why a chunk is relevant, explains even a wrong one. Show scores to engineers and grade relevance with a yes or no.
  • Put a record’s description in page_content and its ids, numbers and dates in metadata. In the lab, embedding every column shrinks the lead of the right rows from 0.115 to 0.0004, and What is the average monthly price? answered from the top 4 rows gives $36.25 where the table says $102.50.
  • The local pipeline embeds with bge-base-en-v1.5 and searches FAISS on your machine, but generates through the Hugging Face Inference API. Fully local means HuggingFacePipeline as well.

Mental model

Each box adds something a reader can verify. The router keeps questions that need the whole table away from top-k retrieval; the metadata carried from retrieval to the answer is what makes a citation point somewhere; the quote check is the one step that runs as code, not as a model call.

Grounded generation

Lesson 20.1: Environment setup and a complete RAG system. Notebooks: 01a_setup.ipynb, 01b_build_a_simple_rag_system.ipynb, 01c_simple_rag_pdf.ipynb (optional)

A grounded answer comes from evidence the system retrieved for this question, and the model is told to use nothing else. Lesson 20.1 builds the whole pipeline in one notebook, from two kinds of source to a chain that answers from them.

Stage What 01b does
Load JSONLoader reads wikidata_rag_demo.jsonl one line per Document; each article’s paragraphs are joined and title, id and source kept as metadata. PyMuPDFLoader reads every PDF in data/sample/.
Split RecursiveCharacterTextSplitter, chunk_size=3500, chunk_overlap=200, for the PDFs. Wikipedia articles stay whole.
Embed text-embedding-3-small, 1,536 dimensions.
Store Chroma, persisted to ./my_db, with collection_metadata={"hnsw:space": "cosine"}. Without it Chroma uses Euclidean distance (M11.4).
Retrieve as_retriever(search_type="similarity", search_kwargs={"k": 5}).
Generate gpt-4o-mini at temperature=0, with a prompt that restricts it to the retrieved context.

The chain is three LCEL steps:

Grounding rests on three things, and the notebook’s prompt has all three:

  1. The evidence is retrieved for this question. The model sees five chunks, not the corpus.
  2. The instruction limits the model to that evidence. “Answer the following question using only the following pieces of retrieved context.”
  3. The model has a way out. “If the answer is not in the context, do not make up answers, just say that you don’t know.” Without a permitted refusal, a model asked about something the context lacks will answer from what it learned in training.

On the Larkspur handbook, Can I export my data after I cancel my plan? retrieves the export and retention chunks, and the answer should say “within 30 days, from Settings, then Data”. Does Larkspur offer a free tier? has no chunk in the handbook, so the grounded answer is “I don’t know”. Whether a given model complies is a property you test: put questions with no answer in the golden set and count the refusals.

The instruction does not guarantee compliance. A model can still blend in outside knowledge or misread a chunk; M29 and M32 add a second call that grades the answer against its evidence.

What this chain throws away

format_docs joins doc.page_content and nothing else, so the title, id and source in metadata never reach the model, and the chain returns only an AIMessage. The answer may be grounded, but nobody can check it. There is no list of chunks and no way to say which one a sentence came from. Lesson 20.2 keeps both.

A setup trap from the notebook

openai_embed_model.embed_documents("Hello, world!") returns 13 vectors. embed_documents expects a list of strings, and a Python string is iterable, so each of the 13 characters is embedded on its own. Use embed_query(text) for one string, or embed_documents([text]); either gives one 1,536-dimension vector. The same mistake inside an indexing loop embeds characters and stores garbage without an error.

The optional 01c notebook builds the same pipeline on FAISS from one PDF, Understanding_Climate_Change.pdf, with 1,000-character chunks, 200 overlap and k=2, and reconstructs the index matrix to show its shape: one row per chunk, 1,536 columns.

Key Takeaways

  • Grounding needs three things in the prompt: evidence retrieved for this question, an instruction to use only that evidence, and permission to say “I don’t know”.
  • The instruction does not guarantee compliance. Put questions with no answer in the golden set and count the refusals.
  • A chain that formats only page_content and returns only the answer cannot be checked. Keep the chunks and their metadata if anyone needs to verify a sentence.

Returning the sources

Lesson 20.2: Answers with sources and per-claim citations. Notebooks: 02a_rag_system_with_sources.ipynb, 02b_rag_system_with_citations.ipynb

Both notebooks start with %run on the M16 contextual retrieval notebook, 05b_contextual_retrieval_rag_system.ipynb (M16.5). That run builds the index the citations depend on, and it writes four metadata fields on every chunk:

Field Wikipedia articles PDF chunks
id the article’s id from the JSONL a fresh uuid4() per chunk
source "Wikipedia" the file path
title the article title the file name
page always 1 PyMuPDFLoader’s page number, which counts from 0

Shown as stored, the 0-based page tells a reader “page 0” or sends them to the page before the right one. Add 1 when you display it.

02a keeps the retrieved Documents in the chain’s output instead of formatting them away:

rag_chain_w_sources = (
    {"context": similarity_retriever, "question": RunnablePassthrough()}
    | RunnablePassthrough.assign(response=src_rag_response_chain)
)

RunnablePassthrough.assign runs the answer chain on the dict and adds its result under response, so the output holds context (the five Documents), question and response. The retriever runs once, and the chunks the user sees are the chunks the model read. This is source attribution at the answer level: the reader gets a list of five sources and has to find the supporting sentence in each.

Citation schema

02b asks for more: which chunk supports the answer, and the exact sentences. A second model call, after the answer, fills a Pydantic schema through with_structured_output:

class Citation(BaseModel):
    id: str        # the SPECIFIC context article that justifies the answer
    source: str
    title: str
    page: int
    quotes: str    # VERBATIM sentences from that article

class QuotedCitations(BaseModel):
    citations: List[Citation]

The answer chain formats each chunk with format_docs_with_metadata, which prints Context Article ID, Source, Title and Page above its text, so the model can copy real ids into the citation. Each field earns its place:

  • id joins a citation back to a retrieved chunk, which is what lets code check it.
  • page sends a reader to the right place in a long PDF.
  • quotes is the part a machine can check. A quote either appears in the chunk or it does not.

On the Larkspur handbook, Can I get a refund on my annual plan? should produce a citation like this one (a representative output, not a recorded run):

{"id": "refund-window", "source": "handbook.pdf", "title": "handbook.pdf", "page": 2,
 "quotes": "An annual plan can get a full refund within 30 days of purchase if the account used less than 100 GB of outbound traffic."}

What the schema does not guarantee

  • Citations come after the answer. The second call looks for support for text that already exists. It shows the answer can be justified from the chunks, not that the model used them. A claim with no support may get a loose citation or none, and nothing marks which.
  • It is per answer, not per claim. QuotedCitations is a flat list. Nothing ties a citation to the sentence of the answer it supports. For true per-claim citations, add a claim: str field (the answer sentence) or have the answer call emit numbered markers that the citations reference.
  • The quote may not be verbatim. The schema asks for exact sentences; the model can still paraphrase or merge two. The notebook’s display code highlights each quoted sentence in its chunk with a regex. A paraphrase highlights nothing and raises nothing, and a citation whose id matches no retrieved chunk comes back with its context set to None. Both fail silently.

So check every citation in code before showing it:

import re

def norm(text):
    return re.sub(r"\s+", " ", text).strip()

def quote_found(citation, chunks_by_id):
    chunk = chunks_by_id.get(citation.id)
    return chunk is not None and norm(citation.quotes) in norm(chunk.page_content)

On the refund chunk, the verbatim quote above passes, the same quote broken across lines passes, and the paraphrase “Annual plans are fully refundable for 30 days.” fails. Drop or flag the citations that fail, and track the failure rate as a production metric: a rising rate means the prompt, the model or the chunk text changed.

One bug to fix when you reuse the notebook: cite_response_chain passes itemgetter('context') straight into the prompt, so the model reads the Python repr of a list of Documents ([Document(metadata={...}, page_content='...')]). Run it through format_docs_with_metadata, as the answer chain does, so both calls see the same text.

Key Takeaways

  • RunnablePassthrough.assign keeps the retrieved Documents in the output, so the retriever runs once and the sources shown are the chunks the model read.
  • A citation schema with id, page and verbatim quotes makes citations checkable. It is still a flat list per answer, so add a claim field for true per-claim citations.
  • The model can paraphrase a quote or cite an id that was never retrieved. Verify every quote against its chunk in code, drop failures, and track the failure rate.

Explaining a retrieved chunk

Lesson 20.3: Explainable retrieval. Notebooks: 03a_explainable_retrieval.ipynb

ExplainableRetriever wraps a FAISS index (OpenAI embeddings, k=5) and, for every chunk it returns, makes one more gpt-4o-mini call that writes a paragraph on why the chunk fits the query. The output is a list of {"content", "explanation"} pairs.

Three properties of this design decide where it is useful.

It costs one call per chunk. The loop calls the explanation chain k times, one after another. At k=5 a single search becomes five model calls before any answer is written. Run them with batch to cut the wait, or explain only the chunks the answer cites.

The prompt assumes relevance. It says “Explain why this context is relevant to the query”. The model never sees the similarity score or the other chunks, and it is not offered “this chunk is not relevant” as an answer. In the M11 TF-IDF index of the Larkspur handbook, What happens if my server goes down? ranks the reboot chunk first, on the shared word “server” (M11.2). Asked why reboot is relevant, with no way to say it is not, the model’s likely reply is a reason, such as “rebooting is one way to recover a server” (a representative output). That reads as an explanation and is a rationalisation of a ranking error.

It explains the text, not the ranking. The chunk was ranked by cosine similarity between two vectors. The paragraph is the model’s reading of the query and the chunk side by side, written after the fact. It can be a good guide for a user and a poor guide for an engineer: to debug retrieval, print the scores (similarity_search_with_score) and the rank of the chunk you expected.

A version that helps both readers changes the question it asks:

The notebook asks Ask instead
Why is this context relevant? Is this context relevant to the query? Answer yes or no, then quote the sentence that decides it.
One free-text paragraph A structured result: relevant: bool, evidence: str (verbatim), the retriever’s score
Every retrieved chunk Only the chunks the answer used, or the ones a user expands

The yes or no form is a relevance grader. M28 uses it to filter chunks and rewrite the query, and M32.1 adds a hallucination check and source highlighting on top.

Two notes on running the notebook today. retrieve_and_explain calls self.retriever.get_relevant_documents(query), which langchain-core 1.7 no longer has, so it raises AttributeError; use self.retriever.invoke(query). And the demo indexes three sentences with k=5; FAISS returns all three, so each query gets three explanations, including two for texts about photosynthesis and global warming when the question is why the sky is blue.

Key Takeaways

  • An explainable retriever adds one LLM call per chunk. Batch the calls, or explain only the chunks the answer cites.
  • A prompt that asks why a chunk is relevant gets a reason even for a ranking error. The paragraph explains the text, not the cosine ranking, so debug retrieval with scores and ranks.
  • Ask a yes or no relevance question with a verbatim quote and the retriever’s score instead. That turns the explainer into a relevance grader.

Record representation

Lesson 20.4: RAG over structured data: CSV and JSON. Notebooks: 04a_structured_data_rag.ipynb, 04b_simple_csv_rag.ipynb (optional), 04c_json_rag.ipynb (optional)

A table row is a set of typed fields; an embedding model takes one string. Something has to turn the row into text, and that choice decides what the index can find. 04a shows three ways to write the same row. On the Larkspur server catalogue (ten sizes, the table the lab uses), the ls-mem-4 row becomes:

Representation Text that gets embedded
Every column (CSVLoader style) name: ls-mem-4 vcpu: 4 memory_gb: 32 price_usd: 140 notes: Memory-optimised server for large PostgreSQL databases and analytics queries., one field per line
Natural language A 4-vCPU, 32 GB server, ls-mem-4, at $140 a month. Memory-optimised server for large PostgreSQL databases and analytics queries.
Description only Memory-optimised server for large PostgreSQL databases and analytics queries.

The notebook’s rule picks the third and moves everything else to metadata: free text carries meaning and belongs in page_content; identifiers, categories, numbers and dates are things you filter on and belong in metadata, where a filter compares them exactly.

The lab measures what the choice does with real all-MiniLM-L6-v2 scores:

  • Fields dilute the vector. For A server for a memory-hungry database, the description-only index ranks ls-mem-4 (0.733) and ls-mem-2 (0.626) first, 0.115 ahead of the third row. Embed every column and the two still lead, but ls-mem-2 (0.464491) beats the general-purpose ls-small (0.464116) by 0.0004. The names and numbers in each string pull every row towards every other.
  • Ids in the text make lookups a coin toss. For Tell me about ls-cpu-8., the description never names the server, so similarity matches “cpu” to “CPU cores” and ranks the sibling ls-cpu-4 first (0.535 against 0.517). With every column embedded, ls-cpu-8 wins by 0.050 (0.708 against 0.659). Neither is a lookup; store.get(ids=["ls-cpu-8"]) is.

Two details from the notebook make the split work. row_to_document casts every number with int() before it goes into metadata, because a range filter compares numbers and CSVLoader returns strings (M12.3). And the context sent to the model adds the metadata back: its format_docs prints address, price, bedrooms and year after each description, so the model can quote a price it could not search on.

The rule is a default. “Built in 1962” carries meaning a buyer might search for, in a way “295000” does not; judge each field by whether its value has meaning or only magnitude.

Nested JSON

JSON adds depth: a support ticket has a nested customer object, a tags list and a messages list. ticket_to_document in 04a makes two separate decisions:

  • Meaning goes to page_content: the subject and the conversation, one from: body line per message.
  • Filters go to flat metadata: customer.tier becomes customer_tier, because Chroma rejects nested dicts in metadata.

Lists are the hard case. The notebook joins tags into "export,performance,timeout", and an $eq filter on that string matches only the whole string in that order. Check what your store accepts before you flatten: the chromadb 1.5.9 installed here stores a list value as metadata, and {"tags": {"$contains": "export"}} matches list membership (in a scratch test it returned the record whose tags were ["export", "performance"] and not the one holding the string "export,timeout"). Where the store has no list type, the options are a boolean field per tag or a relational table for tags with only ids in the vector store. When filtering is that relational, the vector store is the wrong primary home for the data.

The optional notebooks show the two ends. 04b loads customers-100.csv with CSVLoader defaults (every column in the text) and asks which company does Sheryl Baxter work for?, an exact lookup by name. 04c uses the jrag library with jsonpath expressions ($.year, $.laureates[*].full_name) to pick the fields of each Nobel Prize record that become Year: …, Category: … text before embedding.

Retrieval reads a sample

Retrieval returns the k rows most similar to the question. Four kinds of question need something else, and on a table they look like ordinary questions:

Question Needs Why retrieval cannot answer it
Aggregation: average, count, sum every row it reads k rows; raising k only moves the cliff and fills the context
Comparison: “under $50”, “since 2025” rows that pass a test the number in the question is embedded as text and filters nothing
Exact lookup: by id, SKU, order number one known row identifiers have no useful similarity
Ranking: the three cheapest a total order similarity orders by meaning, not by price

The interactive lab runs all four on the server catalogue. With description-only text:

  • What is the average monthly price of a Larkspur server? The table’s answer is $102.50. At k = 4 the four retrieved rows average $36.25; at k = 9, $60.56. Only k = 10, the whole table, is right, because the most expensive server, ls-gpu-1 ($480), ranks last for this question in both representations.
  • Which servers cost less than $50 a month? Four servers qualify. k = 4 retrieves three of them plus ls-large at $80; k = 5 gets all four, with ls-large still in the context. With every column embedded it takes k = 6, and two over-budget rows come along.
  • Tell me about ls-cpu-8. At k = 1 the model reads only ls-cpu-4 and would describe the wrong server.

Each of these would come back as a fluent, specific answer. The notebook’s comparison of the two approaches names the difference: query generation fails loudly (a bad query raises or returns nothing), retrieval fails quietly (it answers from whatever it retrieved).

So route by the kind of question, not the kind of data:

The notebook builds each branch in its simplest form:

  • Router. One prompt classifies a question as AGGREGATE, LOOKUP or SEMANTIC, and StructuredRAG refuses the first two instead of answering from a sample.
  • Self-query. llm.with_structured_output(ListingQuery) turns Which properties cost less than $400,000? into a semantic part and, when extraction works, max_price=400000, which becomes a Chroma filter {"price": {"$lte": 400000}}. ($lte lets a listing at exactly $400,000 through; “less than” is $lt.) The full version is M18’s self-querying lesson.
  • Query generation. The model writes one line of pandas over the schema and the notebook evals it. That executes model-written code with full interpreter access, and a data field can carry a prompt injection. In production, generate SQL against a read-only connection with a timeout, or run a sandboxed executor.

Key Takeaways

  • Embed fields whose values carry meaning and put identifiers, numbers and dates in metadata, cast to their real types. Embedding every column dilutes the vector.
  • Retrieval reads a sample of k rows. Aggregation, numeric comparison, exact lookup and ranking need every row, a filter or an id, and retrieval fails on them quietly with a fluent answer.
  • Route by the kind of question: a query engine for aggregates, get-by-id for lookups, self-query filters for ranges, semantic search for the rest. Never eval model-written code without a sandbox.

Local inference

Lesson 20.5: Fully local RAG with Hugging Face and FAISS. Notebooks: 05a_local_rag_huggingface_faiss.ipynb

The notebook replaces every OpenAI call with open models. Its configuration:

Setting Value
Document Understanding_Climate_Change.pdf, loaded with PyPDFLoader
Chunks 1,000 characters, 200 overlap
Embeddings BAAI/bge-base-en-v1.5 through HuggingFaceEmbeddings, on CPU, normalize_embeddings=True, 768 dimensions
Index FAISS, in memory
Retrieval k = 3
Generation HuggingFaceH4/zephyr-7b-beta through HuggingFaceEndpoint, max_new_tokens=256

“Local” has to be checked per component, because one remote call is enough to send the data out. Here the embedding model and the index run on your machine. The generator does not: HuggingFaceEndpoint calls the Hugging Face Inference API, and the notebook asserts that HUGGINGFACEHUB_API_TOKEN is set before it starts. Every prompt, with the three retrieved chunks inside it, leaves the machine.

So the notebook’s own comparison table, which lists data privacy as “Stays local”, is true only for indexing. Its “Next steps” names the fix: replace HuggingFaceEndpoint with HuggingFacePipeline, which loads the model weights and generates in your process. That is the version to offer a Larkspur customer whose contract says support tickets and the handbook may not leave their network.

Component 05a as written Fully offline
Embeddings local, CPU local, CPU
Vector index local, FAISS in memory local, FAISS saved to disk
Generator remote, HF Inference API, needs a token local, HuggingFacePipeline, needs the weights and enough memory
Data leaving the machine every prompt, chunks included none

What you trade for keeping it local:

  • Hardware and latency. A 7B model generating on your own CPU or GPU replaces a network call. Measure tokens per second on the target machine before you promise a latency.
  • One embedding model on both sides. The query must be embedded by the model that embedded the chunks. Switching from OpenAI’s 1,536-dimension vectors to bge’s 768 means re-embedding the whole corpus, not only new documents.
  • Saving the index runs pickle. The notebook’s commented FAISS.load_local(..., allow_dangerous_deserialization=True) needs that flag because the docstore is a pickle file, and loading a pickle can run code. Load only index files your own pipeline wrote.

Two smaller things to change when you reuse the code:

  • RunnableParallel(answer=rag_chain, sources=retriever) retrieves twice, once inside rag_chain and once for sources (a counting retriever in a scratch test was called two times). On a fixed FAISS index the two lists match, so the cost is the extra search. On an index that updates between the calls, the sources shown could differ from the context the model read. The RunnablePassthrough.assign pattern from 20.2 retrieves once.
  • ask keeps the text after the last Answer:, to strip a prompt echoed back with the completion. The installed HuggingFaceEndpoint already defaults to return_full_text=False, so the split guards against nothing today and cuts any answer that itself contains “Answer:”. Drop it, or keep return_full_text=False explicit if you move to HuggingFacePipeline.

The notebook’s fallback evaluation counts expected keywords in each answer (“carbon dioxide”, “methane”). Substring matching rewards any answer that mentions the words, right or wrong; treat it as a smoke test and use the golden-set metrics from M11 for decisions.

Key Takeaways

  • Check “local” per component. One remote call sends the data out: HuggingFaceEndpoint ships every prompt, chunks included, to the Inference API, while HuggingFacePipeline generates in your process.
  • Changing embedding models means re-embedding the whole corpus. Measure tokens per second on the target hardware before promising a latency.
  • Load only FAISS index files your own pipeline wrote, because the docstore is a pickle. Retrieve once and reuse the result so the sources shown match the context.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. A Larkspur customer forwards a support answer about annual-plan refunds. Its citation quotes “Annual plans are fully refundable for 30 days” and points to page 0 of the handbook. Neither the sentence nor a page 0 exists. What happened, and what do you change?

What a strong answer covers:

  • Two separate faults: the quote is a paraphrase the model wrote, and the page is the PDF loader’s 0-based number shown without adding 1
  • Logs the request: the retrieved chunk ids, the answer, the raw QuotedCitations, to confirm the cited id was among the retrieved chunks
  • Adds a code check before display: each quote, whitespace-normalised, must appear in the chunk with that id; failures are dropped or flagged, never shown as citations
  • Tracks the quote-failure rate per day and alerts on a jump, which signals a model, prompt or chunking change

2. The team wants to cut latency by asking for the answer and its citations in one structured call instead of two. What do you gain and lose?

What a strong answer covers:

  • Gains one round trip and the tokens of sending the context twice
  • In one call the model writes claims and their support together, which can tie each citation to a claim; in two calls citations are a post-hoc search for support
  • Either way the quote check in code stays, since neither design makes quotes verbatim
  • Decides on the golden set: citation precision, unsupported-claim rate and latency for both designs, not on intuition

3. After the citation feature ships, how do you know whether answers are better supported than before, and how do you keep watching it?

What a strong answer covers:

  • Offline: on the golden set, citation precision (cited chunk supports the claim), citation recall (claims with a citation) and the quote-match rate
  • Online: share of answers with at least one verified citation, share of “I don’t know” answers, and quote-failure rate
  • Samples traffic for an LLM or human judge of whether each claim is supported by its quote
  • Watches refusals on questions the handbook does answer, since a stricter prompt can trade hallucinations for missed answers

4. Product adds the server catalogue to the index, and the assistant tells a customer the average Larkspur server costs about $36 a month. The real average is $102.50. Why, and what is the fix?

What a strong answer covers:

  • Retrieval read the top 4 of 10 rows, the ones whose descriptions resemble the question most; they average $36.25, and the $480 GPU server ranks last
  • No k fixes it below the whole table; aggregation, comparisons, id lookups and rankings need every row or an exact filter
  • Routes by question type: aggregates to SQL on a read-only connection, id lookups to a get by id, price limits to a metadata filter, descriptive questions to the vector store
  • Adds these four question kinds to the golden set, with the right answer computed from the table, so a regression shows up as a wrong number

5. A bank evaluating Larkspur’s assistant requires that no customer data leaves its network. The team says the system is local because it uses bge-base-en-v1.5 and FAISS. Is it, and what changes?

What a strong answer covers:

  • Checks every component: embeddings and FAISS run locally, but HuggingFaceEndpoint sends each prompt, retrieved chunks included, to the Hugging Face Inference API
  • Moves generation in-process with HuggingFacePipeline (or another self-hosted server inside the network) and removes the API token
  • Sizes the hardware: memory for a 7B model, tokens per second on the target machine against the latency requirement
  • Keeps the same embedding model for queries and documents, and loads saved FAISS indexes only from files the pipeline wrote, since load_local unpickles them

Key Takeaways

  • Carry metadata from the store to the answer. A chunk without its id, source and page in the output cannot be cited.
  • Treat citations as model output to verify: check each quote against the chunk it names, show the page counting from 1, and count the failures.
  • Route a question by what it needs. If it needs every row, a filter or one known record, send it to a query, a filter or a get by id, not to top-k retrieval.
  • Call a pipeline local only after checking each component, the generator above all.
