M22 Framework fluency with LlamaIndex

M22 rebuilds pipelines you already know from the LangChain modules in LlamaIndex: a plain vector RAG, hybrid fusion, reranking and an enrichment window. The ideas are the same; the class names and several defaults change. The M22 notebooks build on four ideas: the Node as the unit LlamaIndex indexes, the QueryEngine that wraps retrieval and answering, the postprocessors that edit the retrieved list in between, and the sentence window that retrieves one sentence and sends its neighbours.

Sentence window lab
Open the lab

The notebooks run on a 33-page climate-change PDF and a 100-row customer CSV. These pages and the lab use the Larkspur Cloud handbook from M11 to M13, loaded as two Documents: the refunds section from M13 and a short exports section. Three golden questions carry the module: Can I get a refund on an annual plan after 45 days?, How long does a refund take to appear? and Can I export my data after I cancel my plan? The first one is the hard case. Its best-matching sentence is the 30-day full-refund rule, and the answer sits in the sentence after it.

TL;DR

  • A LlamaIndex Node is a chunk with an id, metadata and links to its source Document and its neighbours. chunk_size counts tokens, and the metadata string counts against it: on the notebook’s PDF the page label and file path take 38 of the 200 tokens.
  • index.as_query_engine() builds a retriever, a list of node postprocessors and a response synthesizer, and returns the answer with its source_nodes. Check the defaults: similarity_top_k is 2, and QueryFusionRetriever makes 4 queries (3 of them written by the LLM) unless you set num_queries=1.
  • Postprocessors run in list order on the retrieved nodes. On the handbook, retrieving 10 sentences and letting the ms-marco-MiniLM-L-6-v2 cross-encoder keep 2 brings in the prorated-refund rule that plain top-2 retrieval misses.
  • A sentence window embeds one sentence and sends up to window_size sentences on each side. In the lab the retrieval scores are identical for every window size; only the text the LLM reads changes, from 142 characters for the bare sentence to 621 at the notebook’s window_size=3.
  • The notebooks pass a FAISS store to IngestionPipeline without an embedding step, so FAISS stays empty and VectorStoreIndex(nodes) builds a second, in-memory index. Read what each object actually holds before trusting a port.

Mental model

The diagram is M11’s lifecycle with LlamaIndex names on the boxes, plus a stage M11 does not have. Node postprocessors sit between retrieval and the LLM, and reranking, filtering and window replacement all plug in there. Each one takes a scored list of nodes and returns another.

Nodes

Lesson 22.1: Simple PDF and CSV RAG in LlamaIndex. Notebooks: 01a_simple_rag_with_llamaindex.ipynb, 01b_simple_csv_rag_with_llamaindex.ipynb (optional)

LlamaIndex has two text objects where LangChain has one. A Document is what a reader loads: SimpleDirectoryReader turns the notebook’s climate-change PDF into 33 Documents, one per page, and PagedCSVReader turns the 100-row customer CSV into 100 Documents, one per row. A Node is what the index stores: a piece of a Document with its own id, text, metadata, an optional embedding, and relationships. Every node that SentenceSplitter produces from the PDF carries three: SOURCE (its Document), PREVIOUS and NEXT (its neighbours). The neighbour links let a query engine fetch the text around a hit later; PrevNextNodePostprocessor follows them from the docstore.

The concepts map onto the LangChain pieces from M11 to M19:

LangChain LlamaIndex What changes
Document from a loader Document from a reader Loaded unit; PDF readers give one per page in both
Document chunk from a text splitter TextNode from a node parser Node has an id and neighbour links
RecursiveCharacterTextSplitter SentenceSplitter Size in tokens, not characters
Embed, then add_documents IngestionPipeline, then VectorStoreIndex Transformations run as a list
vectorstore.as_retriever(k=…) index.as_retriever(similarity_top_k=…) Default k is 2
EnsembleRetriever QueryFusionRetriever Four fusion modes (22.2)
Compressor or reranker wrapper Node postprocessor A list on the query engine (22.3)
A retrieval chain QueryEngine Retrieve, postprocess, synthesise

Two differences change the chunks you get from the same numbers.

chunk_size counts tokens. 01a sets CHUNK_SIZE = 200 and CHUNK_OVERLAP = 50 and says so in a comment: LangChain’s splitter measures characters by default, SentenceSplitter measures tokens. 200 tokens is several times longer than 200 characters, so a “200” ported from a LangChain notebook is not the same split.

Metadata counts against the chunk and goes into the embedding. SentenceSplitter builds the metadata string a node will carry, measures it in tokens and subtracts it from chunk_size before splitting. The PDF reader attaches page_label, file_name, file_path, file_type, file_size and two dates, and excludes all of them from the embedding and LLM text except page_label and file_path. On the checkout used for this page those two come to 38 tokens, so a 200-token chunk holds at most 162 tokens of text; the largest of the 123 nodes holds 158. The absolute file path is part of every vector. Set excluded_embed_metadata_keys and excluded_llm_metadata_keys on the Documents before splitting when a field should be stored but not embedded.

Splitting never crosses a Document boundary. 02a uses SentenceSplitter() with its defaults of 1,024 tokens and 200 overlap, and every PDF page fits in one chunk, so the 33 pages become exactly 33 nodes. The page, not the chunk size, decides what a chunk is.

On the Larkspur handbook the two sections load as two Documents. Lesson 22.4 splits them into one node per sentence: 13 for the refunds section and 4 for exports.

What the 01a ingestion actually builds

01a creates a FAISS index, passes it to IngestionPipeline(..., vector_store=vector_store), then builds VectorStoreIndex(nodes). With llama-index-core 0.14.25 two things go wrong:

  • The cleaner runs on Documents and crashes. TextCleaner comes before the splitter, so it receives Documents, and Document.text is a read-only property: AttributeError: property 'text' of 'Document' object has no setter. 02a puts the cleaner after SentenceSplitter, where the nodes’ text can be set; 01a needs the same order. With that change the 33 pages become 123 nodes.
  • FAISS stays empty. The pipeline has no embedding transformation, and IngestionPipeline only adds nodes that already have an embedding to its vector store. After the run the FAISS index holds 0 vectors. VectorStoreIndex(nodes) then embeds the nodes again into the default in-memory store, and that is the index the notebook queries. The same pattern repeats in every M22 notebook.

To keep the vectors in FAISS, embed in the pipeline and give the store to the index:

pipeline = IngestionPipeline(transformations=[SentenceSplitter(chunk_size=200, chunk_overlap=50), TextCleaner(), Settings.embed_model])
nodes = pipeline.run(documents=documents)            # nodes now carry embeddings
index = VectorStoreIndex(nodes, storage_context=StorageContext.from_defaults(vector_store=vector_store))

Run on the notebook’s PDF with a local embedding model in place of OpenAI’s: the pipeline makes 123 embedding calls, one per node, the index makes none, and FAISS ends with 123 vectors. VectorStoreIndex.from_vector_store(vector_store) does not work here, because the FAISS store keeps vectors but not text; it raises Cannot initialize from a vector store that does not store text.

QueryEngine

index.as_query_engine(similarity_top_k=2) returns a RetrieverQueryEngine. Each query(question) call runs three stages and returns the Response to the caller:

  • The retriever embeds the question and returns the similarity_top_k nearest nodes as NodeWithScore objects. The default is 2.
  • The postprocessors are the node_postprocessors list, applied in order. 01a passes none; lessons 22.3 and 22.4 add a reranker and a window replacement here.
  • The synthesizer puts the nodes’ text into a prompt for Settings.llm. The default response_mode is compact: it packs the nodes’ text into as few prompts as the context window allows, then refines the answer across them.

response.response is the answer; response.source_nodes is the list of nodes the answer was built from, with their scores. 01a’s evaluate_rag reads both: the answer goes to the correctness and faithfulness metrics, the source node texts become the retrieval context for DeepEval’s ContextualRelevancyMetric. Logging source_nodes on every production query gives the same view without an evaluation run.

query_engine.retrieve(QueryBundle(question)) runs the retriever and the postprocessors without the LLM, which is how the lab in 22.4 was checked. Building the engine still needs an LLM: as_query_engine() resolves Settings.llm when it is created, and with no model set and no OpenAI key it raises before any retrieval. Set Settings.llm (a MockLLM works for tests) or use index.as_retriever() when you only need nodes.

The CSV variant

01b reads each CSV row as one Document whose text is one column: value line per field:

Index: 1
Customer Id: DD37Cf93aecA6Dc
First Name: Sheryl
Last Name: Baxter
Company: Rasmussen Group

It skips splitting, embeds each row, and asks which company does sheryl Baxter work for? with similarity_top_k=2. The answer is in row 1 (Rasmussen Group), and the row’s own text names her, so one retrieved row is enough. A question about many rows (“how many customers are in Chile?”) gets the same two rows, and no prompt can count the other 98. Row-per-Document RAG answers lookups; counts, sums and filters belong to a query over the table, which M20 covers.

Key Takeaways

  • A Document is what a reader loads; a Node is what the index stores, with an id, metadata and neighbour links. Splitting never crosses a Document boundary.
  • SentenceSplitter counts tokens, not characters, and subtracts embedded metadata from chunk_size. Exclude fields such as file paths from the embedding when they should only be stored.
  • A query engine retrieves, postprocesses and synthesises; log source_nodes on every query. Put the embedding model in the ingestion pipeline, or the vector store you passed stays empty.

QueryFusionRetriever

Lesson 22.2: Fusion retrieval with QueryFusionRetriever. Notebooks: 02a_fusion_retrieval_with_llamaindex.ipynb

QueryFusionRetriever is LlamaIndex’s EnsembleRetriever: it runs several retrievers and merges their lists. 02a gives it a vector retriever and a BM25Retriever, both at similarity_top_k=2:

retriever = QueryFusionRetriever(
    retrievers=[vector_retriever, bm25_retriever],
    retriever_weights=[0.6, 0.4],
    num_queries=1,
    mode="dist_based_score",
    use_async=False,
)

Three of its defaults change what a port does:

  • num_queries defaults to 4. The retriever keeps your question and asks Settings.llm to write 3 more, then runs every query on every retriever: with two retrievers, 8 retrievals and one LLM call per question. 02a sets num_queries=1, which turns query generation off. M18 covers what the extra queries buy.
  • similarity_top_k defaults to 2. It cuts the fused list. 02a does not set it, so two retrievers with two hits each still return two nodes.
  • mode defaults to simple. The four modes, as llama-index-core 0.14.25 implements them:
Mode Scaling inside each list How lists combine
relative_score Min-max: best 1, worst 0 Times weight, summed per node
dist_based_score Min-max between mean ± 3 std Times weight, summed per node
reciprocal_rerank 1 / (60 + rank), rank from 0 Summed per node; weights ignored
simple None Highest raw score per node

retriever_weights are divided by their sum, so [0.6, 0.4] stays as it is and [3, 2] becomes the same thing. Scores in the two score modes are also divided by num_queries.

On the Larkspur handbook, split into one node per sentence, the 45-day refund question gives two short lists. The vector side (all-MiniLM-L6-v2, run locally in place of the notebook’s OpenAI model) returns the 30-day rule at 0.6922 and “Monthly plans are not refundable” at 0.5373. BM25 returns the 30-day rule at 2.3898 and the prorated rule, the one that answers the question, at 1.9076. Fused by the real QueryFusionRetriever with 02a’s settings:

Mode Fused top 2 Prorated rule
dist_based_score 30-day rule 0.6667, monthly 0.2000 3rd, 0.1333
relative_score 30-day rule 1.0, monthly 0.0 3rd, 0.0
reciprocal_rerank 30-day rule 0.0333, monthly 0.0164 3rd, tied at 0.0164
simple 30-day rule 2.3898, prorated 1.9076 2nd

Only simple keeps the answer, and for the wrong reason: it compares a BM25 score with a cosine similarity, and BM25 scores run higher. Three behaviours explain the rest of the table:

  • With two hits per list, dist_based_score ignores the gap. Two scores have a mean halfway between them and a standard deviation of half their difference, so mean ± 3 std always maps the better one to 2/3 and the worse to 1/3. In a check with fixed scores, dropping the vector runner-up from 0.80 to 0.10 left every fused score unchanged. The 0.6 and 0.4 weights then decide the order: 0.6 × 1/3 = 0.2 for the vector runner-up beats 0.4 × 1/3 = 0.1333 for the BM25 runner-up. Flip the weights to 0.4 and 0.6 and the prorated rule wins the second place at 0.2.
  • relative_score with two hits sends every runner-up to 0. Both second places score 0 here, and the cut falls between equal scores.
  • reciprocal_rerank drops retriever_weights. The constant is 60 and ranks start at 0, so a node first in one list scores 1/60. EnsembleRetriever in M17 multiplies each term by its weight and counts ranks from 1; the two “RRF” scores are not interchangeable.

02a’s note on the modes says reciprocal rerank is unsuitable “since there is no normalization”. Rank fusion never looks at the scores, so their scales cannot hurt it; the mode where scales collide is simple, the default. M17’s fusion lesson works through score and rank fusion in general. In LlamaIndex the same mode names carry different constants.

The BM25 side differs from LangChain’s too. LlamaIndex’s BM25Retriever runs bm25s with an English stemmer, English stop words and the token pattern \b\w\w+\b, so “refund” in the question matches “refunds” in the prorated rule. LangChain’s BM25Retriever splits on whitespace and would not match them.

Score direction

Every fusion mode assumes a higher score is better. The vector retriever in 02a comes from VectorStoreIndex(nodes) with the default in-memory store, which returns cosine similarity, so the assumption holds. Wire the notebook’s FAISS store in properly (22.1) and it stops holding: IndexFlatL2 returns squared L2 distances as score, where lower is better.

The same three handbook sentences, retrieved for the 45-day question through two FAISS indexes:

Sentence IndexFlatIP score IndexFlatL2 score
30-day full-refund rule 0.6922 0.6155
Monthly plans are not refundable 0.5373 0.9254
Prorated rule 0.5267 0.9465

The order is the same; the scale runs the other way. On unit-length vectors the squared distance is 2 minus twice the cosine (2 - 2 × 0.6922 = 0.6156). Feed the L2 list to relative_score and the nearest sentence scales to 0 while the farthest gets the full weight. Use IndexFlatIP on normalised vectors when FAISS feeds a fusion retriever, and print each retriever’s raw scores once before trusting the fused list.

Key Takeaways

  • Check the defaults before porting: num_queries=4 adds an LLM call and multiplies retrievals, similarity_top_k=2 cuts the fused list, and the default simple mode compares raw scores across retrievers.
  • With two hits per list, the score modes flatten the gap and the weights decide the order. reciprocal_rerank ignores retriever_weights and counts ranks from 0.
  • Every fusion mode assumes higher is better. Use inner product on normalised vectors rather than L2 distance, and print each retriever’s raw scores once.

Postprocessors

Lesson 22.3: Reranking with node postprocessors. Notebooks: 03a_reranking_with_llamaindex.ipynb

A node postprocessor takes the retrieved list of NodeWithScore and the question, and returns a list. It can reorder the nodes, drop some, replace their scores or rewrite their text. A query engine runs its node_postprocessors in list order, after the retriever and before the synthesizer; outside an engine, postprocess_nodes(nodes, QueryBundle(question)) runs one by hand, as 03a does for its comparison.

03a uses the slot for two-stage retrieval (M19): retrieve wide with similarity_top_k=10, rerank, keep top_n=5.

The two rerankers in 03a fill that box differently:

  • LLMRerank(top_n=5) sends the nodes to Settings.llm in batches of choice_batch_size (default 10), so 03a’s 10 nodes cost one call. The prompt numbers the documents and asks for lines like Doc: 9, Relevance: 7, a score from 1 to 10, and tells the model to leave out irrelevant documents. Listed nodes get that integer as their new score; unlisted nodes are dropped, and so are lines the parser cannot read, without an error. The result can be shorter than top_n, and integer scores tie often. The default top_n is 10.
  • SentenceTransformerRerank(model="cross-encoder/ms-marco-MiniLM-L-6-v2", top_n=5) scores every question and node pair with a cross-encoder and keeps the best top_n. It reads each node’s embedding text, metadata included, and replaces the retrieval score with the model’s raw output; keep_retrieval_score=True copies the old score into the node’s metadata first. Its defaults are cross-encoder/stsb-distilroberta-base and top_n=2, so a port that drops the arguments changes the model and the cut.

M19 compares the two families in depth (LLM against cross-encoder reranking). In LlamaIndex both are node postprocessors and swap in the same list.

The handbook, reranked

Split the Larkspur handbook into one node per sentence, ask Can I get a refund on an annual plan after 45 days?, retrieve 10 with all-MiniLM-L6-v2 and rerank with 03a’s cross-encoder keeping 2:

First Second
Retrieval alone, top 2 30-day full-refund rule (0.6922) Monthly plans are not refundable (0.5373)
Cross-encoder over top 10 30-day full-refund rule (7.0657) Prorated rule after day 30 (-2.1011)

The reranker brings the sentence that answers the question into the context. It also scores that sentence below zero. ms-marco-MiniLM-L-6-v2 returns a logit, not a probability, so its scores only rank; a filter that drops nodes under 0 would have dropped the answer. Calibrate any cut-off on the golden set.

The capital-of-France example

03a builds five chunks: three one-liners that repeat the question’s words (“The capital of France is great.”, “…huge.”, “…beautiful.”) and two longer passages about visiting Paris. Asked what is the capital of france?, the embedding retriever ranks the one-liners first. Run locally with the same two models as above:

Chunk Bi-encoder (all-MiniLM-L6-v2) Cross-encoder (ms-marco-MiniLM-L-6-v2)
The capital of France is huge. 0.8105 6.8955
The capital of France is great. 0.7805 8.0029
The capital of France is beautiful. 0.7687 7.3871
Have you ever visited Paris? … 0.5174 1.0889

The cell that sets up the example also carries a port bug. It builds Document(page_content=sentence), LangChain’s keyword. Order in the list

Postprocessors see whatever the one before them produced. With lesson 22.4’s MetadataReplacementPostProcessor in the same list, putting the reranker first means it scores the single sentence that was embedded; putting it second means it scores the whole window, which gives a cross-encoder more context at the cost of longer inputs. Decide which text the reranker should judge, and write the list in that order.

Key Takeaways

  • Node postprocessors run in list order between the retriever and the synthesizer, and can reorder, drop, rescore or rewrite nodes. Retrieve wide and let a reranker keep top_n.
  • LLMRerank can silently return fewer than top_n nodes with tied integer scores. SentenceTransformerRerank defaults to a different model and top_n=2, so always pass both arguments.
  • Cross-encoder scores are logits that only rank; the answering sentence can score below zero. Calibrate any cut-off on the golden set.

Sentence window

Lesson 22.4: Sentence-window retrieval. Notebooks: 04a_context_enrichment_window_with_llamaindex.ipynb

Small chunks match a question precisely and large chunks answer it completely (M13). A sentence window does both: it embeds single sentences and, once one is retrieved, sends the model the sentences around it. LlamaIndex builds it from two pieces, a node parser at indexing time and a postprocessor at query time.

SentenceWindowNodeParser splits each Document into sentences with NLTK’s Punkt tokenizer and makes one node per sentence. For sentence i it stores two metadata fields: the sentences from i - window_size to i + window_size joined with spaces (window), and the sentence itself (original_text; 04a renames it original_sentence). It adds both keys to the node’s excluded embed and LLM metadata, so the vector is the sentence alone. window_size defaults to 3, seven sentences in all, as 04a’s comment says, and must be greater than 0: window_size=0 fails validation. A window never crosses into another Document.

MetadataReplacementPostProcessor(target_metadata_key="window") runs after retrieval and sets each node’s text to its window metadata (a node without that key keeps its text). The synthesizer then reads the window. The notebook’s note that “metadata replacement” sounds off-topic comes from this: the neighbours travel as metadata until this step puts them in the text.

On the Larkspur handbook the parser makes 17 nodes: 13 sentences in the refunds section and 4 in exports. The first sentence of each section carries the section title with it, because Punkt does not split at a blank line.

The interactive lab runs that index with all-MiniLM-L6-v2 (the notebook uses OpenAI’s text-embedding-3-small, which scores differently), lets you move window_size from 0 (postprocessor off) to 5 and similarity_top_k between 1 and 2, and shows what the model receives. Its windows are a port of the parser’s join, checked against the real LlamaIndex pipeline on all 30 settings of question, window and k: the same retrieved sentences, the same scores and the same window text, character for character. At similarity_top_k=1:

Question Window 0 Window 1 Window 2 Window 3
Refund on an annual plan after 45 days? 142 chars, answer missing 284, answer in 495 621
How long does a refund take to appear? 90, answer in 291 496 620
Export my data after I cancel? 86, 1 of 2 facts 188, 1 of 2 272, both 272
  • The window changes what the model reads, never what is retrieved. Every sentence scores the same at every window size, because the window is excluded from the embedding. Tuning window_size cannot fix a retrieval miss.
  • Each question needs a different window. The 45-day question retrieves the 30-day full-refund rule; the prorated rule that answers it is the next sentence, so a window of 1 is enough. The refund-timing sentence answers its question alone. The export question needs the “Settings, then Data” sentence two places back.
  • The Document boundary caps the window. The exports section has four sentences, so every window from 2 up sends the same 272 characters. A section split into its own Document limits how far a window can reach, which is useful when sections are independent and harmful when the answer spans two of them.
  • Two hits can send the same sentences twice. At similarity_top_k=2 the refund-timing question retrieves its sentence and the 30-day rule two places before it. At window_size=3 their windows share 5 sentences, and the model reads 1,241 characters to cover 9 distinct sentences. Merge overlapping windows before synthesis when k is above 1.

The window is stored, not computed at query time. Each node holds its window and a copy of its sentence in metadata: on the handbook that is 5,249 characters of metadata at window_size=1, 9,313 at 3 and 12,342 at 5, against 1,380 characters of sentence text. At the notebook’s default the metadata is 6.75 times the text, held in the docstore or the vector store’s payload for every node.

M19’s enrichment windows do the same job with character chunks and a neighbour lookup at query time. LlamaIndex moves the work to indexing time and the unit to the sentence, and 04a compares it against a SentenceSplitter() index at its 1,024-token default, both at similarity_top_k=1. Both of 04a’s pipelines are handed the same FAISS store, which stays empty for the reason in 22.1; each VectorStoreIndex builds its own in-memory store.

Key Takeaways

  • A sentence window embeds single sentences and swaps in the surrounding sentences after retrieval. The window changes what the model reads, never what is retrieved.
  • Each question needs a different window, and a Document boundary caps how far a window reaches. Merge overlapping windows when similarity_top_k is above 1.
  • Windows are stored in metadata on every node. At the default window_size of 3, the handbook’s metadata is 6.75 times its sentence text.

Check yourself

1. Why can changing the window size never fix a retrieval miss?

The window is excluded from the embedding, so the vector is the sentence alone and every sentence scores the same at every window size. The window only changes what the model reads after retrieval, when MetadataReplacementPostProcessor swaps the node’s text for its window metadata.

2. For the question about exporting data after cancelling, at top-k of 1, what window size do you need, and why does a larger one change nothing?

A window of 2, because the “Settings, then Data” sentence sits two places back from the retrieved one; that window holds both facts in 272 characters. The exports section is its own Document with four sentences, and a window never crosses a Document boundary, so every window from 2 up sends the same 272 characters.

3. At top-k of 2 and window size 3, the refund-timing question sends the model 1,241 characters. What is wasted, and what do you do?

The two retrieved sentences are two places apart, so their windows share 5 sentences, and 1,241 characters cover only 9 distinct sentences. Merge overlapping windows before synthesis whenever k is above 1.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. You port Larkspur’s hybrid retriever to LlamaIndex: a FAISS IndexFlatL2 vector store and BM25, fused with QueryFusionRetriever(mode="relative_score"). The fused top result is now the least relevant handbook passage. What happened?

What a strong answer covers:

  • Prints each retriever’s raw scores before fusion. With IndexFlatL2, LlamaIndex’s FAISS store returns squared L2 distances as score, so lower is better
  • relative_score min-max scales each list with higher meaning better, so the nearest chunk gets 0 and the farthest gets the full weight
  • Fixes the direction at the source: IndexFlatIP on normalised vectors (cosine similarity), or a retriever wrapper that flips distances
  • Adds a golden-set check that compares fused results with each retriever alone, so a scale or direction bug shows up as a regression

2. The refund assistant answers “Can I get a refund after 45 days?” with “No, only within 30 days.” The handbook prorates refunds after day 30. Do you raise window_size, raise similarity_top_k, or add a reranker?

What a strong answer covers:

  • Checks the retrieved sentence first: it is the 30-day rule, and the prorated rule is the next sentence, ranked third
  • A window of 1 sends both rules in 284 characters; similarity_top_k=2 adds “Monthly plans are not refundable” instead
  • A cross-encoder over the top 10 also brings the prorated rule into the top 2, at the cost of a model call per candidate
  • Weighs storage too: at window_size=3 the handbook’s window metadata is 6.75 times its text, held on every node

3. The M22 lab asks you to port the Part VI hybrid-plus-rerank pipeline to LlamaIndex and confirm the metrics match. They do not. How do you find out why?

What a strong answer covers:

  • Compares retrieved node ids per golden question before comparing answer scores, so retrieval and generation differences separate
  • Lists the default changes: chunk_size in tokens against LangChain’s characters, metadata counted in the chunk budget and embedded with the text, and similarity_top_k=2
  • Checks BM25 tokenisation: LlamaIndex’s BM25Retriever stems and drops English stop words, LangChain’s splits on whitespace
  • Checks fusion: LlamaIndex’s reciprocal_rerank ignores retriever_weights, while EnsembleRetriever applies weights to RRF

4. LLMRerank(top_n=5) sometimes returns one node, and on a few questions none. The answers that follow are thin or refuse. What is going on, and what do you change?

What a strong answer covers:

  • The default prompt tells the LLM to leave out documents that are not relevant, so the output can be shorter than top_n
  • Nodes the LLM omits are dropped, and the parser skips lines it cannot read without raising, so a reply in another format drops its whole batch of up to 10
  • Logs the raw reranker reply and the count in and out per query, and alerts on empty results
  • Falls back to the retrieval order when the reranker returns too few nodes, or uses a cross-encoder, which always scores every candidate

5. A refactor removed num_queries=1 from the fusion retriever. Retrieval quality looks the same on the golden set, but latency and the LLM bill went up. Why?

What a strong answer covers:

  • QueryFusionRetriever defaults to num_queries=4: one LLM call writes 3 extra queries, and each query runs on every retriever
  • With two retrievers that is 8 retrievals and one generation call before the answer step starts
  • Treats default parameters as part of the pipeline’s config: pin them explicitly and diff them in code review
  • Measures per-stage latency and token use in traces, not only end-to-end quality, so a cost regression shows even when accuracy holds

Key Takeaways

  • Map the concepts first: Document and Node, retriever, postprocessor, QueryEngine. Then read the defaults, because they differ from LangChain’s.
  • Check what each component holds after the pipeline runs: vectors in the store, metadata in the embedding text, and the score direction of every retriever.
  • Put reranking, filtering and window replacement in node_postprocessors, in the order you want them applied.
  • Retrieve small, send big: a sentence window keeps the retrieval scores of a sentence and gives the model the paragraph around it. Size the window per question type and watch overlap when k is above 1.
