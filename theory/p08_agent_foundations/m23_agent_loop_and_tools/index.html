M23 The agent loop and tool calling

An agent is a model call inside a loop. The model reads the conversation and either answers or asks for tools; your code runs the tools, appends their results, and calls the model again. The M23 notebooks build on four ideas: the loop itself, the schema a tool becomes when the model reads it, how to score whether the model called the right tool with the right arguments, and who runs the tool, you or the provider.

Open the lab

The running example is a support agent for Larkspur Cloud, the fictional host from M11 to M13. It has two client-side tools: search_handbook, which ranks the twelve handbook chunks from the M11 lab with TF-IDF and returns the best two, and get_server_status, which looks up one of the customer’s servers. The golden questions are an M11 one (Can I export my data after I cancel my plan?), a two-tool one (Is my server web-1 running, and does a reboot change its IP address?), and two that fail on purpose: a server that does not exist and a tool call with the wrong argument name.

TL;DR

  • The loop has one rule: while the model’s reply holds tool calls, run them and call the model again; a reply with no tool calls is the answer. Cap the rounds (the from-scratch ReactAgent stops at max_rounds=10).
  • A tool reaches the model only as a schema: a name, a description and typed parameters. Without type hints the @tool decorator emits "query": {}, and the model gets no type to follow.
  • Tool results go back as one ToolMessage per call, matched by tool_call_id. A two-tool question in the lab ends with 5 messages; a retried call ends with 6.
  • A tool error has to reach the model as a message. ToolNode’s default only catches bad arguments and re-raises exceptions from inside the tool; in the lab, handle_tool_errors=True answers 4 of 4 questions, the default 3 and False 2.
  • Score tool selection, tool input and synthesis separately. Run code yourself when it touches customer data; use a hosted tool for commodity work where nothing needs enforcing between the call and the result.

Mental model

The model never runs anything. It writes a request; your code decides whether to run it, runs it, and writes the result into the conversation. Every later agent in this course, from create_agent to a multi-agent graph, is this loop with more around it.

Agent loop

Lesson 23.1: Agentic patterns from scratch: reflection, tool use, ReAct planning. Notebooks: 01b_tool_use_pattern.ipynb, 01c_planning_pattern_react.ipynb, 01a_reflection_pattern.ipynb (optional)

The three notebooks build the same machine three times, each with more of a loop in it. They use only the raw OpenAI SDK and gpt-4o-mini: no tools= parameter and no framework, so every step that frameworks hide is a line of Python you can read.

Pattern Notebook What repeats Stops when
Reflection 01a (optional) Generate a draft, critique it with a second persona, regenerate The critic answers <OK>, or after n_steps rounds
Tool use 01b Nothing: one round of tool calls, then the answer The model has answered from the observation
ReAct planning 01c Thought, tool call, observation The model writes <response>, or after max_rounds (10 by default)

Tool calling by hand. In 01b the model never receives a function. It receives text: a system prompt that lists each tool’s signature inside <tools> tags and asks for calls in a fixed format. The model answers What’s the current temperature in Madrid, in Celsius? with text, not an answer:

<tool_call>
{"name": "get_current_weather","arguments": {"location": "Madrid", "unit": "celsius"}}
</tool_call>

Your code does the rest: a regular expression strips the tags, json.loads turns the call into a dict, get_current_weather(**arguments) runs it, and the result goes back as a user message, Observation: {"temperature": 25, "unit": "celsius"}. A second model call turns that into the sentence the user reads. The @tool decorator automates the signature (name, docstring, type hints), and validate_arguments casts values to the annotated types, so "5" becomes 5 when the hint says int.

01b’s ToolAgent stops after one round. It cannot use one tool’s result to choose the next call, and that is the gap ReAct fills.

The ReAct loop. 01c gives the model a protocol: think inside <thought>, act with a <tool_call>, read the <observation> your code sends back, and finish inside <response>. The notebook’s task needs three calls in order, each depending on the one before:

Dependent steps work because every observation stays in the chat history for the next turn. Written out, ReactAgent.run() is a short loop:

for _ in range(max_rounds):                    # 10 by default
    reply = model(history)
    if has_tag(reply, "response"):
        return the response                    # the model says it is done
    for call in tool_calls(reply):
        history.append(observation(run(call)))  # results feed the next turn

The loop has two exits. The <response> tag is the model’s own decision to stop. max_rounds is yours: without it, a model that keeps asking for tools (because the tool keeps returning nothing useful, say) runs and bills forever.

What the hand-written version cannot guarantee. Nothing forces the model to write valid JSON, name a real tool or supply every argument; the parser raises ValueError when the tags or the JSON are wrong. The type casting covers four types (int, str, bool, float). Native tool calling (lesson 23.4) moves the schema into the API, so the provider returns structured tool_calls with ids. The loop stays the same.

For Larkspur’s support agent the loop is identical with different tools. How long does a refund take? becomes a thought (“I need the refund policy”), a call to search_handbook, an observation holding the retrieved chunks, and a response that quotes them. The M23 lab runs that question through LangGraph’s version of this loop, including a first call that fails.

Check yourself

1. Why can the ReAct agent chain three dependent tool calls when the one-round tool-use agent cannot?

The ToolAgent in 01b runs one round of tool calls and then answers, so it cannot use one result to choose the next call. ReactAgent.run() loops, and every observation stays in the chat history, so the model sees 6912 before it asks to multiply it by 5.

2. The ReAct task sums 1234 and 5678, multiplies the result by 5, then takes the log. How many observations does your code send back, and what is the second?

Three observations: 6912, 34560 and 10.450452222917992. The second, 34560, is the result of multiply_two_elements(6912, 5). After the third the model finishes inside <response> with about 10.45.

3. A hand-written ReAct agent keeps calling a search tool that returns nothing useful, and the bill keeps growing. Which exit was missing?

max_rounds, the exit you own (10 by default). The <response> tag only fires when the model decides it is done, and a model that keeps asking for tools never decides that. Without max_rounds the loop runs and bills forever.

Tool schema

Lesson 23.3: Defining tools and binding them to a model. Notebooks: 03a_defining_tools.ipynb

A tool never reaches the model as Python. When you bind tools to a model, LangChain turns each one into a JSON schema with three parts, and that schema is all the model reads when it decides whether to call the tool and with what arguments.

Part Comes from What the model uses it for
name The function name, or name= The call it writes; your code dispatches on it (tool_mapping[name] in lesson 23.4)
description The docstring, or description= Deciding when to call the tool, out of all the tools it holds
parameters Type hints, or a Pydantic args_schema Deciding what to pass: each argument’s type, its description, and which are required

The function body is the one part the model never sees. A vague description produces wrong or missing calls however good the code behind it is.

Typed arguments or none. The notebook’s first multiply has no type hints. Its arguments come out as {'a': {'title': 'A'}, 'b': {'title': 'B'}}, with no type at all, and multiply.invoke({'a': 2, 'b': 'abc'}) returns abcabc, because Python multiplies a string by an integer without complaint. The Pydantic version (StructuredTool.from_function with an args_schema) declares both as number with a description each, and the same call fails with a ValidationError before the function runs.

Here is Larkspur’s search_handbook at the same three levels, as convert_to_openai_tool prints them with langchain-core 1.7:

Definition parameters the model receives
@tool on def search_handbook(query) {"properties": {"query": {}}, "required": ["query"], "type": "object"}
@tool on def search_handbook(query: str) -> str {"properties": {"query": {"type": "string"}}, "required": ["query"], "type": "object"}
StructuredTool with a Pydantic Field(description=…) the typed version plus "description": "Words to look up in the handbook, for example 'refund window'" on query

The full schema of the last one:

{
  "type": "function",
  "function": {
    "name": "search_handbook",
    "description": "Search the Larkspur Cloud handbook and return the two best-matching chunks. Use it for policy questions: billing, refunds, exports, outages, server sizing.",
    "parameters": {
      "properties": {
        "query": {
          "description": "Words to look up in the handbook, for example 'refund window'",
          "type": "string"
        }
      },
      "required": ["query"],
      "type": "object"
    }
  }
}

The description says what the tool returns and which questions it is for, so the model can tell it apart from get_server_status. The argument description says what a good query looks like. Passing {"query": 3} to this tool fails Pydantic validation (Input should be a valid string); in an agent that error goes back to the model as a message (lesson 23.5).

Built-in and wrapped tools. LangChain’s built-in tools carry their own schema: WikipediaQueryRun is named wikipedia and takes one string, query. Wrapping one in Tool(name=…, func=…, description=…) gives it your name and description, and changes its argument to the generic tool_input, which is worth checking before you bind it. Whatever the source, print tool.name, tool.description and tool.args (or the convert_to_openai_tool output) before you trust a tool in a loop: that printout is exactly what the model will read.

The from-scratch signatures in lesson 23.1 wrote Python type names ("type": "int") into a prompt. The native schema uses JSON Schema types (string, number) and travels in the API request, so the provider can return structured calls against it.

Check yourself

1. The model never sees a tool's function body. Which three parts of the schema does it read, and what does each one decide?

name, description and parameters. The name is the call it writes and your code dispatches on; the description decides when to call the tool out of all the tools it holds; the parameters decide what to pass, with each argument’s type, description and whether it is required. A vague description gives wrong or missing calls however good the code is.

2. The untyped multiply tool gets 2 and the string abc. What comes back, and what does the Pydantic version do with the same call?

The untyped tool returns abcabc, because its schema has no types and Python multiplies a string by an integer without complaint. The StructuredTool with an args_schema declares both arguments as number, so the same call fails with a ValidationError before the function runs.

3. You wrap the built-in Wikipedia tool in Tool with your own name and description, and the agent starts passing odd arguments. What should you check before binding it?

The argument name. Wrapping changes the built-in’s query argument to the generic tool_input. Print tool.name, tool.description and tool.args, or the convert_to_openai_tool output, before you trust a tool in a loop, because that printout is exactly what the model reads.

Native tool calls and the message trace

Lesson 23.4: The manual tool loop and the augmented LLM in LangGraph. Notebooks: 04a_tool_calling_manual_loop.ipynb, 04b_augmented_llm_with_tools_langgraph.ipynb

llm.bind_tools(tools) returns a model that sends the tool schemas with every request. Its reply is an AIMessage with empty content and a tool_calls list. In 04a, How will the weather be in Munich today? comes back as one call:

[{'name': 'fake_weather_api', 'args': {'city': 'Munich'}, 'id': 'call_GRGobvpFuPRkrEUTERCcyNIw', 'type': 'tool_call'}]

Ask about the weather and outdoor seating together and the same reply holds two calls, one per tool, with finish_reason: 'tool_calls'. The model asks for both at once because neither depends on the other; there is no extra round trip.

The model still runs nothing. The loop from lesson 23.1 is now four steps over typed messages:

  1. Send the HumanMessage and append the model’s AIMessage with its tool_calls.
  2. For each call, look the tool up by name and invoke it with args.
  3. Append one ToolMessage(output, tool_call_id=call["id"]) per call.
  4. Call the model again with the whole list; it answers from the results.

The tool_call_id is what pairs a result with its request. With two parallel calls the model would otherwise have two unlabelled strings and no way to tell which tool produced which. OpenAI’s API also rejects a history in which an AIMessage’s tool call has no matching ToolMessage, so a loop that drops a failed call’s result breaks the next request.

The lab’s two-tool question shows the shape on Larkspur’s tools:

# Message Content
0 HumanMessage Is my server web-1 running, and does a reboot change its IP address?
1 AIMessage two calls: get_server_status(server_id='web-1'), search_handbook(query='reboot server IP address')
2 ToolMessage web-1: running
3 ToolMessage reboot (0.747): You can reboot a server from the console. A reboot takes about a minute and does not change the server IP address. and sizing (0.156): …
4 AIMessage the answer, no tool calls

Five messages, two of them tool results. The scores are real TF-IDF over the M11 chunks; the model turns are scripted.

For a model without native tool calling, 04a ends with the old route: render_text_description(tools) writes the signatures into the system prompt, and JsonOutputParser reads a {"name": …, "arguments": …} blob from the reply. It works on the notebook’s two questions, but nothing guarantees valid JSON, a real tool name or every argument. Use it only when the model leaves no choice.

The augmented LLM

04b hands step 2 to LangGraph. A tool_calling_llm node calls the bound model, the prebuilt tools_condition routes to a ToolNode when the reply has tool_calls and to END when it has none, and the ToolNode runs every requested call and writes the ToolMessages into state.

The solid edges are 04b’s graph. Explain AI in 2 bullets ends at the first END with a direct answer. What is the latest news on OpenAI product releases calls search_web, and the run ends on the raw Tavily JSON in a ToolMessage: nobody reads the result, the user gets no sentence, and a second, dependent call is impossible.

That graph is an augmented LLM. One more edge makes it an agent: tools back to the model instead of to END (the dashed line). Lesson 23.5’s create_tool_agent adds it with graph.add_edge("tools", "agent"), and the graph becomes the loop in the module’s mental model.

Check yourself

1. Why does every ToolMessage carry the id of the tool call it answers?

The tool_call_id pairs a result with its request. With two parallel calls the model would otherwise get two unlabelled strings and no way to tell which tool produced which. OpenAI’s API also rejects a history in which a tool call has no matching ToolMessage, so dropping a failed call’s result breaks the next request.

2. A customer asks if web-1 is running and if a reboot changes its IP. How many messages does the trace hold, and why are both tools requested at once?

Five: the HumanMessage, one AIMessage with two calls (get_server_status and search_handbook), two ToolMessages and the final AIMessage. Neither call depends on the other, so the model asks for both at once and saves a round trip.

3. The graph from the second notebook answers a news question with raw Tavily JSON and no sentence. What is missing, and which one change fixes it?

The tools node goes straight to END, so nobody reads the result and no dependent call is possible. That graph is an augmented LLM. Adding the edge from tools back to the model (graph.add_edge("tools", "agent") in lesson 23.5’s create_tool_agent) makes it an agent loop.

Where tool errors go

Lesson 23.5: Tool errors and evaluating tool calls. Notebooks: 05a_tool_loop_errors_and_evaluation.ipynb

05a closes the loop from lesson 23.4 with one edge, tools back to agent, and a router that ends the run when the last AIMessage has no tool calls. The message count tells you how the run went: What’s 25 * 17? ends with 4 messages (question, tool call, result, answer), and What’s 100 / 4 and what’s the weather in London? with 5, because the model asked for two tools in one reply.

Then the tools fail. What matters is where the failure goes. If it reaches the model as a ToolMessage, the model can explain it or retry with better arguments. If it escapes as an exception, graph.invoke raises and the user gets nothing. There are two ways to send it to the model:

  1. The tool returns the error. divide checks for zero and returns "Error: Division by zero"; the model reads it like any other result and explains that division by zero is undefined.
  2. The tool raises, and the ToolNode catches it. That depends on handle_tool_errors, whose default is narrower than it looks.
handle_tool_errors Bad arguments from the model Exception raised inside the tool
default Error ToolMessage (Please fix the error and try again.) Re-raised: the run crashes
True Error ToolMessage (Please fix your mistakes.) Error ToolMessage with the exception text
False Re-raised Re-raised

The interactive lab runs Larkspur’s four golden questions through this loop under each setting. Its tool results and error texts are byte for byte what LangGraph 1.2.18 produces for the same calls (12 runs, 0 mismatches); the model’s turns are scripted.

Question default True False
Can I export my data after I cancel my plan? Answered, 4 messages Answered, 4 Answered, 4
Is my server web-1 running, and does a reboot change its IP address? Answered, 5 Answered, 5 Answered, 5
Is my server web-9 up? (the tool raises ValueError) Crashed Answered, 4 Crashed
How long does a refund take? (the model passes q, not query) Answered, 6 Answered, 6 Crashed
Answered 3 of 4 4 of 4 2 of 4
  • The unknown server is an execution error. get_server_status raises ValueError("Unknown server 'web-9'; your servers: ['db-1', 'web-1']"). Only True catches it, and the model can then name the customer’s real servers, because the exception text lists them.
  • The wrong argument name is a validation error. The default and True both return it as a message, the model retries with query, and the run costs one extra round trip (6 messages instead of 4). False re-raises it as ToolInvocationError.
  • The two questions with no failure behave the same under every setting. That is why a test suite with only happy-path questions never shows the difference.

Write error messages the model can act on. Say what was wrong and what would work. handle_tool_errors also accepts a custom string, an exception type or a tuple of them (catch only those), or a function that formats the message. Return an error yourself when the tool knows the failure (an unknown id, an empty result), and keep handle_tool_errors=True as the net for the failures it does not expect.

Tool-call evaluation

A run can finish and still be wrong. For a tool-using agent, 05a scores three things separately, all read from the message trace:

Dimension Question How to score it
Tool selection Did it pick the right tool or tools? Compare called names with the golden set’s expected calls
Tool input Were the arguments well formed and relevant? Validate against the schema, compare key values with the expected ones
Synthesis Did the answer use what the tools returned, and nothing else? An LLM judge or a reference answer

The first two often need no model at all. Give each golden question its expected calls (Is my server web-1 running, and does a reboot change its IP address? expects get_server_status and search_handbook) and check the trace: the lab’s trace column does exactly this, and marks the refund question’s first call Right tool, missing query. A selection score that drops after a description change points at the description; an input score that drops points at the schema.

Synthesis needs judgement. The notebook’s judge reads the trace of Calculate 15% of 250 and check weather in Paris and returns structured scores through with_structured_output(ToolUseEvaluation): 5, 5 and 5, with a justification. Two cautions come with it:

  • The judge is the agent’s own model (gpt-4o-mini judging gpt-4o-mini), which tends to be lenient on its own work. Use a different, ideally stronger, model, and check its scores against a few human-graded runs before you trust a trend.
  • A single trace scored 5 out of 5 proves little. The scores mean something across a fixed golden set, compared before and after one change, as with the baseline in M11.

Add trace-level counts to the per-call scores: rounds per run, error ToolMessages per tool, and crashed runs. They are cheap to log and catch the failures the lab shows, where the answer never arrives.

Check yourself

1. Why does it matter whether a tool failure reaches the model as a message or escapes as an exception?

As an error ToolMessage, the model can explain the failure or retry with better arguments. As an exception, graph.invoke raises and the user gets nothing. You send it to the model either by returning the error from the tool or by letting the ToolNode catch it.

2. A customer asks whether web-9 is up, and the server-status tool raises ValueError. Under which error-handling setting does the run still answer, and how does the model help?

Only handle_tool_errors=True. The default re-raises exceptions raised inside the tool, and False re-raises everything, so both crash. With True the exception text reaches the model, and because it lists the customer’s servers (db-1 and web-1), the model can name them.

3. After a description edit, the tool selection score drops while the input score holds. Where do you look, and why is no model needed to score it?

Look at the description: a selection drop points at the description, an input drop at the schema. Both scores come from the message trace, by comparing the called names and arguments with each golden question’s expected calls. Only synthesis needs an LLM judge.

Hosted vs client-side tools

Lesson 23.6: Hosted vs client-side tools: code execution and image generation. Notebooks: 06a_hosted_vs_client_side_tools.ipynb, 06b_hosted_code_execution.ipynb (optional), 06c_agentic_image_generation.ipynb (optional)

Every tool so far ran on your machine: the model returned a call, your code ran it, you sent the result back. A hosted tool runs on the provider’s infrastructure instead, and the reply arrives with the result already folded in. The API difference is a few lines; the difference in what you can see and control is large.

06a answers What is the current population of Lisbon? both ways with gpt-4o-mini:

In the notebook’s run the client-side path took two round trips and 1.86 s; the hosted path took one round trip and 3.16 s. One run proves little about latency, but it does show that one round trip is not automatically faster. The hosted reply carries a web_search_call output item with its status and the query the provider chose (current population of Lisbon 2023). That item is your only window into the execution: you did not choose the query, you cannot see the raw results, and nothing of yours ran between retrieval and generation.

Client-side Hosted
Who executes Your process The provider’s infrastructure
See the arguments Yes, before execution Sometimes, after the fact
Intercept or refuse a call Yes, it is your code No
Deterministic tests Yes, stub the function No, it hits the live world
Failure Your exception, your retry A status across an API boundary; you can only re-run the whole request
Cost Tokens and your infrastructure Tokens and a fee per tool call (code interpreter: per container session)

The seam. The gap between “the model asked” and “the model sees the result” is where policy lives. 06a’s guarded_lookup is four lines that refuse any city outside an allow-list; asked about Pyongyang, it returns an error and the model says it cannot retrieve that population. Allow-lists, tenant scoping, PII redaction and spend caps all sit in that seam, and choosing a hosted tool means choosing not to have it.

Visibility varies by tool. The optional notebooks refine the rule that a hosted tool shows you nothing:

Hosted tool What comes back besides the answer
web_search The query, roughly; no raw results
code_interpreter (06b) The source it ran, its output and any files, so you can audit the method
image_generation (06c) The revised_prompt the model wrote for itself and the image as base64

Code interpreter is also configurable: 06b sets a memory ceiling and a network policy ({"type": "disabled"} for a sandbox that works only on data you supplied). What you still cannot do is approve the code before it runs, veto one call, or stub it in a test. 06c adds a different caution: the agent narrates what it meant to draw, and only feeding the image back to a vision model shows what it actually drew. The model also has to leave the tool alone when a turn asks for advice; 06c checks that it does.

For Larkspur’s support agent the split follows the data:

  • search_handbook and get_server_status stay client-side. They read the customer’s account and Larkspur’s own policy, need tenant scoping and logging, and must be stubbed in tests (the M23 lab runs them deterministically for this reason).
  • A hosted web_search fits questions the handbook cannot answer, about public software or third-party services, where there is nothing to enforce between the call and the result.
  • Hosted code execution fits arithmetic on numbers the customer pasted into the chat. 06b’s point holds: a model that runs three lines of Python computes, while one that answers directly samples plausible digits.

Hosted tools exist only on OpenAI’s Responses API; Chat Completions offers function tools only. 06a calls client.responses.create on the raw OpenAI client, because LangChain does not surface hosted-tool configuration. A third placement, a tool on a server you run that the model reaches over a protocol, is MCP (M38 to M40), and it gives back much of the seam that hosted tools remove.

Check yourself

1. What do you give up when you move a tool from client-side to hosted?

The seam between the model asking and the model seeing the result, which is where policy lives: allow-lists, tenant scoping, PII redaction and spend caps. You also lose the chance to see arguments before execution, refuse a call, or stub the tool in a deterministic test, and a failure can only be handled by re-running the whole request.

2. Larkspur's support agent needs the customer's server status and an answer about a third-party service. Which should run client-side, and which suits a hosted tool?

get_server_status stays client-side: it reads the customer’s account, needs tenant scoping and logging, and must be stubbed in tests. A hosted web_search fits the third-party question, which the handbook cannot answer and where there is nothing to enforce between the call and the result.

3. The hosted search took one round trip and 3.16 s, the client-side path two and 1.86 s. Is hosted the way to cut latency?

Not on this evidence. One round trip is not automatically faster: in that run the hosted path was the slower one. One run also proves little about latency, so measure on your own traffic. And going hosted removes the seam where your code could log, refuse or redact the call.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s support agent returns a 500 whenever a customer mistypes a server name (“Is web-9 up?”). The logs show ValueError: Unknown server 'web-9'. The tool works for valid names. What is wrong, and what do you change?

What a strong answer covers:

  • The exception escapes the ToolNode: its default catches invalid arguments but re-raises exceptions from inside the tool, so graph.invoke fails and the model never sees the error
  • Two fixes: set handle_tool_errors=True, or have the tool catch the failure and return a descriptive string; either way the model receives a ToolMessage with status error
  • Makes the error text useful to the model: list the customer’s real servers, so the model can ask “did you mean web-1?” instead of apologising
  • Adds the typo to the test set and alerts on the share of ToolMessages with status error per tool, so a new failure mode shows up before customers report it

2. A product manager wants to drop search_handbook and give the agent the provider’s hosted web search, since “the handbook is public anyway”. What do you weigh before agreeing?

What a strong answer covers:

  • Execution location decides control: with a client-side tool you see the arguments before execution, can refuse or redact, and own the raw result; with hosted web search you see a status and the query after the fact
  • Accuracy and scope: the handbook index returns Larkspur’s own current policy with chunk ids to cite, while web search can return third-party pages or an old cached copy
  • Testing and cost: a client-side tool can be stubbed for deterministic tests; a hosted call hits the live web and bills per call on top of tokens
  • A reasonable split: client-side for anything that touches customer data or policy, hosted search only for questions the handbook cannot answer, and log which path answered

3. You change the description of get_server_status and swap in a new model in the same release. How do you know the agent still calls the right tool with the right arguments?

What a strong answer covers:

  • A golden set of questions with the expected tool calls, run before and after; change one thing at a time, so a regression points at its cause
  • Scores tool selection and tool input deterministically from the trace (names match, arguments validate against the schema), with no judge needed
  • Uses an LLM judge only for synthesis, from a different and ideally stronger model than the agent, checked against a few human-graded traces, because a model grading its own run tends to be lenient
  • Watches production too: per-tool call rates, the share of error results, and rounds per run, segmented by question type

4. A trace shows the agent calling search_handbook eight times with slightly different queries for “How long does a refund take?” before it gives up. What is going on, and how do you stop it?

What a strong answer covers:

  • Checks the tool results first: TF-IDF matches exact tokens, so “refund” never meets “Refunds” in the refund-timing chunk; the tool returned the wrong chunk or nothing, and the model kept rephrasing
  • Fixes the retriever (embeddings or query rewriting, M14 and M18) rather than the loop, and makes the empty result say so plainly, so the model can stop
  • Caps the loop anyway: max_rounds in the from-scratch agent, recursion_limit in LangGraph, with a fallback answer when the cap is hit
  • Detects repeated near-identical calls in the trace as a monitoring signal, since they cost a model call each round

5. The model sometimes calls get_server_status with “my database server” instead of an id like db-1. The schema says server_id: string. How do you make wrong arguments rarer, and what catches the ones that remain?

What a strong answer covers:

  • The schema is the only thing the model reads: add a Field description with the id format and an example, and say in the tool description when to use it
  • Constrains the type where the values are known, for example an enum of the customer’s server ids, so a free-text value fails validation
  • Validation errors go back as messages (the ToolNode default does this), so the model can retry with a valid id
  • Measures the tool-input score on the golden set before and after the description change, and keeps the version that scores better

Key Takeaways

  • Write the loop’s exit conditions first: no tool calls means answer, and a round cap means stop with a fallback.
  • Treat the tool schema as the interface. Type every argument and describe it, because the model reads nothing else.
  • Every tool failure must come back as a ToolMessage the model can read. Set handle_tool_errors deliberately and test it with a tool that raises.
  • Run tools that touch customer data in your own process, where you can log, refuse and stub them. Hosted tools fit commodity capabilities with nothing to enforce.
