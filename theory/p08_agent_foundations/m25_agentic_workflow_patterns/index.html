M25 Agentic workflow patterns

A workflow is a graph you draw before the first token: the LLM fills in the nodes and, at most, picks one of the edges you wrote. Five such graphs cover most of what agentic RAG systems do: prompt chaining, routing, parallelization, orchestrator-worker and evaluator-optimizer. The M25 notebooks build on four ideas: the line between a workflow and an agent, checks between steps, running branches at once and merging them, and loops that always stop.

Open the lab

The running example is the Larkspur Cloud support assistant from M11 to M13, answering from the same handbook. Its golden question Can I export my data after I cancel my plan? needs two evidence chunks, export and retention, which makes it the natural case for orchestrator-worker decomposition. The notebooks run their own small demos (an email, a story, a joke, a code review), and every number on these pages is one they printed or one the lab computes.

TL;DR

  • In a workflow, code fixes the path through the LLM calls; in an agent (M24), the model picks its next step. Each M25 pattern hands the model one decision at most: a gate’s verdict, a route, a vote, a plan’s length or a grade.
  • A quality gate checks an intermediate result before the next step spends tokens on it. In lesson 25.1 a concrete topic passed on attempt 1 (four LLM calls); an abstract one was rejected three times and stopped before drafting (six calls, no email).
  • Routing by model tier sent 1 of 7 requests to o4-mini and scored 86%, against 71% for all-cheap and 100% for all-reasoning. The router’s costly mistake is sending a hard request to the cheap tier.
  • A fan-out lasts as long as its slowest branch: the 25.3 sections took 7.0 s in parallel against a 13.4 s sum. In the lab a cap of two concurrent branches costs nothing on that workload, until the slowest branch is submitted last.
  • Every loop gets a cap in code. LCEL cannot loop at all, so a generate, critique, refine cycle lives in LangGraph, a Python loop or agent middleware, and at MAX_ITERATIONS = 5 it makes at most ten LLM calls.

Mental model

Real systems nest these. CRAG (M29) is an evaluator-optimizer around retrieval, adaptive RAG (M30) is a router, and query decomposition (M18) is orchestrator-worker. Read an architecture by asking which of the five each node belongs to, and where the model, rather than your code, makes the call.

Workflow vs agent

Lesson 25.1: Prompt chaining with quality gates. Notebooks: 01a_prompt_chaining_langgraph.ipynb, 01b_prompt_chaining_structured_output.ipynb (optional), 01c_prompt_chaining_lcel.ipynb (optional)

Anthropic’s Building Effective Agents (December 2024), the source every M25 notebook cites, draws the line by who controls the next step. In a workflow, LLM calls and tools run along code paths you defined in advance. In an agent, the model directs its own process: it picks the next tool, reads the result and decides when to stop. The ReAct agent of M24 is an agent. All five M25 patterns are workflows.

Workflow (M25) Agent (M24)
Who picks the next step Your edges. The model at most chooses among edges you wrote The model, on every turn
LLM calls per request Known, or bounded by a cap in your code Known only when it stops; bounded by a step limit
Testing Each node and each router, like a function Whole trajectories, end to end
A failed run Ends at a node you named, with a reason Shows up in the trajectory: a repeated tool call, an early stop
Fits Tasks you can draw before they run Tasks whose steps depend on what the model finds

Each workflow pattern hands the model exactly one kind of decision, and keeps the rest in code:

Pattern Code fixes The model decides
Prompt chaining (25.1) the order of the steps each step’s content, and a gate’s verdict
Routing (25.2) the set of handlers which single handler runs
Parallelization (25.3) the branches and the merge each branch’s content, each vote
Orchestrator-worker (25.4) the worker’s job and the merge how many workers run, and what each one gets
Evaluator-optimizer (25.5) the criteria and the iteration cap the grade, and so whether to go round again

The lesson 25.1 graph shows how little the model controls. get_graph() prints five nodes and eight edges; three edges are conditional, and all three leave the gate. Everything else is a fixed add_edge. A Larkspur refund reply has the same shape: pull the plan and the purchase date out of the ticket, check them, draft, polish. A question nobody drew a path for, such as investigating why one customer’s servers keep rebooting, is where an agent earns its extra calls.

Quality gates

Prompt chaining splits one task into a fixed sequence of focused calls, each reading the previous step’s output. The 25.1 chain turns a topic into an email: extract three key points, draft, polish. A quality gate sits between steps and decides whether the intermediate result may go on. Failing at step 1 costs one cheap check; failing at the end costs a draft and a polish written from nothing.

The notebook’s gate has three parts, and each choice is deliberate:

  • The check. A keyword rule (“does it mention request, deadline, support?”) leaks: philosophical key points mention “support” too. The gate is a gpt-4o-mini judge at temperature 0 returning a structured GateVerdict with actionable: bool and a one-sentence reason.
  • The split. A node, check_key_points, runs the judge and writes gate_passed to state. A pure function, route_after_check, reads it and returns write_draft, regenerate or fail. The router makes no LLM call, so it can be tested like any function.
  • The bound. retry_count is Annotated[int, operator.add], so each extraction adds 1. At MAX_VALIDATION_RETRIES = 3 the router takes the fail edge to a terminal node that writes why the chain stopped. A recursion_limit of 12 is the second net, in case the router itself has a bug. Regeneration helps only because the extractor runs at temperature 0.7; at temperature 0 it would return the same key points three times.

The two runs in the notebook:

Topic Extraction attempts Gate verdicts Reached the draft LLM calls
Request for project deadline extension due to technical challenges 1 pass yes 4 (extract, judge, draft, polish)
The meaning of life and happiness 3 reject, reject, reject no, ended in fail_validation 6 (three extracts, three judges)

The second run spent three judge calls to avoid writing and polishing an email with no purpose, and it ended with a reason a caller can show or log.

The optional notebooks move the gate around. In LCEL (01c) the gate is a RunnableLambda that passes the payload through or raises KeyPointsRejected; .with_retry(stop_after_attempt=3) re-runs extraction and gate together, which plays the part of the regenerate edge, and .with_fallbacks(...) plays fail_validation. With structured output (01b) every step returns a validated Pydantic object, so a schema check runs at every hop for free. A schema guarantees fields and types, though, and says nothing about whether the content is usable; that still needs a gate like the judge here.

For Larkspur, the gate belongs right after extraction: does the ticket name a plan and a purchase date? Without them the refund-window chunk cannot be applied, and the right next step is to ask the customer, which a terminal node with a reason makes easy.

Key Takeaways

  • In a workflow your code fixes the path and the model makes one kind of decision; in an agent the model picks every step. Use a workflow for any task you can draw before it runs.
  • Gate early steps with an LLM judge that returns a structured verdict, since keyword rules leak. Keep the routing in a pure function so you can test it without an LLM call.
  • Bound retries with a counter and end at a terminal node that records why the chain stopped. A schema guarantees fields and types, not usable content, so structured output still needs a gate.

Check yourself

1. Why does the quality gate sit right after extraction instead of checking the finished email?

Failing at step 1 costs one cheap check, while failing at the end costs a draft and a polish written from nothing. The gate stops unusable key points before any later step spends calls on them, and the chain ends with a reason a caller can show or log.

2. The topic about the meaning of life is rejected by the gate three times. How many LLM calls does the run make, and where does it end?

Six: three extractions and three judge calls. At MAX_VALIDATION_RETRIES = 3 the router takes the fail edge to fail_validation, which writes why the chain stopped. No draft or polish call runs.

3. You set the extractor to temperature 0, and the gate rejects the same key points three times in a row. Why did regenerating not help?

Regeneration helps only because the extractor runs at temperature 0.7. At temperature 0 it returns the same key points on every attempt, so each retry gets the same rejection. Keep the extractor at 0.7 and the judge at 0, so the verdict is stable and the retry can differ.

Routing by handler

Lesson 25.2: Routing by handler and by model tier. Notebooks: 02a_routing_langgraph.ipynb, 02b_routing_by_model_tier.ipynb, 02c_routing_lcel_runnable_branch.ipynb (optional)

A router classifies the input once and sends it down exactly one specialist path. The model makes one small decision, a label from a fixed set, and everything after it is ordinary Python dispatch.

The 25.2 router has the same two-part shape as the 25.1 gate:

  • A constrained classifier. with_structured_output(ContentRoute), where content_type is Literal["story", "poem", "joke"]. The model cannot return a label the graph has no edge for, which a free-text answer like “I think they want a poem” could.
  • A pure condition function. determine_next_step maps the stored label to a node name with .get(..., "generate_story"), so even an unexpected label lands somewhere.

The notebook tests it with phrasing that implies the category without naming it: Tell me something funny about artificial intelligence, I want to hear a tale about a brave knight, Create something poetic about the ocean. All three reached the expected handler. Each request cost two LLM calls, one to classify and one in the handler, however many handlers exist; a fourth category is one more Literal value, one node and one edge. The LCEL version (02c) builds the same router with RunnableBranch and confirms that exactly one specialist chain runs per request.

For Larkspur, the closed set is the ticket queue: billing, technical, sales. The test that matters is the one the notebook models: check the routing decision itself, not only whether the final answer reads well.

Routing by model tier

The second notebook routes on a different axis. The conditional edge picks a model, not a handler: a cheap model triages each request as easy or hard, easy work stays on the cheap model and hard work goes to a reasoning model. You pay reasoning prices only on the traffic that needs them.

Both answering nodes send the same prompt; only the model differs, so a measured difference belongs to the model. Two details bite on the first real call: o-series models reject a custom temperature, so the reasoning tier passes temperature=1, and reasoning_effort="high" only means something to a reasoning model.

The workload is mixed the way real traffic is, mostly easy: seven requests, four easy (extract an order id, a capital, a time conversion, reply “ok”) and three hard (a deploy-schedule puzzle, an LRU eviction, a backoff sum). A router means nothing without “cheaper than what”, so the notebook runs all three strategies:

Strategy Accuracy Answering time, total Reasoning calls
All cheap 71% 5.2 s 0 of 7
Routed 86% 13.4 s 1 of 7
All reasoning 100% 20.1 s 7 of 7

The time column counts the answering calls only; the routed row also pays one triage call per request on top. With seven requests one question moves accuracy by 14 points, so read the table for its shape: routed accuracy should track all-reasoning while its reasoning-call count tracks all-cheap. A router that sends everything to hard is worse than no router, because it adds triage to the full reasoning bill.

The router predicts difficulty; it does not observe it. So it has a confusion matrix:

Sent to reasoning Sent to cheap
Truly hard 1 2, one answered wrong (the LRU question)
Truly easy 0 4

The two errors are not symmetric. Easy sent to reasoning wastes money: bounded, and visible on a bill. Hard sent to cheap returns a confident wrong answer: invisible until someone acts on it. So bias the triage prompt toward hard on borderline cases and accept the overspend as insurance. The same asymmetry fixes the fallback direction. “Try cheap, detect a bad answer, retry on reasoning” needs a reliable wrong-answer detector, and if you had one you would not need the router. Escalate on uncertainty before answering.

On Larkspur, Can I get a refund after 45 days? is the case to watch: it looks like a lookup and needs proration arithmetic. Put questions like it in the labelled set the router is measured on.

Key Takeaways

  • A router makes one small decision, a label from a fixed set, and dispatches in plain code. Each request costs two calls however many handlers exist, so test the routing decision itself.
  • Routing by model tier pays reasoning prices only on hard traffic. In the notebook the routed strategy reached 86% accuracy with 1 of 7 reasoning calls, against 71% all cheap and 100% all reasoning.
  • Hard work sent to the cheap tier returns confident wrong answers, while easy work sent up only costs money. Lean the triage prompt toward hard on borderline cases and accept the overspend.

Fan-out / fan-in

Lesson 25.3: Parallelization: sectioning and voting. Notebooks: 03a_parallelization_langgraph.ipynb, 03b_parallelization_sectioning_and_voting.ipynb, 03c_parallelization_lcel.ipynb (optional)

Chaining runs steps one after another and routing runs one of several. Parallelization runs all of a fixed set of branches at once. In LangGraph the graph says it with edges alone:

  • Fan-out: several edges leave one node. Their targets run in the same step, concurrently.
  • Fan-in: several edges enter one node. It waits until every one of them has finished.
  • Uneven branches: when one path is longer (A to B to X, beside A to C), add_edge(["x", "c"], "d") is the explicit sync point.
  • Shared keys need a reducer. Two branches writing the same state key at once lose a write unless the key has one, such as Annotated[list, operator.add]. Branches that each own a key (character_profiles, story_setting, plot_premise) need none.

Wall time follows the longest path, not the sum. The notebooks measure it with nodes that sleep 0.5 s each, then with real LLM calls:

Graph Wall time Why
A, B, C, D in a line 2.01 s four steps, one after another
A, then B and C in parallel, then D 1.51 s B and C overlap: three steps’ worth
A, then B to X beside C, then D 2.02 s paced by the longer path A, B, X, D
Three story sections, then synthesis 10.6 s sections finish at 1.6, 4.7 and 7.0 s; a sequence would take about 13.4 s

The synthesis step cannot overlap anything: it needs every section. That is the general shape of a fan-out’s cost: the step before, plus the slowest branch, plus the merge.

Production adds a limit the toy graphs do not have: the API behind the branches is rate-limited, so you cap how many run at once. In LCEL the cap is config={"max_concurrency": n} on the call, and the 03c notebook measures it: six 0.5 s branches took 0.51 s unbounded and 1.51 s at two at a time, three rounds of two. The interactive lab schedules the notebooks’ measured durations the way the thread pool does, branches submitted in order and each starting on the first free slot. On the story sections:

Concurrency cap Submitted Merge starts Wall time
3 (all at once) as written 7.0 s 10.6 s
2 as written 7.0 s 10.6 s
2 fastest first 8.6 s 12.2 s
1 any order 13.3 s 16.9 s

A cap of 2 is free here: setting (7.0 s) gets a slot at once, and premise runs after characters in the other slot, finishing at 6.3 s. Submit the fast branches first and setting waits 1.6 s for a slot, which the whole request pays. Under a cap, submit the slowest branch first. (The lab sums the printed one-decimal times, so its sequence shows 13.3 s where the notebook printed 13.4 s.)

For Larkspur, the natural fan-out is retrieval from independent sources for one question: the handbook index, the status page, the customer’s account. The answer arrives when the slowest source returns, so each branch needs a timeout and a fallback value, and each source should stay labelled in the merged context so the model can cite it.

Sectioning and voting

The same mechanics serve two different jobs:

Sectioning Voting
Branches do different parts of one task the same kind of task, independently
25.3 example characters, setting and premise of a story three security reviews of one function
State one key per branch, no reducer one shared votes list, reducer required
Fan-in an LLM call that weaves the parts together plain Python that counts and applies a threshold
Buys you latency confidence

The voting graph gives each reviewer one concern (injection, secrets handling, input validation), and no reviewer sees another’s vote. Each returns a structured Vote; the aggregator blocks the code when at least FLAG_THRESHOLD = 2 of 3 flag it:

Snippet Flags Verdict
SQL built with an f-string from user input, a hard-coded password printed to the log 3 of 3 BLOCK
Parameterised query, validated username, password read from the environment 0 of 3 APPROVE

The threshold trades false alarms against misses. Raising it to 3 blocks less often: fewer false alarms, more misses. Lowering it to 1 blocks on any single flag. On the unsafe snippet the validation reviewer flagged the SQL injection too, outside its own concern, so the votes are not fully independent; count on that when you set the threshold.

For Larkspur, voting fits a check before a reply goes out: does it promise a refund the policy does not allow, does it quote the right refund window, does it commit to a support response time. Three narrow reviewers and a threshold are easier to tune than one judge asked about everything.

Key Takeaways

  • A fan-out costs the step before, plus the slowest branch, plus the merge. Give any state key that parallel branches share a reducer, or one of the writes is lost.
  • Rate limits force a concurrency cap, and then submission order matters. A slow branch that waits for a free slot delays the whole request, so start it first.
  • Sectioning splits one task to cut latency; voting repeats one check to raise confidence. Set the vote threshold knowing it trades false alarms against misses and that reviewers are not fully independent.

Check yourself

1. Why does a fan-out's wall time follow its slowest branch rather than the sum of its branches?

The targets of a fan-out run in the same step, concurrently, and the fan-in node waits until all of them finish. So the cost is the step before, plus the slowest branch, plus the merge: the three story sections took 10.6 s, against about 13.4 s in sequence.

2. Under a concurrency cap of 2, the story sections take 1.6, 4.7 and 7.0 seconds. Should you submit the fastest or the slowest branch first?

The slowest first. Submitted as written, setting (7.0 s) gets a slot at once and the request still takes 10.6 s, the same as with no cap. Submitted fastest first, setting waits 1.6 s for a slot, the merge starts at 8.6 s and the request takes 12.2 s.

3. The security vote blocks code at 2 of 3 flags and raises too many false alarms. Which way do you move the threshold, and what does it cost?

Raise it to 3. The aggregator then blocks less often: fewer false alarms, but more misses. Allow for the votes not being fully independent, since the validation reviewer flagged the SQL injection outside its own concern.

Dynamic fan-out with Send

Lesson 25.4: Orchestrator-worker with the Send API. Notebooks: 04a_orchestrator_worker_send_api.ipynb, 04b_orchestrator_worker_lcel_map.ipynb (optional)

Orchestrator-worker looks like parallelization: several LLM calls run at once and a final step merges them. The difference is who decides the branches. In parallelization you wrote them into the graph; here an orchestrator LLM decides, per input, how many subtasks there are and what each one covers.

Parallelization (25.3) Orchestrator-worker (25.4)
Who decides the subtasks you, when you build the graph the orchestrator, at run time
Number of branches fixed follows the input
Branch identity known in advance (characters, setting, premise) generated (whatever sections this topic needs)
Graph shape static add_edge fan-out one conditional edge returning a list of Send

The same graph is often called map-reduce: the plan is the list, the Send fan-out is the map, and the synthesizer is the reduce.

The parts, as the notebook builds them:

  • A plan with a variable length. The orchestrator calls with_structured_output(ReportPlan), where sections is a list[Section], each with a name and a description.
  • Dispatch from the plan. A normal conditional edge returns one node name. assign_workers returns a list, one Send("llm_call", {"topic": ..., "section": section}) per planned section, and LangGraph starts that many runs of llm_call. The graph drawing shows the orchestrator to llm_call edge once, because the graph does not know the count until the orchestrator has run.
  • A narrow worker state. Each worker gets a WorkerState with the topic and its one section, and its prompt uses section.description. That is what makes the plan load-bearing.
  • A reducer for the results. completed_sections is Annotated[list, operator.add], because an unknown number of workers write to it at once. The notebook notes that the merged list follows the order the Sends were created, while stream_mode="updates" reports workers in the order they finish.

Two failure modes come from the notebook. The first is in the prompt: a planner told “simple topics might need 2 sections, broad topics 5+” answered with five sections, Introduction and Conclusion included, for every topic. Asking for one section per distinct question and banning padding sections let the plan size follow the input. The second is the anti-pattern of a plan nobody reads: the orchestrator runs, but five fixed workers wired with add_edge ignore its output. If the set of workers that ran is the same for every input while the plan changes, the plan does not drive execution. That graph is parallelization with a decorative LLM call in front.

LCEL can express the fan-out with .map() (04b), with four gaps against Send:

LangGraph Send LCEL .map()
Worker identity each Send names its own target node every item goes to the same runnable
Results land in shared state, merged by a reducer an ordered list matching the input
One worker fails the graph can route around it the whole batch raises, unless you use batch(..., return_exceptions=True)
Durability per-worker checkpoints, interrupts, resume none: the chain is stateless

This is the shape of query decomposition (M18) and of the module lab: the orchestrator splits a Larkspur question into sub-questions, each worker retrieves and answers one, and the synthesizer writes the reply. Can I export my data after I cancel my plan? splits into “how do I export?” and “what happens to my data after I cancel?”, whose evidence is the export and retention chunks of the M11 golden set. How long does a refund take? should get a plan of one item. Bound the plan in code as well as in the prompt: a maximum number of Sends, a direct path for one-item plans, and a decision about what an empty plan returns.

Key Takeaways

  • In orchestrator-worker an LLM decides at run time how many subtasks there are, and a conditional edge returns one Send per plan item. Merge the workers’ results with a reducer such as operator.add.
  • Make the plan drive execution by giving each worker only its own section and using that section’s description in its prompt. Fixed workers that ignore the plan waste the orchestrator call.
  • Planner prompts tend to pad. One that suggested 2 to 5+ sections returned five for every topic. Ask for one section per distinct question, and cap the number of Sends in code.

Check yourself

1. Both orchestrator-worker and parallelization run several LLM calls at once and merge them. What separates them?

Who decides the branches. In parallelization you wrote them into the graph with a static add_edge fan-out. In orchestrator-worker an LLM decides at run time how many subtasks there are and what each covers, and one conditional edge returns a list of Send, one per plan item.

2. How should the orchestrator plan the export-after-cancelling question and the refund-duration question?

The export question splits into “how do I export?” and “what happens to my data after I cancel?”, whose evidence is the export and retention chunks. The refund question should get a plan of one item. Bound the plan in code too: a maximum number of Sends, a direct path for one-item plans and a decision about what an empty plan returns.

3. The orchestrator's plan changes with every topic, yet the same five workers run every time. What is wrong?

The plan drives nothing: five fixed workers wired with add_edge ignore the orchestrator’s output, so the graph is parallelization with a decorative LLM call in front. Dispatch from the plan with one Send per section, and let each worker’s prompt use its section.description.

Bounded loops

Lesson 25.5: Evaluator-optimizer loops, always bounded: LangGraph vs LCEL. Notebooks: 05a_evaluator_optimizer_langgraph.ipynb, 05b_evaluator_optimizer_lcel.ipynb

Evaluator-optimizer generates a draft, grades it against explicit criteria and feeds the critique into the next draft, until the grade passes. The 25.1 gate checked once and stopped; this check feeds back into the generator. It pays off when two things hold: the criteria are clear, and feedback measurably improves the next attempt.

The evaluator is only as useful as its criteria. A first version of the notebook asked for one holistic grade against loose criteria such as “is it genuinely funny?”, and with gpt-4o-mini the loop almost never converged: the evaluator kept finding something that could be better. The working version changes three things:

  • One boolean per criterion. JokeReview asks four yes-or-no questions: a clear punchline, a punchline that depends on agentic AI specifically, no stock template, appropriate. A met criterion passes even if the joke could be better.
  • Code checks what code can check. Length is len(joke.split()) <= MAX_WORDS with MAX_WORDS = 40, not an LLM judgement.
  • The verdict is computed. approved only when every criterion and the length check pass. The model never asserts the grade itself, and improvement_feedback names a fix for each failed criterion.

The generator runs at temperature 0.7 so a revision can differ from the draft before it, and the evaluator at 0 so the same draft gets the same grade. Later passes receive the previous draft plus the feedback, so they revise instead of starting over.

A structured verdict does not guarantee the evaluator will ever approve. So the router checks a cap: approved ends the run, iteration >= MAX_ITERATIONS (5) ends it too, anything else loops back. The notebook proves the cap with a stub reviewer that rejects every draft; without the iteration_cap_reached branch that cell would never finish. The cap also bounds cost: each pass is one generator call and one evaluator call, so a run makes at most ten.

The bound can live in three places, one per implementation:

Implementation The loop is The bound is
LangGraph (05a) a conditional edge back to generate_content MAX_ITERATIONS checked in the router, with LangGraph’s recursion_limit as a backstop
LCEL plus Python (05b) a for loop around two chains range(1, MAX_ITERATIONS + 1)
create_agent middleware (05b) after_model returning jump_to="model" ModelCallLimitMiddleware(run_limit=5, exit_behavior="end")

A run that ends at the cap returns the last draft marked needs_improvement, so count it as a failure. Watch the share of runs that end there. It rises when the criteria drift, or when a new evaluator model is stricter than the old one.

For Larkspur, an answer-quality check is the natural evaluator, written as booleans: does the reply cite a handbook chunk, does it state the refund window the chunk states, does it avoid promising anything the handbook does not say, and is it under a length limit counted in code. CRAG (M29) applies the same loop to retrieval: grade the documents, rewrite the query, try again, within a bound.

Where LCEL stops

Every earlier pattern is a directed acyclic flow, so each maps onto an LCEL operator. This one has a cycle, and LCEL has no operator for “go back and try again until a predicate passes”. a | b | a does not loop: it builds a three-step chain that runs a twice. .with_retry() comes close but retries blind, with no memory of why the last attempt failed, and feeding the critique forward is the point of the pattern.

Pattern LangChain 1.x primitive Full coverage
Prompt chaining \| plus .with_retry() plus .with_fallbacks() yes
Routing RunnableBranch yes
Parallelization RunnableParallel yes
Orchestrator-worker .map() the fan-out; shared state and per-worker durability need Send
Evaluator-optimizer a Python loop, or after_model plus jump_to yes

Choosing between the two LangChain loops comes down to what you need around the loop. The Python for loop is easy to read and returns a dict you shaped, but traces each pass as separate chain runs and has no streaming, checkpointing or interrupts. The middleware loop is one agent run with every pass nested, keeps the full message history as its state, and inherits tools, streaming and persistence from the agent runtime. Two details matter there: can_jump_to=["model"] on the decorator is what creates the conditional edge, and the critique reaches the next draft as an appended HumanMessage. When the loop needs checkpoints, interrupts or a human in it, that is the point to move to LangGraph.

Key Takeaways

  • Evaluator-optimizer feeds a critique into the next draft until the grade passes. Use it only when the criteria are clear and feedback measurably improves the next attempt.
  • Grade with one boolean per criterion, check length in code and compute approved from the checks. A single holistic grade with gpt-4o-mini almost never converged.
  • Cap every loop and count a run that hits the cap as a failure. LCEL cannot express the cycle, so use a Python loop or middleware, and move to LangGraph when you need checkpoints or interrupts.

Check yourself

1. Why did replacing one holistic grade with one boolean per criterion make the joke loop converge?

Against a loose holistic grade the evaluator kept finding something that could be better. With four yes-or-no criteria, a met criterion passes even if the joke could improve, length is checked in code (MAX_WORDS = 40), and approved is computed only when every check passes, so the model never asserts the grade itself.

2. With a cap of 5 iterations, how many LLM calls can one run make at most, and how should you count a run that hits the cap?

Ten, because each pass makes one generator call and one evaluator call. A run that ends at the cap returns its last draft marked needs_improvement, so count it as a failure and watch the share of runs that end there.

3. A teammate builds the loop in LCEL by piping generator, evaluator and generator again, or by adding a retry. Why does neither work?

a | b | a builds a three-step chain that runs a twice; it never loops. .with_retry() retries blind, with no memory of why the last attempt failed, and feeding the critique forward is the point of the pattern. Use a Python for loop or after_model with jump_to, and move to LangGraph when the loop needs checkpoints or interrupts.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s reply drafter is an evaluator-optimizer loop. After an evaluator model upgrade, p95 latency triples and cost per ticket doubles, but no request fails. What happened, and what do you change?

What a strong answer covers:

  • Suspects the loop first: the new evaluator approves less often, so more tickets run to the iteration cap, and the cap returns a draft instead of an error
  • Confirms it from logs: drafts per ticket, the share of runs ending at iteration_cap_reached, and which criterion fails most
  • Fixes the criteria, not the cap: one boolean per criterion, counts and lengths checked in code, and a re-check of the new evaluator on drafts already graded by hand
  • Alerts on the cap-hit rate as its own metric, and marks capped answers so they are not sent as approved

2. Larkspur routes support questions by model tier. “Can I get a refund after 45 days?” needs proration arithmetic, and the triage step sends it to the cheap tier, which answers it wrong with confidence. Which way should the router err, and how do you prove the router pays for itself?

What a strong answer covers:

  • Names the asymmetry: over-escalation costs money and shows on a bill; under-escalation returns a wrong answer nobody sees until a customer acts on it
  • Biases triage toward hard on borderline cases and escalates before answering, since detecting a confident wrong answer afterwards is the hard problem
  • Measures routed accuracy and reasoning-call share against all-cheap and all-reasoning baselines on a labelled, honestly mixed set
  • Reads the router’s own confusion matrix, counting hard-sent-cheap separately, and remembers that triage is one more call on every request

3. The assistant fans out to the handbook index, the status page and the account API, then merges. p95 latency is 9 s and nobody knows which branch is slow. How do you find out, and what can you change?

What a strong answer covers:

  • Times each node as it finishes (stream_mode="updates" in LangGraph, or per-run traces), since the fan-in waits for the slowest branch and the mean hides it
  • Gives each branch a timeout and a fallback value, so one slow source degrades the answer instead of stalling it
  • Checks the concurrency cap against the API rate limits and submits the slowest branch first when a cap applies
  • Checks whether the merge step itself dominates: it needs every branch, so no fan-out can shorten it

4. You rebuild query decomposition as orchestrator-worker. For “How long does a refund take?” the planner returns five sub-questions, including “Introduction” and “Conclusion”. What went wrong, and what guards do you add?

What a strong answer covers:

  • Spots padding: a prompt with numeric anchors (“simple topics need 2, broad topics 5+”) produced five sections for every topic in lesson 25.4
  • Rewrites the planner prompt to ask for one item per distinct question and forbids padding sections
  • Bounds the plan in code: a maximum number of Sends, a direct path for single-part questions, and a defined result for an empty plan
  • Checks that workers consume their item, by confirming the set of workers that ran changes with the plan

5. A product manager wants to replace the fixed refund workflow with a ReAct agent “so it can handle anything”. When do you agree, and what do you keep?

What a strong answer covers:

  • Keeps a workflow where the steps are known: its calls are countable, each node and router can be unit-tested, and it stops at a known node with a reason
  • Uses an agent where the steps depend on what the model finds, such as a multi-step account investigation, and accepts trajectory-level evaluation and a step limit as the bound
  • Proposes a hybrid: a router that sends known intents to workflows and only the rest to the agent
  • Compares both on the same golden questions for accuracy, LLM calls, p95 latency and the share of runs that hit a limit

Key Takeaways

  • Draw the graph first. If you can, it is a workflow; give the model one decision per node at most, and keep that decision in a closed set your edges cover.
  • Put a gate where a bad intermediate result would waste the steps after it, and give every gate a retry count and a terminal “stop with a reason” node.
  • Measure a router against both of its baselines, and bias it toward the error that costs money rather than the one that costs correctness.
  • Every loop has a cap in code, and hitting the cap is a metric. A fan-out costs its slowest branch, so time branches one by one before tuning any of them.
