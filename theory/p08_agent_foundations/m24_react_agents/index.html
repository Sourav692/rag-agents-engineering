M24 ReAct agents and LangChain create_agent

A ReAct agent reasons about one step, acts with a tool, reads the result and decides again, until it can answer. LangChain 1.x packages that loop as create_agent and opens it to middleware, which is where call limits, redaction and human review go. The M24 notebooks build on four ideas: the reason, act and observe loop, the create_agent graph, structured output, and middleware.

The ReAct loop and its call cap
Open the lab

The running example is a support agent for the Larkspur Cloud handbook from M11 to M13. Its one tool, search_handbook, is the M11 lab’s TF-IDF retriever over twelve chunks, and its questions are the M11 golden set: Can I export my data after I cancel my plan?, How long does a refund take? and What happens if my server goes down? The interview questions add the tools a real support agent would have, such as an account lookup and a refund action.

TL;DR

  • ReAct interleaves reasoning and tool calls, and reads every observation before choosing the next step. The difference from a single-shot tool call is one edge, tools → model.
  • In the lab, the loop lifts mean evidence recall on the M11 golden set from 0.50 (one search, the M11 baseline) to 1.00 by rewording failed searches, for 9 model calls instead of 3. Every call rereads the whole message list, so cost grows each round.
  • create_agent(model, tools, system_prompt=...) returns that loop as a compiled LangGraph graph (model ⇄ tools) on native tool calls, so there is no text to parse.
  • response_format=Schema on an agent, or with_structured_output(Schema) on a model, returns typed data the next system can trust; Pydantic is the style that validates it.
  • Middleware hooks run before and after each model call: ModelCallLimitMiddleware bounds the loop, HumanInTheLoopMiddleware pauses irreversible tool calls for approve, edit or reject, PIIMiddleware redacts, SummarizationMiddleware compresses history.

Mental model

The model is the only part that decides; the graph executes and the middleware guards. A run is as long as the model’s decisions make it, so every production agent pairs the loop with a cap, and every irreversible tool with a checkpoint where a person can stop it.

Reason–act–observe

Lesson 24.1: The ReAct loop in LangGraph; tool calling vs ReAct. Notebooks: 01a_react_agent_langgraph.ipynb, 01b_tool_calling_vs_react.ipynb

A ReAct agent does not plan its steps up front. It reasons about the next step only, acts by calling a tool, observes the result, and reasons again with that result in front of it. The loop ends when the model replies without asking for a tool (Yao et al., ReAct: Synergizing Reasoning and Acting in Language Models, ICLR 2023).

In LangGraph the whole run lives in one state key, a message list with the add_messages reducer, so every model call sees everything that came before:

HumanMessage   the question
AIMessage      tool_calls=[search_handbook(...)]     reason + act
ToolMessage    what the tool returned                observe
AIMessage      another tool call, or the answer

The model never runs a tool. bind_tools() lets it return a request for a tool call; ToolNode executes the request and appends the ToolMessage. The difference between a one-shot augmented LLM and an agent is one edge:

With tools → END, the last message is the ToolMessage itself: the user gets search snippets, and no search can build on another. With tools → agent, tools_condition sends the run back to the model after every observation and ends it when the model stops calling tools. The notebook asks both graphs a question that needs a chain of searches (the company behind Dune, its CEO, its latest film, that film’s budget). The single-shot graph returned a ToolMessage; the loop wrote an answer from several searches, each naming something only an earlier result contained. The same loop costs nothing extra on a question that needs no tool: Explain AI in 2 bullets goes START → agent → END in one call.

The interactive lab runs this loop over the twelve Larkspur handbook chunks from the M11 lab. The tool, search_handbook, returns the top two chunks by real TF-IDF. The model is scripted: it writes the queries a model might write and answers once the evidence is in the message list. The retrieval, the loop and the counts are computed. On the three M11 golden questions:

Question Single shot ReAct ReAct, run_limit=3
Can I export my data after I cancel my plan? evidence 1.00, raw tool output 1.00, 2 calls, answered answered
How long does a refund take? 0.50, raw tool output 1.00, 3 calls, answered answered
What happens if my server goes down? 0.00, raw tool output 1.00, 4 calls, answered stopped at the cap, evidence 1.00
Mean, total 0.50, 3 calls, 0 of 3 answered 1.00, 9 calls, 3 of 3 answered 8 calls, 2 of 3 answered

What the numbers show:

  • Single shot equals the M11 baseline. One top-2 retrieval per question gives the same mean recall, 0.50, and the user receives chunks instead of an answer.
  • The loop recovers vocabulary mismatch by rewording. The refund question’s first search misses refund-timing (“Refunds” in the chunk, “refund” in the question); the second, written after reading the first result, finds it. The outage question needs three searches: the question’s own words and “server outage” both rank reboot and sizing first, and “what happens during an outage incident” returns incidents and sla.
  • Every call rereads the whole list. The outage run reads about 451 tokens of context over four calls, against 9 for the single search. Cost grows with every round, which is why a loop needs a cap (lesson 24.2).
  • A cap set too low cuts off the answer, not the search. At run_limit=3 the outage run already holds both evidence chunks when the middleware stops it; the call it blocks is the one that would have written the answer.

ReAct earns its extra calls on questions whose path depends on what the searches find. When you already know the fixed sequence of steps, a workflow is cheaper, more predictable and easier to test (lesson 24.5, M25).

Native tool calls vs text-based ReAct

The ReAct paper predates tool-calling APIs. It drove the loop with text: the prompt listed the tools and asked the model to write Thought:, Action: and Action Input: lines; the framework stopped generation at Observation:, parsed the action with a regular expression, ran the tool and pasted the result back. Native tool calling moves the same loop onto structured tool_calls returned by the provider.

Native tool calling Text-based ReAct
How the call travels Structured tool_calls from the provider API Free text, parsed with a regex
Needs a tool-calling model Yes No, any instruction-following model
Parallel calls in one turn Yes No, one Action per turn
Visible reasoning Optional Always, the Thought: lines
Typical failure Wrong tool or bad arguments Format drift, or arguments polluted by quotes and whitespace

The notebook runs both on the same two stub tools. With gpt-4o-mini, the text agent often wrote Action Input: 'Tokyo' with the quotes, the tool looked up the city 'Tokyo' and found nothing, and the calculator received '0.25 * 80' as a quoted string. The model knew which tool it wanted; the transport failed. Text-driven tools need input cleaning, and handle_parsing_errors=True turns a format break into an observation the model can react to.

On What’s the weather in Tokyo and calculate 25% of 80? the native agent asked for both tools in one turn and needed 2 model calls; the text agent, one Action per turn, needed 3. LangChain 1.x create_agent uses native tool calls, so there is nothing to parse. The ReAct idea, read every observation before choosing the next step, is unchanged.

Key Takeaways

  • A ReAct agent reasons about one step, calls a tool, reads the result and repeats until it replies without a tool call. The tools → agent edge is what turns a single-shot graph into that loop.
  • Rewording after each observation recovers vocabulary mismatch, but every call rereads the whole message list. In the lab the outage run read about 451 tokens over four calls, against 9 for one search.
  • Prefer native tool calls to text-based ReAct. They need no regex parsing, allow parallel calls in one turn and avoid format drift such as quoted arguments. Use a fixed workflow when the steps are known.

Check yourself

1. Why does adding one edge from the tools node back to the agent turn a single-shot graph into a ReAct agent?

With tools → END the last message is the ToolMessage, so the user gets search snippets and no search can build on another. With tools → agent, tools_condition sends the run back to the model after every observation, so each search can use what earlier results named. The run ends when the model replies without a tool call.

2. In the lab, the first search for the refund question misses the refund-timing chunk. What does the loop do next, and how many calls does the run need?

The model reads the first result and rewords its query, and the second search finds refund-timing (the chunk says “Refunds”, the question says “refund”). The ReAct run takes 3 calls and reaches evidence 1.00, against 0.50 for the single shot.

3. A text-based ReAct agent picks the weather tool for Tokyo but the tool finds no such city. What failed, and how do you fix it?

The transport failed, not the choice: the model wrote Action Input: 'Tokyo' with the quotes, so the tool looked up 'Tokyo'. Text-driven tools need input cleaning, and handle_parsing_errors=True turns a format break into an observation. Native tool calling, as in create_agent, removes the parsing step.

create_agent

Lesson 24.2: ReAct with LangChain create_agent. Notebooks: 02a_react_with_create_agent.ipynb

create_agent(model, tools, system_prompt=...) from langchain.agents builds the loop of lesson 24.1 for you and returns a compiled LangGraph graph (CompiledStateGraph). The notebook prints its structure:

nodes: __start__, model, tools, __end__
__start__ -> model
model -> tools      (conditional: the model asked for a tool)
tools -> model      (the ReAct feedback loop)
model -> __end__    (conditional: no tool call)

Because it is a graph, everything from M09 and M10 applies: .stream(..., stream_mode="values") replaces 0.x’s verbose=True, and a checkpointer plus a thread_id gives memory. Input and output are message lists: invoke({"messages": [...]}) returns the whole trail, and result["messages"][-1] is the answer.

The model decides how much to do per turn:

  • Dependent calls take one turn each. Get Google’s price, then email it to an analyst needs get_stock_price, an observation, then send_email, because the email body needs the price.
  • Independent calls share a turn. Weather in Bangalore and Mumbai, and 25 * 4 came back as three tool calls in one AIMessage; the tools node ran all three before the model’s second and last call.

What changed from LangChain 0.x, from the notebook’s migration table:

LangChain 0.x LangChain 1.x
initialize_agent(...), create_tool_calling_agent + AgentExecutor, or LangGraph’s create_react_agent(prompt=...) create_agent(llm, tools, system_prompt=...)
max_iterations=3 ModelCallLimitMiddleware(run_limit=3)
verbose=True .stream(..., stream_mode="values")
memory=ConversationBufferMemory(...) checkpointer= plus thread_id in the config
invoke({"input": ...}) returns {"output": ...} invoke({"messages": [...]}) returns {"messages": [...]}

Renaming only the function is not enough: the old prompt= argument raises TypeError on create_agent, which takes system_prompt=. create_react_agent in langgraph.prebuilt is deprecated since LangGraph v1.0.

Tools come in three weights. load_tools (now in langchain_community) gives ready-made ones such as llm-math; @tool turns a function into a tool; a BaseTool subclass carries configuration, such as which vector store to search. In every case the model chooses tools by their name and description, so the description is prompt text.

Call limits and runaway loops

A loop that decides its own length can run long. The notebook builds the failure on purpose: a restaurant FAQ indexed badly, with only the questions stored and the answers lost. Asked When does the restaurant open?, a plain agent searched once, saw four questions and no hours, and said it could not answer. An agent told to keep searching until it found the answer reworded its query again and again, getting the same answerless questions back each time, until ModelCallLimitMiddleware(run_limit=3, exit_behavior="end") ended the run and appended its notice. The cap bounded the bill; the user still had no opening hours.

The notebook ranks the fixes by how much they change what the model sees:

Fix Where
1. Fix the data: store each question with its answer ingestion
2. Retrieve more documents (search_kwargs={"k": 6}) the retriever
3. Format results clearly (“Restaurant Information:” headers) the tool’s return value
4. Say in the description what the tool returns the tool’s description
5. Raise the call cap create_agent(middleware=[...])

Fix 5 is the least effective: it buys more attempts at a retrieval problem. With fixes 1 to 4 the same question took one search and one answer, under the same cap.

ModelCallLimitMiddleware counts model calls per run (run_limit) and per thread across runs (thread_limit). It checks before each model call; at the limit, exit_behavior="end" jumps to the end with an AIMessage such as Model call limits exceeded: run limit (3/3), and "error" raises ModelCallLimitExceededError. In the M24.1 lab the golden questions need 2, 3 and 4 calls; at run_limit=2 only the export question is answered, even though the refund run already holds both evidence chunks. Set the cap from the call counts your golden set needs, with headroom, and alert when runs hit it.

Key Takeaways

  • create_agent builds the ReAct loop as a compiled LangGraph graph, so streaming, checkpointers and thread_id memory work as usual. Pass system_prompt=; the old prompt= argument raises TypeError.
  • ModelCallLimitMiddleware replaces max_iterations and checks before every model call. A cap set below what real questions need stops runs that already hold the evidence.
  • When an agent loops without an answer, fix what it retrieves first: the data, k, the result format and the tool description. Raising the call cap only buys more attempts at the same problem.

The fault is in retrieval: the index stored the questions without their answers, so every search returns answerless questions. A higher cap only buys more attempts at the same problem. Structured output

Lesson 24.3: Models, messages and structured output in LangChain 1.x. Notebooks: 03c_structured_output.ipynb, 03a_model_integration.ipynb (optional), 03b_messages.ipynb (optional)

An agent’s last message is prose. When the next consumer is code (a ticket queue, a database row, a judge’s score), ask for a schema instead. The schema goes to the provider, not into the prompt as an instruction: providers that support structured output constrain decoding to it, so the reply parses.

There are two places to attach a schema:

  • On a model. llm.with_structured_output(Movie) returns a new runnable; llm itself is unchanged. Its invoke() returns a Movie instead of an AIMessage. The judge in lesson 24.1 is built this way, so its scores are fields rather than sentences.
  • On an agent. create_agent(model=llm, response_format=ContactInfo) runs the agent as usual and adds structured_response to the result state, next to messages. It selects ProviderStrategy where the provider supports native structured output.

The three schema styles differ in what they check:

Style Returns Validation Optional field
Pydantic BaseModel an instance yes, raises on a wrong type budget: float \| None = Field(None, description=...)
TypedDict a plain dict none Annotated[float \| None, None, "description"]
@dataclass an instance none

Choose Pydantic when the data crosses a trust boundary: if a provider returns a string where you declared an int, Pydantic raises and TypedDict hands you the string. Two TypedDict traps from the notebook: = Field(...) inside a TypedDict is silently discarded, so the field stays required and its description never reaches the model; and NotRequired[...] is rejected by LangChain’s schema converter (TypeError: NotRequired accepts only a single type). Use the middle slot of Annotated for the default.

Three details matter in production:

  • Descriptions are prompt text. Field(description="The movie's rating out of 10") tells the model the scale; without it the model guesses one.
  • Optional fields stop invented values. A field the source may not contain (a budget, a refund amount on a question that has none) should be optional with a None default, so the model is not forced to write a number.
  • include_raw=True returns {"raw", "parsed", "parsing_error"}. You keep the AIMessage with its usage_metadata (119 input and 22 output tokens for the notebook’s four-field Movie), and a parse failure becomes a value you can branch on instead of an exception.

Not every model supports structured output. llm.profile (LangChain 1.1) reports capabilities from the open models.dev data; for gpt-4o-mini it lists structured_output: true, tool_calling: true and max_input_tokens: 128000. Branch on it rather than guessing.

The two optional notebooks cover the parts underneath. init_chat_model builds a model for any provider behind one interface, with streaming and batching. Messages are the unit of context: SystemMessage, HumanMessage, AIMessage and ToolMessage, and the list you pass is all the model sees. An AIMessage that asks for a tool usually has content="" and carries the call in .tool_calls, so print both when you debug a run.

Key Takeaways

  • Ask for a schema when code consumes the output. with_structured_output() makes a model return a schema instance, and response_format= adds structured_response to an agent’s result next to messages.
  • Use Pydantic when data crosses a trust boundary, because it validates types and TypedDict does not. Inside a TypedDict, = Field(...) is silently dropped.
  • Field descriptions are prompt text, and optional fields with a None default stop invented values. include_raw=True keeps token usage and turns a parse failure into a value you can branch on.

Check yourself

1. When should a structured-output schema be a Pydantic model rather than a TypedDict?

When the data crosses a trust boundary. Pydantic returns an instance and raises if the provider sends a string where you declared an int; a TypedDict returns a plain dict with no validation and hands you the string.

2. A ticket schema has a required refund amount, and the model writes a number even for questions that mention no refund. What change stops it?

Make the field optional with a None default, for example refund_amount: float | None = Field(None, description=...). A required field forces the model to write a value, while an optional one lets it leave a missing fact empty.

3. You add a field description inside a TypedDict with an equals Field call, yet the field stays required and the model never sees the description. What happened?

= Field(...) inside a TypedDict is silently discarded. NotRequired[...] will not help either, because LangChain’s schema converter rejects it. Put the default and description in Annotated[float | None, None, "description"], or switch to Pydantic.

Middleware

Lesson 24.4: Middleware, including human-in-the-loop. Notebooks: 04a_middleware.ipynb

Middleware attaches hooks at fixed points of the create_agent loop: before the model call, after it, and around a model or tool call. You use it for observability (logging, timing), transformation (rewriting the prompt, filtering tools), control flow (retries, early exit) and guardrails (call limits, PII redaction, human approval), without rebuilding the loop as raw LangGraph nodes.

Each hook compiles to a node in the agent’s graph. The notebook prints them:

SummarizationMiddleware              model, SummarizationMiddleware.before_model
HumanInTheLoopMiddleware             model, tools, HumanInTheLoopMiddleware.after_model
PIIMiddleware("email") + call limit  model, tools, PIIMiddleware[email].before_model, PIIMiddleware[email].after_model,
                                     ModelCallLimitMiddleware.before_model, ModelCallLimitMiddleware.after_model

The built-ins the notebooks use:

Middleware What it does Key arguments
SummarizationMiddleware Before the model call, replaces old history with a summary, keeps recent messages verbatim model (the summariser), trigger and keep in ("messages", n), ("tokens", n) or ("fraction", f)
HumanInTheLoopMiddleware After the model call, pauses before a gated tool call runs interrupt_on={tool: {"allowed_decisions": [...]}}, or False to let a tool run
PIIMiddleware Before and after the model call, redacts one PII type in inputs and tool results the type ("email", "credit_card", "ip", …), strategy="redact", apply_to_input, apply_to_tool_results
ModelCallLimitMiddleware Counts model calls after each call, checks them before the next, and ends the run at the cap run_limit, thread_limit, exit_behavior

With trigger=("messages", 10) and keep=("messages", 4), the notebook’s history grew 2, 4, 6, 8, 10 over five turns and dropped to 6 on the sixth, when the summary replaced the older turns. A message count is predictable but a poor proxy for context pressure; tokens track what runs out, and a fraction of the context window keeps its meaning when you change models. Summarisation and human approval both need a checkpointer, because they rewrite or suspend the run between calls.

Middleware runs in the order you list it. A custom one subclasses AgentMiddleware and overrides the hook it needs, with two rules that are easy to break. Every hook takes (self, state, runtime); leaving out runtime raises TypeError at run time. And a hook returns a state update instead of mutating state: to pass a value from before_model to after_model, declare it on a custom state_schema and return {"key": value}. To end a run early, follow ModelCallLimitMiddleware’s own before_model: it is decorated with @hook_config(can_jump_to=["end"]) and returns {"jump_to": "end", "messages": [AIMessage(...)]}. The M24 lab brief’s off-topic guard has the same shape.

Human-in-the-loop

HumanInTheLoopMiddleware turns an irreversible tool call into a decision. Gate the writes (sending email, issuing a refund) and let the reads run; pausing on reads is friction with no safety gain.

The pause is a real suspension: the state is checkpointed under the thread_id and nothing runs until you resume with one decision per gated call. The three decisions, as the notebook’s message trails show them:

  • Approve. The tool runs with the model’s arguments.
  • Edit. {"type": "edit", "edited_action": {"name": ..., "args": {...}}} replaces the arguments, and the tool runs with yours. The ToolMessage tells the model a reviewer replaced its call, so it does not re-issue the original.
  • Reject. The tool never runs. The model receives a ToolMessage saying the user rejected the call and not to retry unless asked, and it explains to the user that it could not send.

One pitfall breaks real deployments. When the middleware interrupts, the AIMessage with the tool call is already saved on the thread. Invoking that thread again with a new user message instead of Command(resume=...) leaves the call unanswered, and the provider rejects the next request: An assistant message with ‘tool_calls’ must be followed by tool messages responding to each ‘tool_call_id’ (OpenAI, error 400). Resume a parked thread, or start a new one.

Key Takeaways

  • Middleware hooks run before, after or around model and tool calls, in the order you list them. A custom hook takes (self, state, runtime) and returns a state update instead of mutating state.
  • Trigger summarisation on tokens or a fraction of the context window rather than a message count. Summarisation and human approval both need a checkpointer, because they rewrite or suspend the run.
  • Gate tools that write and let reads run. Resume a paused thread with Command(resume=...); a new user message on it leaves the tool call unanswered, and the provider rejects the next request.

Check yourself

1. Why should human approval gate tools that write, such as sending email, but not tools that only read?

The middleware turns an irreversible call into a decision, and only writes are irreversible. Pausing on reads adds friction with no safety gain. The pause is a real suspension checkpointed under the thread_id, so approval needs a checkpointer.

2. With summarisation triggered at 10 messages and keeping 4, history grows by two messages a turn. On which turn does it shrink, and to how many messages?

On the sixth turn. The notebook’s history grew 2, 4, 6, 8 and 10 over five turns and dropped to 6 on the sixth, when the summary replaced the older turns. A message count is predictable but a poor proxy for context pressure; tokens or a fraction of the window track what runs out.

3. An agent paused on a send_email approval is invoked again with a new user message, and OpenAI returns error 400. Why, and what should the app do?

The AIMessage with the tool call was saved on the thread when the middleware interrupted, and the new message leaves that call without a matching tool message, which the provider rejects. Resume the parked thread with Command(resume=...), one decision per gated call, or start a new thread.

Planned pipeline vs ReAct loop

Lesson 24.5: Applied ReAct: web research, SWE and computer-use agents. Notebooks: 05a_web_research_agent.ipynb, 05b_swe_agent_applied.ipynb (optional), 05c_browser_agent_computer_use.ipynb (optional), 05d_vision_driven_computer_use.ipynb (optional)

The most common “research agent” is not a loop. It plans every search up front and runs them in a straight line. The notebook builds both on the same topic, Artificial Intelligence in Healthcare:

The pipeline’s state carries more than messages: the topic, the planned questions, a {question: results} dict merged by a custom reducer, the report, and a log appended with operator.add. Each node returns only the keys it changes. The plan is fixed before any result comes back, and no edge goes back, so the pipeline cannot notice an empty search or follow a lead. The ReAct researcher is create_agent with one web_search tool, a prompt asking for one search per turn and 3 to 5 in all, and ModelCallLimitMiddleware as the bound.

One live run (search results change, so the counts vary between runs):

Planned pipeline ReAct agent
Web searches 3 4
LLM calls 2 5
Report characters 7,229 4,298

The pipeline’s three questions were written together and are broad and parallel. The agent started broad, then searched for things its results had named (AI models in surgery at Duke University, physician adoption statistics). The trade-off:

Planned pipeline ReAct agent
Who chooses the searches The plan, up front The model, after each observation
Cost Fixed and predictable Varies; bound it with a call cap
Reacts to empty or surprising results No Yes
Easy to test and debug Yes, same steps every run Harder, the path changes run to run
Good for Known-shape reports, batch jobs Open questions, multi-hop facts

Many production researchers combine them: plan first, then let each step react. M25 treats the pipeline side as workflow patterns.

The same loop in other environments

The optional notebooks keep the agent ⇄ tools graph and change only the tools and the environment.

  • SWE agent. The actions are file edits and the observation is a test run. Every file sits in a tempfile.mkdtemp() sandbox, paths are reduced to a filename inside it, and run_tests() runs one fixed pytest command, so the model cannot touch anything else whatever it writes. Tests are the reward signal; diff the changes and re-run the tests yourself instead of trusting the final message.
  • Browser agent. screenshot_text, click, type_text and navigate are ordinary tools over a deterministic mock browser. Actions now change state, so the turn cap becomes a safety bound, and success is graded on the environment (the cart’s contents), not the agent’s words.
  • Vision-driven computer use. When the observation is pixels, locating a control is the hard part. In the notebook’s runs gpt-4o-mini missed 53 of 53 clicks, even with every miss fed back; gpt-4o missed 15 of 26 and met the goal in 2 of 3 runs, at half the cost per screenshot. A miss raises no error, so the step cap is the only bound on the loop. Prefer selectors to coordinates.

Key Takeaways

  • A planned pipeline fixes its searches up front. Its cost is predictable and it is easy to test, but it cannot react to an empty result or follow a lead.
  • A ReAct researcher picks each search after reading the last result, so it suits open and multi-hop questions at a variable cost that needs a call cap. Many production researchers plan first, then let each step react.
  • Moving the loop to code, browsers or screens changes only the tools. Sandbox the actions, grade success on the environment rather than the agent’s words, and prefer selectors to coordinates.

Check yourself

1. Why can the planned research pipeline not follow a lead that one of its searches turns up?

Its questions are fixed before any result comes back, and no edge goes back to planning, so it cannot notice an empty search or add one. The ReAct researcher chooses each search after reading the last observation, which is how it went on to search for things its results had named.

2. You need a weekly report with the same sections on a fixed topic, at a predictable cost. Planned pipeline or ReAct agent?

The planned pipeline. It suits known-shape reports and batch jobs, its cost is fixed, and it runs the same steps every time, so it is easy to test. A ReAct agent suits open questions and multi-hop facts, and its cost varies and needs a call cap.

3. A vision-driven computer-use agent keeps clicking, never reaches its goal and raises no error. What is going on, and what stops it?

It cannot locate the controls from pixels: in the notebook gpt-4o-mini missed 53 of 53 clicks even with every miss fed back. A miss raises no error, so the step cap is the only bound on the loop. Prefer selectors to coordinates.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s support agent cost three times as much yesterday as the day before. Traces show some runs making a dozen search_handbook calls with reworded queries before giving up. What do you check, and what do you change?

What a strong answer covers:

  • Reads the ToolMessages in the long runs first: a loop that keeps rewording usually means the tool returns nothing useful, such as an index re-ingested without the answer text
  • Checks what changed that day (an index rebuild, a new document type, a prompt that says “never give up”) against the calls-per-run distribution
  • Fixes what the model sees (data, retrieval depth, result formatting, the tool description) before touching the cap; raising the cap only buys more attempts
  • Keeps a ModelCallLimitMiddleware with run_limit sized from the golden set’s call counts plus headroom, and alerts on the share of runs that hit it

2. Product wants a monthly account summary for every Larkspur customer: usage, invoices, open incidents. A teammate wants to reuse the ReAct support agent. What do you build instead, and why?

What a strong answer covers:

  • The steps are known in advance, so a planned pipeline (fetch usage, fetch invoices, fetch incidents, write) is cheaper, has a fixed cost per customer and runs the same way every time
  • ReAct pays off when the next step depends on what a result says; a batch report has no such step
  • Testing and debugging are easier when every run takes the same path; failures are recorded per step instead of steering the run
  • Keeps the agent for open support questions, and considers plan first, then react, if a summary section sometimes needs follow-up

3. You replace the M11 baseline retriever with a ReAct agent that uses it as a tool. How do you show the change is worth it?

What a strong answer covers:

  • Runs the frozen golden set through both and reports evidence recall and answer quality per question, not only the mean (in the lab, mean recall goes from 0.50 to 1.00)
  • Reports what the loop costs: model calls per question (the lab’s questions need 2, 3 and 4), tokens read, latency at p50 and p95
  • Grades answers with a judge that is not the agent’s own model, since live search results and sampling make single runs noisy
  • Checks the questions the baseline already answered for regressions, such as a loop that over-searches easy questions

4. Larkspur’s agent can call issue_refund behind HumanInTheLoopMiddleware. A support engineer, tired of waiting, pastes the customer’s message into the same conversation again, and the next model call fails with a 400 about tool_call_ids. What happened, and how do you prevent it?

What a strong answer covers:

  • The interrupt saved the AIMessage with the issue_refund call on the thread; the new user message left that call without a ToolMessage, which the provider rejects
  • The only valid next step on a parked thread is Command(resume={"decisions": [...]}), with one decision per gated call
  • The UI shows pending interrupts per thread_id and blocks new messages until a reviewer approves, edits or rejects
  • Uses edit to fix a wrong amount instead of rejecting, and keeps reads such as an account lookup ungated so approval stays rare

5. The ticketing system needs {category, priority, refund_amount} from every Larkspur conversation. Some days the agent returns prose; on questions with no refund it writes refund_amount: 0. How do you make the output reliable?

What a strong answer covers:

  • Passes a Pydantic schema as response_format on create_agent and reads structured_response, so the provider constrains the reply
  • Makes refund_amount optional with a None default, so the model is not forced to invent a number; 0 and “no refund” stay distinct
  • Writes field descriptions as instructions (units, allowed categories), because they reach the model as part of the schema
  • Logs parse failures with include_raw=True where the model is called directly, and checks llm.profile for structured-output support before switching models

Key Takeaways

  • Use ReAct when the next step depends on what a tool returns; use a planned pipeline when the steps are known.
  • Read the ToolMessages before you blame the model. A loop that keeps searching usually has a tool that returns the wrong thing.
  • Give every loop a call cap sized from your golden set, and gate every irreversible tool with human approval.
  • When code consumes the answer, ask for a schema, validate it with Pydantic, and make fields optional when the source may not contain them.
