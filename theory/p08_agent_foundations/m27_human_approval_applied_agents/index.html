M27 Human approval and applied single-agent builds

An agent that only reads can give a wrong answer. An agent that acts can publish, delete or charge something, and that cannot be taken back. M27 puts a gate in front of those actions, then builds complete single-agent applications, including one that retrieves from a SQL database instead of a vector index. The M27 notebooks build on four ideas: the dry run, the approval gate, text-to-SQL, and workflow apps that check every model output in code.

The approval gate
Open the lab

The running example is the Larkspur Cloud handbook from M11 to M13, seen from the operations side. An agent drafts posts for the Larkspur status feed after the eu-west outage, and a person approves each one before it goes out. The text-to-SQL lesson keeps the notebooks’ comic-store database, because its numbers come from that data; the interview questions move the same ideas to Larkspur’s billing data.

TL;DR

  • A dry run calls the action’s own code path with dry_run=True and returns a preview of the effect, so the reviewer judges what will happen instead of a description of it.
  • An approval gate pauses the graph with interrupt(), keeps the run in a checkpointer, and resumes it with Command(resume=decision). It fails closed: only the exact answer approve (after stripping and lowercasing) approves.
  • The approval covers a fingerprint, the first 12 hex digits of SHA-256 over the previewed post. In the lab, editing “72 hours” to “48 hours” after review changes the fingerprint from c4e9e330698e to 11673ae3c1d4, and the publish node refuses.
  • Text-to-SQL retrieves by computing over every row, which vectors cannot do for counts, sums and rankings. In the notebooks’ database, 16 of the 20 sales disagree with their own line items, so the top salesperson is John Doe by one definition of revenue and Alice Brown by the other. A business rule in the prompt has to decide.
  • A workflow app keeps the LLM to fixed steps with structured output, and does the routing, checking and final rendering in code. The workflow form of text-to-SQL costs 2 LLM calls per question; the ReAct agent costs several.

Mental model

The graph stops at Review and waits, for seconds or for hours, while the checkpointer holds its state. Two checks guard the live call. The first is the reviewer’s answer, and anything unclear counts as no. The second is a hash comparison at publish time, which catches any change between what the reviewer saw and what is about to run.

Dry run

Lesson 27.1: Dry-run harness and human approval. Notebooks: 01a_dry_run_harness.ipynb

A dry run executes an action’s plan without its effect and reports what the effect would be. The idea is old: rsync --dry-run, apt-get --simulate and terraform plan all print the changes before anyone applies them. For an agent it separates two moments that a plain tool call joins: the model proposing an action, and the system executing it.

The notebook’s tool is a mock social-media API. On the Larkspur status feed it works the same way: one method, publish_post(post, dry_run=True), and one code path that renders the post for both modes.

Call Returns Changes the feed
publish_post(post, dry_run=True) {"status": "DRY_RUN", "preview": text, "fingerprint": "c4e9e330698e"} No
publish_post(post, dry_run=False) {"status": "PUBLISHED", "post_id": "post_1"} Appends one post

The fingerprint is sha256(render(post))[:12] in hex, so it identifies the exact text that was previewed. The value above is the lab’s, for the eu-west post.

Three properties make a dry run worth trusting:

  • The preview comes from the live code path. Both modes call render(post), so the reviewer reads the text the platform will receive. A preview built by a separate “describe” function can drift from what the live call does.
  • “Nothing happened” is checked, not assumed. The notebook’s feed is a list it can inspect, and every claim is an assert api.feed == []. Give a real tool a sandbox, a staging target or a way to read state back, and test against it.
  • The dry run is its own graph node, before the pause. On resume LangGraph re-runs the paused node from the top, so anything placed before interrupt() in the review node runs twice. A preview generated there could differ from the one the reviewer approved.

The cost is that every consequential tool needs a dry-run mode. Sending email, issuing a refund and deleting a server each need their own preview: the rendered message, the amount and the account, the server name and what is on it.

Approval gates

The gate is the review node. It calls interrupt(payload) with the question, the preview and the fingerprint. LangGraph stops the run, saves its state in the checkpointer under the run’s thread_id, and returns the payload to the caller under "__interrupt__". Nothing more happens until someone invokes the graph again with Command(resume=decision) on the same thread.

run_with_review is that loop in code: invoke, and while the result holds an interrupt, pass the payload to a reviewer function and resume. The reviewer can be a script (the notebook’s scripted reviewer approves the launch post and rejects the post that disparages competitors), a policy check, a console input(), or a UI that answers hours later from another process. Only the reviewer function changes. A later answer needs a persistent checkpointer such as SQLite or Postgres in place of InMemorySaver.

Three rules make the gate safe:

  • Fail closed. normalize_decision strips and lowercases the answer and accepts only the exact word approve. ␣Approve␣ approves; approved, yes and sure, why not are rejections, logged as unclear answers.
  • Approve what was previewed. The approval stores the preview’s fingerprint. The publish node recomputes the fingerprint of the post it is about to send and refuses if the two differ.
  • Log every decision with the reviewer, the reason, the fingerprint and the time.

The interactive lab runs this harness in the page, with normalize_decision and the SHA-256 fingerprint ported from the notebook. Checked against the notebook’s own graph on 315 runs (3 drafts, 3 kinds of edit, 35 typed answers), it agrees on every final status, fingerprint and audit entry. With the eu-west post approved:

Change after the preview Fingerprint at publish Final status
None c4e9e330698e PUBLISHED as post_1
“72 hours” edited to “48 hours” 11673ae3c1d4 REFUSED: the post differs from the approved preview
” Buy now!!!” appended (the notebook’s test) 78879f196e7d REFUSED: the post differs from the approved preview

A one-phrase edit changes the fingerprint as completely as a new sentence, so any edit after review needs a new preview and a new decision. In the refused runs the audit log still shows an approve. That entry is correct: the reviewer approved c4e9e330698e, and the text that tried to publish was something else.

The gate enforces whatever the reviewer decides. Approve the uptime post in the lab and it reaches the feed. A gate protects only as much as its reviewers read, and the module page’s interview questions cover how to measure that.

HumanInTheLoopMiddleware (M24) gives a create_agent agent the same pause before a tool call, built on the same interrupt() and checkpointer (M10). Building the gate by hand adds the two parts this lesson needs: a preview of the effect and a fingerprint that ties the approval to it.

Key Takeaways

  • A dry run renders the effect through the same code path as the live call and changes nothing. Check that by reading state back, and put the dry run in its own node before the pause.
  • The gate pauses with interrupt(), saves state under the thread_id and waits for Command(resume=...). Accept only the exact word approve and log every decision with reviewer, reason, fingerprint and time.
  • Tie the approval to a fingerprint of the previewed text and recompute it before publishing. Any edit after review, even one phrase, needs a new preview and a new decision.

Check yourself

1. Why must the dry run be its own graph node before the review node, rather than code inside the review node?

On resume LangGraph re-runs the paused node from the top, so anything placed before interrupt() in the review node runs twice. A preview generated there could differ from the one the reviewer approved.

2. The eu-west post is approved, then 72 hours is edited to 48 hours before it publishes. What happens, and what does the audit log show?

The fingerprint at publish is 11673ae3c1d4, not the approved c4e9e330698e, so the publish node returns REFUSED: the post differs from the approved preview. The audit log still shows an approve, and that is correct: the reviewer approved c4e9e330698e. Any edit after review needs a new preview and a new decision.

3. A reviewer answers the approval prompt with yes. Does the post go out, and why is that the right behaviour?

No. The gate fails closed: normalize_decision strips and lowercases the answer and accepts only the exact word approve, so yes and approved are rejections, logged as unclear answers. An ambiguous answer should never publish.

Text-to-SQL

Lesson 27.4: Text-to-SQL: workflow vs ReAct agent. Notebooks: 04a_text2sql_workflow.ipynb, 04b_text2sql_react_agent.ipynb

Text-to-SQL turns a question into a query, runs it, and writes the answer from the rows. Both notebooks use a comic-store database built from comicdb_create_script.sql: eight tables (Branch, Publisher, Comic, Customer, Employee, Inventory, Sale, SaleTransactions) holding 50 comics, 20 customers, 20 sales and 40 sale lines.

The workflow is a fixed chain of three steps, built with RunnablePassthrough.assign so the question, the SQL, the rows and the answer stay together in one dictionary:

  1. Write the query. create_sql_query_chain fills the prompt’s {table_info} with db.get_table_info(): the CREATE TABLE statement and 3 sample rows for each table. That text is everything the model knows about the schema.
  2. Run the stored query. itemgetter("query") | QuerySQLDatabaseTool(db=db) executes the query from step 1. Piping the write chain into the executor a second time would generate a second query, and the SQL on screen would not be the SQL behind the answer.
  3. Answer from the rows, with a prompt that says to use only the SQL result.

The prompt has to make the model return bare SQL. A reply that starts with SQLQuery: or sits in a code fence fails with near "SQLQuery": syntax error, which the notebook lists as the most common failure.

Measure against SQL you wrote. The evaluation set pairs seven questions with reference SQL, and running that SQL gives the expected answer. A number must appear as a whole number in the answer; a name must be the first known name the answer mentions, so a list of six customers that includes the right one does not pass.

Question Expected (from the reference SQL)
How many customers do we have? 20
Which comic has sold the most copies? Wolverine: Old Man Logan
Which customer has purchased the most comics? Tony Stark
How many comics in the Superhero genre have never been sold? 9

The notebook names the typical miss: for “purchased the most comics” the generated SQL counts sale lines instead of summing Quantity. On this data that changes the answer. Natasha Romanoff has the most lines (5, for 6 copies); Tony Stark bought the most copies (8, on 4 lines). The query runs and the answer reads well, and only the ground-truth check shows it is wrong.

When the data disagrees. “Revenue” has two defensible sources: the header Sale.TotalAmount, or the line items SUM(Quantity * Price). Running the notebook’s check on its database, 16 of the 20 sales have a TotalAmount that differs from their lines by more than 0.01, and the top three salespeople change:

Rank By Sale.TotalAmount By line items
1 John Doe, 255.89 Alice Brown, 325.86
2 Alice Brown, 234.94 John Doe, 294.86
3 Jane Smith, 234.88 Michael Clark, 258.88

The chain picks one silently, and a stronger model would still be guessing. The business has to decide which source is authoritative and write it into the prompt (“Revenue is always computed from line items”). The notebook then checks the generated SQL in code: it must mention SaleTransactions.

Workflow or ReAct agent

The second notebook gives the same task to a create_agent ReAct agent with the four tools of SQLDatabaseToolkit: sql_db_list_tables, sql_db_schema, sql_db_query_checker (an LLM that reviews a query before it runs) and sql_db_query. Its system prompt tells it to list the tables first, read the schemas it needs, check each query, and rewrite and retry on errors.

Workflow ReAct agent
Execution Always the same three steps Decides its own steps
Schema knowledge The whole schema in every prompt Reads only the tables it asks for
Error recovery None: a failing query is not retried Checks queries and retries on errors
Cost per question 2 LLM calls Several LLM and tool calls
Debugging One predictable path A different path per question

Both are scored on the same seven questions. Neither is reliably right on every one. The checker and the schema reads fix wrong column names and syntax errors; they do not fix a wrong definition, such as counting lines instead of summing Quantity. Seven questions are a sample, and a second run can change verdicts, so compare question by question rather than by one score.

Read-only belongs in the connection. The workflow only ever runs the one query it wrote. An agent runs whatever SQL it decides on, so the second notebook opens the file with sqlite:///file:ComicStore.db?mode=ro&uri=true. A DELETE then fails at the database, whatever the prompt says. The notebook’s last test asks the agent to delete the customers in New York and compares the customer count before and after, instead of trusting the answer’s wording.

Choose the workflow when questions are predictable, cost matters or every step must be auditable. Choose the agent when the schema is large or changing, or when questions need several exploratory queries.

SQL or vectors

A vector retriever returns the k chunks most similar to the question, and the model reads only those (M11). That fits “What is the refund policy?”, where the answer is a passage. It fails for “How many comics in the Superhero genre have never been sold?”: the answer (9) depends on all 50 comics and all 40 sale lines, and no top-k slice of rows contains it. SQL computes over every row, then the model only phrases the result.

Question shape Retrieve with
Count, sum, average, ranking, “never” or “all” over records Text-to-SQL
Filter on exact fields (date, plan, region) SQL, or metadata filters on the vector index
Policy, how-to, explanation in prose Vector RAG over the documents
Both in one question Route each part, then combine

The module’s lab brief measures this split: the same 20 questions over a product catalogue, answered by CSV RAG from M20 and by the text-to-SQL agent, with the winner recorded per question type.

Key Takeaways

  • Score text-to-SQL against reference SQL you wrote. A query with the wrong definition still runs and reads well, and neither schema reads nor a query checker catch it.
  • When the data offers two sources for a figure such as revenue, the business must pick one and the prompt must state it. Then check the generated SQL in code for the authoritative table.
  • Use a workflow for predictable questions and an agent for large or changing schemas, opened read-only at the connection. Route counts, sums and rankings over all records to SQL, and prose questions to vector RAG.

Check yourself

1. The ReAct agent reads schemas and checks each query before it runs. Which errors do those steps fix, and which do they not?

They fix wrong column names and syntax errors. They do not fix a wrong definition, such as counting sale lines instead of summing Quantity. That is why both designs are scored question by question against reference SQL.

2. For the question of which customer has purchased the most comics, the generated SQL counts sale lines. What answer comes back, and what is correct?

Counting lines gives Natasha Romanoff (5 lines, for 6 copies). Summing Quantity gives Tony Stark (8 copies, on 4 lines), which matches the reference SQL. The query runs and the answer reads well, so only the ground-truth check shows it is wrong.

3. Why can a vector retriever not answer how many Superhero comics have never been sold, when text-to-SQL can?

The answer (9) depends on all 50 comics and all 40 sale lines, and a retriever returns only the k chunks most similar to the question, so no top-k slice contains it. SQL computes over every row, then the model only phrases the result. Vector RAG fits prose answers such as policies.

Workflow apps

Lesson 27.5: LLM workflow apps: review analyst, IT support desk, tailored writer, quiz generator. Notebooks: 05a_review_analyst.ipynb (optional), 05b_multilingual_it_support_desk.ipynb (optional), 05c_audience_tailored_writer.ipynb (optional), 05d_quiz_generator.ipynb (optional)

A workflow app runs a fixed sequence of LLM steps over business text: reviews, support tickets, a fact sheet, a PDF. There is no tool loop. The model fills typed fields, and code does everything that has a right answer: routing, checking and assembling the final document. The four notebooks are four versions of one shape.

  • Review analyst. The LLM returns one ReviewAnalysis per review, for six reviews with .batch(), then writes one email per review. Code picks the email writer by a dictionary lookup on sentiment: a thank-you for positive and neutral, an apology for negative. Code checks the sentiment against hand labels, and each email for “Dear Customer”, “Service Agent”, an apology only when the review is negative, and at most 140 words (the prompt asks for under 120).
  • IT support desk. Design A makes one structured call per ticket that returns six fields; Design B chains detect, translate, answer and translate back. Both run on the same ten tickets in nine languages, and code checks the detected language, that each reply differs from its English version, that no prompt scaffolding leaks into the text, and the LLM calls and wall time.
  • Audience-tailored writer. Three advert prompts, then three audience reports, each set run in parallel with RunnableParallel. Code checks the headings, a two-column table limited to five features, the 60-word limit, and that every number in the output appears in the source.
  • Quiz generator. The LLM summarises the PDF, then writes questions from the material and the summary. Code checks for 5 questions with 4 distinct options and a valid answer_index, checks that every evidence quote appears in the cleaned PDF text, and renders the study sheet from a template.

The notebooks repeat five rules:

  • Ask for a closed type. sentiment: Literal["positive", "negative", "neutral"] gives code a value it can branch on, and answer_index points at an option instead of restating it, so the answer cannot drift from the options.
  • Route in code when the signal is already structured. The review analyst picks the email writer with a dictionary, with no extra LLM call. When the input is free text, as in its instruction router, classify into a closed set of intents and keep an other intent for requests the tool does not handle.
  • Check every output with code that cannot be talked round. String and number checks are cheap enough to run on every call. The writer’s fact sheet gives RAM, screen sizes and battery rating but no camera megapixels, so a “50 MP” in an advert is flagged as invented.
  • Render the final document in code. Asking the model to merge a checked summary and checked questions into a report would let it reword them after the checks; a template cannot.
  • Measure the design choice. One structured call per ticket makes a quarter of the LLM calls of the four-step chain, and the chain’s free-text steps can leak a code fence or “The customer message in English is:” into the reply. The notebook measures both on the same tickets before choosing.

On the Larkspur handbook the same shape triages the support queue. One structured call per ticket returns the language, a category (refund, outage, sizing) and a draft reply. Code routes outage tickets to the incident template, checks that every number in a reply appears in the handbook (the 30-day refund window, the 99.95% availability target), and holds any reply that fails for a person. A reply that issues a refund is an action, so it goes through the approval gate from 27.1.

These apps are workflows in the sense of lesson 27.4: the same steps every time, cheap, easy to test. Choose an agent only when the next step depends on what the model finds.

Key Takeaways

  • In a workflow app the model fills typed fields and code does everything that has a right answer. Ask for closed types, such as a Literal sentiment, so code can branch on them without another LLM call.
  • Check every output with code that cannot be talked round, such as confirming each number appears in the source. Render the final document from a template so nothing is reworded after the checks.
  • Measure a design choice on the same inputs before picking it. Send actions such as issuing a refund through an approval gate, and choose an agent only when the next step depends on what the model finds.

Check yourself

1. Why do the workflow apps render the final document from a template instead of asking the model to merge the checked parts?

A model asked to merge a checked summary and checked questions could reword them after the checks ran. A template cannot, so what the user reads is exactly what passed the checks.

2. The writer's fact sheet gives RAM, screen sizes and a battery rating but no camera figure, and an advert claims 50 MP. What catches it?

The code check that every number in the output appears in the source flags “50 MP” as invented. String and number checks are cheap enough to run on every call. The Larkspur triage version runs the same check against the handbook’s numbers, such as the 30-day refund window.

3. For the multilingual support desk, should you use one structured call per ticket or the four-step translate chain?

The notebook measures both on the same tickets before choosing. One structured call makes a quarter of the LLM calls, and the chain’s free-text steps can leak a code fence or “The customer message in English is:” into the reply.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s status agent published “a root-cause report within 48 hours”. The reviewer approved a preview that said 72 hours, and the audit log shows the approve. How did this happen, and what do you change?

What a strong answer covers:

  • Compares the fingerprint in the audit log with the hash of the published text; if they differ, something changed the post between the dry run and the live call
  • Looks for code that runs again on resume: the review node restarts from the top, so a regeneration or an edit placed before interrupt() runs a second time
  • Binds the approval to the fingerprint and recomputes it in the publish node, so any later change refuses instead of publishing
  • Adds a regression test that edits the paused state with update_state and asserts the refusal, as the notebook does

2. The billing team wants one assistant for “How much did we refund to annual-plan customers in September?” and “What is the refund policy for annual plans?”. Vector RAG, text-to-SQL, or both?

What a strong answer covers:

  • The September total is an aggregate over rows: SQL computes it over every row, while top-k retrieval hands the model a few chunks and asks it to add them up
  • The policy question is prose in the handbook, so the vector index answers it with a citation
  • Routes by question type, and scores each route on its own ground truth: reference SQL for the database questions, labelled chunks for the policy questions
  • Writes the business definition down (“refunded” means which table and which status) as a rule in the SQL prompt, then checks the generated SQL for it in code

3. The approval gate has been live for a month and almost every post was approved. How do you find out whether it is protecting anything?

What a strong answer covers:

  • Tracks approval rate, time to decision and rejection reasons per action type from the audit log
  • Watches for rubber-stamping: approvals that arrive seconds after the preview, from the same reviewer, at a rate near 100%
  • Seeds known-bad drafts (an uptime claim about competitors, a wrong number) and measures how many reviewers catch
  • Treats any fingerprint refusal as a bug to investigate, since in a correct pipeline nothing edits a post after its preview

4. A reviewer approves an outage post four hours after the agent drafted it. In the meantime the incident was reopened. The fingerprint matches. Should the post go out?

What a strong answer covers:

  • The fingerprint covers the text and says nothing about the world the text describes, so a match does not mean the post is still true
  • Adds an expiry to approvals, or a precondition checked at execute time (incident status, the version of the data the draft used)
  • Re-runs the dry run and asks again when the approval is stale, instead of executing an old preview
  • Uses a persistent checkpointer (SQLite or Postgres) so the paused run survives the wait, and alerts when runs sit at review too long

5. You give a text-to-SQL ReAct agent access to Larkspur’s billing database. A user writes “Delete the invoices for my test servers, then show what is left.” What stops the agent, and how would you support legitimate changes?

What a strong answer covers:

  • The guarantee lives in the connection: a read-only connection (mode=ro in SQLite) or a read-only database role, so a talked-around prompt still cannot write
  • Scopes rows per customer in a view or a bound parameter, never through instructions to the model
  • Routes real changes through the approval harness, with a dry run that previews the affected rows (a SELECT with the same filter) before any DELETE
  • Logs every query the agent runs and checks the outcome in code (row counts before and after), not from the answer’s wording

Key Takeaways

  • Split every consequential action into a dry run and a live call that share one code path, and keep the dry run in its own node before the pause.
  • Fail closed. Only an explicit approve approves, and the approval covers the fingerprint of what was previewed, recomputed at execute time.
  • Use SQL to retrieve when the answer is a count, sum or ranking over rows, enforce read-only access in the connection, and write ambiguous business terms down as rules.
  • Let the LLM fill typed fields and keep routing, checks and the final document in code, where a test can run on every output.
