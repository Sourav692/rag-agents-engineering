M08 LCEL, Runnables & Chains

LCEL is how LangChain 1.x composes work: prompts, models, parsers and retrievers snap together with |, and the result runs with the same methods as each piece. Every RAG chain from M11 onwards is one of these pipes. The M08 notebooks build on four ideas: the one interface every component shares, the pipe that joins components into a sequence, the parallel and branching shapes a pipe can take, and map-reduce for documents longer than one prompt.

Open the lab

The running example is the Larkspur Cloud handbook used from M11 onwards: a support assistant that answers refund and outage questions, triages tickets, and summarises handbook sections. The lab summarises three handbook documents of 1,111, 1,833 and 2,746 characters.

TL;DR

  • A Runnable has one interface: invoke for one input, batch for a list, stream for chunks, and an async twin of each. Prompts, models, parsers, retrievers and whole chains all have it.
  • a | b is Python’s __or__ returning a RunnableSequence. A dict inside a pipe becomes a RunnableParallel, so {"context": retriever | format_docs, "question": RunnablePassthrough()} | prompt | llm | parser is a complete RAG chain.
  • RunnableParallel runs its branches on the same input at once: notebook 03a’s description, pros and cons chains plus a merge chain make 4 model calls in 2 rounds. RunnableBranch runs the first branch whose condition is true.
  • LLMChain, RetrievalQA and load_summarize_chain now live in langchain-classic, deprecated with removal set for 2.0.0. Each rewrites as a short pipe.
  • Map-reduce trades calls for a small prompt. In the lab the whole handbook at chunk_size=400 is 10 chunks: map-reduce makes 11 calls in 4 rounds at max_concurrency=4, refine makes 10 calls in 10 rounds, and stuff makes 1 call that reads all 2,746 characters.

Runnable interface

Lesson 8.1: LCEL and the Runnable interface. Notebooks: 01a_LCEL_Introduction.ipynb, 01b_Runnables.ipynb

A Runnable is any LangChain component that takes one input and returns one output through a fixed set of methods. A prompt template, a chat model, an output parser, a retriever and a chain built from them all have the same methods, so code that runs one runs any of them.

Method Takes Returns Use it for
invoke(x) one input one output a single request
batch([x1, x2, …]) a list of inputs a list of outputs, in order many independent requests, run on a thread pool
stream(x) one input an iterator of chunks showing tokens as the model writes them
ainvoke, abatch, astream the same awaitables and async iterators async servers such as FastAPI

Each method also takes a config argument. It carries tags, metadata and callbacks for tracing, and max_concurrency, which caps how many batch calls run at once.

One input, always. invoke passes exactly one argument. Notebook 01b shows the three ways to get more than one value in: a tuple, a dict, or a lambda that unpacks a dict for an existing function (RunnableLambda(lambda d: sum_values(d["a"], d["b"]))). A function with two parameters fails: RunnableLambda(lambda a, b: a).invoke(1) raises TypeError: missing 1 required positional argument: 'b'. Dicts are the common choice, because prompt templates read their variables from a dict and RunnableParallel returns one.

Three helpers cover most glue code.

  • RunnablePassthrough() returns its input unchanged. It keeps the original question available next to a transformed copy.
  • RunnableLambda(f) wraps any Python function so it can sit in a pipe: cleaning input, formatting retrieved documents, extracting a key.
  • RunnableParallel(a=..., b=...) runs several Runnables on the same input and returns a dict of their outputs. Lesson 8.3 covers it in depth.

Each step changes the type. Notebook 02a invokes the pieces of prompt | model | parser one at a time. On a Larkspur question the data changes shape at every step:

Most pipe errors are a type mismatch at one of these arrows: a function that expects a string receives a dict, or a prompt receives an AIMessage. Invoke each step alone and print what it returns, as notebook 02a does before it builds anything else.

batch and stream come for free, with two details. The default batch runs invoke on a thread pool, and with a single input it skips the pool and runs inline, so a one-item batch shows no speed-up. A RunnableLambda that wraps a generator streams each yield: notebook 01b’s streaming_processor yields four strings for "building scalable data solutions", one per word. Called with invoke instead, the same Runnable returns all four strings added together into one, which is rarely what you want.

For the Larkspur assistant this means one test harness covers every part. The same three lines that check the refund prompt (invoke, print, assert) check the retriever, the parser and the finished chain.

Key Takeaways

  • Every Runnable takes one input through the same methods: invoke, batch, stream and their async forms. Pass several values as a dict, which prompt templates and RunnableParallel already use.
  • RunnablePassthrough, RunnableLambda and RunnableParallel cover most glue code. A RunnableLambda around a generator streams each yield.
  • The data changes type at every step of a pipe. When a chain fails, invoke each step alone and print what it returns.

Pipe composition

Lesson 8.2: LCEL deep dive. Notebooks: 02a_LCEL_Deepdive.ipynb, 02b_LCEL_and_Runnables.ipynb (optional)

The | in prompt | model | parser is ordinary Python. a | b calls a.__or__(b), the same way 2 + 4 calls (2).__add__(4). LangChain’s Runnable.__or__ returns a RunnableSequence that holds both sides, and the sequence’s invoke runs the first step and feeds its output to the next.

Notebook 02a proves this by building the mechanism from scratch. CRunnable.__or__ returns a CRunnableSequence(self, other), and its invoke is self.second.invoke(self.first.invoke(data)). Three small steps piped together give:

LangChain’s real RunnableSequence works the same way and adds what the toy lacks: batch, stream and async on the whole pipe, tracing of every step, and flattening, so (a | b) | c is one sequence of three steps rather than a sequence nested in a sequence.

A dict in a pipe becomes a RunnableParallel. When the left side of | is a plain dict, Python calls the Runnable’s __ror__ instead, and LangChain turns the dict into a RunnableParallel. Each value runs on the same input and the output is a dict with the same keys. Notebook 02a’s runs, which you can repeat without an API key:

Chain Input Output
RunnableParallel({"x": RunnablePassthrough(), "y": RunnablePassthrough()}) "hello" {'x': 'hello', 'y': 'hello'}
same, with "y": lambda z: z["input2"] {"input": "hello", "input2": "goodbye"} {'x': {'input': 'hello', 'input2': 'goodbye'}, 'y': 'goodbye'}
"x": RunnablePassthrough() \| RunnableLambda(find_keys_to_uppercase) the same dict {'x': 'HELLO', 'y': 'goodbye'}
RunnableParallel({"x": RunnablePassthrough()}).assign(extra=RunnableLambda(lambda _: 100)) the same dict {'x': {'input': 'hello', 'input2': 'goodbye'}, 'extra': 100}

Two rules follow from the table. A plain lambda in a dict is wrapped in a RunnableLambda for you. A branch can be a pipe of its own, so pipes nest inside dicts and dicts inside pipes.

.assign() adds keys and keeps the rest. RunnableParallel replaces its input with the new dict; .assign(key=runnable) (or RunnablePassthrough.assign(...)) computes the new key from the current dict and returns the old keys with it. This is how a pipe carries the question forward while later steps add context, then answer, then sources.

Finished chains compose like any step. Notebook 02a pipes the .assign() chain into a second chain that reads extra and upper-cases it; the result is the string '100'. Optional notebook 02b applies the same pieces to a RAG chain over a vector store.

For Larkspur, the RAG chain from lesson 8.4 is the dict rule in action:

rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt | llm | StrOutputParser()
)
rag_chain.invoke("How long does a refund take?")

The question string goes to both dict values. The retriever turns it into Documents and format_docs joins them into one string; the passthrough keeps the question as it is. The prompt receives {"context": ..., "question": ...}, which is exactly the pair of variables it declares.

Key Takeaways

  • The | operator calls __or__, which returns a flattened RunnableSequence that feeds each step’s output to the next and adds batch, streaming, async and tracing.
  • A plain dict in a pipe becomes a RunnableParallel: every value runs on the same input, and lambdas are wrapped for you. Pipes nest inside dicts and dicts inside pipes.
  • Use .assign() to add a key while keeping the rest, so the question travels forward as later steps add context, answer and sources.

RunnableParallel / Branch

Lesson 8.3: Branching, routing and merging chains. Notebooks: 03a_Branching_Routing_Merging_Chains.ipynb

A straight pipe runs one step after another. Notebook 03a builds the three other shapes a chain needs, each from the pieces of lessons 8.1 and 8.2: a pipeline that keeps every intermediate result, a fan-out that merges, and a router.

Linking: RunnablePassthrough.assign keeps the trail. The notebook’s IT-support pipeline runs four LLM chains in order: detect the message’s language, translate it to English, write a resolution, translate the resolution back. Each step is an .assign(), so the output dict holds orig_msg, orig_lang, trans_msg, trans_response and orig_response, and the last step can still read orig_lang from the first. final_chain.map() runs the pipeline over all four queued messages at once: 16 model calls, in 4 rounds rather than 16, because the four messages run side by side while each message’s four steps stay in order. (Counted by running the notebook’s chain shapes with a stub model in place of ChatOpenAI.)

Branching and merging: RunnableParallel, then one more chain.

The three LLM branches share one input and run at the same time; itemgetter('topic') copies the topic through without a model call. The merge prompt reads all four keys and writes the report. That is 4 model calls in 2 rounds, so the wall time is the slowest branch plus the merge. A Larkspur version compares plans: description, pros and cons of the annual plan in parallel, then one call that writes the comparison table.

Routing: RunnableBranch runs the first true condition.

RunnableBranch((cond1, chain1), (cond2, chain2), …, default) takes (condition, Runnable) pairs and a default. It tests the conditions in order, runs the first whose condition returns true, and runs the default when none does. It needs at least one pair and a default: RunnableBranch(f) raises ValueError: RunnableBranch requires at least two branches. In the notebook a dict runs the classifier and copies instruction, review and sentiment beside its label, then the branch picks a chain: 2 model calls per request in 2 rounds, or 1 call when the default answers.

For the Larkspur support desk the same shape triages tickets: a classifier labels each ticket refund, outage or export, and the branch sends it to the chain whose prompt holds that policy. Two properties of this design matter in production:

  • Order decides ties. The conditions in 03a are substring tests on free text. A label such as “summarize and email” matches the first condition and never reaches the email chain.
  • Plan the default. In 03a it returns a fixed apology string. For a support desk it should usually hand the ticket to a person and be counted, because a rising default rate is an early sign that the classifier has drifted.

The notebook ends with moderation: piping a chain into the legacy OpenAIModerationChain from langchain_classic screens its output before it reaches the caller. Any Runnable can take that last position, which is how output checks and guardrails attach to a pipe.

Key Takeaways

  • Link steps with .assign() to keep every intermediate result, and use .map() to run several inputs side by side while each input’s steps stay in order.
  • Fan out with RunnableParallel and merge with one more chain. Wall time is the slowest branch plus the merge.
  • RunnableBranch runs the first true condition, so order decides ties. Make the default hand off to a person and count it, since a rising default rate signals classifier drift.

Check yourself

1. How does RunnableBranch choose a chain, and where does a label such as "summarize and email" end up in notebook 03a?

It tests the conditions in order, runs the first whose condition returns true, and runs the default when none does. The 03a conditions are substring tests, so “summarize and email” matches the first condition and goes to the summary chain; it never reaches the email chain. Order decides ties.

2. The Larkspur plan comparison runs description, pros and cons in parallel, then one merge. How many model calls and rounds is that, and what sets the wall time?

Legacy chains to LCEL

Lesson 8.4: Legacy chains and migration to LCEL. Notebooks: 04a_Chain_Migrations.ipynb, 04b_Basics_of_Chains.ipynb (optional), 04c_Chains_Basics_and_OutputParsers.ipynb (optional), 04d_Advanced_Chains.ipynb (optional), 04e_Chain_Migration_Advanced.ipynb (optional)

Before LCEL, LangChain packaged each pattern as a class: LLMChain for prompt plus model, RetrievalQA for retrieval plus answer, load_summarize_chain for summaries. In LangChain 1.x these classes left the langchain package. They live in the compatibility package langchain-classic, still run, and carry deprecation markers with removal set for 2.0.0. Older tutorials and older Larkspur services still use them, so each one is listed here with the pipe that replaces it.

Legacy (0.x) LCEL (1.x) What changes for the caller
LLMChain(llm=llm, prompt=prompt) prompt \| llm \| StrOutputParser() the legacy chain returns a dict with the inputs and a text key; the pipe returns a string
RetrievalQA.from_llm(llm, retriever=retriever, prompt=prompt) {"context": retriever \| format_docs, "question": RunnablePassthrough()} \| prompt \| llm \| StrOutputParser() input key query and output key result become a plain string in and a string out
load_summarize_chain(llm, chain_type=...) one of three short pipes (lesson 8.5) you join the Documents into the prompt’s {text} yourself
chain({...}), chain.run(...) chain.invoke({...}) the call style was replaced in 0.1.0
hub.pull("rlm/rag-prompt") the prompt written inline in ChatPromptTemplate.from_messages no network call and no untrusted object to load

Two deprecations per legacy cell. Notebook 04a points out that running a legacy cell warns twice: once for the class and once for calling a chain directly with chain({...}). RetrievalQA usually warns more often, because it builds a StuffDocumentsChain and an LLMChain inside itself, and both are deprecated too.

hub.pull fails outright. langchain_classic.hub.pull is deprecated since 1.0.6, and on the repo’s pinned langsmith it raises ValueError: Pulling a public prompt by owner/name is disabled by default because prompts may contain untrusted serialized LangChain objects. Notebook 04a lists the three options in order: inline the prompt, call langsmith.Client().pull_prompt(..., dangerously_pull_public_prompt=True) and accept the risk, or keep hub.pull, which raises.

No warning at build time. Notebook 05b shows that load_summarize_chain(llm, chain_type="stuff") returns a deprecated StuffDocumentsChain and emits no warning when it is built. The only warning arrives when .run() is called, and it is about .run(), not about the class. Code built this way keeps working until 2.0 removes it, which is why audits should grep for imports from langchain_classic rather than wait for warnings.

A migration that does not break callers.

  1. Repoint the imports to langchain_classic so the service runs on 1.x unchanged.
  2. Replace one chain with its pipe behind the same function, mapping the output shape: callers that read result["result"] from RetrievalQA now receive the string itself.
  3. Replace chain(...) and .run() with .invoke().
  4. Run a fixed question set through old and new versions and compare answers before you delete the old class.

The optional notebooks show more legacy classes: 04b builds LLMChain and SimpleSequentialChain, 04c adds StructuredOutputParser, 04d covers SequentialChain and the router class MultiPromptChain (whose LCEL form is lesson 8.3’s RunnableBranch), and 04e rewrites ConversationalRetrievalChain as a rephrase pipe followed by a retrieval pipe.

Key Takeaways

  • Legacy chain classes still run from langchain-classic but are set for removal in 2.0.0. Each has a short LCEL pipe that replaces it, usually with a plain string in and out.
  • Some legacy chains warn only when called, or not at all. Find them by grepping for imports from langchain_classic, not by waiting for warnings.
  • Migrate one chain at a time behind the same function: map the output shape, switch to .invoke(), and compare old and new answers on a fixed question set before deleting the old class.

Map-reduce summarisation

Lesson 8.5: Summarization: stuff, map-reduce, refine. Notebooks: 05a_Summarization_Essentials.ipynb, 05b_Doc_Chains_to_LCEL_LangChain_v1.ipynb

A model reads a finite context window, and a handbook, a contract or a quarter of support tickets can be longer. There are three ways to get many documents through one model, and notebook 05b writes each out in a few lines of LCEL in place of the old load_summarize_chain(llm, chain_type=...):

  • Stuff: join the documents, fill one prompt, call once. It is the cheapest strategy and the least lossy, because nothing is summarised twice, and it works only while the text fits.
  • Map-reduce: summarise each chunk on its own (the map), then summarise the summaries (the reduce). The map calls are independent, so map_chain.batch(...) runs them on a thread pool.
  • Refine: summarise the first chunk, then revise that summary once per remaining chunk. Each call needs the previous answer, so the calls run one after another, and later chunks get more say than earlier ones.

The map-reduce from notebook 05b, in full:

partials = map_chain.batch([{"text": c} for c in chunks], config={"max_concurrency": 4})
summary = reduce_chain.invoke({"text": "\n\n".join(partials)})

On the whole Larkspur handbook (2,746 characters) split at chunk_size=400 with an overlap of 20, that is 10 chunks:

A round here is one wait on the model: calls in the same round run at the same time, so wall time grows with rounds, and cost grows with calls.

Strategy Model calls Rounds (max_concurrency=4) Most source text in one call Parallel
Stuff 1 1 2,746 characters nothing to parallelise
Map-reduce 11 4 399 characters the map step
Refine 10 10 399 characters, plus the running summary no, by design

Notebook 05b gives the general form: stuff is 1 call, map-reduce N + 1 calls, refine N calls. The interactive lab computes all three on three handbook documents, splitting them with a port of LangChain’s RecursiveCharacterTextSplitter that matches the library on every chunk size from 200 to 1200. Its numbers show where each strategy wins:

  • Chunk size sets the call count. On the whole handbook, chunk size 1200 gives 3 chunks and chunk size 200 gives 21. Refine’s rounds climb from 3 to 21; map-reduce at max_concurrency=4 goes from 2 rounds to 7, and at 16 it needs only 3 rounds for all 22 calls.
  • Concurrency is what makes map-reduce fast. At max_concurrency=1 the map step is a loop, and map-reduce takes N + 1 rounds, one more than refine. Rate limits often force a low cap, so measure at the cap you can run in production.
  • Small chunks cost calls without adding much. Notebook 05a splits its 630-character sample at chunk_size=100: 11 chunks, two of them only 13 and 18 characters long. Map-reduce then makes 12 calls on a text that one stuff call reads whole.

The reduce step has a limit of its own. It reads every map summary at once, so a long enough document produces joined summaries that no longer fit. The fix is to reduce in groups and reduce the results again, the recursive summarisation that M42’s RAPTOR builds into a tree.

Routing by length

Stuff is the best strategy whenever it fits, so the summariser should decide per input. This is the module’s lab brief in miniature: rebuild load_summarize_chain as LCEL, then add a branch that routes short and long inputs differently.

summarise = RunnableBranch(
    (lambda x: len(x["text"]) <= 1500, stuff_chain),
    map_reduce_chain,
)

In the lab, the refunds section (1,111 characters) goes to stuff, and the refunds and outages sections together (1,833) and the whole handbook (2,746) go to map-reduce. The check runs a real RunnableBranch in Python and the lab’s routing matches it on all three. The 1,500-character limit stands in for a context budget. In production, count tokens with the model’s tokenizer and set the limit to the context window minus the prompt template and the room the answer needs.

The two branches return the same type, a summary string, so callers never see which strategy ran. Log it anyway: when the share of map-reduce runs rises, documents have grown, and cost and latency will follow.

Key Takeaways

  • Stuff makes 1 call, map-reduce N + 1 and refine N. Cost grows with calls and wall time with rounds, and only map-reduce can run its calls in parallel.
  • Chunk size sets the call count, and concurrency is what makes map-reduce fast. Measure at the concurrency cap your rate limit allows.
  • Route by length: stuff whatever fits and map-reduce the rest. Set the limit from a token budget, and log which strategy ran.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s nightly job runs triage_chain.batch() over 2,000 support tickets. Last night it died at ticket 1,412 with a rate-limit error and wrote nothing. What do you change?

What a strong answer covers:

  • Caps parallel calls with config={"max_concurrency": n} sized to the provider’s rate limit, since the default is Python’s thread-pool size
  • Wraps the model step in .with_retry() so a transient 429 retries that call instead of failing the batch
  • Passes return_exceptions=True so one bad ticket returns an exception in its slot and the other 1,999 results survive
  • Writes results in pages (or checkpoints them) and adds .with_fallbacks([...]) to a second model if outages are common

2. Product wants a weekly digest of every handbook change. Some weeks one paragraph changes; in release weeks, 40 pages do. Which summarisation strategy do you build?

What a strong answer covers:

  • A RunnableBranch on input length: stuff below a token budget (one call, nothing summarised twice), map-reduce above it
  • Map-reduce for the long case: the map step parallelises, so latency is about one map round plus the reduce, and every chunk is treated the same
  • Refine only if later changes should override earlier ones, accepting one sequential call per chunk and order sensitivity
  • A guard for the reduce step itself: if the joined summaries exceed the budget, reduce in groups and reduce again

3. The support chain routes tickets with a classifier and a RunnableBranch. How do you find out, in production, which branch each ticket took and which branch is slow?

What a strong answer covers:

  • Traces every run (LangSmith or any callback handler); a pipe records each step as a child run with its own latency
  • Names the steps with .with_config(run_name=...) and tags runs with metadata such as ticket id and plan, so traces can be filtered
  • Logs the classifier’s raw output next to the chosen branch, since a wrong route usually starts as an unexpected label
  • Dashboards the share of tickets per branch and the default-branch rate, which rises when the classifier drifts

4. The ticket classifier returns “Refund.” for most refund tickets, but for one ticket it returns “Refund or outage”. The branch conditions are "refund" in label and "outage" in label. What happens, and how do you make routing safe?

What a strong answer covers:

  • RunnableBranch tests conditions in order and runs the first true one, so the ticket silently goes to the refund chain
  • Substring checks on free text are fragile: punctuation, case and multi-label answers all route somewhere
  • Constrains the classifier with structured output (an enum of labels) and validates it before the branch
  • Keeps a default branch that escalates to a human, and counts how often it fires

5. You inherit a Larkspur service built on RetrievalQA, LLMChain and hub.pull("rlm/rag-prompt") on LangChain 0.x. How do you migrate it to 1.x without breaking the API that callers use?

What a strong answer covers:

  • Repoints imports to langchain_classic first so the service runs on 1.x, then rewrites chain by chain behind the same interface
  • Replaces RetrievalQA with {"context": retriever | format_docs, "question": RunnablePassthrough()} | prompt | llm | StrOutputParser(), and maps the output shape: the legacy chain returns a dict with query and result, the pipe returns a string
  • Inlines the prompt, because hub.pull is deprecated and raises for public prompts on the repo’s pinned langsmith
  • Replaces every chain(...) and .run() call with .invoke(), and compares old and new answers on a fixed question set before switching

Key Takeaways

  • Every component and every chain shares one interface, so test each step alone with .invoke() before you pipe it.
  • Build data flow with dicts: a dict fans one input out, and RunnablePassthrough.assign() adds a key while keeping the rest.
  • Write new chains as pipes. Treat langchain_classic imports as a staging post for old code, never as a destination.
  • Choose a summarisation strategy by length and latency: stuff when it fits, map-reduce when it does not, refine only when order should matter.
