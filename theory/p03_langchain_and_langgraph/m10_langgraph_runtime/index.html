M10 LangGraph runtime

M09 builds a graph that runs from start to end in one call. Real workflows stop and start again: a person approves a step hours later, a payment provider times out, a deploy restarts the worker, a user wants to see progress while the graph runs. The M10 notebooks build on four ideas: the checkpointer, interrupt(), subgraphs and streaming modes, plus the retry policies, loop bounds and state rules that make a resumed run safe.

What runs twice on resume
Open the lab

The running example is the refund desk of Larkspur Cloud, the fictional host whose handbook M11 to M13 index. A refund request enters a graph modelled on the refund agent in 06a_LangGraph_State_Management.ipynb: triage, assess risk, refund at once when the risk is low, and wait for the billing team’s approval when it is high. Two threads carry the pages and the lab, refund-17 (low risk) and refund-99 (high risk).

TL;DR

  • A checkpointer saves the whole state after every step under a thread_id. The four-node low-risk refund saves 6 checkpoints, steps -1 to 4. Any process with the same saver and thread id can read them, resume from them or fork them.
  • interrupt() pauses a node, saves the run and returns the payload to the caller under __interrupt__. Command(resume=value) continues it, and the node runs again from its first line, so code above the interrupt() call runs twice.
  • A subgraph is a compiled graph used as a node. With shared keys you add it directly; with different keys a wrapper node maps parent state in and out. Keys the parent does not declare are dropped on the way out.
  • Streaming modes decide what the caller sees while a run is in flight. For the same four-node run, values yields 5 chunks, updates 4, checkpoints 6, tasks 8 and debug 14. messages yields LLM tokens from every model call inside every node.
  • Every resumed or retried node can repeat a side effect. In the lab, a refund whose provider response is lost reaches the customer twice unless the call carries an idempotency key.

Mental model

The checkpointer writes after every step. At the gate, the first invoke returns while refund-99 waits at human_gate, and nothing runs until somebody calls Command(resume="approve") on the same thread, minutes or days later, from any worker that can reach the saver. Everything this module adds is about what happens between those two calls and after them: which code runs again, what the caller sees, and what the outside world receives twice.

Checkpointer

Lesson 10.1: Checkpointing and threads. Notebooks: 01a_Checkpointing.ipynb

A graph compiled without a checkpointer forgets everything when invoke returns. Compile it with one and pass a thread id in the config, and LangGraph saves a snapshot of the whole state after every step:

app = graph.compile(checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "refund-17"}}
app.invoke(request, cfg)

The thread_id is the key. Two calls with the same id share one history, so the second turn of a chat sees the first. Different ids never see each other, which is how one compiled graph serves every Larkspur customer at once. MemorySaver in the notebook is the older name for InMemorySaver; in the installed LangGraph 1.2.18 they are the same class.

For the low-risk refund (triage, assess, execute, done), the thread’s history holds 6 checkpoints, one before the first node and one after each step:

Step Source next Events in state
-1 input __start__ 0
0 loop triage 0
1 loop assess 1
2 loop execute 2
3 loop done 3
4 loop (empty: finished) 4

Each snapshot carries the fields the notebook prints: values (the state), next (the nodes still to run), config (thread id plus a checkpoint_id), parent_config (the previous checkpoint, so the history is a linked list), metadata (source and step) and created_at.

Where the checkpoints live decides what survives:

  • InMemorySaver keeps them in the process. Fast, no setup, and gone on restart. Use it in tests and notebooks.
  • SqliteSaver writes a file. The notebook closes the connection, opens a new one, and the second session still knows “ALPHA-7”. Fine for one process on one machine.
  • PostgresSaver has the same interface and suits several workers sharing threads, the production case in lesson 10.6.

The graph code does not change between them. That is why workers can stay stateless: any worker that can reach the saver can continue any thread.

History, replay and forks

app.get_state(cfg) returns the latest snapshot; app.get_state_history(cfg) walks all of them, newest first. Because each snapshot has an id, you can go back:

  • Replay. app.invoke(None, older.config) continues from an old checkpoint with no new input. Replaying refund-17 from step 2 re-runs execute and done; triage and assess stay as recorded. Use it to reproduce what the graph saw when it made a decision.
  • Fork. app.update_state(older.config, {"risk": "high"}) writes a new checkpoint (source update, step 3, still waiting on execute) whose parent is the old one. invoke(None, fork_config) continues the fork; the original branch stays in the history. On refund-17 the history grows from 6 checkpoints to 9.
  • Copy to a new thread. The notebook’s branching demo calls update_state on a fresh thread_id with an old snapshot’s values, then lets each thread run on its own.

Use the snapshot’s own config when you fork. The 06a notebook notes that a hand-built config without checkpoint_ns breaks update_state.

A replayed node runs its code again. If execute sends a refund, replay sends another one; lesson 10.6 shows how to make that harmless.

Key Takeaways

  • A checkpointer saves the whole state after every step, filed under the thread_id. Same id shares one history; different ids never see each other.
  • Use InMemorySaver for tests, SqliteSaver for one process, PostgresSaver for several workers. The graph code stays the same, so workers can stay stateless.
  • Replay re-runs nodes from an old checkpoint and a fork adds a new branch beside the original. Fork from the snapshot’s own config, and remember replayed side effects happen again.

interrupt()

Lesson 10.2: Interrupts and human-in-the-loop. Notebooks: 02a_HITL_Mechanics.ipynb, 02b_LangGraph_Interrupt_Primitive.ipynb, 02c_HITL_Patterns.ipynb

interrupt(payload) called inside a node stops the run at that line. LangGraph saves the state, and invoke returns with the payload under __interrupt__. The thread now waits at that node; get_state(cfg).next is ("human_gate",). Days later, any process calls invoke(Command(resume=value), cfg) on the same thread, and interrupt() returns value inside the node.

def human_gate(state):
    approval = interrupt({"question": f"Approve refund for {state['task']}?"})
    return {"decision": "approved", "events": [f"human_gate: human said '{approval}'"]}

Three rules follow from the mechanism:

  • A checkpointer is required. Without one, the first call still returns __interrupt__, but nothing was saved, and the resume call raises RuntimeError: Cannot use Command(resume=...) without checkpointer.
  • The node runs again from the top. On resume, LangGraph does not continue mid-function; it calls the node again, and this time interrupt() returns the resume value. The 02a resume-lifecycle demo prints “Node execution started” twice. In the refund graph human_gate runs 2 times for one approval, so anything above the interrupt() call (a notification, a counter, an LLM call) happens twice.
  • The resume value is yours to define. A string, a dict with edited_plan, a list in the Agent Inbox format: interrupt() returns whatever you pass, so validate it. The 02a age example calls interrupt() in a while loop until the answer parses as a non-negative integer.

The notebooks also show the compile-time form, compile(interrupt_before=["assistant"]) or interrupt_after=[...]. It pauses between nodes without touching node code, and you continue with invoke(None, cfg). It suits debugging and step-through review. interrupt() suits approvals, because the node decides when to pause and what to show.

Approval patterns

The 02b and 02c notebooks build four shapes on the same primitive. On the Larkspur refund desk they look like this:

  • Approve or reject. The gate returns Command(goto="execute") or Command(goto="cancel") depending on the decision, with update={"decision": ...}. Annotate the return type, Command[Literal["execute", "cancel"]], so the graph knows the possible targets.
  • Edit then continue. The gate shows the draft reply to the customer and resumes with {"edited_summary": ...}; the node writes the edited text to state and the graph follows its one path.
  • Edit state while paused. With interrupt_before, the caller runs update_state(cfg, {...}) on the parked thread, then invoke(None, cfg). The 02c demo swaps “Multiply 2 and 3” for “No, please multiply 15 and 6” this way.
  • Review a tool call. interrupt() inside a sensitive tool, or a wrapper such as the notebook’s add_human_in_the_loop, lets a person accept, edit or answer instead of running it. HumanInTheLoopMiddleware in M24 packages the same idea for create_agent.

Whichever shape you use, approve on an exact value and treat anything else as no. M27 builds that fail-closed gate, with a fingerprint that catches edits made after the review. What can happen twice around the gate is the subject of the lab in lesson 10.6.

Key Takeaways

  • interrupt() saves the state and parks the thread; Command(resume=value) continues it from any process. It needs a checkpointer, or the resume call fails.
  • On resume the node runs again from its first line. Keep notifications, counters and model calls out of the code above interrupt().
  • The resume value is whatever the caller passes. Validate it, approve only on an exact value, and treat anything else as no.

Subgraphs

Lesson 10.3: Subgraphs. Notebooks: 03a_Subgraphs.ipynb

A subgraph is an ordinary compiled graph used as a node of another graph. The notebook builds a weather agent (an agent node, a ToolNode, a loop between them), invokes it on its own to check its input and output, then nests it two ways. On the Larkspur desk the same move turns a self-contained “check refund eligibility” agent into one step of the refund graph.

  • Shared keys: add it directly. When parent and child both use MessagesState, add_node("subgraph", subgraph) is enough. The parent’s messages channel is the child’s, and the child’s reply lands on it with the same reducer.
  • Different keys: wrap it. The notebook’s parent stores the transcript under parent_messages. A wrapper node calls subgraph.invoke({"messages": state["parent_messages"]}) and writes the result back. The child does not change; only the parent knows the mapping.

Only the keys the parent declares come back out of a directly added subgraph. A child that writes a private scratch key next to a shared decision key returns decision to the parent and drops scratch. So the child can keep working notes the parent never sees. It also means a key you expected in the parent has to be in the parent’s schema.

The runtime features from this module reach inside subgraphs:

  • Checkpoints. A subgraph compiled without a checkpointer uses the parent’s. A parent thread parked in a subgraph reports the subgraph node in next, and get_state(cfg, subgraphs=True) shows the child’s own state and its next.
  • Interrupts. An interrupt() inside the child pauses the whole run, in both forms. Resuming re-runs only the interrupted child node; the child’s earlier nodes keep their saved results. With a wrapper, the wrapper function also runs again from its first line, so any parent-side code before subgraph.invoke repeats. In a two-node child (a check, then a gate) both forms ran the check once and the gate twice; the wrapper ran twice.
  • Streaming. stream(..., subgraphs=True) yields (namespace, chunk) pairs, where the namespace names the subgraph node (("approval:<task id>",)) and the parent’s own events have the empty namespace ().

Choose a subgraph when a piece has its own loop or its own state that the parent should not carry, when a team owns it separately, or when several parents reuse it. M35 to M37 build multi-agent systems out of exactly these pieces. For a straight sequence of steps on the same state, plain nodes are simpler.

Key Takeaways

  • Add a compiled subgraph directly when it shares keys with the parent, and wrap it in a node that maps keys when it does not. Only keys the parent declares come back out.
  • Checkpoints, interrupts and streaming reach inside subgraphs. A resume re-runs only the interrupted child node, but a wrapper also runs again from its first line.
  • Use a subgraph for a piece with its own loop or state, a separate owner, or several parents. For a straight sequence on one state, plain nodes are simpler.

When the keys differ, as with the notebook’s parent_messages, a wrapper calls subgraph.invoke({"messages": ...}) and writes the result back. The child does not change; only the parent knows the mapping.

Streaming modes

Lesson 10.4: Async and streaming. Notebooks: 04a_Async_and_Streaming.ipynb

invoke returns once, at the end. stream (and astream) yields chunks while the graph runs, and stream_mode decides what a chunk is. The installed LangGraph 1.2.18 has seven modes. Here is what each yields for one run of the four-node low-risk refund (triage, assess, execute, done), counted in the scratchpad:

Mode One chunk is Chunks
values the whole state, once at the start and after each step 5
updates {node: what it returned}, after each node 4
checkpoints a snapshot in the shape get_state() returns 6
tasks a node starting, then finishing with its result or error 8
debug checkpoints and tasks together, with step and timestamp 14
messages (token chunk, metadata) from a chat model inside a node per token
custom whatever a node writes with StreamWriter per write

Match the mode to the screen:

  • Progress labels (“checking eligibility”, “waiting for approval”): updates. Each chunk names the node that just finished. When the run pauses, the last chunk is {"__interrupt__": ...}, so the client knows to show an approval card.
  • A typing effect: messages. The 04a notebook prints each token as it arrives and adds the AIMessageChunk objects with + to rebuild the full reply.
  • A client that renders the whole state: values.
  • Audits and debugging: checkpoints or debug.

messages mode streams tokens from every chat-model call inside every node, not only the one that writes the answer. A RAG graph with a grader node streams the grader’s “yes relevant” before the answer. Each chunk’s metadata names its node, so filter on metadata["langgraph_node"] before you render.

Pass a list to get several modes from one run: stream_mode=["updates", "messages"] yields (mode, chunk) pairs. On the refund run, ["updates", "values"] yields 9 pairs, the 4 and the 5 from the table.

Async nodes

A node can be async def and await model.ainvoke(...); the graph then runs with await graph.ainvoke(...) or async for chunk in graph.astream(...). The notebook’s async graph has the same shape as its synchronous one; only the node and the call change.

Async matters when one server process handles many conversations. A synchronous invoke holds its worker for the whole run, model calls included. An async node gives the event loop back while it waits on the model or a tool, so a FastAPI handler can serve other Larkspur customers in the meantime. Streaming and async are separate choices: stream works synchronously, and ainvoke returns once at the end like invoke. A chat endpoint usually wants both, astream with messages and updates.

Two details from the notebook:

  • streaming=True on the model makes the provider send tokens as they are generated, which messages mode then passes through.
  • Checkpoints work the same. The async graph is compiled with MemorySaver, and a second ainvoke on the same thread sees the first turn.

Key Takeaways

  • Choose the stream mode for the screen: updates for progress labels and pauses, messages for a typing effect, values for whole-state clients, checkpoints or debug for audits.
  • messages mode streams tokens from every model call in every node. Filter on metadata["langgraph_node"] before you render.
  • Async nodes free the event loop while waiting on models and tools, so one process serves many conversations. Streaming is a separate choice; a chat endpoint usually wants both.

Retry policies

Lesson 10.5: Retry policies and bounded cycles. Notebooks: 05a_Retries.ipynb, 05b_Cycles_and_Loops.ipynb

A RetryPolicy attached with add_node(name, fn, retry_policy=...) re-runs that node when it raises, inside the same invoke. The caller sees one call; the updates stream shows the node once, when it finally succeeds. The 05a notebook wraps a weather API that fails 70% of the time:

RetryPolicy(max_attempts=5, initial_interval=1.0, backoff_factor=2.0,
            max_interval=10.0, jitter=True, retry_on=APIError)

In the installed LangGraph 1.2.18 the wait after the n-th failure is min(max_interval, initial_interval * backoff_factor ** (n - 1)), plus a random 0 to 1 second when jitter is on. For the notebook’s policy:

After failure Wait With jitter
1 1 s 1 to 2 s
2 2 s 2 to 3 s
3 4 s 4 to 5 s
4 8 s 8 to 9 s
5 no wait, the exception reaches the caller

So a run that exhausts the policy waits 15 to 19 seconds before it fails. With a 70% failure rate, all five attempts fail with probability 0.7^5 ≈ 0.168, about one run in six. More attempts would lower that and lengthen the worst wait; max_interval caps any single wait at 10 seconds.

With no retry_on, the default retries ConnectionError and HTTP 5xx errors from httpx and requests, and never retries ValueError, TypeError, RuntimeError, LookupError and the other programming errors on its list. Any exception class not on that list is retried, so a custom APIError(Exception) is retried even without retry_on. Name the exceptions you mean, as the notebook does, so a bug in the node fails on the first attempt instead of after every wait.

A retry repeats the node’s side effects. If the payment provider applied a Larkspur refund and then the connection dropped, the retry refunds again. Lesson 10.6 shows the fix and the lab that counts it.

Bounded cycles

A cycle is a conditional edge that routes back to a node the run already visited. The 05b notebook uses one to regenerate code until it passes its tests, and another to research a topic to a fixed depth. Every cycle needs a reason to stop that does not depend on the model getting it right.

The notebook’s guard has three parts:

  • The node counts. generate returns iteration + 1. The router only reads it. A router function picks an edge; anything it writes to state is discarded, so a counter bumped there never grows.
  • The router checks success first, then the cap. With max_iterations=3 and a validator that always fails, the run is generate, validate, three times over, then finalize: 7 node runs, 3 errors accumulated through the operator.add reducer, and a result with success still false that the caller must handle.
  • recursion_limit is the backstop. It counts steps, not loops. The installed LangGraph’s default is 10,007 (set by LANGGRAPH_DEFAULT_RECURSION_LIMIT), far too high to save an LLM budget. Pass it per run: the same loop with no counter and {"recursion_limit": 10} stops after 10 steps (five generates, five validations) with GraphRecursionError.

A loop on the Larkspur desk, such as “rewrite the customer reply until the tone checker passes”, gets the same treatment: a counter in the rewriting node, a cap in the router, an explicit recursion_limit, and a fallback path when the cap is hit. M29’s grade-and-rewrite loops are built this way.

Key Takeaways

  • A RetryPolicy re-runs a failing node inside one call, with exponential backoff capped by max_interval. Name the exceptions in retry_on so a bug fails on the first attempt.
  • Every retry repeats the node’s side effects, so an external write that already succeeded can happen twice.
  • Bound every cycle: count in the node, check success then the cap in the router, and pass an explicit recursion_limit. The default of 10,007 steps will not protect an LLM budget.

The default retries ConnectionError and HTTP 5xx errors and skips the programming errors on its list, but any class not on that list is retried, including a custom APIError(Exception). Naming the exceptions makes the policy retry only what you mean.

Reducers and parallel writes

Lesson 10.6: State management in practice. Notebooks: 06a_LangGraph_State_Management.ipynb

The 06a notebook runs without an API key: its LLM and tools are deterministic stubs, so every result in this section comes from running its code. The state schema is the contract between steps, and each field’s reducer decides how a node’s partial update lands. In the notebook, nodes a then b each return 1 for two fields:

Reducer Two nodes in a row each write Two parallel nodes write in one step
None (plain: int) the last write wins: 1 InvalidUpdateError
operator.add (summed) the writes add up: 2 the writes add up
add_messages appended, matched by id appended; RemoveMessage(id=...) deletes

A missing reducer fails in the parallel case. When two reviewers fan out from START and both return risk, LangGraph cannot choose, and stops with At key ‘risk’: Can receive only one value per step. Use an Annotated key to handle multiple values. Give the field a reducer and the merge is deterministic; that is how parallel reviewers’ scores are summed.

The refund graph keeps one field as an audit trail, events: Annotated[list[str], operator.add]. Every node appends a line, nothing overwrites it, and the checkpoint history records when each line arrived. The model-facing messages list is the opposite case: section 10 of the notebook prunes it with RemoveMessage to fit the context window, while events is never pruned.

Resume and side effects

A durable workflow re-executes code. The run resumes after an approval, a worker restarts after a crash, a RetryPolicy tries again. The checkpointer makes the state safe across all three; it cannot take back what a node already did to the outside world. The notebook’s refund agent shows three ways a node runs again, and the Larkspur refund graph in the lab records each one with LangGraph 1.2.18:

  • Resume after interrupt() re-runs the interrupted node from its first line (lesson 10.2). Nodes before it do not run again.
  • Resume after a crash is invoke(None, cfg) on the same thread once the cause is fixed. The failed node runs again; triage and assess keep their checkpointed results. The low-risk refund takes 2 client calls: the first raises ConnectionError and leaves the thread parked at execute, the second finishes.
  • A RetryPolicy re-runs the node inside the same call (lesson 10.5). The caller sees no error; the provider sees two requests.

The interactive lab counts what reaches the outside world for each combination. Its headline numbers, for the high-risk refund refund-99:

Fault in execute Guards off: notices, refunds Guards on: notices, refunds
None 2, 1 1, 1
503, crash then invoke(None) 2, 1 1, 1
503, RetryPolicy 2, 1 1, 1
Response lost, RetryPolicy 2, 2 1, 1

Two guards account for every difference:

  • Keep side effects off the resumed path. With guards off, the approval notice is sent inside human_gate above interrupt(), so the billing team gets it again when the gate resumes. Moved into its own notify node before the gate, it runs once. The graph gains a node and one checkpoint (8 instead of 7), and the client still makes 2 calls.
  • Make external writes idempotent. A 503 before the provider refunds is harmless to retry. A lost response after it refunds is not: with guards off the customer is refunded twice. With guards on, the call carries the key refund:refund-99, the provider recognises the second request and returns the stored result. The notebook’s EXECUTION_LEDGER does the same check in process.

Put together, these are the notebook’s closing rules: workers stay stateless, state lives in the checkpointer, the events field is the audit log, the workflow is an explicit graph with the human gate as a waiting state, and every side effect can run twice without harm.

Key Takeaways

  • Give any field that parallel nodes write a reducer, or the step fails with InvalidUpdateError. An operator.add list makes a durable audit trail that nothing overwrites.
  • Nodes run again after an interrupt, a crash or a retry. The checkpointer protects the state, never what a node already did outside the graph.
  • Move side effects off the resumed path into their own node, and send external writes with an idempotency key such as refund:refund-99.

Check yourself

1. Two reviewers fan out from the start node and both return risk, and the run stops. Why, and what fixes it?

The risk field has no reducer, so LangGraph cannot choose between two writes in one step and raises “Can receive only one value per step”. Give the field a reducer, such as operator.add, and the merge is deterministic; that is how parallel reviewers’ scores are summed.

2. In the lab, refund-99's provider applies the refund and the response is lost, then a RetryPolicy retries. How many refunds does the customer get with guards off, and with guards on?

Two with guards off, one with guards on. With guards on the call carries the key refund:refund-99, so the provider recognises the second request and returns the stored result. A 503 before the refund is harmless to retry either way.

3. The billing team gets every high-risk approval notice twice, even with no faults. What causes it, and what is the fix?

The notice is sent inside human_gate above interrupt(), and a resume re-runs that node from its first line. Move the notice into its own notify node before the gate, so it runs once. The graph gains a node and one checkpoint (8 instead of 7), and the client still makes 2 calls.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Finance reports that refund-99 was paid out twice, and the billing team says it got two approval requests for it. The approval itself was given once. How do you investigate?

What a strong answer covers:

  • Reads the thread’s checkpoint history and the provider’s logs side by side, and counts how many times human_gate and execute ran
  • Knows that resuming after interrupt() re-runs the gate node from its first line, so a notification above the call goes out again
  • Knows that a RetryPolicy or an invoke(None) after a crash re-runs execute, and a provider that applied the refund but lost the response gets called twice
  • Fixes both at the source: the notice moves to its own node before the gate, and the refund call carries an idempotency key such as refund:refund-99 that the provider dedups on

2. High-risk refunds wait up to two days for approval, and the service runs on three workers that redeploy daily. The prototype uses InMemorySaver. What do you change, and what do you check before launch?

What a strong answer covers:

  • InMemorySaver lives in one process; a redeploy loses every parked refund, and a resume that lands on another worker finds no thread
  • Moves to a shared durable saver (PostgresSaver for several writers; SqliteSaver is fine for one process on one machine), with no change to graph code
  • Tests the restart path: start refund-99, kill the worker, resume from a fresh process with the same thread_id
  • Plans retention: checkpoints accumulate per step, so old finished threads need a cleanup job

3. Your manager wants a dashboard showing how many refunds are waiting for approval and for how long. Where does the data come from?

What a strong answer covers:

  • A thread parked at the gate has get_state(config).next == ("human_gate",) and a pending interrupt in its tasks
  • The latest checkpoint’s created_at gives the wait time; alerts fire when a refund waits past an agreed limit
  • Keeps an append-only events field (an operator.add reducer) as the audit trail, since values alone shows only the latest state
  • Records the decision and who made it in state when resuming, so the dashboard and the audit agree

4. A refund was assessed as high risk on Friday and approved on Monday. Over the weekend the policy team changed the refund window. Which policy applies when the graph resumes, and should it?

What a strong answer covers:

  • The checkpoint holds Friday’s state; resuming continues from it and does not re-run triage or assess
  • Decides whether stale assessments are acceptable; for money, re-checks the policy in execute or routes back to assess when the policy version changed
  • Stores the policy version in state at assessment time, so the check is a comparison, not a guess
  • For a deliberate correction, forks with update_state from the checkpoint before execute instead of editing the database

5. The support chat streams tokens with stream_mode="messages". After a grader node was added, customers briefly see “yes relevant” before the answer. Why, and how do you fix it?

What a strong answer covers:

  • messages mode streams tokens from every chat-model call inside every node, the grader included
  • Each chunk comes with metadata; filters on metadata["langgraph_node"] == "answer" before rendering
  • Uses updates mode in parallel for progress labels (“checking the handbook”), passing a list of modes and reading (mode, chunk) pairs
  • Adds a test that streams a scripted run and asserts no grader tokens reach the client

Key Takeaways

  • Compile with a checkpointer and pass a thread_id whenever a run may pause, crash or continue later; use a durable, shared saver in production.
  • Treat every node as code that can run more than once. Keep side effects after interrupt() or in their own node, and give every external write an idempotency key.
  • Pick the stream mode for the screen: updates for progress, messages filtered by node for typing, values when the client renders whole state.
  • Bound every loop twice: a counter that a node increments and the router reads, and an explicit recursion_limit as the backstop.
