M09 LangGraph core

A LangGraph application is a state object and the functions that update it. Nodes read the state and return a partial update, a reducer per key decides how that update merges, and edges, fixed or conditional, decide which node runs next. Agentic RAG, memory and multi-agent systems later in the course are all built from these parts. The M09 notebooks build on four ideas: the graph and its state, the reducers that merge updates, conditional edges that route on state, and Command, which updates and routes in one return.

Open the lab

The running example is a Larkspur Cloud support graph over the same handbook as M11 to M13. A classify node reads the customer’s question and writes a route; a conditional edge sends it to a billing, technical or human node; the handler answers from the handbook. The notebooks use their own small demos (weather, comic books, a temperature alarm), and they ship without saved outputs. Every figure and error message on these pages comes from running the notebooks’ code, or small variations of it, against the installed LangGraph 1.2.18, or from the lab, which matches that version’s graph on all 24 of its settings.

TL;DR

  • A StateGraph is a schema, nodes that return partial updates, and edges from START to END. compile() turns it into a runnable; invoke returns the final state and starts from a fresh state every call.
  • Each state key can have a reducer. Without one, the last write wins. In the lab the support graph ends with 1 message and no question when nodes return only their new message, with 3 under add_messages, and with 7 (four copies of the question) when operator.add meets nodes that return the whole list.
  • A conditional edge calls a router after its source node and goes to the node name it returns. A name outside the destination list raises KeyError, and the order of the router’s rules decides close calls: Can I export my data after I cancel my plan? goes to billing.
  • Command(update=..., goto=...) writes and routes in one return. Its Literal annotation only draws the graph; a goto to a node that does not exist ends the run with a logged warning and no error.
  • TypedDict state is hints only, and Pydantic state validates the input at invoke before any node runs, though not what nodes write. Input and output schemas hide private keys; config and runtime context carry settings and dependencies that are not state.

Mental model

Every node gets the whole state and returns only the keys it changes. Between nodes the graph merges each returned key with that key’s reducer, so a node never sees another node’s raw return value, only the merged state. The three-way choice after classify is a conditional edge: a plain function reads route and names the next node.

StateGraph

Lesson 9.1: State, graphs and reducers. Notebooks: 01a_State_and_Graph_Basics.ipynb, 01b_MessagesState.ipynb

A StateGraph has three parts. The state is a schema, usually a TypedDict, that every node receives. A node is a plain function that takes the state and returns a dict with only the keys it changes. An edge says which node runs next; START and END are the entry and exit. compile() turns the builder into a runnable, and invoke runs it and returns the final state.

The Larkspur support graph from the lab, written the way notebook 01a builds its graphs:

class SupportState(MessagesState):        # messages, with the add_messages reducer
    route: str
    answer: dict

builder = StateGraph(SupportState)
builder.add_node("classify", classify)
builder.add_node("billing", billing)
builder.add_node("technical", technical)
builder.add_node("human", human)
builder.add_edge(START, "classify")
builder.add_conditional_edges("classify", lambda s: s["route"], ["billing", "technical", "human"])
for name in ("billing", "technical", "human"):
    builder.add_edge(name, END)
graph = builder.compile()

graph.invoke({"messages": [HumanMessage("When will my refund appear on my statement?")]})

MessagesState is a ready-made schema with one key, messages, already paired with the add_messages reducer. Notebook 01b subclasses it to add turn_count; that key has no reducer, so the counter node’s write replaces it. Run once, the notebook’s three-node graph ends with 2 messages and turn_count 1: two keys in one schema, merged by two different rules.

Two habits from the notebooks keep graphs readable. Nodes return partial updates, never the whole state, so each node’s return shows exactly what it changed. And the state holds data the graph works on; per-call settings and dependencies such as a database client go elsewhere (lesson 9.4 and 9.5).

Reducers

A reducer decides what a node’s write does to a key. Without one, the write replaces the value. Notebook 01a shows the cost: three nodes each return {"messages": "..."} into a str key, and the final state holds only 'Hello this is the final node'; the customer’s input is gone after the first node.

A reducer is attached with Annotated[type, function] and is called as function(current, update). Notebook 01a starts from {"count": 5, "animals": ["lion", "tiger"]} and runs one node that returns {"count": 1, "animals": ["cat"]}:

  • No reducer: the state becomes {"count": 1, "animals": ["cat"]}.
  • Annotated[int, custom_increment] and Annotated[list, operator.add]: the state becomes {"count": 6, "animals": ["lion", "tiger", "cat"]}.
  • Annotated[list, add_messages]: appends messages, gives each one an id, and replaces a message whose id is already in the list. It also turns a bare string into a message: in notebook 01a the input and the three nodes’ strings end as four HumanMessage objects, so a node that should speak as the assistant must return an AIMessage.

The reducer and what the nodes return have to agree. The interactive lab runs the Larkspur graph with each reducer, once with nodes that return only their new message and once with nodes that return state["messages"] + [msg]. Messages in the final state for the refund question:

Reducer on messages Node returns its message Node returns the whole list
None (overwrite) 1, and the question is lost 3
operator.add 3 7, the question four times
add_messages 3 3
  • Overwrite with new-message returns loses the question after classify, so the billing node has nothing to answer and the structured answer has no source.
  • Overwrite with whole-list returns works, but only while every node copies the list forward. One node written the other way erases the history.
  • operator.add with whole-list returns concatenates the copy onto the original: 1, then 3, then 7 messages. A chat-model node would read and pay for every copy.
  • add_messages gives 3 either way, because the copied messages carry ids and replace themselves.

Reducers matter again when nodes run in parallel. If two nodes in the same step write a key that has no reducer, LangGraph 1.2.18 raises InvalidUpdateError: At key 'out': Can receive only one value per step. The fan-out patterns in M25 give such keys a reducer, usually operator.add.

Check yourself

1. What does a reducer decide, and what happens to a key that has none?

A reducer decides what a node’s write does to a key; LangGraph calls it as function(current, update). Without one, the write replaces the value. In notebook 01a, three nodes write into a str key and the final state holds only 'Hello this is the final node'; the customer’s input is gone after the first node.

2. The state starts as count 5 and animals lion and tiger. A node returns count 1 and animals cat. What is the state with custom_increment on count and operator.add on animals?

{"count": 6, "animals": ["lion", "tiger", "cat"]}. Each reducer combines the current value with the update. Without reducers the same write gives {"count": 1, "animals": ["cat"]}.

3. The Larkspur graph with operator.add on messages ends with 7 messages, the question four times. What went wrong, and what fixes it?

The nodes return the whole list, state["messages"] + [msg], and operator.add concatenates that copy onto the original: 1, then 3, then 7 messages. Either have each node return only its new message, or use add_messages, which gives 3 either way because the copied messages carry ids and replace themselves.

Conditional edges

Lesson 9.2: Conditional edges and LLM nodes. Notebooks: 02a_Conditional_Routing.ipynb, 02b_LLM_Powered_Chatbot.ipynb

A normal edge always goes from A to B. A conditional edge calls a routing function after its source node finishes; the function reads the state and returns the name of the node to run next.

builder.add_conditional_edges("classify", route_question, ["billing", "technical", "human"])

The Larkspur router reads the words of the question and checks two rule sets in order, billing words first:

Three things follow from how LangGraph runs the router.

  • The destination list is a check. With ["rainy", "sunny"] passed, notebook 02a’s weather router fails on humid with KeyError: 'humid'. Without the list, LangGraph 1.2.18 logs “wrote to unknown channel branch:to:humid, ignoring it” and ends the run with no error, and the drawn graph shows no branches at all.
  • The router only reads. It runs between nodes, and in LangGraph 1.2.18 any change it makes to state is thrown away. A retry counter or a “reason for the route” must be written by a node, such as classify, before the router runs.
  • Rule order decides the close calls. Can I export my data after I cancel my plan? is a data question, but cancel and plan match the billing rule first, so the billing node answers from the cancel page instead of export. The M09 lab shows the route for each question. A fallback route, as in notebook 02a’s comic-book router (node_others for anything unknown), turns a router gap into a handoff instead of an error: Can I pay by bank transfer? matches no rule and goes to human.

A model can make the decision instead of keywords: the classify node asks a chat model for a label, writes it to route, and the router stays a one-line read. That keeps the model call in a node, where it can be retried and traced, and keeps the edge testable without a model. M25 and M30 build routers this way.

A chat model inside a node

A node that calls a model is an ordinary node: read the messages, call the model, return the reply under messages, and let add_messages append it. Notebook 02b’s chatbot is one such node between START and END, on gpt-4o-mini:

def chatbot(state: State):
    return {"messages": [llm.invoke(state["messages"])]}

The graph keeps no memory between calls. Each invoke starts from the input you pass, so notebook 02b’s follow-up What did we discuss so far? reaches the model on its own (q1 and q2 are the two questions):

Notebook 01a works around this by passing turn1_state["messages"] + [message2] into the second call. M10 replaces that with a checkpointer that saves the state per thread.

invoke waits for the whole run. stream yields as nodes finish, in two modes notebook 02b compares:

  • stream_mode="values": the full state after each step, useful for watching a list grow, as in the M09 lab.
  • stream_mode="updates": only what each node returned, keyed by node name, such as {"chatbot": {"messages": [...]}}. It is smaller, and it names the node that made each change.

Check yourself

1. Notebook 02b's chatbot answers a first question, then gets "What did we discuss so far?" in a second invoke and cannot say. Why?

The graph keeps no memory between calls. Each invoke starts from the input you pass, so the second question reaches the model on its own and the first is gone. Notebook 01a works around it by passing the first run’s messages plus the new one; M10 replaces that with a checkpointer that saves state per thread.

2. The Larkspur router gets "Can I export my data after I cancel my plan?" Which node answers it, and why?

The billing node, from the cancel page. The router checks the billing words first, and cancel and plan match before the technical rule sees export and data. Rule order decides the close calls, even when the question is really about data.

3. You leave the destination list out of the conditional edge, and a run whose router returns an unknown name ends with no error and no answer. What happened?

LangGraph 1.2.18 logged “wrote to unknown channel branch:to:humid, ignoring it” and ended the run, and the drawn graph shows no branches. With the destination list passed, the same route fails loudly with KeyError: 'humid'. Pass the list, and add a fallback route such as human so a router gap becomes a handoff.

Choosing a state schema

Lesson 9.3: State schemas and validation. Notebooks: 03a_Different_Graph_States.ipynb, 03b_Pydantic_State_Validation.ipynb

StateGraph accepts four kinds of schema, and notebook 03a runs the same two-node graph on each. The wiring, the nodes and the reducers (Annotated[int, custom_add], Annotated[list, add_messages]) stay the same; the choice changes how nodes read the state and where a bad input is caught. Measured on LangGraph 1.2.18:

Schema Nodes read Defaults Wrong type in the input
dict state["key"] none accepted
TypedDict state["key"] none accepted
@dataclass state.key yes accepted
Pydantic BaseModel state.key yes ValidationError at invoke
  • dict has no schema, so it cannot attach reducers: notebook 03a’s dict run ends with messages holding only "Step B Completed" and step_count 1, where the other three end with two messages and a count of 2.
  • TypedDict annotations are hints for you and your editor. Notebook 03b passes {"name": 123} into a graph whose node appends a string; the run starts, and the node fails with TypeError: unsupported operand type(s) for +: 'int' and 'str'. A missing key fails the same way, as a KeyError inside the node.
  • @dataclass adds defaults (private_data: str = "") and passes nodes an instance, but checks no types: {"name": 123} goes through.
  • Pydantic checks the input against the model before the first node. The same {"name": 123} raises ValidationError at graph.invoke, and no node runs. It also converts where it can: "5" for an int field arrives as 5.

Two limits apply to every schema. invoke returns a plain dict even when the schema is a dataclass or a Pydantic model. And Pydantic validates what comes in, not what nodes write: a node that returns {"name": 5} for a str field finishes without an error, and the final state holds 5. A node whose output matters, such as Larkspur’s structured answer, validates it itself, for example by building the answer as a Pydantic model before returning it.

For the Larkspur support graph the question arrives from a web widget, so the state schema itself is a Pydantic model: question: str, with route and answer given defaults. The check comes from the state schema. In LangGraph 1.2.18 a Pydantic input_schema on a TypedDict state lets {"question": 123} through to the first node, which fails with TypeError; with a Pydantic state the same input stops at invoke before any node runs. Lesson 9.5 then narrows what the caller sends and receives. Validation costs a parse on every invoke, which is small next to one model call.

Check yourself

1. A graph with a TypedDict state receives a name of 123, and its node fails with a TypeError. Why did the schema not stop it?

TypedDict annotations are hints for you and your editor; LangGraph checks no types, so the run starts and the node fails when it adds a string to the int. With a Pydantic BaseModel state, the same input raises ValidationError at graph.invoke and no node runs.

2. The Larkspur question arrives from a web widget. Why make the state schema itself Pydantic instead of adding a Pydantic input schema to a TypedDict state?

In LangGraph 1.2.18 the Pydantic input_schema on a TypedDict state lets {"question": 123} through to the first node, which fails with TypeError. The check comes from the state schema: with a Pydantic state the same input stops at invoke before any node runs.

3. A node in a Pydantic-state graph returns 5 for a str field, and the run finishes cleanly. How should Larkspur protect its structured answer?

Validate it in the node. Pydantic checks what comes in at invoke, not what nodes write, so the final state simply holds 5. A node whose output matters builds its answer as a Pydantic model before returning it.

Node signatures and runtime context

Lesson 9.4: Nodes, runtime context and Command. Notebooks: 04a_Node_Patterns.ipynb, 04b_Runtime_Context.ipynb, 04c_Command_Objects.ipynb

A node always receives the state first. It can ask for more by declaring a second parameter, and LangGraph passes it in:

Signature The node also gets Larkspur use
f(state) nothing classify reads the question
f(state, config: RunnableConfig) config["configurable"] the thread_id for logs
f(state, runtime: Runtime[Ctx]) runtime.context the customer’s plan, a database client

Runtime context is typed. The graph declares its shape with StateGraph(State, context_schema=Ctx), and each call passes values with invoke(..., context={...}). Notebook 04b uses a dataclass, so fields without a default are required and the rest can be overridden per call: user_agent has no default, while docs_url and db_connection do. In LangGraph 1.2.18 a missing context fails when the node reads it, not when the graph starts:

  • invoke with no context: the node raises AttributeError: 'NoneType' object has no attribute 'user_agent'.
  • context={}: the call raises TypeError for the missing user_agent argument.

Context holds things the graph uses but does not produce: connections, clients, the caller’s identity. None of it appears in the returned state. Lesson 9.5 sets context beside config and state.

Command

A node can route by itself. Instead of a dict, it returns Command(update=..., goto=...): the update is merged like any node return, and goto names the next node. Notebook 04c’s check_temp_node sends a reading above 90 to warn_user with warning_sent: True, and anything else to success, without a single edge leaving the node. Both handlers end the run because no edge leaves them either.

def classify(state) -> Command[Literal["billing", "technical", "human"]]:
    route = route_for(state["messages"])
    return Command(update={"route": route}, goto=route)

The return annotation looks like a check, and notebook 04c calls it compile-time safety. In LangGraph 1.2.18 it is a drawing hint, and three behaviours follow:

  • The Literal list draws the graph. With it, the drawn graph shows dashed edges to warn_user and success. Without it, routing still works, but the drawing shows the node going straight to END. A goto to a node missing from the Literal still runs that node.
  • A goto to a node that does not exist is ignored. LangGraph logs “wrote to unknown channel branch:to:nowhere, ignoring it” and the run ends with no error and no handler output.
  • goto adds to static edges. If the node also has add_edge("check_temp_node", "success"), a hot reading runs warn_user and success in the same step, and both write final_action_performed, so the run fails with InvalidUpdateError: Can receive only one value per step.

Choose a conditional edge when routing is a pure read of state: the router is testable alone, and the graph lists every destination at build time. Choose Command when the node that decides must also write, such as the route with the reason for it, or when the target lies outside the current graph. The same object carries resume for a paused run in M10 and graph=Command.PARENT for handoffs between agents in M35.

Check yourself

1. When should a node return a Command instead of leaving the route to a conditional edge?

When the node that decides must also write, such as the route with the reason for it, or when the target lies outside the current graph. When routing is a pure read of state, a conditional edge is better: the router is testable alone and the graph lists every destination at build time.

2. Notebook 04c's check_temp_node also gets a static edge to success, and a reading of 95 arrives. What happens?

The run fails. A reading above 90 makes the node goto warn_user, and goto adds to static edges, so warn_user and success run in the same step. Both write final_action_performed, and LangGraph raises InvalidUpdateError: Can receive only one value per step.

3. A node reads user_agent from runtime context and fails with an AttributeError on NoneType. What went wrong?

The graph was invoked with no context. In LangGraph 1.2.18 a missing context fails when the node reads it, not when the graph starts. Pass it with invoke(..., context={...}), and include user_agent, which has no default; context={} raises TypeError for it.

Input, output and private state

Lesson 9.5: Input/output schemas and configuration. Notebooks: 05a_Advanced_State.ipynb

With one schema, the caller sends and receives the graph’s whole state. Notebook 05a’s ChatMessages holds question, answer and llm_calls, a counter the node bumps on each call, and invoke({"question": ...}) returns all three. The counter is bookkeeping, but every caller now sees it and may start to depend on it.

The fix gives the graph three views of one state:

class InputState(TypedDict):    question: str
class PrivateState(TypedDict):  llm_calls: int
class OutputState(TypedDict):   answer: str
class OverallState(InputState, PrivateState, OutputState): pass

StateGraph(state_schema=OverallState, input_schema=InputState, output_schema=OutputState)

Nodes still read and write every key of OverallState. Only what crosses the boundary changes: rerun on LangGraph 1.2.18 with a stub in place of the model, the split graph returns {"answer": ...} and nothing else. For the Larkspur support graph the input is the question, the output is the structured answer (route, source, text), and the message history and the top-level route key stay private. That leaves room to rename or add internal keys later without breaking the web widget.

A TypedDict output schema filters keys and checks no types. As lesson 9.3 shows, type checks come from a Pydantic state schema, and they cover the input only.

Config, context or state

Some values a node needs are not data the graph works on. Notebook 05a’s call_model reads config["configurable"].get("language", "English") and answers the same mountain question in Spanish, then in German, from the same graph; language never appears in the returned state. Three places hold values, and each has one job:

Place Holds Returned?
State data the graph reads and changes yes, through the output schema
config["configurable"] per-call settings: language, thread_id no
Runtime context dependencies: clients, the caller’s identity no

For Larkspur, the question, route and answer are state; the reply language and the conversation’s thread_id go in config; the customer id and the database client go in runtime context (lesson 9.4). Putting a client or a secret in state is the usual mistake: state is returned to the caller, and once M10 adds a checkpointer, it is saved after every step. The thread_id in config is what that checkpointer uses to find a conversation’s saved state.

Check yourself

1. Why split a graph's state into input, private and output schemas when the nodes still read and write every key?

Because only what crosses the boundary changes. The caller sends the question and gets the answer, so bookkeeping such as llm_calls stays private and no caller starts to depend on it. For Larkspur, that leaves room to rename or add internal keys without breaking the web widget.

2. The Larkspur graph needs a reply language, a thread id, a customer id and a database client. Where does each one go?

The reply language and the thread_id go in config["configurable"], as per-call settings. The customer id and the database client go in runtime context, as dependencies. Neither place is returned; state holds only the question, route and answer the graph works on.

3. A teammate puts the database client and a secret in state. Why is that a mistake, and why does it get worse once a checkpointer is added?

State is returned to the caller, so the client and the secret leave the graph with the answer. Once M10 adds a checkpointer, state is also saved after every step. Dependencies and secrets belong in runtime context, which is never returned.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. After a refactor of Larkspur’s support graph, token cost per conversation doubles and the model starts repeating the customer’s question back. No test fails. What do you look for?

What a strong answer covers:

  • Prints the messages list after each node with stream_mode="values" and counts copies of the first human message, rather than reading the final answer
  • Checks the reducer on messages and what each node returns: operator.add with a node that returns state["messages"] + [msg] doubles the list on every step (1, 3, 7 in the M09 lab)
  • Fixes it at the schema with add_messages, which replaces messages with a known id, or by returning only the new message, and keeps one convention across the graph
  • Adds a test that asserts the message count and the number of human messages after a two-node run

2. The triage step can be a conditional edge reading route, or a classify node that returns Command(goto=...). Which do you choose for Larkspur, and what changes in testing and debugging?

What a strong answer covers:

  • A conditional edge keeps routing a pure function of state: it can be unit-tested without the graph, and the graph shows every destination at build time
  • Command fits when the node that decides also writes, for example the route plus the reason for it, in one return
  • Names the Command traps: the Literal annotation is only for drawing, a misspelled goto ends the run with a warning, and a static edge from the same node runs as well
  • Logs the route in state either way, so a trace shows which branch ran and why

3. How do you know, week by week, that the router sends questions to the right handler?

What a strong answer covers:

  • Keeps a labelled set of real questions with the handler each should reach, and runs the router alone against it on every rule or prompt change
  • Reads the confusion matrix as well as accuracy: a billing question sent to technical costs less than a refund question sent nowhere
  • Tracks the route distribution and the fallback rate in production; a jump in human handoffs after a release means the rules stopped matching
  • Samples close calls such as Can I export my data after I cancel my plan?, where rule order, not meaning, picked billing

4. A release renames the technical node to tech_support. The router node returns Command(goto="technical"). Outage questions now get no answer and the error rate stays at zero. Why, and how do you stop it happening again?

What a strong answer covers:

  • In LangGraph 1.2.18 a goto to a missing node logs “wrote to unknown channel … ignoring it” and the run ends normally with no answer key
  • Finds it in the output: the final state has no answer key, so a caller that reads it gets nothing, while the error logs stay empty
  • Prevents it with names held in one constant or enum, a test that every route reaches an answer node, and an alert on runs that end without an answer
  • Notes that a conditional edge with a destination list fails loudly instead, with a KeyError for an unknown name

5. The support graph becomes an API that a web widget calls. What do you put at the boundary, and what stays inside the graph?

What a strong answer covers:

  • A Pydantic state schema, so a malformed request fails at invoke before any node or model call runs; a Pydantic input_schema on a TypedDict state does not check types in LangGraph 1.2.18
  • An input schema with only question and an output schema with only the structured answer, so route, the message history and counters such as llm_calls never leak to the client
  • Remembers that Pydantic checks the input but not node writes, so nodes that produce the answer still validate it themselves
  • Passes the customer id and database client as runtime context and per-call settings such as language in config, not as state the graph would return or save

Key Takeaways

  • Decide the reducer for every key that more than one node writes. Use add_messages for message lists and keep one convention for what nodes return.
  • Route with a plain function of state, list every destination, and give the router a fallback; the order of its rules decides the close calls.
  • Use Command when a node must write and route together, and test that every goto names a real node.
  • Validate input with a Pydantic state schema, narrow what callers send and receive with input and output schemas, and keep settings and dependencies out of state.
