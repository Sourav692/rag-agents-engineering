M07 LangChain Core: Models, Prompts & Parsers

Every LangChain program in this course has the same three parts: a prompt template that turns variables into messages, a chat model that turns messages into an AIMessage, and an output parser that turns the AIMessage into something your code can use. The M07 notebooks build on four ideas: chat models, messages, prompt templates and output parsers.

The parser bench
Open the lab

The running example is the Larkspur Cloud support assistant that M11 to M13 build, at the step after retrieval. It holds three handbook passages (refund-window, refund-timing and billing) for the question How long does a refund take? and must return a JSON answer with a list of the passages it cites. That is the module’s lab brief, and the lab runs it.

TL;DR

  • LangChain 1.x splits the old langchain package by how fast each part changes: base types in langchain-core, one partner package per provider, retired APIs in langchain-classic. A 0.x path such as langchain.chains raises ModuleNotFoundError with no deprecation warning first.
  • Every chat model takes a string, a message list or a PromptValue and returns an AIMessage with .content, .usage_metadata and .response_metadata. Changing provider changes one class or one "provider:model" string.
  • A chat model keeps no state. The conversation is the message list you send, so every earlier turn is paid for again on every call.
  • A prompt template turns variables into a PromptValue, which becomes a string or a message list for whichever model receives it. Its input_variables are recomputed from the template text, so a typo in the list you pass is replaced without an error.
  • A parser cannot make a reply good. It decides whether a bad reply raises. On the lab’s eight replies, JsonOutputParser raises on 1 and returns 4 unusable results; PydanticOutputParser with the passage ids as a Literal raises on 5 and returns none. Both give the same 3 usable answers.

Mental model

The prompt template and the parser are where your code meets the model’s text. The template decides what the model reads; the parser decides what reaches the rest of your program, and whether a malformed reply arrives as an exception or as a value that looks fine.

The 1.x package split

Lesson 7.1: LangChain introduction and the 1.x package split. Notebooks: 01a_LangChain_Introduction.ipynb, 01b_Package_Split_and_Imports_LangChain_v1.ipynb

Through the 0.x releases, the langchain package held the whole ecosystem: chains, agents, memory, retrievers, every provider integration and the prompt hub. Installing it pulled in all of that, and a break in any one integration could break the import. Version 1.0 split the surface by how fast each part changes and by who owns it:

Package Holds Changes
langchain-core messages, documents, prompts, output parsers, Runnable rarely, deliberately
langchain the agent loop and short re-exports such as init_chat_model with the agent API
langchain-openai, langchain-groq, … one provider each at that provider’s pace
langchain-classic retired chains, retrievers, indexing, the hub frozen

Everything else in this module comes from langchain-core: the prompt template classes, the message classes and all four output parsers. Only the model class comes from a partner package (langchain_openai.ChatOpenAI), or from langchain.chat_models.init_chat_model when the provider is named in a string.

The first notebook already shows the shape every later chain keeps: prompt | llm | StrOutputParser(), a template, a model and a parser joined with LCEL’s |. M08 covers the pipe itself; the next pages of this module cover the three parts.

Reading an import error

Old code fails on 1.x in two different ways, and the exception class says what moved. Checked against the course environment (langchain 1.4.7, langchain-core 1.7.0):

  • from langchain.chains import LLMChain raises ModuleNotFoundError: No module named 'langchain.chains'. The module is gone, so the fix is a new path: langchain_classic.chains, or a rewrite as an LCEL chain (M08).
  • from langchain import hub raises ImportError: cannot import name 'hub' from 'langchain'. The package still exists; it no longer exports the name. Import it from langchain_classic instead.
  • No module named 'langchain_classic' is a third problem: the package is not installed in this environment. uv add langchain-classic declares it in pyproject.toml and installs it.

The short paths that langchain keeps are aliases. langchain.messages.HumanMessage is langchain_core.messages.HumanMessage returns True; the notebook reads a False as two LangChain installs on sys.path.

Memory is the one place where the moved class is not the recommended answer. ConversationBufferMemory still imports from langchain_classic.memory, but the 1.x replacement is a LangGraph checkpointer with a thread_id (M10, M33).

Version 1.0 split the surface by how fast each part changes and who owns it: langchain-core changes rarely, each partner package moves at its provider’s pace, and langchain-classic is frozen.

It runs, but it is not the recommended answer. The class still imports from langchain_classic.memory; the 1.x replacement is a LangGraph checkpointer with a thread_id (M10, M33). Memory is the one place where moving the import is not the fix.

Chat models

Lesson 7.2: Commercial LLMs natively and with LangChain. Notebooks: 02a_Commercial_LLMs_with_LangChain.ipynb, 02b_Commercial_LLMs_Natively.ipynb (optional)

A chat model is any class that implements LangChain’s BaseChatModel interface. The provider SDKs in the optional notebook (and in M02) each return their own response object; the LangChain classes return the same one for every provider. Every chat model has the same three calls:

Call Takes Returns
invoke a string, a message list or a PromptValue one AIMessage
batch a list of inputs a list of AIMessage, run concurrently on a thread pool
stream one input the reply in chunks as it arrives

The AIMessage carries more than the text. Lesson 7.2 reads three attributes:

  • .content: the reply text.
  • .usage_metadata: input, output and total token counts, under the same keys for every provider.
  • .response_metadata: what the provider reported, such as model_name and finish_reason. On OpenAI a finish_reason of length means the reply hit the token limit and stopped mid-sentence, or mid-JSON; lesson 7.6 shows what the parsers make of that.

Changing provider changes one class. In the notebooks the same prompt | model chain runs on all of these:

Class Where the model runs Model in the notebook
ChatOpenAI OpenAI’s API gpt-4o-mini
ChatGoogleGenerativeAI Google’s Gemini API gemini-2.5-flash
ChatGroq Groq’s hosted inference llama-3.1-8b-instant
ChatHuggingFace over HuggingFaceEndpoint Hugging Face Inference Providers moonshotai/kimi-k2-instruct-0905
ChatHuggingFace over HuggingFacePipeline your own machine TinyLlama/TinyLlama-1.1B-Chat-v1.0

The last three come from lesson 7.3’s 03a_Open_Source_LLMs_with_LangChain.ipynb. ChatHuggingFace is a wrapper: the two Hugging Face classes underneath are completion-style LLMs, and the wrapper gives them the chat interface (lesson 7.4).

init_chat_model moves the choice out of the import line and into a string, which is how notebook 01b loads its model:

from langchain.chat_models import init_chat_model
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_template("Explain {topic} in 2 bullet points")
llm = init_chat_model("openai:gpt-4o-mini", temperature=0)
# llm = init_chat_model("groq:openai/gpt-oss-120b", temperature=0)

reply = (prompt | llm).invoke({"topic": "AI"})   # an AIMessage

The swap keeps the code running. It does not keep the replies the same: another model formats, refuses and rambles differently. For Larkspur, a provider change is a release like any other, checked against the golden questions from M11 before it ships.

Check yourself

1. What does a LangChain chat model give you that calling each provider SDK directly does not?

The same response object for every provider. Each SDK returns its own object, while every BaseChatModel offers invoke, batch and stream and returns an AIMessage, with token counts under the same keys in .usage_metadata. Changing provider then changes one class.

2. A Larkspur reply on OpenAI stops mid-JSON, and its response metadata shows a finish reason of length. What happened?

The reply hit the token limit and stopped mid-sentence, or here mid-JSON. .response_metadata reports what the provider said, and finish_reason of length is OpenAI’s signal for it. Lesson 7.6 shows what each output parser makes of such a truncated reply.

3. You change the init_chat_model string from an OpenAI model to a Groq model and the chain still runs. Can you ship the change?

Not yet. The swap keeps the code running, but another model formats, refuses and rambles differently, so the replies change. For Larkspur, a provider change is a release like any other, checked against the M11 golden questions before it ships.

Messages

Lesson 7.4: Inputs and outputs: messages, LLM vs chat model. Notebooks: 04a_LangChain_Inputs_and_Outputs.ipynb, 04b_LLM_vs_ChatModel.ipynb

A chat model reads a list of messages, each with a role:

Class Role Holds
SystemMessage system the instructions for the whole conversation
HumanMessage user what the user said
AIMessage assistant a reply from the model, including earlier replies you send back

The OpenAI-style spelling, {"role": "user", "content": "..."}, works too: LangChain converts each dict to the matching class before the call (convert_to_messages shows the result). Tool results add a fourth class, ToolMessage, in M23.

A chat model keeps no state between calls. To continue a conversation, the app appends the model’s AIMessage and the next question to the list and sends the whole list again:

In notebook 04a, “What did we discuss so far?” gets an answer only because the earlier turns are in the list. Two consequences follow for Larkspur’s assistant. Every earlier turn is paid for again as input tokens on every call, so history needs a bound (M33). And the history is just data your app holds, so it can be trimmed, summarised or filtered before it is sent. In a template, history goes in a MessagesPlaceholder (lesson 7.5).

For several conversations at once, .batch() takes a list of inputs and returns a list of AIMessage. The older .generate() takes a list of message lists and returns an LLMResult, whose generations is a nested list (one entry per conversation) and whose llm_output["token_usage"] sums the batch.

LLM vs chat model

LangChain has two model interfaces:

Interface In and out Classes in notebook 04b
BaseLLM a string in, a string out OpenAI (gpt-3.5-turbo-instruct), HuggingFaceEndpoint, HuggingFacePipeline
BaseChatModel messages in, an AIMessage out ChatOpenAI, ChatGoogleGenerativeAI, ChatHuggingFace

Both accept both shapes, because LangChain first turns the input into a PromptValue and then asks it for the shape the model needs. With langchain-core 1.7.0 (empty fields left out of the printout):

from langchain_core.messages import HumanMessage, SystemMessage
from langchain_core.prompt_values import ChatPromptValue, StringPromptValue

StringPromptValue(text="How long does a refund take?").to_messages()
# [HumanMessage(content='How long does a refund take?')]

ChatPromptValue(messages=[
    SystemMessage("Answer only from the passages."),
    HumanMessage("How long does a refund take?"),
]).to_string()
# 'System: Answer only from the passages.\nHuman: How long does a refund take?'

A string sent to a chat model becomes one HumanMessage, so nothing is lost. A message list sent to a completion model is flattened into System: and Human: lines of plain text, which the model continues like any other text; the system instruction becomes a hint instead of a role it was trained to follow. That is why every chain in this course uses a chat model, and why a completion model appears only in notebook 04b, for contrast.

Prompt templates

Lesson 7.5: Prompt templates and few-shot composition. Notebooks: 05a_Prompt_Templates.ipynb, 05b_Few_Shot_Composition_and_Serialization.ipynb (optional)

A prompt template is a function from variables to a prompt. It has {slots} filled with Python’s str.format syntax, and it comes in two kinds:

Class Produces Use with
PromptTemplate a StringPromptValue: one string completion models, or one human message
ChatPromptTemplate a ChatPromptValue: a list of role-tagged messages chat models, and anything with a system prompt or history

Both work with a chat model, because a string becomes one HumanMessage (lesson 7.4). ChatPromptTemplate.from_template("Explain {topic}") is exactly from_messages([("human", "Explain {topic}")]); the notebook compares the two and gets the same messages. Use from_messages whenever there is a system prompt.

Three calls fill a template. .format() returns a plain string; .format_prompt() and .invoke() return the PromptValue. .invoke() takes a dict, and it is the call an LCEL chain makes for you.

The Larkspur answer prompt, with a slot for the parser’s format instructions and one for the conversation so far:

from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

prompt = ChatPromptTemplate.from_messages([
    ("system", "Answer from the Larkspur Cloud handbook passages only.\n{format_instructions}"),
    MessagesPlaceholder("history"),
    ("human", "Passages:\n{passages}\n\nQuestion: {question}"),
])
prompt.input_variables
# ['format_instructions', 'history', 'passages', 'question']
prompt.partial(format_instructions=parser.get_format_instructions()).input_variables
# ['history', 'passages', 'question']

.partial() fills a slot once, at build time, so callers never pass it. MessagesPlaceholder takes a whole list of messages at call time, which is where the history from lesson 7.4 goes.

Two of these template mistakes raise and two pass without a word. Each was checked against langchain-core 1.7.0:

Mistake What happens
A typo in the input_variables you pass The list is recomputed from the template text and the typo disappears. Only validate_template=True raises.
A variable left out at format time KeyError names it. This one is loud.
Literal JSON braces in a template, {"answer": ...} "answer" becomes a variable, and formatting raises KeyError. Double the braces: {{"answer": ...}}.
.partial() for a slot the template does not have Ignored without an error; the value never reaches the model (lesson 7.6 shows this in a course notebook).

Printing input_variables and the formatted messages once, before the first model call, catches the silent pair.

Few-shot and composition

Examples in the prompt steer both the answer and its format. Notebook 05b puts nine labelled reviews into one template string; the classes keep examples as data instead:

  • FewShotPromptTemplate formats a list of example dicts with an example_prompt and adds a suffix holding the real input. Adding an example is appending a dict.
  • FewShotChatMessagePromptTemplate (optional notebook 07e_prompt_templates_all.ipynb) turns each example into a human message and an AI reply, and slots the block into a ChatPromptTemplate between the system prompt and the question.

For Larkspur, one or two examples of a question, its passages and the exact JSON answer show the model the citation format better than a description of it. Examples written inside a template string need their braces doubled, as in notebook 05b.

Templates compose with +. Adding two PromptTemplate objects concatenates the text and merges the variables: a passages part plus a question part gives one template with ['passages', 'question']. ChatPromptTemplate objects add the same way, message list to message list. PipelinePromptTemplate, the 0.x class for this, is in neither langchain-core 1.7.0 nor langchain-classic.

A template is data, so it can be versioned like code. In 1.x, dumps and loads from langchain_core.load save and restore it as JSON. loads takes allowed_objects=[PromptTemplate]: deserialising rebuilds objects from the file’s contents, so you name the classes you trust. The older .save() still runs and warns that it was deprecated in langchain-core 1.2.21 and will be removed in 2.0.0.

Output parsers

Lesson 7.6: Output parsers. Notebooks: 06a_Output_Parser.ipynb

An output parser is the last step of a chain, prompt | llm | parser. It works in two places: before the call, get_format_instructions() returns text that goes into the prompt; after it, parse() turns the reply text into a Python value or raises OutputParserException.

Parser Returns Raises when
StrOutputParser the reply text never
CommaSeparatedListOutputParser a list of strings never; "Sure: a, b" becomes ['Sure: a', 'b']
JsonOutputParser whatever JSON it finds, usually a dict it finds no JSON it can repair
PydanticOutputParser an instance of your model no JSON, or the JSON fails the model’s validation

JsonOutputParser is more forgiving than its name suggests. In langchain-core 1.7.0 it strips whitespace and backticks, looks inside a ```json fence, and when the JSON is incomplete it closes open strings and brackets and drops trailing characters until something parses. PydanticOutputParser runs that same JSON step, then validates the result against the schema. A parser only checks what the schema states, and a reply can be valid JSON and still wrong.

The interactive lab runs eight representative replies to the Larkspur refund question through four parsers. The replies are hand-written, since no model was called; the parsers are JavaScript ports of the library code, which agree with langchain-core 1.7.0 and Pydantic 2.14.1 on all 4,452 checks (1,113 reply texts, including every truncation of the eight replies, times four parsers). Its counts:

Parser Raised Returned, unusable Usable
StrOutputParser 0 8 0
JsonOutputParser 1 4 3
PydanticOutputParser, list[str] ids 3 2 3
PydanticOutputParser, Literal ids 5 0 3

“Usable” is the lab’s own rule: an answer string and at least one citation that names one of the three passages. The table shows four things:

  • The usable count never moves. Three replies are good (clean, fenced, and one with a trailing note, which the repair step drops) and every parser that reads fields accepts them. A stricter parser does not produce more good answers; it moves bad ones from the returned column to the raised column, where a retry or a fallback can catch them.
  • JsonOutputParser raises on one reply only: the one with prose before unfenced JSON. It returns the truncated reply, the reply with no citations key, the one with citations as a string and the one with an invented id, each as an ordinary dict.
  • list[str] stops the shape errors but not the made-up ids. The missing key and the string raise; "refund-win" (a truncated id) and "handbook-p4" (an invented one) are strings, so they pass.
  • A Literal of the passage ids raises on all five. The schema now states the rule the lab grades by.

Truncation is where the repair step matters most. Cutting the clean 124-character reply at each of its 125 lengths, as a max_tokens limit would: JsonOutputParser raises on 1 cut (the empty one) and returns a dict for the other 124, of which 4 are usable. PydanticOutputParser with list[str] raises on 107 and returns 14 unusable answers, such as a citation cut to "refund-t". With Literal ids it raises on 120; the one unusable cut it lets through is "citations": [], cut just after the bracket, which no Literal can catch. A min_length=1 on the list would catch it, at the cost of refusing an honest “the handbook does not say” with no citations.

The schema behind the Literal row:

from typing import Literal
from pydantic import BaseModel, Field
from langchain_core.output_parsers import PydanticOutputParser

PassageId = Literal["refund-window", "refund-timing", "billing"]

class CitedAnswer(BaseModel):
    answer: str = Field(description="The answer, using only the passages")
    citations: list[PassageId] = Field(description="Ids of the passages the answer uses")

parser = PydanticOutputParser(pydantic_object=CitedAnswer)
chain = prompt.partial(format_instructions=parser.get_format_instructions()) | llm | parser

The three ids are fixed here because the lab has one question. In a live pipeline the retrieved ids change per question, so either build the Literal per request or check the ids against the retrieved set right after parsing. The check has to exist somewhere; the lab shows what happens where it does not.

Check that the instructions arrive

Format instructions only help if they reach the model. The prompt needs a {format_instructions} slot, filled with .partial() or partial_variables, as notebook 06a does. The instructions are long: for the two-field schema, the lab measures 748 characters from PydanticOutputParser and 1,301 from JsonOutputParser(pydantic_object=...), sent as input tokens on every call.

The optional notebook 07f_output_parsers_demo.ipynb shows the silent version of this mistake. Its PydanticOutputParser example calls .partial(format_instructions=...) on a template with no {format_instructions} slot. LangChain ignores the value without an error, so the model never sees the schema, and the chain works only when the model happens to produce matching JSON from the one-line request. Printing the formatted prompt once shows whether the schema is in it.

Structured output

Lesson 7.7: LangChain 1.x recap course, ending in a structured-output Q&A bot. Notebooks: 07a_smart_bot_section1.ipynb, 07f_output_parsers_demo.ipynb (optional), 07g_output_parsers_final.ipynb (optional)

llm.with_structured_output(Schema) returns a new runnable that outputs an instance of the schema. Unlike a parser, it sends the schema to the provider with the request instead of writing it into the prompt, and providers that support structured output constrain the reply to it. Notebook 07g’s advice is to prefer it over PydanticOutputParser for any model that supports it.

PydanticOutputParser with_structured_output
Where the schema goes into the prompt, as format instructions (748 characters for the lesson 7.6 schema) to the provider’s API
Which models any model that follows instructions models with structured-output or tool-calling support
Prose around the JSON, fences, trailing notes repaired or raised by the parser not produced when the provider constrains the reply
Values the schema allows but your app does not pass pass

The last row is the same for both. A schema bound to the model still lets through a made-up passage id if citations is list[str], so the lesson 7.6 rule holds: put every rule you can into the schema, with Literal for ids and fixed labels.

Notebook 07a builds SmartQABot on this: a ChatPromptTemplate with a system prompt and a {question} slot, piped into ChatOpenAI(...).with_structured_output(QAResponse). QAResponse has five fields: answer, confidence, reasoning, follow_up_questions and sources_needed. Two of its choices are worth copying, and two are worth fixing before Larkspur uses the pattern:

  • Copy: a fallback object. ask() catches any exception and returns a valid QAResponse with confidence="low" and the error in reasoning, so the caller always gets the same type back.
  • Copy: tracing. @traceable sends every call to LangSmith when LANGSMITH_API_KEY is set, so a bad answer can be traced to its exact prompt and reply.
  • Fix: confidence is a str. Its description asks for high, medium or low, but nothing enforces it; Literal["high", "medium", "low"] would.
  • Fix: ask_batch() has no fallback. It calls chain.batch(inputs), and by default batch raises the first exception and loses every result. Checked with a three-input batch whose middle input fails: plain batch raises, batch(..., return_exceptions=True) returns the two results with the exception in place of the middle one.

For the lab brief, the same shape answers Larkspur’s refund question: CitedAnswer from lesson 7.6 as the schema, the three passages and the question in the human message, and a fallback that says the handbook could not be checked instead of guessing.

Check yourself

1. How does with_structured_output differ from the Pydantic output parser in where the schema goes, and what does that buy?

It sends the schema to the provider’s API with the request instead of writing it into the prompt as format instructions (748 characters for the lesson 7.6 schema). Providers that support structured output constrain the reply to it, so prose around the JSON, fences and trailing notes are not produced.

2. You bind CitedAnswer with citations typed as a list of strings to the model. Can it still return a made-up passage id?

Yes. A schema bound to the model still passes any value the schema allows, and any string is allowed. The lesson 7.6 rule holds for both approaches: put the rule into the schema, with Literal for passage ids and fixed labels.

3. SmartQABot's ask_batch sends three questions and the middle one fails. What does the caller get, and how do you fix it?

An exception and no results, because batch raises the first exception by default and loses every result. batch(..., return_exceptions=True) returns the two good results with the exception in place of the middle one, which a fallback like the one in ask() can then replace.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions in the style of OpenAI, Anthropic and Google interviews for applied AI roles.

1. Larkspur’s refund answers start failing: about one request in fifty raises OutputParserException after a model upgrade. The previous model never did. Where do you look first?

What a strong answer covers:

  • Pulls the raw AIMessage.content for failed requests before changing any code; the exception’s llm_output holds what the parser saw
  • Sorts the failures by shape: prose before the JSON, a truncated reply (finish_reason of length in response_metadata), a missing field, a wrong type
  • Fixes each shape at its cause: a token limit for truncation, the schema description for a wrong type, with_structured_output where the provider supports it
  • Adds the failing replies to a parser test set, so the next upgrade is checked against them before it ships

2. The answer must cite the passages it used. A teammate proposes JsonOutputParser because it “never breaks”. Do you agree?

What a strong answer covers:

  • JsonOutputParser rarely raises because it repairs text: it strips fences, drops trailing prose and closes truncated JSON, so a cut-off reply arrives as a dict with a half-written citation
  • An exception is the cheaper failure: it can be retried or logged, while a wrong dict reaches the customer
  • Puts the rules in a schema: citations as a list of the retrieved passage ids (a Literal or a post-parse check), answer as a required string
  • Keeps a fallback for the raise, as the lesson 7.7 bot does, and counts how often it fires

3. How do you monitor the structured-answer step in production?

What a strong answer covers:

  • Rate of OutputParserException per model and per prompt version, with the raw reply logged for each one
  • Rate of answers whose citations are not among the retrieved passage ids, checked in code after parsing
  • Token counts from usage_metadata, split into input and output, because format instructions and history grow the input side
  • Share of replies with finish_reason of length, which predicts truncated JSON before the parser sees it

4. A customer asks “How long does a refund take?” and then “And for annual plans?”. The second answer ignores the first turn. What happened, and how do you fix it without the prompt growing forever?

What a strong answer covers:

  • Chat models keep no state; the second call saw only the second question unless the app resent the first turn and the reply
  • Puts history in a MessagesPlaceholder and appends the AIMessage after each turn
  • Bounds the history: keep the last few turns, or summarise older ones (M33), and measures the input-token cost per turn
  • Rewrites the follow-up into a standalone question before retrieval, because the retriever needs “annual plans” and “refund” in one query (M33)

5. You move the refund assistant from gpt-4o-mini to a Groq-hosted open model to cut cost. The chain code does not change. What can still break?

What a strong answer covers:

  • The call shape survives a swap (init_chat_model("groq:…") or ChatGroq), the replies do not: format compliance, refusal style and verbosity can all change
  • with_structured_output depends on the provider’s structured-output or tool-calling support; check it before relying on it, or fall back to a parser
  • Re-runs the golden questions from M11 and the parser test set, and compares usable-answer rate, citation validity, tokens and latency
  • Keeps the provider in configuration (a "provider:model" string) so a rollback is a config change

Key Takeaways

  • Import from langchain_core for prompts, messages and parsers, and from a partner package for the model. A ModuleNotFoundError on an old path means the module moved; an ImportError means the name did.
  • Send the conversation every time. The model remembers nothing between calls, and every resent turn costs input tokens.
  • Build prompts from templates with explicit slots, and check input_variables and the formatted messages before the first model call.
  • Pick the parser for which failures you want to see. Put every rule you can into the schema, so a bad reply raises instead of passing.
