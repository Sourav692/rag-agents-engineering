## Current operating model: Option A (this repo is canonical)

Since 1 Nov 2026 this repository is the only place the course is maintained. Edit notebooks, helpers and data here, directly. The nine source repos are archived with a README pointing here, so a fix made there reaches no one. `scripts/migrate.py` is retired and exits at once: it built the v1 `course/` tree, which no longer exists.

Since 8 Nov 2026 (Phase 6, [plan/phase-6-switch.md](plan/phase-6-switch.md)) the course is the v2 curriculum in part folders. The v1 trees `course/` and `theory/` are deleted; git history has them.

## Layout

```
<part>/                                   e.g. p07_advanced_agents/
  README.md                               generated: the part's modules
  <module>/                               e.g. m26_coding_computer_use_and_deep_agents/
    README.md                             generated: objectives, lessons, tiers, sources
    assets/  projects/                    where the module has them
    lab/
      README.md                           brief, how to run, data, results
      data/                               the lab's data, with a README.md naming each file's source and licence
      solution/m<NN>_solution.ipynb       the lab solution (plus small files it needs), outputs cleared
    mandatory/
      notebook/                           mandatory items and their helper files
      theory/                             module page, index.html, module diagrams, pages of lessons with a mandatory notebook
    optional/
      notebook/                           alternate, platform-specific, extension and exercise items
      theory/                             pages of lessons whose notebooks are all optional
```

- Every module has all four tier folders; an empty one holds `.gitkeep`.
- A lesson's tier is `optional` when it has notebooks and none is mandatory; otherwise `mandatory` (lessons with no notebook too). `lesson_tier()`, `lesson_dir()` and `lesson_pages()` in `scripts/curriculum_lib.py` give the paths.
- Lab rules: a solution reads data only from `../data/` and may import from `src/` (`src/lab_kit.py` has the metrics and the TF-IDF baseline); it never reads `data/`, another module's folder or another lab's output. Lab data is at most 5 MB per lab. The shared corpus, `data/larkspur/`, is copied unchanged into `lab/data/larkspur/`. Numbers in a lab README come only from a real run of its solution, with the date and the models used. `tests/test_labs.py` checks these rules.
- The build never writes under `lab/`, and never writes a theory page.

### Editing the curriculum

Edit `curriculum.yaml`, then run `scripts/build_curriculum.py` and `uv run pytest -q`. Moving or renaming a notebook means `git mv` in the part folder as well as changing its `folder` or `file`; `test_every_curriculum_item_exists` fails until both agree.

- Each lesson item has `source` (`<key>:<path in the source repo>`, provenance only), `tier`, `folder` and `file`. Modules keep `previous_num`, lessons `previous` (`"24.5"`) and parts `previous_title`: where each piece was in the v1 curriculum.
- `tier` is `mandatory`, `alternate`, `platform` or `extension`. Mandatory items go in `folder: mandatory/notebook`; optional ones (exercises included) in `optional/notebook`.
- `file` names start with the lesson number and a letter (`03b_...` is lesson 3, second item), so a lesson's mandatory and optional notebooks sort side by side.
- `folder` may add a subfolder (e.g. `mandatory/notebook/05_training`) when a lesson's companion files would clash with another lesson's; the fine-tuning lessons in M45 use this. Sub-projects use `folder: projects` and keep their source names, because notebooks write into `../projects/<name>/`.
- Every `.ipynb` in a part folder, outside `lab/`, must appear in exactly one lesson. `tests/test_course.py` enforces this.
- Module text uses resolved module numbers (`M20`). If modules are renumbered, update those references.
- Generated docs never hard-code module numbers: `build_curriculum.py` and `build_docs.py` look modules up by `key`, so renumbering only needs a rebuild. `docs/agentic-architectures.yaml` names notebooks by source path and modules by key for the same reason; the build fails if one is no longer placed.
- Renaming a part, module or lesson means `git mv` on its folder (and on its lesson theory folder); the tests fail until you do.

## Theory pages

Concept explanations with diagrams live inside each module, beside its notebooks, with one folder per lesson:

```
<part>/<module>/mandatory/theory/
  README.md                               module page: overview, lesson list, interview questions, takeaways
  index.html                              generated: the module page and its lesson pages as one HTML page
  diagrams/*.anim.html                    animated SVG fragments (also inside lesson folders)
  <NN>_<slug of lesson title>/            a lesson with a mandatory notebook, e.g. 02_indexing_from_scratch_with_tf_idf_and_nearest_neighbours/
    README.md                             lesson page: that lesson's key concepts
    diagrams/*.svg                        static diagrams Mermaid cannot draw (spatial layouts, charts)
    interactive/*.html                    labs: one self-contained HTML file each, opened locally in a browser
<part>/<module>/optional/theory/
  <NN>_<slug of lesson title>/            a lesson whose notebooks are all optional, same contents
```

- **Writing a module:** use the project skill `theory-module` (`.claude/skills/theory-module/`, run as `/theory-module <module> [lesson or topic]`). It resolves the module, plans concepts per lesson, writes the pages, diagrams and lab in the M10 format, and runs every check below. M10 (`p04_rag_foundations/m10_rag_lifecycle/`) is its reference build.
- **Names:** `theory_dir()` (the module page's folder), `lesson_dir()` and `lesson_folder()` in `scripts/curriculum_lib.py` give the paths; `NN` is the lesson's position in the module (`lesson_folder(3, "NumPy, pandas and Matplotlib")` is `03_numpy_pandas_and_matplotlib`). Renaming a lesson in `curriculum.yaml`, or changing whether it has a mandatory notebook, means `git mv` on its theory folder; the test fails until you do.
- **Module page outline:** a header line in italics (`Part <numeral> · <part title>`, then links to the module README and to `THEORY.md`), TL;DR, mental model, a `## Lessons` table linking each lesson page (*planned* for lessons without one), the interactive lab, how it connects, an Interview Spotlight with 5 production questions, key takeaways.
- **Lesson page outline:** a header line with the module page, lesson number and notebooks, then one `## <concept>` section for each of the module's `concepts:` taught in that lesson (exact text, so the generated READMEs and the syllabus site can link to the anchor), a `## Key Takeaways` section (three bullets, four when the page has four or more concepts, drawn only from the page), a `## Check yourself` section, and a previous/next footer. Check yourself has three questions, each a `<details>` block whose `<summary>` is the numbered question (plain text, no Markdown or module codes) and whose body is a short answer drawn from the page; `test_lesson_pages_end_with_check_yourself` checks the shape, and `build_theory_html.py` renders the answers' Markdown. Each concept is a `##` heading on exactly one page of the module.
- **One HTML page per module, always:** `scripts/build_theory_html.py` (run by `build_curriculum.py`) renders every module that has a module page into `<module>/mandatory/theory/index.html`: the module page with its `## Lessons` table replaced by the lesson pages (from both tier folders) in lesson order, each under a "Lesson N.M: title. Notebooks: …" line, in the Almanac design from `scripts/site/theory.template.html`. Never write a per-lesson HTML page, a multi-module HTML page or an `index.html` by hand; edit the READMEs and rebuild. Labs and SVGs are linked relatively, so the page works opened from disk; notebooks and Markdown pages link to GitHub; Mermaid loads from jsdelivr, and offline the diagram source shows instead. A new module gets its page from the same template, so a design change goes in the template and reaches every module. Lint the template's output with Hallmark's `sloplint --genre editorial --render` on a copy of the part folders outside the repo (so the relative SVGs load); its waivers live in the template's stamp.
- **Labs inside the module page:** a `<!-- lab: interactive/<name>.html -->` line in a lesson page (invisible on GitHub) embeds that lab at that spot in `index.html`: a lazy frame, an "Open full screen" link to the standalone file, and a focus ring the page script sets. Put it in the section whose claims the lab tests (M10: after the top-k bullets). The lab file stays the one source and still opens on its own. A lab is embeddable only once it has an embedded mode: a head script adds `embedded` to `<html>` when `window.self !== window.top`; `html.embedded` rules hide its bar and intro, drop the inner scrollbar and order its parts so the control and its main output share a screen in a ~700px column; and a `ResizeObserver` posts `{ labHeight }` to the parent, which sizes the frame. M10's top-k lab has it; add it to a lab before you mark its lesson.
- **Animated diagrams:** an animated version of a Mermaid diagram is an SVG fragment in `diagrams/<name>.anim.html`, named by an HTML comment on the line after the Mermaid block (`<!-- animated: diagrams/<name>.anim.html -->`, invisible on GitHub). `build_theory_html.py` draws each fragment in place of its diagram in `index.html`, with the controller from `scripts/site/theory-anim.{css,js}`; the README keeps the Mermaid version, since GitHub cannot run the animation. Animate only diagrams that show a process over time (a pipeline, a loop); decision trees and charts stay static. Each fragment: inline SVG coloured only through the page tokens, steps marked with the `in-N`, `mv-N`, `n-N`, `e-N` classes, Previous, Play and Next buttons, and a numbered step list whose buttons are the short step names. It plays itself while on screen, never under reduced motion, and shows its finished frame without script. Use the lab's real numbers or none. GIFs are for social posts only; export them from the SVG rather than drawing them. M10 has the first two (the lifecycle and the baseline loop).
- **Diagrams:** Mermaid inline first (it renders on GitHub and diffs cleanly); SVG in `diagrams/` with its own light background; HTML labs only when a parameter is worth playing with.
- **Labs:** built with the Hallmark skill in its Almanac theme (slate paper, a pale printed sheet for tables and charts, Hanken Grotesk heads, Newsreader text, IBM Plex Mono for figures and code, one deep magenta for the evidence or answer mark). Each lab is one self-contained HTML file: the Hallmark stamp, the Almanac tokens and inline JS, with Google Fonts the only external request. Keep new labs in that system and run Hallmark's `sloplint --scope app --render` on a copy outside the repo, because it writes `.hallmark/` beside the file. Run the real algorithm in JS when it is small (TF-IDF, recursive splitting) and check it against the Python library before publishing; label hand-written outputs as representative.
- **Diagrams in SVG** use the same Almanac colours as hex (sheet `#e5eaef`, ink `#060e15`, muted `#3b434b`, magenta `#970d63`).
- **Running example:** the fictional Larkspur Cloud handbook, shared across pages.
- **Links:** theory pages link to notebooks by their part-folder path and to modules by number; `check_links.py` catches a broken path after renumbering, but update module and lesson numbers in the prose by hand.
- **Build:** `build_curriculum.py` adds a Theory section and concept anchors to the module README and the site card for every module that has a module page, links each lesson row to its lesson page, and regenerates `THEORY.md`. `test_theory_pages_sit_in_their_tier_folders` checks that every theory page is a module page or a lesson page in its tier folder, that each concept heading appears once, that the module page links every lesson page, and that every lab is linked from the page beside it; `test_theory_module_pages_have_a_current_index_html` fails when a module's `index.html` is missing or older than its READMEs.

## forwarddeployedprep.com export

The theory pages are also the AI Engineering topic of forwarddeployedprep.com (plan: `.website_plan/2026-10-31-ai-engineering-integration-plan.md`, local only). Three hand-maintained files feed it: `docs/fde-site-slugs.yaml` (frozen site ids; never change a published slug, even when a title changes or a lesson moves to another module: move its entry instead), `docs/fde-site-copy.yaml` (track copy) and `docs/fde-site-mistakes.yaml` (one to four common mistakes per module, each drawn from that module's Check yourself questions; update it when those change). `scripts/export_site_curriculum.py --out <site>/site/src/lib/rag-tracks.ts` writes the site's curriculum data; the site's `npm run import:rag-theory -- --from <this repo>` vendors the pages (its importer read the v1 `theory/` tree and must be pointed at the part folders). Both are deterministic, and tests fail when a part, module or lesson has no slug. The v1 tracks `ingest` and `apps` stay in the slugs file, unused, so their slugs are never reused.

## How the migration transformed files (history)

What `migrate.py` did to every file it copied into the v1 `course/` tree (`course/<part>/<module>/<folder>/`, folders `notebooks`, `optional`, `exercises`, `projects`). Phase 6 moved those files into the part folders at the same depth, so the paths and companion files below still explain what you see.

- **Depth:** notebooks moved from `modules/<m>/notebooks/` to `course/<part>/<module>/<folder>/`, one level deeper. `../../../data/`, `../../../src` and `../../../docs/` were rewritten to the new depth; source docs went to `docs/source/<key>/`.
- **Links and `%run`:** relative links and `%run` targets that point to another source notebook, module README or asset were rewritten to the new course path. Links to content outside the course (e.g. the planned CacheRAG module) point to the source repo on GitHub.
- **Companion files:** non-notebook files that sit beside a notebook in the source (`helper_functions.py`, `hotel_common.py`, `evaluation/`, `docker-compose.yaml`, …) were copied beside it, so imports work unchanged.
- **Assets:** `modules/<m>/assets/` from every contributing source module was merged into the destination module's `assets/`.
- **Shared code:** `src/helpers/` was identical in 05, 08, 09 and 10. `src/rag_paths.py` comes from 05; its asset roots point at the part folders.
- **Data:** `data/` from all repos was merged (only the READMEs collided; they are archived as `docs/source/<key>/data-README.md`).
- **Environment:** `.env.example` is the union of the source repos' files, each key annotated with the repos that use it.
- **RAG Techniques helpers** live once, in `src/rag_techniques/` (`helper_functions.py`, `evalute_rag.py`). The copies beside the notebooks are one-line shims that re-export them, so `from helper_functions import *` and `from evaluation.evalute_rag import *` work unchanged. Fix helpers in `src/rag_techniques/`, never in a shim.

## Dependency notes

- One environment for the whole course: `uv sync`, plus groups per need (see `README.md`).
- `pandas>=2.2`: repos 06 and 08 asked for `>=3.0.5`, but `llama-index` (the `llamaindex` group) needs `<3`.
- `hf` and `hf-foundations` cannot share an environment with `colpali` (`byaldi` pins `transformers<5`); declared as uv conflicts.
- `finance` (OpenBB) pins old `uvicorn`/FastAPI releases, so it conflicts with `protocols`, `mcp-labs` and `mcp-apps`; the MCP and A2A SDKs live in the `protocols` group rather than the default dependencies for this reason.
- Repo 02 pins LangChain 0.3 and `openai<2`; this repo uses LangChain 1.x and `openai>=2`. Its one LangChain-0.3-specific import (`AgentExecutor`) falls back to `langchain_classic`, so its notebooks run here too.
- `grouse` (evaluation cells in M31) cannot coexist with this stack; use a separate environment, as in repo 09.
