Open the lab

The module’s lessons are runnable projects, not notebooks, and they ship without recorded output. The running example puts the Larkspur Cloud handbook from M10 to M12 behind one stdio server, larkspur-handbook, with the same retrieve(query, n) tool as the 06 project. The golden questions are the M10 ones: How long does a refund take?, Can I export my data after I cancel my plan? and What happens if my server goes down? Every library behaviour quoted here was checked against the versions in the course’s mcp-apps dependency group: mcp 1.30.0, fastmcp 3.4.11, langchain-mcp-adapters 0.3.2, mcp-use 1.7.1, langchain-chroma 1.1.0 and LangGraph 1.2.18.

TL;DR

  • A server is written once and reached by any host: Claude Desktop starts it from a config entry, an mcp_use agent on Ollama starts it from the same kind of entry, and a LangGraph app loads its tools through langchain-mcp-adapters. The host, not the server, decides how long a session lives.
  • The client decides how long a session lives, and nothing in the server’s code shows the cost. In the lab, three questions with two retrieval calls each start the server once when the client holds a session, three times with a session per question (06’s app.py) and seven times with MultiServerMCPClient.get_tools() (07’s client): 17, 27 and 47 messages on the wire.
  • Over stdio, the server’s stdout is the protocol channel. With unbuffered output, each stray print() reaches the client as a line it cannot parse; mcp 1.30.0’s client logs “Failed to parse JSONRPC message from server” and carries on, and other hosts may not be as forgiving.
  • A tool result is a contract every client reads. 06’s retrieve reports similarity_score = 1 - distance on Chroma’s default squared L2 distance, so a chunk at right angles to the query scores −1.0 and an opposite one −3.0. A client that filters on that field filters on the wrong scale.
  • The EC2 server binds 0.0.0.0 with no authentication. fastmcp’s default is 127.0.0.1:8000/mcp; changing the host publishes every tool, including one that passes a model-chosen topic name to shutil.rmtree.

Mental model

The server holds the retriever and the index; everything to its left belongs to the host. Each host picks the model, writes the queries, decides when to start and stop the server process, and reads the tool result in its own way. Two hosts can send the same question to the same server and get different answers, and the difference is almost always on the host side: a different query, a different n, or a different reading of the result.

Larkspur’s on-call engineer wants an assistant on a laptop that can check the weather at a data-centre region and do a quick sum, with no API key and no cloud model. Two ways to reach a server

The project ships two server maps. In mcp.json each entry is a command, uv run --directory …/servers weather_server.py, and the agent starts the server as a subprocess that speaks over stdin and stdout:

Figure 1: Command entry. The host owns the server’s life: it starts it, talks over stdio, and stops it.

In mcp-http.json each entry is a URL: weather at http://localhost:8001/mcp, math at :8000/mcp. You start both servers in other terminals first, and the agent connects over streamable HTTP:

Figure 2: URL entry. The servers outlive the agent, and several clients can share them.

The shipped servers fit only the second map. Their __main__ block runs mcp.run(transport="streamable-http", ...), with the stdio line commented out. Launched as a stdio subprocess, the math server started Uvicorn on port 8000 and wrote nothing to stdout, and a scratch probe with the mcp 1.30.0 client got no reply to initialize within 8 seconds. That is the engineer’s hang at start-up. Before using mcp.json, switch the servers to the commented stdio line.

Room for retries and detours

The server manager trades prompt size for turns. With two servers and six tools it costs two extra calls; with the thirteen servers of the 40.2 config it keeps dozens of tool definitions out of every prompt. Without the manager the same question needs four model calls (three tools and the answer) and fits the default of 5 with one to spare. Both clients raise max_steps to 30, which leaves room for either mode and for retries.

Return types are part of the contract

FastMCP builds a tool’s schemas from its signature. In fastmcp 3.4.11, add(a: int, b: int) -> int lists as:

Schema Fields
inputSchema a integer, b integer, both required; additionalProperties: false
outputSchema result integer, required; marked x-fastmcp-wrap-result: true

Table 2: The schemas a client receives for add, from a scratch list_tools call.

A call to add with 5 and 7 returns two things: the text 12 and the structured content {"result": 12}. The client keeps the output schema and checks every structured result against it.

The math server’s divide breaks its own schema. It is annotated -> float and returns the string "Error: Division by zero" when b is 0. The server sends that result, and the mcp 1.30.0 client raises RuntimeError: Invalid structured content returned by tool divide: 'Error: Division by zero' is not of type 'number'. The friendly message never reaches the model. The host gets an exception from its own client library instead of a tool result it could show the model.

Three ways to write divide, all called with 1 and 0 through the mcp 1.30.0 client. Pick one to see what the host receives.

Return "Error: Division by zero" from a -> float tool

The client raises RuntimeError: the string is not of type number. No tool result exists for the model to read, and the agent loop sees a crash.

raise ToolError("Division by zero")

The result arrives with isError: true and the text Division by zero. The model reads it and can tell the user or try again.

Plain a / b

Python raises ZeroDivisionError; FastMCP catches it and returns isError: true with Error calling tool 'divide': division by zero. Safe for the client, though the text exposes an internal message.

The other fix keeps the string and widens the annotation to -> float | str. The schema then accepts both, and every client must tell a number from an error message on its own. Raising keeps the error inside the protocol, where isError already says what happened.

Pitfall: a friendly error string in a typed tool. It reads well in the server’s code and never reaches the model: the client rejects it before the agent sees it.

Limits of this evidence

  • The schemas, results and exceptions come from scratch runs of the projects’ own servers with fastmcp 3.4.11 and mcp 1.30.0, over stdio, with no model. Other client libraries may handle a schema mismatch differently.
  • The step sequence in the walkthrough is structural. No Ollama model ran here, and a real model may batch tool calls, call search_mcp_tools first, or wander.
  • The mcp-use defaults and the five management tools come from the installed 1.7.1 source; later releases may change them.

Key Takeaways

  • A host reaches a server by command, starting it as a stdio subprocess, or by URL, where you start the server first. The shipped servers run HTTP, so they fit mcp-http.json; switch them to stdio before using mcp.json.
  • max_steps caps model calls, one per tool call plus the answer. use_server_manager=True keeps the prompt small but adds a connection call for each server the question touches, which pushes the three-tool question past the default of 5.
  • The return annotation is a contract the client enforces. Raise ToolError for failures instead of returning a string from a tool typed -> float.

Check yourself

1. What does use_server_manager=True change about what the model sees, and what does it trade?

The model no longer sees the servers’ tools directly. It gets five management tools and must call connect_to_mcp_server before a server’s tools appear, one active server at a time. The prompt stays small when many servers are configured, at the price of extra model turns.

2. The advanced query asks for New York's weather, its 3-day forecast and 12 times 342. Why does it fail with the default max_steps of 5?

max_steps caps model calls. With the server manager on and one call per turn, the query takes two connections and three tool calls, five calls in all, and the answer needs a sixth. The run stops before the sum is reported, which is why both clients raise the cap to 30.

3. Calling divide with b equal to 0 gives the host a RuntimeError about invalid structured content instead of a tool result. Why, and how do you fix it?

divide is annotated -> float but returns the string "Error: Division by zero", and the mcp 1.30.0 client checks structured results against the output schema. Raise ToolError("Division by zero"), which comes back with isError: true. Annotating -> float | str also works but moves the job of telling numbers from errors to every client.

What each entry decides

The config is short, and each line decides something the server’s code cannot:

  • The working directory. The host, not the server, chooses the folder a process starts in, and relative paths resolve there. The 40.4 server writes to Path(".") / "jobs"; uv --directory makes that land inside the project. That was the handbook server’s stray files.
  • Secrets, per server. notionApi gets NOTION_TOKEN in its own env block and nothing else does. excel sets a paging limit, EXCEL_MCP_PAGING_CELLS_LIMIT, to 4000 cells (lesson 40.3).
  • Which code runs. @playwright/mcp@latest takes whatever version is current at each launch, and the sqlite entry installs from a Git repository whenever uvx needs it. Pin versions for anything you depend on.
  • What the model is offered. Thirteen servers means thirteen sets of tool definitions in every request; M38 measures what connected servers cost in tokens, and lesson 40.1’s server manager is one way to hide them.

Reaching a remote server

Claude Desktop launches local commands. The config reaches the EC2 server from lesson 40.7 through a bridge, npx mcp-remote http://<EC2_PUBLIC_IP>:8000/mcp --allow-http: a local stdio process that forwards every message to the remote URL.

Figure 2: The bridge turns a URL into a command the host can start. The hop after it is plain HTTP.

The mcp-remote README allows --allow-http only on trusted private networks. Here it points at a public address, and every request and result crosses the internet unencrypted. Put the server behind HTTPS, or keep it on a private network.

Stdout belongs to the protocol

Over stdio, the host writes requests to the server’s stdin and reads responses from its stdout, one JSON-RPC message per line. The specification says a server must not write anything to stdout that is not a valid MCP message. Anything else the server writes there arrives in the same stream.

Figure 3: Two output streams. Only stdout is the protocol; stderr goes to the host’s log.

The 06 server breaks this rule. Its main() prints a banner before mcp.run(transport="stdio"), and ingest_pdf prints progress lines while it works. A scratch probe used mcp 1.30.0’s stdio client and a server that prints the same way: two banner lines at start-up and one line per file inside a tool call.

The same printing server, called once with a two-file ingest. Pick the buffering mode to see what the client received.

Unbuffered (PYTHONUNBUFFERED=1)

All four stray lines reached the client. It logged Failed to parse JSONRPC message from server four times, dropped each line and carried on. The tool result, Added 2 files, still arrived.

Default buffering

Python block-buffers stdout when it is a pipe. The prints sat in the buffer and none reached the client during the short session: 0 parse failures. The bug was there and did not show.

The Python client is forgiving. Another host may treat a bad line as a broken connection. In a longer session, such as a big ingest, the buffer fills and flushes mid-session, and the stray lines arrive then: a failure that comes and goes with the workload. The fix is the one the MCP server guide gives: keep print() out of a stdio server, and log through the logging module, whose default handler writes to stderr, or with print(..., file=sys.stderr).

Pitfall: testing a stdio server only in a short session. Buffering hides stray prints until a flush. A clean test run proves nothing about stdout.

Limits of this evidence

  • The config facts come from reading the project’s claude_desktop_config.json. No Claude Desktop instance ran here, and the host’s own handling of a bad stdout line was not tested.
  • The buffering results come from one scratch probe with the mcp 1.30.0 Python client and a stand-in server that prints like the 06 server, not from the 06 server itself, which needs Ollama and Chroma.
  • Versions taken by @latest and Git installs change over time; this page cannot say what they install today.

Key Takeaways

  • In claude_desktop_config.json, use absolute paths with uv --directory, give each server only its own secrets in env, and pin versions instead of @latest.
  • A remote server reaches a stdio host through a bridge such as mcp-remote. Keep --allow-http to trusted private networks, and use HTTPS for anything public.
  • Over stdio, stdout carries only JSON-RPC. Send logs to stderr, because buffering can hide stray prints in testing that break a stricter host.

Make the tool compute

The excel server can do the sums itself. Its README says a value written through excel_write_to_sheet that starts with = is a formula. Writing =AVERAGE(support_tickets_data!I2:I51) would let the workbook compute the average satisfaction and keep the source of the number visible in the cell:

Figure 2: Added for comparison. The model writes formulas and the workbook does the arithmetic. Each figure can be audited in its cell.

The analysis sheet holds typed strings such as 2.84/5 instead. Its seven section headings begin with = (==== EXECUTIVE SUMMARY ===), and the workbook stored them as formulas with no cached value. Read with pandas, those seven cells come back empty: the one place the run used the formula path, it did so by accident.

Three rules for analysis sessions over MCP:

  • Make the tool compute. Ask for formulas, or give the host a code or SQL tool. Each figure then has a derivation you can inspect.
  • Recompute the headline numbers before a deck leaves the room. Here that took one pandas cell and found two wrong figures and one wrong verdict.
  • Check the paging limit against the data. EXCEL_MCP_PAGING_CELLS_LIMIT is 4000 cells per read in the 40.2 config. This sheet is 612 cells with its header row, so one read covered it. A larger sheet arrives in pages, and a model that stops after the first page analyses part of the data.

Back at Larkspur, the meeting about critical tickets should be about the response-time target instead.

  • The recomputation uses pandas and openpyxl on the shipped workbook and reads the deck’s slide text; the run that produced them is not reproducible here, and its prompts are not shipped.
  • How the model arrived at 42.9% is inferred from the matching agent row and the equal ticket counts. The transcript is not available.
  • The formula behaviour comes from the excel-mcp-server README, not from running the server.

Start with one server that three people drive

Lesson 40.4: Tools, resources and prompts together. Notebooks: 05_mcp_tools_resources_and_prompts

What you’ll learn

  • Explain who triggers each of a server’s three primitives, and which of them can change anything.
  • Trace one session that uses all three, through the files they share on the server’s disk.
  • Diagnose a host that loads only tools and leaves a prompt with nothing to read.

Larkspur’s support server could offer three different things: a handbook search the model runs when it needs a fact, a customer’s plan record the agent’s screen attaches, and a “refund reply” template a support agent picks from a menu. Each has a different owner, and MCP gives each its own primitive. The Job Market Explorer server in this project is the worked case: one server with all three, and a design flaw that only shows with two users.

One server, three controllers

M38 introduced the three things a server can offer. This server uses all three at once, which shows how they divide the work. The project’s presentation names who controls each: tools are “Model-controlled”, resources “Application-controlled” and prompts “User-controlled”.

Primitive In this server Who triggers it Side effects
Tool search_jobs(role, location, max_results=5), save_job(job_id, salary=None) The model, when it decides to Calls the JSearch API on RapidAPI; writes JSON files
Resource resume://default (text from resume/resume.pdf), jobs://saved (every saved job as Markdown) The application, usually because the user attached it None: they only read
Prompt analyze_job_market(role, location, num_jobs=5), personalized_job_recommender(), create_match_report() The user, by picking it None: they return instructions

Table 1: The server’s seven features. A scratch list_tools, list_resources and list_prompts call returned exactly these.

The prompts are scripts for the model. personalized_job_recommender says to read the resume, “Call job search mcp tool”, then “Optionally call save job mcp tool on top matches”. create_match_report starts “Given the attached jobs data and resume”, and it only works once the user has attached both resources. What a tools-only host sees

Hosts differ in how much of that they support. A desktop host such as Claude Desktop (lesson 40.2) shows prompts in a menu and lets the user attach resources. A LangGraph app built with langchain-mcp-adapters 0.3.2 gets less: load_mcp_tools and MultiServerMCPClient.get_tools() load tools only. A scratch run of load_mcp_tools on this server returned search_jobs and save_job and nothing else, 2 of its 7 features.

Figure 2: In a tools-only host, resources and prompts reach the model only if the application fetches them and puts them in the conversation.

The adapter’s client has the calls: get_resources(server_name, uris=...) returns the resources as blobs, and get_prompt(server_name, prompt_name, arguments=...) returns the prompt as messages. Nothing calls them for you. An app that skips them still runs, but create_match_report arrives with nothing attached and the model writes a match report about a resume it never saw.

Two users, one temp file

The server is built for one person at a time, in two ways:

  • Hidden coupling between tools. save_job only works after search_jobs, because it reads the single file fetched_jobs_temp.json, not the results in the conversation.
  • Shared folders. Every saved job goes into jobs/saved_by_candidate/general/, and jobs://saved lists every file there. On a shared server each user’s match report reads everyone’s saved jobs.

A scratch replay ran the server’s own code over stdio, with the JSearch request stubbed to return three jobs per search. User A searched for data analyst roles and user B for nurse roles, in that order, before either saved:

Step Call Result
1 A: search_jobs("data analyst", "Leeds") Temp file holds data-0 to data-2
2 B: search_jobs("nurse", "Leeds") Temp file now holds nurse-0 to nurse-2
3 A: save_job("data-0") “Job ID data-0 not found in fetched data.”
4 B: save_job("nurse-1") Saved to general/nurse-1.json

Table 2: Two users on one server, replayed with a stubbed API. A’s job vanished because B’s search replaced the file.

The fix is to keep state per user or per request: return everything save_job needs inside the search result, or key the temp file and the saved folder by a session id. One more design point compounds the problem: BASE_DIR = Path(".") puts jobs/ and resume/ wherever the server process starts. The Claude Desktop entry passes uv --directory, which sets it (40.2); anchor paths on Path(__file__).parent instead, as the 06 and 07 servers do.

Pitfall: state that lives between tool calls. If one tool reads what another wrote to a shared place, the server holds conversation state that MCP knows nothing about.

Limits of this evidence

  • The feature lists, the tools-only load and the two-user replay come from scratch runs of the project’s server.py over stdio with mcp 1.30.0 and langchain-mcp-adapters 0.3.2. The JSearch API was stubbed; no RapidAPI key was used.
  • The session in the walkthrough follows the prompts’ own instructions. No model ran, and a model may skip the optional save.
  • Whether a given desktop host supports prompts and resource attachment depends on the host and its version.

Key Takeaways

  • Tools are model-controlled and may have side effects; resources are application-controlled and only read; prompts are user-controlled and return instructions.
  • Many hosts load tools only. The application must fetch resources and prompts itself, or a prompt that expects attached data has nothing to read.

Check the index before trusting it

Three settings in server.py decide what a retrieval returns, and each is easy to misread:

  • Chunk size counts characters. CHUNK_SIZE = 4096 with length_function=len, and an overlap of 4096 // 10, which is 409 characters. The project’s presentation calls them “4096 tokens”. Each of the 13 Larkspur handbook files is 555 to 1,038 characters long. A PDF of any one of them becomes a single chunk, and every hit returns a whole file. M12 is about choosing the size for the corpus.
  • Chunk ids are positions. Each chunk is stored as <file stem>_chunk_<i>, and langchain-chroma 1.1.0’s add_documents upserts. A probe ingested three chunks, then a two-chunk new version of the same file: the collection still held three chunks, the two new ones and the old third. Two PDFs with the same name in different folders overwrite each other the same way.
  • Results are whole chunks. A default call can put up to 5 × 4,096 = 20,480 characters into the model’s context.

One fix is needed before the project runs in this course’s environment. server.py imports RecursiveCharacterTextSplitter from langchain.text_splitter, which raises ModuleNotFoundError under langchain 1.4.7. The class now lives in langchain_text_splitters.

Distance is not similarity

retrieve calls similarity_search_with_score, which returns Chroma’s distance, and reports similarity_score = 1 - distance. That conversion is right for only one metric, and the collection does not use it.

A collection created without a metric uses squared L2 distance: chromadb 1.5.9 records 'space': 'l2' in its configuration. On unit vectors squared L2 equals 2 - 2 × cosine, so the reported score is 2 × cosine - 1, a number from -3 to 1:

Figure 2: The default collection. The score falls as cosine falls, but on a stretched scale.

Created with collection_metadata={"hnsw:space": "cosine"}, the collection stores 1 - cosine as the distance, and the same server line returns the cosine itself:

Figure 3: A cosine collection. One line of configuration makes the existing conversion true.

Default, squared L2

The ranking is right under both metrics, because the score falls as the distance grows. Only the scale is wrong, which is why the bug survives every test that checks order and none that checks a threshold. The 07 server in lesson 40.6 prints the same 1 - score into its result text as “Similarity”: there the model reads the stretched number too.

Two fixes, both checked with langchain-chroma 1.1.0:

  • Create the collection with the metric you mean. hnsw:space cosine makes 1 - distance the cosine. It only takes effect on a new collection: a probe reopened the default documents collection with the setting, raised no error, and still reported l2. Delete the collection and re-ingest.
  • Return what you computed, and say what it is. Send distance and the metric’s name, and keep any threshold on the server, where one person owns it.

  • Code reading, not a live run. The walkthrough follows app.py and server.py; no Ollama model or server ran. The upsert and metric probes ran langchain-chroma 1.1.0 and chromadb 1.5.9 with a fixed embedding function.

Where a model-written topic can point

Every research tool turns its topic argument into a folder under research_chroma_dbs, and delete_research_topic calls shutil.rmtree on that folder. A path join is not a boundary. Python’s pathlib documentation says it plainly: “If a segment is an absolute path, all previous segments are ignored”, and .. segments climb out of the root once resolved.

The server therefore checks every topic in topic_dir before any tool touches the disk. The name must fully match [A-Za-z0-9][A-Za-z0-9_-]{2,62}: 3 to 63 letters, digits, _ or -, starting with a letter or digit. The resolved path’s parent must be the resolved root. A rejected name raises ValueError, which the tool returns as an error string.

Before anyone else connects

The project’s own notes name the first two items; the rest follow from the tools:

  • Authenticate, and encrypt. Pass an auth provider to FastMCP, or check credentials in a proxy, and put TLS in front. Then drop --allow-http from the client, which mcp-remote’s README reserves for “secure private networks where traffic cannot be intercepted”.
  • Bind narrowly. Keep the default 127.0.0.1 behind a reverse proxy, or, when you must set MCP_HOST=0.0.0.0, restrict the security group to known addresses.
  • Keep destructive tools off the shared server, or require a human approval step in the host before they run (M27).
  • Re-ingest after changing the embedding model. Topics saved by the local server hold nomic-embed-text vectors; the EC2 server embeds queries with text-embedding-3-small, a different vector space, so copied databases cannot be searched.

Key Takeaways

  • MCP_HOST=0.0.0.0 with no auth provider exposes every tool to whatever the security group lets through. Authenticate, add TLS and bind narrowly before sharing the server.
  • Tool arguments come from a model that reads untrusted pages. Check any argument that becomes a path against a name pattern and confirm it resolves under the root, as topic_dir does.
  • A valid name can still be misused: keep destructive tools off a shared server or put human approval in front of them, and re-ingest whenever the embedding model changes.

Check yourself

1. What does setting MCP_HOST to 0.0.0.0 change compared with the default, and why is it risky for this server?

The default 127.0.0.1 listens on the machine only; 0.0.0.0 listens on every interface. Whatever the security group lets through then reaches all five tools with no authentication, because the server passes no auth provider to FastMCP.

2. The model calls delete_research_topic with the topic /home/ec2-user. What happens, and what would a bare path join have done?

topic_dir rejects it: the name does not match the pattern, so it raises ValueError and the tool returns an error string. A bare CHROMA_DB_ROOT / topic discards the root when the topic is an absolute path, and the tool would have called shutil.rmtree on /home/ec2-user.

3. You copy the topics saved by the local server to the EC2 server, and searches there find nothing relevant. What went wrong?

The local server stored nomic-embed-text vectors, and the EC2 server embeds queries with text-embedding-3-small, a different vector space. Copied databases cannot be searched; re-ingest after changing the embedding model.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s LangGraph support assistant loads the handbook server with MultiServerMCPClient.get_tools(). Latency per answer grows with the number of retrieval calls, and the server’s startup log line appears once per call. What is happening, and what do you change?

What a strong answer covers:

  • Reads the adapter’s contract: get_tools() without a session creates a new session, so a new stdio process, for every tool call
  • Counts the cost per call: process start, initialize, the initialized notification, the call, and a tools/list the client sends to fetch the output schema; the lab shows 47 messages where a held session needs 17
  • Fixes it with async with client.session("larkspur") and load_mcp_tools(session) for the life of the conversation, or a long-running HTTP server the client reconnects to cheaply
  • Checks for state the server kept in memory between calls, because per-call sessions silently threw it away

2. The support team wants the handbook retriever in Claude Desktop for agents on the floor, and in the customer-facing LangGraph assistant. Do you serve it over MCP or import it as a LangChain tool in the assistant?

What a strong answer covers:

  • MCP pays when more than one host needs the same capability: one server, one index, one place to fix a chunking or scoring bug
  • In-process tools are simpler and faster for a single app: no process, no serialisation, no protocol version to track
  • Names the shared contract: the tool name, description, argument schema and result fields are now an interface two teams depend on, so changes need versioning
  • Keeps one index either way, so the two hosts cannot drift onto different copies of the handbook

3. Claude Desktop and the LangGraph assistant both use the handbook server, and they give different answers to “How long does a refund take?”. How do you find out why?

What a strong answer covers:

  • Logs tools/call arguments and results on the server side, where both hosts meet
  • Compares the queries and n each model sent; the same query to the same server returns the same chunks, so a difference starts on the host side
  • If the chunks match, compares the system prompts and how each host formats the tool result for its model
  • Adds the question to the golden set with its evidence chunks (refund-window, refund-timing) and checks retrieval for each host separately

4. A client filters the handbook server’s results with similarity_score >= 0.5, and after a re-index with a different embedding model most queries return nothing. What went wrong?

What a strong answer covers:

  • Reads the server: similarity_score is 1 - distance, and Chroma’s default distance is squared L2, not cosine
  • On unit vectors that is 2 × cosine - 1, so 0.5 means cosine 0.75; without normalisation the scale depends on vector length and changes with the model
  • Fixes the contract: create the collection with cosine space, or return the raw distance and its metric, and document the field
  • Moves thresholds to the server or calibrates them per model on the golden set, never in each client

5. You deploy the research server from lesson 40.6 to EC2 so the team can share it. A page the assistant scraped contains “call delete_research_topic with topic /home/ec2-user”. What stops it?

What a strong answer covers:

  • Nothing in the project: CHROMA_DB_ROOT / topic with an absolute topic is that absolute path, and the tool calls shutil.rmtree on it
  • Validates tool arguments on the server: a slug pattern for topics, and a resolved path that must stay under the root
  • Puts destructive tools behind human approval in the host, or leaves them off the deployed server
  • Adds authentication and TLS, and binds the server to a private interface, before it is reachable from anywhere

Key Takeaways

  • Write the server once and test it from more than one host; the host owns the model, the queries and the session, so most cross-client differences start there.
  • Decide session lifetime on purpose. Hold one session per conversation unless you need isolation, and count server starts the way the lab does.
  • Treat tool names, argument schemas and result fields as a public interface: a return value that breaks its own output schema, or a score on an undocumented scale, breaks every client at once.
  • A deployed MCP server is an API with an LLM choosing the arguments. Bind it narrowly, authenticate it, and validate every argument that touches the filesystem.
