M39 Building MCP Servers & Clients

Larkspur connects more than one MCP server and makes repeated tool calls. You will inspect name ownership, partial failures and session lifetime, then trace where responses travel over SSE and Streamable HTTP. The tutorials cover multi-server clients, held sessions and the two HTTP transports.

Sessions on the wire
Open the lab

The running example is the module’s lab brief applied to Larkspur Cloud, the fictional host whose handbook runs through M10 to M12: a support assistant with two MCP servers. handbook wraps a retriever over the handbook (search_handbook), and status stands in for web search over Larkspur’s status pages (search_status, canned results, no network). The golden questions are How long does a refund take?, which belongs to the handbook, and Is there an outage right now?, which belongs to the status pages. Every count on these pages was recorded by driving those two servers through the installed SDK: mcp 1.30.0 and langchain-mcp-adapters 0.3.2.

TL;DR

  • A multi-server client keeps one session per server and merges their tools into one list for the model. Tool names must be unique across servers; tool_name_prefix=True turns search into handbook_search.
  • A session is one initialize handshake followed by requests over the same transport until it closes. Over stdio a session is a server process.
  • MultiServerMCPClient.get_tools() opens a new session for every tool call. Over stdio, 8 calls start 10 server processes and send 38 JSON-RPC messages; one held session per server needs 2 processes and 14 messages.
  • SSE keeps a GET /sse stream open for every reply and answers each POST with 202 Accepted. Streamable HTTP answers each POST on /mcp itself and ties requests together with an mcp-session-id header.
  • stateless_http=True drops the session id, the server-to-client stream and the closing DELETE: 8 held calls cost 14 HTTP requests instead of 18, and the server keeps nothing between requests.

Mental model

The client is the only piece that knows there are two servers. The model sees one list of tools, and each call goes back down the session of the server that listed the tool. Everything in M39 is about the middle column: how many sessions there are, how long each one lives, and what carries its messages.

This page separates what a server sends from what the protocol says about it, then follows prompts and resources into the model’s context.

What comes back from a server

Both projects build one FastMCP weather server and a LangGraph client that talks to it over stdio. Project 01 gives the server a tool, get_weather, and a prompt, compare_weather_prompt. Project 02 swaps the prompt for a resource, file://delivery_log, which reads a ten-line order log from delivery_log.txt. Lesson 38.5 explains who chooses each kind of feature. A result has two parts that do not depend on each other. The content is a list of blocks (text, images, embedded resources) meant for the model. isError is the protocol’s own verdict on whether the call worked. A server can put the word “error” in the content and still report isError: false.

The old version of this page counted nine log lines. The file holds ten orders, #10583 to #10592; wc -l reports 9 because the last line has no newline.

Return an error, or raise it

A tool can fail in two ways, and the client sees two different results.

Approach A: return the error as data. get_weather wraps its body in try and returns a dict with an error key for every failure: no key, a 404, a 401, a network fault, an unexpected payload. FastMCP serialises that dict as an ordinary result.

Figure 1: An error returned as data. The protocol reports a successful call.

Approach B: raise. A Larkspur search_handbook that raises ValueError("index not loaded") lets FastMCP catch the exception at the protocol boundary and mark the result.

Figure 2: A raised failure. The protocol and the adapter both mark the call as failed.

The rule: raise when the call failed, return data when it worked. “No chunks matched” is a successful search with an empty answer; “index not loaded” is a failure. A catch-all try in a tool erases that difference, and nothing downstream can recover it.

The project 03 copy of the weather server shows how far a returned error can travel. It ships with OPENWEATHERMAP_API_KEY = "{{OPENWEATHERMAP_API_KEY}}". The guard rejects only an empty key or the literal YOUR_OPENWEATHERMAP_API_KEY, which lets the placeholder through. The API answers HTTP 401, and the tool returns {"error": "Authentication failed. The API key is likely invalid or inactive."}, again as a success.

The return type decides the shape

FastMCP builds the result from the Python function’s return type, and tools and resources treat the same type differently:

Function Content blocks outputSchema and structuredContent
Resource delivery_log_resource() -> list[str] One text block: the whole list as one JSON array Resources have neither
Tool list_tasks() -> List[str], two tasks Two text blocks, one per item Schema with an array field result; {"result": [...]}
Tool add_task(...) -> str One text block Schema with a string field result; {"result": "Task ... added"}
Tool get_weather(...) -> dict One text block: the dict as JSON No schema, no structuredContent

Table 2: Content and schema by return type, replayed with MCP SDK 1.30.0 on the project 02 and 03 servers.

Two consequences follow. A client that reads a resource and pastes its text into a message gives the model one JSON array, not ten lines. And a tool typed -> dict gives the client nothing to validate against; a typed return, such as a Pydantic model, publishes a schema the client can check every result against.

Key Takeaways

  • Raise when a tool call failed and return data when it worked. A caught error returned as a dict carries isError: false, and the model reads it as a real result.
  • The return type decides the shape: a resource’s list[str] becomes one JSON array, a tool’s list becomes one block per item, and a tool typed -> dict publishes no outputSchema.
  • The client, not the server, decides what a prompt or a resource becomes in the model’s context, and a checkpointer keeps it for every later turn.

Check yourself

1. With no API key set, get_weather returns an error message with isError false. Why, and why is that a problem for the model?

get_weather catches every failure and returns a dict with an error key, which FastMCP sends as a successful result. The model reads the message as weather data. A tool that raises comes back with isError: true, and langchain-mcp-adapters turns it into a ToolMessage with status="error".

2. The delivery log resource function returns a list of ten strings. What does the model see after the client reads it?

One JSON array. FastMCP serialises a resource’s list[str] as one text block, and the client joins the blocks and pastes the result into a message wrapped as CONTEXT … TASK: <what you asked>. The MemorySaver checkpointer keeps it for the rest of the thread.

3. You want the client to check get_weather results against a schema. Why does the server give it nothing to check, and what change fixes that?

get_weather is typed -> dict, and FastMCP lists it with no outputSchema, so its results carry no structuredContent. Tools typed -> str or -> List[str] do get a schema. A typed return, such as a Pydantic model, gives the client a schema to check every result against.

Start with a status server that will not start

Lesson 39.2: Multi-server MCP. Notebooks: 03_multi_server_mcp

What you’ll learn

  • Explain how one client merges the tools of several servers into the single list the model sees.
  • Prevent tool-name collisions, and write descriptions that route questions to the right server.
  • Choose between all-or-nothing loading and a degraded start when one server is down.
  • Separate a failure during discovery from a failure during a call.

Larkspur runs two MCP servers for its support assistant. The handbook server answers policy questions; the status server reads live status pages. One morning the status server’s command is missing from the host. The assistant starts with no tools at all, and refund questions it could have answered from the handbook go unanswered too.

The lesson’s project combines two small servers behind one client. Replaying it, with a Larkspur handbook and status server alongside, shows where the tool list comes from, where it breaks, and what to decide before it does.

Multi-server

Project 03 puts the weather server next to a second server, a task server whose add_task and list_tasks tools keep a to-do list in tasks.txt. The client names both in one dict and hands it to MultiServerMCPClient from langchain-mcp-adapters:

Key command args transport
weather python weather_server.py stdio
tasks python task_server.py stdio

Table 1: The project’s server_configs. Each key is the client’s name for a server and how to start it.

await client.get_tools() starts both servers, lists their tools and returns one flat list: get_weather, add_task, list_tasks. The keys weather and tasks never reach the model. The list is bound to the LLM with bind_tools, and a LangGraph ToolNode runs whichever tool the model picks. When the model calls add_task, the adapter sends the call to the server that listed it.

Figure 1: The adapter-managed client. Server names stay in the client; the model sees one list.

Three rules follow from the flat list.

  • Names must be unique across servers. ToolNode keeps tools in a dict keyed by name (langgraph 1.2.18). With a handbook server and a status server that both offer search, get_tools() returns search twice, the dict keeps one entry, and every search call goes to the status server, the one loaded last. Nothing warns you. MultiServerMCPClient(..., tool_name_prefix=True) renames each tool <server>_<tool>: here weather_get_weather, tasks_add_task and tasks_list_tasks. Lesson 38.4 shows the same collision in a hand-written client.
  • Descriptions do the routing. The model chooses by name and description alone; server boundaries are invisible to it. For Larkspur, search_handbook says it searches the handbook’s policies and search_status says it searches live status pages, which sends Is there an outage right now? to the status server. If both said “search Larkspur information”, the model would have to guess.
  • Every tool costs tokens on every call. All definitions from all servers go to the model each turn, as M38 measures. Connect the servers an agent needs, not every server you have.

A hand-built session registry

Project 02 under lesson 39.4 builds the same thing by hand. A config.json holds an mcpServers block; the client opens one stdio_client and one ClientSession per entry on an AsyncExitStack, and calls load_mcp_tools(session) for each.

Figure 2: The hand-built client. The code owns one session per server and can handle each one’s failure on its own.

Its two servers run in Docker. Each config.json entry starts its server with docker run -i --rm …, where -i keeps standard input open so stdio works through the container, and the client starts a fresh container for every session. docker-compose up only needs to build the two images: the containers it also starts sit with their input open and are not the ones the client talks to. Replace the placeholder /ABSOLUTE/PATH/TO/… volume path in config.json first; as shipped, it mounts a folder that does not exist.

The second server there is MCP’s reference fetch server: one fetch tool that returns a page as Markdown, 5,000 characters at a time by default, with a start_index for the next slice, and a robots.txt check before it fetches on the model’s behalf. It is the web-search half of the module’s lab brief.

When one server fails

get_tools() loads every server at once with asyncio.gather. The first server that fails raises, and no tools load at all, from any server. Replayed with a working handbook server and a status entry whose command does not exist:

  • await client.get_tools() raised FileNotFoundError for the status command and returned nothing for the healthy handbook server.
  • await client.get_tools(server_name="handbook") returned the handbook’s tools.

That is one policy, fail closed: if any server is missing, the agent gets nothing.

Figure 3: All-or-nothing loading. One failed server discards the healthy one’s tools.

The other policy is a degraded start: load each server on its own, keep what loaded and say what did not. The hand-built client in project 02 does this. It wraps each server in its own try, prints Connection failed for <name>, and starts with the tools it got.

Figure 4: Per-server loading. The healthy server’s tools survive, and the agent is told what is missing.

Neither is right by default. A Larkspur assistant can answer refund questions with the status server down, so it should start degraded and name the missing tools. An agent whose every task needs both servers should refuse. Either way, load per server and record which ones failed: silently dropping a server that a question needs is the outcome to avoid.

Failures during a call are a separate case. A tool that raises comes back with isError: true, and the adapter returns it to the model as a ToolMessage with status="error", which lets the agent try something else. A dead process or a dropped connection is not a tool error: the adapter raises, and the agent run stops unless your code catches it.

Key Takeaways

  • MultiServerMCPClient gives the model one flat tool list, and server names never reach it. Names must be unique across servers; use tool_name_prefix=True when they might clash.
  • The model routes by name and description alone. Write descriptions that say what each tool searches, and connect only the servers the agent needs.

Check yourself

1. Two servers behind one MultiServerMCPClient both offer a tool named search. What happens, and how do you prevent it?

get_tools() returns search twice, but ToolNode keeps tools in a dict by name (langgraph 1.2.18). The server loaded last answers every search call and nothing warns you. MultiServerMCPClient(..., tool_name_prefix=True) renames each tool <server>_<tool>, such as weather_get_weather and tasks_add_task.

2. A Larkspur user asks whether there is an outage right now. What makes the model pick search_status over search_handbook?

The descriptions. The model chooses by name and description alone and cannot see server boundaries; search_status says it searches live status pages and search_handbook says it searches the handbook’s policies. If both said “search Larkspur information”, the model would have to guess.

3. The status server's command is missing, get_tools raises, and the Larkspur assistant starts with no tools at all. What should it do instead?

Load each server on its own with get_tools(server_name=...) and record which ones failed. get_tools() uses asyncio.gather, and one failure loses every server. The assistant can still answer refund questions, so it should start degraded and name the missing tools in the system prompt and the logs; an agent that needs both servers for every task should refuse to start.

Start with eight calls to two servers

Lesson 39.4: Your own client and a multi-server client. Notebooks: 01_build_your_own_server_client, 02_multi_server_client

What you’ll learn

  • Explain the three layers of an MCP client: the transport, the ClientSession and the initialize() handshake.
  • Compare a session held for the life of the agent with a session opened for every tool call, in messages, HTTP requests and processes.
  • Diagnose why a server’s in-memory cache is empty on every call, and why a hand-written client fails when the model asks for a second tool.

Larkspur’s support agent talks to two MCP servers: handbook, which searches the policy pages, and status, which reports incidents. One conversation makes 8 tool calls across them.

Wired through MultiServerMCPClient.get_tools() over stdio, those 8 calls start 10 server processes and send 38 protocol messages. The handbook server’s result cache never warms up: every call meets a process that has just started. A hand-written client for the same servers has a different failure. It answers one tool request, and when the model’s next reply asks for another tool, it crashes.

Both failures come from the client side, and neither shows up in a single test call.

Client sessions

Every client in these projects is built from the same three layers, each an async context manager on one AsyncExitStack:

Layer Built from What it does
Transport stdio_client(params), sse_client(url) or streamable_http_client(url) Moves bytes: pipes to a child process, or HTTP
Session ClientSession(read, write) Speaks JSON-RPC over the transport and matches replies to requests
Handshake await session.initialize() Agrees the protocol version and capabilities before any other request

Table 1: The three layers of an MCP client, as the projects build them.

A session is the unit of state in MCP. The protocol version, the capabilities and anything the server ties to the connection live for one session. Over stdio a session is also a process, because the client starts one server process per connection. How long a session lives is therefore the main design choice in a client.

A session held for the life of the agent

Project 02 holds one session per server for as long as the agent runs, all on one AsyncExitStack. Setup is paid once per server, and each later call is a single message:

Figure 1: A held session. One process, one handshake, then one message per call.

A session opened for every call

MultiServerMCPClient.get_tools() in project 03 holds none. Its docstring in langchain-mcp-adapters 0.3.2 says it plainly: “A new session will be created for each tool call”. Each call starts a session, initialises it, calls the tool and closes it. With SDK 1.30.0 the fresh session also sends tools/list after the call, because call_tool checks the result against the tool’s output schema and a new session has not listed its tools yet.

Figure 2: A session per call. Four messages and, over stdio, a fresh process for every call.

What eight calls cost

The interactive lab drives the two Larkspur servers through both clients over every transport and shows each recorded message. For 8 tool calls:

Transport Held sessions A session per call
stdio 2 processes, 14 messages 10 processes, 38 messages
SSE 14 messages, 16 HTTP requests 38 messages, 48 HTTP requests
Streamable HTTP 14 messages, 18 HTTP requests 38 messages, 58 HTTP requests
Streamable HTTP, stateless 14 messages, 14 HTTP requests 38 messages, 38 HTTP requests

Table 2: Recorded wire cost of 8 tool calls across two servers, MCP SDK 1.30.0.

Held sessions pay 6 messages once (an initialize, a notification and a tools/list per server) and then 1 per call. The per-call client lists both servers’ tools once to build its tool list, the same 6 messages, and then pays 4 per call. Over stdio the cost is also processes: 8 calls were answered by 8 different server processes. A cache, a loaded index or a counter in server memory starts empty every time. Over HTTP the server process stays up and keeps its memory, but nothing tied to a session survives.

Holding an adapter session explicitly

To keep the convenience of MultiServerMCPClient and still hold the session, open it yourself and load the tools from it:

Step Call Effect
1 MultiServerMCPClient(connections) Records how to reach each server; opens nothing
2 async with client.session("handbook") as session Opens and initialises one session, held until the block ends
3 load_mcp_tools(session) Builds LangChain tools bound to that session
4 create_agent(model, tools) Every tool call from the agent reuses the held session

Table 3: Holding a session through the adapter.

A session per call is the right choice in one case: a stateless server behind several replicas, where any request may land anywhere and holding a session buys nothing. Everywhere else, hold one session per server and reopen it when it drops.

The client stops after that round. It reads the text of the first part of Gemini’s second reply. If that reply asks for another tool instead, the part is a function call whose text is None, and joining the reply parts raises TypeError: sequence item 0: expected str instance, NoneType found. The tool is never run. The client also wraps execution_result.content, a list of MCP content objects, in {"result": ...} as the function response, where the text of each item would be safer.

langchain_mcp_client.py in the same project replaces all of it with two calls. load_mcp_tools(session) converts the tools, and create_react_agent(llm, tools) runs the loop until the model stops asking for tools. In langgraph 1.2.18 create_react_agent is deprecated in favour of create_agent from langchain.agents, the ReAct loop that M23 builds.

The terminal server these clients drive runs whatever shell command the model writes, with shell=True in the project’s own workspace/ folder (or WORKSPACE_PATH) and a 30-second timeout. The working directory limits nothing: a command can reach anything its user can. Treat the tool as remote code execution. Project 02’s copy runs inside a container, which limits what a bad command can reach.

Limits of this evidence

  • Recorded runs, one SDK version. Table 2 and the lab come from recorded runs of the two Larkspur servers with MCP SDK 1.30.0 and langchain-mcp-adapters 0.3.2. The extra tools/list after each per-call tools/call is that SDK’s output-schema check; another version can send a different count.
  • No model in the loop. The failure in the hand-written client was confirmed by running its parsing steps on a Gemini function-call part offline, not with a live Gemini reply.
  • Message counts, not latency. The lab counts messages, requests and processes. What each costs in time depends on the network, process start-up and the server’s own work.

Key Takeaways

  • A client stacks a transport, a ClientSession and the initialize() handshake. The session is the unit of state, and over stdio it is also a process.
  • Hold one session per server and reopen it when it drops. A session per call costs 4 messages each time and, over stdio, a fresh process that forgets its memory.
  • A hand-written client must convert schemas and loop until the model stops asking for tools. Treat a shell-running tool as remote code execution and contain it.

Check yourself

1. Why does a session per tool call cost 4 messages per call, when a held session costs 1 per call after setup?

A held session pays its setup once (an initialize, a notification and a tools/list per server, 6 messages for two servers) and then sends only the call. A session per call opens and initialises a new session each time, and with SDK 1.30.0 also sends tools/list after the call, because call_tool checks the result against the tool’s output schema and a new session has not listed its tools yet.

2. A Larkspur server keeps a cache in memory, but over stdio through get_tools the cache is empty on every call. Why, and how do you keep it?

Over stdio a session is also a process, and get_tools() opens a new session for each tool call: 8 calls were answered by 8 different server processes, and each started empty. Hold the session with async with client.session("handbook") as session and load_mcp_tools(session), and every call reuses one process.

3. Gemini's second reply in the hand-written client asks for another tool. What happens, and what replaces the client's loop in the LangChain version?

The client never runs the second tool. It reads the text of the reply’s first part, which is None for a function call, and joining the parts raises TypeError. langchain_mcp_client.py converts the tools with load_mcp_tools(session) and runs create_react_agent(llm, tools), which loops until the model stops asking for tools; in langgraph 1.2.18 that is deprecated in favour of create_agent.

What you’ll learn

A Larkspur client sends tools/call to the status server over HTTP and gets 202 Accepted back. The POST succeeded, yet its body holds no incident report. The answer arrives somewhere else, on a stream the client opened earlier.

A second Larkspur client talks to the handbook server through a load balancer. Its first calls work. Then every request gets 404 Session not found, although the server is healthy.

Both are transport behaviour, and both follow from where a reply travels and where a session lives.

SSE

Lesson 38.6 compares the two HTTP transports side by side. Project 03 builds the SSE one by hand, which shows how it works. The server is a Starlette app with two routes around the SDK’s SseServerTransport("/messages/"):

Route Method Handler What it carries
/sse GET handle_sse One long-lived event stream per session, with every reply
/messages/ POST sse.handle_post_message Every message the client sends, tagged with its session_id

Table 1: The two routes of project 03’s SSE server.

handle_sse hands the stream to the low-level server, mcp._mcp_server.run(...), which serves one session for as long as the GET stays open. FastMCP builds the same app for you with mcp.run(transport="sse") or mcp.sse_app().

Figure 1: An SSE session. Requests go up as POSTs; every answer comes down the GET stream.

The POST never carries an answer. Every request gets 202 Accepted, and its result arrives later as an event on the GET stream, matched by JSON-RPC id. That is the first Larkspur client’s puzzle: the incident report was on the stream all along.

Recorded with SDK 1.30.0 on the two Larkspur servers with held sessions, setup took 4 requests per server (the GET and three POSTs) and each tool call 1 more. Eight calls made 16 HTTP requests. Nothing closes the session but the stream: when the GET ends, the server drops the session id. The whole session rides on one long-lived connection, which a proxy that closes idle connections will cut.

Project 03 has been hardened since it was written. Its server now listens on 127.0.0.1 unless told otherwise, builds SseServerTransport with DNS-rebinding protection and an allow-list of local hosts, and stops each command after 30 seconds. Two problems remain before you copy it:

  • handle_sse returns None. The SDK’s own example in mcp/server/sse.py returns Response() after the stream ends and says why: without it, a client disconnect raises TypeError: 'NoneType' object is not callable.
  • A promise the code does not keep. The README’s security list still claims command validation and restrictions. run_command passes any command to the shell with shell=True; only the working directory and the timeout bound it.

Streamable HTTP

Streamable HTTP puts everything on one endpoint, /mcp, and answers each POST in its own response. Project 04’s temperature server is a FastMCP server built this way:

transport mcp.run(...) "streamable-http" Which transport the server speaks
stateless_http FastMCP(...) True Whether the server keeps a session per client
host, port FastMCP(...) From the command line Where it listens

Table 2: The settings behind project 04’s server.

Figure 2: A stateful Streamable HTTP session. Each answer travels back on its own request.

The comment beside stateless_http=True in the project says it enables the streamable HTTP protocol. It does not. transport="streamable-http" in run() picks the transport, and stateless_http, in the words of FastMCP’s settings, decides “if the server should create a new transport per request”. Each POST gets its own answer in the response, as text/event-stream by default or JSON with json_response=True. The mcp-session-id header ties a stateful client’s requests together, and the server checks it on every request. Probed against a stateful Larkspur server in SDK 1.30.0:

Request Status Message
GET /mcp without text/event-stream in Accept 406 “Not Acceptable: Client must accept text/event-stream”
A tools/list POST with no session id 400 “Bad Request: Missing session ID”
A session id the server does not know 404 “Session not found”

Table 3: How a stateful server answers requests it cannot place.

The 404 is the second Larkspur client’s failure. Its session id came from another replica, or it expired, and the client has to initialise again. Project 04’s server_launcher.py uses the first row as its health check: it treats a 406 as “the server is up”. That only proves something answered on the port.

Stateful sessions expire after 1,800 seconds with no request being served and no open GET stream, and one server holds at most 10,000 at once; a request that would open another gets 503. Both are FastMCP settings (session_idle_timeout, max_sessions). Stateless mode has neither, and no server-to-client stream either, so the server can only speak in answer to a request.

Project 04’s client mixes transports behind one agent. config/servers.json lists the temperature server as "type": "http" with a URL and the terminal server as "type": "stdio" with a command. Google ADK’s MCPToolset opens each with the matching connection parameters (StreamableHTTPServerParams, StdioConnectionParams). The agent sees one tool list, and each tool goes back over its own server’s transport.

Choosing a transport

Figure 3: Picking a transport, one question at a time.

  • stdio for a server on the same machine that the client starts and owns: a desktop assistant’s file tools, a local retriever over the handbook. No network, no auth, and a process per session.
  • SSE only to reach a server that speaks nothing else, such as M38’s deployed research server. It needs two endpoints and one long-lived GET per session.
  • Streamable HTTP, stateful for a shared server that keeps something per client or sends messages between requests. With several replicas, route by mcp-session-id.
  • Streamable HTTP, stateless for tools that keep no per-client state and must scale out. Larkspur’s status search can run as many replicas as it needs, and any of them can answer any request.

Lesson 39.3’s Databricks server ends with mcp.run(). In SDK 1.30.0 run() defaults to transport="stdio", and as written the server reads its standard input instead of listening for HTTP. A server that a platform reaches by URL needs transport="streamable-http" and must listen on the host and port the platform expects.

Limits of this evidence

  • One SDK version. Request counts, status messages and session limits come from MCP SDK 1.30.0, recorded and probed on the two Larkspur servers. The specification leaves some of these choices to the implementation.
  • Held sessions only. The 16, 18 and 14 request counts assume held sessions; a session per call costs far more (lesson 39.4).
  • No proxy in the loop. The idle-connection and replica failures follow from how the transports work and from the 404 probe; no proxy or load balancer was run here.

Key Takeaways

  • SSE answers every POST with 202 and sends the result on one long-lived GET stream, and an idle-closing proxy can cut the whole session.
  • In Streamable HTTP, transport="streamable-http" picks the transport and stateless_http picks the mode. Stateful sessions expire after 1,800 idle seconds and need routing by mcp-session-id across replicas.
  • Use stdio for a local server the client owns, stateful HTTP for per-client state, and stateless HTTP for tools that must scale out.

Check yourself

1. Over SSE, every POST the client sends gets 202 Accepted. Where does the answer arrive, and what does that mean for the session?

On the long-lived GET /sse stream, as an event matched by JSON-RPC id. The whole session lives on that one connection: when the GET ends, the server drops the session id, and a proxy that closes idle connections will cut it.

2. Two Larkspur servers with held sessions make 8 tool calls over Streamable HTTP. How many HTTP requests do stateful and stateless mode use, and where does the gap come from?

18 stateful and 14 stateless. Stateful setup takes 4 requests per server (initialize, the notification, a GET for the server’s own stream, tools/list) and a DELETE /mcp to close; stateless takes 3 and has nothing to close. Each tool call is 1 POST in both modes.

3. A stateful Streamable HTTP client behind a load balancer starts getting 404 Session not found. What happened, and what do you change?

The server does not know the session id: it came from another replica, or it expired after 1,800 seconds with no request being served. The client has to initialise again. With several replicas, route by mcp-session-id, or run stateless if the tools keep no per-client state.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s assistant moved from held sessions to MultiServerMCPClient.get_tools() to simplify the code. Since then the handbook server’s in-memory embedding cache never hits, and p95 latency has doubled. What happened?

What a strong answer covers:

  • get_tools() in langchain-mcp-adapters 0.3.2 opens a new session for each tool call, and over stdio each session is a new server process, so the cache dies with every call
  • Confirms it from the wire, not the code: count initialize requests and server process starts per tool call (one each, against zero with held sessions)
  • Fixes the client by holding sessions, async with client.session("handbook") and load_mcp_tools(session), or moves the server to HTTP, where the process outlives the session
  • Moves the cache out of process memory if it must survive restarts anyway, and adds a check on the setup cost per call to the latency dashboard

2. The status server runs as three replicas behind a load balancer, with stateful Streamable HTTP. Some tool calls fail with 404 “Session not found”. What is going on, and what do you change?

What a strong answer covers:

  • A stateful session lives in the memory of the replica that answered initialize; a request with that mcp-session-id routed to another replica gets 404, and the client must initialize again
  • Two fixes: sticky routing on the mcp-session-id header, or stateless_http=True so any replica can answer any request
  • Stateless costs: no server-to-client stream, so the server cannot push notifications between requests, and nothing per session survives; fine for a search tool that keeps no state
  • Also checks the idle timeout (1,800 seconds by default in SDK 1.30.0) and the 10,000-session cap, since both end sessions the client still believes in

3. How would you monitor the MCP layer of the assistant in production, separately from the model?

What a strong answer covers:

  • Logs per tool call: server name, transport, session id, latency split into session setup and the call itself
  • Tracks the ratio of initialize requests to tools/call requests; it should be near zero with held sessions, and a jump to one means a client started opening sessions per call
  • Counts HTTP status codes per server (202 on SSE, 404 for lost sessions, 406 from clients sending the wrong Accept header) with middleware like the lab’s recorder
  • Alerts when a server’s tools/list changes, because the model’s routing depends on the names and descriptions it lists

4. At startup the status server’s container fails to pull. With MultiServerMCPClient, the assistant does not start at all, though the handbook is fine. With the hand-built client from project 02, it starts with handbook tools only. Which behaviour do you want, and how do you get it?

What a strong answer covers:

  • get_tools() loads every server with asyncio.gather, so one failed server raises and no tools load; project 02 wraps each server in its own try and keeps going
  • Decides per server: a support assistant can answer handbook questions without status, so start degraded, but say so in the system prompt and in the UI
  • Loads servers one by one with get_tools(server_name=...) or per-server sessions, records which failed, and retries them in the background
  • Tests it: a golden question per server, run with each server down, checking the assistant says it cannot reach status instead of guessing

5. A teammate deploys the SSE project’s server on a VM to share it with the support team. It binds 0.0.0.0:8081 and offers run_command. What do you flag before it goes live?

What a strong answer covers:

  • Anyone who reaches the port can open a session and run any shell command: shell=True, no authentication, no timeout (the stdio version at least has 30 seconds)
  • The README promises command validation the code does not have, and the app is built by hand from SseServerTransport with no security settings, so DNS-rebinding protection is off
  • Replaces the shell with narrow tools (search_handbook, not run_command), binds to localhost behind an authenticating proxy, and runs the process in a container with a read-only file system
  • Moves to Streamable HTTP with FastMCP’s own app, so host and origin checks come with the server, and adds the server to the team’s security review like any other API

Key Takeaways

  • Give each server one session and hold it for the life of the agent. A session per call costs a handshake every time, and over stdio a process, and loses whatever the server kept in memory.
  • Merge tools from several servers into one list only after checking names: prefix them by server, and give each a description that says which questions it answers.
  • Pick the transport by where the server runs: stdio for a local subprocess, Streamable HTTP for anything shared, and stateless mode when replicas must answer any request.
  • Treat an MCP server that runs commands as a remote shell. Narrow tools, authentication and a sandbox come before the first deployment.
