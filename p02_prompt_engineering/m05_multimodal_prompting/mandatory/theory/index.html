M05 Multimodal Prompting

A multimodal model reads pictures, documents and sound in the same request as the question. The prompt becomes an ordered list of parts, and each part has a token price you can work out before you send it. The M05 notebooks build on three ideas: how an image goes into a prompt, how a PDF or an audio file goes in, and how a video becomes sampled frames plus a transcript.

Open the lab

The running example is the Larkspur Cloud handbook from M10 to M12, in the forms a support team holds it: a pricing page as a screenshot, the handbook as a PDF, a recorded support call, and a 90-second screen recording of the data export. The M10 question Can I export my data after I cancel my plan? now has visual evidence as well: the export walkthrough, which the lab samples frame by frame.

TL;DR

  • A multimodal request is a list of parts. Gemini takes PIL images inline, and PDFs, audio and video by reference after genai.upload_file; GPT-4o takes image_url parts that hold a public URL or a base64 data URL.
  • Every part has a price you can compute first. Gemini counts 258 tokens per PDF page and 32 per second of audio. gpt-4o counts 85 tokens per image at detail="low", and 1,105 for a 1280 by 720 frame at detail="high".
  • The GPT-4o notebook sends no video file. It samples frames itself and transcribes the soundtrack with whisper-1, so the sampling gap sets both the cost and what the model can see.
  • In the lab’s 90-second walkthrough, the notebook’s default gap of 2 s sends 45 frames and misses a 1.2 s toast. A 1 s gap sends 90 frames, 7,650 tokens at low detail, and catches all eight steps.
  • A media prompt names what the media holds, what to extract, the output shape, and what to do with anything unreadable ([NOT_EXTRACTED], “do not make up any information”).

Mental model

Whatever the provider, the request is a list of parts and the model reads every part as tokens. Decide how each file gets in by its size and by whether you will send it again, then count the tokens before you call: a 10-minute support call is 19,200 tokens before the question is read.

Image prompts

Lesson 5.1: Multimodal prompting with Gemini. Notebooks: 01a_multimodal_google_gemini.ipynb

What you’ll learn

  • Build an image prompt as an ordered list of parts that says what the pictures hold.
  • Explain why PDFs, audio and video go in by uploaded handle instead of inline bytes.
  • Price a page, an image and a second of audio in tokens before you call the model.
  • Design prompts that fix the output shape and refuse anything the file does not contain.

M04 wrote prompt patterns for text alone: roles, few-shot examples, chain of thought. This lesson keeps those patterns and adds the part they never needed: the evidence arrives as a picture, a document or a recording.

A Larkspur customer sends a screenshot of the pricing page and asks How much outbound traffic does the starter plan include? A text-only assistant cannot see the screenshot. A multimodal model can, and it can still answer badly: it can describe the page instead of reading it, or estimate a value from a bar that carries no printed number. The prompt has three jobs here. It must tell the model what kind of image it holds, ask the exact question, and give it a way to say the answer is not on the page.

An image prompt is a list of parts: one or more images, then the question as text. The notebook sends two scanned pages on US wildfires to Gemini this way, with the pictures first and the question last:

Figure 1: An image prompt is an ordered list. The pictures travel inline with the request; nothing is uploaded first.

The notebook’s code runs gemini-2.5-flash at temperature 0, although its Markdown cells still describe Gemini 1.5 Flash. The model name changes over time; the shape of the request stays.

Three choices that carry over

The wildfire prompt makes three choices worth copying for any image question:

Choice in the prompt What it does Larkspur pricing screenshot
“can contain graphs, tables and text” tells the model to read the chart and the table, not describe the picture “This is a pricing page with a plan table and a traffic chart.”
“analyze all of them” spreads the answer across both pages one screenshot, one image
one question per call two calls over the same images: top five years, then the acreage trend one call per question, each graded on its own

Table 1: The wildfire prompt’s choices, applied to the Larkspur question.

The third choice is a trade-off. Lesson 5.2 sends both wildfire questions in one GPT-4o call. Separate calls pay for the images twice, but each answer can be graded by itself.

The Larkspur prompt adds one line the wildfire prompt lacks: “If the value is not printed on the page, say so.” Without it the model meets a bar with no label and estimates its height. Call that failure guessing from the picture: an answer that looks like a reading of the page but is a measurement of pixels.

An image as the question

An image can also be the thing you ask about. The notebook’s last example sends a video, a still image and the prompt “When is the moment in the image happening in the video? Provide a timestamp.” For a support team that is a customer’s screenshot of an error, matched against a recorded walkthrough to find the step where they are stuck.

What an image costs

Images cost tokens like text. Gemini’s token documentation counts an image of 384 pixels or less on both sides as 258 tokens, and tiles larger images into 768 by 768 tiles of 258 tokens each [1]. A large screenshot therefore costs a multiple of a small one. Documents and recordings are priced the same way, by page and by second, and they travel differently.

PDF and audio input

PDFs, audio and video go through the File API: you upload the file once and get back a file handle, a reference the model can read. The handle takes the image’s place in the contents list. The notebook uploads a Congressional Research Service PDF on wildfire statistics, an interview recording, three videos and one still image this way.

The upload happens once. The notebook reuses one audio handle for three prompts:

Figure 2: One upload, three prompts. Each call sends the handle, not the recording’s bytes.

Sending the bytes again with every prompt is the re-upload tax: the same file crosses the network three times for three questions. A handle avoids it, and uploaded files stay available for 48 hours [2].

Three prompts over one recording

Each of the three prompts fixes the output shape and keeps the model to what is in the recording:

Prompt Output shape it asks for Guard against invention
Chapters chapter titles with timestamps, short, no chapter summaries “Do not make up any information that is not part of the audio”
Transcript [timecode] - [speaker] : caption, speakers A, B and so on mapped to real names first, one caption per speaker turn only the part of the conversation about the Pixel Watch
Summary three headed lists: key speakers, products and features, other notable discussion scoped to the audio file

Table 2: The notebook’s three audio prompts. The notebook ships without outputs, and the answers depend on your run.

For Larkspur, the transcript prompt turns a recorded support call into turns labelled Customer and Agent. A follow-up question such as “What refund window did the agent quote?” can then be checked against the handbook’s 30 days. A summary that states the wrong window is the expensive error here, because a customer will act on it.

What a document or a call costs

The token rates come from Gemini’s documentation: 258 tokens per PDF page [3] and 32 tokens per second of audio [1]. With Larkspur sizes:

Input Gemini rate Larkspur example Tokens
PDF 258 per page 40-page handbook 10,320
Audio 32 per second 10-minute support call 19,200

Table 3: The token price of two Larkspur files, before the question is read.

A 10-minute call costs almost twice the whole handbook. Every question about that call pays the 19,200 again, because the handle saves transfer, not tokens.

When to upload

Gemini accepts PDFs up to 50 MB or 1,000 pages [3]. Its Files API guide says to upload whenever the whole request, files and prompt together, is larger than 100 MB [2]. Upload below that size too when the same file serves several prompts, as the audio handle does in Figure 2:

  • Inline: small images sent once, such as the pricing screenshot.
  • Uploaded handle: PDFs, recordings and anything you will ask about more than once.

Video goes in the same way, and Gemini samples it into frames by itself. Lesson 5.2 samples video by hand and shows what the sampling rate decides.

Key Takeaways

  • An image prompt is an ordered list of images followed by the question. Say what the images hold, ask the model to use all of them, and give it a way to say a value is not printed.
  • Upload PDFs, recordings and video once through the File API and reuse the handle across prompts; upload anything that takes a request over 100 MB.
  • Media cost tokens on every call: 258 per small image or PDF page and 32 per second of audio. Fix the output shape in the prompt and forbid anything that is not in the file.

Check yourself

1. Why does the notebook upload the interview recording through the File API instead of sending it inline with each prompt?

The upload returns a handle that takes the image’s place in the contents list, and one upload serves the chapters, transcript and summary prompts. Sending the bytes with each prompt pays the re-upload tax three times. The handle saves transfer, not tokens: each call still pays for the audio’s seconds.

2. How many tokens does Gemini count for the 40-page Larkspur handbook as a PDF, and for a 10-minute support call as audio?

10,320 for the PDF, at 258 tokens per page. 19,200 for the call, at 32 tokens per second over 600 seconds, almost twice the handbook.

3. You want the starter plan's included outbound traffic from a pricing-page screenshot. How do you build the prompt?

Send the screenshot first and the question last, say that the image holds a plan table and a chart, and add “If the value is not printed on the page, say so.” That last line stops the model guessing from the picture when a bar has no label. Ask one question per call and grade each answer on its own.

Image content parts

Lesson 5.2: Multimodal prompting with GPT-4o. Notebooks: 02a_multimodal_openai_gpt_4o.ipynb (optional)

What you’ll learn

  • Build a chat message that mixes text and image parts, sent as a data URL or a public URL.
  • Price an image for gpt-4o at low and high detail from its size.
  • Explain how a video becomes sampled frames plus a transcript when the API takes no video.
  • Choose a frame gap from the shortest event you need the model to see.

Lesson 5.1 sent images, PDFs and recordings to Gemini as a list of parts. The OpenAI Chat Completions API uses the same idea with a different envelope, and it takes no video file at all.

A Larkspur customer records a 90-second screen capture of the data export and asks support whether the export finished. The answer is on screen for 1.2 seconds, as an “Export ready” toast. A pipeline that samples one frame every 2 seconds can send 45 frames and still never show the model that toast. This lesson builds up to that failure from single images.

Text and image parts in one message

In the Chat Completions API a user message’s content can be a list of typed parts instead of one string. The notebook’s first image call sends a system message (“Help me with my math homework!”) and a user message with two parts:

Part Type What it carries
1 text “What’s the area of the triangle?”
2 image_url the scanned page, as a URL

Table 1: The two parts of the notebook’s first image message.

The URL field takes either of two forms, and the notebook sends the same scanned page both ways:

  • A base64 data URL: the notebook reads the file from disk and base64-encodes it into the request. Use it for private files, such as a Larkspur customer’s console screenshot. The request carries the bytes, and base64 makes them about a third larger (4 characters for every 3 bytes).
  • A public https URL: the request stays small, but OpenAI fetches the image itself, which only works for images anyone can reach.

The notebook keeps one answer as a Markdown cell. From a scanned page of The Algebra of Mohammed Ben Musa (al-Khwarizmi), the model read the triangle’s sides as 6, 5 and 9 and applied Heron’s formula: semi-perimeter 10, area √200 = 10√2, about 14.14. The arithmetic checks out; whether the sides were read correctly is a question about the scan, which is why later lessons grade answers against values printed on the page.

Extraction prompts with an escape

The notebook’s extraction prompts share one shape: a role in the system message, a fixed output format, and an explicit escape for anything the model cannot read:

Image Role (system) Output format Escape
Clinical note expert in handwritten clinical notes Markdown table with columns Symptoms, Present/Denies and Probability; acronyms expanded in an appendix table “Do not make up terms, if something is not detectable leave it out.”
Handwritten page handwriting expert the text “exactly as in the image” [NOT_EXTRACTED] for any word it cannot read
Sales chart data analyst a brief summary, then detailed statistics on the top 3 salesmen none
Two wildfire pages analyst of document scans both 5.1 questions in one call none

Table 2: The notebook’s image prompts. Outputs are not shipped, and only the triangle answer is recorded.

An escape marker turns an unreadable word into a visible gap instead of a plausible guess. For Larkspur, a screenshot of a console error gets the same treatment: read the error code exactly, or mark it [NOT_EXTRACTED].

What detail costs

Each image part also takes a detail setting, and it sets the price. OpenAI’s images and vision guide gives the rule for gpt-4o [1]. At detail="low" an image costs the base 85 tokens whatever its size. At detail="high" the image is scaled to fit 2048 by 2048, its shortest side is scaled down to 768 if longer, and every 512-pixel tile covering the result adds 170 tokens:

Figure 1: How gpt-4o prices one 1280 by 720 frame at each detail setting.

Applying the rule to three sizes:

Image Size after scaling Tiles High Low
Video frame, 1280 by 720 1280 by 720 3 by 2 1,105 85
Screenshot, 1920 by 1080 1365 by 768 3 by 2 1,105 85
Report page, 860 by 1064 (lesson 5.3) 768 by 950 2 by 2 765 85

Table 3: gpt-4o image tokens from OpenAI’s published rule, computed for each size.

A 1280 by 720 frame costs 13 times less at low detail. The 1920 by 1080 screenshot costs the same as the smaller frame, because scaling happens before tiling. The notebook sends its video frames at detail="low", which matters once a video becomes dozens of images.

Frame sampling

Frame sampling turns a video into a list of still images taken at a fixed gap, so a model that reads only text and images can follow it. The notebook was written when the GPT-4o API took text and images only, and it builds the video input itself with OpenCV and moviepy:

  1. Read the video’s frame rate and frame count.
  2. Compute the step between sampled frames as frame rate times seconds_per_frame, truncated to a whole number.
  3. Read every step-th frame, encode it as JPEG, then as base64.
  4. Write the soundtrack to an mp3 at a 32k bitrate and transcribe it with whisper-1.
  5. Send the frames and the transcript in one user message.

Figure 2: A 90-second recording at the notebook’s 3-second example gap: every 90th frame, 30 frames, plus the transcript.

The notebook then writes three summaries of an OpenAI DevDay recap video: from the frames alone, from the transcript alone, and from both in one message. Its own conclusion is that the combined summary is the most accurate. The frames miss what the speaker says, and the transcript misses what is on screen.

The gap decides what the model sees

seconds_per_frame is the setting that matters. It decides how many frames the model reads, which sets the cost. It also decides which moments the model sees at all: something on screen for less time than the gap may fall between two frames. Call that failure the event between frames.

The interactive lab runs a port of the notebook’s sampling on a fictional 90-second Larkspur screen recording (30 fps, 1280 by 720) that walks through a data export in eight steps. Two of them are short: a 1.8 s confirm dialog and a 1.2 s “Export ready” toast, the only frame that shows the export finished. Its numbers:

Gap (s) Frames Tokens, low Tokens, high Steps seen
1 90 7,650 99,450 8
2, the notebook default 45 3,825 49,725 7, toast missed
2.5 36 3,060 39,780 8
3, the notebook example 30 2,550 33,150 7, toast missed
10 9 765 9,945 6

Table 4: Frames, tokens and coverage per gap in the frame sampling lab.

  • Only a gap shorter than the shortest event guarantees a frame on it. The toast lasts 1.2 s, and 1 s is the widest gap in the lab that always catches it. At 2.5 s the frames happen to land on both short steps; if the toast came 1.2 s later, the same gap would miss it.
  • Cost grows with the number of frames. Halving the gap doubles the frames and the tokens. High detail multiplies the bill by 13 again.
  • The transcript is the other source. A step the narrator mentions survives a missed frame; a silent toast does not.

Gemini takes the video file itself and samples it at 1 frame per second by default, and a request can set a custom rate [2]. Its documentation warns that “fast action sequences might lose detail due to the 1 FPS sampling rate”. At 1 frame per second the lab’s 1.2 s toast always gets a frame.

Two sharp edges in the sampler

The notebook’s sampler has two bugs worth knowing before you copy it:

Planted input What happens Why
29.97 fps, 3 s gap step of 89 frames, one frame every 2.97 s truncation drops the fraction of 89.91
30 fps, 0.02 s gap the loop never ends the step truncates to 0 and the frame position never advances

Table 5: Planted inputs for the sampler, worked from the notebook’s own arithmetic.

Rounding the step to the nearest whole frame, with a floor of 1, fixes both: the loop always advances, and the 29.97 fps gap comes back to 3.003 s. The video setup also needs moviepy 1.x, because moviepy 2 removed the moviepy.editor module the notebook imports; this repo pins moviepy<2 for that reason.

Choosing a frame gap

Pick the gap from the event, then check the bill:

Figure 3: Choosing a gap and a detail level for a recorded walkthrough.

For the Larkspur export recording, the toast is silent and lasts 1.2 s. The widest lab gap that always catches it is 1 s: 90 frames, 7,650 tokens at low detail. Try low detail on the toast frame first, and move to high only if the model cannot read the toast’s text.

Key Takeaways

  • Send private images as base64 data URLs and public ones as https URLs. Give extraction prompts a role, a fixed output format and an explicit marker for anything unreadable.
  • detail sets the image price: 85 tokens at low, plus 170 per 512-pixel tile at high, so a 1280 by 720 frame costs 13 times more at high.
  • For video, the frame gap sets both cost and coverage. Only a gap shorter than the shortest event guarantees a frame on it, and a transcript covers what the narrator says.

Check yourself

1. When should an image part use a base64 data URL rather than a public https URL?

Use a data URL for private files, such as a Larkspur customer’s console screenshot: the request carries the bytes, about a third larger after base64. A public URL keeps the request small, but OpenAI fetches the image itself, and that works only for images anyone can reach.

2. What does a 1920 by 1080 screenshot cost gpt-4o at detail high, and at detail low?

1,105 tokens at high: it fits within 2048 by 2048, its shortest side is scaled to 768 (giving 1365 by 768), and six 512-pixel tiles cost 85 + 6 × 170. At low it costs the base 85 tokens, 13 times less.

3. At the notebook's default 2-second gap, the lab's frames never show the Export ready toast. Why, and which gap guarantees it?

The toast lasts 1.2 s, shorter than the gap, and it falls between two frames. Only a gap shorter than the shortest event guarantees a frame on it: 1 s in the lab, at 90 frames and 7,650 tokens at low detail. The 2.5 s gap catches it by luck and would miss it if the toast came 1.2 s later.

Questions about a report page

Lesson 5.3: Exercise: financial report analysis. Notebooks: 03a_financial_report_analysis.ipynb (optional)

What you’ll learn

  • Replace an open summary request with questions whose answers are printed on the page.
  • Order a report prompt as extraction first, interpretation second.
  • Check extracted values in code, with a tolerance for the report’s own rounding.
  • Handle unlabelled charts and answers the page does not contain.

Lessons 5.1 and 5.2 sent images to a model and asked it to read them. This exercise asks the harder question: how you know the reading was right.

The exercise sends two page images from ABN AMRO’s third-quarter 2024 report to gemini-2.5-flash:

  • Balance sheet (779 by 597 pixels): the condensed statement of financial position at 30 September 2024, 30 June 2024 and 31 December 2023.
  • Figures at a glance (860 by 1064 pixels): nine bar charts from Q3 2023 to Q3 2024, each bar labelled with its value.

Its prompt casts the model as a financial analyst and asks for a six-part summary: key metrics, income and expenses, balance sheet, credit quality, strategy, outlook. The notebook ships without its output. Even with one, a summary is hard to grade, since no single line of it is right or wrong. Call that failure the ungradable summary.

The module’s lab brief asks for five questions instead. Each one has a value printed on the page, so each answer can be graded line by line:

Question On the page
Net profit in Q3 2024 EUR 690 million
Return on equity in Q3 2024 11.6%, target 9 to 10%
Cost/income ratio in Q3 2024 59.2%, target circa 60%
Total assets, 30 September 2024 403,771 million
Total equity, 30 September 2024 25,810 million

Table 1: Five gradable questions and the values printed on the two pages.

Extract, check, then answer

Ask for extraction before interpretation. A prompt that first lists each value with its label, unit and period, then answers from that list, leaves a record you can check against the page:

Figure 1: Extract first, let code check the totals, then answer from the checked values.

The balance sheet gives you a check for free. At 30 September 2024, total liabilities of 377,961 plus total equity of 25,810 is 403,771, the printed total assets. Do that sum in code, not in the prompt: code adds exactly, while a model asked to check its own reading can make a second error on top of the first. Most misread digits in any of the three values show up here.

Planted check: the report’s own rounding

An exact-equality check fails on values the model read correctly. The report prints every line in millions, rounded, and its subtotals do not always match the sum of its own rounded lines. Summing the columns of the printed page:

Check Printed total Sum of printed lines Gap
30 Sep 2024: liabilities + equity 403,771 403,771 0
30 Sep 2024: eight liability lines 377,961 377,959 2
30 Jun 2024: liabilities + equity 393,404 393,403 1
31 Dec 2023: eight asset lines 377,909 377,911 2

Table 2: Totals on the balance sheet image against sums of its own printed lines.

A tolerance of a few million in the check keeps rounding from raising false alarms, while a misread digit in the thousands still fails it. Call the opposite mistake the false alarm: a checker so strict that reviewers learn to ignore it.

Reading charts honestly

Two more rules keep the answers honest:

  • Read labels, do not measure bars. Every bar on “Figures at a glance” carries its value, and the model reads a number instead of estimating a height. For a chart without labels, ask for the axis range and an estimate, and grade with a tolerance.
  • Allow “not on the page”. A question whose answer is not printed should get that answer, not a guess from neighbouring figures.

Sent to gpt-4o at high detail, each of the two images costs 765 tokens under the rule from lesson 5.2: 2 by 2 tiles of 512 pixels, after “Figures at a glance” is scaled to 768 by 950. Five questions in one call cost the images once; five calls cost them five times.

In practice: Larkspur pricing

The same method reads a Larkspur pricing page:

  1. Extract each plan’s printed figures with label, unit and billing period: price, included outbound traffic, refund terms.
  2. Check in code what can be checked, such as an annual price against twelve monthly prices when the page states a discount.
  3. Answer customer questions from the extracted list, and reply “not on the page” for a value the page does not print.

The extracted list doubles as a test fixture. When the pricing page changes, rerunning the extraction shows exactly which values moved.

Key Takeaways

  • Ask specific questions whose values are printed on the page, not for a summary, and grade each answer line by line.
  • Extract each value with its label, unit and period before interpreting, and check totals in code with a small tolerance for the report’s own rounding.
  • Have the model read printed labels instead of measuring bars, and accept “not on the page” as an answer rather than a guess.

Check yourself

1. Why should the prompt extract each value with its label, unit and period before answering the five questions?

Extraction before interpretation leaves a record you can check against the page. It also lets code test the extracted values, such as whether the balance sheet adds up, before any answer is built on them.

2. The model extracts total liabilities of 377,961 million and total equity of 25,810 million at 30 September 2024. What check do you run, and where?

Add them in code, not in the prompt: 377,961 + 25,810 = 403,771, the printed total assets. Allow a gap of a few million, because the report’s rounded lines can miss their printed totals by 1 or 2. A larger gap means a misread digit: re-read the page or flag it for review.

3. A question asks for a figure the two report pages do not print, and another chart has no value labels. How should each be handled?

The first should get the answer that the figure is not on the page, not a guess from neighbouring figures. For a chart without labels, ask for the axis range and an estimate, and grade the answer with a tolerance.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur summarises recorded export walkthroughs with GPT-4o, sampling a frame every 3 seconds. A customer’s summary says the export “may not have finished”, but the recording shows an “Export ready” toast. What went wrong, and how do you fix it?

What a strong answer covers:

  • Lists the timestamps of the frames sent and compares them with when the toast was on screen: a 1.2 s toast and a 3 s gap can miss each other
  • States the rule: only a gap shorter than the shortest event you need guarantees a frame on it; 1 s does that here, at 90 frames instead of 30
  • Considers cheaper options than a dense gap everywhere: extra frames on scene changes, or relying on the transcript for events the narrator mentions
  • Adds the recording to a golden set with the question “Did the export finish?” so the fix is measured

2. The billing team wants answers from the 40-page handbook PDF. One engineer sends the whole PDF to Gemini on every question; another wants to extract the text and use RAG. How do you decide?

What a strong answer covers:

  • Prices the first option: 40 pages at 258 tokens is 10,320 tokens on every call, before the question
  • Uploads once and reuses the file handle if the whole document is sent, instead of re-sending bytes per call
  • Notes what text extraction loses (charts, tables laid out as pictures) and what it gains (citations, smaller prompts, access control per chunk)
  • Proposes a measured comparison on the golden questions, and page-level retrieval (M20) as the middle path

3. Support calls are transcribed and summarised with Gemini audio input. How do you measure transcript quality and catch the model putting words in the wrong speaker’s mouth?

What a strong answer covers:

  • Builds a small set of calls with human transcripts and measures word error rate and speaker attribution separately
  • Checks timestamps against the audio, since chapter titles and captions carry timecodes the prompt asked for
  • Spot-checks facts the agent quoted (the 30-day refund window) against the handbook, because a wrong policy in a summary is the costly error
  • Tracks cost per call from duration: 32 tokens per second is 1,920 tokens a minute

4. A customer sends a screenshot of the pricing page and asks how much outbound traffic the starter plan includes. The chart on the page has bars but no printed values. What should the assistant do?

What a strong answer covers:

  • Separates reading a printed value from estimating a bar height; only the first is an answer to quote
  • Tells the model to say when a value is not printed rather than guess from the picture
  • Answers from the handbook text instead, where the plan lists its included traffic
  • Logs the case so the pricing page gets printed labels, which makes every later screenshot answerable

5. To cut cost, a teammate proposes detail="low" for every customer screenshot sent to gpt-4o. When is that safe?

What a strong answer covers:

  • Quotes the difference: 85 tokens against 1,105 for a 1280 by 720 image at high, 13 times less, and the same 85 at any size
  • Notes that a 1920 by 1080 screenshot also costs 1,105 at high, because it is scaled to 1365 by 768 first, so size alone does not drive the bill
  • Tests both settings on real screenshots for the task that needs small text, such as reading an error code, and keeps high only where low fails
  • Redacts secrets before sending, because a base64 image carries everything on the screen to the provider

Key Takeaways

  • Treat a multimodal prompt as a list of parts, and say in the text what the parts contain and what to extract from them.
  • Price each part before you send it: pages, seconds of audio, frames and image tiles all have published token rates.
  • When you sample video yourself, set the gap below the shortest event you need to see, and check what that costs.
  • Give the model a way out for unreadable input ([NOT_EXTRACTED], “not on the page”) and grade answers on questions with known values.
