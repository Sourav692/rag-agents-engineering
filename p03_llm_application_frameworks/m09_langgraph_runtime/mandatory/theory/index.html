M09 LangGraph runtime

M08 builds a graph that runs from start to end in one call. Real workflows stop and start again: a person approves a step hours later, a payment provider times out, a deploy restarts the worker, a user wants to see progress while the graph runs. The M09 notebooks build on four ideas: the checkpointer, interrupt(), subgraphs and streaming modes, plus the retry policies, loop bounds and state rules that make a resumed run safe.

What runs twice on resume
Open the lab

The running example is the refund desk of Larkspur Cloud, the fictional host whose handbook M10 to M12 index. A refund request enters a graph modelled on the refund agent in 06a_LangGraph_State_Management.ipynb: triage, assess risk, refund at once when the risk is low, and wait for the billing team’s approval when it is high. Two threads carry the pages and the lab, refund-17 (low risk) and refund-99 (high risk).

TL;DR

  • A checkpointer saves the whole state after every step under a thread_id. The four-node low-risk refund saves 6 checkpoints, steps -1 to 4. Any process with the same saver and thread id can read them, resume from them or fork them.
  • interrupt() pauses a node, saves the run and returns the payload to the caller under __interrupt__. Command(resume=value) continues it, and the node runs again from its first line, so code above the interrupt() call runs twice.
  • A subgraph is a compiled graph used as a node. With shared keys you add it directly; with different keys a wrapper node maps parent state in and out. Keys the parent does not declare are dropped on the way out.
  • Streaming modes decide what the caller sees while a run is in flight. For the same four-node run, values yields 5 chunks, updates 4, checkpoints 6, tasks 8 and debug 14. messages yields LLM tokens from every model call inside every node.
  • Every resumed or retried node can repeat a side effect. In the lab, a refund whose provider response is lost reaches the customer twice unless the call carries an idempotency key.

Mental model

The checkpointer writes after every step. At the gate, the first invoke returns while refund-99 waits at human_gate, and nothing runs until somebody calls Command(resume="approve") on the same thread, minutes or days later, from any worker that can reach the saver. Everything this module adds is about what happens between those two calls and after them: which code runs again, what the caller sees, and what the outside world receives twice.

A graph that forgets every refund

Lesson 9.1: Checkpointing and threads. Notebooks: 01a_Checkpointing.ipynb

What you’ll learn

  • Explain what a checkpointer saves, when it saves it, and how a thread_id keeps one customer’s run apart from another’s.
  • Trace the six checkpoints of a four-node refund run, field by field.
  • Choose a saver for tests, for one process and for several workers.
  • Compare replay, fork and copy-to-a-new-thread, and predict how many checkpoints each one adds.
  • Diagnose a fork that sends a finished refund down a different branch.

M08 built graphs from state, reducers, nodes and conditional edges. Each one ran from START to END inside a single invoke and returned the final state. Nothing survived the call.

That is fine for a demo and wrong for Larkspur Cloud’s refund desk. The desk runs a graph modelled on the refund agent in the state-management notebook: triage reads the request, assess sets the risk, low-risk refunds go straight to execute and then done, and high-risk refunds wait for the billing team. Two requests follow us through this module. refund-17 is an annual plan cancelled within 30 days, which the handbook refunds in full. refund-99 is a prorated annual refund that needs approval.

Without anything extra, the graph fails the desk in three ways:

  • A second message starts from nothing. We ran the four-node graph twice with no checkpointer. The second call’s event log held only its own four lines, with no trace of the first.
  • A restart loses work in flight. A refund waiting two days for approval lives only in the worker’s memory.
  • Nobody can say what the graph saw. When finance asks why refund-17 went through without review, there is no record of the state at the moment assess decided.

We call the first of these the amnesiac run: every call begins with empty state because nothing outside the call remembers it. The fix is a store that sits beside the graph and keeps one history per conversation:

Figure 1: One compiled graph, many threads. The checkpointer files every saved state under the thread it belongs to.

Checkpointer

A checkpointer is an object you pass to compile() that saves a snapshot of the whole graph state after every step of a run. You give each run a thread id in the config, and the checkpointer files every snapshot under that id. A thread is one conversation or one workflow: the refund request refund-17 is one thread, refund-99 another.

The thread id is the key to everything the checkpointer does. Two calls with the same id share one history, and the second turn of a chat sees the first. Calls with different ids never see each other. One compiled graph therefore serves every Larkspur customer at once, and nobody’s refund leaks into anybody else’s. We checked this offline: after refund-17 had finished, get_state on an unused thread id returned empty values.

The notebooks import the saver as MemorySaver. That is the older name for InMemorySaver, and in the installed LangGraph 1.2.18 both names point to the same class.

What one refund leaves behind

LangGraph saves a checkpoint before the first node runs and after each step. Running the low-risk refund refund-17 with stub nodes and InMemorySaver leaves this history:

Step Source next Events in state
-1 input __start__ 0
0 loop triage 0
1 loop assess 1
2 loop execute 2
3 loop done 3
4 loop (empty: finished) 4

Table 1: The six checkpoints of refund-17, oldest first (offline run with stub nodes, LangGraph 1.2.18).

Step -1 holds the raw input. Step 0 is the state with the input applied and triage queued. Each later step adds one line to the events log, because every node appends to it. The last checkpoint has an empty next, which is how a dashboard tells a finished thread from a paused one.

Every snapshot carries the same six fields, and each one answers a question an operator will ask:

Field What it holds The question it answers
values the state itself what did the graph know at this point
next the nodes still to run is this thread finished, paused or mid-run
config the thread id, a namespace and a checkpoint_id how do I address this exact snapshot
parent_config the previous checkpoint’s address what came before (the history is a linked list)
metadata the source (input, loop, update, fork) and the step how did this snapshot come to exist
created_at a timestamp when was it saved

Table 2: The fields of a checkpoint snapshot.

Pitfall: reading writes from metadata. Older LangGraph releases recorded which node wrote a checkpoint under metadata["writes"]. In 1.2.18 the metadata holds the source, the step and parent ids, and nothing else. Code that searches it for a node name finds nothing. Read next on the previous snapshot instead.

Where the checkpoints live

The saver decides what survives a restart. Three savers share one interface:

  • InMemorySaver: checkpoints in the process. Fast and free of setup, and gone when the process stops. Use it in tests and notebooks.
  • SqliteSaver: checkpoints in a file. The checkpointing notebook stores a secret code (“ALPHA-7”), closes the connection, opens a new one, and the second session still knows the code. We repeated the restart offline with a fresh connection and a freshly compiled graph, and get_state returned the first session’s events. It suits one process on one machine.
  • PostgresSaver: the same interface backed by a database server. It suits several workers sharing threads, the production case in lesson 9.6.

The graph code does not change between them. That is what lets workers stay stateless: any worker that can reach the saver can continue any thread.

Planted failures

Each misconfiguration below fails in its own way, and only one of them raises an error:

Setup What happened Why
No checkpointer, two calls the second run’s log had 4 events, none from the first the amnesiac run: nothing outside the call kept state
Checkpointer, no thread id ValueError: the checkpointer requires thread_id, checkpoint_ns or checkpoint_id it has nowhere to file the snapshot
A new thread id for a follow-up empty state, no error the follow-up opened a new conversation
InMemorySaver, worker restarted every thread gone the process-bound thread: the store died with the process

Table 3: Planted checkpointer failures (offline runs; the restart row follows from the saver living in process memory).

The two silent rows are the dangerous ones. A follow-up on the wrong thread id looks like a fresh customer, and nothing in the logs says otherwise. Once the history is safe, it becomes something we can walk back through.

History, replay and forks

get_state(config) returns the latest snapshot of a thread, and get_state_history(config) walks all of them, newest first. Every snapshot has its own id and a pointer to its parent. The history is a chain we can step back along and branch from:

Figure 2: A fork from step 2 of refund-17. The new checkpoint’s parent is the old one, and the original branch stays in the history.

Three operations use the chain, and each adds checkpoints in a different way:

  • Replay: invoke with no input on an old snapshot’s config. Replaying refund-17 from step 2 re-ran execute and done, while triage and assess kept their recorded results. LangGraph first writes a checkpoint with source fork at step 3, then one per node, and the history grows from 6 to 9. Use replay to reproduce what the graph did after a given decision.
  • Fork: update_state on an old snapshot’s config writes a new checkpoint with source update whose parent is that snapshot. Patching a field no router reads (we patched decision) left next at execute, as in Figure 2, and continuing ran execute and done on the fork: 9 checkpoints again. The original branch stays.
  • Copy to a new thread: the notebook’s branching demo takes one thread’s values and writes them with update_state into two fresh thread ids, then lets each thread run on its own. The original thread never changes.

The fork that took another branch

A fork is a write by a node, and the graph treats it like one. update_state without as_node records the patch as coming from the node that last wrote, here assess, and then re-evaluates that node’s outgoing edges. Patching a field the router reads changes where the run goes next:

Patch at step 2 next on the fork After invoke(None) Checkpoints in the thread
decision (no router reads it) execute ran execute, done 9
risk set to high human_gate paused at the gate 7, then 10 after approval

Table 4: Two forks of the finished refund-17 (offline run, LangGraph 1.2.18).

The second row is the rerouted fork. A finished low-risk refund came back as a high-risk one waiting for the billing team, and its event log still said assess low, because assess never ran again. That can be exactly what you want (a correction that forces review), but only if you expected it.

Two habits keep forks predictable:

  • Fork from the snapshot’s own config. It carries the checkpoint_ns key. We rebuilt a config by hand with only the thread id and checkpoint id, and update_state raised KeyError: 'checkpoint_ns', the failure the state-management notebook warns about.
  • Remember that replay re-executes. A replayed node runs its code again. If execute sends a refund to the payment provider, replay sends another one. This replayed side effect is the subject of lesson 9.6.

The next section puts the whole lesson together on one incident.

In practice: auditing refund-17

Finance asks why refund-17 was paid without review. With a checkpointer and the thread id, the desk can answer from the history alone:

  1. Read the latest snapshot. next is empty: the thread finished.
  2. Walk the history to step 2. Its values show risk set to low and its next is execute. The graph skipped the gate because assess said low.
  3. Check the handbook rule against those values. An annual plan within 30 days and under 100 GB of outbound traffic gets a full refund, which makes low risk the right call.
  4. If it was wrong, fork from step 2 with risk set to high and continue. The thread parks at human_gate beside the original branch, as in Table 4, and the billing team sees it.

Lesson 9.2 uses the same saved state to stop a run on purpose and wait for a person.

Key Takeaways

  • A checkpointer saves the whole state after every step, filed under the thread_id. Same id shares one history, different ids never see each other, and a missing id is an error while a wrong one is silent.
  • InMemorySaver suits tests, SqliteSaver one process, PostgresSaver several workers. The graph code stays the same, and the workers can stay stateless.
  • Replay re-runs nodes from an old checkpoint and a fork adds a branch beside the original. Fork from the snapshot’s own config, and expect a patched routing field to send the run down a different branch.

Check yourself

1. How does one compiled graph with a checkpointer serve every Larkspur customer at once without mixing their conversations?

The thread_id in the config is the key. Calls with the same id share one saved history, and a second turn sees the first. Calls with different ids never see each other. The checkpointer saves a snapshot of the whole state after every step, filed under that id.

2. The finished refund-17 thread holds 6 checkpoints. You fork it at step 2 by setting risk to high and invoke with no input. What happens, and why?

The run parks at human_gate instead of going to execute. update_state records the patch as a write by assess, the node that last wrote, and re-evaluates its conditional edge, which now routes high risk to the gate. The thread has 7 checkpoints at that point and 10 after approval, and the original branch stays in the history.

3. Larkspur runs several workers that share threads, and threads must survive a restart. Which saver do you choose, and what fails with the in-memory one?

PostgresSaver. InMemorySaver keeps checkpoints in one process, and a restart loses every thread. SqliteSaver writes a file that suits one process on one machine. The graph code does not change between savers: the workers stay stateless and any of them can continue any thread.

A refund that must wait for billing

Lesson 9.2: Interrupts and human-in-the-loop. Notebooks: 02a_HITL_Mechanics.ipynb, 02b_LangGraph_Interrupt_Primitive.ipynb, 02c_HITL_Patterns.ipynb

What you’ll learn

  • Explain what interrupt() saves, what it returns to the caller, and what runs again on resume.
  • Trace a high-risk refund from the first call, through the pause, to the approval.
  • Compare interrupt() inside a node with interrupt_before and interrupt_after at compile time.
  • Choose among approve or reject, edit then continue, edit state while paused, and tool-call review.

Lesson 9.1 gave every refund a thread and a saved snapshot after each step. This lesson uses that saved state to stop a run on purpose.

refund-99 is a prorated annual refund, and Larkspur’s policy says a person in billing approves every high-risk refund. The approval can take two days. A worker that blocks inside invoke for two days is a worker serving nobody else, and a deploy in the meantime kills the run. The graph has to do three jobs: stop at the gate and show the reviewer what to decide, give the worker back while it waits, and continue from the gate with the reviewer’s answer, on whichever worker picks it up.

interrupt()

interrupt(payload) called inside a node stops the run at that line, saves the state through the checkpointer, and returns the payload to the caller under the __interrupt__ key. The thread now waits at that node. Later, any process calls invoke with Command(resume=value) on the same thread, and inside the node interrupt() returns that value.

The whole exchange takes two calls with a gap between them:

Figure 1: The two calls of an approved refund. Between them the run exists only as saved state.

We ran the refund graph offline with stub nodes and an InMemorySaver to watch each call:

Call What the caller sent Nodes that ran Returned Thread after the call
1 the refund request triage, assess, human_gate (stops at interrupt()) __interrupt__ with the question 4 checkpoints, next = human_gate
2 Command(resume="approve") human_gate again, execute, done final state 7 checkpoints, finished

Table 1: refund-99 across the pause (offline run, LangGraph 1.2.18).

A dashboard finds parked refunds by reading next: a thread whose next is ("human_gate",) is waiting for billing.

Three rules that follow

The mechanism has consequences that catch teams the first time:

  • A checkpointer is required. Without one, the first call still returns __interrupt__, but nothing was saved. The resume call then raises RuntimeError: Cannot use Command(resume=...) without checkpointer. We reproduced both halves offline.
  • The node runs again from the top. On resume LangGraph does not continue mid-function. It calls the node again, and this time interrupt() returns the resume value instead of stopping. The HITL mechanics notebook prints “Node execution started” twice for one resume. In the refund graph human_gate ran 2 times for one approval (Table 1). Anything above the interrupt() call (a notification, a counter, a model call) happens twice. We call this the double-run gate.
  • The resume value is yours to define. It can be a string, a dict with an edited_plan, or a list in the Agent Inbox format. interrupt() returns whatever the caller passes, so the node has to check it.

The mechanics notebook checks it with a loop. Its node asks for an age and calls interrupt() again until the answer parses as a non-negative integer:

Resume value What the node did
(first call) paused with “Please enter your age…”
“not a number” paused again, quoting the bad value
“-10” paused again
“25” stored age 25 and moved on

Table 2: The validation loop over four calls (offline replay of the notebook’s node).

Each bad answer costs one more round trip and nothing else. The checkpointer holds the thread between them.

Pausing at compile time instead

The notebooks also pause without touching node code. Compiling with interrupt_before=["assistant"] stops the run before that node, and interrupt_after stops it right after. You continue with invoke and no input. The two forms differ in who decides to stop:

interrupt() in a node interrupt_before / interrupt_after
Where it is declared inside the node at compile()
What the caller gets __interrupt__ with your payload the state so far, with no __interrupt__ key in our run
How to continue Command(resume=value) invoke with no input
What the reviewer can return any value the node reads nothing, unless you call update_state first
Suits approvals, questions, validation debugging and step-through review

Table 3: Runtime and compile-time pauses compared.

The second row matters for clients: after a compile-time pause, the caller learns the run stopped by reading next from get_state. With the gate’s decision settled as a mechanism, the next section is about what the gate does with it.

Approval patterns

The interrupt-primitive and HITL-patterns notebooks build four shapes on the same primitive. On the Larkspur refund desk they look like this:

  • Approve or reject: the gate returns Command(goto="execute") or Command(goto="cancel") depending on the decision, with an update that records it. The return type is annotated as a Command over the two target names, so the graph knows where the gate can go.
  • Edit then continue: the gate shows the draft reply to the customer and resumes with an edited_summary. The node writes the edited text to state and the graph follows its one path.
  • Edit state while paused: with interrupt_before, the caller runs update_state on the parked thread and then continues with no input. The patterns notebook swaps “Multiply 2 and 3” for “No, please multiply 15 and 6” this way, and the agent multiplies the new numbers.
  • Review a tool call: interrupt() inside a sensitive tool, or a wrapper such as the notebook’s add_human_in_the_loop, lets a person accept the call, edit its arguments, or answer instead of running it. HumanInTheLoopMiddleware in M23 packages the same idea for create_agent.

The approve-or-reject shape is the one the refund desk needs:

Figure 2: A fail-closed approval gate. Only one exact value reaches the payment step.

Planted failure: the rubber-stamp gate

The state-management notebook’s gate stores decision = "approved" whatever the resume value is. It records the reviewer’s words in the event log and then approves anyway. We call that the rubber-stamp gate. The patterns notebook’s gate compares the value with "approve" and sends everything else to the reject path. We resumed a copy of that gate with the first three values below, and “no” takes the same reject branch:

Resume value Rubber-stamp gate Exact-match gate
“approve” execute execute
“Approve” execute cancel
“yes” execute cancel
“no” execute cancel

Table 4: Four reviewer answers through two gates (exact-match column from an offline run; rubber-stamp column read from the notebook’s node, which never reads the value).

The exact-match gate rejects “Approve” and “yes”, which annoys reviewers once and costs nothing. The rubber-stamp gate pays out on “no”. Approve on an exact value and treat anything else as no. M27 builds that fail-closed gate, with a fingerprint that catches edits made after the review.

In practice: refund-99 at the gate

Put together, the high-risk path through the desk runs like this:

  1. The first call runs triage and assess, reaches human_gate, and returns the question under __interrupt__. The worker is free.
  2. The billing dashboard lists threads whose next is human_gate and shows the payload: the request, the risk and the prorated amount rule (unused whole months, minus the 15% early-termination fee).
  3. Two days later a reviewer clicks approve. Any worker calls invoke with Command(resume="approve") on refund-99.
  4. human_gate runs again from its first line, reads “approve”, and routes to execute. Any notice sent above interrupt() goes out a second time.

Key distinction: the checkpointer makes the wait safe for the state. It does nothing for code that runs twice. Step 4 is why the approval notice belongs in its own node before the gate.

What else runs twice around the gate, and how to count it, is the subject of the lab in lesson 9.6. Lesson 9.3 first moves the gate into a graph of its own.

Key Takeaways

  • interrupt() saves the state and parks the thread, and Command(resume=value) continues it from any process. It needs a checkpointer, or the resume call fails.
  • On resume the node runs again from its first line. Keep notifications, counters and model calls out of the code above interrupt().
  • The resume value is whatever the caller passes. Validate it, approve only on an exact value, and treat anything else as no.

Check yourself

1. Why does anything written above the interrupt call in human_gate happen twice for one approval?

On resume, LangGraph does not continue mid-function. It calls the node again from the top, and this time interrupt() returns the resume value. In the refund graph human_gate runs 2 times per approval, and a notification, a counter or a model call above the interrupt() line repeats.

2. A teammate runs the refund graph without a checkpointer. The first call returns an interrupt payload. What happens when they resume?

The resume call raises RuntimeError: Cannot use Command(resume=...) without checkpointer. The first call still returned __interrupt__, but nothing was saved, and there is no parked thread to continue.

3. A reviewer resumes refund-99 with the word no, and the refund is paid. What is wrong with the gate, and how should it treat the resume value?

It is a rubber-stamp gate: it sets the decision to approved whatever value comes back. interrupt() returns whatever the caller passes, so the gate must compare it with one exact value, route that to execute with Command(goto=...), and send everything else to the reject path. That fail-closed rule is the gate M27 builds.

One graph inside another

Lesson 9.3: Subgraphs. Notebooks: 03a_Subgraphs.ipynb

What you’ll learn

  • Explain what a subgraph is and the two ways to nest one: directly, or through a wrapper node.
  • Predict which keys come back out of a subgraph, and when a shared list key doubles.
  • Trace an interrupt inside a subgraph and count which nodes run again on resume.
  • Choose between a subgraph and plain nodes for a piece of the refund desk.

Lesson 9.2 paused the refund graph at a gate and resumed it. The gate was one node of one graph. Real teams split the work further.

Larkspur’s eligibility rules (annual or monthly plan, days since purchase, outbound traffic under 100 GB) grow into a small agent of their own: it looks up the account, checks the rules, loops on a tool when data is missing, and keeps working notes. The refund graph needs its verdict, not its notes. Copying its nodes into the refund graph would mix two teams’ state into one schema and make every eligibility change a refund-graph change. The desk wants to build, test and own that agent separately, then drop it in as one step.

Subgraphs

A subgraph is an ordinary compiled graph used as a node of another graph, the parent. The subgraphs notebook builds a weather agent with an agent node, a ToolNode and a loop between them. It invokes that agent on its own first, to check its input and output, and then nests it two ways. On the Larkspur desk the same move turns the eligibility agent into one step of the refund graph.

The two ways differ in how state crosses the boundary:

Figure 1: Nesting with shared keys (add the compiled graph as a node) and with different keys (call it from a wrapper that maps state).

  • Shared keys: add it directly. When parent and child both use MessagesState, adding the compiled subgraph as a node is enough. The parent’s messages channel is the child’s, and the child’s reply lands on it with the same reducer.
  • Different keys: wrap it. The notebook’s second parent stores the transcript under parent_messages. A wrapper node calls the subgraph with {"messages": ...} built from parent_messages, then writes the result back. The child does not change. Only the parent knows the mapping.

What crosses the boundary

A directly added subgraph returns its whole final state, and the parent keeps only the keys it declares. We built a two-node eligibility child (check, then decide) whose state has a private scratch key, a shared decision key and a shared log list with an operator.add reducer, and ran it inside a parent whose first node writes intake to the log:

Key Child wrote Parent received Why
scratch “notes” nothing the parent’s schema has no scratch
decision “eligible” “eligible” shared, no reducer: the value is replaced
log check, decide intake, intake, check, decide shared with a reducer: the child’s whole list is added again

Table 1: State crossing a directly added subgraph (offline run with stub nodes, LangGraph 1.2.18).

The first row is a feature. The child keeps working notes the parent never sees, and a key you expect in the parent has to be in the parent’s schema. The third row is the echoed log. The child received the parent’s ["intake"], appended its own two entries, and returned all three. The parent’s reducer then added those three to the ["intake"] it already had. Any list key with an add reducer on both sides doubles everything the parent wrote before the subgraph ran.

Two fixes work: give the child its own log key that the parent does not declare, or call the child from a wrapper that returns only what the child added. Both keep an audit trail honest, which lesson 9.6 relies on.

Checkpoints, interrupts and streams inside a subgraph

The runtime features from lessons 9.1 and 9.2 reach inside subgraphs:

  • Checkpoints: a subgraph compiled without its own checkpointer uses the parent’s. A parent thread parked inside a subgraph reports the subgraph’s node name in next. Asking get_state with subgraphs=True also shows the child’s own state and its own next. In our run the parent showed approval and the child showed gate.
  • Interrupts: an interrupt() inside the child pauses the whole run, in both nesting forms, and one Command(resume=...) on the parent thread continues it.
  • Streams: streaming with subgraphs=True yields pairs of a namespace and a chunk. The namespace names the subgraph node and its task (approval:<task id> in our run), and the parent’s own events carry the empty namespace.

The interrupt case needs a closer look, because nesting adds one more place where code runs twice. We moved the refund gate into a two-node child (check, then a gate that calls interrupt()), paused it, resumed it, and counted runs:

Figure 2: The approval child behind a wrapper. A resume restarts the interrupted child node and the parent node around it.

Node Added directly Behind a wrapper
check 1 1
gate 2 2
wrapper (none) 2

Table 2: Runs per node for one pause and one resume (offline run, LangGraph 1.2.18).

Resuming re-runs only the interrupted child node. check kept its saved result in both forms. The wrapper is different: it is the parent’s node, and the parent’s node is the one that was interrupted, so the wrapper function runs again from its first line. Any parent-side code before the call into the child repeats. This is the double-run gate from lesson 9.2, one level up.

Choosing a subgraph or plain nodes

A subgraph costs a boundary: a schema to keep in step, a mapping or a shared reducer to reason about, and one more level in streams and state. It pays for that boundary in four situations:

Situation Subgraph Plain nodes
The piece has its own loop (a tool-calling agent) ✓ keeps the loop inside ✗ the loop’s edges clutter the parent
The piece keeps private state (working notes) ✓ undeclared keys stay inside ✗ every key joins the parent schema
Another team owns it, or several parents reuse it ✓ build and test it alone ✗ copies drift apart
A straight sequence on the same state ✗ boundary for nothing ✓ simpler

Table 3: When a subgraph earns its boundary.

M35 to M37 build multi-agent systems out of exactly these pieces: each agent is a compiled graph, and a supervisor or a handoff decides which one runs.

In practice: nesting eligibility

The desk nests the eligibility agent like this:

  1. Build the agent as its own graph with its own state (account, plan, days since purchase, traffic, scratch) and test it alone on refund-17 and refund-99.
  2. Choose the wrapper form, because the refund graph’s state and the agent’s state share almost nothing. The wrapper passes the request in and copies only decision back.
  3. Keep side effects out of the wrapper above the call into the child, since a pause inside the agent re-runs the wrapper.
  4. Stream with subgraphs=True and show progress only for the parent’s namespace. Customers then see “checking eligibility” once and not every tool step inside it.

Pitfall: one reducer, two graphs. If the agent and the refund graph both declare events with an add reducer and the agent is added directly, every event written before eligibility appears twice in the audit trail.

Lesson 9.4 looks at streaming itself: which events a caller can ask for while any of these graphs runs.

Key Takeaways

  • Add a compiled subgraph directly when it shares keys with the parent, and wrap it in a node that maps keys when it does not. Only keys the parent declares come back out.
  • A shared list key with an add reducer on both sides doubles whatever the parent wrote before the subgraph ran. Give the child its own key or return only its new entries.
  • Checkpoints, interrupts and streams reach inside subgraphs. A resume re-runs only the interrupted child node, but a wrapper also runs again from its first line.

Check yourself

1. When can you add a compiled subgraph directly as a node, and when do you need a wrapper node?

Add it directly when parent and child share keys, as with MessagesState on both sides: the parent’s messages channel is the child’s. When the keys differ, as with the notebook’s parent_messages, a wrapper calls the subgraph with the child’s keys and writes the result back. The child does not change, and only the parent knows the mapping.

2. A parent writes intake to an events list, then runs a directly added child that appends check and decide to the same list. Both declare the list with an add reducer. What does the parent end up with?

Four entries: intake, intake, check, decide. The child receives the parent’s list, appends its two entries and returns its whole state. The parent’s reducer then adds all three to the intake it already had. Give the child its own key or wrap it so only new entries come back.

3. A two-node approval child (a check, then a gate) runs through a wrapper, pauses at the gate and resumes. What runs twice?

The gate and the wrapper. Resuming re-runs only the interrupted child node: the check runs once and the gate twice. The wrapper is the parent’s interrupted node, so it also runs again from its first line, and any parent-side code before the call into the child repeats.

Streaming modes

A stream mode decides what one chunk is when you call stream (or astream) instead of invoke. invoke returns once. stream yields chunks while the graph runs, and stream_mode picks their content. The installed LangGraph 1.2.18 has seven modes.

We counted the chunks for one run of the four-node low-risk refund refund-17 (triage, assess, execute, done) with stub nodes, in the scratchpad:

checkpoints a snapshot in the shape get_state() returns 6
tasks a node starting, then finishing with its result or error 8
debug checkpoints and tasks together, with step and timestamp 14
messages (message chunk, metadata) from a chat model inside a node per token
custom whatever a node writes with StreamWriter per write

The counts follow from the run. Four nodes give four updates. values adds the starting state for five. checkpoints matches the six snapshots of lesson 9.1. tasks reports a start and a finish for each node, eight in all, and debug carries both streams, six plus eight.

Matching the mode to the screen

Each screen wants a different slice of the run. Asking three questions in order picks the mode:

  • Progress labels (“checking eligibility”, “waiting for approval”): updates. Each chunk names the node that just finished. When the run pauses, the last chunk is {"__interrupt__": ...}. Streaming tells the caller what is happening. It does nothing for the server’s capacity, which is where async comes in.

Async nodes

An async node is a node written as async def that awaits its slow calls, such as await model.ainvoke(...). The graph then runs with await graph.ainvoke(...) or async for chunk in graph.astream(...). The notebook’s async graph has the same shape as its synchronous one: only the node and the call change.

Async matters when one server process handles many conversations. A synchronous invoke holds its worker for the whole run, model calls included. An async node hands the event loop back while it waits on the model or a tool, and the loop runs other conversations in the gap:

Figure 2: Two refund runs sharing one event loop. Each await frees the loop for the other run.

A FastAPI handler built on astream can therefore serve other Larkspur customers while one customer’s answer is still being written. We call the opposite the blocked worker: a synchronous handler whose process does nothing else while a model call is in flight.

Async and streaming are separate choices:

Returns once Yields chunks
Blocks the worker invoke stream
Frees the event loop while waiting ainvoke astream

Table 3: Async and streaming are two independent switches.

stream works synchronously, and ainvoke returns once at the end like invoke. A chat endpoint usually wants the bottom-right cell: astream with messages and updates.

Two details from the notebook complete the picture:

  • streaming=True on the model makes the provider send tokens as they are generated, which messages mode then passes through.
  • Checkpoints work the same. The async graph is compiled with MemorySaver, and a second ainvoke on the same thread sees the first turn. Our offline async run kept both turns’ events on one thread.

In practice: the refund chat

The desk’s chat endpoint combines everything on this page:

  1. The handler is async and calls astream on the refund graph with the thread id from the session and the modes updates and messages.
  2. Each updates chunk maps a node name to a label: triage to “reading your request”, assess to “checking the refund rules”.
  3. Each messages chunk is rendered only when its langgraph_node is the reply node. Grader and tool text never reach the customer.
  4. If the last updates chunk is __interrupt__, the chat shows “waiting for billing” and the handler returns. Billing’s approval later resumes the thread from another request.

Interview tip: when asked how to make an agent feel fast, separate the two questions. Streaming changes what the user sees during the run. Async changes how many runs one process can hold.

Flaky providers and endless loops

Lesson 9.5: Retry policies and bounded cycles. Notebooks: 05a_Retries.ipynb, 05b_Cycles_and_Loops.ipynb

What you’ll learn

  • Explain how a RetryPolicy re-runs a node inside one call, and compute its waits from its four numbers.
  • Predict which exceptions the default policy retries, and why naming them is safer.
  • Build a loop guard from three parts: a counter in a node, a cap in the router, and a recursion_limit.
  • Diagnose a loop whose counter never grows.

Lesson 9.4 showed a caller what a run is doing while it runs. This lesson is about runs that go wrong in two different ways.

Larkspur’s refund graph calls a payment provider that sometimes answers 503 for a few seconds. One failed call should not fail the refund, and nobody wants retry code inside every node. The support chat has the opposite problem: a node rewrites the customer reply until a tone checker passes it, and on a bad day the checker never passes. Without a guard, that loop calls the model until something outside the graph stops it. The desk needs retries that are short, bounded and aimed at the right errors, and loops that end whether or not the model gets it right.

Retry policies

A RetryPolicy attached to a node with add_node(..., retry_policy=...) re-runs that node when it raises, inside the same invoke. The caller sees one call and one result. We gave a node a policy and made it fail twice with ConnectionError before succeeding: the updates stream showed the node once, after the third attempt.

The retries notebook wraps a weather API that fails 70% of the time and gives it this policy: max_attempts 5, initial_interval 1 second, backoff_factor 2, max_interval 10 seconds, jitter on, and retry_on set to the notebook’s own APIError. A run that succeeds on the third attempt looks like this:

Figure 1: Retries happen between the graph and the node. The caller of invoke sees none of them (jitter left out).

How long the waits are

In the installed LangGraph 1.2.18 the wait after the n-th failure is the smaller of max_interval and initial_interval × backoff_factor^(n − 1), plus a random 0 to 1 second when jitter is on. (The notebook’s summary writes the exponent as the attempt number. The source uses one less.) For the notebook’s policy:

After failure Wait With jitter
1 1 s 1 to 2 s
2 2 s 2 to 3 s
3 4 s 4 to 5 s
4 8 s 8 to 9 s
5 no wait, the exception reaches the caller

Table 1: Waits under the retries notebook’s policy, from the formula in the installed source.

A run that exhausts the policy waits 15 to 19 seconds before it fails. With a 70% failure rate and independent attempts, all five fail with probability 0.7^5 ≈ 0.168, about one run in six. More attempts would lower that and lengthen the worst wait. The max_interval of 10 seconds caps any single wait. With five attempts it never bites. A sixth attempt would bring it into play: the wait after the fifth failure would double to 16 seconds and be cut to 10.

A policy you create without arguments is shorter: 3 attempts, a first wait of 0.5 seconds, a factor of 2, a cap of 128 seconds, and jitter on.

Which errors get retried

With no retry_on, a policy uses a default rule. We read it in the installed source and tested it offline:

Exception Retried by default Why
ConnectionError (and ConnectionResetError) yes checked first, as a network blip
HTTP 5xx from httpx or requests yes server errors are worth another try
TimeoutError no it is an OSError, and OSError is on the never list
ValueError, TypeError, RuntimeError, LookupError (incl. KeyError) no programming errors
a custom APIError(Exception) yes anything not on the never list is retried

Table 2: The default retry rule in LangGraph 1.2.18 (offline checks; a custom exception made 3 attempts, a ValueError made 1).

Two rows surprise people. A plain timeout is not retried, and a custom exception is, even without retry_on. The second one hides bugs. A node that raises its own error class for a bad input waits through every backoff before failing. We call this the patient bug. Name the exceptions you mean in retry_on, as the notebook does, so a bug fails on the first attempt and a real outage gets the retries.

Pitfall: the retried side effect. A retry repeats everything the node did before it raised. If the payment provider applied a Larkspur refund and then the connection dropped, the retry refunds again. Lesson 9.6 shows the fix and the lab that counts it.

Retries handle a node that fails. A loop that keeps succeeding without ever finishing needs a different guard.

Bounded cycles

A cycle is a conditional edge that routes back to a node the run already visited. The cycles notebook uses one to regenerate code until it passes its tests, and another to research a topic to a fixed depth. Every cycle needs a reason to stop that does not depend on the model getting it right:

Figure 2: The bounded code-generation loop. The node counts, and the router reads the count.

The three-part guard

The notebook’s guard has three parts, and each one covers a failure the others miss:

  • The node counts. generate returns iteration + 1. The router only reads it. A router function picks an edge, and anything it writes to state is discarded.
  • The router checks success first, then the cap. With a cap of 3 and a validator that always fails, the run is generate, validate, three times over, then finalize.
  • recursion_limit is the backstop. It counts steps, not loops. The installed LangGraph’s default is 10,007 (read from the environment variable LANGGRAPH_DEFAULT_RECURSION_LIMIT), far too high to protect a model budget. Pass it on every run.

We ran the loop offline with stub nodes and a validator that fails every time, the worst case a real model can produce:

Round generate sets iteration validate Router sees Goes to
1 1 fails, error 1 not success, 1 below 3 generate
2 2 fails, error 2 not success, 2 below 3 generate
3 3 fails, error 3 not success, 3 reaches 3 finalize

Table 3: The bounded loop with an always-failing validator (offline run, LangGraph 1.2.18).

That is 7 node runs, 3 errors accumulated through the operator.add reducer, and a result whose success is still false. The caller must handle that result: a capped loop ends, but it does not end well.

Planted failure: the counter in the router

Move the increment into the router function and the guard stops working. We ran that version with the same always-failing validator:

Version Where the count grows Outcome
Counter in generate node update, saved to state finalize after 3 rounds, 7 node runs
Counter in the router, recursion_limit 10 router writes, discarded GraphRecursionError after 10 steps (5 generates, 5 validations)
Counter in the router, default limit router writes, discarded stops only after 10,007 steps

Table 4: Where the counter lives decides whether the cap ever fires (first two rows from offline runs; the third follows from the default limit).

We call this the runaway loop: the cap is written correctly and never reached, because the number it reads never grows. With an explicit recursion_limit the run fails loudly after a few steps. With the default it can make thousands of model calls first. The safe habit is to test every loop with a grader that always says no, and check that it ends where you expect.

In practice: the tone-check loop

The support chat’s “rewrite until the tone checker passes” loop gets the same treatment:

  1. The rewriting node increments attempts in its update. The router only reads it.
  2. The router sends a passing reply to send first, then sends a reply that has used 3 attempts to a fallback node, and only then loops.
  3. The fallback hands the conversation to a person instead of sending an unchecked reply.
  4. Every run passes an explicit recursion_limit a little above the steps three rounds need.
  5. The model call inside the rewriting node gets a RetryPolicy with retry_on naming the provider’s connection and 5xx errors, and nothing else.

M29’s grade-and-rewrite loops are built this way. Lesson 9.6 puts retries, resumes and crashes together and counts what reaches the outside world.

Key Takeaways

  • A RetryPolicy re-runs a failing node inside one call, with waits that double from initial_interval up to max_interval. Name the exceptions in retry_on, because the default retries any custom exception and skips timeouts.
  • Every retry repeats the node’s side effects, and an external write that already succeeded can happen twice.
  • Bound every cycle: count in the node, check success then the cap in the router, and pass an explicit recursion_limit. The default of 10,007 steps will not protect a model budget.

Check yourself

1. Why should a RetryPolicy name its exceptions in retry_on instead of relying on the default?

The default retries ConnectionError and HTTP 5xx errors and skips the programming errors on its list, but any class not on that list is retried, including a custom APIError(Exception). A node that raises its own error for a bad input then waits through every backoff before failing. Naming the exceptions makes a bug fail on the first attempt and keeps retries for real outages.

2. With the retries notebook's policy and a weather API that fails 70% of the time, how long does a run that exhausts the policy wait, and how often does that happen?

15 to 19 seconds: waits of 1, 2, 4 and 8 seconds, plus up to 1 second of jitter each, and no wait after the fifth failure. All five attempts fail with probability 0.7^5 ≈ 0.168, about one run in six.

3. A rewrite loop bumps its attempt counter in the router function, and the loop runs until GraphRecursionError. What went wrong?

Anything a router writes to state is discarded: the counter never grows and the cap is never reached. The node must count (generate returns iteration + 1) and the router only reads it, checking success first, then the cap. Pass an explicit recursion_limit as the backstop, since the default of 10,007 steps is far too high to protect a model budget.

Paid twice, notified twice

Lesson 9.5 made nodes retry and loops stop. Every lesson in this module has ended on the same warning: some code runs twice. This lesson counts it.

Finance at Larkspur reports two problems with refund-99. The customer was refunded twice, and the billing team got two approval requests for it. The approval itself was given once. The state-management notebook builds the refund agent this module has followed, with a deterministic stub in place of the model and stub tools. It runs without an API key, and every result on this page comes from running its code or the lab’s recorded runs. The page answers two questions: how state stays correct when several nodes write it, and how the outside world stays correct when nodes run more than once.

Reducers and parallel writes

The state schema is the contract between steps, and each field’s reducer decides how a node’s partial update lands on it. A field with no reducer is overwritten. A field annotated with operator.add accumulates. A field annotated with add_messages merges chat messages by id. The notebook makes nodes a then b each return 1 for two fields, and adds a parallel case:

Reducer Two nodes in a row each write Two parallel nodes write in one step
None (plain: int) the last write wins: 1 InvalidUpdateError
operator.add (summed) the writes add up: 2 the writes add up
add_messages appended, matched by id appended; RemoveMessage(id=...) deletes

Table 1: What each reducer does with two writes (the notebook’s reducer, fan-out and pruning cells, run offline).

Planted failure: two reviewers, one field

A missing reducer only fails when writes collide in one step. The notebook fans out two reviewers from START, and both return risk:

Figure 1: Two reviewers in one super-step. Both write the same field in the same step.

LangGraph cannot choose between the two values and stops with At key ‘risk’: Can receive only one value per step. Use an Annotated key to handle multiple values. We call this the ambiguous write. Give the field a reducer and the merge is deterministic. The notebook’s fixed version sums the reviewers’ scores into risk_score, and the merged result is 3 with both reviewers’ events kept.

The audit trail and the context window

Two list fields in the refund agent use reducers for opposite purposes:

  • events, annotated with operator.add, is the audit trail. Every node appends a line, nothing overwrites it, and the checkpoint history from lesson 9.1 records when each line arrived. It is never pruned.
  • messages, annotated with add_messages, is what the model sees. The notebook’s trimming node sends RemoveMessage updates to fit the context window: after a node adds 5 transcript messages, the trimmer keeps the last 2, and the audit log records “pruned 3 old messages”.

Keeping the two apart means the model’s context can shrink while the record of what happened never does. Lesson 9.3 showed one way to break this: a directly added subgraph that declares the same events key echoes the parent’s entries into it twice. State inside the graph is now safe. The outside world is the harder half.

Resume and side effects

A durable workflow re-executes code. The run resumes after an approval, a worker restarts after a crash, a RetryPolicy tries again. The checkpointer makes the state safe across all three. It cannot take back what a node already did to the outside world: a refund sent, an email delivered. The notebook’s refund agent shows three ways a node runs again, and the Larkspur refund graph in the lab records each one with LangGraph 1.2.18:

Figure 2: Three paths to a second run. Earlier nodes keep their checkpointed results on all three.

  • Resume after interrupt() re-runs the interrupted node from its first line (lesson 9.2). Nodes before it do not run again.
  • Resume after a crash is invoke with no input on the same thread, once the cause is fixed. The failed node runs again, and triage and assess keep their checkpointed results. The low-risk refund takes 2 client calls: the first raises ConnectionError and leaves the thread parked at execute, the second finishes.
  • A RetryPolicy re-runs the node inside the same call (lesson 9.5). The caller sees no error. The provider sees two requests. The notebook’s flaky provider succeeds on its third attempt under a three-attempt policy.

The guards-off column holds both of finance’s problems. The notice doubles on every row, faults or not. The refund doubles only on the last row, where the provider applied the refund and the response never came back.

The two guards

Two guards account for every difference in Table 2:

  • Keep side effects off the resumed path. With guards off, the approval notice is sent inside human_gate above interrupt(), and the billing team gets it again when the gate resumes: the double-run gate. Moved into its own notify node before the gate, it runs once. The graph gains a node and one checkpoint (8 instead of 7), and the client still makes 2 calls.
  • Make external writes idempotent. A 503 before the provider refunds is harmless to retry. A lost response after it refunds is not: with guards off the customer is refunded twice. We call that the lost-response double charge. With guards on, the call carries the key refund:refund-99, the provider recognises the second request and returns the stored result.

An idempotency key is a name for one intended effect that the receiver remembers. The notebook’s EXECUTION_LEDGER does the same check in process:

Call Key Ledger before Returned
first refund:order-99:v1 empty executed: refunded $42.00
duplicate refund:order-99:v1 holds the first result skipped (already executed): refunded $42.00

Table 3: The notebook’s idempotency ledger on a duplicate call (run offline).

The key has to name the intended effect, not the attempt. A key built from a timestamp or a retry counter changes on every run and dedups nothing.

In practice: fixing refund-99

The desk’s fix for finance’s report follows the two guards:

  1. Read refund-99’s checkpoint history beside the provider’s log. human_gate ran twice and execute ran twice, and the provider applied two refunds.
  2. Move the approval notice out of human_gate into a notify node before it. The gate keeps only the interrupt() call and the decision.
  3. Send every refund with the key refund:<thread id>, so a retry, a crash resume or a replay asks the provider for the same refund and gets the stored result.
  4. Keep events as the append-only audit trail and record the reviewer’s decision in it on resume.
  5. Open the lab, set Response lost, RetryPolicy, and turn the guards on: both counts drop to 1 with the same number of client calls.

Key distinction: the checkpointer guarantees the graph’s state. Idempotency guarantees the world’s state. A production workflow needs both.

Put together, these are the notebook’s closing rules: workers stay stateless, state lives in the checkpointer, the events field is the audit log, the workflow is an explicit graph with the human gate as a waiting state, and every side effect can run twice without harm.

Key Takeaways

  • Give any field that parallel nodes write a reducer, or the step fails with InvalidUpdateError. An operator.add list makes an audit trail that nothing overwrites, kept apart from the pruned messages list.
  • Nodes run again after an interrupt, a crash or a retry. The checkpointer protects the state, never what a node already did outside the graph.
  • Move side effects off the resumed path into their own node, and send external writes with an idempotency key that names the effect, such as refund:refund-99.

1. Finance reports that refund-99 was paid out twice, and the billing team says it got two approval requests for it. The approval itself was given once. How do you investigate?

What a strong answer covers:

  • A thread parked at the gate has get_state(config).next == ("human_gate",) and a pending interrupt in its tasks
  • The latest checkpoint’s created_at gives the wait time; alerts fire when a refund waits past an agreed limit
  • Keeps an append-only events field (an operator.add reducer) as the audit trail, since values alone shows only the latest state
  • Records the decision and who made it in state when resuming, so the dashboard and the audit agree

4. A refund was assessed as high risk on Friday and approved on Monday. Over the weekend the policy team changed the refund window. Which policy applies when the graph resumes, and should it?

What a strong answer covers:

  • The checkpoint holds Friday’s state; resuming continues from it and does not re-run triage or assess
  • Decides whether stale assessments are acceptable; for money, re-checks the policy in execute or routes back to assess when the policy version changed
  • Stores the policy version in state at assessment time, so the check is a comparison, not a guess
  • For a deliberate correction, forks with update_state from the checkpoint before execute instead of editing the database

5. The support chat streams tokens with stream_mode="messages". After a grader node was added, customers briefly see “yes relevant” before the answer. Why, and how do you fix it?

What a strong answer covers:

  • messages mode streams tokens from every chat-model call inside every node, the grader included
  • Each chunk comes with metadata; filters on metadata["langgraph_node"] == "answer" before rendering
  • Uses updates mode in parallel for progress labels (“checking the handbook”), passing a list of modes and reading (mode, chunk) pairs
  • Adds a test that streams a scripted run and asserts no grader tokens reach the client

Key Takeaways

  • Compile with a checkpointer and pass a thread_id whenever a run may pause, crash or continue later; use a durable, shared saver in production.
  • Treat every node as code that can run more than once. Keep side effects after interrupt() or in their own node, and give every external write an idempotency key.
  • Pick the stream mode for the screen: updates for progress, messages filtered by node for typing, values when the client renders whole state.
  • Bound every loop twice: a counter that a node increments and the router reads, and an explicit recursion_limit as the backstop.
