M07 LCEL, Runnables & Chains

LCEL is how LangChain 1.x composes work: prompts, models, parsers and retrievers snap together with |, and the result runs with the same methods as each piece. Every RAG chain from M10 onwards is one of these pipes. The M07 notebooks build on four ideas: the one interface every component shares, the pipe that joins components into a sequence, the parallel and branching shapes a pipe can take, and map-reduce for documents longer than one prompt.

Open the lab

The running example is the Larkspur Cloud handbook used from M10 onwards: a support assistant that answers refund and outage questions, triages tickets, and summarises handbook sections. The lab summarises three handbook documents of 1,111, 1,833 and 2,746 characters.

TL;DR

  • A Runnable has one interface: invoke for one input, batch for a list, stream for chunks, and an async twin of each. Prompts, models, parsers, retrievers and whole chains all have it.
  • a | b is Python’s __or__ returning a RunnableSequence. A dict inside a pipe becomes a RunnableParallel, so {"context": retriever | format_docs, "question": RunnablePassthrough()} | prompt | llm | parser is a complete RAG chain.
  • RunnableParallel runs its branches on the same input at once: notebook 03a’s description, pros and cons chains plus a merge chain make 4 model calls in 2 rounds. RunnableBranch runs the first branch whose condition is true.
  • LLMChain, RetrievalQA and load_summarize_chain now live in langchain-classic, deprecated with removal set for 2.0.0. Each rewrites as a short pipe.
  • Map-reduce trades calls for a small prompt. In the lab the whole handbook at chunk_size=400 is 10 chunks: map-reduce makes 11 calls in 4 rounds at max_concurrency=4, refine makes 10 calls in 10 rounds, and stuff makes 1 call that reads all 2,746 characters.

Runnable interface

M06 built the pieces of a LangChain app one at a time: a chat model, a prompt template, an output parser. Each had its own way of being called. The Larkspur Cloud support assistant needs all of them at once, plus a retriever over the handbook, and the first version of its refund chain fails with AttributeError: 'AIMessage' object has no attribute 'upper'. Nothing in that message says which of the four steps broke. This lesson gives every step the same shape, and that shape is what lets you find the broken step in one pass.

A Runnable is any LangChain component that takes one input and returns one output through a fixed set of methods. A prompt template, a chat model, an output parser, a retriever and a chain built from them all have the same methods. Code that runs one of them runs any of them. LCEL, the LangChain Expression Language, is the pipe syntax that joins Runnables into a chain; lesson 7.2 opens it up. The methods every Runnable shares:

Method Takes Returns Use it for
invoke one input one output a single request
batch a list of inputs a list of outputs, in input order many independent requests, run on a thread pool
stream one input an iterator of chunks showing tokens as the model writes them
ainvoke, abatch, astream the same awaitables and async iterators async servers

Table 1: The Runnable methods. Every component and every chain has all of them.

Each method also takes an optional config. It carries tags, metadata and callbacks for tracing, and max_concurrency, which caps how many batch calls run at once. The same config works on a single prompt and on a ten-step chain, which is why tracing and rate limits attach once rather than per component.

One input, always

invoke passes exactly one argument. When a step needs two values, they travel together in one container. Notebook 01b shows three ways: a tuple the function unpacks, a dict the function reads by key, and a small lambda that takes a dict and calls an existing two-parameter function with its two keys. Dicts win in practice. Prompt templates read their variables from a dict, and RunnableParallel returns one, which lets a dict flow from step to step without conversion.

We planted three wrong inputs and ran them against the installed langchain-core 1.7, with a fake chat model standing in for a real one:

A prompt that declares {question}, given {"q": ...} KeyError: Input to ChatPromptTemplate is missing variables {'question'} the dict keys must match the template’s variables
A function that upper-cases a string, placed right after the model AttributeError: 'AIMessage' object has no attribute 'upper' the model returns a message object, not a string

The third row is the Larkspur refund chain’s bug. It belongs to a family worth naming.

Each step changes the type

Notebook 02a invokes the pieces of prompt | model | parser one at a time before building anything. On a Larkspur question the data changes shape at every arrow:

Figure 1: The type that crosses each arrow of a prompt, model and parser chain.

A seam mismatch is a step that receives a different type from the one it was written for. A function that expects a string receives a dict, a prompt receives an AIMessage, or a string function receives the model’s message before the parser has turned it into text. Most pipe errors are seam mismatches, and the exception names the type at the broken seam, never the step.

The cure is the same three moves for every step: invoke it alone, print what it returns, check the type against what the next step expects. We traced the refund chain that way, with a fake model that always gives the same reply (Illustrative):

Step Receives Returns
Prompt {"question": "How long does a refund take?"} ChatPromptValue holding one human message
Chat model that ChatPromptValue AIMessage with the reply text
StrOutputParser that AIMessage the reply as a plain str
Upper-case function a str, once it sits after the parser the same text in capitals

Table 3: The refund chain traced step by step. Moving the upper-case function after the parser fixes the seam mismatch from Table 2.

Three helpers for glue code

Most of the code between prompts and models is glue, and three Runnables cover nearly all of it:

  • RunnablePassthrough: returns its input unchanged. It keeps the original question available beside a transformed copy.
  • RunnableLambda: wraps any Python function so it can sit in a pipe, for cleaning input, formatting retrieved documents or pulling out one key.
  • RunnableParallel: runs several Runnables on the same input and returns a dict of their outputs, one key per branch. Lesson 7.3 covers it in depth.

Notebook 01b combines the first two before a prompt. One branch passes the text through untouched, the other keeps the first three words longer than four characters. On “Building scalable data platforms requires careful architecture planning” the keyword branch returns building, scalable and platforms, and the prompt receives both the original sentence and that list.

Batch and stream come with it

batch and stream need no extra code, but each has a detail that changes what you see.

The default batch runs invoke once per input on a thread pool. With no max_concurrency set, the pool uses Python’s default worker count, the smaller of 32 and the CPU count plus 4 (19 workers on the 15-core machine we ran on). With exactly one input, batch skips the pool and runs inline on the calling thread. The installed source checks the count before it builds an executor:

Figure 2: How batch chooses where calls run. A one-item batch shows no speed-up by design.

A failure in one input fails the whole batch unless you pass return_exceptions=True. With it, a list of three inputs whose second raises returns the first result, the exception object and the third result, each in its slot.

A RunnableLambda that wraps a generator streams each yield. Notebook 01b’s word processor upper-cases one word at a time:

Call On “building scalable data solutions” What you get
stream 4 chunks “Processed: BUILDING”, then “Processed: BUILDING SCALABLE”, and so on up to all four words
invoke 1 string the four chunks added together end to end, with no separator

Table 4: The same generator Runnable called two ways, from a run of the notebook’s function.

The invoke result is the concatenated stream: a Runnable combines streamed chunks by adding them, which suits token deltas and garbles cumulative snapshots. A generator that yields growing snapshots belongs behind stream only.

In practice: testing each step

For the Larkspur assistant the shared interface turns into one way of testing every part:

  1. Invoke the refund prompt with a sample question and check that it returns a ChatPromptValue with the question filled in.
  2. Invoke the retriever with the same question and check that the refund paragraph of the handbook comes back.
  3. Invoke the parser on a hand-written AIMessage and check that it returns a string.
  4. Invoke the finished chain and check the answer. When it fails, steps 1 to 3 have already shown which seam is wrong.

The same three lines (invoke, print, assert) work on each of them because each is a Runnable. Lesson 7.2 shows how the pipe operator turns those separate steps into one Runnable without losing that property.

Key Takeaways

  • Every Runnable takes one input through the same methods: invoke, batch, stream and their async forms. Pass several values as a dict, which prompt templates read and RunnableParallel returns.
  • Most pipe failures are seam mismatches. Invoke each step alone, print what it returns, and compare the type with what the next step expects.
  • batch uses a thread pool except for a single input, and fails as a whole unless return_exceptions=True. A generator RunnableLambda streams each yield, and invoke adds those chunks together.

Check yourself

1. Why can the same few test lines check the Larkspur refund prompt, the retriever, the parser and the finished chain?

Each of them is a Runnable with the same fixed methods: invoke, batch, stream and their async forms. Code that runs one runs any of them, which is why the same three lines (invoke, print, assert) work on every part.

2. An existing function takes two parameters, a and b. How do you put it in a pipe?

Wrap it in a small lambda that takes one dict and calls the function with the dict’s a and b values. invoke passes exactly one argument, and a two-parameter lambda raises TypeError for the missing b. Dicts are the usual container because prompt templates read their variables from one and RunnableParallel returns one.

3. A pipe of prompt, model and your own string function fails with an AttributeError on AIMessage. Where is the bug, and how do you confirm it?

It is a seam mismatch: the string function sits right after the model, which returns an AIMessage, not a string. Invoke each step alone and print what it returns (dict, then ChatPromptValue, then AIMessage, then str). Moving the function after StrOutputParser gives it the string it expects.

This page explains where it went, starting with what | actually does.

The pipe is a Python operator

The | in prompt | model | parser is ordinary Python. a | b calls a.__or__(b), the same way 2 + 4 calls (2).__add__(4). A class decides what its operators mean: notebook 02a’s toy StupidAdder makes 5 + 10 return 57 by adding 42 on every sum. LangChain’s Runnable.__or__ returns a RunnableSequence that holds both sides, and the sequence’s invoke runs the first step and feeds its output to the next.

Notebook 02a proves this by building the mechanism from scratch. Its CRunnable.__or__ returns a CRunnableSequence holding the two sides, and the sequence’s invoke hands the first step’s result to the second. Three small steps piped together give:

Figure 1: The notebook’s hand-built pipe. Each arrow carries the previous step’s output; running it prints 10, 20 and 40 before returning “Result: 40”.

LangChain’s real RunnableSequence works the same way and adds what the toy lacks:

Capability Toy CRunnableSequence LangChain RunnableSequence
invoke feeds each output forward ✓ ✓
batch, stream and async on the whole pipe ✗ ✓
A traced child run per step ✗ ✓
Flattening: (a \| b) \| c is one sequence of three steps ✗, it nests ✓, we checked: 3 steps

Table 1: What the library sequence adds to the bare operator.

Flattening matters when you read traces. A chain assembled from smaller chains still shows one flat list of steps, and each step keeps its own latency.

A dict in a pipe runs in parallel

When the left side of | is a plain dict, Python asks the Runnable on the right through __ror__, and LangChain turns the dict into a RunnableParallel. A dict on the right side is converted the same way. Each value runs on the same input, and the output is a dict with the same keys. We reran notebook 02a’s cells, which need no API key:

Chain Input Output
x and y both RunnablePassthrough() "hello" {'x': 'hello', 'y': 'hello'}
same, with y a plain lambda reading input2 {"input": "hello", "input2": "goodbye"} {'x': {'input': 'hello', 'input2': 'goodbye'}, 'y': 'goodbye'}
x becomes a pipe: passthrough, then a function that upper-cases input the same dict {'x': 'HELLO', 'y': 'goodbye'}
x a passthrough, then .assign(extra=...) returning 100 the same dict {'x': {'input': 'hello', 'input2': 'goodbye'}, 'extra': 100}

Table 2: The notebook’s RunnableParallel runs, reproduced offline.

Two rules follow from the table. A plain lambda in a dict is wrapped in a RunnableLambda for you. A branch can be a pipe of its own, which means pipes nest inside dicts and dicts inside pipes.

Adding a key, keeping the rest

Here is the bug from the opening. A RunnableParallel replaces its input with the dict it builds. .assign(key=runnable), on RunnablePassthrough or on a parallel, computes the new key from the current dict and returns the old keys with it. On the input {"q": "refund?"} with a branch that counts characters:

Step Output
RunnableParallel(n=...) {'n': 7}
RunnablePassthrough.assign(n=...) {'q': 'refund?', 'n': 7}

Table 3: Parallel replaces the input; assign extends it. Both runs are from the installed library.

We call the parallel case the lost question: a key that a later step needs is dropped because an intermediate step rebuilt the dict from scratch. .assign() is how a pipe carries the question forward while later steps add context, then answer, then sources.

Finished chains compose like any step. Notebook 02a pipes the .assign() chain from Table 2 into a second chain that reads extra and upper-cases it as text; the result is the string '100'. Optional notebook 02b applies the same pieces to a RAG chain over a vector store.

Key Takeaways

  • The | operator calls __or__, which returns a flattened RunnableSequence that feeds each step’s output to the next and adds batch, streaming, async and tracing.
  • A plain dict in a pipe becomes a RunnableParallel: every value runs on the same input, and lambdas are wrapped for you. Pipes nest inside dicts and dicts inside pipes.
  • RunnableParallel replaces its input. Use .assign() to add a key while keeping the rest, or a later step meets the lost question.

Check yourself

1. What does Python actually do when you join two Runnables with the pipe operator, and what object comes back?

a | b calls a.__or__(b), the same way 2 + 4 calls (2).__add__(4). LangChain’s Runnable.__or__ returns a RunnableSequence holding both sides, whose invoke runs the first step and feeds its output to the next. It also flattens, so (a | b) | c is one sequence of three steps.

2. The Larkspur RAG chain starts with a plain dict of context and question. What does each value receive, and what reaches the prompt?

The dict becomes a RunnableParallel, and the question string goes to both values. The retriever turns it into documents that are joined into one string, while the passthrough keeps the question as it is. The prompt receives a dict with context and question, exactly the two variables it declares.

3. A later step needs the original question, but the RunnableParallel before it replaced its input. What should you use instead?

.assign(). RunnableParallel replaces its input with the new dict, while .assign(key=runnable) computes the new key from the current dict and returns the old keys with it. That is how a pipe carries the question forward while later steps add context, then answer, then sources.

The Larkspur support desk needs more: tickets arrive in Spanish and French and must be answered in the customer’s language, sales wants a plan comparison written from three angles at once, and every ticket must reach the chain that holds the right policy. Fan-out, then merge

Some jobs split into independent parts that meet again. The notebook writes a report on a topic from three branches:

Routing with RunnableBranch

Figure 2: The review router in notebook 03a. Conditions are tested top to bottom.

RunnableBranch takes (condition, Runnable) pairs followed by a default, tests the conditions in order, runs the first whose condition returns true, and runs the default when none does. It needs at least one pair and a default: given a single argument, the installed library raises ValueError: RunnableBranch requires at least two branches. In the notebook a dict first runs the classifier and copies instruction, review and sentiment beside its label, and the branch then picks a chain. A routed request costs 2 model calls in 2 rounds, or 1 call when the default answers with its fixed string.

We fed the notebook’s branch a set of planted labels, with stubs in place of the three model chains:

Classifier label Chain that ran Why
“Summarize” summary the conditions lower-case the label first
“Email.” email a substring test ignores the trailing full stop
“summarize and email” summary the first true condition wins; email is never tested
“translate” default, 0 model calls no condition matches

Table 2: Planted classifier labels and where the router sent them.

The third row is first-match capture: a request that matches two conditions goes to whichever comes first, silently. The same thing happens in the keyword router of notebook 01b, which checks machine-learning words before cloud words. A deployment question that mentions both models and a cloud provider is answered by the machine-learning handler, although the notebook’s own comment expects the cloud one. For the Larkspur triage router the opening ticket behaves the same way: with a refund condition ahead of an outage condition, “Refund or outage” reaches the refund chain, and “refunds” matches too because “refund” is inside it.

Planning the default

The default is where every request the classifier cannot place lands. In notebook 03a it returns a fixed apology. We call that a silent default: the request gets an answer, nothing is logged, and a classifier that has started returning new labels looks healthy. For a support desk the default should hand the ticket to a person and be counted, because a rising default rate is an early sign that the classifier has drifted.

The notebook ends with a guard of a different kind. It pipes a chain into OpenAIModerationChain, a chain class from the langchain-classic package, which screens the output before it reaches the caller. Any Runnable can take that last position, which is how output checks and guardrails attach to a pipe.

Choosing a chain shape

The three shapes answer different questions about the work:

Shape Use it when Calls and rounds (notebook examples) Main risk
Linked .assign() steps each step needs earlier results 4 calls in 4 rounds per message latency adds up step by step
Fan-out and merge parts are independent, then combined 4 calls in 2 rounds wall time set by the slowest branch
Router each input needs one of several chains 2 calls in 2 rounds, 1 for the default first-match capture and a silent default

Table 3: The three shapes compared on the notebook’s own chains.

In practice: ticket triage

A ticket triage chain for Larkspur combines all three:

  1. A dict runs the classifier and copies the ticket text and the customer’s plan beside the label, as the review router does.
  2. The classifier returns one of a fixed set of labels (refund, outage, export), which removes most multi-label answers before they reach the branch.
  3. The branch sends each label to the chain whose prompt holds that policy. Exact matches replace substring tests: “refunds” no longer passes as “refund”.
  4. The default hands the ticket to a person, and its rate is logged per day.
  5. A non-English ticket runs through the linked translation steps around whichever chain answers it.

Lesson 7.4 turns to older code: the chain classes that did these jobs before LCEL, and how to replace them.

Key Takeaways

  • Link steps with .assign() to keep every intermediate result, and use .map() to run several inputs side by side while each input’s steps stay in order.
  • Fan out with RunnableParallel and merge with one more chain. Wall time is the slowest branch plus the merge.
  • RunnableBranch runs the first true condition, which makes first-match capture the default behaviour. Constrain the labels, and make the default hand off to a person and count it.

Where the old classes went

Before LCEL, LangChain packaged each pattern as a class. In 1.x those classes left the langchain package. They live in the compatibility package langchain-classic, still run, and carry deprecation markers. We read the markers from the installed langchain-classic 1.0.8 source:

Legacy class or call Deprecated since Removal
LLMChain 0.1.17 2.0.0
RetrievalQA 0.2.13 2.0.0
StuffDocumentsChain (what load_summarize_chain returns for stuff) 0.2.13 2.0.0
Calling a chain directly, chain({...}) 0.1.0 2.0.0
Chain.run 0.1.0 2.0.0
hub.pull 1.0.6 2.0.0

Table 1: Deprecation markers in the installed source.

Each class has a short pipe that replaces it. The column that matters most for a running service is the last one:

Legacy (0.x) LCEL (1.x) What changes for the caller
LLMChain(llm=llm, prompt=prompt) prompt \| llm \| StrOutputParser() the legacy chain returns a dict with the inputs and a text key; the pipe returns a string
RetrievalQA.from_llm(llm, retriever=retriever, prompt=prompt) a dict of context (retriever, then join) and question (passthrough), then prompt, model and parser input key query and output key result become a plain string in and a string out
load_summarize_chain(llm, chain_type=...) one of three short pipes (lesson 7.5) you join the documents into the prompt’s {text} yourself
chain({...}), chain.run(...) chain.invoke({...}) the call style was replaced in 0.1.0
hub.pull("rlm/rag-prompt") the prompt written inline in a ChatPromptTemplate no network call and no untrusted object to load

Table 2: Each legacy form and its replacement.

We confirmed the output shapes with a fake chat model. LLMChain on {"adjective": "funny"} returned {'adjective': 'funny', 'text': ...}, and RetrievalQA on a refund question returned {'query': ..., 'result': ...}. A caller that reads result["result"] breaks the moment it receives a bare string. We call that a shape break, and it is the main thing a migration has to manage.

How loud a legacy chain is

You might expect the deprecation markers to warn on every use. We counted the warnings each legacy pattern emits on the installed versions, each in a fresh process:

Planted legacy code Warnings at build Warnings at call
LLMChain built directly, called as chain({...}) 1, for the class 1, for the call style
RetrievalQA.from_llm, called as qa(...) 0 1, for the call style

Notebook 05b shows the last row: the loader returns a deprecated StuffDocumentsChain and says nothing when it is built, and the only warning is about .run(), not about the class. Our run shows RetrievalQA.from_llm behaving the same way. A RetrievalQA built directly does warn, and so do the LLMChain and StuffDocumentsChain built by hand, but from_llm builds them inside the library, and inside the library they stay quiet. Notebook 04a’s Markdown expects at least two warnings from its RetrievalQA cell; on the installed versions we saw one.

This is the silent deprecation: code that keeps working until 2.0 removes it, with nothing in the logs to say so. Audits should grep for imports from langchain_classic rather than wait for warnings.

The prompt hub raises

langchain_classic.hub.pull is deprecated since 1.0.6 and hands the request to the LangSmith SDK. The installed langsmith refuses public prompts by owner and name unless the caller opts in, raising ValueError: Pulling a public prompt by owner/name is disabled by default because prompts may contain untrusted serialized LangChain objects. A hub prompt is a serialized LangChain object, so loading one can configure a model’s base URL, headers or other constructor arguments. Notebook 04a lists the options in order of preference:

  • Inline the prompt: write it into a ChatPromptTemplate. No network call and no trust decision.
  • Opt in through the SDK: pull it with dangerously_pull_public_prompt=True and accept the risk.
  • Keep hub.pull: deprecated, and it raises.

Key Takeaways

  • Legacy chain classes still run from langchain-classic but are set for removal in 2.0.0. Each has a short LCEL pipe that replaces it, usually with a plain string in and out.
  • Many legacy chains warn only when called, or not at all, when a library helper built them. Find them by grepping for imports from langchain_classic, not by waiting for warnings.
  • Migrate one chain at a time behind the same function: map the output shape, switch to .invoke(), and compare old and new answers on a fixed question set before deleting the old class.

Check yourself

1. A Larkspur service built with load_summarize_chain runs on 1.x and prints no warning when the chain is built. Why is that not proof it is safe?

load_summarize_chain returns a deprecated StuffDocumentsChain and warns nothing at build time; the only warning comes from .run(), and it is about .run(), not the class. The code keeps working until 2.0 removes it, so audits should grep for imports from langchain_classic rather than wait for warnings.

2. Callers read the result key from a RetrievalQA chain's output dict. What do they receive after you swap in the LCEL pipe, and how do you avoid breaking them?

The answer string itself, a shape break. RetrievalQA takes the key query and returns result in a dict, while the pipe takes a plain string and returns a string. Swap the chain behind the same function and have that function wrap the string back into the old shape until every caller reads a string.

3. A legacy notebook pulls rlm/rag-prompt from the hub and raises a ValueError. Which option should you take, and why?

Inline the prompt in a ChatPromptTemplate. It makes no network call and loads no untrusted serialized object. The other two options are pulling through the LangSmith SDK with dangerously_pull_public_prompt=True, which accepts the risk, and keeping hub.pull, which is deprecated and raises.

Map-reduce summarisation

Lesson 7.5: Summarization: stuff, map-reduce, refine. Notebooks: 05a_Summarization_Essentials.ipynb, 05b_Doc_Chains_to_LCEL_LangChain_v1.ipynb

What you’ll learn

  • Explain stuff, map-reduce and refine as three short LCEL patterns.
  • Count the model calls and rounds each strategy needs for a given chunk size and concurrency cap.
  • Diagnose when chunks are too small and when the reduce step itself overflows.
  • Build a router that sends short inputs to stuff and long ones to map-reduce.

Lesson 7.4 left one legacy call to replace: load_summarize_chain(llm, chain_type=...), which hid three strategies behind one string. Larkspur’s weekly digest summarises handbook changes. In a quiet week that is one section of 1,111 characters; in a release week it is the whole handbook, 2,746 characters across refunds, outages, exports and server sizing, and a real handbook runs far longer than one prompt can hold. A model reads a finite context window. The digest needs a way to summarise text that does not fit, and a way to avoid paying for that when the text does fit.

Notebook 05b writes each strategy out in a few lines of LCEL:

  • Stuff: join the documents, fill one prompt, call once. It is the cheapest strategy and the least lossy, because nothing is summarised twice, and it works only while the text fits.
  • Map-reduce: summarise each chunk on its own (the map), then summarise the summaries (the reduce). The map calls are independent, which lets batch run them on a thread pool.
  • Refine: summarise the first chunk, then revise that summary once per remaining chunk. Each call needs the previous answer, which forces the calls to run one after another.

In map-reduce the map step is one summarising chain batched over every chunk with a max_concurrency cap, and the reduce step is a second chain invoked once on the map outputs joined with blank lines. On the whole Larkspur handbook (2,746 characters) split at chunk_size=400 with an overlap of 20, that is 10 chunks:

Figure 1: Map-reduce on the whole handbook at chunk size 400 and max_concurrency=4.

A round is one wait on the model: calls in the same round run at the same time. Wall time grows with rounds, and cost grows with calls. The three strategies on the same 10 chunks:

Strategy Model calls Rounds (max_concurrency=4) Most source text in one call Parallel
Stuff 1 1 2,746 characters nothing to parallelise
Map-reduce 11 4 399 characters the map step
Refine 10 10 399 characters, plus the running summary no, by design

Table 1: Calls and rounds on the whole handbook at chunk size 400, as the lab computes them.

Notebook 05b gives the general form: stuff is 1 call, map-reduce N + 1 calls, refine N calls. The interactive lab computes all three on three handbook documents, splitting them with a port of LangChain’s RecursiveCharacterTextSplitter that matches the library on every chunk size from 200 to 1200. We reran the library splitter on the lab’s three texts and got the same chunk counts. The numbers show where each strategy wins:

  • Chunk size sets the call count. On the whole handbook, chunk size 1200 gives 3 chunks and chunk size 200 gives 21. Refine’s rounds climb from 3 to 21; map-reduce at max_concurrency=4 goes from 2 rounds to 7, and at 16 it needs only 3 rounds for all 22 calls.
  • Concurrency is what makes map-reduce fast. At max_concurrency=1 the map step is a loop, and map-reduce takes N + 1 rounds, one more than refine. Rate limits often force a low cap, so measure at the cap you can run in production.
  • Small chunks cost calls without adding much. Notebook 05a splits its 630-character sample at chunk_size=100: 11 chunks, and five of them are 31 characters or fewer, the smallest 13 and 18. Map-reduce then makes 12 calls on a text that one stuff call reads whole. We call this confetti chunking: chunks so small that the overlap fragments become calls of their own.

Where each strategy breaks

Each strategy has one failure that the call counts do not show:

Strategy Failure What happens
Stuff the text outgrows the context window the call fails or the input is cut, with no partial result
Map-reduce reduce overflow: the joined map summaries no longer fit the reduce call hits the same limit stuff did
Refine order bias: later chunks get more say the summary changes when the chunks are reordered

Table 2: The failure each strategy leaves behind.

The fix for reduce overflow is to reduce in groups and reduce the results again, the recursive summarisation that M42’s RAPTOR builds into a tree. Order bias is a feature only when later text should override earlier text, such as a changelog where the newest entry wins. Notebook 05b suggests running its refine loop with the documents reversed to see the effect.

Writing the strategies out also opens choices the loader could not express: a smaller model for the many map calls and a larger one for the single reduce, or a retry wrapped around the map chain so one failed chunk does not sink the batch.

Routing by length

Stuff is the best strategy whenever it fits, which means the summariser should decide per input. This is the module’s lab brief in miniature: rebuild load_summarize_chain as LCEL, then add a branch that routes short and long inputs differently. The branch is a RunnableBranch with one condition, the text is 1,500 characters or fewer, which sends the input to the stuff chain; the default is the map-reduce chain:

Figure 2: The length router. Stuff for what fits, map-reduce for the rest.

We ran a real RunnableBranch with that condition on the lab’s three documents and on the edges of the limit:

Input length Strategy chosen
1,111 (refunds section) stuff
1,500 stuff
1,501 map-reduce
1,833 (refunds and outages) map-reduce
2,746 (whole handbook) map-reduce

Table 3: The length router on the lab’s documents. The lab’s routing matches on all three.

The 1,500-character limit stands in for a context budget. In production, count tokens with the model’s tokenizer and set the limit to the context window minus the prompt template and the room the answer needs.

The two branches return the same type, a summary string, and callers never see which strategy ran. Log it anyway: when the share of map-reduce runs rises, documents have grown, and cost and latency will follow.

In practice: the weekly digest

The digest job puts the page together:

  1. Join the week’s changed sections into one text, the step load_summarize_chain used to do for you.
  2. Route it by length. A quiet week (the 1,111-character refunds section) goes to stuff: 1 call.
  3. A release week (the whole handbook at chunk size 400) goes to map-reduce: 10 map calls, 4 at a time, then 1 reduce call, 11 calls in 4 rounds.
  4. If the joined map summaries exceed the budget, reduce them in groups and reduce again.
  5. Log the strategy and the call count for every run.

Key Takeaways

  • Stuff makes 1 call, map-reduce N + 1 and refine N. Cost grows with calls and wall time with rounds, and only map-reduce can run its calls in parallel.
  • Chunk size sets the call count, and concurrency is what makes map-reduce fast. Measure at the concurrency cap your rate limit allows, and avoid confetti chunking.
  • Route by length: stuff whatever fits and map-reduce the rest. Set the limit from a token budget, and log which strategy ran.

Check yourself

1. Why is stuff the best summarisation strategy whenever the text fits in one call?

It is the cheapest and the least lossy. It joins the documents into one prompt and calls the model once, so nothing is summarised twice. Map-reduce and refine exist only because a long text does not fit, which is why the router sends short inputs to stuff.

2. The Larkspur handbook splits into 10 chunks at chunk size 400. How many model calls and rounds does map-reduce need at a max concurrency of 4, and how does refine compare?

Map-reduce makes 11 calls in 4 rounds: 10 map calls, 4 at a time over 3 rounds, then 1 reduce. Refine makes 10 calls in 10 rounds, because each call needs the previous summary. At max_concurrency=1 map-reduce would take N + 1 rounds, one more than refine.

3. Your length router sends anything over 1,500 characters to map-reduce. In production, what should replace that limit, and what should you log?

A token budget: count tokens with the model’s tokenizer and set the limit to the context window minus the prompt template and the room the answer needs. Log which strategy ran, because a rising share of map-reduce runs means documents have grown, and cost and latency will follow.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s nightly job runs triage_chain.batch() over 2,000 support tickets. Last night it died at ticket 1,412 with a rate-limit error and wrote nothing. What do you change?

What a strong answer covers:

  • Caps parallel calls with config={"max_concurrency": n} sized to the provider’s rate limit, since the default is Python’s thread-pool size
  • Wraps the model step in .with_retry() so a transient 429 retries that call instead of failing the batch
  • Passes return_exceptions=True so one bad ticket returns an exception in its slot and the other 1,999 results survive
  • Writes results in pages (or checkpoints them) and adds .with_fallbacks([...]) to a second model if outages are common

2. Product wants a weekly digest of every handbook change. Some weeks one paragraph changes; in release weeks, 40 pages do. Which summarisation strategy do you build?

What a strong answer covers:

  • A RunnableBranch on input length: stuff below a token budget (one call, nothing summarised twice), map-reduce above it
  • Map-reduce for the long case: the map step parallelises, so latency is about one map round plus the reduce, and every chunk is treated the same
  • Refine only if later changes should override earlier ones, accepting one sequential call per chunk and order sensitivity
  • A guard for the reduce step itself: if the joined summaries exceed the budget, reduce in groups and reduce again

3. The support chain routes tickets with a classifier and a RunnableBranch. How do you find out, in production, which branch each ticket took and which branch is slow?

What a strong answer covers:

  • Traces every run (LangSmith or any callback handler); a pipe records each step as a child run with its own latency
  • Names the steps with .with_config(run_name=...) and tags runs with metadata such as ticket id and plan, so traces can be filtered
  • Logs the classifier’s raw output next to the chosen branch, since a wrong route usually starts as an unexpected label
  • Dashboards the share of tickets per branch and the default-branch rate, which rises when the classifier drifts

4. The ticket classifier returns “Refund.” for most refund tickets, but for one ticket it returns “Refund or outage”. The branch conditions are "refund" in label and "outage" in label. What happens, and how do you make routing safe?

What a strong answer covers:

  • RunnableBranch tests conditions in order and runs the first true one, so the ticket silently goes to the refund chain
  • Substring checks on free text are fragile: punctuation, case and multi-label answers all route somewhere
  • Constrains the classifier with structured output (an enum of labels) and validates it before the branch
  • Keeps a default branch that escalates to a human, and counts how often it fires

5. You inherit a Larkspur service built on RetrievalQA, LLMChain and hub.pull("rlm/rag-prompt") on LangChain 0.x. How do you migrate it to 1.x without breaking the API that callers use?

What a strong answer covers:

  • Repoints imports to langchain_classic first so the service runs on 1.x, then rewrites chain by chain behind the same interface
  • Replaces RetrievalQA with {"context": retriever | format_docs, "question": RunnablePassthrough()} | prompt | llm | StrOutputParser(), and maps the output shape: the legacy chain returns a dict with query and result, the pipe returns a string
  • Inlines the prompt, because hub.pull is deprecated and raises for public prompts on the repo’s pinned langsmith
  • Replaces every chain(...) and .run() call with .invoke(), and compares old and new answers on a fixed question set before switching

Key Takeaways

  • Every component and every chain shares one interface, so test each step alone with .invoke() before you pipe it.
  • Build data flow with dicts: a dict fans one input out, and RunnablePassthrough.assign() adds a key while keeping the rest.
  • Write new chains as pipes. Treat langchain_classic imports as a staging post for old code, never as a destination.
  • Choose a summarisation strategy by length and latency: stuff when it fits, map-reduce when it does not, refine only when order should matter.
