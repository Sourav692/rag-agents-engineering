M08 LangGraph core

A LangGraph application is a state object and the functions that update it. Nodes read the state and return a partial update, a reducer per key decides how that update merges, and edges, fixed or conditional, decide which node runs next. Agentic RAG, memory and multi-agent systems later in the course are all built from these parts. The M08 notebooks build on four ideas: the graph and its state, the reducers that merge updates, conditional edges that route on state, and Command, which updates and routes in one return.

Open the lab

The running example is a Larkspur Cloud support graph over the same handbook as M10 to M12. A classify node reads the customer’s question and writes a route; a conditional edge sends it to a billing, technical or human node; the handler answers from the handbook. The notebooks use their own small demos (weather, comic books, a temperature alarm), and they ship without saved outputs. Every figure and error message on these pages comes from running the notebooks’ code, or small variations of it, against the installed LangGraph 1.2.18, or from the lab, which matches that version’s graph on all 24 of its settings.

TL;DR

  • A StateGraph is a schema, nodes that return partial updates, and edges from START to END. compile() turns it into a runnable; invoke returns the final state and starts from a fresh state every call.
  • Each state key can have a reducer. Without one, the last write wins. In the lab the support graph ends with 1 message and no question when nodes return only their new message, with 3 under add_messages, and with 7 (four copies of the question) when operator.add meets nodes that return the whole list.
  • A conditional edge calls a router after its source node and goes to the node name it returns. A name outside the destination list raises KeyError, and the order of the router’s rules decides close calls: Can I export my data after I cancel my plan? goes to billing.
  • Command(update=..., goto=...) writes and routes in one return. Its Literal annotation only draws the graph; a goto to a node that does not exist ends the run with a logged warning and no error.
  • TypedDict state is hints only, and Pydantic state validates the input at invoke before any node runs, though not what nodes write. Input and output schemas hide private keys; config and runtime context carry settings and dependencies that are not state.

Mental model

Every node gets the whole state and returns only the keys it changes. Between nodes the graph merges each returned key with that key’s reducer, so a node never sees another node’s raw return value, only the merged state. The three-way choice after classify is a conditional edge: a plain function reads route and names the next node.

StateGraph

A StateGraph is a graph whose nodes share one state object: each node reads the state and returns the changes it wants to make. It has three parts:

  • State: a schema, usually a TypedDict, naming the keys every node can read.
  • Node: a plain function that takes the state and returns a dict holding only the keys it changes.
  • Edge: which node runs next. START and END mark the entry and the exit.

The Larkspur support graph maps onto those parts like this:

Part In the Larkspur support graph What it decides
State messages, route, answer what every node can read
Nodes classify, billing, technical, human the work, one partial update each
Fixed edges START to classify; each handler to END the steps that always happen
Conditional edge classify to one handler, chosen from route the branch (lesson 8.2)

Table 1: The parts of a StateGraph in the running example.

Building a graph and running it are separate phases. You declare the schema, add nodes and edges to a builder, and call compile(), which checks the wiring and returns a runnable. Then invoke runs it on an input and returns the final state:

Two habits from the notebooks keep graphs readable.

  1. Return partial updates. A node returns only the keys it changed, never the whole state, and each return shows exactly what that node did.
  2. Keep state for data. State holds what the graph works on. Per-call settings and dependencies, such as a database client, go elsewhere (lesson 8.4 and lesson 8.5).

The second and third rows of Table 2 differ only in the rule attached to the key, and that rule has a name.

Reducers

A reducer is the function that decides what a node’s write does to one key of the state. Without one, the write replaces the value. With one, LangGraph calls it with the current value and the update, and stores the result:

Figure 2: What happens to each key a node returns.

You attach a reducer in the schema by annotating the key’s type with a function, Annotated[type, function]. The function receives two arguments, the current value and the update. The basics notebook starts from a count of 5 and the animals lion and tiger, then runs one node that returns a count of 1 and the animal cat:

Schema Final count Final animals
No reducers 1 cat
custom_increment on count, operator.add on animals 6 lion, tiger, cat

Table 3: One node’s write under two schemas (notebook rerun on LangGraph 1.2.18).

The same write gives different states. The node never decides how its output merges; the schema does.

The message reducer

add_messages is the reducer built for chat histories, and the one MessagesState uses. It does four things:

  • Appends new messages to the list.
  • Assigns an id to every message that lacks one.
  • Replaces a message whose id is already in the list, instead of adding a second copy.
  • Converts a bare string into a HumanMessage.

The last rule plants a quiet failure. In the basics notebook, the input and three nodes each write a plain string, and the final list holds four HumanMessage objects. We call this speaker drift: the assistant’s replies are stored as if the customer said them, and a model reading that history sees four customer turns. A node that speaks as the assistant returns an AIMessage.

Planted failures: return style

A reducer and the nodes’ return style have to agree. The lab runs the Larkspur graph under each reducer, once with nodes that return only their new message and once with nodes that return the whole list plus their message. Messages in the final state for the refund question:

Reducer on messages Node returns its message Node returns the whole list
None (overwrite) 1, and the question is lost 3
operator.add 3 7, the question four times
add_messages 3 3

Table 4: Final message counts in the lab for each reducer and return style.

Each bold cell, plus one fragile cell, is a named failure:

  • Lost question (overwrite, new-message returns). After classify, the list holds only its route message. The billing node has nothing to answer and the structured answer has no source. This is the failure the page opened on.
  • Copy discipline (overwrite, whole-list returns). It works, but only while every node copies the list forward. One node written the other way erases the history.
  • Doubling history (operator.add, whole-list returns). Each node returns the current list plus one message, and operator.add concatenates that onto the current list. A list of n messages becomes 2n + 1: 1, then 3, then 7. A third step would give 15, and a chat-model node would read, and bill for, every copy.

add_messages gives 3 either way, because the copied messages already carry ids and replace themselves. Try each cell in the reducer lab, which prints the list after every step:

Reducers matter a second time when nodes run in parallel. If two nodes in the same step write a key that has no reducer, LangGraph 1.2.18 stops the run with InvalidUpdateError: At key 'out': Can receive only one value per step. With operator.add on the same key, the run ends with both writes in the list. The fan-out patterns in M24 give such keys a reducer for this reason.

The rule that follows: decide the reducer for every key that more than one node writes, then hold every node to one return style.

In practice: the refund question

Here is the refund question through the graph with add_messages on messages and nodes that return only their new message, as the lab runs it:

  1. Input. The caller sends the question. State: 1 message.
  2. classify reads the question, finds the billing word refund, writes route as billing and appends a route message. State: 2 messages.
  3. The conditional edge reads route and sends the run to billing.
  4. billing still sees the question, matches it to the handbook’s refund-timing page, writes answer and appends its reply. State: 3 messages, one of them the customer’s.

The answer key holds the route (billing), the source (refund-timing) and the page’s text: refunds take 5 to 10 business days to appear on the statement.

Next lesson: step 3 is a conditional edge. Lesson 8.2 opens it up: what the router may return, what happens when it returns a name no node has, and why the order of its rules decides close calls.

Key Takeaways

  • A graph is state, nodes and edges. Have each node return only the keys it changes, and keep settings and dependencies out of the state.
  • A key with no reducer is replaced on every write. Attach one with Annotated[type, function] when a key should accumulate, as messages does with add_messages.
  • Match the reducer to what nodes return. operator.add with whole-list returns grows 1, 3, 7 messages, while add_messages stays at 3 because ids replace duplicates.

Check yourself

1. What does a reducer decide, and what happens to a key that has none?

A reducer decides what a node’s write does to one key; LangGraph calls it with the current value and the update. Without one, the write replaces the value. Three nodes writing strings into a key with no reducer leave only the last string, “Hello this is the final node”, and the original input is gone after the first node.

2. The state starts as count 5 and animals lion and tiger. A node returns count 1 and animals cat. What is the state with custom_increment on count and operator.add on animals?

A count of 6 and the animals lion, tiger and cat. Each reducer combines the current value with the update. Without reducers the same write gives a count of 1 and the animal cat alone.

3. The Larkspur graph with operator.add on messages ends with 7 messages, the question four times. What went wrong, and what fixes it?

The nodes return the whole list plus their message, and operator.add concatenates that copy onto the current list: 1, then 3, then 7 messages. This is the doubling history. Either have each node return only its new message, or use add_messages, which gives 3 either way because the copied messages carry ids and replace themselves.

Lesson 8.1 followed the refund question through the Larkspur support graph and stopped at step 3, where a conditional edge read route and picked the billing handler. That step is where most routing bugs live.

Here it fails. A customer asks Can I export my data after I cancel my plan? It is a question about data: the customer wants the export page and the 30-day retention window. The graph sends it to billing, and the billing node answers from the cancellation page. Every step ran, nothing raised, and the answer is about the wrong thing.

The one-line reason: the router is plain code that checks its rules in order, and LangGraph trusts whatever name it returns. This page covers what a router may return, what happens when the name is wrong, and what changes when a chat model makes the decision or writes the answer.

Conditional edges

A conditional edge is an edge whose target is chosen at run time: after its source node finishes, LangGraph calls a routing function on the state and goes to the node whose name it returns. A fixed edge always goes from A to B. A conditional edge goes from A to whichever node the router names.

You register one with the source node, the router and, optionally, the list of nodes it may return. The Larkspur router reads the words of the question and checks two rule sets in order, billing words first:

Figure 1: The Larkspur router. The first rule that matches wins.

Three rules follow from the table.

  1. Pass the destination list. It turns a bad name into an exception, and it is what lets the drawn graph show its branches. A silent dead end returns a final state with no answer, and the error logs stay empty.
  2. Keep the router read-only. It runs between nodes, and LangGraph 1.2.18 throws away any change it makes to state. A retry counter or a “reason for the route” must be written by a node, such as classify, before the router runs.
  3. Give the router a fallback. The comic router’s node_others and Larkspur’s human turn a gap in the rules into a handoff instead of an error: Can I pay by bank transfer? matches no rule and reaches a person.

Rule order is the failure the page opened on. The export question contains two billing words and two technical words, and the billing rule is checked first. The reducer lab prints the route and the answer source for each of its four questions, including this one.

A model can make the decision instead of keywords. The classify node asks a chat model for a label, writes it to route, and the router stays a one-line read. The model call then sits in a node, where it can be retried and traced, and the edge stays testable without a model. M24 builds its routing workflow this way.

M30 does the same at a larger scale, routing each question between knowledge bases. A model call inside a node is the next thing to look at.

A chat model inside a node

A node that calls a chat model is an ordinary node: it reads the messages from state, calls the model, and returns the reply under messages for add_messages to append. The chatbot notebook builds the smallest such graph: one chatbot node between START and END, on gpt-4o-mini. Its replies change from run to run, and we describe them as the notebook states them.

With a stub in place of the model, the same graph shows its mechanics exactly:

Call What comes back Size

The forgetful chatbot

The graph keeps no memory between calls. Each invoke starts from the input you pass. The notebook asks two questions in separate calls, then asks What did we discuss so far? in a third, and the model has nothing to report: the follow-up reaches it on its own.

Figure 3: Two invoke calls. Nothing from the first call reaches the second.

The basics notebook from lesson 8.1 works around this by hand: the second call’s input is the first call’s final messages plus the new question. That works, and it has a cost the caller carries. Each turn resends the whole history:

Turn Messages sent to the graph Messages the model reads
1 1 (q1) 1
2 3 (q1, reply 1, q2) 3
3 5 5
n 2n - 1 2n - 1

Table 4: History passed by hand. Counted from the pattern: one question and one reply per turn.

The message count grows with every turn, and every caller has to store and resend it correctly. M09 moves that job into the graph with a checkpointer that saves the state per conversation thread.

Choosing a router

The routing decision can live in three places:

Router Strength Main risk
Keyword rules in the router fast, free, testable without a model rule-order capture; misses paraphrases
Model label written by classify handles meaning and paraphrase a model call per question; labels drift with the prompt
Fallback branch (human) turns a gap into a handoff hides a rising miss rate unless you count it

Table 5: Where the routing decision can live, with the risk each one carries.

The three combine well: a model label, a router that reads it, and a fallback whose rate you count. Whichever decides, the edge still passes a destination list.

In practice: the export question

Here is the opening failure again, step by step, as the lab runs it with add_messages:

  1. classify splits Can I export my data after I cancel my plan? into words and checks the billing rule first. cancel and plan match, and it writes route as billing. The technical words export and data are never checked.
  2. The conditional edge reads route and sends the run to billing.
  3. billing finds its best page among the billing pages, cancel, and answers that cancelling stops the next charge.
  4. The customer, who asked about exporting data, gets no word about the export page or the 30-day retention window.

Reordering the rules would only move the capture: billing questions that mention data would then go to technical. The fix is a router that reads meaning, a model label written by classify, measured against a labelled set of Larkspur questions before each change.

Key Takeaways

  • Always pass the destination list to a conditional edge. With it an unknown route fails loudly; without it the run ends silently and the drawing shows no branches.
  • A router only reads state, and checks its rules in order. Write anything the route needs from a node, and add a fallback route such as human for questions no rule matches.
  • A graph keeps no memory between invoke calls. Use stream_mode="updates" to see which node changed what, and a checkpointer for conversation history.

1. The chatbot answers one question, and a second invoke asks it what was discussed so far. Why can it not say?

The graph keeps no memory between calls. Each invoke starts from the input you pass, and the second question reaches the model on its own. Passing the first run’s messages plus the new one works around it, at the cost of resending the history every turn; M09 replaces that with a checkpointer that saves state per thread.

2. The Larkspur router gets the question about exporting data after cancelling a plan. Which node answers it, and why?

The billing node, from the cancellation page. The router checks the billing words first, and cancel and plan match before the technical rule sees export and data. This is rule-order capture: the order of the rules decides the close calls, even when the question is really about data.

3. You leave the destination list out of the conditional edge, and a run whose router returns an unknown name ends with no error and no answer. What happened?

Lesson 8.2 ended with a router that trusts whatever is in the state. Every node so far has done the same.

Here is that trust failing. Larkspur’s support graph sits behind a web widget, and a client bug sends the question as a ticket number, 123, instead of text. The state schema says the question is a string. The run starts anyway, classify tries to split the number into words, and the graph fails inside the first node with an error about an int. With a model call in that node, the failure would also have cost a request.

The one-line reason: a TypedDict annotation is a hint for people and editors, and LangGraph checks no types against it. This page compares the four schema kinds by what they check, and when.

Choosing a state schema

A state schema is the type you pass to StateGraph to declare the state’s keys, their types and their reducers. StateGraph accepts four kinds, and the schemas notebook runs the same two-node graph on each. The wiring, the nodes and the reducers (custom_add on step_count, add_messages on messages) stay the same. The choice changes how nodes read the state and where a bad input is caught. Measured on LangGraph 1.2.18:

Schema Nodes read Defaults Wrong type in the input
dict state["key"] none accepted
TypedDict state["key"] none accepted
@dataclass state.key yes accepted
Pydantic BaseModel state.key yes ValidationError at invoke

Table 1: The four schema kinds by how nodes read them and what they check.

  • dict has no schema at all, and so no place to attach a reducer.
  • TypedDict names keys and types, and checks neither.
  • @dataclass adds defaults (private_data: str = "") and passes nodes an instance, but checks no types.
  • Pydantic checks the input against the model before the first node, and converts values where it can.

Both nodes in the schemas notebook return one message and a step_count of 1. We reran all four builds:

Schema Final messages Final step_count Type invoke returns
dict only “Step B Completed” 1 dict
TypedDict 2 messages 2 dict
@dataclass 2 messages 2 dict
Pydantic 2 messages 2 dict

Table 2: The schemas notebook’s two-node graph under each schema (rerun on LangGraph 1.2.18).

The dict row is lesson 8.1’s lost write again: with no schema there are no reducers, and node B’s write replaces node A’s. The last column holds for every schema. Nodes of a dataclass or Pydantic graph receive an instance, yet invoke hands the caller a plain dict.

Where a bad input stops

The validation notebook builds a one-key graph (name: str) whose node appends a greeting to the name, then feeds it a number. We planted that case and its neighbours on each schema:

Planted case What happened Where
TypedDict, name is 123 TypeError: unsupported operand type(s) for +: 'int' and 'str' inside the node
TypedDict, name missing KeyError: 'name' inside the node
dataclass, name is 123 the node receives the int 123; no error nowhere
Pydantic, name is 123 ValidationError; no node runs at invoke
Pydantic, name missing ValidationError; no node runs at invoke
Pydantic, “5” for an int field the node receives the int 5; the returned state still holds the string “5” converted for nodes only
Pydantic, a node writes 5 into the str field no error; the final state holds 5 nowhere
Pydantic input_schema on a TypedDict state, question 123 the number reaches the first node, which fails inside the node

Table 3: One planted case per check, on LangGraph 1.2.18. The first and fourth rows are the validation notebook’s own runs.

Two named failures come out of this table.

  • Late failure. A bad input passes the schema and fails deep inside a node, after any work that node did first. The TypedDict and dataclass rows show it. The error names an operand, not the field the caller got wrong.
  • Unchecked write. Pydantic validates what comes in, never what nodes write. A node that returns 5 for a str field finishes cleanly and leaves a wrong type in the state for every later node.

The last row is a trap worth naming separately. An input schema narrows which keys a caller may send (lesson 8.5). Made from a Pydantic model on a TypedDict state, it still let the number through on LangGraph 1.2.18. The type check comes from the state schema itself.

Which schema, when

Validation costs a parse on every invoke, small next to a single model call. A TypedDict stays the right choice for a graph whose only callers are your own code and tests, where a late failure is a bug you will see in a stack trace.

In practice: the widget question

For Larkspur the question arrives from a web widget, and the state schema itself becomes a Pydantic model: question as a string, with route and answer given defaults.

  1. The client bug returns. The widget sends 123 as the question. invoke raises ValidationError naming the question field. No node runs and no model is called.
  2. A real question arrives. When will my refund appear on my statement? passes validation, and classify receives an instance with question as text.
  3. The billing node answers. Pydantic will not check what it writes. The node builds its structured answer (route, source, text) as a Pydantic model of its own before returning it, and a malformed answer fails inside the node that produced it.
  4. The caller reads the result. invoke returns a plain dict holding every key. Lesson 8.5 narrows that to the answer alone.

Next lesson: every node so far has taken one argument, the state. Lesson 8.4 shows what else a node can ask for, and how a node can route the run by itself.

Key Takeaways

  • TypedDict and dataclass annotations check no types, so a bad input fails late, inside a node. A plain dict cannot attach reducers at all.
  • Use a Pydantic state schema when input comes from outside. It raises ValidationError at invoke before any node runs, and converts values for nodes where it can.
  • Pydantic validates input only, never what nodes write, and invoke always returns a plain dict. Validate important node output, such as a structured answer, inside the node.

Check yourself

1. A graph with a TypedDict state receives a name of 123, and its node fails with a TypeError. Why did the schema not stop it?

TypedDict annotations are hints for people and editors; LangGraph checks no types against them. The run starts and the node fails when it adds a string to the int: a late failure. With a Pydantic BaseModel state, the same input raises ValidationError at invoke and no node runs.

2. The Larkspur question arrives from a web widget. Why make the state schema itself Pydantic instead of adding a Pydantic input schema to a TypedDict state?

On LangGraph 1.2.18 a Pydantic input schema on a TypedDict state let a question of 123 through to the first node, which failed there. The type check comes from the state schema: with a Pydantic state the same input stops at invoke before any node runs.

3. A node in a Pydantic-state graph returns 5 for a str field, and the run finishes cleanly. How should Larkspur protect its structured answer?

Validate it in the node. Pydantic checks what comes in at invoke, not what nodes write, and the final state simply holds 5: an unchecked write. A node whose output matters builds its answer as a Pydantic model before returning it, and a bad answer then fails in the node that made it.

Node signatures and runtime context

A node’s signature decides what LangGraph passes into it: the state always, and, if the node declares them, the run’s config or its runtime context. A node asks for more by declaring a second parameter:

Signature The node also gets Larkspur use
f(state) nothing classify reads the question
f(state, config: RunnableConfig) config["configurable"] the thread_id for logs
f(state, runtime: Runtime[Ctx]) runtime.context the customer’s plan, a database client

Table 1: The three node signatures.

The node patterns notebook chains one node of each kind and invokes the graph with a state of input “World”, a config holding thread_id “user-1234” and a context holding user_id “alice_smith”. The plain node writes “Hello, World!”, the config node reads the thread id, and the runtime node reads the user id. None of the config or context values appears in the final state.

The graph declares its shape with a context_schema, and each invoke passes values in a context argument. Command

Command is a value a node returns instead of a dict to do two jobs at once: update is merged into the state like any node’s return, and goto names the node that runs next. The Command notebook’s check_temp_node sends a reading above 90 to warn_user with warning_sent set, and anything else to success. No edge leaves the node, and none leaves either handler, which end the run:

The Command traps

The node’s return annotation, Command[Literal["warn_user", "success"]], looks like a check, and the notebook calls it compile-time safety. On LangGraph 1.2.18 it only draws the graph. We planted one case per assumption:

Planted case What happened Named failure
Literal annotation removed routing still works; the drawing shows the node going straight to END invisible branches
goto names a real node missing from the Literal that node runs no check
goto names a node that does not exist logs “wrote to unknown channel branch:to:nowhere, ignoring it”; the run ends with no handler output silent dead end
static edge to success added; reading 95 warn_user and success run in the same step, both write final_action_performed: InvalidUpdateError double dispatch
same static edge; reading 40 runs: goto and the edge name the same node hidden until a hot reading

Table 4: One planted case per assumption about Command.

The silent dead end is the one from lesson 8.2, reached by a different road: a misspelled goto ends the run with an empty answer and no error. Double dispatch comes from goto adding to static edges rather than replacing them. It also hides: the cool reading passes, and only a hot reading triggers it.

Which one, when

The choice turns on whether the deciding node must also write:

Figure 3: Choosing between a conditional edge and Command.

Choose a conditional edge when routing is a pure read of state. The router is testable alone, and the destination list names every target at build time. Choose Command when the node that decides must also write, such as the route with its reason, or when the target lies outside the current graph.

In practice: classify with a reason

In this design classify takes the runtime parameter and returns a Command:

  1. The call. The widget invokes the graph with the question as state, the conversation’s thread_id in config, and the customer id and database client as context.
  2. classify reads the customer’s plan through the client in runtime.context, matches refund, and returns Command with route billing and the reason “matched refund” as the update, and billing as the goto.
  3. billing answers. The final state holds the route and its reason for the triage log. The client and customer id appear nowhere in it.
  4. The guard. A test runs one question per route and asserts that every run ends with an answer key. A misspelled goto fails that test instead of shipping as a silent dead end.

Next lesson: the final state still returns every key, including the reason and the message history. Lesson 8.5 decides what a caller may send and receive, and where per-call settings such as the reply language go.

Key Takeaways

  • A node gets extra inputs by declaring them: config for per-call settings, runtime for typed context. Absent context fails only when a node reads it.
  • Command(update=..., goto=...) lets a node write and route in one return. Its Literal annotation only draws the graph, and a goto to an unknown node is silently ignored.
  • Use a conditional edge when routing is a pure read of state, and Command when the deciding node must also write. Never combine goto with a static edge from the same node.

Check yourself

1. When should a node return a Command instead of leaving the route to a conditional edge?

When the node that decides must also write, such as the route with the reason for it, or when the target lies outside the current graph. When routing is a pure read of state, a conditional edge is better: the router is testable alone and the destination list names every target at build time.

2. The temperature node that returns a Command also gets a static edge to success, and a reading of 95 arrives. What happens?

The run fails. A reading above 90 makes the node goto warn_user, and goto adds to static edges, so warn_user and success run in the same step. Both write final_action_performed, and LangGraph raises InvalidUpdateError: double dispatch. A reading of 40 passes, which is why the bug hides.

3. A node reads user_agent from runtime context and fails with an AttributeError on NoneType. What went wrong?

The graph was invoked with no context, and runtime.context was None. On LangGraph 1.2.18 absent context fails when a node reads it, not when the graph starts. Pass it in the context argument and include user_agent, which has no default; an empty context raises TypeError for it.

Lesson 8.4 gave classify a route reason in state and a database client in runtime context. Every key in state still goes back to whoever called the graph.

Here is what that costs. The Larkspur widget receives the whole final state: the messages, route, the route reason and a counter of model calls. A widget developer starts reading route to choose an icon. Months later the graph team renames route during a refactor, no test in the graph fails, and the widget breaks in production. The key was never meant for callers, and nothing said so.

The one-line reason: with one schema, the state is the graph’s public interface. This page separates the two, then sorts the values a node needs into state, config and context.

Input, output and private state

An input schema and an output schema are narrower views of the state: the caller may send only the input schema’s keys and receives only the output schema’s keys, while nodes keep reading and writing the whole state. The advanced state notebook starts from one schema with question, answer and llm_calls, a counter the node bumps on each model call. It then splits that state into four schemas:

Schema Keys Who sees it
Input question the caller, on the way in
Private llm_calls nodes only
Output answer the caller, on the way out
Overall all three, by inheriting from the other three every node

For the Larkspur support graph, the input is the question and the output is the structured answer (route, source, text). The message history, the route reason and the top-level route key stay private. That is what lets the team rename or add internal keys without breaking the widget: the leaked key from the opening never leaves the graph.

Config, context or state

Some values a node needs are not data the graph works on. In the advanced state notebook, the model node reads a language setting from config["configurable"], falling back to English, and puts it in a system message. The notebook asks the same mountain question in Spanish, then in German, from one compiled graph. We confirmed the plumbing with a stub: language reaches the node, defaults to English when the config has none, and never appears in the returned state.

Config holds per-call settings; runtime context holds dependencies; state holds the data the graph reads and changes. Each place has one job:

Place Holds Returned?
State data the graph reads and changes yes, through the output schema
config["configurable"] per-call settings: language, thread_id no
Runtime context dependencies: clients, the caller’s identity no

Table 4: The three places a node’s inputs can live.

Putting a client or a secret in state is the usual mistake, and we call it state as a junk drawer. State is returned to the caller. Once M09 adds a checkpointer, state is also saved after every step, and a secret in it is written to storage on every turn. The thread_id in config is what that checkpointer uses to find a conversation’s saved state.

In practice: the widget contract

The Larkspur support graph, with every value in its place:

  1. The widget sends the question, which the input schema admits, plus a config with the reply language and the conversation’s thread_id.
  2. The server adds the customer id and the database client as runtime context. The widget never sees either.
  3. The nodes run on the full state: messages, route, the route reason, the answer.
  4. The widget receives only the structured answer. A refactor that renames route changes nothing it can see.

That completes the boundary of one run. M09 makes runs remember each other, using the thread_id this page placed in config.

Key Takeaways

  • Give a graph separate input, private and output schemas, so callers send only the question and receive only the answer. Internal keys can then change without breaking callers.
  • A TypedDict output schema filters keys but checks no types. Type checks come from a Pydantic state schema and cover input only.
  • Put data the graph changes in state, per-call settings such as language and thread_id in config, and clients and identity in runtime context. Never put a client or secret in state.

Check yourself

1. Why split a graph's state into input, private and output schemas when the nodes still read and write every key?

Because only what crosses the boundary changes. The caller sends the question and gets the answer, and bookkeeping such as llm_calls stays private, where no caller can depend on it or set it. For Larkspur, that leaves room to rename or add internal keys without breaking the web widget.

2. The Larkspur graph needs a reply language, a thread id, a customer id and a database client. Where does each one go?

The reply language and the thread_id go in config["configurable"], as per-call settings. The customer id and the database client go in runtime context, as dependencies. Neither place is returned; state holds only the question, the route and the answer the graph works on.

3. A teammate puts the database client and a secret in state. Why is that a mistake, and why does it get worse once a checkpointer is added?

State is returned to the caller, and the client and the secret leave the graph with the answer. Once M09 adds a checkpointer, state is also saved after every step, and the secret is written to storage on every turn. Dependencies and secrets belong in runtime context, which is never returned.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. After a refactor of Larkspur’s support graph, token cost per conversation doubles and the model starts repeating the customer’s question back. No test fails. What do you look for?

What a strong answer covers:

  • Prints the messages list after each node with stream_mode="values" and counts copies of the first human message, rather than reading the final answer
  • Checks the reducer on messages and what each node returns: operator.add with a node that returns state["messages"] + [msg] doubles the list on every step (1, 3, 7 in the M08 lab)
  • Fixes it at the schema with add_messages, which replaces messages with a known id, or by returning only the new message, and keeps one convention across the graph
  • Adds a test that asserts the message count and the number of human messages after a two-node run

2. The triage step can be a conditional edge reading route, or a classify node that returns Command(goto=...). Which do you choose for Larkspur, and what changes in testing and debugging?

What a strong answer covers:

  • A conditional edge keeps routing a pure function of state: it can be unit-tested without the graph, and the graph shows every destination at build time
  • Command fits when the node that decides also writes, for example the route plus the reason for it, in one return
  • Names the Command traps: the Literal annotation is only for drawing, a misspelled goto ends the run with a warning, and a static edge from the same node runs as well
  • Logs the route in state either way, so a trace shows which branch ran and why

3. How do you know, week by week, that the router sends questions to the right handler?

What a strong answer covers:

  • Keeps a labelled set of real questions with the handler each should reach, and runs the router alone against it on every rule or prompt change
  • Reads the confusion matrix as well as accuracy: a billing question sent to technical costs less than a refund question sent nowhere
  • Tracks the route distribution and the fallback rate in production; a jump in human handoffs after a release means the rules stopped matching
  • Samples close calls such as Can I export my data after I cancel my plan?, where rule order, not meaning, picked billing

4. A release renames the technical node to tech_support. The router node returns Command(goto="technical"). Outage questions now get no answer and the error rate stays at zero. Why, and how do you stop it happening again?

What a strong answer covers:

  • In LangGraph 1.2.18 a goto to a missing node logs “wrote to unknown channel … ignoring it” and the run ends normally with no answer key
  • Finds it in the output: the final state has no answer key, so a caller that reads it gets nothing, while the error logs stay empty
  • Prevents it with names held in one constant or enum, a test that every route reaches an answer node, and an alert on runs that end without an answer
  • Notes that a conditional edge with a destination list fails loudly instead, with a KeyError for an unknown name

5. The support graph becomes an API that a web widget calls. What do you put at the boundary, and what stays inside the graph?

What a strong answer covers:

  • A Pydantic state schema, so a malformed request fails at invoke before any node or model call runs; a Pydantic input_schema on a TypedDict state does not check types in LangGraph 1.2.18
  • An input schema with only question and an output schema with only the structured answer, so route, the message history and counters such as llm_calls never leak to the client
  • Remembers that Pydantic checks the input but not node writes, so nodes that produce the answer still validate it themselves
  • Passes the customer id and database client as runtime context and per-call settings such as language in config, not as state the graph would return or save

Key Takeaways

  • Decide the reducer for every key that more than one node writes. Use add_messages for message lists and keep one convention for what nodes return.
  • Route with a plain function of state, list every destination, and give the router a fallback; the order of its rules decides the close calls.
  • Use Command when a node must write and route together, and test that every goto names a real node.
  • Validate input with a Pydantic state schema, narrow what callers send and receive with input and output schemas, and keep settings and dependencies out of state.
