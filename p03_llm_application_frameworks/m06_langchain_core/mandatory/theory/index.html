M06 LangChain Core: Models, Prompts & Parsers

Every LangChain program in this course has the same three parts: a prompt template that turns variables into messages, a chat model that turns messages into an AIMessage, and an output parser that turns the AIMessage into something your code can use. The M06 notebooks build on four ideas: chat models, messages, prompt templates and output parsers.

The parser bench
Open the lab

The running example is the Larkspur Cloud support assistant that M10 to M12 build, at the step after retrieval. It holds three handbook passages (refund-window, refund-timing and billing) for the question How long does a refund take? and must return a JSON answer with a list of the passages it cites. That is the module’s lab brief, and the lab runs it.

TL;DR

  • LangChain 1.x splits the old langchain package by how fast each part changes: base types in langchain-core, one partner package per provider, retired APIs in langchain-classic. A 0.x path such as langchain.chains raises ModuleNotFoundError with no deprecation warning first.
  • Every chat model takes a string, a message list or a PromptValue and returns an AIMessage with .content, .usage_metadata and .response_metadata. Changing provider changes one class or one "provider:model" string.
  • A chat model keeps no state. The conversation is the message list you send, so every earlier turn is paid for again on every call.
  • A prompt template turns variables into a PromptValue, which becomes a string or a message list for whichever model receives it. Its input_variables are recomputed from the template text, so a typo in the list you pass is replaced without an error.
  • A parser cannot make a reply good. It decides whether a bad reply raises. On the lab’s eight replies, JsonOutputParser raises on 1 and returns 4 unusable results; PydanticOutputParser with the passage ids as a Literal raises on 5 and returns none. Both give the same 3 usable answers.

Mental model

The prompt template and the parser are where your code meets the model’s text. The template decides what the model reads; the parser decides what reaches the rest of your program, and whether a malformed reply arrives as an exception or as a value that looks fine.

The 1.x package split

M02 called the provider SDKs directly, and M04 and M05 wrote the prompts those calls send. This module wraps both in LangChain, the framework most notebooks in this course are written in.

The Larkspur Cloud support assistant has a script from an older LangChain tutorial. It imports LLMChain from langchain.chains, HumanMessage from langchain.schema and the prompt hub from langchain. On the course environment (langchain 1.4.7, langchain-core 1.7.0) the script stops on its first line. The old path has no shim that forwards it and no warning that names the new one.

The reason is a change in where code lives. Through the 0.x releases, the langchain package held the whole ecosystem: chains, agents, memory, retrievers, every provider integration and the prompt hub. Installing it pulled in all of that, and a break in any one integration could break the import. Version 1.0 split the surface by how fast each part changes and who owns it:

Package Holds Changes
langchain-core messages, documents, prompts, output parsers, Runnable rarely, deliberately
langchain the agent loop and short re-exports such as init_chat_model with the agent API
langchain-openai, langchain-groq, … one provider each at that provider’s pace
langchain-classic retired chains, retrievers, indexing, the hub frozen

Table 1: The four kinds of package in LangChain 1.x.

Every other package builds on langchain-core:

Figure 1: The dependency direction. A partner package can change at its provider’s pace without touching the base types.

Reading an import error

Old code fails on 1.x in two different ways, and the exception class says what moved. We ran the notebook’s import audit and the hub import on the course environment:

Old import Error on 1.x Fix
langchain.chains ModuleNotFoundError langchain_classic.chains, or rewrite as an LCEL chain (M07)
langchain.schema ModuleNotFoundError langchain_core.messages, .documents or .output_parsers
langchain.text_splitter ModuleNotFoundError langchain_text_splitters
langchain.memory ModuleNotFoundError langchain_classic.memory, or better a checkpointer (below)
langchain.llms ModuleNotFoundError the provider’s partner package
langchain.retrievers, langchain.indexes ModuleNotFoundError langchain_classic
from langchain import hub ImportError: cannot import name 'hub' langchain_classic

Table 2: The seven 0.x module paths the notebook audits, plus the hub. All seven raise ModuleNotFoundError; only the hub raises ImportError.

ModuleNotFoundError means the module is gone. ImportError means the package still exists and no longer exports the name. A third message looks similar and means something else: No module named 'langchain_classic' says the replacement package is not installed in this environment. Listing it in a requirements file is not the same as installing it. Declare it in the project’s dependencies and sync.

Read the three messages in order:

Figure 3: Diagnosing an old import. Each “no” moves one question down.

The short paths that langchain keeps are aliases, not copies. langchain.messages.HumanMessage is langchain_core.messages.HumanMessage returns True on the course environment. The notebook reads a False as two LangChain installs on sys.path, a broken environment that no import change will fix.

Moved is not recommended

Memory is the one place where the moved class is the wrong answer. ConversationBufferMemory still imports from langchain_classic.memory, and the old app would run again after a one-line change. The 1.x replacement is a LangGraph checkpointer with a thread_id (M09, M33), which stores each conversation outside the process. We call the shortcut the moved-class migration: the import works, and the design it carries is the one 1.x retired. Retired chains are a milder case of the same thing. langchain_classic.chains still runs them, and M07 rewrites them as LCEL.

In practice: the refund script

For the Larkspur script, the error classes give the order of work:

  1. ModuleNotFoundError on langchain.schema: import HumanMessage from langchain_core.messages.
  2. ModuleNotFoundError on langchain.chains: rewrite LLMChain as template, model and parser joined with |, which needs no classic package.
  3. ImportError on hub: import it from langchain_classic, and add that package to the project’s dependencies if the next error says it is missing.
  4. Any conversation memory: move it to a checkpointer, not to langchain_classic.memory.

Key distinction: a ModuleNotFoundError names a path, an ImportError names a symbol. Fix the path for the first and the import source for the second.

Lesson 6.2 takes the middle part of Figure 2, the chat model, and shows what stays the same when its provider changes.

Key Takeaways

  • Version 1.0 split LangChain by pace of change. Prompts, messages, parsers and Runnable live in langchain-core, each provider in its own package, and retired chains and the hub in the frozen langchain-classic.
  • Read the exception class. ModuleNotFoundError means the module moved, ImportError means the package no longer exports the name, and a missing langchain_classic means it is not installed.
  • Not every old class should simply move. Replace conversation memory with a LangGraph checkpointer and a thread_id, and rewrite retired chains in LCEL.

Check yourself

1. Why did version 1.0 split the single langchain package into several packages?

In 0.x, installing langchain pulled in every provider integration, and a break in any one of them could break the import. Version 1.0 split the surface by how fast each part changes and who owns it: langchain-core changes rarely, each partner package moves at its provider’s pace, and langchain-classic is frozen.

2. Old code runs from langchain import hub on 1.x. Which error do you expect, and where should hub come from now?

ImportError: cannot import name 'hub' from 'langchain'. The package still exists but no longer exports the name, so import it from langchain_classic. Compare langchain.chains, where the module itself is gone and the error is ModuleNotFoundError.

3. A 0.x app keeps chat history in ConversationBufferMemory. Is changing its import path the right migration?

It runs, but it is not the recommended answer. The class still imports from langchain_classic.memory; the 1.x replacement is a LangGraph checkpointer with a thread_id (M09, M33). Memory is the one place where moving the import is not the fix.

Chat models

A chat model is any class that implements LangChain’s BaseChatModel interface: it takes messages and returns an AIMessage, whichever provider answers. The provider SDK still makes the call underneath; the class translates the request on the way out and the response on the way back:

Figure 1: A chat model wraps the provider’s call. The chain sees one response type.

Every chat model has the same three calls:

Call Takes Returns
invoke a string, a message list or a PromptValue one AIMessage
batch a list of inputs a list of AIMessage, run concurrently on a thread pool
stream one input the reply in chunks as it arrives

Table 2: The three calls every chat model offers.

What comes back

The AIMessage carries more than the text. Notebook 02a reads three attributes:

Attribute Holds Same keys for every provider
.content the reply text ✓
.usage_metadata input, output and total token counts ✓
.response_metadata what the provider reported, such as model_name and finish_reason ✗

Table 3: The three parts of an AIMessage that lesson 6.2 reads.

The last row matters more than it looks. On OpenAI, a finish_reason of length means the reply hit the token limit and stopped mid-sentence, or mid-JSON. We call this the truncated reply: the text reads like an answer and ends early. Lesson 6.6 shows what each output parser makes of one.

The notebook also takes the chain apart. prompt | model builds a RunnableSequence, and so do prompt.pipe(model) and RunnableSequence(prompt, model); we ran all three with a stub model and each gave a sequence of 2 steps. Calling the template on its own returns a ChatPromptValue holding one HumanMessage (“Explain AI in 2 bullet points”), which is exactly what the model then receives. Invoking each step by hand is how you debug a prompt.

Planted failure: the silent provider swap

The swap keeps the code running. It does not keep the replies the same: another model formats, refuses and rambles differently. We call this the silent provider swap: every call succeeds, and the answers drift. For Larkspur, the refund question might come back with the timing right and the citation format wrong, which no exception reports. A provider change is a release like any other, checked against the golden questions from M10 before it ships.

In practice: comparing two providers

For the Larkspur comparison, the chat model reduces the work to this:

  1. Build one chain from the answer template and a chat model named by an init_chat_model string.
  2. Run the golden questions through it once per provider string.
  3. Compare .content against the expected answers, .usage_metadata for cost, and finish_reason in .response_metadata for truncated replies.
  4. Ship the provider that passes, and keep the string in configuration so a rollback is one edit.

Interview tip: “LangChain makes models interchangeable” is half true. The call shape is interchangeable. The behaviour is not, and a strong answer says how you would measure the difference.

Lesson 6.3 runs the same chain on open-source models, locally and hosted.

Key Takeaways

  • Every LangChain chat model offers invoke, batch and stream and returns an AIMessage, with token counts under the same keys for every provider.
  • Read .response_metadata as well as .content. A finish_reason of length means the reply hit the token limit and stopped mid-sentence or mid-JSON.
  • Changing provider changes one class or one init_chat_model string, but the replies change too. Treat a provider swap as a release and check it against the golden questions.

The first row is the one to understand. A chat model trained on roles still reads one sequence of tokens; the roles are marked with special tokens that differ by model family. Choice Why
Keep the chain, swap the model object The template and everything after the model stay the same: a backend comparison changes one line (lesson 6.2)

Limits

  • No token counts locally. The pipeline path returns the text without usage metadata. Cost and length checks that read .usage_metadata see nothing.
  • The last message must be human. The local wrapper raises an error when the last message is a system or AI message, and it accepts only system, human and AI messages. Tool results (M22) cannot pass through it.
  • Replies differ by backend. A 1.1B model on a laptop and a large hosted model give different answers to the same prompt. Re-run the golden questions before relying on any of them (the silent provider swap from lesson 6.2).

To run it, the local part needs the course’s optional Hugging Face dependency group and downloads about 2 GB of weights on first use; the hosted parts need a Hugging Face token and a Groq API key in the project’s environment file.

Key Takeaways

  • The same prompt | model chain runs on a local model, a hosted Hugging Face model and Groq; only the model object changes.
  • ChatHuggingFace gives completion-style Hugging Face classes the chat interface. Locally it renders messages with the model’s own chat template; hosted, it sends role dicts to the server.
  • The interface hides real differences: the local path reports no token counts and accepts only system, human and AI messages, and every backend answers differently.

Check yourself

1. What does ChatHuggingFace do on the local path that the hosted path leaves to the server?

It renders the message list into one string with the model’s own chat template, the special tokens that mark each role for that model family. The pipeline then generates from that string. On the hosted path the wrapper sends role dicts and the server does the rendering.

2. Larkspur logs input and output tokens from every reply. What happens to those logs when the refund chain moves to the local TinyLlama backend?

They go empty. The pipeline path returns an AIMessage with the text only and no usage metadata, while the hosted endpoint and Groq report token counts. Cost and length checks need another source of counts on the local path.

3. The chain runs on all three backends without a code change. Which backend should Larkspur pick for structured refund answers?

The chain running proves only that the call shape is the same. Re-run the golden questions and the parser test set on each backend and compare usable answers, citation validity and latency; a small local model may follow the JSON format instructions less reliably than a large hosted one.

Messages

Lesson 6.4: Inputs and outputs: messages, LLM vs chat model. Notebooks: 04a_LangChain_Inputs_and_Outputs.ipynb, 04b_LLM_vs_ChatModel.ipynb

What you’ll learn

  • Explain the three message roles and why a chat model keeps no state between calls.
  • Trace a conversation as the list the app resends on every turn.
  • Compare invoke, batch and generate by what they take and return.
  • Diagnose an ignored system rule as a completion model flattening the roles.

Lessons 6.2 and 6.3 sent one prompt to a chat model and read one AIMessage back. A support conversation has more than one turn.

A Larkspur customer asks How long does a refund take? and gets a good answer. The follow-up is And for annual plans? The assistant replies as if it had never seen the first question. Nothing failed: the app sent only the second question, and the model had nothing else to read.

A message is one turn of a conversation, tagged with the role of whoever said it. A chat model reads a list of them:

Class Role in an OpenAI-style dict Holds
SystemMessage system the instructions for the whole conversation
HumanMessage user what the user said
AIMessage assistant a reply from the model, including earlier replies you send back

Table 1: The three message classes. Tool results add a fourth, ToolMessage, in M22.

The dict spelling works too. LangChain converts each dict to the matching class before the call; we ran the notebook’s convert_to_messages on a system, a user and an assistant dict and got a SystemMessage, a HumanMessage and an AIMessage, in that order. Both spellings send the same request.

The conversation is the list

A chat model keeps no state between calls. To continue a conversation, the app appends the model’s AIMessage and the next question to the list and sends the whole list again:

Figure 1: Two turns. The second call carries the first turn because the app put it there.

We call the opening bug the forgotten turn: the app sent the new question without the old ones. In notebook 04a, “What did we discuss so far?” gets a real answer only because the earlier turns are in the list. Drop them and the model has nothing to summarise.

Resending has a price. Every earlier turn is paid for again as input tokens on every call:

Turn Messages sent Earlier turns resent
1 system, human 0
2 system, human, AI, human 1
5 system plus 4 earlier exchanges plus the new question 4
20 system plus 19 earlier exchanges plus the new question 19

Table 2: How the list grows. The input cost of turn n includes all n minus 1 earlier exchanges.

History therefore needs a bound (M33). It is also just data your app holds, which can be trimmed, summarised or filtered before it is sent. In a template, history goes in a MessagesPlaceholder (lesson 6.5).

One call or several

For several requests at once, notebook 04a uses two calls besides invoke:

Call Input Output
.invoke() a string or one message list one AIMessage
.batch() a list of inputs a list of AIMessage, run concurrently
.generate() a list of message lists an LLMResult: generations holds one entry per conversation, and llm_output["token_usage"] sums the batch

Table 3: Three ways to call a model, from notebook 04a.

With .generate(), each inner list is its own conversation with its own system prompt; the notebook translates one sentence into German and Spanish in one call this way. Each conversation is still its own request to the provider. The model reads roles because it was trained on them, which raises the question of what happens with a model that was not.

LLM vs chat model

LangChain has two model interfaces, and every model class implements one of them. We ran the notebook’s base-class check on the installed packages:

Interface In and out Classes
BaseLLM a string in, a string out OpenAI (gpt-3.5-turbo-instruct), HuggingFaceEndpoint, HuggingFacePipeline
BaseChatModel messages in, an AIMessage out ChatOpenAI, ChatGoogleGenerativeAI, ChatHuggingFace, ChatGroq

Table 4: The two interfaces. A completion model (BaseLLM) continues text; a chat model answers roles.

Both accept both input shapes, because LangChain first turns the input into a PromptValue and then asks it for the shape the model needs:

Figure 2: One input, two conversions. The model’s interface decides which one runs.

We ran both conversions with langchain-core 1.7.0 on Larkspur inputs:

Input Sent to What the model receives
the string “How long does a refund take?” a chat model one HumanMessage with that text
a system message “Answer only from the passages.” and a human message with the refund question a completion model one string: System: Answer only from the passages. then a new line and Human: How long does a refund take?

Table 5: The two conversions, traced.

A string sent to a chat model becomes one HumanMessage, and nothing is lost. A message list sent to a completion model is flattened into plain text lines, which the model continues like any other text. We call this the flattened role: the system instruction becomes a hint instead of a role the model was trained to follow. That is why every chain in this course uses a chat model, and why a completion model appears only in notebook 04b, for contrast.

Pitfall: the flattened role. A system rule that works on a chat model can be ignored by a completion model given the same messages. Check the base class before blaming the prompt.

In practice: the follow-up question

For Larkspur’s follow-up, the fix is in the app:

  1. Keep the conversation as a list of messages per customer session.
  2. After each call, append the returned AIMessage, then the next HumanMessage.
  3. Send the whole list, through a chat model, so the system rules keep their role.
  4. Cap the list at a few turns, or summarise older ones, and watch input tokens per turn.

Lesson 6.5 moves the list into a template, with the history in a placeholder and the passages and question in their own slots.

Key Takeaways

  • A chat model reads a list of system, human and AI messages and keeps no state. The app resends the history on every call: bound it, and trim or summarise it as data before sending.
  • LangChain turns any input into a PromptValue, so a string sent to a chat model becomes one HumanMessage and nothing is lost.
  • Use chat models for chains. A completion model flattens messages into plain text lines, and a system instruction becomes a hint instead of a role.

Check yourself

1. Why can the model answer "What did we discuss so far?" in notebook 04a, when a chat model keeps no state between calls?

Because the app sends the earlier turns again. After each call it appends the model’s AIMessage and the next question to the list and sends the whole list. The model reads the conversation from its input, not from memory.

2. Larkspur's assistant reaches its twentieth turn. What does each new call cost, and what can the app do about it?

Every earlier turn is paid for again as input tokens on every call, so the twentieth call resends nineteen earlier exchanges and history needs a bound (M33). The app holds the history as data and can trim, summarise or filter it before sending, and a template takes it through a MessagesPlaceholder.

3. A teammate sends a system and a human message to a completion model, and the system rule is ignored. Why?

The message list is flattened into System: and Human: lines of plain text, which the model continues like any other text. The system instruction becomes a hint instead of a role the model was trained to follow. That is why every chain in the course uses a chat model.

The prompt now fails on a key named "answer", and the error points at the wrong line.

A prompt template is a function from named variables to a prompt. Its {slots} are filled with Python’s str.format syntax, and it comes in two kinds:

Class Produces Use with
PromptTemplate a StringPromptValue: one string completion models, or one human message
ChatPromptTemplate a ChatPromptValue: a list of role-tagged messages chat models, and anything with a system prompt or history

Table 1: The two template classes.

Both work with a chat model, because a string becomes one HumanMessage (lesson 6.4). ChatPromptTemplate.from_template("Explain {topic}") is exactly from_messages([("human", "Explain {topic}")]); we ran the notebook’s comparison and the two produce the same messages. Use from_messages whenever there is a system prompt.

Planted failures: four template mistakes

Two of these mistakes raise and two pass without a word. We planted each one on the course environment:

Mistake What happens
A typo in the input_variables you pass (output_langauge) The list is recomputed from the template text and the typo disappears. Only validate_template=True raises, with a Pydantic validation error.
A variable left out at format time KeyError names it ('output_language'). This one is loud.
Literal JSON braces in a template, {"answer": ...} "answer" becomes a variable, and formatting raises KeyError('"answer"'). Double the braces: {{"answer": ...}}.
.partial() for a slot the template does not have Ignored without an error: input_variables is unchanged and the value never reaches the model. Lesson 6.6 finds this in a course notebook.

Table 4: Four template mistakes and what langchain-core 1.7.0 does with each.

We call the quiet pair the silent slot: a value you meant to send, or a check you meant to run, that LangChain drops without telling you. Printing input_variables and the formatted messages once, before the first model call, catches both. The opening refactor bug is the third row: double the braces in any example JSON.

Few-shot and composition

Examples in the prompt steer both the answer and its format. The optional notebook 05b first writes nine labelled restaurant reviews (three restaurants, three sentiments each) straight into one template string, with every JSON brace doubled. The few-shot classes keep examples as data instead:

  • FewShotPromptTemplate: formats a list of example dicts with an example_prompt and adds a suffix holding the real input. Adding an example is appending a dict.
  • FewShotChatMessagePromptTemplate: turns each example into a human message and an AI reply, and slots the block into a ChatPromptTemplate between the system prompt and the question. Lesson 6.7’s optional template notebook builds one.

Composing templates

Templates compose with +. Adding two PromptTemplate objects concatenates the text and merges the variables. We ran it: a passages part plus a question part gives one PromptTemplate with passages and question. ChatPromptTemplate objects add the same way, message list to message list. The notebook builds its sentiment prompt from three parts (an introduction, a worked example and the request) and gets one template with 6 variables; .partial() on the five example slots leaves only input.

PipelinePromptTemplate, the 0.x class for this, is in neither langchain-core 1.7.0 nor langchain-classic. The one thing + does not do is place a part into a named slot of a larger template; for that, fill a final template with the formatted parts yourself.

Saving templates

A template is data, so it can be versioned like code. In 1.x, dumps and loads from langchain_core.load save and restore it as JSON:

allowed_objects is a security boundary. Deserialising rebuilds objects from the file’s contents, and you name the classes you trust.

In practice: the answer prompt

For Larkspur, the prompt comes together in this order:

  1. Write the system rules as a ChatPromptTemplate message, with {format_instructions} as a slot and every literal brace doubled.
  2. Add one or two worked examples as a few-shot block.
  3. Add a history placeholder and a human message with {passages} and {question}.
  4. Fill format_instructions with .partial(), then print input_variables and one formatted prompt.
  5. Save the template with dumps next to the code, where a prompt change shows up in review.

Key distinction: a loud mistake stops the first request; a silent slot ships. Print the formatted prompt once, before any model sees it.

Key Takeaways

  • Use ChatPromptTemplate.from_messages whenever there is a system prompt or history. Fill fixed slots once with .partial() and pass history through a MessagesPlaceholder.
  • Double literal JSON braces in templates, and print input_variables and the formatted messages once before the first call, since a typo or an unused partial fails silently.
  • Keep few-shot examples as data in a few-shot template, compose templates with +, and save them with dumps and loads, naming the classes you trust.

Lesson 6.5 left a {format_instructions} slot in the Larkspur answer prompt. An output parser fills it, and then reads what comes back.

The refund assistant asks for a JSON answer with a list of cited passages. One reply stops at the token limit, mid-citation. JsonOutputParser returns a dict for it without an error, and the citations list ends in "refund-win", a passage id that does not exist. The bad answer reaches the customer because nothing raised.

An output parser is the last step of a chain, prompt | llm | parser, and it works in two places. Before the call, get_format_instructions() returns text that goes into the prompt. After it, parse() turns the reply text into a Python value or raises OutputParserException:

Figure 1: One parser, two jobs. The same object writes the instructions and reads the reply.

Notebook 06a uses four parsers:

Parser Returns Raises when
StrOutputParser the reply text never
CommaSeparatedListOutputParser a list of strings never; "Sure: a, b" becomes ['Sure: a', 'b']
JsonOutputParser whatever JSON it finds, usually a dict it finds no JSON it can repair
PydanticOutputParser an instance of your model no JSON, or the JSON fails the model’s validation

Table 1: The four parsers in notebook 06a.

Four things follow from the two tables:

  • The usable count never moves. A stricter parser produces no extra good answers. It moves bad ones from the returned column to the raised column, where a retry or a fallback can catch them.
  • JsonOutputParser raises on one reply only, the one with prose before unfenced JSON. The trailing note is dropped by the repair step, and the truncated reply comes back as an ordinary dict.
  • list[str] stops the shape errors but not the made-up ids. "refund-win" (a truncated id) and "handbook-p4" (an invented one) are strings and pass. We call this the stringly-typed citation.
  • A Literal of the passage ids raises on all five. The schema now states the rule the lab grades by.

Planted failure: the repaired truncation

Truncation is where the repair step matters most. The lab cuts the clean 124-character reply at each of its 125 lengths, as a max_tokens limit would:

JsonOutputParser 1 120 4

PydanticOutputParser, Literal ids 120 1 4

JsonOutputParser raises only on the empty cut and returns a dict for the other 124. We call that the repaired truncation: a reply the model never finished arrives as a value that looks complete. With list[str], 14 cuts get through as unusable answers, such as a citation cut to "refund-t". With Literal ids, the one unusable cut is "citations": [], cut just after the bracket, which no Literal can catch. A min_length=1 on the list would catch it, at the cost of refusing an honest “the handbook does not say” with no citations.

In practice: the refund answer

For Larkspur’s cited answers:

  1. Use PydanticOutputParser with CitedAnswer, building the Literal from the retrieved passage ids, or check the ids right after parsing.
  2. Put {format_instructions} in the system message and fill it with .partial(); print one formatted prompt.
  3. Treat OutputParserException as a signal: log the raw reply, retry once, then fall back.

Key Takeaways

  • A parser adds format instructions to the prompt and turns the reply into a value or raises. JsonOutputParser repairs truncated JSON and returns broken replies as ordinary dicts.
  • A stricter schema does not make more good answers. It turns bad ones into errors a retry can catch, so state every rule in the schema, such as Literal passage ids, or check ids against the retrieved set.
  • Format instructions help only if they reach the model. Give the prompt a {format_instructions} slot and print the formatted prompt once to confirm the schema is there.

Lesson 6.6 put the schema in the prompt and checked the reply afterwards. The parser could refuse a bad reply; it could not stop the model from writing one.

Larkspur’s assistant still pays for that design on every call. The format instructions for CitedAnswer run to 803 characters of input, and a reply that opens with a sentence of prose before the JSON still raises, as the lesson 6.6 lab shows. The rule that the reply must be JSON lives only in the prompt, where the model may ignore it.

llm.with_structured_output(Schema) returns a new runnable whose output is an instance of the schema. It sends the schema to the provider with the request instead of writing it into the prompt, and providers that support structured output constrain the reply to it. Notebook 07g’s advice is to prefer it over PydanticOutputParser for any model that supports it:

Figure 1: The two routes. The parser checks the reply after the fact; structured output tells the provider the shape before it writes.

Which models any model that follows instructions models with structured-output or tool-calling support
Prose around the JSON, fences, trailing notes repaired or raised by the parser not produced when the provider constrains the reply
Values the schema allows but your app does not pass pass

Inside SmartQABot

Notebook 07a builds SmartQABot on structured output: a ChatPromptTemplate with a system prompt and a {question} slot, piped into a chat model bound to QAResponse. The schema has five fields:

Field Type Purpose
answer string the answer
confidence string asked to be high, medium or low
reasoning string why the bot answered as it did
follow_up_questions list of strings, empty by default suggestions for the user
sources_needed boolean, false by default whether external sources would help

Table 2: QAResponse, the bot’s return type.

Two of its choices are worth copying, and two are worth fixing before Larkspur uses the pattern:

  • Copy: a fallback object. ask() catches any exception and returns a valid QAResponse with confidence="low" and the error in reasoning. The caller always gets the same type back.
  • Copy: tracing. @traceable sends every call to LangSmith when a LangSmith API key is set, and a bad answer can then be traced to its exact prompt and reply.
  • Fix: confidence is a str. Its description asks for high, medium or low, but nothing enforces it; Literal["high", "medium", "low"] would.
  • Fix: ask_batch() has no fallback. It calls chain.batch(inputs), and by default batch raises the first exception and loses every result.

Planted failure: the all-or-nothing batch

We checked the batch behaviour with a three-input batch whose middle input fails, using a stub step in place of the model:

Call Result
batch([1, 2, 3]) raises the middle input’s ValueError; no results returned
batch([1, 2, 3], return_exceptions=True) the first and third results, with the exception object in the middle slot

Table 3: One failing input in a batch of three, run with langchain-core 1.7.0.

We call the default the all-or-nothing batch: one bad question costs the answers to the good ones. With return_exceptions=True, the caller can replace each exception with the same fallback object ask() returns.

In practice: Larkspur’s cited answer

For the lab brief, the same shape answers Larkspur’s refund question:

  2. Put the three passages and the question in the human message; the system message holds the rules, with no format instructions.
  3. Bind the schema with with_structured_output if the provider supports it, and fall back to PydanticOutputParser if not (Figure 2).

Interview tip: structured output removes a class of format failures; it does not validate meaning. Name the check you still run after it.

Key Takeaways

  • Prefer with_structured_output on models that support it. It sends the schema to the provider instead of the prompt, and the provider constrains the reply to it.
  • Neither approach stops values the schema allows, so type fixed labels and ids as Literal.
  • Return a fallback object of the same type when a call fails, trace every call, and pass return_exceptions=True to batch so one failure does not lose the other results.

Check yourself

1. How does with_structured_output differ from the Pydantic output parser in where the schema goes, and what does that buy?

It sends the schema to the provider’s API with the request instead of writing it into the prompt as format instructions (748 to 803 characters for the lesson 6.6 schemas). Providers that support structured output constrain the reply to it, so prose around the JSON, fences and trailing notes are not produced.

2. You bind CitedAnswer with citations typed as a list of strings to the model. Can it still return a made-up passage id?

Yes. A schema bound to the model still passes any value the schema allows, and any string is allowed. The lesson 6.6 rule holds for both approaches: put the rule into the schema, with Literal for passage ids and fixed labels.

3. SmartQABot's ask_batch sends three questions and the middle one fails. What does the caller get, and how do you fix it?

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s refund answers start failing: about one request in fifty raises OutputParserException after a model upgrade. The previous model never did. Where do you look first?

What a strong answer covers:

  • Pulls the raw AIMessage.content for failed requests before changing any code; the exception’s llm_output holds what the parser saw
  • Sorts the failures by shape: prose before the JSON, a truncated reply (finish_reason of length in response_metadata), a missing field, a wrong type
  • Fixes each shape at its cause: a token limit for truncation, the schema description for a wrong type, with_structured_output where the provider supports it
  • Adds the failing replies to a parser test set, so the next upgrade is checked against them before it ships

2. The answer must cite the passages it used. A teammate proposes JsonOutputParser because it “never breaks”. Do you agree?

What a strong answer covers:

  • JsonOutputParser rarely raises because it repairs text: it strips fences, drops trailing prose and closes truncated JSON, so a cut-off reply arrives as a dict with a half-written citation
  • An exception is the cheaper failure: it can be retried or logged, while a wrong dict reaches the customer
  • Puts the rules in a schema: citations as a list of the retrieved passage ids (a Literal or a post-parse check), answer as a required string
  • Keeps a fallback for the raise, as the lesson 6.7 bot does, and counts how often it fires

3. How do you monitor the structured-answer step in production?

What a strong answer covers:

  • Rate of OutputParserException per model and per prompt version, with the raw reply logged for each one
  • Rate of answers whose citations are not among the retrieved passage ids, checked in code after parsing
  • Token counts from usage_metadata, split into input and output, because format instructions and history grow the input side
  • Share of replies with finish_reason of length, which predicts truncated JSON before the parser sees it

4. A customer asks “How long does a refund take?” and then “And for annual plans?”. The second answer ignores the first turn. What happened, and how do you fix it without the prompt growing forever?

What a strong answer covers:

  • Chat models keep no state; the second call saw only the second question unless the app resent the first turn and the reply
  • Puts history in a MessagesPlaceholder and appends the AIMessage after each turn
  • Bounds the history: keep the last few turns, or summarise older ones (M33), and measures the input-token cost per turn
  • Rewrites the follow-up into a standalone question before retrieval, because the retriever needs “annual plans” and “refund” in one query (M33)

5. You move the refund assistant from gpt-4o-mini to a Groq-hosted open model to cut cost. The chain code does not change. What can still break?

What a strong answer covers:

  • The call shape survives a swap (init_chat_model("groq:…") or ChatGroq), the replies do not: format compliance, refusal style and verbosity can all change
  • with_structured_output depends on the provider’s structured-output or tool-calling support; check it before relying on it, or fall back to a parser
  • Re-runs the golden questions from M10 and the parser test set, and compares usable-answer rate, citation validity, tokens and latency
  • Keeps the provider in configuration (a "provider:model" string) so a rollback is a config change

Key Takeaways

  • Import from langchain_core for prompts, messages and parsers, and from a partner package for the model. A ModuleNotFoundError on an old path means the module moved; an ImportError means the name did.
  • Send the conversation every time. The model remembers nothing between calls, and every resent turn costs input tokens.
  • Build prompts from templates with explicit slots, and check input_variables and the formatted messages before the first model call.
  • Pick the parser for which failures you want to see. Put every rule you can into the schema, so a bad reply raises instead of passing.
