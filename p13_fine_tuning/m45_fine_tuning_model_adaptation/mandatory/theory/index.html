M45 Fine-tuning and model adaptation

Fine-tuning changes a model’s weights with your own examples, so the change travels with the model instead of sitting in every prompt. It is good at behaviour (a format, a tone, a refusal, one narrow task) and poor at facts that change. The M45 notebooks build on four ideas: how instruction data turns a text predictor into an assistant, how that data becomes token tensors, what the Hugging Face Trainer does with them, and how to tell whether the result is better.

Open the lab

The notebooks fine-tune EleutherAI/pythia-70m on lamini_docs, 1,400 questions and answers about one company’s product. These pages run the same steps on the Larkspur Cloud support assistant from M10 to M12: the support team wants answers that lead with Yes or No, state the policy in a sentence, and decline questions that are not about Larkspur. The examples reuse M10’s golden questions (How long does a refund take?, Can I export my data after I cancel my plan?, What happens if my server goes down?) and add the notebooks’ off-topic probe, What do you think of Mars?

TL;DR

  • Fine-tune for behaviour, retrieve for facts. The notebooks’ clearest result is a format change: the base Llama 2 continues “Tell me how to train my dog to sit” with more questions, and the chat model answers it. A fact that changes next month belongs in the M10 index.
  • The training text is all the model learns from. The lamini/lamini_docs copy that lesson 45.5 trains on joins each question to its answer with no template and no end token, in all 1,260 training rows. A model trained that way never learns where an answer stops.
  • Truncation and padding decide what survives. In the lab, max_length = 48 cuts 11 answer tokens from the refund example with right truncation, or the header and 7 question tokens with left truncation. Padding the batch to its longest row adds 18 pad tokens, 13% of the batch.
  • Count examples, not steps. The lesson 45.5 run is max_steps = 3 with a batch of 1 and 4 accumulation steps: 12 of 1,260 training examples, under 1% of one epoch, and the first update runs at learning rate 0.
  • Exact match fails on free text. The notebooks’ evaluation set has 0 exact matches in 139 answers, and 127 predicted answers repeat a sentence. Measure the behaviour you trained for, on held-out questions, against the prompted or RAG baseline.

Mental model

When evaluation shows a problem, the fix is usually in the examples or in how they were prepared (a missing end token, a truncated answer, a template the model never sees at inference), and the loop goes back to the data before it goes back to the training settings.

The modules before this one never touched a model’s weights. M04 shaped behaviour with instructions and examples, and M10 put the Larkspur Cloud handbook in an index so each answer could quote it. This module changes the weights themselves, and the first job is knowing when that is the right tool.

The Larkspur support lead brings two complaints to one meeting. The assistant’s answers wander before they reach the point, and it cheerfully discusses What do you think of Mars? when it should decline. The same week, the policy team shortens the refund window. A team that reaches for fine-tuning to fix all three ends up with a model that opens crisply, declines Mars, and quotes the old refund window until someone retrains it. We call that baked-in staleness: a fact trained into the weights that the world has since changed.

When to fine-tune

Fine-tuning updates the model’s weights with your own examples. Prompting changes only the input, and RAG changes only what evidence the input contains. Each one puts the change in a different place.

Three places a change can live

Prompting puts the change in the text of every call. Nothing is stored between calls, and a new rule is an edit to the prompt.

Figure 1: Prompting. The change lives in the prompt text sent with each call.

RAG puts the change in an index. A retriever picks the passages for each question and pastes them into the call, and a policy change is a re-index.

Figure 2: RAG. The change lives in the index, read again on every call.

Fine-tuning puts the change in the weights. Training runs once on your examples, and every later call uses the new weights without any extra text.

Figure 3: Fine-tuning. The change lives in the weights, written once by a training run.

The [INST] row shows a second, quieter failure. The chat model was trained with that wrapper around every request. With it, the answer starts cleanly; without it, the model first completes the sentence (“on command.”) and only then answers. We call this format mismatch: the model sees a prompt shaped differently from its training text and spends its first tokens repairing the shape. Key Takeaways

  • Prompting changes the instructions, RAG changes the evidence and fine-tuning changes the weights. Keep facts that change in the index, and fine-tune for behaviour too long or subtle to describe.
  • Try a clear prompt with examples first. Fine-tune only when you can write a few hundred examples of the behaviour, since you need them to train and to evaluate.
  • A base model continues text and a chat model answers requests, with the same architecture. The difference comes from training data, and a fine-tuned model expects the format it was trained on.

2. You send Tell me how to train my dog to sit, without any wrapper, to the Llama 2 base and chat models. What does each return, and why?

3. A team wants to fine-tune for a behaviour but cannot write a few hundred examples of it. What should they do?

Not fine-tune: without the examples they can neither train for the behaviour nor evaluate it. The decision chain says to prompt it if a clear prompt with examples works (M04), retrieve it if the gap is a fact that changes (M10), and otherwise define the task before training.

Pre-training, then fine-tuning

Both stages train the same way: show the model text and adjust the weights so it predicts each next token better. What differs is the data each stage feeds in:

Figure 1: One objective, two datasets. Pre-training produces the base model; fine-tuning reshapes it.

The notebook prints both kinds side by side. It streams the first five rows of C4, a web-crawl corpus. Each row is a scraped page with three fields, text, timestamp and url, and the first one begins “Beginners BBQ Class Taking Place in Missoula!”. Nothing in it says what a good answer looks like. The fine-tuning file, lamini_docs.jsonl, has 1,400 rows, each a question and an answer about one company’s product. Pre-training gives the model language and general knowledge from a huge, unlabelled corpus. Fine-tuning shows it, in a small labelled one, what a good response looks like:

Data Raw text, unlabelled, web scale Curated pairs, labelled, hundreds to thousands of rows (1,400 here)
What the model learns Language, facts, patterns of text A format, a task, a tone, when to decline
Who runs it Model labs, once per model You, whenever the behaviour needs to change

Key distinction: pre-training decides what the model knows how to say; fine-tuning decides which of those things it says when a request arrives.

The template at inference

A model learns the exact surface form of its training text, and the prompt at inference has to match it. When it does not, we call it template drift: the training rows used one shape and the serving code sends another. Lesson 45.1 showed the cost on Llama 2, which finished the user’s sentence (“on command.”) before answering.

The M45 notebooks hold a quiet example. Lesson 45.4 builds ### Question: / ### Answer: prompts, but the lamini/lamini_docs copy that lesson 45.5 trains on carries none of them. Every one of its 1,260 training rows decodes to the bare question followed immediately by the bare answer (…from Lamini models?There are several metrics…), with no separator and no end token. The inference helper then sends the bare question, which matches that training text, so the two stay consistent by accident.

Changing either side alone breaks that accident. The planted cases below each change one side:

Training text Serving prompt What the model sees
Bare question + bare answer Bare question A match by accident: the answer follows directly
Bare question + bare answer ### Question: … ### Answer: Headers it never saw; template drift
### Question: … ### Answer: + answer Bare question No cue that an answer should start; it may continue the question
Template + answer + end token Same template A clean start and a learned stop

Table 4: Planted template drift. Only the last row is a match by design.

Three rules keep training and inference in step:

  • One template, in code, used by both. Write the formatting function once and import it in the data script and the serving code. Many tokenizers now ship such a function as a chat template.
  • Mark where the answer starts and where it ends. A header such as ### Answer: tells the model to start answering; an end token (<|endoftext|> for Pythia) tells it, and your decoder, that the answer is over.
  • Check the tokenized row, not the string. Decode a few prepared rows before training; the lab in lesson 45.4 shows what to look for.

The end token is the rule the M45 data breaks, and it is the one with the loudest consequence. Lesson 45.4 shows where it has to be added, and lesson 45.6 shows what a model trained without it does.

The Hugging Face Trainer runs the training loop you would otherwise write by hand: batch the data, run the model forward, compute the loss, run it backward, step the optimiser and the learning-rate schedule, evaluate, log and save checkpoints. The notebook’s custom trainer

The notebook does not use the library Trainer directly. It imports a subclass from its utilities.py that adds three things:

  • An empty-input guard: it skips a batch whose input_ids are empty. The training split has exactly one such row, the blank row lesson 45.4 found.
  • Speed logging: it logs iteration time, floating-point operations per second and remaining time.
  • A smoothed loss: before it appends a log entry to state.log_history, it replaces the loss with an exponential average that gives each new step a weight of 1/100.

The smoothing only touches the history. The progress output receives the raw loss, while the history that plots and later cells read holds the average. After three steps the stored value is still 98% the first step’s loss (0.99 × 0.99 of its weight), whatever the model learned. Read the raw loss when you judge a short run.

Sizing a real Larkspur run

The fix for the step-count illusion is to plan in examples and derive the steps, in this order:

  1. Decide how many epochs the data supports; a small dataset seen too many times starts to memorise.
  2. Multiply by the training rows and divide by examples per update to get the number of updates.
  3. Set warmup as a fraction of those updates, not a fixed count.
  4. Put eval_steps and save_steps well inside the run. The held-out loss is then tracked while it trains, and the best-checkpoint setting has something to choose.

As an illustration with the notebook’s own data: two epochs of 1,260 rows at 4 examples per update is 630 updates. A 10% warmup is 63 updates, and evaluating and saving every 63 updates gives ten held-out losses to choose from.

The held-out loss tells you the model fits unseen rows of the same kind. It does not yet tell you the model does the Larkspur job, which is the next lesson.

LoRA and 4-bit loading

LoRA (low-rank adaptation, the PEFT method used here) freezes every original weight matrix W and trains two small matrices beside it, A and B, whose product is added to the layer’s output. With rank r, a layer of shape d_out × d_in gains r × (d_in + d_out) trainable parameters:

Figure 1: A LoRA layer. The input goes through the frozen weight and through the trained low-rank pair, and the two results are summed.

The intuition: the change fine-tuning makes to a layer is assumed to need far fewer dimensions than the layer itself. Rank 16 says “the update can be described by 16 directions”, and the two thin matrices hold exactly that much.

For the attention query projection of Llama 2 7B at rank 16, the arithmetic is small enough to do by hand:

The 4.2 GB is an estimate. Four bits for every weight would be 3.4 GB, but the input embedding and the output layer usually stay in 16-bit (0.52 GB together), and with AutoTrain’s 4-bit settings (no double quantisation) the per-block scaling constants add about 0.4 GB more.

The adapter is saved on its own. You can merge it into the base model for serving, or keep one base model and load a different adapter per task, for instance a Larkspur support adapter and a separate one for an internal tool. Pick full fine-tuning only when you have the memory and need to change the whole model; for a style and refusal job like Larkspur’s, QLoRA is the default.

Pitfall: the oversized learning rate. LoRA trains few parameters, but they still need a small step size; AutoTrain’s default is 3e-5. The notebook’s command sets a value thousands of times larger, which is its second problem.

Check yourself

1. Why does LoRA with 4-bit loading bring a 7B fine-tune within reach of one GPU?

LoRA freezes every original weight matrix and trains small A and B matrices beside it, so at rank 16 on every linear layer only 39,976,960 parameters (0.59%) train, and gradients and optimiser state exist only for those. 4-bit loading stores the frozen weights in about 4.2 GB instead of 13.5 GB in 16-bit floats. Together this is QLoRA.

2. How many trainable parameters does rank-16 LoRA add to a 4096 by 4096 query projection, and what share of the layer is that?

r × (d_in + d_out) = 16 × (4,096 + 4,096) = 131,072 trainable parameters, beside 16,777,216 frozen ones: 0.78%.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur fine-tuned a small model on 2,000 support transcripts. In testing it answers the refund question correctly, then keeps going: it repeats the policy sentence until the response hits its token limit. What do you check?

What a strong answer covers:

  • Decodes a few training rows and checks that each ends with the tokenizer’s end-of-text token; the Pythia tokenizer does not append one, so a model trained on raw question-plus-answer text never sees an answer end
  • Checks that truncation did not cut the end token off long examples, and that padding with the same id is masked to -100 in labels
  • Confirms generation stops on that token (eos_token_id) and sets max_new_tokens rather than a total max_length that includes the prompt
  • Adds answer length and repeated-sentence rate to the evaluation, since exact match never shows this failure

2. The support lead wants to fine-tune the assistant “so it knows the new refund policy and answers in our house style”. What do you build?

What a strong answer covers:

  • Splits the request: the policy is a fact that changes, so it goes in the M10 index and is cited; the house style is behaviour, which fine-tuning can carry
  • Starts with a prompt that states the style and shows two examples, and fine-tunes only if that fails on a measured set or costs too many tokens per call
  • Builds training examples whose answers follow the style but take their facts from retrieved context, so the model learns to use context rather than memorise the policy
  • Plans for the next policy change: re-index, no retraining, and a golden question that checks the new window is cited

3. Your fine-tuned model’s training loss fell for two epochs. How do you decide whether it replaces the prompted model in production?

What a strong answer covers:

  • Evaluates on a held-out split the model never trained on (the notebooks hold out 10%) plus the M10 golden questions, never on training loss
  • Scores what was trained: the share of answers that lead with Yes or No, faithfulness to the retrieved policy, refusal rate on off-topic questions such as What do you think of Mars?
  • Runs a general benchmark (lesson 45.6 uses ARC Easy) before and after, to catch lost general ability
  • Compares against the prompted baseline on the same questions, with cost and latency per call, and reviews the regressions question by question

4. Ten percent of Larkspur’s transcripts are longer than the 512-token limit you can afford in training. What do you do with them?

What a strong answer covers:

  • Measures the length distribution first; lesson 45.4’s lamini_docs rows peak at 479 tokens, well under the 2,048 the notebook allows, so its truncation never fires
  • Knows the trade-off: right truncation cuts the end of the answer and its end token, left truncation cuts the question and the template header
  • Prefers fixing the data (drop long greetings and signatures, split multi-turn threads into single exchanges) over silently cutting
  • Logs how many rows were truncated on every run, so a change in the data shows up as a number

5. The team has one 24 GB GPU and wants to fine-tune a 7-billion-parameter model. Is that feasible, and with which settings?

What a strong answer covers:

  • Does the arithmetic: Llama 2 7B has 6.74 billion parameters, 13.5 GB of weights in 16-bit before any gradients or optimizer state, so full fine-tuning does not fit
  • Loads the base weights in 4 bits (about 4.2 GB) and trains LoRA adapters: at rank 16 on every linear layer that is 40.0 million trainable parameters, 0.59% of the model
  • Uses a LoRA-sized learning rate; AutoTrain’s default is 3e-5, and the notebook’s 0.4 is more than 13,000 times that
  • Keeps batch size small with gradient accumulation and gradient checkpointing, and merges or serves the adapter separately depending on how many variants are deployed

Key Takeaways

  • Try prompting first, put changing facts in retrieval, and fine-tune for behaviour you can describe and measure.
  • Before training, decode a few prepared rows: check the template, the end token, what truncation removed and what padding added.
  • Report training runs in examples and epochs, and read the learning-rate schedule for the steps you actually run.
  • Evaluate the fine-tuned model on held-out questions, on the behaviour you trained for, against the baseline it is meant to replace.
