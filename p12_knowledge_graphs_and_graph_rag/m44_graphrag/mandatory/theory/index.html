M44 GraphRAG Techniques

Graph retrieval changes which evidence reaches the answer model. A question can start at one entity, follow a relationship to another passage, or ask for themes across communities. The M44 notebooks build on four ideas: community detection, global and local search, graph expansion, and the indexing work those choices require.

Expansion and the evidence set
Open the lab

The running example is the fictional Larkspur Cloud handbook. “Which export mechanism remains available after cancellation?” needs a connection between policy and product pages. “What dependencies recur across cancellation, exports and outages?” asks for a corpus overview. These questions need different retrieval plans, even when they share an index.

TL;DR

  • Decide what a node and an edge mean before calling a system GraphRAG. A similar pair of chunks, an extracted factual relation and a community membership support different inferences.
  • Local search starts near entities; global search uses community reports to cover the corpus. Choose using the question’s required evidence.
  • Expansion increases the candidate set. In the lab’s cancellation fixture, degree 0 returns 2 relations; degree 1 returns 4. Neither count measures answer accuracy.
  • Carry source passages through extraction, traversal and generation. A citation marker alone does not establish that its claim follows from its source.
  • Compare indexing, updates and query work on the same question set before replacing the flat retrieval baseline.

Mental model

Both routes must return evidence that the answer can cite. The graph supplies candidate connections; the source passages establish what the handbook actually says. Community reports add a summary layer whose omissions need checking against those passages.

Chunk graphs and traversal

Lesson 44.1: Concept-graph traversal. Notebooks: 01a_graph_rag.ipynb

What you’ll learn

  • Explain how a chunk graph is built from cosine similarity and shared concepts, and what its edge weight means.
  • Trace the notebook’s priority-queue traversal and the completeness check that stops it.
  • Diagnose two traversal faults: an inverted seed priority and neighbours that are discovered but never expanded.
  • Choose the budgets and logs that make a traversal auditable.

M43 stored facts as typed nodes and relationships and queried them with Cypher. This module asks a different question: how can graph structure decide which passages reach the answer model?

Take a Larkspur Cloud customer who asks which export mechanism remains available after cancellation. The answer depends on three passages: the cancellation policy, the export options and the snapshot retention rule. Flat top-k retrieval scores each chunk against the question on its own, and the retention passage barely mentions cancellation. It can rank below a billing chunk that shares more words with the question.

A chunk graph is a graph whose nodes are text chunks and whose edges join chunks that are similar enough to be read together. Retrieval finds a few seed chunks, then walks the edges to collect neighbours that the question alone would not rank. The first notebook builds one over the first 10 pages of a climate-change PDF and walks it to answer a question.

The build runs in four stages:

Stage What the notebook does What it produces
Split Recursive splitter, 1,000 characters with 200 of overlap 30 chunks from the 10 pages
Concepts A structured LLM call per chunk, plus spaCy named entities (people, organisations, places, works) A concept list per node
Embed and compare One embedding per chunk, cosine similarity for every pair 435 pair scores (30 × 29 / 2)
Link An edge when cosine is strictly above 0.8 Weighted, undirected edges

Table 1: The chunk-graph build. Chunk and pair counts come from running the notebook’s loader and splitter in the scratchpad; no model was called.

The comparison is quadratic. Doubling the corpus to 60 chunks would mean 1,770 pairs, and the concept stage costs one model call per chunk on top of the embeddings.

Figure 1: Edge creation. The threshold decides whether an edge exists; shared concepts only change its weight.

Once a pair passes the threshold, the notebook weights the edge as 0.7 × cosine + 0.3 × the shared-concept fraction. The fraction divides the number of shared concepts by the size of the smaller concept set, and is zero when that set is empty. We ran the notebook’s own weight function on four illustrative Larkspur chunk pairs:

Edge Cosine Shared concepts Smaller set Weight
Cancellation policy, Export options 0.86 1 3 0.702
Cancellation policy, Billing cycle 0.84 1 2 0.738
Export options, Snapshot retention 0.88 1 2 0.766
Billing cycle, Outage status 0.82 0 2 0.574

Table 2: Edge weights from the notebook’s weight function. Cosine scores and concept lists are illustrative inputs.

The billing edge outweighs the export edge despite a lower cosine, because the billing chunk has a smaller concept list. The weight mixes two signals the notebook author chose. It has no calibrated meaning as a probability that one chunk supports the other.

Pitfall: the edge as evidence. A cancellation chunk and an export chunk can share a product name while describing different dates or account states. An edge is a retrieval lead; read both passages before turning it into a policy statement.

At query time the notebook retrieves 5 chunks from FAISS and compresses each with an LLM extractor that keeps only the question-relevant sentences. To find each compressed span’s place in the graph, it runs a second nearest-neighbour search with the compressed text and takes the closest stored chunk. That chunk may not be the one the span came from, and two chunks with identical text map to whichever node comes first. Stable chunk IDs carried through compression remove the guess.

How the traversal runs

The notebook describes its walk as Dijkstra-like. Each seed enters a min-heap with priority 1 / score, where the score comes from the seed lookup. Popping a node adds its text to the context and asks the model whether the context now answers the question. If not, and the node brings concepts not seen yet, each neighbour gets a distance of the current priority plus 1 / edge weight.

The loop has one detail that changes its reach:

Figure 2: The traversal loop. A neighbour joins the path when it is discovered, so the pop that later reaches it is skipped.

Read the right-hand branch closely. A neighbour’s text is added, and the neighbour is recorded as visited, at the moment it is discovered. When the heap later pops that neighbour, the “already in path” test skips it, and its own neighbours are never examined. We call this discovered but never expanded: the walk reaches the seeds and their direct neighbours, and stops.

The seed priority has a second problem. LangChain’s FAISS store returns L2 distance by default, where a lower score means a closer match. Dividing 1 by a distance gives the closest seed the largest priority, and the min-heap pops it last. We call this the inverted seed priority. A distance of exactly zero would also divide by zero.

None of this makes the notebook useless as a teaching build. It shows the moving parts of graph-guided retrieval. It should not be described as an unmodified shortest-path search, and its reach should be measured before it is trusted with multi-hop questions.

Budgets and stopping

The query engine sets a maximum context length of 4,000, but no branch of the traversal reads it. A variable named as a budget supplies no protection until code checks it. Count the accumulated context with the answer model’s tokenizer and stop before an explicit limit. Cap visited nodes and completeness calls separately, since each check is a model call over the whole context so far.

The cost of checking grows with the walk:

Nodes added Completeness calls Context sent per call
1 1 1 chunk
4 4 1, 2, 3, then 4 chunks
n n 1 + 2 + … + n chunks in total

Table 5: Completeness calls in the notebook’s loop. Table 3’s run made four calls over contexts of 1, 2, 3 and 4 chunks.

At 1,000-character chunks, a walk that adds 10 nodes resends 55 chunks of text across its checks. That is the price of asking after every node.

An LLM saying “complete” is a stopping heuristic. For the cancellation question, check that the context holds the cancellation condition, the available export mechanism and the retention condition. If the graph has no path to one of those passages, report the missing evidence. More context cannot create a relation absent from the index.

For each query, log the seed IDs, the edges followed, the source spans retrieved, the context size and the stopping reason. Then compare against flat retrieval on the same golden questions. A longer traversal can add work while leaving the answer’s supporting evidence unchanged, and lesson 44.2 turns that evidence into explicit citations.

Key Takeaways

  • A chunk graph joins chunks whose cosine passes a threshold and weights each edge by similarity and shared concepts. The weight is a retrieval lead, never a calibrated probability.
  • Measure a traversal’s reach before trusting it: the notebook’s walk inverts its seed order on L2 distances and never expands the neighbours it discovers; it stops one hop out.
  • A budget variable protects nothing until code checks it. Count context with the answer model’s tokenizer, cap nodes and completeness calls separately, and treat “complete” as a heuristic.

Check yourself

1. Two chunks have cosine similarity 0.85 and share 2 concepts, with 4 in the smaller concept set. What weight does their edge get, and what does that weight mean?

The edge exists because 0.85 is above the 0.8 threshold, and its weight is 0.7 × 0.85 + 0.3 × 0.5 = 0.745. The weight combines two signals the notebook author chose and is not a calibrated probability that either chunk supports the other. Treat the edge as a retrieval lead and read both passages.

2. The traversal sets max_context_length=4000. Does that stop the context from growing past 4000?

No. No branch of the traversal checks that attribute, so it supplies no protection. Count the accumulated context with the answer model’s tokenizer and stop before an explicit budget, and cap visited nodes and completeness-check calls separately.

3. The snapshot retention chunk sits two edges from the cancellation seed, yet it never reaches the context. What in the traversal explains that?

The loop adds a neighbour to the path the moment it discovers it, and later skips that neighbour when it is popped, so its own neighbours are never examined. The walk reaches the seeds and their direct neighbours only. Log the path and measure reach on a question whose evidence is two hops away before relying on the traversal.

Source attribution

Lesson 44.2: Local GraphRAG with source attribution. Notebooks: 02a_graph_rag_local_attribution.ipynb (optional)

What you’ll learn

  • Explain the difference between the route that found evidence and the passage that supports a claim.
  • Trace how the notebook turns [N] markers into citations, and what that check leaves out.
  • Diagnose provenance lost to overwrites and results hidden by a shared visited set.
  • Choose what to report when a local extraction model fails.

Lesson 44.1 walked a graph of similar chunks and ended on a log of seeds, edges and source spans. This lesson makes the last item explicit: every claim in the answer should point at the sentence that supports it.

Suppose the Larkspur assistant answers that exports stay available for 30 days after cancellation, and tags the claim [1]. Marker 1 resolves to a real handbook sentence. The sentence says that cancelling ends billing at the end of the period, which says nothing about exports. The answer looks cited and is unsupported. We call this citation without support.

Source attribution links each generated claim to the exact source span that supports it, and keeps that link separate from the graph path that found the span. The optional notebook builds a local version: Ollama runs extraction and generation, all-MiniLM-L6-v2 embeds entities, and a directed NetworkX graph holds the relationships.

Each record the notebook stores carries its provenance:

Record Fields that carry provenance What it decides
Entity source document, source sentence Which sentence a node description came from
Relationship relation type, source document, source sentence Which sentence asserted the edge
Citation claim, source document, source sentence, confidence, graph path What the answer points at

Table 1: The notebook’s data model, read from its dataclasses.

At query time the notebook embeds the question, takes the 3 most similar entities as entry points, and follows outgoing edges breadth-first for up to 2 hops. For Larkspur, a path might run from Cancellation to Export to Snapshot. That path explains why retrieval reached the snapshot document. The policy claim still needs a passage that states when a snapshot export remains available.

Figure 1: Route and support are separate checks. The path finds a span; only the span can support the claim.

Keep two records for each generated claim: the route by which retrieval found evidence, and the exact passage used to support the claim. A traversable relation can be stale, wrongly extracted, or cut off from the conditions in the original text. Inspecting the source is how a reviewer rejects that relation.

What the notebook verifies

The answer prompt lists the retrieved entities as numbered lines of name and description, and asks the model to cite with [N]. After generation, a regular expression finds the markers, and each valid number is mapped back to the stored source document and sentence. The source sentence never enters the prompt; it is attached afterwards from the map.

We ran the notebook’s ingestion, traversal and citation code with a scripted extraction (four Larkspur entities, four relations) and a scripted answer, so no model was called:

Marker Claim in the answer Resolved sentence Supports the claim
[1] Exports stay available for 30 days Cancelling ends billing at period end. no
[3] Snapshots last 30 days Exports use the latest snapshot. no
[9] (see also) none: dropped without a warning not checked

Table 2: Citation resolution on a scripted run. Both resolved markers become citations with confidence 0.9.

Both valid markers became citation records. Each has a confidence of 0.9, a fixed constant in the code, and a claim field that holds the label “Reference [N]” rather than the sentence of the answer it supports. Marker 9 pointed past the three context items and vanished. Nothing in the run noticed that neither resolved sentence supports its claim.

The code therefore demonstrates provenance storage and citation resolution. It does not check entailment, that is, whether the cited sentence actually implies the claim. A useful check splits the answer into claims, resolves each marker to a span, and asks whether the span supports the claim with its conditions and dates intact. Until that check passes, call the answer cited, not verified.

Where provenance is lost

The graph keeps one source record per entity and one edge per ordered pair of entities. Both rules overwrite data silently. We call the pattern last write wins, and the same scripted run planted two cases:

Planted case What the graph kept Why
An old FAQ re-extracts “export” after the policy page The node now cites the old FAQ: “Exports are removed at cancellation.” Entity IDs hash the lowercased name, and a later write replaces the node’s fields
Two relations from Export to Snapshot (uses, related to) One edge, typed “related to”; 4 relations extracted, 3 edges stored A directed graph allows one edge per ordered pair
A relation whose endpoint was never extracted as an entity No edge Edges are added only when both endpoints exist

Table 3: Overwrites and drops in the notebook’s graph. The first two rows come from a scratchpad run of its ingestion code; the third is the guard in that code.

The first row is the dangerous one. A stale FAQ sentence now contradicts the policy, and the traversal will cite it as the export node’s source. Keep a list of source spans per entity, and a multigraph or a relation list when distinct relations between the same pair carry separate claims.

Local execution boundaries

When Ollama is not installed, the notebook’s extraction helper returns an empty result rather than an error. An empty graph from that branch does not show that the documents contain no relationships. Report model availability and extraction failures separately from a legitimate zero-result retrieval.

The traversal has a subtler boundary. It shares one visited set across all seeds and processes them in order. A node already reached from an earlier seed is skipped when a later seed starts from it, along with everything beyond it. We ran the notebook’s traversal over the same four entities with 2 hops:

Seeds, in order Entities returned (depth) Retention returned
Cancellation, then Snapshot Cancellation 0, Export 1, Snapshot 2 no
Snapshot, then Cancellation Snapshot 0, Retention 1, Cancellation 0, Export 1 yes

Table 4: Seed order changes the result of the notebook’s multi-seed traversal (scratchpad run).

Retention is one hop from the Snapshot seed, well inside the budget, and still missing in the first row. We call this seed-order shadowing. When the required meaning is “within this many hops of any seed”, store the best depth per node or run a true multi-source breadth-first search, which starts every seed at depth 0 together. Apply source access filters during traversal and again when building the context.

Lesson 44.3 moves from entity neighbourhoods to the whole corpus, where the evidence for an answer is a set of community summaries rather than a path.

Key Takeaways

  • Keep two records per claim: the graph route that found the evidence, and the exact passage that supports the claim. A traversable relation can be stale or wrongly extracted.
  • Resolving [N] markers to sources proves provenance storage, not entailment. A fixed confidence of 0.9 is a constant; add a claim-to-span review before calling an answer verified.
  • Report extraction failures separately from empty results, keep every source span and relation the graph would otherwise overwrite, and check that seed order cannot hide a result.

Check yourself

1. A graph path runs from Cancellation to Export to Snapshot. Why record both that path and the exact passage behind each claim?

The path explains how retrieval reached the snapshot document; it does not support the policy claim. A traversable relation can be stale, wrongly extracted or cut off from the conditions in the original text. The source passage is what lets a reviewer check the claim, or reject the relation.

2. Each citation the notebook produces carries confidence 0.9. What does that number tell you about the answer?

Nothing measured: it is a fixed constant, and the claim field holds a reference label rather than the answer’s claim. The code finds [N] markers and maps valid IDs back to source records, but it never checks that the cited sentence supports the claim. Add a claim-to-span review before treating an answer as verified.

3. After an old FAQ is ingested, answers about exports start citing it instead of the current policy. What in the graph caused that?

Entity IDs come from the lowercased name, so the FAQ’s “export” maps to the same node as the policy’s Export, and the later write replaces its description and source. This is last write wins. Keep a list of source spans per entity, with document versions, so a stale source can be filtered rather than silently substituted.

Community detection

Lesson 44.3: Microsoft GraphRAG: communities, global vs local search. Notebooks: 03a_microsoft_graphrag.ipynb

What you’ll learn

  • Explain the difference between a community, which comes from graph structure, and its report, which a model writes.
  • Compare global search over community reports with local search around entities.
  • Diagnose an overview answer that omits a region of the corpus or repeats an extraction mistake.
  • Count the indexing and query calls a graph pipeline adds before you compare it with flat retrieval.

Lessons 44.1 and 44.2 started from a few seeds and walked outwards. That works when a question names something. A Larkspur support lead asks a different kind of question: which operational dependencies recur across cancellation, exports and outages? No single seed holds the answer. A walk from the cancellation node returns cancellation’s neighbours and nothing about outage recovery.

Community detection partitions a graph into groups of nodes that are more densely connected to each other than to the rest. A community report is a summary a model writes for one group, from the entities and relations inside it. The two are separate artifacts. Changing the summary prompt changes the report without changing the partition, and a bad partition produces a fluent report about the wrong grouping.

Microsoft GraphRAG builds both during indexing. Its pipeline extracts entities and relations from text chunks, detects communities with the hierarchical Leiden algorithm (clustering recursively until communities fall under a size threshold), writes a report per community at each level, and embeds text for later lookup (Microsoft GraphRAG indexing dataflow, read November 2026). Those artifacts are reused by every later query.

Figure 1: The community half of indexing. Detection is a graph algorithm; report generation is a model call per community.

A partition is only as stable as the structure underneath it. We ran NetworkX’s Louvain algorithm, a close relative of Leiden and the one this module’s lab uses, on the eight-entity Larkspur fixture from lesson 44.4’s lab. That fixture is a single ring of eight relations, with no dense region:

Random seed Communities found
0, 2, 3 {Cancellation, Export}, {Billing, Refund}, {Snapshot, Storage}, {Account, Outage}
1 {Billing, Cancellation}, {Export, Snapshot}, {Account, Refund}, {Outage, Storage}
4 {Billing, Cancellation, Export}, {Outage, Snapshot, Storage}, {Account, Refund}

Table 1: Louvain partitions of the lab fixture across five random seeds (NetworkX 3.7, scratchpad run). Three seeds agree; two give different groupings.

Whether Cancellation and Export share a community, and therefore a report, depends on the random seed. We call this the unstable partition. Real handbooks have denser regions than a ring, which helps, but the lesson holds: review extracted edges and group membership before reading a report as a reliable account of a product area. Fix the seed in evaluation runs, so that a change in the answers traces back to a change in the data.

Global vs local search

Microsoft GraphRAG answers from the same index in two ways.

  • Local search: starts from entities related to the question and combines their relations, nearby graph material and the source text units they came from (Microsoft local search).
  • Global search: answers from community reports at a chosen level of the hierarchy, in a map and reduce pass over all of them (Microsoft global search).

Global search works in two stages:

Figure 2: Global search as map and reduce. Every report chunk costs a model call before any point is filtered out.

The map stage splits the reports into chunks of a set size, and each chunk yields a list of points, each with an importance rating. The reduce stage keeps the most important points and writes the answer from them. Lower levels of the hierarchy hold more, smaller reports: answers get more thorough and the map stage makes more calls.

For the cancellation and export question, local search fits: the evidence centres on specific entities and their conditions. Check that the context includes the original policy spans. For the recurring-dependencies question, global search fits, and you inspect which reports contributed. A fluent answer can still omit a small community or repeat an extraction mistake. We call the first failure the missing community.

Question Evidence to require Failure to inspect
A named product’s cancellation condition Entity relations and original policy spans Wrong identity or stale version
Themes across product areas Reports covering the relevant corpus regions Omitted communities
Exact retention wording The current source passage Summary dropping a qualification

Table 2: Route each question by the evidence it needs, and inspect the failure that route invites.

Its command names and settings structure match the release it was written for. Check the installed package’s interface and configuration schema before adapting them; this page concerns retrieval behaviour, which outlasts any one release.

Indexing cost

Flat RAG pays to split, embed and store passages. A graph pipeline adds entity and relation extraction, identity resolution and relation storage. Community retrieval adds detection and one report per community. When a source page changes, the derived records change too, including every report whose community contains an affected entity.

The module lab makes the arithmetic concrete. Its GraphRAG build indexes 20 documents split into 38 chunks, and answers 10 global and 5 multi-hop questions. Counting model calls from its code:

Work Model calls Count in the lab
Extraction 1 per chunk 38
Community reports 1 per community known only after a run
Global question 8 report maps + 1 answer 10 × 9 = 90
Local question 1 answer 5 × 1 = 5

Table 4: Model calls in the lab’s GraphRAG build. Chunk and question counts come from running its loader and splitter in the scratchpad; the per-question calls are read from its search functions.

Before any report is written, indexing already costs 38 extraction calls, against zero model calls for a flat index. Each global question makes nine times the model calls of a local one. Those ratios are what amortisation has to beat.

Record each stage separately: model and prompt version, input and output tokens, call count, retries, elapsed time, stored artifact size and changed source IDs. At query time record report selections, expansion candidates, reranking calls and answer context. The notebook sets a maximum of 10,000 context tokens for global search and asks for answers of at most 300 tokens. The first is a configured ceiling, not a measured bill. The second is an instruction in the prompt, which nothing enforces.

The lab brief compares GraphRAG, RAPTOR and a hybrid on that shared question set. Hold source versions, answer model and evaluation criteria constant. Report indexing and update work beside answer quality, and derive any break-even point from measured indexing work, measured query work and the expected query volume. The architecture alone implies no break-even figure. Lesson 44.4 keeps the entity graph but moves it into a vector database, where expansion is a matrix product.

Key Takeaways

  • A community comes from graph structure and its report is a generated summary of it. Partitions can change with the random seed, so review edges and membership before trusting a report about a product area.
  • Route questions about named entities to local search and corpus-wide themes to global search, then inspect which reports contributed; a fluent overview can miss a community.
  • Count the work a graph pipeline adds (an extraction call per chunk, a report per community, a map call per report at query time) and derive cost from measured runs.

Check yourself

1. How does a community differ from its community report, and why does the difference matter when you debug?

The community is a group derived from graph structure; the report is a generated summary of the material in that group. Changing the summary prompt changes the report without changing the partition, and on the lab’s ring fixture the partition itself changed with the Louvain random seed. Review the extracted edges and the group membership before trusting a report as an account of a product area.

2. Which search mode fits a question about the export mechanism left after cancellation, and which fits one about dependencies that recur across the handbook?

Local search fits the first: the evidence centres on specific entities and their conditions, so check that the context includes the original policy spans. Global search fits the second, because the evidence is spread across the corpus and answered from community reports. Inspect which reports contributed, since a fluent answer can omit a small community.

3. A teammate says global search costs at most 10000 tokens per query because that is what the notebook configures. Is that a sound cost figure?

No. 10,000 is a configured maximum context setting, neither a measured bill nor proof that every run uses the whole allowance. Global search also makes a map call per report chunk before the final answer. Record each stage’s tokens, calls, retries and time, and derive cost from measured indexing and query work.

Graph expansion

Lesson 44.4: Graph expansion inside a vector database (Milvus). Notebooks: 04a_graphrag_with_milvus.ipynb (optional)

What you’ll learn

  • Explain how powers of an incidence matrix expand vector-search seeds into candidate relations.
  • Trace the candidate set and source passages at each expansion degree.
  • Diagnose a hub that floods the candidates, and an entity split across spellings.

Lesson 44.3 answered corpus-wide questions from community reports. This lesson goes back to multi-hop questions, with no graph database at all: the graph lives in a few arrays beside a vector store.

The notebook’s question is “What contribution did the son of Euler’s teacher make?” Answering it takes three hops: Euler’s teacher was Johann Bernoulli, Johann’s son was Daniel, and Daniel’s contributions are in a passage that never mentions Euler. A flat search on the question scores passages against Euler and contributions, and the Daniel passage has little reason to rank. Larkspur has the same shape: cancellation leads to export, export to snapshot, and the snapshot passage holds the retention rule.

Graph expansion grows a set of retrieved entities or relations into their graph neighbourhood, a fixed number of steps at a time, before reranking picks what reaches the answer. The Milvus notebook stores three collections and two adjacency maps:

Store What it holds Used for
Entity collection One vector per entity name Seeds from entities named in the question
Relation collection One vector per relation sentence (subject, predicate and object joined) Seeds from the whole question
Passage collection One vector per passage The flat baseline
Entity to relations map Which relations each entity takes part in Building the incidence matrix
Relation to passages map Which passages each relation came from Resolving relations to text

Table 1: The notebook’s stores. Traversal runs in application memory; Milvus supplies vector search and stored records.

Its four-passage Bernoulli dataset yields 26 entities and 22 relations, counted by running the notebook’s preparation cells in the scratchpad.

Let B be the entity-by-relation incidence matrix: B[e,r]=1 when entity e takes part in relation r. Then B Bᵀ connects entities that share a relation, and Bᵀ B connects relations that share an entity. The notebook raises these to the target degree, multiplies the entity side by B to land on relations, takes the nonzero entries, and merges the candidates from the entity and relation seeds (Milvus Graph RAG tutorial).

Figure 1: Expansion inside the retrieval pipeline. Only the first step touches the vector store.

Matrix products count walks. A nonzero entry says a path exists, and does not certify that the relation helps answer the question. The diagonal of B Bᵀ is nonzero too (each entity shares a relation with itself). A higher degree therefore keeps every earlier candidate and adds new ones. Direction and relation type need separate handling: an undirected incidence matrix forgets which way a predicate points.

The interactive lab computes the entity-side row of (B Bᵀ)^d B on an eight-entity Larkspur fixture. Degree 0 shows the relations touching the seed and serves as a teaching baseline; the notebook’s target degree starts at 1. The fixture has no embedding or model output, and choosing a seed stands in for the vector search.

These control different things. Raising the seed count can enlarge the candidate set and the reranker’s prompt while the final context stays at two passages. Bound the degree, the candidate relation count and the passage count before an expensive reranker runs. When a hub connects many unrelated policies, filter by product, relation type, version and access rights before following it. Record which budget stopped the expansion, so a missing passage can be traced to a stage.

Treat identity mapping as part of retrieval correctness. The notebook’s entities are raw strings from its triplets. “Euler”, “Leonhard Euler” and “leonhard Euler” are three separate nodes, as are “the Bernoulli theorem” and “The Bernoulli theorem”. Table 3 shows the cost: a seed that lands on the wrong spelling reaches one relation instead of ten. We call this the split identity. Normalise names and resolve aliases to stable IDs at indexing time.

The same stable IDs keep vectors and adjacency in step. An operational index needs explicit updates to both on every source change. A fresh vector record with stale adjacency retrieves the right entity and still traverses the wrong policy graph.

Key Takeaways

  • Vector search picks seed entities and relations; powers of the incidence matrix expand them. Products count walks and do not show that a relation answers the question.
  • Each degree adds candidates, and a hub can pull in the whole corpus at degree 1. Bound degree, relation count and passages before the reranker, and rerank against the question.
  • Resolve entity spellings to stable IDs and update vectors and adjacency together. A split identity or stale adjacency sends a correct vector hit down the wrong path.

Check yourself

1. With B the entity-by-relation incidence matrix, what do B Bᵀ and Bᵀ B connect, and what do their powers not tell you?

B Bᵀ connects entities that share a relation, and Bᵀ B connects relations that share an entity. Their powers count walks and expand the seed sets, but they do not certify that a relation supports the question. An undirected incidence matrix also loses a predicate’s direction.

3. Entity search for Euler returns the node spelled "leonhard Euler", and expansion finds one relation instead of ten. What went wrong, and how do you prevent it?

The notebook stores entities as raw strings, so three spellings of Euler became three nodes, and only one of them is linked to Johann Bernoulli. This is a split identity. Normalise names and resolve aliases to stable IDs at indexing time, and update vectors and adjacency mappings together.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s cancellation answer reaches an export node but misses the retention condition. Where do you look first?

What a strong answer covers:

  • Inspect the retrieved seed IDs, traversed relations and final passage IDs before editing the prompt.
  • Check whether the retention relation was extracted, linked and reachable in the allowed direction.
  • Separate an expansion cutoff from a reranking or context-budget omission.
  • Add the complete policy path to the golden question’s evidence set and check its sources.

2. Support asks for themes across the whole handbook, but the current retriever returns only cancellation neighbours. How would you change retrieval?

What a strong answer covers:

  • Route the overview question to community reports with explicit corpus coverage.
  • Check which communities and report levels contributed to the answer.
  • Compare the overview against source passages and a flat baseline on the same corpus.
  • Retain local retrieval for questions about a specific product or policy condition.

3. GraphRAG improves an offline answer score but indexing is too expensive after every handbook edit. What would you measure?

What a strong answer covers:

  • Record extraction, embedding and report-generation work separately from query work.
  • Measure update frequency and which reports depend on each changed source.
  • Include failed calls, retries and storage in the comparison.
  • Compare amortised work over the actual question volume without assuming an unmeasured break-even point.

4. Two documents use “Snapshot” for different products, and the assistant joins their policies. How do you contain the error?

What a strong answer covers:

  • Inspect entity identity, product scope and version fields before increasing traversal depth.
  • Split ambiguous entities and preserve the source record for each relation.
  • Filter candidate passages and graph edges by the caller’s product and access rights.
  • Test a question where the wrong merge would produce a plausible answer with a false policy condition.

5. Every answer has numbered citations, yet reviewers keep finding unsupported claims. What would a useful attribution check do?

What a strong answer covers:

  • Split the answer into claims and resolve each reference to an existing source span.
  • Check that the span supports the claim and preserves its conditions and date.
  • Audit relation evidence as well as the final node’s description.
  • Treat fixed confidence values and valid citation syntax as insufficient evidence of support.

Key Takeaways

  • Name the graph representation and retrieval route in each evaluation result.
  • Bound expansion before context construction and measure the candidate set it creates.
  • Preserve passage provenance through both graph and community retrieval.
  • Re-evaluate source coverage, update work and answer quality whenever extraction or routing changes.
