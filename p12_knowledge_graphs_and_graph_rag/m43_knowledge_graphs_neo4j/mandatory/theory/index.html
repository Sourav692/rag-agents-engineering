M43 Knowledge Graphs with Neo4j

A knowledge graph represents named entities and their relationships explicitly. Cypher matches those relationships; vector retrieval helps find a starting entity when a question uses different words. The M43 notebooks build on four ideas: the property graph, pattern queries, translating questions into Cypher, and combining graph facts with text retrieval.

Open the lab

The running example extends the fictional Larkspur Cloud handbook into plans, features, regions and supporting passages. The golden questions ask which plans support exports in the EU, which source establishes that capability, and what happens after a policy version changes. The notebooks use healthcare, historical and extraction examples; the Larkspur catalogue is a separate teaching fixture.

TL;DR

  • Model identity, edge direction and source provenance before querying the graph.
  • Bind the same plan variable across feature and region patterns when both constraints must hold.
  • The 43.3 notebook executes hand-written Cypher; automatic text-to-Cypher is an explained extension.
  • Vector candidates can fail exact relationship checks. In the lab, k=2 yields no eligible plans, k=3 yields one and k=5 yields both.
  • A stored source link helps only when retrieval carries its passage into the answer evidence.

Mental model

Extraction turns prose into candidate facts. Stable identities let those facts connect across documents, while retained passages let a reader inspect what supports them. Retrieval must carry both the matched relationship and its supporting text into the answer.

M42 ended with lightweight graph retrieval as one option among summaries and memory. This module builds the graph itself, in Neo4j, and asks it questions that similarity search cannot settle.

A Larkspur support engineer asks: Which plans support data export in the EU? A vector index returns two passages that both look relevant. One says a plan supports export. The other says a plan is available in the EU region. Nothing in either passage says they describe the same plan. The question is a join: one entity has to satisfy two facts, and text similarity has no notion of “the same entity”.

This lesson uses a small teaching catalogue of Larkspur plans (EU Team, EU Enterprise, US Export, Legacy plan), the fixture of the lesson 43.4 lab. It is separate from the handbook’s own plan list. The notebook teaches the same ideas on a five-node graph about Albert Einstein.

Nodes, edges, properties

A property graph stores entities as nodes, typed and directed relationships between them, and properties (key and value pairs) on either. A node carries one or more labels, such as Plan or Feature, which say what kind of thing it is. A relationship has exactly one type, such as SUPPORTS, and always points from one node to another.

Larkspur’s question needs three nodes and two relationships:

Direction carries meaning

The arrow is part of the fact. Plan SUPPORTS Feature and Feature DEPENDS_ON Service answer different questions, and reading an edge backwards changes the claim. In Figure 2, BORN_IN points from the person to the country; a query that walks it the other way finds who was born in Germany, which is a different question.

Choosing relationship types and directions is part of modelling the handbook, and it happens before any retrieval algorithm runs. A good test is to write each golden question as a path first. If a question has no path in the model, no query can answer it.

An absent edge is not a no

A graph answers only the relationships you stored or can derive from them. If the EU Team plan has no AVAILABLE_IN edge to the EU region, three different things could be true: the plan is not available there, the source never said so, or extraction missed the sentence that did. We call this silent absence: an empty match looks the same in all three cases.

The practical rule is to keep the source of each relationship (lesson 43.2) so a missing edge can be traced back to a document, and to phrase empty results as “no matching facts in this graph” rather than “no”.

Cypher

Cypher is Neo4j’s query language: you draw the shape you want with nodes in parentheses and relationships as arrows, and the database returns every way that shape matches the stored graph. Variables name parts of the shape. When the same variable appears twice, both appearances must be the same node.

The EU export question becomes one pattern with two arms:

Clause What it says Why it matters
MATCH arm 1 plan p has a SUPPORTS edge to the feature whose id is the parameter feature finds plans with export
MATCH arm 2 the same p has an AVAILABLE_IN edge to the region whose id is the parameter region keeps only those also in the EU
RETURN DISTINCT p.id one row per plan removes repeated rows from several matching paths
ORDER BY plan sorted output stable results for tests
Parameters feature = "export", region = "eu" passed separately from the query text the query is reused, and values never get spliced into Cypher

Table 2: The EU export query, clause by clause.

Pitfall: DISTINCT is not deduplication. DISTINCT removes repeated result rows. If the import created two EU Team nodes, both come back, because they are different nodes. Fixing duplicate entities is an import problem, covered in lesson 43.2.

The notebook’s queries

The notebook defines two read queries. One lists every node’s name. The other returns four paths out of the Einstein node, one per relationship type, joined with UNION. Each arm of that union names its relationship type explicitly, which means a fifth relationship added later would not appear until someone adds a fifth arm. A single pattern with an untyped relationship would return all of them, at the cost of returning edges you did not ask about.

It writes with MATCH followed by MERGE: find both endpoints first, then create the relationship between them only if it is missing. If either endpoint is absent, the MATCH finds nothing and no edge is written, without an error. That is silent absence again, this time created at write time.

Read the paths before the wording

When a model phrases the result (“No plan supports export in the EU”), the sentence can only be as good as the rows behind it. Inspect the returned paths and their source facts first. If the pattern used the wrong label, a reversed direction or the wrong identifier, the rows are empty, and a fluent answer cannot supply the relationship the query failed to match. Lesson 43.2 turns to where those nodes and edges come from.

Key Takeaways

  • A property graph stores labelled nodes, typed directed relationships and properties on both. Choose identity keys, relationship types and directions by writing each golden question as a path first.
  • An empty match cannot tell “false” from “never stored” from “missed by extraction”. Keep each edge’s source and phrase empty results as missing facts.
  • Reuse one variable when one entity must satisfy several patterns, and pass values as parameters. Separate variables give a cross-product match, and DISTINCT does not merge duplicate nodes.

Lesson 43.1 built a graph by hand. Real graphs come from files, and the import code decides which rows become the same entity.

Larkspur loads its plan catalogue from a CSV every night. One morning the graph holds twice as many plans as the catalogue lists. Nothing failed; a product manager had reworded several plan descriptions, and the import treated each reworded plan as a new one. The text-to-Cypher assistant now answers “which plans support export in the EU” with both the old and the new EU Team.

The cause is the identity rule, and the healthcare notebook shows it on real rows.

Identity before import

MERGE looks for a node that matches the whole pattern you give it, every label and every property, and creates a new node when none matches. The properties inside the pattern are the identity. Put a description in the pattern and a changed description means a different entity.

The notebook reads healthcare.csv row by row and turns each row into nodes and relationships:

Location Location node, LOCATED_AT edge from the provider name
Provider and Patient together TREATS edge provider matched by name, patient matched by name only

Table 1: How the notebook maps each CSV column into the graph.

The file has 100 rows, 5 provider names, 7 patient names, 5 specialisations and 5 locations. We replayed the notebook’s merge rules over the file in Python (no Neo4j server was involved; these are the counts the rules imply for one run on an empty database):

Two failures account for the gap.

  • Identity by attributes: every row gives a patient a different age, gender or condition. Merging on all four values makes each of the 100 rows a new patient. Seven people become 100 nodes.
  • Name fan-out: the TREATS step matches the patient by name alone. A name now points at up to 22 nodes (Frank Yellow), and the edge is drawn to every one of them that exists so far. 32 real provider and patient pairs become 368 edges.

The provider merge on name and bio works here only because each provider has one bio in the file. Change one bio between imports and the provider splits in two, which is Larkspur’s doubled plan.

A stable key

For Larkspur’s catalogue the stable key means three rules:

  1. A uniqueness constraint on Plan.id, created once, which the database enforces and which also gives the merge an index to look up.
  2. A merge on id alone, followed by a SET of the display name, description and update time. A reworded description updates the existing node.
  3. A key that includes its scope, such as tenant or catalogue, when the identifier is unique only within one of them. A display name alone rarely captures that scope.

These are a proposed Larkspur schema, not cells from the healthcare notebook. Merging on attributes fits only data with no identifier at all, and then only when every attribute in the pattern is truly fixed.

The flattened row

A CSV row is often an event: one visit, in which this provider saw this patient, in this specialisation, at this location. The notebook turns the row’s columns into separate edges on the provider:

Figure 3: The flattened row. Each column becomes an edge on the provider, and nothing records which values came together.

Once the row is gone, the graph no longer knows which specialisation went with which location. We call this the flattened row. The replay shows how much it costs:

Every provider ends up linked to almost every specialisation and location. A question such as “cardiologists in Houston” returns all five providers. The data in this file is synthetic and noisy, which makes the effect large, but the mechanism is general.

When the row is the fact, model it as a node, such as a Visit or an Assertion, with an edge to each participant:

Figure 4: The row as a node. The visit holds the four values together: “Cardiology in Houston” matches only visits that had both.

The row node costs one extra hop per question and one node per row. It pays whenever a question combines two columns of the same row. For Larkspur the same choice appears with sources. “The 2026 handbook says EU Team supports export” is a row-level fact. Store the source document and its version with the assertion, and deleting an obsolete edition can remove exactly the capabilities that edition asserted.

Key Takeaways

  • MERGE matches the whole pattern, so the properties in it are the identity. Merge on a stable, scoped key backed by a uniqueness constraint, and update descriptions with SET.
  • Matching by name alone draws edges to every node that shares the name. On the notebook’s file, 32 real pairs became 368 TREATS edges.
  • When a row is the fact, store it as a node. Splitting its columns into separate edges loses which values went together.
  • Validate keys, cast types, match both endpoints and count failures. Re-import a fixture with an edited description and keep a source identifier and version on every assertion.

Check yourself

1. The healthcare notebook merges a provider on both name and bio. Why does that break repeated imports?

MERGE matches the whole property pattern. When a bio changes, no existing node matches name and bio together, so the import creates a second provider. Merge on a stable key with a uniqueness constraint, then update the bio with SET.

2. The file has 7 patient names, yet the replayed import creates 100 Patient nodes and 368 TREATS edges. What causes each number?

Patients are merged on name, age, gender and condition, and every row has a different combination. Each of the 100 rows makes a new node. The TREATS step then matches the patient by name alone, which draws an edge to every node with that name. The 32 real provider and patient pairs fan out to 368 edges.

3. Larkspur deletes an obsolete handbook edition, but some plans still show capabilities that only that edition asserted. What did the import leave out?

A source document identifier and version on each assertion. With them, deleting the edition also removes the assertions it supported; without them, the capabilities stay behind with nothing to support them.

Text-to-Cypher

Text-to-Cypher is a loop in which a language model reads the user’s question and the graph schema, writes a Cypher query, the database runs it, and a second model call phrases the returned rows as an answer. The schema is the model’s only map of the graph: which labels exist, which relationship types connect them, which way they point and which properties they carry. For Larkspur’s question the model has to find both SUPPORTS and AVAILABLE_IN and bind them to the same plan.

Figure 1: The text-to-Cypher loop. The answer can only restate what the rows contain.

Each stage hands the next one a different artefact, and each can fail on its own:

Stage Input Output Typical failure
Generate question, schema Cypher text and parameters wrong relationship, direction or property
Validate Cypher text accepted, corrected or emptied query a write clause slips through
Read accepted query rows empty or truncated result
Answer question, rows sentence rows restated as a stronger claim

Table 1: What moves between the stages of Figure 1.

The schema goes stale when the graph changes. LangChain’s Neo4jGraph reads it once, when the object is created. Add a REQUIRES_APPROVAL relationship afterwards and the generator keeps working from the old map until someone calls refresh_schema(). Refresh after every schema change, and re-run the questions that touch the changed labels and properties.

Debug the query before the answer

When an answer is wrong, the bug is usually in the query, and the answer hides it. Save five fields for every request: the original question, the generated Cypher, its parameters, the returned rows, and the final answer. Then compare the generated pattern with the hand-written reference before reading the prose.

Small mistakes in the pattern return nothing without raising an error. We also ran each planted query through the chain’s corrector, the step validate_cypher=True adds, with the Larkspur schema:

Table 3: Planted generation mistakes. Each produces a valid query and a misleading result, and the corrector changes none of the outcomes.

The corrector checks relationship types and directions against the schema. It flips a reversed edge in a single simple pattern, but in both two-arm versions we tried it gave up and returned an empty query, which the chain treats as zero rows. It never looks at properties, at missing conditions or at writes.

This is the silent empty result: Cypher treats an unknown relationship type or property as a pattern that matches nothing (at most with a warning notification), which is a valid answer to the query that was written. The answer step then sees zero rows and phrases them. An empty result should say “no matching facts under this schema and data version”; it cannot establish that a capability is impossible.

A test set for translation

Build the test set from question types, not from one phrasing. For Larkspur:

  • Paraphrase: “Which EU plans can export data?” should produce the same rows as the reference.
  • Unknown entity: a plan that does not exist should return no rows and say so.
  • Ambiguous name: “Team” could be several plans, which needs a clarifying answer rather than a guess.
  • Multi-relationship: export and EU together, the join that a single arm gets wrong.
  • Empty result: a feature no plan has, which checks the wording of a “nothing found” answer.

Grade the rows against the reference query as well as grading the answer.

The database is the guard

A generated query runs with whatever authority its database user has. One design puts the guard in the prompt:

Figure 2: A prompt guard. The instruction shapes what the model usually writes, and nothing stops the query it actually writes.

The other puts it in the database:

Figure 3: A database guard. The same query fails at the database, whatever the model wrote.

Give the chain a read-only database user, a query timeout (Neo4jGraph has none unless you set timeout) and a result limit. Then a bad query fails at the database.

Key distinction: LangChain’s chain refuses to start without an explicit allow_dangerous_requests=True. Its security note explains that the flag records that you accept the risk; it does not enforce any permission.

Key Takeaways

  • Text-to-Cypher generates a query from the question and the schema, runs it and phrases the rows. Neo4jGraph reads the schema once: refresh it after every schema change and re-run the questions it affects.
  • Log question, Cypher, parameters, rows and answer separately. A wrong relationship name, direction or property key returns no rows and no error, and the optional corrector empties or passes such queries rather than fixing them.
  • Hand-written queries are the expected results for generated ones, but a correct query over a flawed graph still returns wrong rows. Enforce safety with a read-only user, timeouts and result limits.

Check yourself

1. Why must Text-to-Cypher generation see the graph schema, and when must that schema be refreshed?

The schema tells the model which labels, relationship types, directions and properties exist, which it needs to write a pattern that matches, such as SUPPORTS and AVAILABLE_IN bound to one plan. Neo4jGraph reads it once at creation, so after a schema change call refresh_schema() and re-run the questions that use the changed parts.

2. The generated query and the reference query both return 368 rows for cardiology patients in Houston. Does that mean the system answered correctly?

No. It means the generated query matches the reference, and both run over a graph whose import flattened its rows. In the CSV only 2 rows pair Cardiology with Houston. The chain would also pass only the first 10 rows to the answer model. Grade some answers against the source data.

3. A team relies on a prompt that says generate read-only queries, plus the allow_dangerous_requests flag. Is the database protected?

No. A prompt does not restrict database authority, the flag only records that the risk was accepted, and the corrector passes a DETACH DELETE unchanged. Use a read-only database user, a query timeout and result limits, so a bad query fails at the database.

Graph + vector hybrid

What a bigger budget cannot fix

The graph check is a post-filter: it can return fewer than k results, including none. A larger k gives the graph more candidates. It cannot fix a missing AVAILABLE_IN edge, an entity that was never resolved to the right plan, or an eligible plan whose text ranks below every budget you can afford. Authorisation is a separate constraint again: apply it to every branch of retrieval, and never treat it as a relevance filter that a bigger budget might relax.

Extraction produces candidate facts

LLM extraction asks a model to read a passage and return the entities it names and relationship tuples of the form (subject, relation, object). Each tuple is a candidate fact: the model’s reading of the passage, which may be right, partial or invented. Nothing in the output proves the passage supports it.

From candidate to edge

A candidate becomes an edge only after it passes the checks the notebook leaves out:

Figure 1: The path from a passage to a stored assertion. The support check comes before identity, and the source travels with the edge.

Each check has a reason:

  • Support: the passage states the tuple, conditions included. A schema-valid tuple can still be unsupported.
  • Types: the subject and object have allowed labels, and the relation is an allowed type between them, such as Plan SUPPORTS Feature.
  • Identity: each name resolves to one existing entity, or to a new one on purpose.
  • Provenance: the stored assertion keeps the passage identifier, the source version and the extraction configuration (model and prompt). It can then be audited, and deleted with its source.

Names are not identities

The notebook removes duplicate entities by putting the names in a set. That merges only exact repeats. “EU Team” and “EU team” stay two entities; “Team” and “EU Team” stay two as well, and here they might really be two products. A string set cannot tell an alias from a different thing.

Resolve names with identifiers and context: the plan id from the catalogue, the document the name appears in, the region it is linked to. When a name could be two entities, send it to review rather than guessing. The next section covers the tuple itself.

Preserve relations and conditions

Chunk boundaries

The chunker adds whole lines until the next line would reach the threshold. A chunk reaches the threshold only when one line reaches it on its own. With the notebook’s 2,665 words that never happens on this file; at a 50-word threshold it makes 148 chunks and 2 of them reach or pass 50 words, because the longest line has 75. Test the boundary before treating the threshold as a hard maximum.

Boundaries also split references. A pronoun at the top of a chunk points to a name in the chunk before it; in this file even one row needs its subject column to resolve “his”. The optional notebook lays out the stages that handle this as separate tasks: named entity recognition, coreference clustering and resolution, then relationship extraction and graph building. Its cells are empty scaffolding for you to fill. When you evaluate those stages, inspect pronouns and aliases at chunk boundaries specifically.

The full-text query is built word by word: each word becomes a fuzzy term that tolerates two character edits, and the terms are joined with AND. We ran the notebook’s builder:

AND means every word must match the same entity. An extracted name with an extra word, such as “Augustus (Octavian)”, misses an entity stored only as “Augustus”. A name made only of punctuation leaves no words, and the builder raises an IndexError that stops the whole chain.

For each extracted name the branch keeps at most 2 matching entities and returns at most 50 relationship rows between them. These are caps, not relevance rules. Nothing orders the 50 rows by how useful they are, which means a highly connected entity can fill the budget before the needed relationship appears. We call this the neighbourhood budget failure. Log which entity each name matched, its score, and whether the 50-row cap was hit.

Check the evidence contract

Ingestion with sources keeps the MENTIONS link from each chunk to the entities it names. The graph branch then excludes MENTIONS and returns bare relation strings. The answer model sees “EU Team SUPPORTS Export” with no passage behind it. We call this the uncited fact: the graph knows where the fact came from, and retrieval throws that away.

The contract that fixes it is one rule: every graph assertion travels with its supporting passage identifier and text. In practice that means following each relationship back to the chunk that mentions both endpoints, and putting the passage beside the relation line in the context:

Follow-up questions

The notebook also handles conversation. When a chat history is present, a model first rewrites the follow-up into a standalone question (“When did he become the first emperor?” becomes a question naming the person), and both branches retrieve with the rewrite. That rewrite runs on a separate OpenAI chat model at temperature 0, not on the model that answers. If it resolves “he” to the wrong person, both branches go to the wrong entity together.

Record the rewritten question beside the original. The answer step never sees the rewrite: its question slot receives the whole input as text, the chat history included (checked by rendering the notebook’s prompt in the scratchpad). The user’s words stay available for judging the answer, mixed with the history.

1. The end-to-end notebook combines two kinds of retrieval. What does each one contribute to the context?

The text branch runs hybrid keyword and vector search over the Document chunks and contributes 4 passages. The graph branch extracts names from the question, resolves them through a full-text index and contributes their incoming and outgoing relationships as relation lines. The context holds both, in two labelled blocks.

2. A question about a highly connected entity misses the relationship it needs. Which caps in the graph branch could explain it?

Each extracted name keeps at most 2 matching entities and 50 relationship rows, and nothing orders those rows by usefulness. A highly connected entity can use up the 50 rows before the needed relationship appears. Log the matched entity and whether the cap was hit.

3. Ingestion stored sources, yet the answer model cannot cite a passage for any graph claim. Why not, and what fixes it?

The graph branch excludes MENTIONS edges and returns bare relation strings, so the passages never reach the prompt. Retrieve the supporting passage identifier and text with each graph assertion and put them beside the relation line in the context.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s EU export plan disappears after a handbook update, although its passage still exists. How do you locate the failure?

What a strong answer covers:

  • Checks ingestion version, entity key and the required feature and region paths.
  • Separates a missing graph edge from a candidate that fell below the vector budget.
  • Reads the extraction input and supporting passage before changing the prompt.
  • Adds the updated plan and previous version to the fixed regression questions.

2. Product wants both a free-text search and exact regional availability. Would you retrieve vectors first or match the graph first?

What a strong answer covers:

  • Uses exact graph predicates when identity and constraints are known.
  • Uses semantic candidates for approximate descriptions and validates their graph relationships.
  • Measures eligible-answer recall against candidate budget, query latency and graph degree.
  • Applies authorization across every retrieval branch and checks all returned source passages.

3. The assistant returns a convincing answer from an empty Cypher result. What should monitoring record?

What a strong answer covers:

  • Logs original question, rewritten question, generated query, parameters and rows separately.
  • Grades query results against known paths as well as grading final answer support.
  • Tracks empty-result and truncation rates by question type and schema version.
  • Requires an explicit unsupported-answer response when the available facts cannot answer.

4. A CSV re-import doubles the number of plans after descriptions change. How do you repair the import design?

What a strong answer covers:

  • Inspects which mutable properties were included in the merge pattern.
  • Uses a stable scoped identifier with an appropriate uniqueness constraint.
  • Updates descriptions separately and resolves existing duplicates with source-aware review.
  • Tests repeated imports and edited descriptions on a fixture before loading the full catalogue.

5. A generated query asks for a plan relationship that is absent from the schema. Should the system retry until it finds an answer?

What a strong answer covers:

  • Checks whether the requested relation is representable and present in the current schema.
  • Bounds retries and query execution, with read-only database permissions.
  • Distinguishes a translation error from missing source data and ambiguous identity.
  • Returns the evidence limitation rather than inventing a relation to satisfy the request.

Key Takeaways

  • Choose stable entity identities and explicit relationship meanings before import.
  • Compare generated Cypher with a hand-written query and inspect rows before grading prose.
  • Separate semantic candidate selection from exact graph validation and measure both stages.
  • Retrieve source passages with graph assertions so each answer claim can be checked.
