M42 Hierarchical & Memory-Augmented Retrieval

A passage index finds local evidence. A question about the whole handbook may need a representation assembled from several passages before retrieval begins. The M42 notebooks build on four ideas: abstraction levels, collapsed-tree retrieval, global memory and dual-level retrieval.

Search the leaves or the whole tree
Open the lab

Larkspur Cloud’s handbook supplies the running example. A customer asks how cancellation affects data access; an operations lead asks how the handbook manages service continuity. Both questions connect policies that live in separate sections. Source passages still decide what the answer may claim.

TL;DR

  • RAPTOR adds summaries at several levels to the retrieval corpus. Preserve their links to the passages they summarise.
  • Collapsed-tree retrieval ranks leaves and summaries together. Tree traversal chooses a route through parent-child links; these are different retrieval algorithms.
  • MemoRAG uses corpus memory to draft retrieval clues. Verify those clues against retrieved evidence before answering.
  • LightRAG separates entity-focused retrieval from retrieval over thematic relationships, then assembles graph context and source passages.
  • The lab uses four authored source passages and three representative summaries. At a two-node budget, the continuity query reaches one source identifier with leaves only and four through summary ancestry. These are fixture retrieval counts, not algorithm benchmark results.

Mental model

Derived representations can make distributed evidence easier to find. They also introduce another place to lose an exception, merge unrelated entities or preserve a deleted policy. Keep source identifiers and versions through every transformation so a retrieved summary can lead back to its evidence.

Questions no single chunk answers

Lesson 42.1: RAPTOR: clustering and recursive summarisation. Notebooks: 01a_raptor.ipynb

What you’ll learn

  • Explain why a passage index struggles with a question about a theme that spans several sections.
  • Trace how RAPTOR builds summary levels by clustering, summarising and repeating.
  • Compare collapsed-tree retrieval with top-down tree traversal under the same context budget.
  • Diagnose a summary that reaches the right sources and still drops the condition a customer asked about.

M10 built the flat baseline: split the handbook into passages, score each passage against the question, keep the top few. That works when one passage holds the answer. This module asks what to do when no single passage does.

An operations lead at Larkspur Cloud asks How does service continuity work? The handbook never answers that in one place. Availability guarantees and outage credits sit in the SLA section, status updates in the outages section, and data protection in export and retention. A flat index scores each of those passages against the word “continuity”, and most of them never use it.

The failure is a scoring problem. A theme is spread across passages, and no passage is about the theme as a whole. RAPTOR (Recursive Abstractive Processing for Tree-Organized Retrieval) answers it by adding new text to the index: summaries that are about the theme. The rest of this page covers how those summaries are built, how retrieval searches them, and how they mislead.

Abstraction levels

An abstraction level is one layer of text in the index, from the original passages at level 0 up through summaries of summaries. Each level answers a different kind of question. A passage keeps the exact wording; a summary connects claims across passages; a summary of summaries names a broad theme.

The same handbook at three levels looks like this:

Level Larkspur example Answers
0, passage The export procedure: Settings, then Data Where to click
1, summary Cancellation joins export, retention and billing What happens when a plan ends
2, summary of summaries Continuity across cancellation and outages How the handbook protects the customer

Table 1: One handbook at three abstraction levels.

RAPTOR builds the levels bottom up. It embeds the current texts, groups them into clusters by meaning, writes one summary per cluster, then treats those summaries as the texts for the next round:

Figure 1: The RAPTOR build loop. Each round clusters the current level and summarises every cluster into the next one.

The notebook builds this loop over a 33-page climate report, one page per level-0 text. It clusters with a Gaussian mixture model, asks a chat model to summarise each cluster, and stops after at most three rounds. The number of clusters per round is half the number of texts, capped at 10. That rule sets an upper bound on the tree’s shape:

Round Texts in Clusters allowed Summaries out, at most
1 33 pages min(10, 16) = 10 10
2 up to 10 min(10, 5) = 5 5
3 up to 5 min(10, 2) = 2 2

Table 2: The tree’s shape from the notebook’s cluster rule. Actual counts can be lower when a mixture component receives no text.

The notebook assigns each text to exactly one cluster. That is a teaching simplification: the RAPTOR paper (Sarthi et al., 2024) uses soft clustering, where one passage can feed several summaries, and it describes both search strategies covered in the next section.

The lab’s fixture is the smallest tree that shows the idea. It has four authored passages, two level-1 summaries and one level-2 summary, with each summary listing the source passages it descends from:

Figure 2: The lab’s fixture tree. The summaries are written by hand and labelled representative; no clustering runs in the browser.

Each node needs more than its text. Store its level, the identifiers and versions of the passages it summarises, and its children. With those fields a retrieved summary can lead back to its evidence, and a changed passage can mark every ancestor for rebuilding.

A summary can be accurate overall and still drop the one exception a customer asks about. Call that lossy compression: the summary’s sources cover the policy, but its text no longer carries the condition. For a policy answer, follow the summary back to its passages before quoting a condition or a number.

The notebook’s metadata does not support that walk yet. Its level-0 records hold level, origin and parent_id but no id, and each summary builds its child_ids by reading that missing field. Every first-level summary therefore points at children with no identifier. Treat the notebook’s tree as a sketch of the structure, not as verified provenance.

With levels in place, the next question is how retrieval chooses among them.

Collapsed-tree retrieval

Collapsed-tree retrieval puts every node, passages and summaries alike, into one pool, scores them all against the question and keeps the best within a budget. The mix of levels in the context then follows the question: a theme question pulls summaries, a procedure question pulls passages.

Tree traversal works the other way. It picks the best nodes at the top level, then searches only their children, and so on down. One early wrong branch excludes every leaf beneath the other branches:

Figure 3: Two ways to search a tree. Collapsed search ranks every level at once; traversal commits to parents before it sees their children.

The notebook stores every level in one FAISS index, which is what makes collapsed search possible. Its query helper then walks the levels from the top down, passing a level filter that FAISS does apply, and returns up to four nodes per level. After each level it appends the text AND id:(…) with the chosen children to the query string. That text changes the query that gets embedded; it does not filter by identifier or join parents to children. Check the identifiers of the nodes you get back before calling this a constrained traversal. A compression step then rewrites each retrieved node to the parts a model judges relevant, one more transformation whose output needs a source check.

The notebook also defines a proper traversal function that filters children by parent identifier. It is never called, and it would fail as written: it calls a FAISS method that the installed library does not provide.

The interactive lab isolates the one change that matters here: adding summary nodes to the pool. It scores the fixture of Figure 2 with real TF-IDF cosine similarity, one vocabulary fitted over all seven nodes. Leaf-only mode keeps level 0; collapsed mode keeps everything.

At a budget of two nodes, the lab computes these results for its first two questions:

Service continuity Leaves only 1 0 1 16
Service continuity All levels 2 2 4 24
Export steps Leaves only 2 0 2 37
Export steps All levels 2 0 2 37

Table 3: Leaf-only against collapsed retrieval at two nodes. Scores checked against scikit-learn’s TfidfVectorizer.

For continuity, the only passage that matches is availability, at a score of 0.168. With summaries in the pool, the handbook summary (0.448) and the continuity summary (0.378) take both places and reach all four source identifiers. For export steps, the export passage scores 0.387 and no summary makes the top two, leaving the context unchanged.

Reaching four source identifiers describes ancestry. It does not mean the context holds the source passages, and it says nothing about the answer a model would write. The lab’s third question shows the gap:

Question at two nodes Leaves only All levels What changed
When is cancelled data permanently deleted? retention, export (37 words) retention, portability (40 words) The portability summary replaces the export passage

Table 4: Planted failure in the lab. The summary that enters has no “30 days” in its text.

The retention passage still ranks first, and the answer survives here. The pattern is what to watch: a summary that matches the question’s vocabulary takes a slot a passage held. Call it summary displacement. At a tighter budget, or with a vaguer passage, the summary would be the only evidence, and lossy compression would decide the answer.

The notebook build has its own planted failures, one per guard it is missing:

Input What the notebook does Why
A summary’s children Records them with no identifier Level-0 records have no id field
A single input text Stops with a parameter error Half of 1 is 0 clusters, and the mixture model needs at least 1
A third round with two summaries Keeps levels 0 to 2 and discards the top two summaries Only a round that ends with one summary is stored
A child filter Adds words to the query The AND id: text is embedded, not applied

Table 5: Planted failures in the notebook’s RAPTOR build.

These are fixes to make before trusting the tree, and none of them changes the idea. Collapsed search over a tree with real provenance is the design worth copying.

In practice: a theme question

A Larkspur support team adding RAPTOR to the handbook would work through it in this order:

  1. Keep the passage index as level 0, with stable identifiers and versions.
  2. Build summaries per cluster and store each one’s level, sources, versions and children.
  3. Search all levels together at a fixed context budget, and log which level each hit came from.
  4. When a summary ranks high, add its source passages to the context before the model quotes a condition.
  5. When a passage changes, rebuild every summary above it.

To test it, freeze the corpus and a question set, then compare flat retrieval, the summary tree and graph retrieval at the same final budget. Count indexing calls apart from retrieval and generation calls. Include precise facts, cross-section comparisons, changed policies and questions the handbook cannot answer.

Lesson 42.2 replaces the summary tree with a different derived representation: a memory of the corpus that writes search clues.

Key Takeaways

  • RAPTOR clusters passages, summarises each cluster and repeats, so one index holds both exact wording and broad themes. Store each node’s level, sources, versions and children with its text.
  • Collapsed-tree retrieval ranks all levels in one pool and lets the mix follow the question; top-down traversal can lose a relevant leaf to an early wrong branch.
  • A summary can reach the right sources and still drop the condition asked about. Follow it back to its passages before quoting a condition or number, and watch for summaries displacing passages at a tight budget.

Check yourself

1. Why does collapsed-tree retrieval rank every level together instead of selecting parents first and then searching their children?

Ranking every level in one pool lets the mix of passages and summaries follow the question. Traversal commits to parents before it sees their children, and one early wrong branch excludes every leaf beneath the others. The notebook stores all levels in one FAISS index, which is what makes the collapsed search possible.

2. In the lab at a budget of two nodes, what changes when summaries join the pool for the continuity question and for the export question?

For continuity, the two summaries replace the availability passage: summary hits go from 0 to 2, source identifiers reached from 1 to 4, and context from 16 to 24 words. For export steps nothing changes: the same two passages and 37 words. Reaching more source identifiers describes ancestry, not a better answer.

3. A customer asks for the exact data-deletion condition, and the top hit is a summary linked to the retention passage. Can you quote the condition from the summary?

No. A summary can cover the right sources and still drop the condition, which is lossy compression; in the lab the portability summary has no “30 days” in its text. Follow the summary back to the retention passage and quote that. In the notebook build, the first-level child links have no identifiers, and its tree cannot yet support that walk.

When the question has no keywords

Lesson 42.2: MemoRAG: global memory and clue-guided retrieval. Notebooks: 02a_memorag.ipynb (optional)

What you’ll learn

  • Explain what corpus memory is and how its clues reach the retriever.
  • Trace one question through memory search, clue writing, retrieval and the answer.
  • Count the extra searches and model calls that clues add per question.
  • Diagnose a fluent clue that points at a product or policy the corpus does not support.

Lesson 42.1 added summaries to the index, which gave a theme question something to match. MemoRAG leaves the index alone and changes the query instead.

A Larkspur operations lead asks How does Larkspur protect continuity? The question names no section. Searched directly, it matches passages that share its words and misses the ones that answer it: export, retention, availability guarantees and incident reports. A reader who knew the whole handbook would turn the question into better searches first. MemoRAG gives the retriever that reader.

Global memory

Global memory is a compact, model-readable representation of the whole corpus that turns a vague question into specific search clues before retrieval runs. For the continuity question, memory might suggest export before cancellation, 30-day retention window and availability guarantee and credits. Each clue is a search, not an answer: the final answer still needs source passages that support every claim.

The MemoRAG paper (Qian et al., 2024) builds the memory with a long-range model that compresses the corpus, then has that model draft clues for the retriever. A clue can contain a wrong detail. Its job is to locate evidence, and the generator checks what comes back:

Figure 1: Clue-guided retrieval. Memory shapes the searches; only retrieved passages reach the answer.

The optional notebook implements a smaller approximation. Its memory is a list of readable text records, each a topic and its details, written by a chat model reading the corpus and validated against a schema. The records are embedded and stored in a FAISS index. The memorising prompt says it mimics KV-cache creation; the records are text, not the attention key and value tensors a model keeps inside, and the analogy stops there.

How the notebook reads the corpus sets how much memory each call sees:

Corpus Memorised as Passage index for retrieval
A 33-page climate report The whole text in one model call Chunks of 1,000 characters, 200 overlap
A book of about 600 pages Chunks of 50,000 characters, 5,000 overlap, one call each The same 1,000-character chunks

Table 1: Memory input and passage index in the notebook. Memory sees large spans; retrieval still returns small passages.

At question time the notebook runs one fixed sequence:

Figure 2: One question through the notebook’s pipeline. Clues come from two separate model calls.

The clue step makes two calls: one asks for text spans likely to appear in the corpus, the other for surrogate questions, narrower questions that clarify the original. The notebook splits both replies into lines, drops any line of three words or fewer, and appends the original question. Each surviving line becomes one search for three passages.

That design has a cost that grows with the clue count. The arithmetic for one question:

Clues kept Searches Passages before deduplication Model calls
0 1 3 3
4 5 15 3
8 9 27 3

Table 2: Retrieval work per question (illustrative clue counts). One memory search is added to every row; the three model calls are the two clue calls and the answer.

Removing duplicate passages is the only control on context size. Deduplication drops repeats; it does not cap tokens. Eight clues that each find three new passages put 27 passages in front of the generator. Call that clue sprawl, and set a passage or token budget after deduplication.

Each stage has its own failure, and its own thing to log:

Stage What to inspect Failure to test
Memorise Topic and detail records, parse failures An exception lost during extraction
Find memory Retrieved records and their source versions Stale or irrelevant memory dominates
Generate clues Exact clue text beside the original query A plausible clue invents a product
Retrieve Source identifiers, ranks and deduplication Repeated clues crowd out another policy
Answer Support for each claim The generator repeats an unsupported clue

Table 3: Where clue-guided retrieval fails, stage by stage.

The invented-product row is the failure that matters most. Call it the fluent clue: a clue that reads well and names something the corpus does not contain. If retrieval then finds a loosely related passage, the generator may treat the clue’s claim as supported. The notebook’s answer prompt tells the model to use only the retrieved context and to say when the context is not enough. Logging clues beside the passages they found is what shows whether that instruction held.

The notebook’s update path has gaps worth planting:

Input What the notebook does Why
A second batch of records Compares new topics with at most four existing ones A nearest-neighbour search for an empty string returns the default four records, not the whole store
A model reply that is not valid JSON Falls back to a line parser for Topic: and Details: A schema error counts as a parse error and triggers the fallback
A question before anything is memorised Stops with an error The clue step returns no list, and the query step loops over it

Table 4: Planted failures in the notebook’s memory store.

A topic registry or stable record identifiers fixes the first row. The third needs a fallback that searches with the original question alone.

Memory is derived data, with the same duties as the summaries in lesson 42.1. When Larkspur changes its retention rules, update the passage index and regenerate every memory record written from those passages. Shared memory must not leak restricted documents through its records or its clues. Test a deletion against the stored memory and against generated answers.

In practice: continuity clues

For Larkspur, a memory-assisted retriever would run like this:

  1. Memorise the handbook into topic records, each tagged with the passages and versions it came from.
  2. For How does Larkspur protect continuity?, retrieve the closest memory records and write clues from them.
  3. Search the passage index with each clue and with the original question.
  4. Deduplicate, cut to a fixed passage budget, and answer only from what remains.
  5. Log the clues, the passages each one found, and the claims each passage supports.

Run the same questions through plain retrieval at the same budget. Report a gain only when the clue-guided run finds supporting passages the plain run missed.

Limits of the notebook

The notebook loads two prebuilt memory stores, one per corpus, and the second corpus is a book PDF. None of those files ships with this repository, and the memorising cells are commented out because they are slow and paid. As shipped, the notebook shows the implementation’s shape and does not run end to end.

Its evaluation compares plain RAG with this MemoRAG approximation on the first 5 of 44 climate questions and on 15 of 16 questions about the book. It also scores answers saved from a run of the original MemoRAG on a GPU. Those scores come from a model judge and a different corpus, and they say nothing about the Larkspur handbook. Report a comparison only after running both pipelines on the same questions and budget.

Lesson 42.3 builds a third derived representation, a graph of entities and relationships, and searches it at two levels.

Key Takeaways

  • Corpus memory writes clues that help the retriever find evidence. A clue can contain a wrong detail, so every claim in the answer must rest on a retrieved passage.
  • Each extra clue adds a search and its passages, and deduplication alone does not bound the context. Log clue text beside the original question and set a budget after deduplication.
  • Treat memory as derived data. Regenerate records when their source passages change, and check that records and clues never expose restricted documents.

Check yourself

1. What is a MemoRAG clue for, and why must the answer still rest on retrieved passages rather than on the clue?

A clue, written from corpus memory, tells the retriever where to look, such as export, retention and availability for a continuity question. It can contain a wrong detail or name something the corpus lacks, the fluent clue. Only retrieved passages count as evidence, and each claim in the answer needs one that supports it.

2. Larkspur changes its retention rules. What has to change besides the passage index?

Every memory record written from the old retention passages has to be regenerated, because memory is derived data with dependencies. Test a deletion against both the stored memory and generated answers. Shared memory also must not expose restricted documents through its records or clues.

3. The notebook keeps eight clues for a question and retrieves three passages for each clue and for the question. What bounds the context the generator sees?

Nothing beyond deduplication. Nine searches at three passages each can return 27 passages, and removing repeats does not cap tokens. Set a passage or token budget after deduplication and log which clue found each passage.

Questions that connect two policies

Lesson 42.3: LightRAG: low-level and high-level graph retrieval. Notebooks: 03a_light_rag.ipynb

What you’ll learn

  • Explain how LightRAG turns passages into a graph of entity and relationship profiles.
  • Compare the low-level route, which searches entities, with the high-level route, which searches relationships.
  • Trace which entities, edges and passages each route adds to the context.
  • Diagnose a graph that merged two products, lost a relation’s direction or kept a withdrawn policy.

Lesson 42.1 summarised the handbook into a tree, and lesson 42.2 wrote search clues from a memory of it. Both help with themes. Neither records how two things in the handbook relate.

A Larkspur customer asks How does cancellation affect export? The export passage explains where to click, and the retention passage says cancelled data is kept for 30 days and then deleted. The answer is the link between them: export before the window closes. A flat index may rank the export procedure first and leave the retention rule below the cut, because the procedure never mentions cancellation.

LightRAG stores that link as an edge in a graph, gives it a short text profile, and searches it like any other passage.

Dual-level retrieval

Dual-level retrieval searches two indexes built from one graph: entity profiles for the specific things a question names, and relationship profiles for the themes that connect them. For the cancellation question, the low-level route finds the entities Cancellation and Export. The high-level route finds a relationship profile about data portability. Both routes add evidence to one context.

High-level here means thematic relationships. It does not mean RAPTOR’s upper summary levels from lesson 42.1, or the community reports that Microsoft GraphRAG builds in M44. The LightRAG paper (Guo et al., 2024) describes graph indexing with entity and relationship profiles, the two retrieval levels, and adding new documents to the graph without a rebuild.

The graph comes first. The notebook builds it in four stages:

Figure 1: Building the graph. One model call per chunk extracts entities and relationships; merging folds repeats into one node or edge.

Each relationship carries a description and a few high-level keywords. The keywords are what the high-level route searches. At question time a model splits the question into two keyword lists, one per route:

Figure 2: The two routes. Each keyword set searches its own index, then expands through the graph.

The routes differ in what they search and what they pull in after a hit:

Route Vector search target Graph expansion Passages added
Low level Entity profiles Every edge touching the entity Every chunk the entity appears in
High level Relation profiles The edge’s two endpoint entities The chunks the relation came from

Table 1: What each route adds after a hit.

The notebook builds this from scratch with NetworkX, structured extraction schemas and two FAISS indexes; it does not use the packaged LightRAG library. It splits a 33-page climate report into chunks of 1,200 characters with 150 overlap, which gives 78 chunks, and keeps the first 20 to save extraction calls. Every later query can only reach those 20.

To see the merge and the routes without a model, we ran the notebook’s merge loop and its selection logic on five scripted extractions from the Larkspur handbook:

The merge did four things a reader should expect:

Extracted What the graph holds Why
“Cancellation” and “CANCELLATION “ One node, two descriptions joined Names are trimmed and lower-cased before matching
Cancellation to Data retention, and Data retention to Cancellation One edge with both descriptions The graph is undirected; the second edge merges into the first

The last row is the failure that hurts policy answers. Call it a name collision: two things share a name, and their facts merge into one profile. Lower-casing causes it here and cannot fix it. Stable identifiers, with the plan or product in the key, can.

The second row is a different loss. An undirected graph keeps that two things relate and drops which way. The notebook’s graph also holds one edge per pair, so a typed model with several relations between the same two entities needs a different graph structure.

Then the two routes, with the vector hits fixed by hand:

Seed hits Entities in context Edges in context Chunks in context
Low level: Cancellation 1 3 3
High level: Export to Data retention 2 1 1
Both: two entities and that relation 3 4 4

Table 3: What the routes select on the scripted graph. Cancellation touches three edges, and all three come in with one hit.

Two things show up in Table 3. First, neighbour sprawl: one low-level hit on a well-connected entity brings in every edge around it. The notebook’s defaults are four entity hits and four relation hits; those are seed counts, not a bound on the context. In a full handbook graph, an entity such as Cancellation touches every policy that mentions it.

Second, the low-level route adds the edges around a hit but not the entity profiles at their far ends. In the low-level row, the relationship block mentions Billing and Account deletion, and the entity block describes only Cancellation. The passages behind those edges do come in: every chunk a relation came from is also recorded for both its endpoints. Check that invariant in your own build before relying on it for provenance.

Combine both routes with their source passages, remove duplicates and apply a context budget before generation. An edge description can help find a policy. It cannot replace the policy’s qualifiers, which live in the passage.

In practice: Larkspur’s graph

For the Larkspur handbook, a LightRAG index would follow these rules:

  1. Key entities by stable identifier, with the plan or product in the key, and keep Business and Enterprise daily backups apart.
  2. Keep relation direction where it carries meaning, such as cancellation starts retention.
  3. Store the source passage and version behind every node description and edge.
  4. Limit graph expansion to evidence the asker may see.
  5. When a policy is withdrawn, recompute the merged profiles as well as removing the passage; the old wording survives inside node and edge descriptions.

To evaluate the routes, run entity-only, relationship-only and combined retrieval on the same precise and cross-section questions. Inspect answer support, source coverage and context size. Count extraction failures and indexing calls apart from query cost: the notebook skips a chunk whose extraction fails and continues, and a graph with plausible labels can still miss the relationship a question needs.

Key Takeaways

  • LightRAG runs two routes over one graph: low-level search over entity profiles and their edges, and high-level search over relationship profiles and their endpoints. Both feed one budgeted context with the source passages.
  • Seed counts do not bound the context, because one well-connected entity brings in every edge around it. Set a budget after expansion.
  • Merging by lower-cased name collides things that share a name, and merged profiles keep old wording after a source is removed. Use stable identifiers, and recompute profiles when a policy is withdrawn.

Check yourself

1. For the question How does cancellation affect export, what does each LightRAG route search for?

The low-level route searches entity profiles for keywords such as Cancellation and Export, then adds every edge touching each hit. The high-level route searches relationship profiles for themes such as data portability, then adds the two endpoint entities. High-level means thematic relationships, not RAPTOR’s upper summary levels or GraphRAG community reports.

2. Larkspur withdraws a policy and removes its source passage from the index. Is the graph now clean?

No. Node and edge descriptions are merged across passages, and the old wording survives inside a profile. Recompute the merged profiles from the remaining passages as well as removing the source passage.

3. An Enterprise customer is told that daily backups are kept for 7 days, although Enterprise keeps them for 30. What in the graph causes this?

A name collision. The notebook merges entities by trimmed, lower-cased name, and the Business and Enterprise daily backups became one node whose profile holds both periods with no plan attached. Key entities by stable identifier with the plan in the key, then rebuild the affected profiles.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s assistant says cancelled accounts lose data immediately, although the source passage describes a retention window. The retrieved summary omits that window. How do you debug it?

What a strong answer covers:

  • Trace the summary to the exact source version and inspect whether summarisation dropped the exception
  • Inspect both the summary rank and the source passage rank before changing the answering prompt
  • Retrieve source evidence for precise policy claims and flag unsupported summary assertions
  • Add the cancellation question to the golden set and rebuild affected summary ancestors

2. Operations asks for themes across the handbook, while support asks exact policy questions. Would you force both through top-down tree traversal?

What a strong answer covers:

  • Compare traversal with collapsed search on both question types under the same context budget
  • Check whether choosing one high-level parent excludes a needed leaf early
  • Retain precise passages when summaries lack the required condition or number
  • Report indexing work and per-query quality separately instead of assuming a tree is faster

3. A new memory-assisted retriever returns fluent clues about a service Larkspur no longer sells. What should you monitor?

What a strong answer covers:

  • Log memory version, generated clues, retrieved source identifiers and final citations
  • Measure evidence recall and answer support separately from clue fluency
  • Invalidate derived memory when its source documents change or are deleted
  • Compare against original-query retrieval and fall back when clues find no supported evidence

4. Larkspur has two products with the same short name. Entity extraction merges them and connects the wrong cancellation rule. How should the graph change?

What a strong answer covers:

  • Use stable identifiers and product context instead of case-normalised names alone
  • Keep relation direction, qualifiers and source identifiers when the domain requires them
  • Inspect extracted assertions against passages before accepting a merge
  • Rebuild affected profiles and test an ambiguous-name query after the correction

5. A private incident report is deleted, but a global handbook summary still mentions it. What must deletion remove?

What a strong answer covers:

  • Follow dependency links through summaries, memory entries, graph descriptions and vector indexes
  • Remove or regenerate derived text that contains the report’s information
  • Apply access controls before derived evidence is exposed, including shared summaries
  • Verify with a deletion regression query and inspect stored representations as well as the answer

Key Takeaways

  • Choose a representation for the information need and compare it against the flat baseline.
  • A summary’s source coverage does not prove that every source fact survived compression.
  • Distinguish a paper’s algorithm from the simplified implementation in its teaching notebook.
  • Measure retrieval, source support, update work and generation quality separately.
