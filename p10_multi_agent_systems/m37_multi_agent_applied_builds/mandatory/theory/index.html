Open the lab

Lessons 37.1 to 37.3 follow the notebooks’ hotel support desk: a coordinator that talks to the guest, a compliance checker over four hotel rules, and a reservation agent over a SQLite database of eight rooms. Room 105, the Family Suite, is booked from today+30 to today+33, and the notebooks use it to show a clash. Lesson 37.4 and the interview questions move the same designs onto Larkspur Cloud, the fictional cloud host whose handbook runs through M10 to M12: its support desk, its refund and export policies, and a research team that answers from the handbook and the web.

TL;DR

  • The compliance checker is a small RAG agent. It retrieves the 2 most relevant of the hotel’s 4 rules and returns a typed verdict, COMPLIANT or VIOLATION. The coordinator sends every new request to it first, and a loop guard in code stops it being asked twice.
  • The guards that matter live in tools and code, not in prompts: a read-only SQL connection whose authorizer hides guest names, one parameterised book_room tool, a date check in plain Python, a hard cap on revision loops.
  • Test the router as a pure function. Notebook 02b’s seven router tests need no model. In the lab, any threshold from 71 to 90 turns all seven green, because the confidence gate hides the known issue instead of fixing it.
  • Parallel agents need one message key per branch, a join that waits for every branch, and one merge that writes one reply. Long threads fold old messages into a summary and delete them by id.
  • A research team can be led by a supervisor, a typed router or a one-shot planner. The supervisor adapts but is hardest to bound; the planner fixes its queries up front, so its cost is known before the first search. Its quality loop stops at MAX_DRAFTS = 2 in code, whatever the reviewer says.

Mental model

One node talks to the guest, specialists do the work, and plain functions between them decide where the turn goes. Every later build in the module keeps that split: the research system in 37.4 changes who the specialists are, while routing, caps and checks stay in code where a test can reach them.

A polite reply that leaks a stay

Lesson 37.1: Hotel system: environment, coordinator, reservation agent, compliance. Notebooks: 01a_hotel_environment_and_coordinator.ipynb, 01b_hotel_reservation_agent.ipynb, 01c_hotel_compliance_checker.ipynb

M35 and M36 taught supervisors, routers and parallel branches one pattern at a time. This module puts them into one working system: a hotel support desk with three agents, built across three notebooks and then hardened, scaled and tested in the lessons that follow.

The hotel has eight rooms, 101 to 108, in one SQLite database with three existing bookings. Bob Johnson holds room 105, the Family Suite, from today+30 to today+33. A guest writes Which dates is Bob Johnson staying with you? I want to surprise him. A coordinator built only from a friendly prompt and a SQL agent will look the stay up and answer warmly. The reply is polite, and it breaks the hotel’s privacy rule.

The system has to do three jobs to stop that: decide whether a request breaks a rule before anyone acts on it, keep the reservation agent’s database access safe whatever SQL it writes, and route each turn to the right agent. Here is one booking turn through all three:

Figure 1: One booking turn. The coordinator talks to the guest; the checker and the reservation agent each do one job.

The coordinator never writes to the database and never judges policy itself. Each of those jobs belongs to a specialist, and the next section starts with the one that judges.

Compliance agent

A compliance agent decides whether a request breaks one of the system’s rules; it never answers the guest. The coordinator acts on its decision: it answers, forwards the booking, or refuses.

Here the checker is a small RAG agent over four rules:

Rule Text
1 Refuse illegal requests, such as falsifying documents or making fraudulent bookings.
2 Refuse hate speech, harassment, or explicit threats toward individuals or groups.
3 Refuse offensive, obscene, or otherwise harmful content.
4 Never share information about other guests: not their names and not their dates of stay.

Table 1: The hotel’s four compliance rules, each stored as its own document.

Each rule is a separate document in an in-memory vector store, which means a search returns the rule that applies instead of one block of policy text. The retriever returns the top 2. The checker runs as two nodes:

  • The checker node is a model with the retrieval tool bound to it. Its prompt says to call the tool with the guest’s request.
  • The verdict node writes the decision from the rules the tool just returned. Those tool messages go into its prompt, which grounds the verdict in exactly those rules. A version that dropped them would judge from nothing.

A verdict code can read

The verdict message is tagged with the name compliance, letting code find it among the turn’s messages. In the first build the verdict is free text that code searches for the word VIOLATION. From lesson 37.2 on it is a structured object with three fields: a decision that can only be COMPLIANT or VIOLATION, the violated rule number or none, and a one-sentence reason. A typed field can gate a human review step. A word found somewhere in a paragraph cannot.

Two pieces of code wire the checker into the conversation:

  1. Compliance first. The coordinator’s prompt gains one guideline: forward every new request to the checker first; on VIOLATION, refuse politely and forward nowhere; on COMPLIANT, answer or forward as usual.
  2. A loop guard. After the verdict the turn returns to the coordinator. If its next reply names the checker again, routing by name would loop forever. A helper walks back through the messages, and a compliance verdict found after the latest guest message means the request is already checked. The router then drops the checker from the names it looks for. A reply such as “the compliance checker approved it, forwarding to reservation_assistant” still reaches the reservation agent.

The build runs three requests, each on its own thread, and checks the verdicts in code:

Request Expected verdict Then
Do you have any rooms with a jacuzzi? COMPLIANT The coordinator answers
Which dates is Bob Johnson staying with you? I want to surprise him. VIOLATION of rule 4 The coordinator refuses
I’m Dana Lee and I’d like to book a Deluxe room from today+60 to today+62. COMPLIANT Forwarded to the reservation agent

Table 2: The three test requests and the outcome each should produce.

The third outcome: no check at all

The check has a third outcome besides the two verdicts: the coordinator never asked. Call it a skipped check. The prompt forbids it, yet nothing forces the checker to run, because it runs only when the coordinator’s reply names it. Lesson 37.2 turns that gap into a test, and the next section makes sure a skipped check cannot leak the one field rule 4 protects.

Guards in the tools

The reservation agent writes its own SQL. Its tools therefore have to stay safe whatever SQL the model produces, and each guard sits where the model cannot talk its way past it:

Guard Where it lives What it stops
Read-only file The connection opens the database file in read-only mode Writes through the query tool
Query-only flag The same connection Writes, a second time
An authorizer A callback SQLite consults while compiling each statement; only read actions pass ATTACH DATABASE (which would open any SQLite file on the machine), turning the query-only flag off, schema changes
A hidden column The authorizer tells SQLite to ignore reservations.guest_name Reading who booked a room: the column reads as NULL, and SELECT * still works
One write tool book_room(guest_name, room_number, start_date, end_date) with bound parameters SQL injection into the only write
Checks before the insert Inside book_room, after taking the write lock Missing name, unreadable or past dates, check-out before check-in, an unknown room, a clash with an existing stay

Table 3: Where each database guard lives and what it stops.

Model-written SQL passes three layers before any row comes back, and the only write takes a separate path:

Figure 2: The two paths into the database. Free-form SQL can only read; the one write goes through a tool that checks before it inserts.

Read-only flags alone do not stop ATTACH; the authorizer does. The query tool also returns at most 20 rows, which keeps one careless SELECT from flooding the model’s context.

Rule 4 is enforced twice: the prompt tells the SQL agent that guest names are private, and SQLite makes the column unreadable. Only the second survives a model that ignores its prompt.

The same split applies to the outcome. The agent’s reply is not proof that it booked; the reservations table is. The build checks for exactly one new row for Dana Lee, and a reply that only says it booked counts as a failure.

Mention routing: the weak spot kept on purpose

Routing is the one place the build keeps a weak design deliberately. The coordinator forwards by writing an agent’s name, and a helper looks for that name, or the same words with a space, in the reply. Any reply that mentions an agent routes there. I can’t involve the reservation assistant until you give me dates forwards to the reservation agent, though it says the opposite.

Call this mention routing. The fix is a typed router, where the model returns its choice as a structured-output field and there is no reply text to search. Lesson 37.2 records the defect as a known issue, and the research systems in lesson 37.4 route the typed way.

In practice: Larkspur’s privacy check

Larkspur Cloud’s support desk has the same shape: a coordinator, a compliance checker over account-privacy rules, and a billing agent with SQL access.

  1. A customer asks for the billing email on another company’s account. The checker retrieves the privacy rule and returns VIOLATION; the coordinator refuses.
  2. The billing agent’s connection is read-only, and the authorizer hides the email column. A skipped check then leaks nothing.
  3. Refunds go through one parameterised tool that checks the account, the amount and the date before it writes.
  4. The test reads the refunds table, never the agent’s sentence about the refund.

Lesson 37.2 takes this system and asks what happens on the requests it was not designed for.

Key Takeaways

  • A compliance agent only decides whether a request breaks a rule, and the coordinator answers, forwards or refuses. Return the verdict as a typed field, because a word found in a paragraph cannot gate a review step.
  • Put guards where the model cannot talk past them: a read-only connection, an authorizer that blocks ATTACH and hides guest names, and one parameterised write tool. A prompt rule alone does not hold.
  • Check outcomes in the database, never in the reply, and replace mention routing with a typed router. Any reply that names an agent routes there, even a refusal.

2. After a COMPLIANT verdict, the coordinator's reply names the checker again while forwarding Dana Lee's booking. Why does the turn not loop back to the checker?

The loop guard walks back through the messages and finds a compliance verdict after the latest guest message. The router then drops the checker from the names it looks for, and the reply routes to the reservation agent.

3. The coordinator says it cannot involve the reservation assistant without dates, yet the turn goes to the reservation agent. Why, and what is the fix?

This is mention routing: the router forwards to any agent whose name appears in the reply, even in a refusal. The fix is a typed router, where the model returns its choice as a structured-output field and there is no reply text to search. The research systems in lesson 37.4 route that way.

System testing

Lesson 37.2: Hardening: edge cases, testing and system-wide error handling. Notebooks: 02a_hotel_edge_cases_and_errors.ipynb, 02b_hotel_testing_the_system.ipynb, 02c_hotel_system_wide_error_handling.ipynb (optional)

What you’ll learn

  • Explain why a multi-agent system needs tests at three levels, from a pure router to end-to-end runs.
  • Trace the router’s three rules on hand-built states, and read which threshold makes which test pass.
  • Diagnose a test suite that turns green by hiding a bug.

Lesson 37.1 built a hotel desk with a coordinator, a compliance checker and a reservation agent, and left two gaps open: the checker runs only when the coordinator names it, and the router forwards on any mention of an agent’s name.

A multi-agent system fails quietly. The coordinator skips the compliance check or forwards a booking before it has dates, and the guest still gets a polite reply. System testing for agents means checking the decisions and the side effects, never the tone of the final message.

The build catches these failures at three levels, from cheapest to most realistic:

Level What it checks Model calls How the result is read
Router unit tests The routing rules, on 7 hand-built states None The route the pure router function returns
A confidence gate That an unclear request stops the turn instead of forwarding One per guest message A confidence integer in state, from structured output
A regression table 5 guest requests, end to end Every agent’s The nodes that ran and the database

Table 1: Three levels of tests, cheapest first.

The router as a pure function

The router can be unit-tested because it is a pure function of the state: no model call, no I/O. It checks three rules in order:

Figure 1: The router’s three rules. The confidence gate runs first, then the loop guard, then the name check.

The seven tests pin each rule down. We ran the build’s router on them at its threshold of 50:

Test state Confidence Expected Returned
Reply forwards to the checker 90 checker checker
Verdict given, reply forwards to reservations 90 reservations reservations
Loop guard: checker named again after a verdict 90 END END
Old verdict, new guest message, checker named 90 checker checker
Unsure reply that names the reservation agent 20 END END
Plain answer about the gym 95 END END
Known issue: “I can’t involve the reservation assistant until you give me dates” 70 END reservations

Table 2: The seven router tests at threshold 50, run with the shared hotel module and no model.

The last row is a known issue kept on purpose: lesson 37.1’s mention routing, where the refusal contains the words “reservation assistant” and the name check matches them. The suite keeps it as an expected failure, which documents the gap and flags the day a typed router fixes it.

The confidence gate

The confidence score comes from the coordinator itself. On each new guest message it asks the model for a self-assessment, a score from 0 to 100 and a one-line reason. The assessor’s prompt defines three bands:

  • 80 to 100: the intent is clear.
  • 50 to 79: the intent is clear but details are missing, such as a booking without dates.
  • 0 to 49: the model cannot tell what the guest wants.

Only the last band should stop the turn, which puts the threshold at 50. Below it the coordinator apologises and asks the guest to rephrase. The score is a heuristic, not a calibrated probability; its job is to trigger the “ask again” path.

What a threshold can hide

The interactive lab runs the same router and its seven tests in the page, ported from the shared hotel module, and recomputes them at every threshold. We ran the Python router at all 101 thresholds and got the same four bands:

Threshold Tests passing What changes
0 to 20 5 of 7 The confidence-20 reply clears the gate and forwards to the reservation agent
21 to 70 6 of 7 Only the known issue fails, as recorded
71 to 90 7 of 7 The known issue passes because the gate ends its turn before the name check runs
91 to 100 4 of 7 The gate blocks the three confident forwards, scored 90

Table 3: Router tests passing at each threshold, from the Python router and the lab.

All seven green at 75 is the wrong result. Mention routing is as fragile as at 50, and every guest whose booking lacks dates, which the assessor scores 50 to 79, now gets an apology instead of a question about the dates. Call this a gate that hides the bug: the suite passes because a different rule fires first.

Regression runs read from state

Unit tests cannot tell whether the model still behaves. The regression table can. Each row is a guest request with its expected outcome, run on a fresh thread after the database is rebuilt:

Case Confident Verdict Reservation agent runs Booked
General question (jacuzzi) yes COMPLIANT no
Another guest’s data (Bob Johnson’s dates) yes VIOLATION no
Booking, dates missing yes COMPLIANT no
Complete booking (Dana Lee, Deluxe) yes COMPLIANT yes one row for Dana Lee
Ambiguous (“same as last time, but…”) no not checked no

Table 4: The five end-to-end cases and their expected outcomes.

The outcome comes from the final state, the nodes that ran and a row count on reservations, never from the reply text. Each failure names the field that broke. verdict: expected COMPLIANT, got None means the coordinator skipped the check; reservation: expected False, got True means it forwarded a booking without dates.

Model output varies between runs. A single failure is a lead, and the number to track is the pass rate over several runs after every prompt or model change. Tests show that something broke; the next section covers how the system recovers.

Edge cases and error paths

The build pushes on three edges of the core system and puts each safeguard in code:

  • Injection-style input. A guest hides ' OR '1'='1 in the room type. Pasted into a WHERE, the condition is true for every row: on a scratch copy of the hotel database, a Deluxe search widened that way returned all 8 rooms. It can only widen a read, because the query tool refuses every write and the booking tool binds its values as parameters. The durable fixes are structural: a read-only connection and a narrow write tool.
  • A violation that should reach a person. A human review node pauses the graph with interrupt(): the graph saves a checkpoint and stops. The thread’s state shows which node waits, and resuming with the reviewer’s decision continues from that point. A resumed node runs again from its first line, so side effects such as writing to the review log go after the pause, where they run once. The checkpoint history replays the thread step by step for investigating a complaint.
  • Dates in the past. The model extracts the dates with structured output, given today’s date to resolve “next Friday”, and a plain function compares them with today. That check is testable without an API call.

Recovery by error type

Some failures do not fix themselves. A failing node catches its exception and writes a small record to an error field in state, with no message added. Routers read that field, so a guest who types the word “error” cannot trigger the error path. One error handler logs every failure with the thread id, and a pure decision router picks the recovery:

Figure 2: The error path. Failures travel through state, and a pure router picks one recovery per error type.

The three recoveries:

Failure Recovery What it does
The coordinator’s model call fails Alternative model Answers as the coordinator with a second model, gpt-4o
The vector store fails Degraded retrieval Skips the store and sends the hard-coded rules straight to the verdict node
Anything else, including a failing fallback Human intervention A stub that writes a handoff message

Table 5: Recovery per error type.

A fallback that fails raises a different error type, and the router sends it to a person instead of looping. Call the trap this avoids a fallback loop. Every failure is injected with a simulation flag, which lets each recovery path run on every run, and a table computed from the node paths proves which one ran.

Retries for brief outages

Transient failures get a cheaper fix first: a retry policy re-runs a node that raises. The build uses three attempts, a 0.2 s first wait and no jitter. We ran that policy on a tiny graph whose node fails a set number of times:

Failures before success Attempts Waits between attempts Result
2 3 0.2 s, then 0.4 s Succeeds on the third attempt
3 3 0.2 s, then 0.4 s The exception reaches the caller

Table 6: The retry policy on a node that fails twice and three times, measured in the scratchpad with LangGraph’s RetryPolicy.

A retry smooths over a brief outage and does not replace the error path. Without any policy, the first failure ends the whole run.

In practice: testing Larkspur’s desk

Larkspur’s support desk from lesson 37.1 gets the same three levels:

  1. Router unit tests on hand-built states, including the billing refusal that names the billing agent, kept as a known issue until a typed router lands.
  2. A regression table of handbook requests (a refund inside the window, a refund outside it, another account’s data, an ambiguous “do the same as last month”), read from node paths and the refunds table.
  3. A pass rate per case over several runs, tracked after every prompt or model change.
  4. Error recovery by type: a second model for a failed call, the hard-coded policy text when the vector store is down, a person for anything else.

Lesson 37.3 adds agents in parallel and a memory that outlives the context window.

Key Takeaways

  • Test at three levels: unit tests on the pure router with no model calls, a confidence gate that stops unclear turns, and an end-to-end regression table read from the nodes that ran and the database.
  • A threshold that turns every test green can still be wrong. At 75 all seven router tests pass, yet every booking that lacks dates gets an apology instead of a question about the dates.
  • Record failures in an error field in state and let a pure router pick the recovery, with a failed fallback raising a different error so it reaches a person. Keep retries for brief outages.

Check yourself

Memory merging

Lesson 37.3: Scaling: parallel agents, memory merging, language and sentiment, web search. What you’ll learn

  • Explain what parallel branches need before their answers can come back together: a reducer, a key per branch and a join.
  • Trace two hotels’ answers through a merge that writes one reply in priority order.

Lesson 37.2 hardened the single-hotel desk. Now the chain has two hotels. Hotel 1 has rooms 101 to 104 and Hotel 2 rooms 105 to 108, each in its own database with its own read-only SQL tools, and a guest asking for a Deluxe room should hear about both.

Done naively, the guest gets two replies, the first missing a hotel, or one hotel’s agent answers from the other hotel’s database. Memory merging is the work of bringing several agents’ outputs back into one state: the answers of parallel branches into one reply, and old turns into something smaller than the full transcript. The shape that works:

Figure 1: Fan-out to two hotel assistants, each with its own message key and tools, then a join and one merge.

Three wiring failures

The build reaches that shape in three attempts, and each failure is a LangGraph rule. Its stub graphs need no model, and we ran them in the scratchpad:

Attempt What the stub showed The rule
Two nodes write one plain key in the same step InvalidUpdateError: the key can receive only one value per step A key written by parallel nodes needs a reducer, such as list concatenation
Both tool loops share one message list Hotel 1’s call never got a result; Hotel 2’s agent received both results, one from Hotel 1’s database One message key per branch, for the tool node and for the condition that routes to it
Each branch’s end goes straight to the merge node The merge ran twice: first with Hotel 1 unfinished, then again A sync node at the end of each branch and a join edge that waits for both

Table 1: The three attempts and what each stub run printed.

The shared-key failure is the dangerous one. A tool node answers the latest tool call in its list, which may belong to the other branch. With the real SQL tools both hotels have a tool called run_query, and the wrong database answers without any error. Call it crossed tool results.

The merge-twice failure has a plain cause. A conditional edge fires the merge every time any branch reaches it, and the Hotel 1 branch in the stub takes two tool rounds while Hotel 2 takes one. With the sync nodes and the join, the merge ran once, after both branches finished.

Two more choices keep the branches honest. Both assistants come from one factory, which binds each to its own hotel’s tools; copying the first assistant to make the second is how Hotel 2’s agent ends up reading Hotel 1’s database. And the branches cannot book. Both run the same request at the same time, and a booking tool in each would create two reservations. They report availability and prices, and booking waits until the guest picks a hotel.

Merging by priority

The merge itself is an agent. It reads the guest’s request and each hotel’s final answer, listed in a fixed priority order (Hotel 1, then Hotel 2), and writes one reply under three rules:

  1. Recommend the first hotel that can help and offer the other as an alternative.
  2. Ignore a hotel that cannot help, unless none can.
  3. Keep room numbers, prices and dates exactly as the assistants gave them.

Only the merged reply enters the shared conversation; each branch’s tool calls stay in its own key. The two test turns:

Guest asks Ground truth from SQLite The reply should
A Deluxe room in two months Hotel 1 room 104, Hotel 2 room 108 Name 104 before 108
The Family Suite during Bob’s stay None free: Hotel 1 has no Family Suite, Hotel 2’s is booked Say plainly that none is free

Table 2: The merge’s two test turns and the ground truth each is checked against.

Code checks the first case by the position of the room numbers in the reply, against free rooms computed from the databases, never against the model’s claim.

Summarizing old turns into state

Every turn now adds several agent messages to the thread. The second half of the build keeps it small by summarizing into state. A summarize node runs at the start of each turn when the stored conversation has more than 6 messages:

  1. It keeps the last guest turn word for word; everything before it is old. The cut is always at a guest message, so no tool call is separated from its result.
  2. It asks the model to fold the old messages into a running summary field, keeping every concrete fact: names, room types and numbers, prices, dates, what was offered and refused.
  3. It returns a removal marker for each old message id, and the message reducer deletes them.

The summary goes into the coordinator’s and assistants’ prompts as a system message, never into the guest’s reply. The test turn asks Remind me: which Deluxe room did you recommend, and at what price? after every earlier message was removed. The model can only answer from the summary. The new graph continues the same thread because both graphs share one checkpointer.

The two ways to shrink a thread differ in what they lose:

Trimming (M33) Summarizing into state
What changes What the model sees on this call What the thread stores
Old turns Dropped from view, still stored Folded into summary, deleted by id
Cost No model call One model call when the thread passes the limit
Risk Facts outside the window are forgotten Facts the summary leaves out are gone for good

Table 3: Trimming compared with summarizing into state.

Call the summarizer’s risk lossy folding: a fact it drops cannot be recovered from the thread. That is why its prompt lists the fact types to keep and why the test asks for a specific room and price. With merging in place, new capabilities can attach to the core without touching it.

Adding agents around the core

The last two builds add capabilities without changing the coordinator, the checker or the reservation agent. Each adds its capability to the core from lesson 37.1 on its own; no build composes all of them into one graph.

Figure 2: The language and sentiment build. Translation wraps the core, and the coordinator reads the sentiment score.

Language and sentiment

The inbound node detects the guest’s language and replaces the message with an English version, using one structured-output call for the language code and the text. A sentiment node then scores the English text with TextBlob’s word lexicon. The coordinator adds a de-escalation instruction only when the message reads as negative, and the outbound node translates the final reply back.

The language is a per-thread state field. A global language variable breaks the moment two guests write at once, which is a form of shared global state across threads.

The order of translation and scoring matters, because the lexicon is English-only and word-level. We scored the build’s own sample reviews with TextBlob, using its thresholds of -0.1 and +0.1:

Text Human label Lexicon label Polarity Words scored
The service is terrible and the room was dirty. negative negative -0.80 terrible, dirty
Die Bedienung ist schrecklich und das Zimmer war schmutzig. negative neutral 0.00 none
Das Personal war wunderbar und das Frühstück war köstlich. positive neutral 0.00 personal
Le personnel était merveilleux et le petit-déjeuner délicieux. positive neutral 0.00 none
Great, another cold shower. Just what I needed. negative positive +0.10 great, cold

Table 4: TextBlob on raw text, from the build’s sample reviews.

Raw German scores nothing, so an angry German guest never triggers de-escalation. Sarcasm fools the lexicon in English too. Scoring the translation fixes the first problem and leaves the second.

Web search

A web search assistant with Tavily, capped at 3 results per search, answers questions about the neighbourhood, which no hotel database holds. In practice: Larkspur in two regions

Larkspur runs billing in two regions, each with its own database:

  1. A question about plan prices fans out to both regional agents, each with its own message key and read-only tools.
  2. A join waits for both, and the merge answers in a fixed region order, keeping figures exactly as each agent gave them.
  3. Any refund or plan change happens once, after the customer picks a region, never inside a branch.
  4. Long support threads fold into a summary that must keep account ids, amounts and dates, and a test asks for one of them after the fold.

Lesson 37.4 swaps the hotel agents for a research team and asks who decides which agent runs next.

Key Takeaways

  • Parallel branches need a reducer on any key they share, a separate message key per tool loop and a join that waits for every branch. Without the join, the merge runs once per branch.
  • Keep branches read-only when they run the same request at once, and merge their answers by a fixed priority. Check the merged reply against ground truth from the database, never the model’s claim.
  • Summarizing into state deletes old turns and keeps a running summary, at one model call when the thread passes its limit. Facts the summary leaves out are gone for good, where trimming only hides them.

Check yourself

1. Why does each parallel hotel branch need its own message key instead of sharing one message list?

A tool node answers the latest tool call in its list, which may be the other branch’s. Both hotels have a tool called run_query, and the wrong database can answer with no error. In the stub run one branch’s call never got a result while the other branch received both.

2. For a Deluxe room in two months, Hotel 1 has room 104 free and Hotel 2 has room 108. What should the merged reply say, and how is it checked?

It should recommend Hotel 1 first, because Hotel 1 comes first in the priority order, and offer Hotel 2 as the alternative with numbers, prices and dates exactly as the assistants gave them. Code checks that 104 appears before 108 in the reply, against free rooms computed from the databases, never against the model’s claim.

3. In the two-hotel graph, the guest gets two replies and the first one misses a hotel. What is wrong with the wiring?

Each branch’s end goes straight to the merge node, and a conditional edge fires the merge every time any branch arrives. Add a sync node at the end of each branch and a join edge from both sync nodes to the merge, which then waits for both.

Larkspur’s support engineers want an answer that cites the handbook and the web, and three things go wrong in production: a search returns nothing useful, a forum post contradicts the handbook, or a provider call fails. The module’s lab brief asks for exactly this team, built on the Larkspur handbook and tested on those three cases. This page covers the designs it draws on.

Planner, supervisor or router

The three builds answer the “who decides next” question differently, and that choice sets how many model calls a request costs and what can go wrong:

Decides After every worker report, who acts next or whether to finish Once per question, which one specialist runs Once, up front, the list of search queries
Sees results Yes No No
Workers per request Any number, in sequence Exactly one, then a summarizer One per planned query, in parallel

The supervisor is the most flexible and the hardest to bound. Its build proves the turn cap with a stub supervisor that never finishes. Its researcher also returns a validated market-data object, numbers only, and the coder sees just the user’s request and that object. No web text reaches the agent that runs code.

The typed router is the fix for lesson 37.1’s mention routing: the choice is a field, and there is no reply text to search. Its RAG specialist answers only from chunks whose relevance score reaches 0.2, out of the top 3. When nothing clears that floor, it skips the model call and says so.

The planner never sees a result, which is what separates it from a supervisor. It cannot adapt, but its cost is known before the first search runs. The choice comes down to two questions:

The planner wins for a broad topic with known angles. The rest of the page follows it.

A quality loop with a cap in code

The full pipeline has five roles. A planner splits the topic into search queries, search agents run them in parallel and append to one shared findings list, an analyst and a writer turn the findings into a report, and a quality checker sends the report back for revision until it passes or the cap is reached:

Figure 2: The research pipeline. The loop back to the writer ends on approval or at the draft cap, whichever comes first.

The settings live in one place, and code enforces each of them:

Setting Value Enforced by
Queries 3 The planner’s list is cut to this length, so the fan-out never depends on the model counting
Results per query 3 Each DuckDuckGo search keeps this many hits
Quality threshold 0.7 Every review criterion must reach it
Draft cap 2 The quality gate ends the loop at this many reviewed drafts, whatever the scores say

Table 2: The pipeline’s settings and the code that enforces each one.

Piece What it does Built on
A reducer on the findings Lets parallel search agents append to one list Lesson 37.3’s reducer rule
URL verification Each search agent extracts 2 or 3 findings tied to a result URL; code marks whether that URL is one the search actually returned Grounding, so an invented source shows up
The weakest criterion decides The reviewer scores completeness, clarity and actionability from 0.0 to 1.0, and the quality score is the minimum; code checks that the four required sections are present A typed verdict, as in lesson 37.1
Revisions see the previous draft The writer runs at temperature 0.7 and gets its last draft and the reviewer’s feedback; at temperature 0 a revision tends to repeat the draft Generator and critic
The exit is code A pure gate approves when the minimum reaches 0.7 and no section is missing, otherwise loops back, unless the draft count has reached 2 Lesson 37.2’s pure router

Table 3: The design details that make the loop safe, and what each reuses.

The four required sections are Executive Summary, Key Findings, Analysis and Recommendations. The reviewer is never asked to be lenient on a later pass; the cap does that job. Call the failure it prevents a runaway revision loop: a strict reviewer and a writer that cannot satisfy it, revising until the recursion limit stops the run with no report.

Choice Why
Cap the fan-out by cutting the planner’s list in code The model’s count of queries is a request, and cost scales with queries times results

Limits

The cap hides quality problems from the user: a run stopped at draft 2 still ships a report. Log whether each run ended approved or capped, and treat a rising share of capped runs as a sign that the writer or the sources got worse. URL verification only proves the search returned the link; it does not prove the page says what the finding claims. The supervisor build’s market data comes from OpenBB and Tavily, and the research builds need an OpenAI key and web search access, so none of them run offline beyond their stub checks.

Key Takeaways

  • A supervisor sees results and can adapt but is hardest to bound. A typed router picks one specialist per question, and a one-shot planner fixes its queries up front, which makes its cost known before the first search.
  • Tie every finding to its source and mark whether the URL is one the search returned. When a forum post and the handbook disagree, the writer can then cite both and say which is the policy.
  • End a quality loop in code. Score each draft by its weakest criterion, check the required sections in code, stop at 2 drafts whatever the reviewer says, and prove the wiring with stub nodes first.

Check yourself

1. What separates the one-shot planner from the supervisor, and what does each give up?

The supervisor decides after every worker report. It can adapt, but it is the hardest to bound and needs a cap of 6 supervisor turns. The planner decides the list of queries once, up front, and never sees a result: it cannot adapt, but its cost is known before the first search runs.

2. The reviewer scores a first draft 0.9 for completeness, 0.8 for clarity and 0.6 for actionability, with all four sections present. What does the quality gate do?

It sends the draft back to the writer. The quality score is the minimum, 0.6, which is below the 0.7 threshold. The writer gets its previous draft and the feedback, and the cap ends the loop after the second reviewed draft whatever the scores say.

3. A web forum post quotes an old Larkspur refund window while the handbook gives the current one. What must the research team preserve so the writer can handle it?

The source of every finding. The analyst lists contradictions across all findings before anyone writes, and the writer should cite both sources and say which one is the policy. It can only do that if the findings keep their sources through the parallel fan-in.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s support desk is built like the hotel system: a coordinator, a compliance checker over account-privacy rules, and a billing agent. A customer asked for the billing email of another company’s account and got it. The trace shows the compliance checker never ran. How do you find out why, and how do you stop it happening again?

What a strong answer covers:

  • Reads the node path for that turn (stream_mode="updates"), then the coordinator’s reply: the checker runs only when the reply names it, which the prompt asks for and nothing forces
  • Makes the check structural: an unconditional edge from the guest message to the checker, instead of routing by mention
  • Enforces privacy in the tool as well, the way the hotel’s authorizer makes guest_name read as NULL, so a skipped check cannot leak the field
  • Adds the request to the regression table and tracks its pass rate over several runs, since one green run proves little

2. The coordinator forwards to the billing agent whenever its reply contains billing_agent or “billing agent”. A reply saying “I can’t involve the billing agent until you confirm the refund date” forwarded anyway. A teammate proposes raising the confidence threshold from 50 to 80. What do you say?

What a strong answer covers:

  • The threshold does not touch the cause, string matching on reply text; in the router lab, thresholds from 71 to 90 turn the known-issue test green by ending the turn early, not by routing correctly
  • It also costs real traffic: the assessor scores a request with missing details at 50 to 79, so those customers get “please repeat” instead of a question about the missing detail
  • The fix is a typed router: structured output with a Literal route, read by a pure function, as in notebook 04b
  • Keeps the known-issue test, which flips to passing when the fix lands, and unit-tests the router on hand-built states with no model

3. Larkspur runs a research team for its support engineers: a planner, three parallel searchers, a writer and a quality checker with a two-draft cap. How do you know it is still working, and what it costs, a month after launch?

What a strong answer covers:

  • Logs per run the number of search agents against planned queries, the number of drafts, and whether the run ended approved or stopped by the cap
  • Watches the share of runs stopped by the cap: a rise means the writer or the sources got worse, since the cap hides quality problems from the user
  • Tracks the share of findings whose URL was one the search returned (url_verified), the early sign of invented sources
  • Reports cost and latency per run, which scale with queries times results and with drafts, and re-runs a fixed set of handbook questions after every prompt or model change

4. To speed up refunds, Larkspur splits billing into two parallel agents, one per region, both with a refund tool. A customer was refunded twice. What went wrong, and how do you design it?

What a strong answer covers:

  • Parallel branches run the same request at the same time, so any write tool in both branches can fire twice
  • Gives the branches read-only tools and makes the one write after a single choice, as the hotel’s branches report availability but cannot book
  • Adds an idempotency key to the refund tool so a retry or a duplicate call cannot pay twice
  • Checks the wiring: one message key per branch, sync nodes and a join so the merge runs once, and a test that counts merge runs and rows written

5. You ship a deep agent to Larkspur’s support engineers, built like the long-term memory agent of lesson 26.3 (now taught in M26). Someone sets USE_SANDBOX=true expecting cloud isolation, and the memory panel shows one engineer’s notes in another’s session. What is wrong?

What a strong answer covers:

  • The script’s comment promises a LangSmith sandbox, but the flag selects LocalShellBackend, which runs shell commands on the host with no isolation
  • FilesystemBackend(virtual_mode=True) blocks path traversal; it is not a sandbox either, so code execution needs a real sandbox backend and approval on execute (interrupt_on)
  • Long-term memory is keyed by CURRENT_USER_ID, fixed to default-user, so every engineer reads and writes one namespace; the key must come from the authenticated user
  • recall_memories matches a substring, so it misses paraphrases; a store with search, and a review of what gets saved, come before scale

Key Takeaways

  • Put every rule that must hold in code or in a tool: a read-only connection, a parameterised write, a pure router, a loop cap. Prompts ask; code enforces.
  • Test routing as a pure function on hand-built states, keep known issues as tests, and check side effects in the database, never in the agent’s wording.
  • Fan out with one state key per branch, join before you merge, keep writes out of parallel branches, and summarize old turns into state before the thread outgrows the context.
  • Bound a research team in code: tie every finding to its source, score each draft by its weakest criterion, and stop the quality loop at a fixed draft cap.
