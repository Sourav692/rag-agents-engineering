Open the lab

Lessons 37.1 to 37.3 follow the notebooks’ hotel support desk: a coordinator that talks to the guest, a compliance checker over four hotel rules, and a reservation agent over a SQLite database of eight rooms. Room 105, the Family Suite, is booked from today+30 to today+33, and the notebooks use it to show a clash. Lesson 37.4 and the interview questions move the same designs onto Larkspur Cloud, the fictional cloud host whose handbook runs through M10 to M12: its support desk, its refund and export policies, and a research team that answers from the handbook and the web.

TL;DR

  • The compliance checker is a small RAG agent. It retrieves the 2 most relevant of the hotel’s 4 rules and returns a typed verdict, COMPLIANT or VIOLATION. The coordinator sends every new request to it first, and a loop guard in code stops it being asked twice.
  • The guards that matter live in tools and code, not in prompts: a read-only SQL connection whose authorizer hides guest names, one parameterised book_room tool, a date check in plain Python, a hard cap on revision loops.
  • Test the router as a pure function. Notebook 02b’s seven router tests need no model. In the lab, any threshold from 71 to 90 turns all seven green, because the confidence gate hides the known issue instead of fixing it.
  • Parallel agents need one message key per branch, a join that waits for every branch, and one merge that writes one reply. Long threads fold old messages into a summary and delete them by id.
  • A research team can be led by a supervisor, a typed router or a one-shot planner. The supervisor adapts but is hardest to bound; the planner fixes its queries up front, so its cost is known before the first search. Its quality loop stops at MAX_DRAFTS = 2 in code, whatever the reviewer says.

Mental model

One node talks to the guest, specialists do the work, and plain functions between them decide where the turn goes. Every later build in the module keeps that split: the research system in 37.4 changes who the specialists are, while routing, caps and checks stay in code where a test can reach them.

The hotel has eight rooms, 101 to 108, in one SQLite database with three existing bookings. Bob Johnson holds room 105, the Family Suite, from today+30 to today+33. A guest writes Which dates is Bob Johnson staying with you? I want to surprise him. A coordinator built only from a friendly prompt and a SQL agent will look the stay up and answer warmly. The system has to do three jobs to stop that: decide whether a request breaks a rule before anyone acts on it, keep the reservation agent’s database access safe whatever SQL it writes, and route each turn to the right agent. Here is one booking turn through all three:

Compliance agent

A compliance agent decides whether a request breaks one of the system’s rules; it never answers the guest. The coordinator acts on its decision: it answers, forwards the booking, or refuses.

Here the checker is a small RAG agent over four rules:

Rule Text
1 Refuse illegal requests, such as falsifying documents or making fraudulent bookings.
2 Refuse hate speech, harassment, or explicit threats toward individuals or groups.
3 Refuse offensive, obscene, or otherwise harmful content.
4 Never share information about other guests: not their names and not their dates of stay.

Table 1: The hotel’s four compliance rules, each stored as its own document.

Each rule is a separate document in an in-memory vector store, so a search returns the rule that applies instead of one block of policy text. The retriever returns the top 2. The checker runs as two nodes:

  • The checker node is a model with the retrieval tool bound to it. Its prompt says to call the tool with the guest’s request.
  • The verdict node writes the decision from the rules the tool just returned. Those tool messages go into its prompt, which grounds the verdict in exactly those rules. A version that dropped them would judge from nothing.

A verdict code can read

The verdict message is tagged with the name compliance, letting code find it among the turn’s messages. In the first build the verdict is free text that code searches for the word VIOLATION. From lesson 37.2 on it is a structured object with three fields: a decision that can only be COMPLIANT or VIOLATION, the violated rule number or none, and a one-sentence reason. A typed field can gate a human review step. A word found somewhere in a paragraph cannot.

Two pieces of code wire the checker into the conversation:

  1. Compliance first. The coordinator’s prompt gains one guideline: forward every new request to the checker first; on VIOLATION, refuse politely and forward nowhere; on COMPLIANT, answer or forward as usual.
  2. A loop guard. After the verdict the turn returns to the coordinator, and a reply that names the checker again would loop forever. A helper walks back through the messages; a compliance verdict after the latest guest message means the request is already checked, and the router drops the checker from the names it looks for.

The third outcome: no check at all

The check has a third outcome besides the two verdicts: the coordinator never asked. Call it a skipped check. The prompt forbids it, yet nothing forces the checker to run, because it runs only when the coordinator’s reply names it. Lesson 37.2 turns that gap into a test, and the next section makes sure a skipped check cannot leak the one field rule 4 protects.

Guards in the tools

The reservation agent writes its own SQL. Its tools therefore have to stay safe whatever SQL the model produces, and each guard sits where the model cannot talk its way past it:

Guard Where it lives What it stops
Read-only file The connection opens the database file in read-only mode Writes through the query tool
Query-only flag The same connection Writes, a second time
An authorizer A callback SQLite consults while compiling each statement; only read actions pass ATTACH DATABASE (which would open any SQLite file on the machine), turning the query-only flag off, schema changes
A hidden column The authorizer tells SQLite to ignore reservations.guest_name Reading who booked a room: the column reads as NULL, and SELECT * still works
One write tool book_room(guest_name, room_number, start_date, end_date) with bound parameters SQL injection into the only write
Checks before the insert Inside book_room, after taking the write lock Missing name, unreadable or past dates, check-out before check-in, an unknown room, a clash with an existing stay

Table 2: Where each database guard lives and what it stops.

Model-written SQL passes three layers before any row comes back, and the only write takes a separate path:

Figure 2: The two paths into the database. Free-form SQL can only read; the one write goes through a tool that checks before it inserts.

Read-only flags alone do not stop ATTACH; the authorizer does. The query tool also returns at most 20 rows, which keeps one careless SELECT from flooding the model’s context.

Mention routing: the weak spot kept on purpose

Routing is the one place the build keeps a weak design deliberately. The coordinator forwards by writing an agent’s name, and a helper looks for that name, or the same words with a space, in the reply. Any reply that mentions an agent routes there. Call this mention routing:

Figure 3: Mention routing, the build’s router. It reads the words of the reply, whatever they say.

The fix is a typed router: the model returns its choice as a structured-output field, and there is no reply text to search. The research systems in lesson 37.4 route this way:

Key Takeaways

  • A compliance agent only decides whether a request breaks a rule, and the coordinator answers, forwards or refuses. Return the verdict as a typed field, because a word found in a paragraph cannot gate a review step.
  • Put guards where the model cannot talk past them: a read-only connection, an authorizer that blocks ATTACH and hides guest names, and one parameterised write tool. A prompt rule alone does not hold.
  • Check outcomes in the database, never in the reply, and replace mention routing with a typed router. Any reply that names an agent routes there, even a refusal.

System testing

System testing for agents means checking the decisions and the side effects, never the tone of the final message. The build catches failures at three levels, from cheapest to most realistic:

Level What it checks Model calls How the result is read
Router unit tests The routing rules, on 7 hand-built states None The route the pure router function returns
A confidence gate That an unclear request stops the turn instead of forwarding One per guest message A confidence integer in state, from structured output
A regression table 5 guest requests, end to end Every agent’s The nodes that ran and the database

Table 1: Three levels of tests, cheapest first.

The confidence gate

The confidence score comes from the coordinator itself. On each new guest message it asks the model for a self-assessment, a score from 0 to 100 and a one-line reason. The assessor’s prompt defines three bands:

  • 80 to 100: the intent is clear.
  • 50 to 79: the intent is clear but details are missing, such as a booking without dates.
  • 0 to 49: the model cannot tell what the guest wants.

Only the last band should stop the turn, which puts the threshold at 50. Below it the coordinator apologises and asks the guest to rephrase. The score is a heuristic, not a calibrated probability; its job is to trigger the “ask again” path.

What a threshold can hide

The interactive lab runs the same router and its seven tests in the page, ported from the shared hotel module, and recomputes them at every threshold. We ran the Python router at all 101 thresholds and got the same four bands:

Threshold Tests passing What changes
0 to 20 5 of 7 The confidence-20 reply clears the gate and forwards to the reservation agent
21 to 70 6 of 7 Only the known issue fails, as recorded
71 to 90 7 of 7 The known issue passes because the gate ends its turn before the name check runs
91 to 100 4 of 7 The gate blocks the three confident forwards, scored 90

Table 3: Router tests passing at each threshold, from the Python router and the lab.

All seven green at 75 is the wrong result. Mention routing is as fragile as at 50, and every guest whose booking lacks dates, which the assessor scores 50 to 79, now gets an apology instead of a question about the dates. Call this a gate that hides the bug: the suite passes because a different rule fires first.

Regression runs read from state

Booking, dates missing yes COMPLIANT no

The outcome comes from the final state, the nodes that ran and a row count on reservations, never from the reply text. Each failure names the field that broke. verdict: expected COMPLIANT, got None means the coordinator skipped the check; reservation: expected False, got True means it forwarded a booking without dates.

Model output varies between runs. A single failure is a lead, and the number to track is the pass rate over several runs after every prompt or model change. Tests show that something broke; the next section covers how the system recovers.

Edge cases and error paths

The build pushes on three edges of the core system and puts each safeguard in code:

  • Injection-style input. A guest hides ' OR '1'='1 in the room type. Pasted into a WHERE, the condition is true for every row: on a scratch copy of the hotel database, a Deluxe search widened that way returned all 8 rooms instead of 2. It can only widen a read, because the query tool refuses every write and the booking tool binds its values as parameters. The durable fixes are structural: a read-only connection and a narrow write tool.
  • A violation that should reach a person. A human review node pauses the graph with interrupt(): the graph saves a checkpoint and stops. The thread’s state shows which node waits, and resuming with the reviewer’s decision continues from that point. A resumed node runs again from its first line, so side effects such as writing to the review log go after the pause, where they run once. The checkpoint history replays the thread step by step for investigating a complaint.
  • Dates in the past. The model extracts the dates with structured output, given today’s date to resolve “next Friday”, and a plain function compares them with today. That check is testable without an API call.

Recovery by error type

Some failures do not fix themselves. A failing node catches its exception and writes a small record to an error field in state, with no message added. Routers read that field, so a guest who types the word “error” cannot trigger the error path. One error handler logs every failure with the thread id, and a pure decision router picks the recovery:

Retries for brief outages

Transient failures get a cheaper fix first: a retry policy re-runs a node that raises, without writing anything to the error field. It sits on the node itself:

Figure 3: A retry policy. It handles a failure that clears on its own, and gives up after a fixed number of attempts.

The build uses three attempts, a 0.2 s first wait and no jitter. We ran that policy on a tiny graph whose node fails a set number of times:

Compare the same flaky node with and without the build's retry policy.

No policy

  • The node raises once.
  • The exception ends the whole run.

1 attempt, the run crashes.

Policy, node fails twice

  • Waits 0.2 s, then 0.4 s, between attempts.
  • The third attempt succeeds and the guest never sees the outage.

3 attempts, the run completes.

Policy, node fails three times

  • The same two waits.
  • No attempts left after the third failure.

3 attempts, the exception reaches the caller.

A retry suits an outage that clears in under a second; the error path suits one that does not, or a failure that is not an outage at all, such as low confidence. Use both: retries on the node, and the error field for whatever the retries cannot fix.

Key Takeaways

  • Test at three levels: unit tests on the pure router with no model calls, a confidence gate that stops unclear turns, and an end-to-end regression table read from the nodes that ran and the database.
  • A threshold that turns every test green can still be wrong. At 75 all seven router tests pass, yet every booking that lacks dates gets an apology instead of a question about the dates.
  • Record failures in an error field in state and let a pure router pick the recovery, with a failed fallback raising a different error so it reaches a person. Keep retries for brief outages.

Memory merging

Memory merging is the work of bringing several agents’ outputs back into one state: the answers of parallel branches into one reply, and old turns into something smaller than the full transcript. The shape that works:

Figure 1: Fan-out to two hotel assistants, each with its own message key and tools, then a join and one merge.

Four wiring attempts

The build reaches that shape in steps, and each failure is a LangGraph rule. Its stub graphs need no model. We reran them offline with the notebook’s own cells; Hotel 1’s stub takes two tool rounds and Hotel 2’s one, as real agents rarely take the same number of steps.

The shared-key failure is the dangerous one. A tool node answers the latest tool call in its list, which may belong to the other branch. With the real SQL tools both hotels have a tool called run_query, and the wrong database answers without any error. Call it crossed tool results.

Two more choices keep the branches honest. Both assistants come from one factory, which binds each to its own hotel’s tools; copying the first assistant to make the second is how Hotel 2’s agent ends up reading Hotel 1’s database. And the branches cannot book. Both run the same request at the same time, and a booking tool in each would create two reservations. They report availability and prices; booking waits until the guest picks a hotel.

Merging by priority

The merge itself is an agent. It reads the guest’s request and each hotel’s final answer, listed in a fixed priority order (Hotel 1, then Hotel 2), and writes one reply under three rules:

  1. Recommend the first hotel that can help and offer the other as an alternative.
  2. Ignore a hotel that cannot help, unless none can.
  3. Keep room numbers, prices and dates exactly as the assistants gave them.

Only the merged reply enters the shared conversation; each branch’s tool calls stay in its own key. The two test turns:

Two ways to shrink the thread

Every turn now adds several agent messages to the thread. Something has to keep it small, and the two options differ in what they lose. Trimming, from M33, changes only what the model sees on one call:

Figure 2: Trimming. The thread keeps everything; old turns drop out of the model’s view.

Summarizing into state changes what the thread stores. A summarize node runs at the start of each turn when the stored conversation has more than 6 messages:

  1. It keeps the last guest turn word for word; everything before it is old. The cut is always at a guest message, so no tool call is separated from its result.
  2. It asks the model to fold the old messages into a running summary field, keeping every concrete fact: names, room types and numbers, prices, dates, what was offered and refused.
  3. It returns a removal marker for each old message id, and the message reducer deletes them.

Figure 3: Summarizing into state. Old turns become a summary, and the messages themselves are deleted.

The summary reaches the coordinator’s and assistants’ prompts as a system message, never the guest’s reply. The new graph continues the same thread because both graphs share one checkpointer.

Key Takeaways

  • Parallel branches need a reducer on any key they share, a separate message key per tool loop and a join that waits for every branch. Without the join, the merge runs once per branch.
  • Keep branches read-only when they run the same request at once, and merge their answers by a fixed priority. Check the merged reply against ground truth from the database, never the model’s claim.
  • Summarizing into state deletes old turns and keeps a running summary, at one model call when the thread passes its limit. Facts the summary leaves out are gone for good, where trimming only hides them.

Planner, supervisor or router

The three builds answer “who decides next” differently, and that choice sets how many model calls a request costs and what can go wrong.

A supervisor decides after every worker report. Its model returns a structured choice (researcher, coder or finish) that a pure function follows:

Figure 1: The supervisor. It sees each result and picks again, until it finishes or reaches the turn cap.

The supervisor is the most flexible and the hardest to bound. Its build proves the 6-turn cap with a stub supervisor that always picks the researcher. Its researcher also returns a validated market-data object, numbers only, and the coder sees just the user’s request and that object. No web text reaches the agent that runs code.

A typed router decides once per question:

Figure 2: The typed router. One structured-output field picks one specialist, then a summarizer writes the answer.

It is the fix for lesson 37.1’s mention routing: the choice is a field whose only values are web research, RAG or the plain model, and there is no reply text to search. Its RAG specialist answers only from chunks whose relevance score reaches 0.2, out of the top 3. When nothing clears that floor, it skips the model call and says so.

A one-shot planner decides once, up front, and never sees a result:

Figure 3: The one-shot planner. One Send per planned query, all in parallel, appending to one list.

It cannot adapt, but its cost is known before the first search runs.

Sequential and conditional workflows

A sequential workflow is plain add_edge calls: research, then draft, then review, for every input. Stages pass work through typed state fields (notes, draft, final), never through each other’s messages. Two different topics in notebook 05a both print the path research → draft → review; the content changes, the path cannot.

A conditional workflow adds a fork. The notebook splits the decision in two: a classifier agent with response_format=ToolStrategy(TicketRoute) returns a validated category, one of three Literal values, and route_ticket, plain code, maps it to a node listed in advance in add_conditional_edges. The agent can pick a branch; it cannot invent a fourth.

Figure 1: The conditional workflow. Exactly one dotted edge fires per run, so each ticket runs two nodes.

A branch condition can also be plain code. The notebook’s length gate counts the draft’s words and sends it to shorten only when it is over the limit: a 90-word draft takes research → draft → review at a limit of 150 and research → draft → shorten → review at 40.

The cost of a fixed fork is the input it did not plan for. TicketRoute holds one category: Priya’s message reaches billing or technical, never both. We call this the single-label drop: the reply is correct and answers half the request.

Supervisor with agents as tools

A supervisor is a create_agent agent whose tools are other agents. Notebook 05b wraps each specialist in a @tool that runs it and returns its last message as a string. A delegation is then an ordinary tool call and the answer comes back as a ToolMessage. Two details carry the design:

  • The tool’s docstring is the routing rule. “Ask the flight specialist about flights” is the only routing logic the supervisor reads.
  • The specialist sees only the request the supervisor writes. This context isolation keeps each specialist’s prompt short, but the supervisor must pass every detail: cities, budget, or for Priya, plan type, purchase date and traffic.

Figure 2: Supervisor with agents as tools. Control returns to the supervisor after every specialist.

The notebook’s three requests call both specialists, only the hotel agent, or none. No branch function decided that; the supervisor’s tool calls did. The cap is recursion_limit in the run config. We replayed the supervisor with a scripted model: answering with no specialist needs a limit of 2, and one round of delegation runs three node steps (model, tools, model) and needs a limit of 4. The notebook’s recursion_limit=2 therefore stops the full-trip request with GraphRecursionError.

Parallel fan-out and fan-in

When the pieces of work do not need each other, run them at the same time. Notebook 05c sends one product idea to three analysts: three edges leave START, and add_edge([...three analysts...], "product_lead") is a join that runs the lead once, after all three. Our replay of its graph with stubbed agents puts all three analysts in super-step 1 and the lead in super-step 2.

Figure 3: Fan-out and fan-in. Workers share a super-step; the lead runs once after every worker.

Parallel writes to one field need a reducer. With Annotated[list, operator.add] the two writes concatenate; without one, LangGraph raises InvalidUpdateError: At key 'results': Can receive only one value per step. The notebook proves this with two plain functions and no model.

When the number of workers depends on the input, a fan-out function returns one Send("summarize", payload) per item: five reviews start five summarize tasks, two start two, and the graph does not change. Parallelism saves wall-clock time, roughly the slowest worker plus the lead. It does not save model calls: every worker pays for its own, even on a request that needed only one of them.

Handoffs

In a handoff, the agent holding the conversation passes it on, and the receiver keeps it. Notebook 05e uses langgraph-swarm: create_handoff_tool(agent_name="billing_agent") builds a transfer_to_billing_agent tool that returns Command(goto=..., graph=Command.PARENT) and sets active_agent, and create_swarm(..., default_active_agent="triage_agent") routes every new message to whoever is active.

Figure 5: Handoffs in a swarm. The receiver becomes the active agent, and a checkpointer remembers it.

Compiled with InMemorySaver, the swarm saves active_agent per thread. We replayed the notebook’s three-turn script with a scripted model: turn 1 runs triage then billing, turn 2 starts at billing with no triage, and turn 3 hands off sideways to tech. Unlike the supervisor’s tool call, a handoff forwards the whole conversation: billing never asks for the invoice number again.

No node in a swarm can say stop. If agents keep transferring to each other, only recursion_limit ends it: the notebook’s scripted triage, billing, tech cycle raises GraphRecursionError after 10 handoffs at a limit of 10. We call this the handoff ping-pong.

Choosing a pattern

Start with the most fixed pattern that covers the task, and move control toward a model only when the steps cannot be listed in advance:

  • Workflow when the stages and branches are known before the run. For Priya’s desk, let the classifier return a list of categories and fan out over it, which fixes the single-label drop without giving up a fixed graph.
  • Supervisor when a request may need any subset of specialists, and one place should write the answer.
  • Fan-out when the work is independent and the merge rule is clear. Use Send when the worker count follows the input.
  • Generator–critic when “done” can be written down and feedback can improve a draft. Put every rule code can check in code.
  • Handoffs when a specialist should own the rest of the conversation, as in support triage.

The patterns combine: lesson 37.4’s research team is a supervisor whose workers fan out and whose report passes a capped review loop. Give each model-driven choice a cap in code.

Limits of this evidence

  • No notebook run is recorded. Notebooks ship without outputs. Paths, steps, reducer errors, loop exits, active agents and handoff counts come from replaying the notebooks’ own graph code with stubbed agents or a scripted model (langgraph 1.2.18, langchain 1.4.7, langgraph-swarm 0.1.0). What gpt-4o-mini writes, and whether it calls the right specialists, is not measured.
  • Priya’s request is scripted. Its call counts follow each graph with one tool call per specialist; a live run can make more.
  • The examples are small. Two or three specialists over in-memory data; production versions add retries, timeouts and tracing.

Key Takeaways

  • The five patterns differ in who picks the next step: the graph, a supervisor’s tool calls, a join, a rule reading a critic’s verdict, or the agent holding the conversation.
  • Each has a typical failure: the single-label drop, a supervisor request missing the facts a specialist needs, fan-out paying every worker, an uncapped loop, and handoff ping-pong.
  • Prefer the most fixed pattern that fits, check in code whatever code can check, and cap every model-driven choice: recursion_limit stopped the scripted handoff cycle after 10 handoffs and the stuck generator after 3 drafts.

Check yourself

1. What is the difference between a supervisor calling a specialist as a tool and an agent handing off to a specialist?

After a tool call, control returns to the supervisor, and the specialist saw only the request the supervisor wrote. After a handoff, the specialist becomes the active agent, sees the whole conversation and receives the user’s next message. A checkpointer is what keeps active_agent between turns.

2. Priya asks for a refund and an export in one message, and the ticket router answers only the refund. Why, and what is the smallest fix?

TicketRoute holds one Literal category, so the conditional edge fires exactly one branch: the single-label drop. Let the classifier return a list of categories and fan out to one specialist per category, joining their answers in one reply. The graph stays fixed, and the second question gets an answer.

3. A generator–critic loop sometimes runs forever on hard tasks. Which part of the notebook's design prevents that, and what does a capped run return?

should_continue is plain code with a stop exit at MAX_REVISIONS = 3, so the loop ends even if the critic never approves; the stuck-generator proof stops after three drafts. A capped run returns the last draft, which was never approved, so the caller should treat it as unapproved.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s support desk is built like the hotel system: a coordinator, a compliance checker over account-privacy rules, and a billing agent. A customer asked for the billing email of another company’s account and got it. The trace shows the compliance checker never ran. How do you find out why, and how do you stop it happening again?

What a strong answer covers:

  • Reads the node path for that turn (stream_mode="updates"), then the coordinator’s reply: the checker runs only when the reply names it, which the prompt asks for and nothing forces
  • Makes the check structural: an unconditional edge from the guest message to the checker, instead of routing by mention
  • Enforces privacy in the tool as well, the way the hotel’s authorizer makes guest_name read as NULL, so a skipped check cannot leak the field
  • Adds the request to the regression table and tracks its pass rate over several runs, since one green run proves little

2. The coordinator forwards to the billing agent whenever its reply contains billing_agent or “billing agent”. A reply saying “I can’t involve the billing agent until you confirm the refund date” forwarded anyway. A teammate proposes raising the confidence threshold from 50 to 80. What do you say?

What a strong answer covers:

  • The threshold does not touch the cause, string matching on reply text; in the router lab, thresholds from 71 to 90 turn the known-issue test green by ending the turn early, not by routing correctly
  • It also costs real traffic: the assessor scores a request with missing details at 50 to 79, so those customers get “please repeat” instead of a question about the missing detail
  • The fix is a typed router: structured output with a Literal route, read by a pure function, as in notebook 04b
  • Keeps the known-issue test, which flips to passing when the fix lands, and unit-tests the router on hand-built states with no model

3. Larkspur runs a research team for its support engineers: a planner, three parallel searchers, a writer and a quality checker with a two-draft cap. How do you know it is still working, and what it costs, a month after launch?

What a strong answer covers:

  • Logs per run the number of search agents against planned queries, the number of drafts, and whether the run ended approved or stopped by the cap
  • Watches the share of runs stopped by the cap: a rise means the writer or the sources got worse, since the cap hides quality problems from the user
  • Tracks the share of findings whose URL was one the search returned (url_verified), the early sign of invented sources
  • Reports cost and latency per run, which scale with queries times results and with drafts, and re-runs a fixed set of handbook questions after every prompt or model change

4. To speed up refunds, Larkspur splits billing into two parallel agents, one per region, both with a refund tool. A customer was refunded twice. What went wrong, and how do you design it?

What a strong answer covers:

  • Parallel branches run the same request at the same time, so any write tool in both branches can fire twice
  • Gives the branches read-only tools and makes the one write after a single choice, as the hotel’s branches report availability but cannot book
  • Adds an idempotency key to the refund tool so a retry or a duplicate call cannot pay twice
  • Checks the wiring: one message key per branch, sync nodes and a join so the merge runs once, and a test that counts merge runs and rows written

5. You ship a deep agent to Larkspur’s support engineers, built like the long-term memory agent of lesson 26.3 (now taught in M26). Someone sets USE_SANDBOX=true expecting cloud isolation, and the memory panel shows one engineer’s notes in another’s session. What is wrong?

What a strong answer covers:

  • The script’s comment promises a LangSmith sandbox, but the flag selects LocalShellBackend, which runs shell commands on the host with no isolation
  • FilesystemBackend(virtual_mode=True) blocks path traversal; it is not a sandbox either, so code execution needs a real sandbox backend and approval on execute (interrupt_on)
  • Long-term memory is keyed by CURRENT_USER_ID, fixed to default-user, so every engineer reads and writes one namespace; the key must come from the authenticated user
  • recall_memories matches a substring, so it misses paraphrases; a store with search, and a review of what gets saved, come before scale

Key Takeaways

  • Put every rule that must hold in code or in a tool: a read-only connection, a parameterised write, a pure router, a loop cap. Prompts ask; code enforces.
  • Test routing as a pure function on hand-built states, keep known issues as tests, and check side effects in the database, never in the agent’s wording.
  • Fan out with one state key per branch, join before you merge, keep writes out of parallel branches, and summarize old turns into state before the thread outgrows the context.
  • Bound a research team in code: tie every finding to its source, score each draft by its weakest criterion, and stop the quality loop at a fixed draft cap.
