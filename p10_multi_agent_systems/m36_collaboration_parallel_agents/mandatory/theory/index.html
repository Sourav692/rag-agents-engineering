Parallel sub-question agents
Open the lab

The running example is the Larkspur Cloud handbook from M10 to M12. One compound support question carries the parallel lessons and the lab: “I’m cancelling my annual plan after this week’s outages. Can I get a full refund, how long will it take, can I still export my data, and do I get credits for the outages?” It splits into four sub-questions whose evidence is the handbook’s refund-window, refund-timing, export and retention, and SLA chunks. The blackboard lesson uses an outage escalation from the same handbook; debate and STORM use a decision and an article about it.

TL;DR

  • A blackboard is one shared list that every specialist reads and appends to. A controller re-reads it after every contribution and picks the next specialist, so it can skip a branch that a fixed pipeline always runs. Guard it with a typed decision and a call cap (the notebook stops at 6 specialist calls, with a recursion limit of 20 behind it).
  • Debate gives two agents opposite sides and a judge who reasons past both. It costs 2N + 1 calls for N rounds (7 at N = 3), so keep it for trade-offs; a factual question is better answered in one call.
  • STORM researches from several perspectives before it writes: personas, simulated interviews, one merged outline, one draft per section. Its cost is countable: 1 + P × (2T + 1) + 1 + S + 1 calls, 22 to 24 in the notebook.
  • LangGraph runs parallel branches in supersteps: every node of a step runs at once and the next step starts when the slowest one ends. In the lab, the four sub-questions take 5.7 s one at a time, 3.4 s in parallel, and 2.7 s once the outage rewrite moves inside its agent node.
  • Parallel branches need a join that waits (a list edge or defer=True) and a reducer on every key they share; without them the synthesizer answers from half the evidence, or the run raises InvalidUpdateError.

Mental model

The patterns differ in who decides what runs next and when that decision is made. A pipeline and STORM fix the order when you build the graph. A fan-out fixes the shape but lets the branches overlap in time. A blackboard leaves the order to a controller at run time, which buys flexibility and costs a model call per step. All four write to one shared state, so all four need the same guards: typed decisions, reducers on shared keys and a cap on the number of steps.

Blackboard

Lesson 36.1: Blackboard architectures. Notebooks: 01a_blackboard_intro.ipynb, 01b_blackboard_research_team.ipynb (optional)

What you’ll learn

  • Explain how a blackboard coordinates specialists through one shared store, with a controller as the only part that decides order.
  • Compare a blackboard controller with a fixed pipeline on a request whose next step depends on an earlier finding.
  • Diagnose the ways an LLM controller goes wrong: an invalid name, an impossible step, a loop that never finishes.
  • Choose between a blackboard, a pipeline and a fan-out by asking when the order of work is known.

M35 built supervisors and handoffs, where one agent passes control to the next. This module adds shared state: several specialists contribute to one record, and something decides who goes next.

Larkspur’s support team gets an escalation: a customer says their server went down twice this week. If the outages pushed availability below the 99.95% SLA, draft a service-credit reply, otherwise draft a reply that points to the status page and the root-cause report. A fixed pipeline of analysts would run the credits analyst and the status analyst on every escalation, because its edges cannot skip a node. Half that work is wasted on each request, and the writer has to ignore one of the two reports.

A blackboard system coordinates specialists through one shared store, the blackboard. Specialists never call each other. Each one reads the board, does its own job and appends its result. A controller reads the whole board after every contribution and picks the next specialist, or FINISH:

Figure 1: The blackboard loop. Every specialist turn sits between two controller turns.

The design comes from the HEARSAY-II speech-recognition system (Erman et al., 1980). In HEARSAY-II the specialists watched the board for their own trigger conditions and a scheduler chose among them. In the reference implementations the controller does all the watching.

The controller is the only part that decides order. The specialists stay narrow, and adding one means adding a node and a name the controller may choose. Nothing else is rewired.

Branching on what the board says

The intro notebook gives both designs one request with an either/or condition: find the latest news about a company, then run a technical analysis if the news is neutral or positive, or a financial analysis if it is negative. Here are both graphs, one row per design:

Design Order of work Branches that run
Fixed pipeline news, technical, financial, writer Both, on every request
Blackboard controller, news, controller, one analyst, controller, writer, controller One, chosen after the news post lands

Table 1: The same conditional request through both designs. The pipeline’s edges fix its order before the run starts.

The notebook does not ask another model whether the instruction was followed. It computes two checks from steps, the list of specialists that ran:

Check, computed from steps Sequential pipeline Blackboard
Followed the either/or Never: both branches run by construction Whatever this run’s controller chose
Correct branch for the sentiment Never: both branches run Checked against a sentiment label from the news post

Table 2: The code-computed comparison. The pipeline fails by structure, the blackboard can fail by judgment.

The blackboard row can fail too, because the controller is an LLM. A run where it calls both analysts, or the wrong one, shows up as a failed check instead of a plausible report. That is why the check runs on every run rather than once.

On the Larkspur escalation the same shape plays out with three specialists. An incident analyst posts what the incident log shows. The controller reads that post and calls either the credits analyst or the status analyst. A writer drafts the reply from the board.

Guarding an LLM controller

A controller that re-decides at every step can also loop, stall or name a step that cannot run yet. We name the three failures and reuse the names:

  • Phantom route: the controller names a specialist that does not exist.
  • Premature step: it names a real specialist whose input is not on the board yet, such as a writer with no findings.
  • Runaway controller: it keeps choosing specialists and never returns FINISH.

The reference implementations guard each one in code. The planted cases below come from the research-team notebook, which feeds hand-written boards to its pure guard functions with no model call. All six checks pass:

Planted case What the guard returned Guard
Fact-Checker chosen on an empty board Refused: there is no finding to check Precondition
Outline-Writer chosen with 1 verified finding Refused: fewer than 2 verified findings Precondition
FINISH chosen with no draft Refused: there is no draft yet Precondition
A flagged finding followed by its revision Only the revision counts as verified Structured posts
Fallback after an unchecked finding Fact-Checker Rule-based next step
Fallback after a needs_revision verdict Researcher Rule-based next step

Table 3: Guard checks on hand-written blackboards, from a scratch run of the research-team notebook’s pure functions.

Four guards cover the three failures:

  • A typed decision stops the phantom route. The decision field is a Literal of the specialist names plus FINISH, so the model can only name a real node. The node writes the decision to state, and a separate, pure routing function reads it.
  • Preconditions checked in code stop the premature step. In the research-team implementation, precondition_problem() rejects impossible choices and rule_based_next() substitutes the rule-based choice. Every override is printed and counted.
  • A cap in code stops the runaway controller. The intro notebook’s controller returns FINISH without calling the model once MAX_SPECIALIST_CALLS = 6 specialists have run (the research team allows 12 contributions). LangGraph’s recursion_limit (20 in the intro, 40 in the research team) is only the backstop: it ends the run with an error rather than a clean stop.
  • Structured contributions let code read the board. Posts in the research team are records with agent, type and content. Code can then tell a finding from a fact-check from a draft, and pair each finding with its own verdict.

Specialists that search must execute their tool. The intro notebook runs each analyst as a small create_agent loop. Binding a tool to the model alone only lets the model request a search, and nothing runs it.

Pitfall: an ungrounded fact-check. The research team’s Researcher and Fact-Checker have no search tool. The Fact-Checker judges clarity and internal consistency, and a fluent but wrong finding can still come out verified. Give the Researcher sources and have the Fact-Checker compare claims against them before trusting the label.

What the controller costs

Every specialist turn sits between two controller turns. A run with k specialists makes up to k + 1 controller calls on top of the specialists’ own. For the Larkspur escalation that looks like this:

Run Specialist calls Controller model calls
Incident analyst, credits analyst, writer 3 4
Pipeline running both analysts 4 0
Intro notebook at its cap 6 6 (the seventh decision is made in code)

Table 4: Calls per run, counting each specialist as one call even when its own tool loop makes more. The first two rows are illustrative.

The blackboard saves a specialist and pays for it in controller calls. That trade pays when the skipped specialist is expensive, such as a search loop, or when its output would mislead the writer.

Traces are harder to read than a pipeline’s, because the path changes from run to run. In the research-team implementation a fact-check that flags a finding sends the controller back to the Researcher, a loop-back no edge in the graph spells out. The notebook counts loop-backs and overrides from the final board. A run with zero loop-backs is valid: every finding passed its first check.

Choosing a coordination shape

The deciding question is when the next step becomes known:

Figure 2: A blackboard earns its controller calls only when the order depends on what earlier steps find.

Fixed pipeline Fan-out Blackboard
Who decides order The graph’s edges The graph’s edges An LLM controller, every turn
Can skip a branch ✗ ✗ ✓
Extra model calls None None Up to k + 1
Same path every run ✓ ✓ ✗
Main risk Wasted branches Joins and shared keys Runaway or wrong choices

Table 5: Three coordination shapes for several specialists.

Use a blackboard for diagnosis, triage and research with verification. When the order is known before the run starts, a pipeline or a fan-out (lesson 36.5) is cheaper and easier to test.

In practice: Larkspur’s outage escalation

  1. Board: the request and the customer’s account go on the board as the first post.
  2. Incident analyst posts what the status page probes recorded for the customer’s region this month, with the month’s availability.
  3. Controller reads that post. Below 99.95% it calls the credits analyst, which posts the credit owed (10% of the month’s server charges in that region, 25% below 99.0%) and the rule that credits are claimed with a Billing ticket within 30 days. At or above 99.95% it calls the status analyst, which posts the status-page link and the 72-hour root-cause report.
  4. Writer drafts from the board, and the controller returns FINISH once a draft exists.
  5. Checks in code: exactly one of the two analysts ran, it matches the availability figure, and the run stayed under the call cap.

Lesson 36.2 swaps cooperation for disagreement: two agents argue opposite sides and a judge weighs them.

Key Takeaways

  • A blackboard coordinates specialists through one shared store, and only the controller decides order. It can pick one branch from what earlier posts found, where a fixed pipeline runs every branch by construction.
  • Guard the controller in code: a typed Literal choice against phantom routes, precondition checks against premature steps, and a specialist-call cap against a runaway controller. recursion_limit is only the backstop, because it ends the run with an error.
  • A run with k specialists makes up to k + 1 controller calls, and its path changes from run to run. When the order is known before the run, a pipeline or fan-out is cheaper and easier to test.

Check yourself

1. A request asks for a technical or a financial analysis depending on the news sentiment. Why does the fixed pipeline never follow it, while the blackboard can?

The pipeline’s edges cannot skip a node, so news, technical, financial and writer run on every request and both analyses always happen. The blackboard controller reads the news analyst’s post and then picks one branch. It can still choose wrong, because it is an LLM, and the implementation computes the check from steps on every run.

2. In the Larkspur outage escalation, the incident analyst posts that availability stayed above the 99.95% SLA. Which specialists should run next?

The controller should call the status analyst, not the credits analyst, and then the writer drafts a reply that points to the status page and the root-cause report. That run makes three specialist calls and four controller calls. A fixed pipeline would pay for both analysts on every escalation.

3. A blackboard controller keeps picking specialists and never returns FINISH. What in the implementations stops the run, and why is that better than relying on recursion_limit?

A cap in code: once MAX_SPECIALIST_CALLS = 6 specialists have run, the controller returns FINISH without calling the model, and the run ends with a reply. recursion_limit = 20 is only the backstop, and it ends the run with an error rather than a clean stop.

Debate

Lesson 36.2: Debate. Notebooks: 02a_debate.ipynb (optional)

What you’ll learn

  • Explain the debate loop: two fixed sides, a round counter and a judge with a structured verdict.
  • Compare the debate this lesson builds with the other research setup that shares its name.
  • Diagnose a debate that adds nothing: parallel monologues, a lopsided persona, a biased judge.
  • Choose between debate, a single call and retrieval by asking whether the question has one correct answer.

Lesson 36.1’s specialists cooperated on one board. Here two agents disagree on purpose, and the reader of the result sees the strongest case for each side before a decision.

Larkspur’s product team asks the support assistant: should we stop retrieving and put the whole handbook in a long-context prompt? One model call returns a tidy recommendation. It may be right, but it shows one framing of a question with real costs on both sides: cost per call, accuracy on facts buried mid-context, and access control (the fifth interview question on the M10 module page). The team wants the counter-case argued properly before it commits.

In a debate two agents argue opposite sides of a question over several rounds. Each reads the whole transcript and rebuts the other’s latest point. A neutral judge then writes the verdict:

Figure 1: The round-robin debate graph. Only the two sides and the judge call a model.

Two research setups share the name:

  • MAD (Liang et al., EMNLP 2024): fixed affirmative and negative sides, and a judge that reads the debate and extracts the answer. MAD’s judge may also end the debate early. The notebook follows MAD but always runs every round.
  • Multiagent debate (Du et al., 2023): every agent gets the same prompt, answers on its own, then reads the others’ answers and revises until they converge. There are no assigned sides and no judge.

The notebook’s own question is a classic trade-off: should a six-person team building a new B2B SaaS product start with microservices or a monolith.

A bounded round-robin

The control flow is a small graph with one counter in state. After side B speaks, an advance_round node adds one to the counter, and a routing function sends the graph back to side A or on to the judge. That function is plain Python, and the notebook checks it without a model call. A scratch run of that check gives:

After round Counter now Route
1 2 Side A
2 3 Side A
3 4 Judge

Table 1: The routing check with MAX_ROUNDS = 3, run in the scratchpad. Three rounds, then the judge.

A counter in code bounds the debate. No agent decides when to stop, so the loop cannot run away the way a blackboard controller can.

What makes a debate worth reading

Three rules carry the pattern. Each one guards against a named failure:

  • Sides that engage. Each persona argues its side without inventing facts. After its opening turn it must rebut the opponent’s strongest recent point before adding one or two of its own, in at most 120 words in this configuration. Without that rule the debate turns into parallel monologues: two cases stated side by side, and nothing for the judge to weigh.
  • A judge that reasons past the debate. The judge fills a DebateVerdict: the strongest point from each side, the weak or overstated claims, a final recommendation and a confidence. Its prompt asks it not to name a winner. The recommendation may be conditional, such as “start with a monolith, split out services when a named pressure appears”.
  • A baseline beside it. The notebook asks the same question in one call with a neutral prompt and prints both answers. A capable model often hedges on its own, and then the debate adds little.

Three weaknesses remain, and the rules above only reduce them:

Planted weakness What happens Why
Shared blind spot Neither side raises a consideration Neither persona was primed to look for it
Lopsided debate One side wins every exchange Its persona prompt is stronger than the other’s
Biased judge The verdict leans one way regardless of the transcript The judge is one model call and a single point of bias

Table 2: Failures the debate pattern does not remove, from the notebook’s own analysis.

Pitfall: treating the verdict as ground truth. A judged recommendation is an argued opinion. When both sides miss a consideration, the judge cannot weigh it.

Counting the calls

Each round costs two debater turns, and the judge adds one call at the end:

Approach LLM calls What you get
Single call 1 One answer, often already balanced
Debate, N rounds 2N + 1 A transcript, the strongest point from each side, a judged recommendation
Debate, N = 3 (this configuration) 7 Six turns and one verdict

Table 3: The cost of a debate against a single call. The advance_round node makes no model call.

Latency grows with the calls too, because every turn waits for the one before it. The deliverable is the auditable trail: what each side said, what the judge found strongest and what it rejected.

Choosing when to debate

Debate earns its cost on questions with legitimate trade-offs and no single correct answer, such as architecture choices, build or buy, and policy. For a factual question with one correct answer, the single call or retrieval is the better choice:

Figure 2: Route facts to retrieval or one call, and keep debate for trade-offs.

On the Larkspur handbook that line is clear. “How long does a refund take?” has one answer, 5 to 10 business days, and belongs to retrieval. “Should the support assistant stop retrieving and use a long-context prompt?” is a trade-off, and a transcript with a judged verdict is a useful input to that decision.

A third case looks like a debate and is not one. When two retrieved chunks disagree, for example an old and a new refund policy, one of them is out of date. Fix the index first with version metadata and a filter (M11) rather than asking two agents to argue about which one is current.

In practice: the long-context question

  1. Frame the question as a trade-off with two sides: keep retrieval, or move the whole handbook into the prompt.
  2. Write two personas of equal strength, each told to argue honestly and to rebut before adding a point.
  3. Run three rounds: six turns and one judge call, seven calls in all.
  4. Run the single-call baseline and read both answers side by side. Look for what the judge adds: named conditions, a staged path, or a counter-argument the single answer never raised.
  5. List what neither side raised before treating the verdict as a decision.

Lesson 36.3 keeps several perspectives but makes them cooperate: STORM uses them to research an article instead of arguing.

Key Takeaways

  • A debate runs two opposing sides over N rounds, each rebutting the other’s latest point, then a judge fills a structured verdict. It costs 2N + 1 calls, 7 at three rounds, against 1 for a single call.
  • Require each side to rebut before adding its own points, or the debate becomes parallel monologues. Ask the judge for the strongest point from each side and a recommendation rather than a winner.
  • Debate questions with real trade-offs, such as build or buy. Send factual questions like the refund time to retrieval, and fix disagreeing chunks in the index with version metadata.

Check yourself

1. Why must each debater rebut the opponent's strongest recent point before adding one or two of its own?

Without the rebuttal rule the debate turns into parallel monologues, and the judge has nothing to weigh. Engagement is what lets the judge’s verdict name the strongest point from each side and the weak or overstated claims.

2. How many LLM calls does the three-round debate cost against a single call, and what do the extra calls buy?

2N + 1 calls, which is 7 for N = 3 (six turns and one verdict), against 1. They buy a transcript, the strongest point from each side and a judged recommendation. A capable model often hedges on its own, and the single call is the baseline to compare against.

3. Two retrieved Larkspur chunks give an old and a new refund policy. Should two agents debate which one is current?

No. Fix the index first with version metadata and a filter (M11). Debate earns its cost on trade-offs with no single correct answer. A factual question such as how long a refund takes (5 to 10 business days) belongs to retrieval.

STORM

Lesson 36.3: STORM: multi-perspective research and writing. Notebooks: 03a_storm.ipynb

What you’ll learn

  • Explain STORM’s four stages and why each one consumes the previous stage’s typed output.
  • Diagnose the two steps that decide article quality: persona design and outline synthesis.
  • Calculate a run’s model calls from its parameters before it starts, and its latency once the interviews run in parallel.
  • Identify where retrieval has to plug in before the article’s facts can be trusted.

Lesson 36.2 used two perspectives to argue toward a decision. STORM uses several perspectives that cooperate, to research a topic before anyone writes about it.

Larkspur’s documentation team wants a help-centre article on what happens to an account when a customer cancels. A single “write an article about cancelling” prompt returns fluent, generic prose from one angle. It mentions refunds in a sentence, skips the 30-day data-retention window entirely, and no one can tell which claim came from where.

STORM (Synthesis of Topic Outlines through Retrieval and Multi-perspective question asking; Shao et al., NAACL 2024, arXiv:2402.14207) writes a long article on a topic the writer knows little about. It researches first, from several perspectives, and writes only from what the research found:

Figure 1: STORM’s pipeline. Each arrow carries a typed object, not free text.

  1. Perspective generation. One structured-output call proposes P distinct editor personas, each a different professional lens on the topic.
  2. Simulated interviews. For each persona, a persona-editor asks one focused question at a time and an expert answers, for T turns. Both roles are the same model with different system prompts. A third call extracts the transcript’s facts into a typed list.
  3. Outline synthesis. An editor-in-chief call merges every persona’s facts into one ordered outline of 4 to 6 sections.
  4. Section drafting. A writer call drafts each section from the research notes. A last call writes the title.

The notebook runs this on the impact of remote work on urban commercial real estate, with three perspectives and two interview turns each.

Typed findings, not transcripts

Each stage hands the next one a typed object produced with structured output, and no stage parses free text:

Stage Consumes Produces
Perspective generation The topic PerspectiveList: persona and focus for each editor
Interview and extraction One persona A transcript, and ResearchFindings: a list of facts
Outline synthesis Every persona’s facts ArticleOutline: ordered sections, each with a scope
Section drafting One section and the facts Prose for that section

Table 1: What travels between STORM’s stages in the notebook.

Only the extracted facts travel into the outline and the drafts. The transcripts stay behind for audit, and you can trace which question surfaced which fact. Two steps decide quality, and each has a named failure:

  • Echo panel. Three reworded generalists produce redundant research. If the personas overlap, tighten the perspective prompt, for example by listing the disciplines to draw from.
  • Stapled outline. Outline synthesis is where P research threads become one narrative. An outline with one section per persona is a concatenation, and the synthesis prompt needs to ask for a merged structure.

A good outline reads as one article’s table of contents, moving from background through each stakeholder’s stake to an outlook. A stapled one reads as three reports in a row.

The missing retrieval boundary

The notebook’s expert is the model playing a knowledgeable role, with no retrieval. Its prompt asks it to label a guess as an estimate, but its “facts” are still only as reliable as the model’s memory. We call this the memory expert, and it is the pattern’s main weakness. The original STORM retrieves from the web at this step. The notebook swaps that out to keep the run self-contained.

Swapping the expert’s plain call for a tool-using agent grounds it without changing any later stage. On the Larkspur handbook the expert would answer from a handbook retriever. For the cancellation article, each persona would surface its own facts with the chunk they came from:

Persona Question it asks Fact it should surface Handbook chunk
Billing editor Can an annual plan be refunded on cancellation? Full refund within 30 days of purchase if outbound traffic stayed under 100 GB Refunds
Billing editor How long does the money take? 5 to 10 business days to the original payment method Refunds
Data editor What happens to the data? Kept for 30 days after cancellation, then permanently deleted Data export and retention

Table 2: What a grounded expert would return for the cancellation article. Illustrative questions, facts from the Larkspur handbook.

Interview tip: when asked how to make STORM trustworthy, name the step. The interview’s expert is the only place facts enter the pipeline, and it is where retrieval and citations go.

Budgeting a STORM run

The cost is fixed by the parameters before the run starts: one call for the perspectives, 2T + 1 per interview (T questions, T answers, one extraction), one for the outline, one per section and one for the title. In total the run makes 1 + P × (2T + 1) + 1 + S + 1 calls:

Perspectives P Turns T Calls With S = 4 to 6 sections
3 2 18 + S 22 to 24 (this configuration)
3 3 24 + S 28 to 30
5 2 28 + S 32 to 34
5 3 38 + S 42 to 44

Table 3: Model calls per STORM run, from the formula.

The notebook attaches a callback that counts every chat-model call, structured-output calls included, and compares the count with this arithmetic. Two caps keep the cost bounded when the model returns more than it was asked for: the perspective list is cut to P, and the outline to MAX_SECTIONS = 6.

Latency is a different number from cost. The interviews are independent of each other, but the notebook runs them in a Python loop, and their waits add up. Dispatching one branch per persona with Send (lesson 36.5’s map-reduce) puts them in one superstep. The section drafts are independent in the same way. Counting the calls that must wait for one another:

Stage Calls in sequence, as written Calls in sequence, with Send
Perspectives 1 1
Interviews (P = 3, T = 2) 15 5
Outline 1 1
Sections (S = 5) 5 1
Title 1 1
Total 23 9

Table 4: The longest chain of dependent calls in one run, assuming every call takes about the same time (illustrative).

The same 23 calls are made either way, and the bill does not change. The reader waits for 9 calls in a row instead of 23.

In practice: the cancellation article

  1. Perspectives: ask for three personas and name the disciplines (billing, data handling, account security) to avoid an echo panel.
  2. Interviews: give the expert the handbook retriever, and keep each fact’s chunk id with it in ResearchFindings.
  3. Outline: ask for one merged structure, such as before you cancel, the refund, your data, closing the account, rather than one section per persona.
  4. Drafts: write each section from the facts with their chunk ids, and dispatch the sections in parallel.
  5. Check: compare the callback’s call count with the formula, and spot-check one sentence per section against its source chunk.

Lesson 36.4 moves from fixed pipelines like this one to controllers that choose which specialist, or which whole architecture, handles a request.

Key Takeaways

  • STORM researches before it writes. P personas each run a T-turn interview, their extracted facts merge into one outline, and each section is drafted from what the research found.
  • Quality rests on distinct personas and an outline that merges the research threads. An echo panel repeats itself, a stapled outline is a concatenation, and a memory expert is only as reliable as the model’s memory.
  • Cost is fixed before the run at 1 + P × (2T + 1) + 1 + S + 1 calls, 22 to 24 in the recorded configuration. Dispatch the interviews and sections with Send to cut the chain of dependent calls without changing the bill.

Check yourself

1. In STORM, why do only the extracted facts travel into the outline and the drafts, while the interview transcripts stay behind?

Each stage consumes the previous stage’s typed object (PerspectiveList, ResearchFindings, ArticleOutline), and no stage parses free text. The facts list is the payload. The transcripts are kept for audit, so you can trace which question surfaced which fact.

2. How many model calls does a STORM run make with 5 perspectives, 2 interview turns and 5 sections?

33 calls: 1 for the perspectives, 5 × (2 × 2 + 1) = 25 for the interviews, 1 for the outline, 5 for the sections and 1 for the title. The table’s row for P = 5 and T = 2 gives 28 + S, which is 33 at S = 5.

3. A STORM outline comes back with exactly one section per persona. What has gone wrong, and where do you fix it?

The outline is stapled: a concatenation of the research threads, not a synthesis. Outline synthesis is where P threads become one narrative, and the fix is the editor-in-chief’s synthesis prompt, which must ask for a merged structure. If the sections also repeat each other, the personas overlap, and the perspective prompt needs tightening.

Three kinds of controller

Lesson 36.4: Meta-controllers, ensembles and emergent systems. Notebooks: 04a_meta_controller.ipynb (optional), 04b_ensemble_parallel_exploration.ipynb (optional), 04c_cellular_automata.ipynb (optional)

What you’ll learn

  • Distinguish a router, a meta-controller and a blackboard controller by what they choose and how often.
  • Diagnose a misrouted request, which still gets an answer, with a table of expected routes checked in code.
  • Compare an ensemble’s independent votes with its aggregator’s verdict.
  • Explain how a grid of cells with one local rule finds shortest paths with no controller at all.

Lessons 36.1 to 36.3 each fixed one way of coordinating agents. This lesson asks who chooses that way, then removes the chooser altogether.

Larkspur’s support assistant now receives every kind of request: “What is a vCPU?”, “Is there an incident right now?”, a four-part refund question, “Should we move to an annual plan?”. One architecture for all of them is wrong somewhere. A single call guesses at the live incident, and a search loop wastes calls on the vCPU definition.

A router, a meta-controller and a blackboard controller are all one structured-output call that picks from a fixed set. They differ in what they pick and how often:

Controller What it decides When Calls per request
Router Which specialist answers, inside one fixed graph Once, before any specialist runs 1
Meta-controller Which whole architecture runs: one call, a search agent, a planner or a debate Once, before any architecture runs 1
Blackboard controller (36.1) Which specialist acts next, given the whole board After every contribution, until done Up to one per specialist turn, plus one

Table 1: Three controllers, one mechanism. The difference is the level and the frequency of the choice.

A router differs from a handoff (M35) in who holds the decision. The router decides before any specialist runs, and the specialist cannot pass the request on. In a handoff the agent holding the conversation transfers it by calling a tool.

The notebook’s router has three specialists: a generalist for conversation, a researcher with web search, and a coder. Its decision is a Literal of the three names, and a conditional edge dispatches to the chosen node.

Dispatch through a strategy registry

A meta-controller makes the same choice one level up. It wraps each architecture as a plain callable that takes the request text and returns an answer, and it never sees inside one. Its decision is a Strategy enum, and a registry maps each member to its callable instead of a chain of ifs. A registry check in code catches a strategy with no callable.

When the route is wrong

The main weakness is a silent misroute. A misrouted request still gets an answer, from the wrong specialist or architecture, and nothing downstream notices. A direct_answer reply to “Is there an incident right now?” reads fine and is a guess.

The notebook’s guard is a table of requests with the route each was written for, compared in code with the route each controller chose:

Chemical symbol for gold direct_answer Extra calls, same answer

Two limits remain. One choice per request cannot handle a mixture (“look up X, then debate whether it is a good idea”), and the classification call adds latency before any real work starts.

Ensembles: vote against verdict

An ensemble runs several independent agents on the same question at the same time, each with a different persona, and an aggregator combines their conclusions. The notebook’s committee has a bullish growth analyst, a cautious value analyst and a quantitative analyst, each a search agent, and a chief investment officer (CIO) who writes the recommendation.

Figure 1: The ensemble graph. Three branches in one superstep, and a join that waits for all of them.

The graph uses every piece of lesson 36.5. One edge from START to each analyst puts all three in one superstep. All three write the shared analyses key in that superstep, and the key carries the operator.or_ reducer, which merges their one-entry dicts. A list edge from the three analysts makes the CIO wait for every report.

The analysts never see each other’s work, and none anchors on another. That independence is what an ensemble buys. The notebook checks two things that are easy to assume:

  • Overlap. Each analyst records its start and end time. The check passes when all three windows were open at once.
  • Vote against verdict. Each analyst ends its report with a Buy, Hold or Sell line. The CIO’s recommendation is a Literal of five values, from Strong Buy to Strong Sell, and code maps it to its direction (Strong Buy counts as Buy). Code then sets the majority vote beside the verdict.
Analyst votes CIO verdict Reading

For Larkspur, the same shape fits an answer review. Three graders read one drafted reply, one for faithfulness to the retrieved chunks, one for tone, one for policy, and an aggregator decides whether it ships. Each grader costs its own model calls, and the committee is priced like three agents. Its latency is set by the slowest grader.

Emergent systems

The cellular-automata notebook has no controller at all. Every cell of a warehouse grid is a small agent with one local rule: its distance to the packing station is 1 plus the smallest distance among its four neighbours. Walls stay at infinity. Applied to every cell at once, tick after tick, the rule spreads a distance wave around the walls. A carrier reaches the station by always stepping to the neighbour with the lowest value.

Figure 2: The automaton’s loop. Every cell computes its next value from the current grid, then all values change together.

The notebook runs this on a 7 by 7 warehouse with walls inside, then checks every emergent path against a global breadth-first search over the same grid. A scratch run of its deterministic cells gives:

Run Ticks until stable Carrier path Breadth-first shortest
Item A, original layout 9 4 moves 4
Item B, original layout 9 3 moves 3
Item A, wall added next to the station 15 12 moves 12

Table 5: Emergent paths against a global search, from a scratch run of the cellular-automata notebook. The count of ticks includes the final tick that changes nothing.

The third row is the adaptability claim. A new wall beside the station blocks item A’s short route, and the same rule finds the 12-move route around the top of the grid with no change to the code.

This is the far end of the control range in this module: no controller, only a local rule applied everywhere in synchronous ticks. It solves a global problem without a planner, at the cost of many cheap updates. A MAX_TICKS guard stops a grid that never settles, and the notebook trusts the result only after the breadth-first check.

In practice: Larkspur’s mixed traffic

  1. Classify each request once with the meta-controller and record its reasoning.
  2. Dispatch through the registry: the vCPU question to one call, the incident question to the search agent, the four-part question to planning (lesson 36.5 runs its parts in parallel), the plan question to debate.
  3. Review drafted replies with a three-grader ensemble, and flag any verdict that overrides the graders without a reason.
  4. Regression-test the routes: keep the expected-route table beside the prompt and run it on every change.

Key Takeaways

  • A router picks a specialist and a meta-controller picks a whole architecture, each once per request, with one structured-output call over a fixed set. A misrouted request still gets an answer: keep a table of requests with their intended routes and compare it in code on every prompt or model change.
  • An ensemble runs independent agents in one superstep with a reducer on their shared key. Set the majority vote beside the aggregator’s verdict, and flag a departure from the majority that gives no reason.
  • A cellular automaton needs no controller: one local rule found the shortest paths in the warehouse (4 and 3 moves, then 12 around a new wall), confirmed by a global search.

Check yourself

1. A router and a meta-controller each make one structured-output call before any work starts. What does each one choose?

A router chooses which specialist answers inside one fixed graph. A meta-controller chooses which whole architecture runs (a direct answer, a search agent, a planner or a debate), each wrapped as a callable it never sees inside. A blackboard controller differs from both by deciding again after every contribution.

2. A Larkspur customer asks whether there is an incident right now. Which strategy should the meta-controller pick, and why not direct_answer?

search_agent, because only the live status page knows the answer. direct_answer suits a self-contained fact the model already knows, such as what a vCPU is. A misrouted request still gets an answer, which is why the implementation compares each chosen route with the route the request was written for.

3. All three ensemble analysts end with Buy, and the CIO recommends Hold. Is that a failure?

Only if the CIO’s summary gives no reason. Code maps the CIO’s five-value recommendation to Buy, Hold or Sell and sets the majority vote beside it. A CIO that departs from the majority and says why is fine. One that departs with no reason is the unexplained override to look for.

Map-reduce / async

Lesson 36.5: Parallel agents, async nodes and streaming. Notebooks: 05a_parallel_agents.ipynb, 05b_async_multi_agent_streaming.ipynb

What you’ll learn

  • Explain how LangGraph runs parallel branches in supersteps, and why the slowest branch sets the pace.
  • Choose a join that waits for every branch, and a reducer for every key that parallel branches share.
  • Use Send for a fan-out whose size is known only at run time.
  • Compare what async nodes, astream modes and a concurrency cap change, and when parallelism buys nothing.

Lesson 36.4’s ensemble ran three analysts at once without taking the machinery apart. This lesson is that machinery.

Larkspur’s assistant receives a compound question: “I’m cancelling my annual plan after this week’s outages. Can I get a full refund, how long will it take, can I still export my data, and do I get credits for the outages?” It splits into four sub-questions with independent evidence. Answered one at a time, the reply takes as long as every model call added together. Answered in parallel with the wrong join, the first reply goes out with nothing about outage credits.

An agent spends almost all of its time waiting: for a model, a search, a database. Three agents that each wait one second take 3 s one after another and 1 s together, because the waits overlap. Nothing runs faster. The async notebook measures exactly that with a one-second sleep standing in for a model call, and a scratch run prints 3.00 s and 1.00 s.

Three of the four sub-questions are answered directly. The outage one first rewrites “outages” into the handbook’s own words (availability, service credits), because TF-IDF missed that evidence in M10:

Supersteps and the barrier

LangGraph runs a graph in supersteps. In each superstep it runs every node that the previous superstep triggered, waits for all of them, applies their state updates together, and only then works out what runs next. Several edges out of one node, a fan-out, put all their targets in the same superstep, and they run in parallel: async def nodes on the event loop, plain def nodes in a thread pool.

The parallel notebook proves the layout with model-free stub nodes and a debug stream that reports the superstep of every task. A scratch run on a planner, three searchers and a report gives:

Superstep Nodes that ran
1 plan
2 search_db, search_docs, search_web
3 report

Table 1: Superstep layout of a one-planner, three-searcher fan-out, from a scratch run (LangGraph 1.2.18).

The barrier at the end of a superstep costs time when branches have different lengths. The lab gives each node a fixed stub latency:

Node plan refund_window refund_timing export rewrite credits synth
Seconds 0.4 1.0 0.8 1.2 0.5 1.0 0.8

Table 2: The lab’s stub latencies.

In Figure 1, rewrite finishes at 0.9 s, but credits cannot start until the whole superstep ends at 1.6 s, when export (the slowest, 1.2 s) finishes. The outage branch waits 0.7 s for work it does not depend on. We call this the barrier tax. Moving the rewrite inside the credits node keeps every branch one node long, and the answer lands at 2.7 s instead of 3.4 s.

Joins that wait for every branch

A join is a node with several incoming branches. With separate edges from each branch, it runs once for every superstep in which one of its predecessors finished. The parallel notebook builds one unequal-branch graph three ways: branch a is one node long, branch b1 then b2 is two. A scratch run counts the join’s runs:

Join style Join runs What each run saw Nodes per superstep
Separate edges 2 a, then a + b2 {a, b1}, {b2, join}, {join}
List edge from a and b2 1 a + b2 {a, b1}, {b2}, {join}
defer=True on the join 1 a + b2 {a, b1}, {b2}, {join}

Table 3: One graph, three join styles, from a scratch run of the notebook’s stub graphs.

The first row is the half-evidence answer. In the lab’s graph the separate-edges synthesizer runs in superstep 3 with 3 of 4 sub-answers, writes a reply with nothing about outage credits, and runs again after credits.

  • A list edge waits for every node it names. Use it when you know the predecessors at build time. If a conditional edge skips one of them, the join never runs.
  • defer=True holds the join until the run has nothing else to do. It also suits branches chosen at run time.

A model-free test like Table 3 counts the synthesizer’s runs and keeps a fixed join fixed.

Reducers for shared keys

Nodes of one superstep write their updates together when it ends. If two of them write the same key and the key has no reducer, LangGraph cannot choose a winner. It raises InvalidUpdateError with the message “At key ‘findings’: Can receive only one value per step.” A reducer in the state schema says how to combine the writes:

Key type Reducer What two parallel writes become
List operator.add One list: every branch appends its sub-answer
Counter operator.add The sum
Dict A dict merge, or operator.or_ One dict keyed by branch

Table 4: Reducers for keys that parallel branches share.

The notebook runs the same two nodes against both schemas. The plain one raises, and the reduced one keeps both writes. The combined list comes out in the same order on every run, whichever branch finished first, because LangGraph applies a superstep’s writes in a fixed order. A key that only one node per superstep writes needs no reducer.

Fan-out sized at run time

Fixed edges cannot express a fan-out whose size is known only at run time: one branch per document, or one per sub-question when the decomposer (M17) returns three for one question and five for the next. A routing function that returns a list of Send objects can. Each Send names a node and a private input for it:

Figure 2: Map-reduce with Send. All the answer_one runs land in one superstep.

An operator.add reducer collects the results. Branches can finish in any order, and the reduce step sorts them by their tag before combining. The parallel notebook maps an LLM summary over three documents this way and counts one map branch per document. A fourth document adds a fourth branch with no change to the graph.

max_concurrency in the run config caps how many tasks run at once, which is how you stay under a provider’s rate limit. LangGraph starts a superstep’s tasks in node-name order, and under a cap the later names wait for a free slot. At a cap of 2, credits and export start first, and the two refund branches wait for a free slot. At a cap of 1 the parallel graph takes as long as the chain. With separate edges it takes longer, 6.5 s against 5.7 s, because the synthesizer still runs twice.

When parallelism buys nothing

  • A chain. If the writer needs the researcher’s output, it cannot start early. The async notebook’s three dependent one-second steps take 3.00 s, async or not.
  • A single agent. One agent waiting is one wait. Streaming can still show progress, but there is no time to win.
  • Fast local work. Arithmetic and string handling are work, not waiting. Async adds overhead to them.

Whole runs can overlap too. Gathering three complete team runs on one event loop takes 1.50 s in a scratch run, against about 4.5 s one after another, with no change to the graph. Inside a running event loop, such as a notebook, await the graph directly: starting a second loop there fails.

In practice: the compound refund question

  1. Plan the four sub-questions, and dispatch them with Send when the decomposer’s count varies.
  2. Keep branches level: do the outage rewrite inside the credits agent and avoid the barrier tax.
  3. Join once: a list edge into the synthesizer, or defer=True when branches are chosen at run time.
  4. Reduce the sub-answers with operator.add and sort them by tag.
  5. Stream updates to show each sub-answer as it lands, starting at 1.2 s in the lab.
  6. Cap concurrency to the provider’s rate limit, and price the cap in latency: 2.7 s becomes 3.7 s at a cap of 2.

Key Takeaways

  • Parallel agents overlap their waits and run no faster: three one-second waits take 1 s together against 3 s in sequence. A chain, a single agent or fast local work gains nothing.
  • LangGraph runs fan-out targets in one superstep and waits for all of them before the next. Keep branches the same length, and join with a list edge or defer=True so the join runs once with every input.
  • Give any key that several nodes write in one superstep a reducer, or LangGraph raises InvalidUpdateError. Use Send for fan-outs sized at run time, and max_concurrency to stay under rate limits.

Check yourself

1. Three agents that each wait one second finish in about one second together. Why, and what does making nodes async not change?

The waits overlap, and nothing runs faster. Edges from one source put nodes in the same superstep, and that is what makes them parallel. Making nodes async def adds overlap on one event loop but does not change which nodes are parallel. A chain of async nodes still runs in order.

2. In the lab, moving the rewrite inside the credits node brings the answer from 3.4 s to 2.7 s. Where does the saving come from?

As its own node, rewrite finishes at 0.9 s, but credits cannot start until the superstep ends at 1.6 s, when export finishes. The outage branch pays a 0.7 s barrier tax for work it does not depend on. Inside one node, every branch is one node long and that wait disappears.

3. The synthesizer writes a reply with nothing about outage credits, then runs a second time. What causes this, and how do you fix it?

The join uses separate edges, and it runs once for every superstep in which a predecessor finished. Its first run saw 3 of 4 sub-answers. Use a list edge when the predecessors are known at build time, or defer=True when branches are chosen at run time. A list edge never runs if a conditional edge skips one of its named nodes.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s support assistant now answers each part of a compound question in a parallel branch. Since the change, some replies to “refund, export and outage credits” questions say nothing about credits, and the trace shows two synthesizer outputs for one request. What happened, and how do you fix it?

What a strong answer covers:

  • Reads the trace by superstep: the outage branch has one more node (a query rewrite) than the others, so it finishes a superstep later
  • With separate edges into the synthesizer, the join runs once per superstep in which a predecessor finished: first with three sub-answers, then again with four. The reply that went out was the first
  • Fixes the join with a list edge (add_edge([...], "synth")) or defer=True, or keeps every branch one node long by moving the rewrite inside the agent
  • Adds a deterministic test with stub nodes that counts synthesizer runs and the sub-answers each run saw, so the fix stays fixed

2. Escalations ask for one of two follow-ups depending on what the incident log shows: a service-credit reply if availability fell below the SLA, a status-page reply otherwise. Would you build this as a fixed pipeline, a router or a blackboard?

What a strong answer covers:

  • A fixed pipeline cannot skip a step, so it runs both follow-ups on every escalation and pays for both
  • A router decides once, before any specialist has run, so it cannot branch on what the incident analyst finds
  • A blackboard controller re-reads the board after each post and can choose the credit branch only after the incident finding lands; that is the behaviour the request needs
  • Guards it: a Literal decision so the controller can only name a real node, a call cap enforced in code, a recursion limit as a backstop, and a computed check of which branches ran

3. You parallelised the four sub-question agents. Median latency fell, but p95 barely moved and the provider started returning rate-limit errors. How do you measure what is going on, and what do you change?

What a strong answer covers:

  • Wall time is the sum, over supersteps, of the slowest task in each, so p95 follows the slowest branch’s tail; logs per-node latency from the updates stream to find it
  • Caps concurrency (max_concurrency in the run config) to stay under the rate limit and measures what it costs: in the lab a cap of 2 takes the answer from 2.7 s to 3.7 s
  • Tracks time to the first streamed sub-answer separately from time to the final answer, since that is what the user sees first
  • Re-runs the golden set from the M10 baseline to confirm the faster path did not change answer quality

4. One of the four branches times out on a provider call. What happens to the three sub-answers that finished, and how should the assistant reply?

What a strong answer covers:

  • A task error fails the whole superstep; the synthesizer never runs on that attempt
  • With a checkpointer, LangGraph keeps the writes of the tasks that succeeded in that superstep, so a resume re-runs only the failed one
  • Adds a retry policy to the flaky node, and decides whether a missing sub-answer should block the reply or become an explicit “could not check outage credits” line the synthesizer must state
  • Alerts on the per-branch failure rate, since one flaky dependency now takes down every compound question that touches it

5. A product manager wants every refund answer to go through a three-round debate “so the assistant considers both sides”. What do you say?

What a strong answer covers:

  • A three-round debate costs 7 calls instead of 1; the notebook’s own advice is that a factual question with one correct answer is better served by a single call
  • Refund policy is a fact in the handbook; if two retrieved chunks disagree (an old and a new policy), the fix is version metadata and filtering at retrieval, not an argument
  • Debate earns its cost on real trade-offs, such as whether to replace RAG with a long-context prompt, where the transcript and the judge’s strongest point from each side are the deliverable
  • Proposes a test: run debate and single-call answers on the golden set and compare correctness, faithfulness, cost and latency before deciding

Key Takeaways

  • Choose the collaboration pattern by who decides the next step and when: fixed at build time (pipeline, STORM), shaped but overlapping (fan-out), or decided at run time (blackboard).
  • Give every LLM controller a typed decision, a call cap enforced in code and a computed check of what actually ran.
  • Parallel branches cost as much as the slowest task in each superstep; keep branches the same length, join with a list edge or defer=True, and put a reducer on every shared key.
  • Debate and STORM multiply calls by design. Count them, run the cheap baseline beside them, and keep them for trade-offs and research where the trail is the product.
