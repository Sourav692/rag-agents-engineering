Open the lab

The running example is the Larkspur Cloud handbook from M10 to M12, split between three specialist RAG agents. The billing agent holds billing, cancellation, refunds and promotional credits; the operations agent holds the availability guarantee, incidents, server sizing and reboots; the data agent holds exports and retention. Three requests come back on every page and in the lab: How long does a refund take? (billing), My server went down last night. Do I get service credits? (operations, then billing) and Can I export my data after I cancel my plan? (data).

TL;DR

  • Split one agent when it has more tools or sources than one prompt can choose among well. A team makes more model calls (the 35.1 notebook’s specialist team costs roughly four times the monolith’s), so measure it against the single agent on the same requests.
  • The five LangGraph architectures share one primitive, Command(goto=..., update=...): a node writes to state and names the next node. They differ in who decides what runs next.
  • A supervisor decides every step and takes control back. On the outage request that costs 5 model calls, 3 of them routing, and buys one place to log, test and cap every decision.
  • A hierarchy nests compiled team graphs under a top supervisor. With three specialists it only adds overhead (7 calls for the same request); it pays off when one supervisor would face too many workers.
  • A handoff is a tool that returns Command(goto=..., graph=Command.PARENT). A swarm stores active_agent per thread, so a follow-up costs 1 call against 3 for the supervisor. Nothing ends a handoff loop except recursion_limit, whose default is 10,007 steps.

Mental model

Both graphs answer the outage request with the same two specialists. The supervisor decides before each specialist and once more to finish, so it spends 3 of its 5 model calls on routing. In the swarm, triage routes once and each agent hands the work on itself: 3 calls. Every architecture in this module sits somewhere between these two, and the choice is about who holds control after an agent finishes.

M34 gave one agent a memory that lasts across sessions. This module asks a different question: when should the work be split across several agents at all?

Larkspur’s support assistant is one agent with the whole handbook and every tool. A customer writes My server went down last night. Do I get service credits? On every step the agent chooses among billing, outage, export and sizing material in one long prompt. The question needs two parts of the handbook: the outage rules, then the credit rule (10% of the month’s server charges when availability falls below 99.95%, claimed by ticket within 30 days). One prompt that covers everything has to get both parts right in one loop.

When one agent becomes a team

A monolithic agent is one ReAct loop with one system prompt and every tool. A specialist team splits the request among agents that each have one domain, a narrow persona and a few tools, plus a step that merges their work. The comparison notebook builds both for a market report with three sections: news and sentiment, a technical read of the price trend, and financial performance.

Figure 1: The monolithic agent. One loop writes all three sections, and each step chooses among every tool and topic.

The team gives each section its own ReAct agent with the same search tool, and a report writer merges their sections:

Figure 2: The specialist team. The three analysts share one super-step, and the writer waits for all of them.

The team runs as fan-out and fan-in: START has an edge to all three analysts, and each analyst has an edge to the writer. LangGraph runs nodes in super-steps. Every node whose inputs are ready runs in the same step, and the next step starts only when they have all finished. The three analysts share the first step and the writer runs in the second.

Comparing the two reports fairly

The notebook does not declare a winner from one run. It measures both reports in two ways:

Evidence What it records What it can claim
Code measures word count, markdown headings, and whether the text covers news, technicals and financials (keyword checks such as “revenue” or “moving average”) facts about the text
Judge scores 1 to 10 for clarity and structure, analytical depth and completeness, plus a justification one model’s opinion of one sample

Table 1: The two kinds of evidence. The judge scores each report as “the report” and never learns which design wrote it.

We call the trap here the single-sample verdict. One request on one company is one sample, and a gap of a point or two on the judge alone is noise. When the code measures and the judge point the same way, the difference is worth testing on more requests. When only the judge prefers one report, it is not.

Key distinction: a team buys focus and parallelism with more model calls. Whether it also buys better answers is an empirical question, settled by measuring many of your own requests.

For Larkspur the same test decides whether to split the support assistant into billing, operations and data agents that each search one part of the handbook. The price is a decision about which of them should answer, and the rest of this module is about that decision. First comes the simplest kind of team, one whose order is fixed before it runs.

A crew is a dependency graph

The optional notebook rebuilds the core of CrewAI without a framework, on the raw OpenAI SDK. Two ideas carry it: an Agent and a Crew.

An agent has a backstory (its system prompt), a task description, an expected output and a context slot. Dependencies are declared with operators borrowed from Airflow:

Declaration Meaning What happens at run time
a >> b b depends on a a’s output lands in b’s context, labelled “Output of a”
b << a the same dependency, written the other way the same
a >> b >> c a chain each agent feeds the next
[a, b] >> c fan-in: c depends on both c waits for both and reads both outputs

Table 2: The crew’s dependency operators.

A crew collects every agent created inside its block and runs them in topological order: an agent runs only after everything it depends on. The notebook sorts with Kahn’s algorithm, which also detects cycles:

The same crew as a StateGraph

The sort fixes an order and nothing more. In the crew, the pros and cons analysts still run one after the other, even though neither needs the other. The notebook’s last part rebuilds the same fan-in as a LangGraph StateGraph, with stub nodes that log what they had seen:

Table 3: The fan-in crew as a StateGraph (the notebook’s bridge cell, run as written).

The two analysts share a super-step and the editor runs once, with both entries in state. Each crew piece has a LangGraph counterpart: an agent is a node, a >> b is add_edge("a", "b"), [a, b] >> c is one edge from a list of nodes, the growing context string becomes typed state with a reducer, and the sort plus run becomes compile() and invoke().

Pitfall: parallel in name only. A dependency graph says what may run together. Whether it does is up to the runtime: Kahn’s sort feeding a plain loop is sequential, and LangGraph’s super-steps run ready nodes together.

LangGraph also adds what a fixed graph lacks: conditional edges, loops and checkpoints. Every architecture from lesson 35.2 on uses them to add a node that chooses the next agent at run time.

Key Takeaways

  • A specialist team gives each agent one domain and a few tools, at roughly four times the model calls of one ReAct loop. Running the specialists in one super-step keeps latency near the slowest one.
  • Compare a team with a single agent using code measures and a judge that does not know which design wrote each report. A gap of a point or two on the judge from one request is noise.
  • A crew is a fixed dependency graph run in topological order, and a cycle fails at the sort before any model is called. Choosing the next agent at run time is what the later architectures add.

Check yourself

1. The specialist team makes roughly four times the monolithic agent's model calls. Why is its latency set by the slowest analyst, not the sum of all three?

START has an edge to all three analysts, so LangGraph runs them in the same super-step, in parallel. The report writer has an edge from each analyst and starts only when all three have finished. The time is the slowest analyst plus the synthesis call.

2. On one company, the team's report scores a point higher than the monolithic report from the judge. Is that enough to switch to the team?

No. One request on one company is one sample, and a gap of a point or two on the judge alone is noise. Check whether the code measures (word count, headings, topic coverage) point the same way, and repeat on more requests before deciding.

3. A crew declares writer >> reviewer and reviewer >> writer. What happens when you run it, and at which point?

The crew raises a ValueError at the topological sort, before any agent runs or any model is called. Kahn’s algorithm never queues an agent caught in a cycle, and the sorted list comes up short. Choosing the next agent at run time, loops included, needs the graph-based patterns from lesson 35.2 on.

Five architectures, one primitive

Every architecture in the routing notebook is built from one return value. A Command is what a node returns to do two jobs at once: write an update to state and name the node that runs next.

Part Example What it decides
goto "writer" the next node, chosen at run time
update {"messages": [reply]} what this node writes to state
Return annotation Command[Literal["writer", "__end__"]] the nodes this one may jump to; LangGraph draws them as the graph’s edges

Table 1: The fields of a Command and the annotation that declares its targets.

add_edge fixes a path when the graph is built, and Command(goto=...) picks one at run time. Most real systems use both. A target listed in the annotation that the code never returns still appears as an edge, which is why the notebook keeps each Literal to the branches the function can take.

The tool-calling supervisor needs no routing code. Its routing quality becomes a prompt and description problem, and you can no longer read the rules in code.

Planted failure: the runaway loop

A network has no node that can say “stop”. The notebook plants a runaway loop: two nodes, ping and pong, that hand off to each other forever. LangGraph counts super-steps and stops a run at recursion_limit:

Setting What happens to ping and pong
Default limit 10,007 super-steps before GraphRecursionError
recursion_limit = 25, as every notebook run passes GraphRecursionError after 25 super-steps; 0.002 s in our stub run
Hierarchy run the notebook doubles the cap to 50, because each team spends steps of its own

Table 2: The ping-pong loop under each limit. The default comes from LangGraph’s installed source.

The limit caps steps, not time. Twenty-five steps of a graph that calls a model at every node is still slow. Treat the limit as a guard against runaway loops, not a timeout. Pass it on every run.

Agent communication

While agents run, they pass work to each other through state. The optional notebook builds three patterns for that:

Figure 7: Three ways to exchange work. One shared transcript, one field per stage, or a draft list and a critique list.

Pattern State Each agent reads Trade-off
Message passing one messages list with the add_messages reducer the whole conversation so far simple and transparent, but every agent re-reads and parses prose
Typed fields one field per stage (raw_data, analysis, confidence_score, recommendations) only the fields it needs structured output fills each field with a validated Pydantic object, and the schema is rigid
Generator and critic running lists of drafts and critiques (operator.add) the last draft and the feedback on it iterates to a better draft and needs a cap

Table 3: Three ways agents exchange work.

With typed fields, a malformed reply fails validation instead of silently becoming a wrong value. The analyst’s confidence must lie between 0.0 and 1.0, and the collector must return points with a source and a finding. Downstream agents read those fields directly and parse nothing.

A critic that quotes its evidence

The generator and critic loop shows how to keep a model from ending its own loop. A critic that answers yes or no can approve a draft that misses a criterion, and nothing checks it. We call this the lenient critic. The notebook’s critic never gives the verdict. For each of three criteria (a named LangGraph feature, a concrete use case, a trade-off) it copies the sentence from the draft that meets it, or writes none. Code computes the verdict:

Figure 8: The generator and critic loop. The model supplies quotes, and code decides.

We ran the notebook’s check function on a three-sentence Larkspur draft (“LangGraph checkpointers let a support thread resume. A billing agent and an outage agent can share one graph. The cost is more model calls per request.”) with planted critiques:

Planted critique Missing criteria returned Why
All three sentences quoted exactly none every quote is in the draft, and the feature quote names “checkpoint”
Trade-off quote invented (“It is slower than plain code.”) trade-off the quote is not in the draft
Use-case quote is none use case none counts as missing
Feature quote is the use-case sentence feature the quote names no feature from the notebook’s list
A critic that always answers none, in the full loop all three the loop stops after 3 drafts with capped set

Table 4: The critic check on planted critiques (notebook functions run with a stub model).

An invented quote cannot pass, because membership in the draft is tested in code. MAX_ITERATIONS = 3 ends the loop whether or not the critic ever approves.

Key distinction: this loop is not a blackboard. Its order is fixed (draft, critique, draft), and only the exit is decided at run time. A blackboard has a controller that picks which of several specialists acts next from what is on the shared board. M36 builds one.

Limits of this evidence

  • Stub paths. The message orders come from the notebook’s graphs with a model that always answers “ok”. They show routing, which keys off role tags, not answer quality.
  • Tool-calling routes are not reproduced. That supervisor routes on the model’s tool choice, which a stub cannot make. Its panel describes the notebook’s claim instead of a run.
  • Timing. The 0.002 s loop is one stub run on one laptop. With a model at every node, 25 steps take as long as 25 model calls.

Key Takeaways

  • Build every architecture from one primitive, a node returning Command(goto=..., update=...). add_edge fixes a path at build time, Command picks one at run time, and most systems use both.
  • Pick the architecture by who should decide what runs next. Use a custom workflow when the order is known, handoffs when the conversation should move with an agent, and a supervisor when routing must be auditable.
  • Always pass recursion_limit, since the default is 10,007 super-steps. In a generator and critic loop, have the critic quote evidence per criterion, compute the verdict in code and cap the iterations.

Check yourself

1. What does a node return to choose the next agent at run time, and how does LangGraph know which edges to draw for it?

It returns Command(goto="writer", update={...}): the update goes into state and the named node runs next. The return annotation, such as Command[Literal["writer", "__end__"]], lists the nodes it may jump to, and LangGraph draws those as edges. add_edge fixes a path at build time, while Command(goto=...) picks one at run time.

2. Larkspur's support assistant may need one specialist or two, so the order is not known in advance. Which question then decides between a swarm and a supervisor?

Whether an agent should pass the conversation on, which comes down to whether conversations stay with one specialist across turns. If yes, use handoffs and a swarm (35.5). If no, and peers need not negotiate and one supervisor can handle the specialists, use a supervisor (35.4).

3. A yes-or-no critic sometimes approves drafts that miss a criterion. How does the notebook's critic design prevent that, and what ends the loop?

The critic never gives the verdict. For each of three criteria it quotes the sentence from the draft that meets it, or writes none. Code checks that each quote is really in the draft and computes the verdict. An invented quote counts as missing. MAX_ITERATIONS = 3 ends the loop whether or not the critic approves.

Human review in a supervisor loop

The notebook builds the same pattern on news articles. A short transfer rumour (“Lionel Messi will join Real Madrid in 2025”) has to become a publishable article. A supervisor, the “news chef”, grades the article and routes it to the specialist that can fix what is missing. A person reads the result before it is published.

Two guards keep the loop safe to run unattended up to the human step:

  • A pass cap. MAX_PASSES = 5. A live grader sometimes marks a check “no” twice, and the same specialist runs again. A grader that never says “yes” cannot keep the loop going past five passes.
  • One place for the output. Only a full pass copies the article into final_article. The published text is always the version that passed, whether or not any specialist ran. The 109-word article reaches publication unchanged for that reason.

The planted failure here is the stale output: a variable set before the last specialist ran, published after it. Writing the output in exactly one place, on a full pass, rules it out.

Static or dynamic review

interrupt_after is static: fixed at compile time, it pauses every run at the named node. A dynamic pause calls interrupt(payload) inside a node. It pauses only when the node decides to, shows the reviewer the payload, and resumes with Command(resume=...). The notebook builds only the static kind; the dynamic design below is an addition.

Key Takeaways

  • Grade in code whatever code can check exactly, such as word count, and use a model with structured output only for checks that need judgement. Route to the first failing check and cap the passes.
  • Write the published output in one place, set only on a full pass, so the text that ships is always the version that passed.
  • A static interrupt_after pauses every run at a node, while a dynamic interrupt(payload) pauses only when the node decides. Use the dynamic kind for a refund outside the 30-day window, and compare the dates in code.

Check yourself

1. Why does the news chef use a model to judge topic, club and market value, but leave the 100-word check to code?

Topic, club and market value need judgement, so a model answers them with structured output. The word count is exact. Code computes it and the model is never asked. A check that code can do exactly should never depend on a model’s answer.

Supervisor

A supervisor decides again after every specialist. It is a node that reads the work so far and picks the next specialist, or decides the task is done, and every specialist reports back to it.

Deciding, routing and counting

The supervisor notebook’s supervisor is a model with structured output. Its decision type, RouteDecision, holds next, a closed Literal["researcher", "writer", "critic", "FINISH"], and a one-line reasoning. A typed choice cannot name a node that does not exist, and the graph never parses prose to find out where to go.

The notebook then splits the work three ways:

Piece Calls a model Writes to state
Supervisor yes, once per decision next_agent, task_complete and one route_log entry; never messages
Specialist (researcher, writer, critic) yes its output to messages, and specialist_calls: 1
route_to_agent (on the conditional edge) no nothing: it reads state and returns the next node

Table 1: Who decides, who works and who routes in the supervisor graph.

Two details make this hold. The operator.add reducer sums each specialist’s specialist_calls: 1, which means the count never depends on reading message text. And route_to_agent reads that counter first. Once it reaches MAX_SPECIALIST_CALLS = 6, the run goes to finalize, whatever the model chose. Only then does it follow task_complete and next_agent:

Figure 1: The supervisor loop. The model’s choice is read only after the counter.

Keeping decisions out of messages gives two clean records: the transcript holds only the work, and route_log holds every routing decision with its reason. The routing log is what you read when a request went to the wrong specialist.

Hierarchical teams

When one supervisor has too many workers to choose among well, group the workers into teams with a supervisor each, and put a coordinator over the team supervisors. That is a hierarchy. In LangGraph each team is its own StateGraph, compiled on its own, and added to the parent graph with add_node like any function node. The parent never sees inside it.

The hierarchy notebook has a CEO over three departments:

Figure 2: The hierarchy notebook. Each department is a compiled graph, and control returns to the CEO after each one.

A team’s inside is its own choice. Research fans out to two specialists and merges in a lead, content has its own supervisor, and analysis is a fixed pipeline. After each department the run returns to the CEO, which can send the work on to a second department (“research X, then write Y” goes to research, then content) or finish.

The state contract between levels

Four rules make the hierarchy compose:

  • One shared contract. TeamState (messages and final_answer) is what the parent and every team speak. A compiled team drops in as a node with no adapter code.
  • Extensions stay at their level. The CEO’s CEOState adds department, route_log and ceo_turns. The content team’s ContentState adds next_step and content_turns. Keys outside TeamState never cross the boundary.
  • Counters stay out of the shared contract. A team hands its whole final state back to the parent, and the parent applies its reducers to it.
  • Cap every level. MAX_CEO_TURNS = 4 and MAX_CONTENT_TURNS = 4, each read by a pure routing function from its own counter.

The third rule guards against the double-counted counter. We planted it in a two-node test in the scratchpad: one increment in the parent, then one inside a team, with the counter declared in two places.

Compare where the counter is declared. The parent adds 1, then the team adds 1.

In the shared contract

  • After the parent's step: 1.
  • The team adds 1 and returns its whole state, count 2, to the parent.
  • The parent's adding reducer adds that 2 to its own 1: the count reads 3, not 2.

A CEO cap that reads this counter stops the run early, and the turn count in the log is wrong.

At each level

  • The parent's ceo_turns reads 1 after its own step.
  • The team's own counter stays inside the team: it never appears in the parent's state.
  • Only the shared keys, here the messages, cross the boundary.

This is the notebook's design: ceo_turns in CEOState, content_turns in ContentState.

Test each team on its own before you assemble the hierarchy. The notebook runs the research team and the content team alone first, because a team that misbehaves is much harder to diagnose once it is one node in a larger graph. The cost is visibility and steps: the parent sees what a team appended, not why, and the five-architectures notebook doubles recursion_limit from 25 to 50 for its two-level run.

Handoffs

A router and a handoff both move a request between agents. They differ in who holds control afterwards:

Router or supervisor Handoff
Who picks the next agent the router, after every step the agent holding the conversation, by calling a tool
Where control goes after an agent back to the router, on a static edge nowhere: the agent finishes the turn or hands off
The next user message starts at the router the active agent, read from active_agent in state
What stops a loop the router’s own cap nothing built in; only recursion_limit

Table 1: Router against handoff.

The handoff tool

A handoff tool is an ordinary tool that returns a Command instead of a string. It runs inside the calling agent’s own graph, but the decision belongs to the parent graph that holds all the agents. The Command is addressed there. The handoff notebook calls one directly, with no model, for a customer charged twice. We ran that cell, unchanged, in langgraph 1.2.18:

Field Value returned What it does
goto billing names the parent node to run next
graph __parent__ (Command.PARENT) applies the command in the closest parent graph, which ends the calling agent’s run
update.messages the conversation plus a ToolMessage the ToolMessage answers call call_demo and carries the note “Customer was charged twice for this month’s subscription.”
update.active_agent billing who answers the next message on this thread

Table 2: The Command a hand-built handoff tool returns (the notebook’s direct-call cell).

InjectedState gives the tool the agent’s messages and InjectedToolCallId gives it the id of the call it answers. The model fills in one argument only: context, a note for the next agent, which spares the customer from being asked again. The parent’s state is MessagesState plus active_agent. Its only routing of its own is at START: read active_agent and send the new message there, or to triage on a new thread.

Planted failure: the handoff ping-pong

Nothing in this graph forces a stop. If agents keep deciding someone else should answer, they pass the request around until recursion_limit raises GraphRecursionError. Each agent run is one super-step of the parent graph. The notebook scripts that handoff ping-pong (triage to support to billing to triage, forever) and caps it:

recursion_limit = 10

  • Every real run in the notebook passes this limit.
  • The same loop would end the same way, after 25 super-steps.

The fix for a real ping-pong is ownership: one agent’s prompt and tool descriptions must claim the topic. The limit only makes the failure fast and visible.

Swarm

A swarm is the same mechanism packaged by the langgraph-swarm library. create_handoff_tool builds the tool, and create_swarm builds the parent graph with one node per agent and the START router. SwarmState is MessagesState plus active_agent, and default_active_agent names the agent a new thread starts at. Compile with a checkpointer and the swarm remembers, per thread_id, which agent holds each conversation.

Figure 3: The swarm’s only routing of its own. Every other move is a handoff tool call.

The swarm notebook builds three agents for a music store: a general QA agent that does RAG over company documents, an NL2SQL agent over the Chinook catalogue, and an invoice agent. Each gets its own tools plus handoff tools to the other two. Two details carry over to any swarm.

The library tool carries no note. It takes no arguments. Called directly in langgraph-swarm 0.1.0, it returns the same goto, graph and update keys as the hand-built tool, and its ToolMessage says only “Successfully transferred to billing”. Whatever the next agent needs must already be in the conversation. The hand-built tool’s context argument exists to fix that.

Choosing a swarm or a supervisor

The swarm’s saving rests on the conversation staying with one specialist. When a follow-up changes topic, the active agent has to recognise that and hand off, and routing quality now lives in every agent’s prompt instead of one supervisor’s. Choose the swarm when threads stay on one specialist’s topic, and the supervisor when you need one decision log and one cap.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s support swarm sometimes takes a minute to fail. The trace shows billing and operations handing the same customer back and forth until LangGraph raises GraphRecursionError. What do you look at, and what do you change?

What a strong answer covers:

  • Reads the handoff ToolMessages and each agent’s prompt: both agents believe the other owns “outage credits”, so the ownership line is unclear
  • Fixes ownership in the agents’ prompts and handoff tool descriptions, and gives one of them the answer instead of another handoff
  • Sets recursion_limit explicitly on every run (25 in the notebooks), because the default of 10,007 steps is what made the failure take a minute
  • Adds a scripted-model test that replays the ping-pong and asserts the run ends with the error, so a prompt change cannot bring the loop back silently

2. The M30 router sends each question to one knowledge base. Customers ask “my server went down, do I get credits?” and get an answer about the outage with nothing about credits. Do you replace the router with a supervisor or a swarm?

What a strong answer covers:

  • Names the failure: a one-shot router picks one specialist, so a two-part request loses its second half
  • Supervisor: re-decides after each specialist, so it covers both halves; 5 calls for this request, with every decision in one log
  • Swarm: operations answers its part and hands off to billing; 3 calls, and follow-ups go straight to the active agent
  • Chooses by traffic shape: many multi-turn conversations with one specialist favour the swarm; audit or compliance needs favour the supervisor’s single decision log

3. Your lab brief says to compare routing accuracy and cost after replacing the router with a supervisor over three specialist RAG agents. How do you measure it?

What a strong answer covers:

  • Labels each golden question with the specialists it needs, in order, and scores the route the system took against that label
  • Logs routing outside the transcript (route_log, one entry per decision with its reason), so routing accuracy is read from state and not parsed from prose
  • Reports model calls, tokens and latency per request, split into routing calls and specialist calls, next to answer quality from the M10 baseline
  • Looks per question, not only at the mean: single-domain questions get more expensive under a supervisor while multi-part ones get correct

4. A swarm thread has active_agent = billing. Three days later the same customer writes “Can I export my data?” What happens, and what should happen?

What a strong answer covers:

  • The START router reads the saved active_agent, so billing receives a question it has no handbook section for
  • Billing needs a handoff tool to the data agent and a prompt that tells it to use it; otherwise it answers from nothing or asks the customer to repeat
  • The library handoff tool carries no note, so whatever data needs must already be in the messages; a hand-built tool can pass a context note
  • Considers expiring or resetting active_agent after a quiet period, so a new topic on an old thread starts at triage

5. Larkspur wants a human to approve any refund the billing agent offers outside the 30-day window before the customer sees it. Where does the pause go in a supervisor workflow?

What a strong answer covers:

  • Uses a checkpointer, because a paused run has to be saved and resumed by thread
  • Prefers a dynamic interrupt(payload) inside the billing node, so only out-of-window refunds pause; a static interrupt_after pauses every run
  • Lets the reviewer edit state (update_state) or resume with Command(resume=...), then sends the edited answer, not the model’s
  • Checks the window in code from the purchase date, so the decision to pause never rests on the model’s judgement

Key Takeaways

  • Split one agent only when its tools or sources are too many to choose among well, and measure the team against the single agent on the same requests.
  • Let the model choose the next agent, and let a pure function in code read that typed choice and a counter. The loop ends where the code says, whatever the model says.
  • A supervisor pays a routing call per specialist plus one to finish; a swarm pays one routing call per thread and then follows active_agent. Pick by whether conversations stay with one specialist and whether you need one decision log.
  • Pass recursion_limit on every run and add a counter cap to any graph that can cycle; test both with a stub or scripted model.
