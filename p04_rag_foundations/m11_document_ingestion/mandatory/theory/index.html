M11 Document ingestion and metadata design

Retrieval can only return text that ingestion extracted, labelled with metadata that ingestion attached. M11 rests on four ideas: what a loader does compared with a parser, why element-level parsing matters for PDFs, how to design a metadata schema before you need it, and why loaders should stream.

One PDF page, three parsers
Open the lab

The running example is page 7 of the Larkspur Cloud customer handbook: two columns, a pricing table, a refund section, a header and a footer.

TL;DR

  • Every loader returns Document(page_content, metadata). page_content is embedded and shown to the model; metadata is never embedded, and it is the only thing you can filter on exactly.
  • A loader gets bytes from a source; a parser turns those bytes into text and structure. Which parser you choose decides what the index can contain.
  • Element-level parsing gives one typed Document per title, paragraph, table or list item, so you can drop boilerplate, keep tables whole and tag every chunk with its section.
  • Design the metadata schema for the filters, citations and access rules you will need later. Adding a field after indexing means re-ingesting the corpus, and every loader names its fields differently (page counts from 0 in PyPDF, seq_num from 1 in JSONLoader), so map them onto the schema at load time.
  • Implement lazy_load so a large source streams through the pipeline instead of loading into memory at once.

Mental model

Loading is lossy. A PDF parser drops layout, an HTML loader drops visual hierarchy, a Word loader drops comments, and a CSV loader drops column types. Know what each loader drops; you cannot retrieve what was never extracted.

M10 put Load first in the lifecycle and measured a baseline that every later change must beat. This module opens that first step, because retrieval can only return text that ingestion extracted, labelled with metadata that ingestion attached.

Larkspur’s assistant answers a refund question from page 7 of the customer handbook PDF. The answer is right, but the chunk behind it starts with the page header “Larkspur Cloud · Customer Handbook”, carries no section name and no policy date, and its page number counts from 0. The assistant cannot say which version of the policy it quoted, and its citation points one page early.

Every loader returns the same shape: a Document, with page_content (the text that gets embedded and shown to the model) and metadata (a dictionary that is never embedded). People say “loader” for the whole step that produces Documents, but LangChain separates two jobs:

Loader Parser
Job Find and fetch the source, yield Documents Turn raw bytes into text and structure
LangChain type BaseLoader (load, lazy_load) BaseBlobParser (lazy_parse(blob))
Examples PyPDFLoader, DirectoryLoader, WebBaseLoader, your own BaseLoader PyPDFParser, PyMuPDFParser, Unstructured’s partition_pdf
What it decides Where documents come from, how many per file What text is extracted, in what order, with what structure

Table 1: The two jobs inside “loading”.

Most built-in loaders bundle both: PyPDFLoader fetches the file and runs pypdf on it. GenericLoader keeps them apart, a blob loader plus a parser, which lets one parser read from a folder, a bucket or an API without new code:

Figure 1: A bundled loader and a composed one. Only the parser box changes the extracted text.

When someone says “the PDF loader is bad”, they usually mean the parser extracts the wrong text. Swapping the parser fixes that. Changing how files are fetched does not, and we call that attempt a fetch-side fix: work on the layer that was never the problem.

Metadata schema

Metadata answers questions about a chunk that similarity search cannot: where it came from, who may see it, how recent it is, what kind of content it is. A metadata schema is the fixed list of fields, with their meanings and types, that every Document must carry. It has to exist before ingestion, because every field you forget costs a full re-ingest to add.

Plan four kinds of field:

Kind Examples Enables
Provenance source, page, row, loader, ingested_at Citations, debugging, re-ingesting one file
Filtering doc_type, section, date, language, version Narrowing the search before similarity
Access control tenant_id, visibility, owner Multi-tenant isolation; never optional
Quality extraction_method, confidence, verified Excluding low-quality text, audits

Table 2: Four kinds of metadata field, and what each makes possible.

The filtering and access fields run before similarity search. A question then only competes against chunks it is allowed to see:

Figure 2: A metadata pre-filter narrows the index before similarity search runs.

The M11 lab asks for one shared schema across PDF, DOCX, Markdown, CSV and a web page, with five fields: source, type, section, page, date. On the handbook page, the loaders fill different parts of it:

Loader Fields it fills Fields you supply
PyPDF source, page, date type, section
Unstructured, element mode source, type, section (via parent_id), page date

Table 3: How much of the lab’s five-field schema each PDF loader fills on the handbook page.

A filled field can still be wrong for your purpose. The file’s modification time is not the policy date. Take date from your CMS.

Three hard constraints shape the design, and each has a failure we name:

Constraint What goes wrong Guard
Metadata is not embedded Invisible title: a title that lives only in metadata never matches a query Put fields that should affect similarity into the text too (M15’s contextual chunk headers do this)
Value types are restricted Chroma 1.5, the version this course installs, accepts str, int, float, bool, None and non-empty lists of one of those types. A nested dict, an empty list or a mixed list such as [1, "x"] fails the write Flatten values before you index
Filters match exactly Case-split filter: {"department": "Engineering"} does not match "engineering", and the filter returns nothing Normalise values when you load

Table 4: Three constraints on metadata, the failure each one causes and its guard.

In practice: a schema for the Larkspur handbook

For the refund chunk in the opening example, the schema decisions come before the first load:

  1. Choose the parser for the layout. Page 7 has two columns and a pricing table. An element-level parser (lesson 11.4) is worth its cost there, and it also separates the page header from the text.
  2. Fill provenance on every Document. source is the file, page is stored 1-based so citations match the printed page.
  3. Supply what the parser cannot. type comes from the route that loaded the file, date from the CMS record of the policy.
  4. Keep the section in two places. As metadata for filtering, and as a short header in the chunk text so a question that names “Refunds” can match it.

Next: lesson 11.2 starts with the simplest sources, plain text and Markdown, where the single choice is whether one file becomes one Document or many.

Key Takeaways

  • A loader fetches the source and a parser turns bytes into text. When the extracted text is wrong, swap the parser.
  • Design the metadata schema before ingestion: provenance, filtering, access control and quality fields. Every forgotten field costs a full re-ingest.
  • Metadata is not embedded, accepts only flat value types, and filters match exactly. Put fields that should affect similarity into the text, flatten values and normalise case.

Check yourself

1. A teammate says the PDF loader is bad because the extracted text comes out wrong. Do you change the loader or the parser?

The parser. The loader decides where documents come from and how many there are per file. The parser decides what text is extracted, in what order and with what structure. Changing how files are fetched is a fetch-side fix, and GenericLoader lets you swap the parser without touching the fetching.

2. You load the handbook page with PyPDF for the lab's five-field schema. Which fields does it fill, and which must you supply yourself?

PyPDF fills source, page and date, so you supply type and section. Unstructured would fill section through parent_id. Even a filled field can be wrong for your purpose: take date from your CMS rather than the file’s modification time.

3. You store each document's title only in metadata, and questions that name the title never retrieve its chunks. What went wrong?

Metadata is not embedded, so a title that lives only there never matches a query. If a field should affect similarity, also put it into the chunk text, which is what M15’s contextual chunk headers do. Keep it in metadata as well when you want to filter on it.

Single mode and element mode

Lesson 11.2: Plain text and Markdown (single vs element mode). Notebooks: 02a_text_loader.ipynb (optional), 02b_markdown_loader.ipynb (optional)

What you’ll learn

Lesson 11.1 defined the Document and the schema it should carry. Plain text and Markdown are the simplest sources: there is no layout to recover. The main decision is how many Documents one file becomes.

The Larkspur handbook ships as 13 Markdown files. Loaded with the plain text loader, the refunds page becomes one Document of 660 characters that begins with “# Refunds”. Its five rules (monthly plans, the 30-day window, proration, the 5 to 10 business days, how to request) sit in one string, and nothing records that they belong under the Refunds heading. The splitter in M12 will cut that string without knowing where the sections were.

We loaded the refunds page three ways. The plain text loader reads the file as it is. The Unstructured Markdown loader parses the Markdown first, and its mode setting decides the output: single mode returns the whole file as one Document, and element mode returns one Document per element (a title, a paragraph, a list item, a table), each tagged with a category:

Loader Documents Text Metadata keys
Plain text loader 1 660 characters, starting “# Refunds”, Markdown marks kept source
Markdown loader, single mode 1 657 characters, starting “Refunds”, heading mark removed source
Markdown loader, element mode 6: 1 Title, 5 NarrativeText “Refunds”, then one Document per paragraph, 106 to 152 characters each source, category, parent_id, element_id, filename, filetype, languages, last_modified, file_directory

Table 1: The refunds page through three loaders (unstructured 0.27.37, langchain-community 0.4.2, run on data/larkspur/handbook/02_refunds.md).

In element mode, every paragraph’s parent_id points at the Title element above it:

Figure 1: One file, two modes. Element mode keeps the link from each paragraph to its heading.

That link is what fills the section field of lesson 11.1’s schema. Single mode loses it before splitting even starts, and we call that a one-blob file: a file reduced to one string, its structure gone. The plain text loader has a second effect, markup in the embedding: heading marks and table pipes stay in the text and get embedded with it unless a later step removes them.

Notebook 02b runs the same loaders on a different file, the LangChain README in data/sample/, and its counts differ from these. It also calls Unstructured’s own partitioner directly, which returns Unstructured elements rather than LangChain Documents; converting them copies each element’s text and metadata into a Document.

The two tables are where the mode matters most. Each Table element has a flat text form and an HTML form. The plain text loader is still the right choice in one case. A Markdown-aware splitter (M12) cuts on the heading marks and needs them in the text:

The raw Markdown, for a splitter that cuts on headings Plain text loader

In practice: loading the Larkspur handbook

For the handbook, element mode does the most work at load time:

  1. Load each file in element mode. The 13 files give 78 elements.
  2. Fill section from parent_id. Each paragraph takes the text of its Title: the refunds rules carry “Refunds”.
  3. Keep the two Table elements whole, in their HTML form, so the server sizes keep their column names.
  4. Hand the rest to the splitter (M12) with section attached, and put the section name into the chunk text as well, since metadata is not embedded.

Next: lesson 11.3 moves to sources that already come in records, CSV rows and JSON objects, where the choice is which record becomes one Document.

Key Takeaways

  • Single mode gives one Document per file. Element mode gives one per title, paragraph, list item or table, each with a category and a parent_id that links it to its heading.
  • The plain text loader keeps Markdown marks in the text. That suits a heading-aware splitter, and puts markup into the embedding when nothing strips it.
  • Keep each Table element as one piece in its HTML form, so values stay under their column names.

Check yourself

1. What does element mode return for the Larkspur refunds page, and how does each paragraph know its section?

Six Documents: one Title (“Refunds”) and five NarrativeText paragraphs of 106 to 152 characters. Each paragraph’s parent_id points at the Title element, which is what fills the section field of the schema. Single mode returns one Document and loses that link.

2. The plain text loader keeps the heading marks in the text. When is that what you want?

When the next step is a Markdown-aware splitter (M12), because it cuts the text on those heading marks. If the text goes to the embedding model without such a splitter, the marks and table pipes are embedded with it, which is markup in the embedding.

3. The server-size table on the plans page loads as a Table element. Why keep its HTML form instead of its flat text?

The flat text runs the header and the rows together (“Size vCPUs Memory … Medium 4 16 GB …”). Once a splitter cuts it, “16 GB” no longer sits under a column name. The HTML form keeps rows and columns, so keep the table as one piece and give the model that form.

One record, one Document

What you’ll learn

Lesson 11.2 loaded Markdown, where the question was how many Documents a file becomes. A CSV or JSON file already has records. The loader’s job is to decide which record becomes one Document. That choice sets the smallest thing retrieval can return, the same way element-level parsing does for a PDF (lesson 11.4).

Larkspur exports the handbook’s plan table as plans.csv so the assistant can answer How much memory does the Business plan have? A teammate moves the plan name and price into metadata to make them filterable. The question stops retrieving the Business row, because the word “Business” is no longer in any text that gets embedded.

The CSV loader makes one Document per row. Each line of page_content is column: value, and metadata gets the file and the row number, counted from 0. plans.csv gives three Documents. The Business row:

Part Value
page_content Five lines: plan: Business, vcpu: 4, memory_gb: 16, traffic_tb: 5, price_usd: 48
metadata source: plans.csv, row: 1

Table 1: The Business row of plans.csv as a Document, with default settings.

The Unstructured CSV loader goes the other way and returns the whole file as one table Document. Use it when the question is about the table as a whole. Use the row loader when each row answers a question on its own, as the Business memory question does.

The JSON loader has no fixed record. A jq schema is a path expression that says where one Document starts, and the notebook’s chat_data.json shows how much it decides:

jq schema Documents Each Document holds
. 1 The whole file as JSON text, 1,612 characters
.messages[] 11 One message object as JSON text, keys included
.messages[].content 11 One message’s text; one of them is empty, because a photo message has no content

Table 2: Three jq schemas on the same chat export.

The empty Document is the failure to watch for here, and we call it an empty record. A jq path that misses on some records still yields a Document for them, with empty page_content, and it gets embedded like any other. Count empty Documents after every load. For JSON Lines files, a flag runs the schema once per line.

Content fields and metadata fields

Every column or key ends up in one of three places: the embedded text, the metadata, or both. Text is what similarity search can match, and metadata is what a filter can match exactly (lesson 11.1). Decide per field:

Figure 1: One row split into embedded text and metadata. plan is listed on both sides: it can be matched and filtered.

The CSV loader takes three settings for this: content_columns, metadata_columns and source_column. Its defaults hold three traps, and all three show up on plans.csv. One more comes from the notebook’s own data:

Setting What happened Name Guard
metadata_columns = plan, price, no content_columns The Business text became vcpu: 4, memory_gb: 16, traffic_tb: 5; “Business” is gone from the embedding Text-stripped column List plan in content_columns too, so it lands in both places
Any metadata column The price reads as the string '48'; a filter for “plans under $50” compares numbers String numbers Cast numeric fields to int or float at load time
source_column = plan The metadata says source: Business, and nothing records which file the row came from Lost file path Keep the file path in its own field
Renamed fieldnames on a file that has a header The five-row data.csv loads as six Documents; the first reads Property ID: Property_ID Header-as-row Rename the columns in the file, or drop the first Document

Table 3: Four CSV loader settings, the failure each caused and its guard.

The JSON loader splits the same decision across two arguments. content_key names the field that becomes page_content, and a metadata function copies the fields you want to filter on. The notebook copies sender_name and timestamp_ms, so a query can ask for one person’s messages in a time range.

The two loaders also disagree on provenance. The JSON loader stores source as an absolute path and counts seq_num from 1. The CSV loader writes source as you passed it and counts row from 0. Lesson 11.5 maps these differences onto one schema.

In practice: plans.csv for the Larkspur assistant

To answer both How much memory does Business have? and Which plans cost under $50? from the same file:

  1. One Document per row, so each plan can be retrieved on its own.
  2. plan in both the text and the metadata, so it can be matched by similarity and filtered exactly.
  3. price_usd cast to a number in metadata, for range filters.
  4. source kept as the file path, with row beside it, so a citation can open the right file at the right row.
  5. Count empty Documents after the load, which catches a column or jq path that missed.

Next: lesson 11.4 returns to files with layout, PDFs and Word documents, where the parser decides what text exists at all.

Key Takeaways

  • For CSV and JSON, decide which record becomes one Document: the CSV loader gives one per row, and the jq schema sets the record for the JSON loader. Count empty Documents after every load.
  • Decide per field whether it goes in the embedded text, the metadata or both. A column listed only in metadata_columns disappears from the text.
  • Loader metadata values arrive as strings and source_column overwrites the file path. Cast numbers and keep the file path in its own field.

Check yourself

1. What does the jq schema passed to the JSON loader decide, and why does it matter for retrieval?

It decides where one Document starts, and so the smallest thing retrieval can return. On chat_data.json, . gives one Document of 1,612 characters, while .messages[] gives 11, one per message. A path that misses on some records still yields an empty Document, so count empty Documents after every load.

2. You load plans.csv with metadata columns set to plan and price and no content columns. What text gets embedded for the Business row, and what breaks?

The text becomes vcpu: 4, memory_gb: 16 and traffic_tb: 5, because metadata_columns alone removes those columns from the text. The word “Business” is gone from the embedding, so a question about the Business plan cannot match it. List plan in content_columns too, and cast price_usd to int, since it stays the string '48'.

3. A five-row CSV loads as six Documents, and the first one reads Property ID: Property_ID. What caused it?

The loader was given new fieldnames to rename columns on a file that already has a header row, so the header was read as a data row. Rename the columns in the file instead, or drop that first Document.

Element-level parsing

What you’ll learn

Lesson 11.3 picked records out of CSV and JSON, where the structure was already in the file. A PDF stores positioned text on a page. The parser has to rebuild the structure, and how much it rebuilds decides what the index can contain.

A customer asks the Larkspur assistant Which plan has 16 GB of memory? Page 7 of the handbook PDF holds the answer in its pricing table. The page was loaded as plain text and then split, and the chunk that reaches the model reads “Business 4 16 GB 5 TB $48”: the values are there, but the column names stayed in another chunk. The model cannot tell which number is the memory.

A page-level parser returns the page as one string. An element-level parser (Unstructured, in element mode) returns one Document per layout element, each with a category such as Title, NarrativeText, Table, ListItem, Header or Footer:

*Figure 1: The same handbook page as one page-level string and as one typed Document per region, each linked to its section title.

Here is what the three PDF loaders in the notebook produce from the handbook page:

PyPDFLoader PyMuPDFLoader UnstructuredPDFLoader, element mode, hi_res
Documents from the page 1 1 10
Header and footer Inside the text Inside the text Separate elements you can drop
Pricing table Rows of space-separated values One cell per line Table element with an HTML form
Section of each piece Unknown Unknown parent_id points to its Title

Table 1: Three PDF loaders on page 7 of the Larkspur handbook.

The comparison has three consequences for retrieval, two of them failures we name:

  • Boilerplate echo. If every chunk starts with “Larkspur Cloud · Customer Handbook”, every chunk shares that text, and similarity between chunks from different pages rises. Drop Header and Footer elements, or strip repeated lines from page-level text.
  • Orphaned cell. “Business 4 16 GB 5 TB $48” can be read, but once a splitter cuts the table, “16 GB” no longer has a column name. This is the failure in the opening example. Keep a table as one chunk and give the model its HTML or Markdown form.
  • Granularity is decided at load time. One Document per file, page, row or element sets the smallest thing retrieval can return, and changing it later means re-ingesting.

The interactive lab puts the handbook page through all three loaders. Hover a Document to see which part of the page it came from, and read how many of the five schema fields each loader fills: three for PyPDF and PyMuPDF, four for Unstructured.

Choosing a parser

Element-level parsing costs time and dependencies. It pays only where layout carries meaning. A short chain of questions settles most documents:

The licence row of Table 1 matters as well: PyMuPDF is the fastest, but its AGPL licence can rule it out for a product you ship.

Word and Markdown files have the same switch. In the Word notebook, the Unstructured Word loader returns the file as one Document by default. In practice: page 7 of the Larkspur handbook

For the handbook PDF, the parser choice follows the page:

  1. Route page 7 to element-level parsing, because it has two columns and a pricing table.
  2. Drop the Header and Footer elements, which removes the boilerplate echo from every chunk.
  3. Keep the Table element whole, in its HTML form, so “16 GB” stays under “Memory”.
  4. Fill section from parent_id and store the page as 1-based, matching lesson 11.1’s schema.
  5. Send plain prose pages to PyPDF, which is faster and needs no system packages.

Key Takeaways

  • Element-level parsing returns one Document per layout element with a category, so headers and footers can be dropped and each piece knows its section.
  • Drop repeated boilerplate before embedding, and keep each table as one chunk in HTML or Markdown form so values keep their column names.
  • Granularity is fixed at load time. Use element-level parsing for reports, manuals, forms and tables. Plain prose PDFs do fine with PyPDF or PyMuPDF.

Check yourself

1. Why does leaving the handbook's page header in every chunk hurt retrieval?

If every chunk starts with “Larkspur Cloud · Customer Handbook”, every chunk shares that text, and similarity between chunks from different pages rises. This is boilerplate echo. An element-level parser returns Header and Footer as separate elements you can drop. With page-level text, strip the repeated lines instead.

2. The pricing table was loaded with PyPDFLoader and then split. Why can a question about which plan has 16 GB of memory fail, and what would Unstructured give instead?

PyPDF flattens the table into rows of space-separated values, and once a splitter cuts a row, “16 GB” no longer has a column name: an orphaned cell. The Unstructured PDF loader in element mode with hi_res returns the table as one Table element with an HTML form. Keep it as one chunk and give the model its HTML or Markdown form.

3. Your corpus is plain prose PDFs with no tables or forms. Should you switch everything to element-level parsing?

No. Element-level parsing is the slowest option and needs layout models and system packages, and plain prose PDFs do fine with PyPDF or PyMuPDF. Use it where layout carries meaning: reports, manuals, forms, anything with tables. Choose before you ingest, because changing granularity later means re-ingesting.

Lessons 11.2 to 11.4 loaded one kind of file at a time. A real corpus arrives as a mixed folder, plus sources that are not files at all.

Larkspur’s nightly ingestion job loads a folder of handbook material and reports success. A week later, a customer’s question about the onboarding guide gets no answer: the DOCX failed to parse on the first night, the job skipped it, and the only record is a line in a log nobody reads. We call this a silent skip.

The M11 lab asks for exactly this kind of folder: the handbook as PDF, the onboarding guide as DOCX, release notes in Markdown, plans.csv and the status page from the web. The directory loader loads a folder with one loader class per file type. The notebook builds one directory loader per extension, each with its own file pattern, loader class and loader settings, because the default loader class is the generic Unstructured file loader for everything.

Two defaults matter on a real folder:

  • Stop on error, or skip. By default the whole run stops at the first file that fails to parse. A nightly job usually turns on silent errors to keep going. Then compare the number of files with the number of distinct source values after every run, because a skipped file only shows up in the log.
  • Progress and threads are off by default. Turn them on for folders of thousands of files. The default concurrency is 4.

Loading the folder is the easy half. Each loader writes its own metadata, with its own key names and counting rules. This is what each one sets, in langchain-community 0.4.2, run on files in this repo’s data/sample/ (the last three read from the loader source, since they need the network):

PyMuPDFLoader page source, page (0-based), total_pages, producer, creationdate, moddate, plus file_path, format, title, author and the dates again in PDF format (creationDate, modDate); no page_label
CSVLoader row source as you passed it, row (0-based)

Table 2: The mapping rule for each of the five schema fields.

The mapping drops the fields a loader did not set instead of storing None, so a filter on page only ever meets numbers. section stays missing on routes that use a page-level parser, because only an element-level parser can fill it.

Web pages, transcripts and papers

Remote sources fail more quietly than files, because the loader returns whatever the server sent.

Web pages. The recursive URL loader crawls from a root URL to a depth of 2 by default and stays under that root. Without an extractor, page_content is the raw HTML: tags, scripts and navigation menus get embedded. The URL notebook passes a BeautifulSoup extractor to keep only the text. Two failures come from its defaults:

Default What gets indexed Name Guard
Response status not checked A 404 page becomes a Document holding the error page’s text Indexed error page Turn the status check on
HTML fetched, JavaScript not run A page that renders in the browser comes back as a near-empty shell Empty shell Flag Documents whose text is much shorter than the HTML they came from

Table 3: Two web-loader defaults and the failure each one causes.

YouTube transcripts. By default the YouTube loader returns one Document per video, with the video id as source. In chunked transcript mode it returns one Document per time window (120 seconds by default; the notebook uses 10 and 15), and each source becomes the video URL with a start time, so a citation opens the video at that moment. Adding the video’s title and author needs another network call, which is where the notebook’s SSL errors come from.

arXiv papers. The arXiv loader downloads each matching PDF, reads it with PyMuPDF, and joins every page into one Document. The page numbers are lost. A citation can name the paper but not the page. Published holds the date of the latest version, not the first submission. The loader fetches up to 100 papers by default, and it can return only the abstracts, which is often enough for a “find me papers about X” index and far cheaper to embed.

In practice: the Larkspur nightly job

For the lab’s mixed folder, the nightly job runs in this order:

  1. Route by extension: PDF to the element-level parser for layout pages (lesson 11.4), DOCX to the Word loader, Markdown in element mode (lesson 11.2), CSV by row (lesson 11.3).
  2. Load the status page with an extractor and the status check on, and flag it if its text is much shorter than its HTML.
  3. Map every Document onto the five-field schema before splitting, dropping unset fields.
  4. Count files against distinct source values. Five files in, five sources out, or the run fails loudly instead of skipping silently.

Key Takeaways

  • Route each file type in a mixed folder to its own loader. With silent errors on, compare the file count with the distinct source values to catch skipped files.
  • Every loader writes different metadata keys and counting rules. Map them onto one schema right after loading, and drop unset fields instead of storing None.
  • Remote sources fail quietly. Pass an extractor for web pages, check the response status, and flag pages whose text is much shorter than their HTML.

Check yourself

1. Why map every loader's metadata onto one schema right after loading, before splitting?

Each loader writes its own keys with its own counting rules: the PyPDF loader counts page from 0, the CSV loader counts row from 0, the JSON loader counts seq_num from 1, and the arXiv loader sets no source. One mapping gives every later stage one shape, with page always 1-based, date always ISO and source always something a reader can open. Dropping unset fields instead of storing None means a filter on page only ever meets numbers.

2. A nightly directory-loader job runs with silent errors turned on and reports success. How do you check that no file was skipped?

Compare the number of files in the folder with the number of distinct source values in the loaded Documents. With silent errors on, a file that fails to parse only shows up in the log, which is a silent skip. With the default setting, the whole run stops at the first failure instead.

3. A web crawl indexes a 404 error page, and a page that renders in the browser comes back almost empty. What causes each?

The recursive URL loader does not check the response status by default. Error responses become Documents and get indexed. Turn the check on. The loader fetches HTML and does not run JavaScript, so a browser-rendered page comes back as an empty shell. Flag Documents whose text is much shorter than the HTML they came from.

Lazy loading

Lesson 11.6: Custom loaders with lazy loading. Notebooks: 06a_custom_loader.ipynb

What you’ll learn

  • Explain the difference between loading a corpus as a list and streaming it from a generator.
  • Design a custom loader for a source no library covers, with the module’s schema in every Document.
  • Diagnose an ingestion job that grows in memory and indexes nothing.
  • Apply a checkpoint so a crashed run resumes instead of starting over.

Lesson 11.5 loaded files and web sources with loaders that already exist. Larkspur’s support tickets live behind its own paginated API. No library loader covers them, and we write one.

The first version builds a list of every ticket and returns it. On the million-ticket backfill, the job’s memory grows for hours, the machine kills it, and the index holds nothing, because no Document could be split or embedded until the whole list was complete. We call this a load-all stall.

A loader has two methods. load() returns a list: the whole corpus sits in memory before anything else runs. lazy_load() is a generator: it yields one Document at a time, and the pipeline can split, embed and upsert in batches while the loader keeps reading.

The custom loader in this lesson, a ticket loader, implements only lazy_load(). It walks the API page by page from a since date and yields one Document per ticket, already in the module’s schema:

Document field Filled from
page_content The ticket body
source ticket: followed by the ticket id
type The fixed value ticket
date The ticket’s updated_at
tenant_id The customer’s organisation, for access control (lesson 11.1)

Table 1: What the ticket loader puts in each Document.

BaseLoader derives load() from lazy_load(). Implementing the generator gives you both methods. The indexer pulls Documents one at a time and sends batches downstream:

Figure 1: Lazy loading. Embedding starts with the first batch while the loader is still reading.

The memory difference is a matter of what is held at once. With an assumed average of 2 KB of text per ticket:

load() lazy_load(), batches of 100 chunks
Held in memory at the peak All 1,000,000 tickets, about 2 GB of text before any Python overhead One batch of 100 chunks, about 200 KB
First vectors reach the index After the last ticket is read After the first batch
Lost on a crash at ticket 900,000 Everything The current batch, if a checkpoint was recorded

Table 2: Load all versus stream, for the million-ticket backfill (illustrative: 2 KB per ticket and per chunk are assumptions).

A failure part-way through only loses the current batch as long as you record a checkpoint: the last id or updated_at written to the index. The loader’s since argument goes straight to the API, so a restart begins from the checkpoint instead of the first ticket.

In practice: the Larkspur ticket backfill

For the backfill and the nightly updates after it, the ticket loader runs in four steps:

  1. Implement lazy_load() only, yielding one Document per ticket in the module’s schema, with tenant_id filled.
  2. Batch downstream: split each Document, collect 100 chunks, embed and upsert them.
  3. Record a checkpoint after each batch is stored: the last updated_at written.
  4. Pass the checkpoint as since on the next run. The nightly job then reads only tickets changed since the last one.

Key Takeaways

  • load() holds the whole corpus in memory as a list, while lazy_load() yields one Document at a time so splitting and upserting run in batches alongside reading.
  • Implement lazy_load() in a custom BaseLoader. load() comes free from it.
  • Record a checkpoint, such as the last id or updated_at written, so a crash loses only the current batch and the next run can resume from there.

Check yourself

1. With lazy loading, why do the first vectors reach the index before the loader has finished reading the source?

lazy_load() is a generator that yields one Document at a time. The indexer splits each one, adds it to a batch, and sends each batch of 100 chunks to be embedded and upserted while the loader keeps reading. With load(), nothing else runs until the whole corpus sits in memory as a list.

2. The ticket loader ingests a million tickets and crashes part-way through. How much work is lost, and what lets you resume?

Only the current batch, as long as you record a checkpoint: the last id or updated_at written. The loader takes a since argument and passes it to the paginated API, so a restart can begin from the checkpoint instead of the first ticket.

3. A teammate writes a custom loader that overrides load and builds a list of every record. Which method should they implement instead?

lazy_load(), as a generator. BaseLoader derives load() from lazy_load(), so the generator gives them both methods. A list keeps the whole corpus in memory, which a million-record source cannot afford, and nothing reaches the index until it is complete: a load-all stall.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. A customer uploads 4,000 product manuals as PDFs: two-column layouts, spec tables, scanned appendices. You have a week to make them searchable. How do you choose a parsing approach?

What a strong answer covers:

  • Samples 20 to 30 pages of each layout type and compares parser output side by side before choosing
  • Uses element-level parsing (or a layout model) for tables and multi-column pages, and a fast text parser for plain prose; routes by document type
  • Detects scanned pages (empty or near-empty text layer) and sends only those to OCR
  • Sets acceptance checks: no empty Documents, tables kept whole, page numbers that match the printed page

2. Users report that the assistant cites “page 6” when the answer is on page 7. What happened, and how do you fix it for existing data?

What a strong answer covers:

  • PyPDF and PyMuPDF page metadata is 0-based; the citation code shows it raw
  • Fixes it at the presentation layer at once (page + 1, or prefer page_label), so no re-index is needed
  • Normalises to one 1-based page field in the schema for future ingests, and documents it
  • Adds a citation test to the golden set: question, expected source and expected page

3. You run a multi-tenant RAG product. Should tenant isolation be a metadata filter in one shared index, or one index per tenant?

What a strong answer covers:

  • A shared index with a tenant_id filter is cheaper to run but depends on every query path applying the filter
  • Per-tenant indexes (or namespaces) make cross-tenant leaks structurally impossible and simplify deletion, at operational cost
  • Whatever the choice, the filter comes from the authenticated session, never from the user’s text or the model
  • Tests for leaks with canary documents and a cross-tenant query suite on every release

4. Ingestion runs nightly over a document store. How do you know it is silently degrading?

What a strong answer covers:

  • Tracks per-run counts by source and type: files seen, Documents produced, empty or tiny Documents, parse errors
  • Alerts on distribution shifts, such as average characters per page dropping (a new scanned batch) or a type disappearing
  • Remembers that many loaders fail quietly (silent_errors=True, empty text from scans, JS-rendered pages) and checks their output explicitly
  • Samples parsed Documents for human or LLM review, and re-runs the golden set after big ingests

5. Your custom loader pulls 2 million support tickets from an API. It crashes at 1.4 million with an out-of-memory error. What changes?

What a strong answer covers:

  • Implements lazy_load as a generator and calls it from the indexer instead of load()
  • Splits, embeds and upserts in fixed-size batches so memory stays flat
  • Checkpoints the last updated_at or id written, so a restart resumes instead of starting over
  • Makes upserts idempotent with stable ids (ticket:{id}), so a retried batch does not create duplicates

Key Takeaways

  • page_content is what gets embedded; metadata is what you filter and cite by, and it is never embedded.
  • Choose the parser by what the documents contain. Element-level parsing keeps structure and costs speed.
  • Write the metadata schema down before the first ingest, including access control, and normalise values at load time.
  • Stream with lazy_load, batch the downstream work, and validate counts after every run.
