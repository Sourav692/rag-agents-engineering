M10 The RAG lifecycle

A language model answers from what it memorised during training. RAG adds a second source: passages retrieved from your own documents at the moment the question arrives. The M10 notebooks build on four ideas: where knowledge lives, the stages of the pipeline, how many chunks to retrieve, and why you measure a baseline before you optimise anything.

Open the lab

The running example throughout these pages and the lab is a small product handbook for a fictional cloud host, Larkspur Cloud. M11 and M12 reuse the same handbook.

TL;DR

  • RAG moves knowledge out of model weights (parametric) into an index you control (non-parametric), so you can update it, restrict it and cite it.
  • The pipeline has an offline indexing phase (load → split → embed → store) and an online query phase (retrieve → augment → generate). A mistake made at indexing time often surfaces only in the generated answer.
  • k controls how much context the model reads. It trades recall against precision, tokens and latency, and it cannot recover a chunk the retriever scores as irrelevant.
  • Embeddings match meaning where TF-IDF matches exact words. On the handbook they find the refund and outage evidence TF-IDF misses, and lose the export question TF-IDF answered at k = 2.
  • Build the plain pipeline first, record its numbers on a fixed question set, then change one stage at a time and compare.

Mental model

The index is the only thing the two phases share. A bad chunk written at indexing time is retrieved, quoted and cited at query time, and nothing in the query phase can repair it.

Parametric vs non-parametric knowledge

Lesson 10.1: The knowledge problem: hallucination, freshness, context-window growth, RAG vs fine-tuning vs long context

What you’ll learn

  • Explain the four ways knowledge stored in a model’s weights fails an application.
  • Compare RAG, fine-tuning and long context by where the knowledge lives and what an update costs.
  • Choose an approach for a fact that changes, a house style, and a corpus small enough to fit in the prompt.

Modules M06 to M09 built chains and graphs around a model. From this module on, the question is what the model knows at the moment it answers, and where that knowledge comes from.

A Larkspur Cloud customer bought an annual plan 45 days ago and asks the support assistant for a refund. With no handbook behind it, the assistant answers from memory: refunds are only available within 30 days of purchase. The handbook says otherwise. After day 30, annual refunds are prorated: the customer gets back the unused whole months, minus a 15% early-termination fee. The answer is fluent, specific and wrong, and nothing in it tells the customer to doubt it.

Parametric knowledge is what a model stores in its weights during training. It is fast and needs no infrastructure, but it fails an application in four ways:

Failure What happens Larkspur example
Stale memory Knowledge stops at the training cut-off The refund policy changed in March 2026, and no model trained before then has seen the new terms
Missing data Private data was never in the training set Larkspur’s tickets, contracts and runbooks
No source The model cannot point to where a fact came from Nobody can check the “30 days” answer against a page
Confident fabrication Asked about something it never saw, the model still writes fluent text The refund answer above, which is a hallucination

Table 1: Four ways parametric knowledge fails an application.

Non-parametric knowledge lives outside the model, in an index you build and query. RAG (retrieval-augmented generation) retrieves the passages relevant to a question and puts them in the prompt. The model then answers from evidence it can quote. Here is the same refund question answered both ways:

Figure 1: The same question answered from memory and from a retrieved handbook chunk. Only the RAG path returns a source.

The index is where an update happens. When the refund terms change, you re-index the refund page and the next answer quotes the new text, while the model’s weights stay exactly as they were.

RAG, fine-tuning and long context

There are three ways to give a model knowledge it did not learn in training, and they solve different problems. Table 2 compares them on what an application cares about:

RAG Fine-tuning Long context
Where the knowledge lives External index Model weights The prompt, every call
Updating a fact Re-index one document Retrain Edit the prompt
Citations Yes, per chunk No Possible, but nothing narrows the evidence
Cost per question Retrieval + a short prompt Cheap once trained Pays for the whole corpus in tokens
Best at Facts that change, private data, auditability Style, format, domain vocabulary, behaviour Small corpora that fit, one-off analysis
Fails when Retrieval misses the evidence Facts change after training The corpus outgrows the window, or the answer sits mid-context

Table 2: Three ways to add knowledge, compared.

Context windows have grown large enough that a small handbook fits in one prompt, which makes long context tempting. Every call then pays for every page in tokens, and nothing ranks the evidence: the model has to find the refund paragraph among the outage, export and sizing pages by itself. Lesson 10.2 shows that a passage’s position in a long prompt also changes how reliably the model uses it.

Key distinction: fine-tuning teaches behaviour, such as style, format and vocabulary. RAG supplies facts at the moment of the question. Anything that changes, or that a user must be able to check, goes on the RAG side.

The two combine well. A model fine-tuned on Larkspur’s support voice would still need retraining at every policy change. The policy itself belongs in the index. M45 covers when fine-tuning is worth its cost. The questions below give a first pass at the choice:

Figure 2: A first-pass choice between the three approaches. When you need both a house voice and current facts, combine fine-tuning with RAG.

Only the RAG row updates a single fact and returns a source. Under RAG the change needed four steps and no retraining:

  1. The policy team edits the refund page. The new text adds proration after day 30, minus the 15% early-termination fee.
  2. Re-index that page. Load it, split it, embed the new chunks and replace the old ones in the index.
  3. Ask the 45-day question again. The assistant now retrieves the proration chunk, answers from it and cites the page.
  4. Keep the question. Add it to the set of test questions, and the next policy change gets checked the same way.

Step 2 hides the core mechanism, an index that scores every chunk against a question. Lesson 10.2 builds one from scratch with TF-IDF.

Limits of this evidence

  • The March change is a scenario. The Larkspur handbook in this course holds only the current refund terms (full refund within 30 days, then proration minus 15%). The earlier policy and its date are part of the story, not a file you can open.
  • Table 2 compares properties, not measurements. No cost, latency or accuracy figure on this page was measured. Lesson 10.2 starts measuring, and lesson 10.5 turns those measurements into a baseline.
  • This lesson has no notebook. The comparison is conceptual. M45 measures what fine-tuning changes in practice.

Key Takeaways

  • Knowledge in the weights goes stale, misses private data, cannot cite a source and stays fluent when wrong. RAG answers from passages retrieved from an index you control.
  • Choose RAG for facts that change, private data and citations; fine-tuning for style, format and vocabulary; long context for small corpora that fit the window.
  • Combine the approaches when you need both: fine-tune for tone and format, retrieve for facts.

Check yourself

1. A model trained before March 2026 answers the Larkspur refund question fluently. Why can you not trust that answer?

Parametric knowledge stops at the training cut-off, and the refund policy changed in March 2026, so the answer may be stale. The model also cannot point to a source, so nobody can check it, and it writes fluent text even about what it never saw. RAG puts the current policy passage in the prompt, so the model answers from evidence it can quote.

2. The refund terms change again next month. What does updating that fact take under RAG, fine-tuning and long context?

With RAG you re-index one document. With fine-tuning you retrain. With long context you edit the prompt, but every call pays for the whole corpus in tokens.

3. Larkspur wants answers in its house tone that also state current policy with citations. Which approach fits?

Combine them: fine-tune for tone and format, retrieve for facts. Fine-tuning alone gives no citations and goes wrong when facts change after training, while RAG cites per chunk and picks up a change with a re-index. M45 covers when fine-tuning is worth it.

Top-k

Lesson 10.2: Indexing from scratch with TF-IDF and nearest neighbours. Notebooks: 02a_indexing_from_scratch.ipynb

What you’ll learn

  • Explain what top-k retrieval returns, and why those k chunks are all the model sees.
  • Measure a retriever with recall@k and precision@k against labelled evidence.
  • Diagnose whether a miss is a ranking problem a bigger k fixes, or a representation problem it cannot fix.
  • Choose k from the recall curve and the token cost of each extra chunk.

Lesson 10.1 moved knowledge out of the model and into an index. This lesson builds the smallest index that works: a vector for each of twelve Larkspur handbook chunks, and a search that finds the chunks closest to a question.

Three customers ask three questions, and the index holds both evidence chunks for each of them. At two chunks per question, the retriever finds both for the first question, one for the second and none for the third. Each miss has a different cause, and only one of the causes has anything to do with how many chunks we keep.

TF-IDF (term frequency, inverse document frequency) turns a text into a vector with one weight per word. A word gets a high weight when it is frequent in this chunk and rare across the others, and a weight of zero when the chunk does not contain it. The question gets a vector the same way, and each chunk is scored by the cosine similarity between the two vectors: 1 when they share the same words in the same proportions, 0 when they share none.

Top-k retrieval scores every chunk against the question and returns the k best:

Figure 1: Top-k retrieval. Only the k kept chunks reach the prompt.

Those k chunks are all the model sees. To judge them we need a golden set: questions whose evidence chunks someone has labelled by hand. Two metrics compare the top k with that label:

Metric How it is computed What it answers
Recall@k Evidence chunks in the top k, divided by all evidence chunks for the question Did the model receive everything it needs?
Precision@k Evidence chunks in the top k, divided by k How much of what it read was evidence?

Table 1: The two retrieval metrics used throughout this module.

The interactive lab indexes the twelve chunks with real TF-IDF (the same weighting scikit-learn uses, English stop words removed) and scores three golden questions, each with two evidence chunks. Its numbers, with R for recall and P for precision:

Table 2: Recall and precision at four values of k, from the lab. A chunk that scores 0 never counts as found, even when a large k includes it. Tokens use the four-characters-per-token rule of thumb.

Each question fails in its own way:

  • Ranking problem (export): both evidence chunks score above zero, and k = 2 retrieves them. Past that, each extra chunk is noise. Precision falls from 1.00 to 0.17 while the prompt grows almost sixfold.
  • Word-form miss (refund): the refund-timing chunk says “Refunds” and the question says “refund”. TF-IDF matches exact tokens, so that chunk scores 0 and no k retrieves it. Meanwhile reboot scores 0.194, because both it and the question contain “does”.
  • Vocabulary gap (outage): the evidence talks about “outage” and “availability”, and the question says “server goes down”. TF-IDF ranks reboot and sizing first because they contain “server”. Embeddings (lesson 10.3, M13) and query rewriting (M17) close this gap, while a bigger k only adds noise.

A larger k fixes only the first kind. The other two are representation problems: the chunk scores zero, and no cut-off below the twelfth place can bring it in.

What an extra chunk costs

Raising k has costs beyond tokens. Every extra chunk adds latency and gives the model more text it can misread. Long prompts also have a position effect: models use information at the start and end of the context more reliably than information in the middle [1].

Pitfall: k as a safety margin. A large k “to be safe” pays the token and latency cost on every call and still cannot retrieve a chunk that scores zero. Retrieve generously only when a reranker (M18) will trim the list before the model reads it. Retrieve tightly when chunks go straight to the model.

In practice: picking k for the Larkspur baseline

For the handbook, the choice of k comes from the lab in four steps:

  1. Sweep k from 1 to 12 for each golden question and read recall and precision at each value.
  2. Find where recall stops rising. For the export question, at k = 2.
  3. Note the flat lines. The refund and outage questions never improve. They go on the list for lesson 10.3, which changes the representation.
  4. Record the baseline at k = 2. Mean recall@2 is (1.00 + 0.50 + 0.00) / 3 = 0.50, and mean precision@2 is also 0.50. Lesson 10.5 makes this the number every later change must beat.

Limits of this evidence

  • Three questions, twelve chunks. The lab’s golden set is small enough to read by hand. Each question has two evidence chunks, so recall moves in steps of 0.50, and one question can swing the mean by a third.
  • The token row is an estimate. It divides characters by four. A real tokenizer gives other counts, though the growth with k is the same.
  • The notebook uses another corpus. Notebook 02a builds the same kind of TF-IDF index over four example sentences and returns only the nearest one, k = 1, as a cosine distance. Every number on this page comes from the lab, whose scoring follows scikit-learn’s defaults (English stop words, smoothed inverse document frequency, unit-length rows).

References

  1. Liu, N. F., et al. Lost in the Middle: How Language Models Use Long Contexts, 2023, on why the middle of a long context is used less reliably.
  2. scikit-learn, Text feature extraction, covering the TF-IDF weighting the lab reproduces.

Key Takeaways

  • Measure retrieval against labelled evidence with recall@k and precision@k. The k chunks returned are all the model ever sees.
  • A larger k fixes only ranking problems. When a chunk scores zero through a word-form miss or a vocabulary gap, change the representation instead.
  • Extra chunks cost tokens and latency, and models use the middle of a long context less reliably. Retrieve generously only when a reranker trims the list afterwards.
  • Pick k where recall stops rising on the golden set, and record that row as the baseline.

Check yourself

1. Why does no value of k let TF-IDF retrieve the refund-timing chunk for How long does a refund take?

It is a word-form miss, a representation problem. The chunk says “Refunds” and the question says “refund”, and TF-IDF matches exact tokens, so the chunk scores 0. Recall stays at 0.50 at every k, and a bigger k only adds noise.

2. For the export question, what are recall and precision at k = 2 and at k = 12, and which k do you pick?

At k = 2 recall and precision are both 1.00, for about 60 tokens of context. At k = 12 recall is still 1.00, but precision falls to 0.17 and the context grows almost sixfold, to about 348 tokens. Pick k = 2: past it every extra chunk is noise.

3. When should a pipeline retrieve generously with a large k, and when tightly?

Retrieve generously when a reranker (M18) will trim the list afterwards. Retrieve tightly when the chunks go straight to the model, because every extra chunk adds latency and text the model can misread, and models use information in the middle of a long context less reliably than at its start and end.

Embedding similarity

Lesson 10.3: Semantic retrieval with embedding similarity. Notebooks: 03a_retrieval_strategies.ipynb

What you’ll learn

  • Explain how an embedding model scores a chunk against a question by the angle between their vectors.
  • Compare embeddings with TF-IDF on the three Larkspur golden questions.
  • Diagnose why a semantic retriever can rank a related chunk above the one that holds the answer.
  • Choose a score threshold from the golden set instead of a fixed number.

Lesson 10.2 left two questions that no k could fix. The refund-timing chunk scored zero because “Refunds” is a different token from “refund”, and the outage evidence scored zero because the customer wrote “server goes down” where the handbook says “outage”. Both are representation problems: TF-IDF vectors only count shared words.

An embedding model turns a text into a fixed-length list of numbers, a vector. Texts with similar meaning get vectors that point in similar directions, even when they share no words. Retrieval with embeddings has the same shape as the TF-IDF index; only the vectors change:

Figure 1: Semantic retrieval. Chunks are embedded once at indexing time. The question is embedded when it arrives.

Each chunk is scored by the cosine of the angle between its vector and the question’s. Libraries report that comparison in one of two forms:

Quantity How it is computed Range Closer chunk
Cosine similarity The dot product of the two vectors, divided by the product of their lengths -1 to 1 Higher number
Cosine distance 1 minus the cosine similarity 0 to 2 Lower number

Table 1: Two forms of the same comparison. Notebook 03a’s nearest-neighbour search prints the distance.

When every vector has length 1, the cosine is the plain dot product. OpenAI’s embeddings come normalised that way, and sentence-transformers returns them so when asked to normalise.

The question and the chunks must go through the same model. Two models produce vectors in different spaces, so the cosine between a vector from one and a vector from the other means nothing. We call that a space mismatch. Notebook 03a avoids it by sending both sides through one embedding function, and it follows that changing the embedding model means re-embedding the whole corpus (M13).

The three questions move in three directions:

  • Word-form miss, fixed (refund): the embedding model places “Refunds” and “refund” close together, and refund-timing, which scored 0 under TF-IDF, ranks first.
  • Vocabulary gap, narrowed (outage): both evidence chunks now reach the top three, though reboot still ranks first because rebooting a server is close in meaning to a server going down. The top three scores sit within 0.137 of each other. A small change to the question can reorder them.

Topic drift is the general weakness. Embeddings measure how close two texts are in topic, which is a different thing from whether a chunk contains the answer. The two retrievers suit different questions:

The question shares with its evidence Better retriever Larkspur example
A rare exact word: a product name, an error code TF-IDF “export”
Meaning, in other words or word forms Embeddings “server goes down” for “outage”, “refund” for “Refunds”
Some of each Hybrid search (M16), then a reranker (M18) The export question, half about cancelling

Table 3: Which retriever wins, by what the question and the evidence have in common.

Hybrid search combines the two scores. A reranker reorders the candidates with a model that reads the question and each chunk together.

Pitfall: the fixed-threshold trap. Cosine scores are not probabilities. The best outage match scores 0.394, while the best export match scores 0.817 on the same model. A rule such as “drop chunks below 0.5” sends the outage question to the model with no context at all.

In practice: switching the Larkspur baseline to embeddings

Moving the handbook index from TF-IDF to embeddings takes four steps, and the last one decides whether the change stays:

  1. Re-embed all 12 chunks with one model, and send every question through the same model.
  2. Rerun the golden set at k = 2. Mean recall@2 rises from 0.50 under TF-IDF to (1.00 + 0.50 + 0.50) / 3 = 0.67. At k = 3 it reaches 1.00, against 0.50 for TF-IDF.
  3. Check every question, not only the mean. The export question fell from 1.00 to 0.50 at k = 2. Lesson 10.5’s rule keeps a change only when it breaks nothing. This one needs k = 3 or hybrid search before it can become the baseline.
  4. Set any score threshold from the golden set. It has to sit below 0.394, the outage question’s best match, and it has to be re-checked whenever the model changes.

Lesson 10.4 replaces the hand-built index with a LangChain vector store, which keeps the embedding model and runs the search for you.

Limits of this evidence

  • A stand-in model. Every score on this page comes from all-MiniLM-L6-v2, run locally on the lab’s 12 chunks. Notebook 03a uses OpenAI’s text-embedding-3-small on its own example sentences, and its distances differ; the three directions above are this model’s, on this corpus.
  • Three questions. One export question shows topic drift. It does not tell you how often embeddings lose to TF-IDF on a real query log, which only a larger golden set can show.
  • No threshold was tuned here. The 0.394 ceiling for a threshold comes from one question. Setting a real threshold needs many logged questions of each kind (M16).

Key Takeaways

  • Embeddings score chunks by the cosine between their vectors, which lets paraphrases and word forms match. Embed questions and chunks with the same model. Changing it means re-embedding the corpus.
  • Embeddings win on paraphrase and TF-IDF wins on rare exact words such as product names or error codes. Topic closeness is not the same as containing the answer.
  • Cosine scores are not probabilities and vary by question. Set any threshold per corpus and model from the golden set.

Because the store keeps the embedding object, the question always goes through the same model as the chunks, and the space mismatch from lesson 10.3 cannot happen by accident. Distance, not similarity

Chroma ranks by distance, and its default metric is squared Euclidean (L2) distance. Lower numbers from similarity_search_with_score mean closer chunks. For vectors of length 1 the two measures are tied by distance = 2 - 2 × cosine, so L2 and cosine rank chunks in the same order. On the 12 Larkspur chunks, embedded with all-MiniLM-L6-v2 as in lesson 10.3 (langchain-chroma 1.1.0, chromadb 1.5.9):

Question Chunk Cosine (10.3) similarity_search_with_score similarity_search_with_relevance_scores
How long does a refund take? refund-timing (1st) 0.766 0.469 0.668
Can I export my data after I cancel my plan? retention (1st) 0.817 0.367 0.741
What happens if my server goes down? reboot (1st) 0.394 1.212 0.143
What happens if my server goes down? sla (3rd, evidence) 0.257 1.487 -0.051

Table 3: The same chunks scored three ways under Chroma’s default L2 space.

The relevance-score method converts L2 distance with 1 - distance / √2, which assumes a range the distances do not keep to:

Figure 2: The relevance conversion on the outage question. Any distance above √2 becomes a negative score.

The sla chunk, which holds the evidence for the outage question, gets a negative relevance score, and LangChain warns that relevance scores must be between 0 and 1. A retriever with a similarity-score threshold of 0.2 returns no chunks at all for the outage question, although all three top chunks have a cosine above 0.25. We call this a metric mismatch: a threshold written for one scale applied to scores from another.

Pitfall: metric mismatch. Choose the metric when you create the collection, by setting its HNSW space to cosine in the collection metadata. Then similarity_search_with_score returns 1 - cosine (0.606 for reboot), the relevance score is the cosine itself (0.394), and the same 0.2 threshold returns reboot, incidents and sla. The ranking does not change.

Baseline-first optimisation

Every later module in this course changes one stage of the pipeline: chunking, embeddings, hybrid search, reranking, query rewriting. Without a baseline you cannot tell whether a change helped, hurt, or moved the failure to another question.

The method has four parts:

  1. Fix a golden set. 20 to 50 real questions, each with its evidence chunks and a reference answer. Freeze it, and add questions when production shows a new failure.
  2. Build the plain pipeline. Default loader, recursive splitter, one embedding model, top-k similarity, a simple prompt.
  3. Record the baseline row. Retrieval metrics (recall@k, hit rate, MRR), answer metrics (correctness, faithfulness), latency and cost per question.
  4. Change one stage, re-run, compare. Keep the change only if the row improves on the questions it targets without breaking the others.

Hit rate is the share of questions with at least one evidence chunk in the top k. MRR (mean reciprocal rank) averages 1 divided by the rank of the first evidence chunk, so it rewards evidence that ranks high. The loop then runs for as long as there are changes to try:

Figure 2: The baseline loop. A change that wins on the mean but breaks a question goes back for rework.

Key Takeaways

  • RAG runs in two phases: indexing (load, split, embed, store) and query (retrieve, augment, generate). Each step has one job and one typical failure.
  • Debug a wrong answer by printing the retrieved chunks first. If the evidence is missing, no prompt change can help.
  • Freeze a golden set of 20 to 50 questions, record a baseline row, and keep a change only when it helps its target questions without breaking others.

Check yourself

1. An answer is wrong. What one check tells you whether to debug retrieval or generation?

Print the retrieved chunks and look for the correct passage. If it is missing, retrieval failed: fix loading, splitting, embedding, k or the query. If it is there, generation failed: fix the prompt, the context order or the model.

2. A teammate rewrites the prompt and the refund question is still wrong. The refund-timing chunk never appears in the top-k. Why did the rewrite not help?

The model never saw the evidence, so no prompt can make it use that evidence. This is a retrieval failure, and the prompt work is a wrong-half fix. The refund question needs better term matching (M13 embeddings, M16 hybrid search), measured against the golden set.

3. Switching to embeddings lifts mean recall@2 from 0.50 to 0.67 but drops the export question from 1.00 to 0.50. Do you keep it?

Not as it stands. The loop keeps a change only when the row improves on the questions it targets without breaking the others. Revert it, or rework it (a larger k or hybrid search) and re-run the golden set before it becomes the new baseline.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s support assistant answers billing questions from the handbook. The policy team changes the refund window on Monday. A teammate proposes fine-tuning the model on the new handbook. What do you recommend, and what has to happen on Monday?

What a strong answer covers:

  • Facts that change belong in the index, not the weights; fine-tuning would need repeating at every policy change and gives no citations
  • Monday’s work is re-indexing the changed document: load, split, embed, upsert, and remove the stale chunks
  • Uses date or version metadata so retrieval can prefer the current policy and the old one can be filtered out
  • Adds the new policy question to the golden set and checks that the assistant now cites the new chunk

2. A customer asks “Can I get a refund after 45 days?” and the assistant says “No, refunds are only available within 30 days.” The handbook says refunds after day 30 are prorated. How do you find out what went wrong?

What a strong answer covers:

  • Prints the retrieved chunks with scores before touching the prompt
  • If the proration chunk was not retrieved: retrieval failure. Check its rank, whether it was split from its context, and whether “45 days” matches nothing lexically
  • If it was retrieved but ignored: generation failure. Check its position in the prompt, conflicting chunks, and the instruction to answer only from context
  • Turns the case into a golden-set question so the fix is measured and stays fixed

3. Your team runs at k = 20 “to be safe”. Latency is 3.1 s, and the product requirement is 1.5 s. How do you choose a new k without hurting quality?

What a strong answer covers:

  • Measures recall@k on the golden set for k = 1 to 20 and finds where the curve flattens
  • Separates the decision: retrieve wide (20 to 50), rerank, then send a small k to the model, if a reranker fits in the latency budget
  • Reports answer quality, not only recall, because fewer distractors often improves faithfulness
  • Watches per-question regressions, not just the mean; one lost question type can matter more than the average

4. The baseline went live last month. How do you know whether retrieval quality is degrading in production before users complain?

What a strong answer covers:

  • Logs every query with retrieved chunk ids, scores and the final answer
  • Tracks retrieval signals: top-1 score distribution, the share of queries below a score floor, out-of-scope fallback rate
  • Samples traffic for offline grading with an LLM judge (faithfulness, relevance) and re-runs the golden set on every index or model change
  • Alerts on drift after content updates, such as a new document type that the loader parses badly

5. Someone suggests skipping RAG because the new model has a 1M-token context and the whole handbook fits. When is that right, and when does it break?

What a strong answer covers:

  • Right for a small, stable corpus with low query volume, or for one-off analysis
  • Cost and latency scale with corpus size on every call, while RAG pays for a few chunks
  • Accuracy can fall for facts mid-context, and the model has no ranked evidence to cite
  • Access control is coarse: every user’s prompt holds every document, unless you filter per user, which is retrieval again

Key Takeaways

  • RAG answers from an index you control. Update it by re-indexing, and cite chunks instead of trusting memory.
  • Indexing happens once and is where most failures start. Always ask whether the correct passage was retrieved before you change the prompt.
  • k trades recall against precision, tokens and latency. If a chunk scores zero, no k will retrieve it; fix the representation instead.
  • Record a baseline on a frozen golden set, change one stage at a time, and keep only the changes that beat it.
