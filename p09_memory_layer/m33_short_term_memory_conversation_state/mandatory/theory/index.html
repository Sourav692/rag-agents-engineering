Part IX
The Memory Layer
Follow-ups and the retriever
Open the lab

The running example is the Larkspur Cloud support assistant answering from the same twelve handbook chunks as the M10 lab. Customers ask a first question and then follow up: Can I get a refund on my annual plan? then How long until the money is back?, or How do I export my data? then How long do I have? The lab runs six of these three-turn chats.

TL;DR

  • The model is stateless. Turn N of a chat that keeps everything sends 2N − 1 messages, so six turns send 36 messages in total, and cost grows with every turn.
  • A session_id (LCEL) or thread_id (LangGraph) picks whose history is loaded. The same chain or graph serves every user; the id is the whole isolation story, so it must come from your server, never from the user.
  • Bounding a history is a choice between forgetting and paying: a window or a token trim drops early facts for free, and a running summary keeps them in compressed form for one extra LLM call per fold.
  • A follow-up such as How long do I have? names no subject, so the retriever searches for the wrong thing. In the lab at k = 1, sending the latest message finds the evidence on 6 of 12 follow-ups; a rewritten standalone question finds it on 10.
  • Appending earlier questions to the query recovers turn 2 (5 of 6) but drowns a change of topic on turn 3 (1 of 6 at k = 1). The rewrite costs an LLM call per follow-up and cannot fix a vocabulary mismatch.

Mental model

One history feeds two consumers. The rewrite step reads it so the retriever searches for the real subject; the answer step reads it so the model can refer back. After the answer, both messages go into the history, keyed by the session, and the next turn starts from there.

Part IX starts here. Earlier modules built chains and agents that answered one question at a time. From this lesson on, the Larkspur Cloud support assistant has to hold a conversation.

A customer writes I’m on the annual Team plan and gets a friendly reply. Their next message is Which plan am I on?, and the assistant has no idea. Nothing crashed and the model works. The second call carried only the second question.

A chat model call is a function of the messages sent in that call and nothing else. The provider keeps nothing between calls, so a stateless chain of prompt, model and parser treats every message as the first one. The notebook shows the same thing with a name: told My name is Sourav in one call, the chain cannot answer What’s my name? in the next. Anything that looks like memory in a chatbot is the application resending earlier messages.

Message history

A message history is the ordered list of typed messages that make up the conversation so far, and the application sends it with every call. The model then reads the earlier turns as part of the current input, exactly as it reads the new question.

Three message types share the list:

Type Who wrote it Stored in the history?
SystemMessage You, the developer: instructions for the model Usually not; the prompt adds it on every call
HumanMessage The user Yes
AIMessage The model Yes

Table 1: The three message types. Because the prompt template adds the system message each time, the stored history holds only the human and AI turns.

Each turn appends the user’s message, sends the whole list and appends the reply. Figure 1 shows three turns:

Figure 1: Full-history replay. Every call carries every earlier message plus the new one.

The notebook’s hand-rolled version does four things per turn: append the human message, call the model with the whole list, append the reply, return it. LangChain gives the same list a home in InMemoryChatMessageHistory, with operations to add a user message, add an AI message, read the messages and clear them. File, SQLite and Redis backends implement that same interface, and lesson 33.2 relies on it.

What full replay costs

A history that keeps everything resends everything. Turn N carries the N questions so far and the N − 1 replies before it, which is 2N − 1 messages:

Turn Messages sent Running total Independent calls, running total
1 1 1 1
2 3 4 2
3 5 9 3
4 7 16 4
5 9 25 5
6 11 36 6

Table 2: Messages sent by a full-history chat over six turns, not counting the system message. The running total is N squared.

Six turns send 36 messages where six independent calls would send 6. Every earlier message is read again on every later turn, and token cost and latency follow that curve. A long enough chat stops fitting in the context window at all. We will call this replay cost; lessons 33.3 and 33.6 bound it.

Planted failures: what the second call receives

Having a history is half the job. Which messages get into it decides what the model can use. Table 3 replays the Larkspur exchange with the history kept in three ways:

History kept Second call receives Can it name the plan?
Full history Human 1, AI 1, Human 2 Yes
None (stateless chain) Human 2 No
Human turns only: the reply was never appended Human 1, Human 2 Usually, but the model has lost its own earlier answers and can contradict or repeat them

Table 3: Three histories for the same two turns. Only the first gives the model a faithful transcript.

The third row is a half-saved history. It looks healthy in a demo, because the customer’s facts survive. It fails later, when the customer asks What did you just tell me about refunds? and the reply that answered it was never stored. The older memory classes had a worse version of this bug, as the next section shows.

The classic memory classes

Before RunnableWithMessageHistory and LangGraph checkpointers, LangChain packaged memory as classes that a chain loaded before each call and saved after it. An LCEL chain has no memory slot. The optional notebook drives them through a loop of three steps:

Figure 2: The load, invoke and save loop. The chain never writes to memory; the caller’s save step does.

The save is the step people forget. Skip it and the chain still runs without an error, but the next load returns nothing and every turn behaves like the first. This is the missing save. In the healthy case, the notebook asks What are the first four colors of a rainbow? and then And the other 3?. The second question only makes sense because the first exchange was loaded, and after two turns memory holds 4 messages, both pairs written by the explicit save.

Each class decides which messages the prompt receives. Table 4 lines them up with the patterns that replaced them:

Class What the prompt receives Keeps early facts Extra LLM calls Where the idea lives now
ConversationBufferMemory Every message Yes None A message history (this lesson)
ConversationBufferWindowMemory The last k exchanges (2k messages) No None A window or trim_messages (33.3, 33.6)
ConversationSummaryMemory One running summary Yes, compressed One per turn Summary memory (33.3)
ConversationSummaryBufferMemory Summary plus recent turns Yes, compressed When over max_token_limit Summary memory (33.3)
VectorStoreRetrieverMemory The past exchanges most similar to the question Only if retrieved None Long-term memory (M34)

Table 4: The five classic classes. Each one is a policy for choosing which earlier messages to resend.

Three details from the notebook are worth carrying forward:

  • The window hides old turns without deleting them. The window class still stores every message underneath and returns only the last k exchanges. With k = 1, a favourite colour given in the first exchange is invisible by the third question, although it is still stored.
  • Choosing k is a guess about the conversation. The notebook suggests 1 to 2 exchanges for quick questions, 3 to 5 for support chats and 6 to 10 for long technical threads. Whatever the value, early facts leave without warning.
  • The format is separate from the policy. A memory can hand the prompt one “Human: … AI: …” string for completion-style prompts or a list of message objects for chat prompts. The choice changes formatting and leaves what is remembered alone.

These classes now live in langchain_classic. You will meet them in older code; new code uses the patterns in lessons 33.2 to 33.6.

In practice: Larkspur’s plan question

Following the Larkspur customer through a full-history chat:

  1. Turn 1. The app appends I’m on the annual Team plan, sends one message and appends the reply. The history holds 2 messages.
  2. Turn 2. The app appends Which plan am I on? and sends 3 messages. The model reads the plan from Human 1 and answers.
  3. Turn 6. The same chat now sends 11 messages per call and has sent 36 in total. Each message the customer adds will be paid for again on every later turn.

Key Takeaways

  • A chat model call sees only the messages sent in that call. Keep an ordered history of human and AI turns, send the whole list each time, and let the prompt add the system message.
  • A history that keeps everything resends everything: turn N sends 2N − 1 messages, and six turns send 36 against 6 for independent calls. That replay cost is what later lessons bound.
  • The classic memory classes load before each call and save after it. A missing save leaves every turn with an empty history and raises no error; expect these classes in older code only.

Check yourself

1. A customer gives their plan in one call and asks for it in the next. Why can a stateless chain not answer, and what fixes it?

A chat model call depends only on the messages sent in that call, so the second call receives the question and nothing else. A message history fixes it: append each human and AI message to an ordered list and send the whole list on every turn. The earlier turn then travels with the new question.

2. A history that keeps everything runs a six-turn chat. How many messages does turn 6 send, and how many over all six turns?

Turn N sends 2N − 1 messages, so turn 6 sends 11, and the six turns send 1 + 3 + 5 + 7 + 9 + 11 = 36 messages. Six independent calls would send 6. Token cost and latency grow with the conversation, which is why lessons 33.3 and 33.6 bound the history.

3. A legacy chain using ConversationBufferMemory runs without errors, but every turn behaves as if the conversation just started. What is the likely bug?

The save step is missing from the load, invoke and save loop. The classic memory classes load the history before each call and save the exchange after it; skip the save and the next turn loads nothing. New code avoids the manual loop with the patterns in lessons 33.2 to 33.6.

Lesson 33.1 kept the conversation in one list and resent it every turn. That works for a single customer in a notebook.

Put the Larkspur assistant behind a web endpoint and two customers arrive at once. Customer A says she is on the annual Team plan; customer B asks Which plan am I on? With one shared list, B’s call carries A’s turns and the model answers with A’s plan. Restart the server and both lists are gone.

Two jobs follow from that failure. Each conversation needs its own history, chosen by something the server trusts. And the history has to live somewhere that outlasts the process.

One history per session

RunnableWithMessageHistory does the load and save of lesson 33.1 around any runnable. You give it the chain and a session factory, a function that takes a session id and returns that conversation’s history object. Every call then carries the id in its config, under session_id, next to the input:

Figure 1: One wrapped call. The wrapper loads the session’s history before the chain runs and saves both new messages after it.

When the chain takes a dict, three keys tell the wrapper where things go:

Key What it names What goes wrong without it
input_messages_key The input field holding the new user message, saved after the call The wrapper cannot find the message to store
history_messages_key The MessagesPlaceholder in the prompt that receives the stored history The history loads but never reaches the prompt
output_messages_key Which field of a dict output to save as the AI message A chain that returns a dict, such as lesson 33.4’s retrieval chain, has no single reply to store

Table 1: The wrapper’s keys. The model receives the system message, the history at the placeholder and the new question, in that order.

Planted failures: where the id comes from

The session_id is the only thing separating one customer’s conversation from another’s. Whoever supplies it chooses which history loads, which makes its source matter more than its format:

Session id taken from What happens
The authenticated server session Each customer reads only their own history
A field in the request body the user can edit Any customer can load another customer’s chat by changing one string: a borrowed session
The user id alone One customer’s separate chats merge into a single history
A fresh value on every request Every turn starts empty, and the app forgets as in lesson 33.1

Table 3: Four sources for the session id. Only the first is safe and correct.

Any string works as an id: a user id, a chat id, or both combined, which lets one customer hold several separate chats. Build it on the server from the authenticated user, never from text the user can edit.

Proving the database remembers

The notebook separates the chain from the store by throwing the chain away. Run 1 builds a chain on SQLite, sends two messages about a user’s preferences and deletes the chain object. Run 2 builds a brand-new chain with no Python-side state and asks three questions about those preferences:

Moment Rows in message_store Where the answer can come from
After run 1 (2 turns) 4
Run 2 asks What’s my name? 4 loaded Only the database
After run 2 (3 more turns) 10

Table 5: Row counts across the restart test. Each turn writes two rows, one per message.

Any correct recall in run 2 came from the rows, because nothing else survived. The rows also outlive the kernel: rerun only the second half after a restart and the answers still come from the file. A file-backed history works the same way for one session, and the notebook resumes a saved JSON conversation from a copy.

Pitfall: the positional connection. The second positional argument of SQLChatMessageHistory is table_name. Passing the database URL second creates no connection, and the error appears only at the first call. Pass it by keyword, as connection.

SQLite is fine for one process. For a service with concurrent writers, use the same interface on Postgres or Redis. These history classes come from the sunset langchain-community package, and RunnableWithMessageHistory is deprecated in langchain-core 1.3.3 and removed in 2.0. Lesson 33.6 does the same job with a LangGraph checkpointer, which is where new code should go.

In practice: Larkspur’s support endpoint

Applying both halves to the Larkspur assistant:

  1. Keying. The endpoint builds the session id from the logged-in account and the chat, for example the customer cust-4821 plus a chat number, and never reads it from the request body.
  2. Storing. The factory returns a SQL-backed history for that id. A deploy that restarts the service loses no conversation.
  3. Checking. A test interleaves two customers and asserts that each summary mentions only its own topics, the same check as Table 2.

What changes next: every stored message still goes back to the model on every turn. Lesson 33.3 bounds that list with trimming, windows and a running summary.

Key Takeaways

  • RunnableWithMessageHistory loads and saves history around any runnable, and the session_id in the call’s config alone separates conversations. Take that id from the authenticated server session, never from text the user can edit.
  • Changing the store means changing only the factory: an in-memory dict for tests, one file per session for single-user tools, and SQL, Postgres or Redis for services that must survive restarts.
  • Pass the database URL to SQLChatMessageHistory by keyword, because the second positional argument is table_name. Put new code on a LangGraph checkpointer, since RunnableWithMessageHistory is deprecated.

Check yourself

1. Two customers send interleaved turns to the same chain wrapped in RunnableWithMessageHistory. What keeps their conversations apart?

The session_id in each call’s config. The wrapper passes it to the session factory, which returns that conversation’s history, loads it before the call and saves the new messages after it. A new session_id starts empty, so each customer’s summary sees only their own turns.

2. A notebook prototype keeps histories in a dict of InMemoryChatMessageHistory. It must now serve a web app and survive restarts. What do you change?

Only the factory: return SQLChatMessageHistory keyed by session_id, and the chain and wrapper stay the same. The in-memory store loses everything on restart. For a service with concurrent writers, use the same interface on Postgres or Redis rather than SQLite.

3. SQLChatMessageHistory built with the session id and the database URL as two positional arguments fails on the first invoke. What went wrong?

The second positional argument is table_name, not the connection, so this form creates no database connection and fails only when invoked. Pass the URL by keyword, as connection, next to session_id.

When the plan falls out of the window

Lesson 33.3: Trimming, windowing and summary memory. Notebooks: 03a_trimming_windowing_and_summary.ipynb

What you’ll learn

  • Trace a token trim and a window on real message lists, and name exactly which facts they drop.
  • Compare trimming, windowing and summarising on early-fact recall, extra calls and what is stored.

Lesson 33.2 gave every customer a history that survives a restart. Every stored message still goes back to the model on every turn, and lesson 33.1 showed that turn N sends 2N − 1 of them.

A Larkspur billing ticket shows why the cheapest fix hurts. On turn 1 the customer says they are on the annual Team plan. Turns 2 to 4 discuss a duplicate charge. On turn 5 they ask Which plan am I on, and can I get the refund on that plan? An assistant that keeps only the last two exchanges sends turns 3 and 4 and has lost the plan.

The oldest messages are often the ones that set the context: the plan, the region, the account the ticket is about. That makes them the worst ones to drop first, and this page compares three ways to bound the history by what each does to them.

Summary memory

Summary memory keeps a short running summary of the older turns, written by a second LLM call, plus the most recent messages word for word. Old exchanges are compressed instead of dropped, which keeps facts like the plan within reach of the model.

The notebook keeps the last MAX_RECENT = 4 messages, two exchanges, verbatim. After each answer it appends the exchange to the recent list. When the list passes four messages, the oldest exchange goes to a summariser chain together with the current summary, and the updated summary replaces the old one in the system prompt:

Figure 1: One turn of summary memory. The fold runs after the answer, and the next turn starts from the updated summary.

Tracing the five-turn ticket

Turn Prompt holds Recent list after the answer Fold? Summary now covers
1 Question only 2 messages No Nothing
2 2 recent + question 4 No Nothing

On turn 5 the recent messages are turns 3 and 4, exactly what a two-exchange window would send. The plan from turn 1 reaches the model only through the summary. The notebook runs the same loop with a user who gives their name, city, job and cats, then asks for everything they said; the final answer can list the first-turn facts because they survived the folds.

What the summary costs

Three costs come with the fold:

  • Extra calls. Each fold is one more LLM call. On a short chat that never passes the threshold, or barely does, summary memory costs about as much as keeping everything.
  • Lossy compression. Names and decisions survive; exact wording does not, and a summariser can drop a fact you needed. Call this summary drift: the memory still sounds confident after the detail has gone.
  • Slow growth. The summary gets a little longer with every fold. The prompt stays bounded only while the summariser keeps it short.

Lesson 33.6 builds the same idea as a LangGraph node, and agents built with create_agent get it ready-made as SummarizationMiddleware. The two cheaper bounds are next.

Trim, window or summarise

Trimming by tokens

trim_messages cuts a list to a token budget on its way to the model. The notebook’s settings keep the newest messages that fit, always keep the system message, never cut a message in half, and make the kept part start on a user message so it reads as a conversation. It runs locally; the model object serves only as the token counter.

The notebook’s chat has eleven messages, starting with a system message and hi! I’m bob, then vanilla ice cream, whats 2 + 2, thanks and having fun?. With gpt-4o-mini’s counter in langchain-openai 1.7.3 the whole list counts 80 tokens. Trimmed to 45:

Input Budget Kept Kept messages Lost facts
The 11-message chat (80 tokens) 45 5 messages, 36 tokens System, thanks, no problem!, having fun?, yes! Bob’s name, vanilla ice cream, the sum
The chat + What ice cream do I like? 45 4 of 12 System, having fun?, yes!, the question The answer to the question
The chat + What math problem did I ask? 45 4 of 12 System, having fun?, yes!, the question The answer to the question

Table 2: The notebook’s trimmer, run in the scratchpad. Another token counter gives other cuts.

Adding the question costs the trimmer one more exchange, which shows a trap of token budgets: a longer question pushes more history out. Both questions ask about facts outside the budget, and neither can be answered from the conversation. Call this silent truncation: nothing errors, and the model either says it does not know or guesses.

Windowing the store

A window does the same job in storage. The notebook’s windowed history keeps only the last k = 2 exchanges and deletes the rest as new messages arrive:

After the user says Window holds (user side)
My name is Paulo Paulo
I live in Seattle Paulo, Seattle
I work as an AI engineer Seattle, AI engineer
I have 2 cats AI engineer, 2 cats
What do you remember about me? Answered from the job and the cats only

Table 3: A two-exchange window. The name and the city slide out before the question arrives.

Comparing the three bounds

Table 4 puts the strategies side by side, with full history as the baseline:

Strategy What the model receives Keeps early facts Extra LLM calls Stored history
Keep everything Every message Yes None Grows forever
Trim by tokens (trim_messages) Newest messages within the budget No None Complete; only the prompt is cut
Window of k exchanges Last 2k messages No None Only the window

Wrap a trimming chain in RunnableWithMessageHistory and the store keeps the full history while the model sees only the trimmed part. That split between what is stored and what is sent is the question lesson 33.6 asks of a LangGraph thread.

In practice: picking a bound for Larkspur tickets

For the Larkspur support assistant, the choice follows from two facts about its tickets:

  1. Early facts matter. Plan, region and account appear in the first turn and decide later answers. A window or a trim alone would fail the turn-5 question in the opening example.
  2. Most tickets are short. While a chat fits the budget, keeping everything is cheapest and loses nothing.
  3. The rule. Keep everything up to the budget, then fold older turns into a summary, and test that the turn-1 plan still reaches the model late in a long ticket.

What changes next: the retriever is a second reader of the conversation, and it sees only the latest message. Lesson 33.4 rewrites follow-ups before retrieval.

Key Takeaways

  • Windows and token trims drop the oldest messages, which often set the context, such as the customer’s plan. Summary memory folds old exchanges into a running summary and keeps the last few messages word for word.
  • Each fold is an extra LLM call and keeps names and decisions but not exact wording. On a short chat, summary memory costs as much as keeping everything.
  • trim_messages cuts only the prompt and leaves the stored history complete, while a window of k exchanges keeps only the last 2k messages in storage. Neither keeps early facts.

Check yourself

1. On turn 5 of the Larkspur billing ticket, the customer asks for the plan they gave in turn 1. Why can summary memory answer when a two-exchange window cannot?

A window drops the oldest messages, so it holds only turns 3 and 4 and the plan is gone. Summary memory folds old exchanges into a running summary instead of dropping them, and turn 1’s plan survives there. The model sees the summary, the last four messages and the question.

2. The notebook's eleven-message chat counts 80 tokens. With a 45-token trim_messages budget, what does the model keep, and can it say which ice cream Bob likes?

It keeps five messages (36 tokens): the system message and the last two exchanges. Bob’s name and his vanilla ice cream fall outside the budget, so it cannot answer. Those counts depend on the token counter; another counter gives other cuts.

3. A team adds summary memory to a support bot whose chats rarely pass three turns, hoping to cut cost. Is that a good choice?

No. Each fold is an extra LLM call, so on a short chat summary memory is no cheaper than keeping everything, and it is lossy: exact wording does not survive and a summariser can drop a fact you needed. Keep everything while the chat fits the budget.

A follow-up with no subject

Lesson 33.4: Conversational RAG with history-aware retrieval. Notebooks: 04a_conversational_rag_with_history.ipynb

What you’ll learn

Lessons 33.1 to 33.3 gave the history to the model. In retrieval-augmented generation (RAG) a second component reads the question: the retriever. It reads only the literal text.

A Larkspur customer asks How do I export my data?, then Is that possible after I cancel?, and gets good answers to both. Then they ask How long do I have? The one useful term left after stop words is “long”, and no chunk of the Larkspur handbook contains it: every chunk scores zero. The model receives the history and knows the customer means their data after cancelling. The chunks it receives were chosen for a question with no subject.

We will call this subject loss. The notebook shows the same failure on Lilian Weng’s post about agents: after What is Self-Reflection?, the follow-up How do we achieve it? retrieves chunks about “it”. The fix has to happen before the search.

History-aware retriever

A history-aware retriever adds one step before retrieval: an LLM reads the chat history and the latest message and writes a standalone question, one that makes sense without the history, and the retriever searches for that. The notebook’s prompt tells the LLM to reformulate the question if needed, return it unchanged otherwise, and not answer it.

Figure 1: The history-aware retriever’s branch. Turn 1 has no history and costs no rewrite call.

The rewrite turns each follow-up back into a question the retriever can score. Table 1 shows what it does to Larkspur follow-ups from the lab’s chats:

History so far Latest message Standalone question (representative)
Can I get a refund on my annual plan? How long until the money is back? How long until the money from an annual plan refund is back?
How do I export my data? Is that possible after I cancel? How long do I have? How long is my data kept after I cancel my plan?
When is a monthly plan billed? And the annual one? Can I get money back on it? Can I get a refund on an annual plan?

Table 1: Three follow-ups from the lab and their rewrites. The rewrites are written by hand to show the shape; the lab’s rankings for them are computed.

create_history_aware_retriever builds exactly the branch in Figure 1. create_retrieval_chain then joins it to a chain that stuffs the retrieved documents into an answer prompt, and that prompt carries the chat history too. The answer step sees the conversation as well. Wrapped in RunnableWithMessageHistory with the answer field named as the output to save, the chain loads and saves the history itself, as in lesson 33.2.

What the rewrite costs, and how it fails

The extra step brings its own failure modes:

Failure What happens Example
Rewrite latency One LLM call runs on every follow-up before retrieval can start Twelve follow-ups in the lab, twelve calls
Dropped constraint The rewrite loses a detail the customer gave Can I get money back on it? rewritten without “annual” no longer points at the annual refund window (illustrative)
Over-carried history The rewrite drags the old topic into a new question A cancel question keeps “refund” and “annual plan” and ranks the refund chunk first
Empty history at runtime A wiring bug passes no history, the branch takes the “yes” path, and every follow-up is searched as typed Follow-up hit rate drops to the latest-message baseline with no error

Table 2: Four ways a history-aware retriever goes wrong. The last one looks like a retrieval regression and is a memory bug.

Rewrite, append or neither

The interactive lab runs six three-turn Larkspur support chats against the twelve handbook chunks from the M10 lab, with the same TF-IDF index (it matches scikit-learn’s TfidfVectorizer to within 5e-16 on all 648 scores). It compares three things the retriever can receive on turns 2 and 3: the latest message as typed, the earlier questions with the latest appended, and a standalone rewrite. The customer messages are hand-written and the rewrites are representative; the rankings are computed.

Retriever receives Turn 2 hits, k = 1 Turn 3 hits, k = 1 Hit rate, k = 1 Hit rate, k = 2
The latest message 2 / 6 4 / 6 0.50 0.58
Earlier questions + latest 5 / 6 1 / 6 0.50 0.92
A rewritten question 5 / 6 5 / 6 0.83 0.92

Table 3: Evidence found on the 12 follow-up turns, recomputed from the lab’s own scoring code. A hit means the labelled evidence chunk is in the top k.

  • The latest message misses the turns that point back. What do I get if you miss it?, How long do I have? and Can I get money back on it? score zero against every chunk, and Is that possible after I cancel? finds the cancel chunk instead of the export evidence. Follow-ups that name their own subject, such as Do my promo credits expire?, hit either way.
  • Appending fixes turn 2 and breaks turn 3. Turn 2 usually continues turn 1’s topic, and the extra words help. Turn 3 often changes topic, and two earlier questions outweigh one new one: at k = 1 the old topic takes the only slot in 5 of 6 chats. Call this topic drag. At k = 2 appending catches up, by spending a context slot on the old topic every time.
  • The rewrite wins at k = 1 and pays for it with 12 LLM calls, one per follow-up. Its two misses are worth reading. How long until the money is back? misses whatever the query says, because the evidence chunk says “Refunds” and “business days” and no phrasing of the question uses those words. A rewrite restores the subject but not the handbook’s vocabulary, which is M10’s representation problem and the reason for embeddings in M13. And What happens if I cancel my annual plan instead of getting a refund? is the over-carried rewrite from Table 2: “refund” and “annual plan” pull the refund chunk above cancel at k = 1.

Measuring turns 2 and 3 separately

The lab is the module’s lab brief in miniature. On your own corpus, write multi-turn conversations, label the evidence for each turn, and report hit rate on turns 2 and 3 separately from turn 1, with and without the rewrite. A single average over all turns hides the follow-ups, because first questions are usually standalone and score well either way.

The same split catches a regression early. If a refactor stops passing the history, the turn-1 numbers stay put while the turn-2 and turn-3 numbers fall to the latest-message row of Table 3.

In practice: Larkspur’s export chat

Following the export conversation through the full chain:

  1. Turn 1. How do I export my data? arrives with an empty history, the branch skips the rewrite, and the retriever finds the export chunk.
  2. Turn 2. Is that possible after I cancel? arrives with one exchange of history. As typed it finds the cancel chunk; rewritten as Can I export my data after I cancel my plan? it finds the export evidence.
  3. Turn 3. How long do I have? scores zero as typed. The rewrite, How long is my data kept after I cancel my plan?, finds the retention chunk: data is kept for 30 days after cancelling.
  4. Answer. The answer prompt receives the retrieved chunk and the history. The reply can then say your data and mean the account from turn 1.
  5. Monitoring. The logs keep the raw message, the rewrite and the retrieved chunk ids per turn, which lets the team check the rewrite as well as the retrieval.

What changes next: these chains keep history with the deprecated wrapper from lesson 33.2. Lesson 33.6 moves conversation state into a LangGraph thread, where the same bounding choices become nodes.

Key Takeaways

  • A retriever reads only the literal question, so a follow-up such as How long do I have? can score zero against every chunk even when the model holds the history.
  • A history-aware retriever has an LLM rewrite each follow-up as a standalone question and skips the rewrite on turn 1. Each rewrite adds a call and can drop a constraint or carry an old topic forward.
  • In the lab, rewriting raised the k = 1 hit rate from 0.50 to 0.83, while appending earlier questions helped turn 2 and broke turn 3. Report follow-up turns separately from turn 1, which is usually standalone.

Check yourself

1. The model receives the chat history, yet the follow-up How long do I have? retrieves nothing useful. Why, and what does a history-aware retriever add?

The retriever reads only the literal question, and its one useful term, “long”, appears in no handbook chunk. Every chunk scores zero. A history-aware retriever first has an LLM rewrite the latest message as a standalone question from the history, and the retriever searches for that. On turn 1, with an empty history, it skips the rewrite.

2. In the lab at k = 1, appending earlier questions hits on 5 of 6 turn-2 messages but only 1 of 6 on turn 3. Why the collapse?

Turn 2 usually continues turn 1’s topic, so the extra words help. Turn 3 often changes topic, and two earlier questions outweigh one new one, so the old topic takes the only slot in 5 of 6 chats. At k = 2 appending catches up to 0.92, but only by spending a slot on the old topic every time.

3. With the rewrite, How long until the money is back? still misses its evidence. Would a better rewrite prompt fix it?

No. The evidence chunk says “Refunds” and “business days”, and no phrasing of the question uses those words. A rewrite restores the subject, not the handbook’s vocabulary; that is a representation problem, which embeddings (M13) address.

The project: two memory apps

Lesson 33.5: Memory apps: product recommender and research agent with SQL memory. Notebooks: 05a_multi_user_product_recommender.ipynb (optional), 05b_multi_user_research_agent_sql_memory.ipynb (optional)

What you’ll build

  • A product recommender that turns a shopper’s follow-ups into one standalone request, filters a 30-product catalogue and recommends from what is left.
  • A research agent with a web-search tool and a weather tool that answers follow-ups such as What about Intel? from the user’s own history.
  • Per-user SQLite memory around both, keyed by a session id per user.

This project adds no new memory pattern. It points the session-keyed SQL history from lesson 33.2 and the standalone rewrite from lesson 33.4 at a shop assistant and a web-searching agent.

What changes is what the memory holds. Both apps store only the user’s raw message and the final reply; rewrites, filtered tables and tool calls are rebuilt each turn.

Limits

  • The filter is model-written code. An empty set of built-ins is not a sandbox. In production, have the model return a structured filter and apply it in code.
  • Specs live in free text. The recommender model enforces display size and storage, and its prompt tells it to recommend five random products when nothing matches.
  • The agent forgets its sources. Only final answers are saved; asking where a figure came from needs a new search.
  • Deprecated APIs. RunnableWithMessageHistory, the community history class and the classic AgentExecutor; lesson 33.6’s checkpointer replaces them.
  • Narrow tools. The weather tool looks up Indian cities only, and SQLite suits one process.

Both notebooks need an OpenAI key. The research agent also needs a Tavily key and an OpenWeatherMap key, and every run issues real searches.

Key Takeaways

  • Per-user SQL history and a standalone rewrite are enough to make a product filter and a tool-calling agent follow a conversation: the rewrite rebuilds each follow-up from that user’s stored turns.
  • Decide what the memory stores. These apps keep the raw messages and final replies, and rebuild rewrites, tables and tool calls each turn, which keeps the history short and loses the sources.
  • Never run model-written code with only an empty set of built-ins as protection; return a structured filter and apply it in code.

No, it follows from the design. The wrapper saves only the user’s question and the agent’s final answer, so the tool calls and pages from the earlier turn are not in the history. Keeping sources would mean saving them with the answer, at the cost of a longer history.

Lessons 33.2 to 33.4 kept history with RunnableWithMessageHistory, which is deprecated. LangGraph keeps the conversation in the graph’s own state instead, and the bounding choices of lesson 33.3 become nodes.

A Larkspur customer opens a ticket about a duplicate charge. Six turns later the prompt has grown on every call, and the team wants it bounded. Support leads also want the whole ticket available for review and for replaying a bad answer. A bound that deletes old turns satisfies the first request and silently breaks the second.

This page first shows where a LangGraph conversation lives, then measures four strategies on one ticket and separates the two things a bound can cut: what the model reads and what the thread stores.

Checkpointer / thread_id

A LangGraph graph keeps the conversation in its state, typically a messages channel with the add_messages reducer: each node returns only its new messages, and the reducer appends them. A checkpointer saves a snapshot of that state, a checkpoint, after every step, and the thread_id in the call’s config names the sequence of checkpoints a run reads and extends. Compile the graph with a checkpointer once; every call then picks its conversation by thread:

Figure 1: One turn on a checkpointed graph. The app sends only the new message; the thread supplies the rest.

This replaces RunnableWithMessageHistory and session_id from lesson 33.2, and LangChain recommends it for new code. A one-node graph that answers every message with a fixed reply shows the isolation without a model call:

Call Thread New message Messages in the returned state
1 dana Annual plan 2
2 dana Which plan? 4
3 omar Hello 2

Table 1: Three calls on one compiled graph with an in-memory checkpointer, run in the scratchpad with a scripted reply.

Call 2 returns four messages because dana’s first exchange was loaded from the thread. Call 3 starts from nothing, although it uses the same graph object. The notebook shows the same thing with a model: user001 asks Explain AI in 1 line and then Do the same for ML, which only makes sense because the first turn is replayed, and user001’s memory is untouched after user002 talks on another thread.

Counting checkpoints

Checkpoints are snapshots of every step, not only of the end of a turn. A turn writes one for the input, one at the start of the run and one per node step:

Graph Checkpoints per turn After six turns
One node (answer) 3 18
Two nodes (bound, then answer) 4 24
The notebook’s tool-calling agent (model, tool, model) about 5

Table 2: Checkpoints written per turn, counted with a stub model in the scratchpad for the first two rows.

get_state returns the latest checkpoint; get_state_history walks all of them, newest first, which is what replay, forking and debugging use. Where they are written depends on the checkpointer:

Checkpointer Survives a restart Use
InMemorySaver No Notebooks and tests
SqliteSaver Yes, a plain SQLite file with checkpoints and writes tables One process; it is a context manager, and the graph is compiled inside its block
PostgresSaver (langgraph-checkpoint-postgres) Yes Deployments with concurrent writers

Table 3: Three checkpointers behind the same compile call.

Two rules follow from this design. Short-term describes scope, not lifetime: a thread on SQLite or Postgres stays on disk until you delete it, which makes it customer data with retention rules like any other. And the thread_id must come from trusted server-side config, never from user text, because whoever picks the id reads that thread.

Delete or hide

A thread that keeps everything sends every earlier message on every turn. The notebook runs one six-turn support ticket through four graphs. Turn 1 reports the duplicate charge and mentions in passing that the customer’s favourite colour is blue; turn 3 asks for the colour back. Counted in messages, the model receives:

Turn Sequential Sliding window Trim on read Summary
1 1 1 1 1
2 3 3 3 3
3 5 3 3 summary + 1
4 7 3 3 summary + 3
5 9 3 3 summary + 1
6 11 3 3 summary + 3
Stored after turn 6 12 4 12 summary + 4

Table 4: Messages sent to the model per turn, not counting system messages. Counted by running the notebook’s four graphs with a stub model in place of gpt-4o-mini; the graph logic decides these numbers, and a real model gives the same counts with different token totals.

Sequential can answer turn 3, and so can the summary graph if its summariser kept the colour. Sliding window and trim on read cannot, since both send only the last MAX_MESSAGES = 3 messages: the previous exchange and the new question.

Same prompt, different thread

The two bounded strategies send the same prompt and differ in what they keep:

  • Sliding window deletes. A truncate node returns a RemoveMessage for every message older than the window, and the add_messages reducer removes them from the checkpointed state. They are gone for every later turn, for get_state and for anyone auditing the ticket. The reducer is the mechanism: plain list concatenation can only append. A deleting window needs add_messages.
  • Trim on read hides. The model node calls trim_messages on a copy of the list and leaves state alone. The thread still holds all 12 messages, turn 1’s colour included. Trimming the prompt never trims the checkpoint: with SqliteSaver the full thread is written to disk on every step.

Call the first one audit loss: the answer quality is identical, and the damage shows up only when someone needs the full ticket.

The summary graph

The summary graph keeps a summary string next to a buffer of recent messages. Once the buffer reaches MESSAGE_THRESHOLD = 4, a node folds all but the newest message into the summary and removes them. It folds every other turn, turns 3 and 5 in Table 4, and each fold is an extra LLM call. Counting those calls, the notebook notes that on a thread this short summarisation costs about as much as the sequential baseline; it pays off on long threads.

The summary channel has no reducer, so any value written to it replaces the old one. Pass the empty summary only on the first turn. An app that sends it on every turn wipes the memory it is building, a failure we will call the summary reset: the folds run, the logs look busy, and each turn starts from nothing.

In practice: Larkspur’s duplicate-charge ticket

Applying the page to the opening ticket:

  1. Thread. The endpoint derives the thread_id from the authenticated customer and ticket, and compiles the graph once with PostgresSaver.
  2. Bound. Support leads need the whole ticket, which rules out the sliding window. Trim on read caps the prompt and keeps all 12 messages in the thread.
  3. Early facts. The billing-address change from turn 2 and the amount from turn 4 matter for the refund at the end. Long tickets switch to a summary seeded once, on the first turn.

Key Takeaways

  • Compile the graph with a checkpointer and take the thread_id from trusted server config. A checkpoint is written after every step, three per turn for a one-node chat graph, for replay and debugging.
  • A sliding window deletes old messages from state through RemoveMessage and add_messages; trim on read hides them from the model and keeps the full thread. Use trim on read when audit or replay needs every message.
  • Keep everything while the thread fits the budget, and summarise older turns once it does not. A persisted thread stays on disk until you delete it, so treat it as customer data with retention rules.

Check yourself

1. The sliding-window and trim-on-read graphs both send the model the last three messages. What differs between them, and when does it matter?

The sliding window deletes: a truncate node returns RemoveMessage instructions and the add_messages reducer removes those messages from checkpointed state. Trim on read hides: it trims a copy for the model, and the thread still holds all 12 messages. Pick trim on read when you need the full thread for audit or replay.

2. How many checkpoints does a one-node chat graph write per turn, and why more than one?

Three: one for the input, one at the start of the run and one per node step. Checkpoints snapshot every step, not just the end of a turn. A two-node graph writes 4 and the notebook’s tool-calling agent about 5. get_state_history walks them newest first for replay, forking and debugging.

3. A summary graph runs its folds, yet each turn starts with an empty summary. What is the likely cause?

The app passes an empty summary on every turn. The summary channel has no reducer, so any value written to it replaces the old one and wipes the memory being built. Pass the empty summary only on the first turn.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. After a refactor, Larkspur’s assistant answers first questions well, but follow-ups like “How long do I have?” now cite billing chunks. Nothing in the retriever changed. How do you find the cause?

What a strong answer covers:

  • Logs the query the retriever actually received on each turn, next to the user’s message, before reading any prompt
  • Checks that history reaches the rewrite step: the session id in the config, the history_messages_key matching the placeholder, and an empty chat_history (which makes create_history_aware_retriever skip the rewrite and search the raw text)
  • Replays a follow-up golden set and compares hit rate on turns 2 and 3 with the last good release
  • Adds those follow-ups to the regression suite so the next refactor is caught by a number, not a customer

2. The rewrite step adds an LLM call, and its latency, to every follow-up. A teammate wants to drop it and append the chat history to the query instead. What do you tell them?

What a strong answer covers:

  • Appending is free and does recover elliptical turns: in the lab, turn 2 hits 5 of 6 either way
  • It fails on topic changes, because earlier questions outweigh the new one: 1 of 6 turn-3 hits at k = 1, against 5 of 6 with a rewrite
  • A larger k hides the problem by spending context slots on the old topic, which costs tokens and adds distractors
  • Middle ground: skip the rewrite on turn 1 and when a cheap check says the question is already standalone, use a small fast model for the rewrite, and measure latency against hit rate

3. How do you know, week by week, whether conversational retrieval is getting better or worse in production?

What a strong answer covers:

  • Logs per turn: turn number, raw message, rewritten query, retrieved chunk ids and scores, session id
  • Tracks retrieval quality split by turn number, since first turns hide follow-up regressions in an overall average
  • Samples rewrites for an LLM judge or human check: is the rewrite faithful to the history, and does it drop or invent constraints
  • Re-runs a frozen set of multi-turn conversations on every prompt, model or index change, as the M33 lab brief describes

4. A product manager wants the conversation id in the URL so customers can share a chat with a colleague. What is the risk, and how would you build it?

What a strong answer covers:

  • The thread_id or session_id is the only thing separating one customer’s history from another’s; whoever can choose it can read that history
  • Derives the id on the server from the authenticated user (or checks ownership before loading), never from request text
  • Builds sharing as an explicit, read-only copy or an access grant, with an audit entry
  • Remembers that a persistent checkpointer keeps the thread until it is deleted, so retention and deletion rules apply to it like any customer data

5. Support tickets now run to 60 turns, and prompt cost per turn keeps climbing. Which memory strategy do you pick, and what do you check before shipping it?

What a strong answer covers:

  • Full history sends every earlier message on every turn, so cost per turn grows without limit
  • A window or trim on read flattens the prompt but loses early facts such as the plan or the region; a running summary keeps them for one extra call per fold
  • Prefers trim on read or a summary over deleting messages, so the full thread stays available for audit and replay
  • Tests recall of an early fact on a late turn, and watches the summary channel: with no reducer, writing summary again on a later turn overwrites the accumulated summary

Key Takeaways

  • Memory is the list of messages you resend. Decide on purpose which ones go back, because every one costs tokens on every later turn.
  • Key every history by a session or thread id that your server controls, and choose a store that survives a restart before real users arrive.
  • Rewrite follow-ups into standalone questions before retrieval, and measure hit rate on turns 2 and 3, not only on first questions.
  • Bound long threads by hiding or summarising old turns rather than deleting them, and test that an early fact still reaches the model late in the thread.
