# Editorial explanation

Start from one real user need or concrete failure. Define unfamiliar terms before relying on them. Show the mechanism in a labelled diagram, then follow an input through its decisions, state changes and output. Keep the running example consistent.

Teach each genuine alternative independently: where work happens, what is read or written, what reaches the next component, what is automatic and what must be wired. Give each approach its own diagram. Follow with a shared worked example, a comparison and an actionable decision rule. A table or interactive switcher supplements the diagrams. It does not replace them.

Add a stepper only when moving through stages changes understanding. Add a switcher when choices expose different evidence, state, trade-offs or results. Keep the explanation available without scripting, and label illustrative examples. For a concept with no architectural alternatives, choose an appropriate static explanation instead of inventing competing designs.

Name a failure, show its consequence and connect it to a guard. Explain cost, latency, persistence and recovery only to the extent supported by the source and topic. Preserve negative findings and evidence limits. Put compact recall in the final takeaways rather than repeated memory cards.

Use source-fidelity.md before drafting and during the final comparison. Descriptive headings may improve. Repository contract headings and protected diagrams remain preserved. Useful additions answer a specific learning gap and have clear provenance.
