The ReAct loop and its call cap
Open the lab

The running example is a support agent for the Larkspur Cloud handbook from M10 to M12. Its one tool, search_handbook, is the M10 lab’s TF-IDF retriever over twelve chunks, and its questions are the M10 golden set: Can I export my data after I cancel my plan?, How long does a refund take? and What happens if my server goes down? The interview questions add the tools a real support agent would have, such as an account lookup and a refund action.

TL;DR

  • ReAct interleaves reasoning and tool calls, and reads every observation before choosing the next step. The difference from a single-shot tool call is one edge, tools → model.
  • In the lab, the loop lifts mean evidence recall on the M10 golden set from 0.50 (one search, the M10 baseline) to 1.00 by rewording failed searches, for 9 model calls instead of 3. Every call rereads the whole message list, so cost grows each round.
  • create_agent(model, tools, system_prompt=...) returns that loop as a compiled LangGraph graph (model ⇄ tools) on native tool calls, so there is no text to parse.
  • response_format=Schema on an agent, or with_structured_output(Schema) on a model, returns structured data for the next system to validate; Pydantic is the style that validates it.
  • Middleware hooks run before and after each model call: ModelCallLimitMiddleware bounds the loop, HumanInTheLoopMiddleware pauses irreversible tool calls for approve, edit or reject, PIIMiddleware redacts, SummarizationMiddleware compresses history.

Mental model

The model is the only part that decides; the graph executes and the middleware guards. A run is as long as the model’s decisions make it, so every production agent pairs the loop with a cap, and every irreversible tool with a checkpoint where a person can stop it.

Reason–act–observe

Module M22 built the agent loop by hand: a model that requests tools, a node that runs them, and an edge back to the model. This lesson gives that loop its name, ReAct, and measures what it buys over a single tool call.

Larkspur’s support agent gets How long does a refund take? Its first handbook search returns the refund-window passage and misses the one that says how many days a refund takes. A single tool call ends there, with half the evidence; finding the rest means reading the result and searching again.

ReAct (reason plus act) is an agent that plans one step at a time: it reasons about the next step, calls a tool, observes the result and reasons again, until it replies without asking for a tool. The pattern comes from the ReAct paper by Yao and colleagues (ICLR 2023), listed under References.

The message list is the trace

In LangGraph the whole run lives in one state key: a list of messages that only ever grows. Every model call sees everything that came before. Each part of the loop leaves one kind of message:

Message Written by What it holds
Human message The user The question
AI message with a tool call The model The reasoning step turned into an action: which tool, with which arguments
Tool message The tool node The observation: what the tool returned
AI message without a tool call The model The final answer, which ends the run

Table 1: One ReAct round leaves an AI message and a tool message on the list.

The model never runs a tool itself: it returns a request, and the tool node executes it and appends the result.

One edge makes the loop

A single-shot graph and a ReAct graph have the same nodes. They differ in where the tool node sends its result:

Figure 1: Single shot sends the tool result to the end. ReAct sends it back to the model.

With the edge to the end, the user receives the tool message itself, raw search results, and no search can build on another: the raw-result handoff. With the edge back to the agent, a router returns the run to the model after every observation and ends it when the model stops calling tools.

The recorded comparison asks both graphs one question whose second half depends on the first: Who is the current CEO of the company that created the sci-fi movie Dune, and what was the budget for that company’s most recent film? Both use the same live web-search tool and the same small model:

Single shot 1 current CEO of Legendary Entertainment 2023 The tool message: a list of search results naming the CEO, no budget
ReAct 1 current CEO of Legendary Entertainment 2023 (observation, back to the model)

The ReAct run’s answer combines both observations. The loop costs nothing when no tool is needed: Explain AI in 2 bullets went straight to the end in one model call.

Pitfall: the lenient judge. The notebook then asks an LLM judge to score both runs. It gave the raw-result handoff 7 out of 10 for task completion, though the user received only search results, and the ReAct run 10. The judge was the agent’s own model. A score that rewards an answer nobody wrote measures the judge. Check its scores against a few runs you grade yourself (lesson 22.5).

What each round costs

Every model call rereads the whole message list, and each round costs more than the one before it. The lab estimates the context each run reads as characters divided by four:

Export 1, about 11 2, about 99
Refund 1, about 7 3, about 243
Outage 1, about 9 4, about 451

Table 4: Context read per run in the lab (characters divided by four, an approximation).

The outage run reads about 50 times the context of its single search to go from 0.00 to 1.00 evidence. Context grows faster than the call count because each round carries every earlier observation: lesson 22.1’s context creep, measured.

Native tool calls vs text-based ReAct

The ReAct paper predates tool-calling APIs. It drove the loop with text: the prompt listed the tools and asked the model to write Thought, Action and Action Input lines. The framework stopped generation at Observation, parsed the action out of the text, ran the tool and pasted the result back. Native tool calling moves the same loop onto structured tool calls returned by the provider, so nothing is parsed from prose.

In text-based ReAct the action exists only as characters. A parser reads them back out, and whatever it extracts is what the tool receives:

Figure 2: Text-based ReAct. The parser is the transport, and it passes on quotes and stray whitespace.

With native tool calling the provider returns the action as a structured field. The tool node reads the name and arguments directly:

Figure 3: Native tool calling. No parsing step, and several calls can travel in one reply.

The two transports differ on five points:

Native tool calling Text-based ReAct
How the call travels Structured tool calls from the provider API Free text, parsed with a pattern
Needs a tool-calling model Yes No, any instruction-following model
Parallel calls in one turn Yes No, one action per turn
Visible reasoning Optional Always, the Thought lines
Typical failure Wrong tool or bad arguments Format drift, or arguments polluted by quotes and whitespace

Table 5: The same loop on two transports.

Planted failure: the quoted argument

The recorded comparison runs both on the same two deterministic stubs: a weather lookup that knows New York, London and Tokyo, and a calculator. The question is What’s the weather in Tokyo and calculate 25% of 80?

Run What the model wrote What the tool received Outcome
Text ReAct Action Input: ‘Tokyo’, with the quotes The six characters ‘Tokyo’, an unknown city “Weather data not available”
Text ReAct Action Input: ‘0.25 * 80’, with the quotes A quoted string, which the calculator returned unchanged Five identical calculator calls, then the run stopped at its limit of 6 steps with no answer
Text ReAct, inputs cleaned The same quoted inputs Quotes and whitespace stripped first Answered in 2 tool steps and 3 model calls
Native tool calls Structured arguments Tokyo and 0.25 * 80 Both tools requested in one turn; answered in 2 model calls

The model knew which tool it wanted every time. The failure was in the transport: the tool receives whatever characters the model happened to write. A text-driven agent needs tools that clean their input, and a setting that turns a format break into an observation. Native calls remove the parsing step and let independent calls share a turn, which is why the native run needed one model call fewer. LangChain 1.x builds its agents on them (lesson 23.2); the ReAct idea is unchanged.

Key Takeaways

  • A ReAct agent reasons about one step, calls a tool, reads the result and repeats until it replies without a tool call. The edge from the tool node back to the model is what turns a single-shot graph into that loop.
  • On the Larkspur golden questions the loop lifts mean evidence recall from 0.50 to 1.00, for 9 model calls instead of 3. Every round rereads the whole message list: the outage run reads about 451 tokens against 9 for one search.
  • Prefer native tool calls to text-based ReAct: no parsing, parallel calls in one turn and no quoted-argument failures. Use a fixed workflow when the steps are known.

Check yourself

1. Why does adding one edge from the tools node back to the agent turn a single-shot graph into a ReAct agent?

With the edge from tools to the end, the last message is the tool message. The user gets raw search results and no search can build on another. With the edge back to the agent, the run returns to the model after every observation, so each search can use what earlier results found. The run ends when the model replies without a tool call.

2. In the lab, the first search for the refund question misses the refund-timing chunk. What does the loop do next, what does the run cost, and what does it gain?

The model reads the first result and rewords its search, and the second search finds the refund-timing chunk, which says “Refunds” where the question says “refund”. The run takes 3 model calls and reads about 243 tokens of context, against 1 call and about 7 tokens for the single shot, and lifts evidence recall from 0.50 to 1.00.

3. A text-based ReAct agent picks the weather tool for Tokyo but the tool finds no such city. What failed, and how do you fix it?

The transport failed, not the choice: the model wrote the city with quotes around it, and the tool looked up the quoted string. Clean text inputs before the tool uses them, and turn format breaks into observations the model can read. Native tool calls, which the LangChain 1.x agent uses, remove the parsing step altogether.

Lesson 23.1 wired the ReAct loop node by node. Every Larkspur agent would repeat that wiring: a model node, a tool node, a router and the edge back. LangChain 1.x packages the wiring as one function.

create_agent takes a model, a list of tools and a system prompt, and returns the ReAct loop as a compiled LangGraph graph. Inspecting the graph it returns shows the loop from lesson 23.1, with the nodes renamed:

Edge Kind Taken when
start to model Fixed Every run begins with a model call
model to tools Conditional The model’s reply contains tool calls
tools to model Conditional Always after the tools run: the feedback loop
model to end Conditional The model’s reply contains no tool calls

Table 1: The four edges of the graph the factory returns.

Figure 1: The compiled graph. Four nodes, and the same feedback edge as lesson 23.1.

Because the result is a graph, everything from M08 and M09 applies to it. Streaming shows each new message as it arrives, a checkpointer plus a thread id gives the agent memory, and the input and output are both message lists. The answer is the last message of the returned list; the rest is the trace.

Dependent and independent calls

The loop is fixed, but the model decides how much to do in each turn. When one call needs another’s result, each call waits for its own model turn:

Figure 2: Dependent calls. The email cannot be written before the price arrives, which costs three model calls.

When no call needs another, the model asks for all of them in one reply:

Figure 3: Independent calls. Three lookups share one turn, and the run takes two model calls.

Two recorded runs with stub tools show the difference:

Request Model turn 1 Model turn 2 Model turn 3 Model calls
What’s the stock price of Google? Once you get it, send an email to an analyst. Stock-price call Email call, body quoting the price Answer 3
Weather in Bangalore and Mumbai, and 25 times 4 Three tool calls at once Answer 2

Table 2: Dependent calls take a turn each; independent calls share one.

  • Dependent calls take one turn each. The email body needs the price. The email call cannot be written until the price comes back as an observation.
  • Independent calls share a turn. None of the three lookups needs another’s result. The model requested all three in one reply, and the tool node ran them before the model’s second and last call.

A third case costs one call: given only a restaurant search tool, the agent answered Who are the members of the A-Team? from its own knowledge without searching, because the tool’s description said it covers the restaurant.

Memory is a thread

The factory has no memory class. A checkpointer stores the message list after every step, and runs that pass the same thread id continue the same conversation. Three turns on one thread, then the last question on a fresh one:

Thread Question Messages on the thread How the question was read
A What is the capital of France? 2 Paris
A Any suggestions what to visit there? 4 “There” resolved to Paris
A What about China? 6 What to visit in China
B (new) What about China? 4 As a question about the restaurant, the only context the agent had

Table 3: The same words on two threads.

Thread B shows the failure we call thread amnesia: on a new thread a follow-up loses its referent, and the agent fills the gap from whatever it does have, here its restaurant tool.

Migrating from LangChain 0.x

Older material builds this loop with an agent executor or LangGraph’s prebuilt ReAct agent. The mapping:

LangChain 0.x LangChain 1.x

A maximum iteration count A model-call limit middleware
Verbose printing Streaming the message list
A conversation memory class A checkpointer plus a thread id
Input and output strings Message lists in, message lists out

Table 4: What replaces what.

Renaming the function is not enough: the factory has no prompt argument. Old code that passes one fails with a type error until it is renamed to the system prompt. LangGraph’s prebuilt ReAct agent is deprecated since LangGraph v1.0.

Tools come in three weights: ready-made ones from the community package (an LLM-backed calculator, for example), a decorated function, and a tool class that carries configuration such as which vector store to search. In every case the model chooses tools by name and description, so the description is prompt text.

How the cap decides

The model-call limit middleware counts model calls per run and, optionally, per thread across runs. It checks the count before each model call:

Figure 4: The cap is checked before the model runs, and the last allowed call is the one that matters.

The check runs before the call. A run that needs four model calls is cut off at a cap of 3 even when its evidence is already in the message list. In the lesson 23.1 lab the three golden questions need 2, 3 and 4 calls:

Cap Export (needs 2) Refund (needs 3) Outage (needs 4) Answered
2 Answered Stopped, evidence 1.00 Stopped, evidence 0.00 1 of 3
3 Answered Answered Stopped, evidence 1.00 2 of 3
4 Answered Answered Answered 3 of 3

Table 7: Golden questions answered at each cap in the lab.

We call the stopped-with-evidence rows the starved final call: the cap spent its budget on searches and blocked the one call that would have written the answer. Set the cap from the largest call count your golden questions need, add headroom for rewording, and alert when the share of runs that hit it rises. A rising share points at retrieval (Table 6), not at the cap.

  • One recorded run each. A live model may search a different number of times; the persistent agent’s three searches are one run.
  • A scripted model in Table 7. The lab’s counts are computed, but its searches are the ones a model might write.

Check yourself

1. Why does the weather-and-arithmetic request finish in two model calls, while fetching a stock price and emailing it needs three?

The three weather and arithmetic lookups are independent, so the model requested all of them in one reply and the tool node ran them before the model’s second and last call. The email body needs the price, so the stock-price call must return its observation before the model can write the email call, which costs a turn of its own.

2. Your golden questions need 2, 3 and 4 model calls. What happens at a cap of 2, and how should you set the cap?

Only the export question is answered. The refund run already holds both evidence chunks when the cap stops it, and the outage run has found neither. Set the cap from the largest count the golden set needs, with headroom, and alert when runs hit it.

3. The restaurant FAQ agent rewords its search until the call cap ends the run, and the user never gets the opening hours. Why is raising the cap the weakest fix?

The fault is in retrieval: the index stored the questions without their answers, so every search returns answerless questions. A higher cap only buys more attempts at the same problem. Messages: what the model sees

What you’ll learn

  • Explain the four message types and why the message list is the model’s whole context.

Lesson 23.2 handed the loop to a factory that takes message lists in and gives message lists out. This lesson looks at both sides of that boundary: the messages that go into a model, and the shape of what comes back.

Larkspur’s ticket queue needs three fields from every support conversation: a category, a priority and a refund amount when there is one. The agent’s last message is a paragraph. Getting the fields out of it with string matching breaks the first time the model adds a preamble, and a refund question with no amount invites the model to write one anyway.

Four message types

A message is the unit of context: one turn’s content plus the metadata that says who wrote it. The list you pass is everything the model sees, and an agent run is that list growing:

Type Written by Carries
System message You The role and rules, sent first
Human message The user The question, with optional metadata such as a name and an id
AI message The model Text, tool calls, or both, plus token usage
Tool message Your tool node One tool’s result, tied to the call by its id

Table 1: The message types and their jobs.

The recorded weather agent shows a trace that looks broken when printed as text:

# Message Content Tool calls
0 Human What is the weather like in New York?
1 AI (empty) Weather lookup for New York
2 Tool The weather in New York is sunny.
3 AI The weather in New York is sunny.

Table 2: Four messages from one agent run. The empty AI message is the tool call.

Message 1 is the empty-looking tool call: when the model only calls a tool, its text is empty and the payload sits in the tool calls. Some providers add a short preamble beside the call. An AI message can carry text, a call, both or neither. Print both fields when you debug a run.

Every AI message also reports its token usage, split into input and output because the two are billed at different rates. A short exchange in the recorded messages notebook used 47 input and 8 output tokens.

One interface for every provider

LangChain’s model initializer builds a chat model from a string such as a provider prefix and a model name. Switching from OpenAI to Gemini or Groq is a one-string change and everything downstream (invoke, stream, batch, tool binding) stays the same. Provider classes remain for settings only one provider has.

Streaming changes when the user sees text, not how much is generated. In one recorded run, the streamed answer showed its first words after 0.56 s and finished after 1.90 s; a separate non-streamed call returned its whole answer after 3.42 s. The two calls generated different text; only the first-word time is a fair comparison.

Structured output

Structured output means asking the model for a reply that matches a schema instead of free text. The schema goes to the provider as a machine-readable description, and the provider constrains the reply to it through native structured output or a tool call, depending on what the model supports.

There are two places to attach a schema:

Figure 1: The same schema on a model or on an agent.

  • On a model. Wrapping a model with a schema returns a new runnable whose result is an instance of the schema; the original model is unchanged. The judge in lesson 23.1 is built this way, and its scores arrive as fields.
  • On an agent. Passing a schema as the agent’s response format runs the loop as usual and adds a structured response next to the messages in the result. The recorded contact-extraction agent returned both keys, with the name, email and phone filled in.

The agent path differs from the model path in when the schema applies. Tools run first, and only the reply that ends the loop is shaped by the schema:

Figure 2: A schema on an agent. The loop is unchanged; the schema shapes its last reply.

The same question asked both ways shows the difference:

Call Returned What the program gets
Plain model call: Provide details about the movie Inception An AI message A paragraph with a plot summary to parse
Same call with a four-field movie schema A movie instance Title Inception, year 2010, director Christopher Nolan, rating 8.8
Same, keeping the raw message Raw message, parsed instance, parsing error The instance, no error, and token usage: 119 input, 22 output, 141 total

Keeping the raw message costs nothing and gives two things in production: the token counts for cost tracking, and a parse failure as a value to branch on instead of an exception that ends the request.

Choose Pydantic when the data crosses a trust boundary. If a provider returns text where you declared a number, Pydantic raises and a typed dictionary hands you the text.

The fourth row is the silent default: the code reads as optional and documented, and the model receives a required field with no description.

Pitfall: the forced number. A ticket schema with a required refund amount makes the model write a number for every conversation, including those that mention no refund. Make the field optional with a default of none. Zero and “no refund” then stay distinct. An optional field permits abstention; it does not check that a number the model does write is true.

Descriptions and capability

Field descriptions reach the model as part of the schema. They are prompt text: “the movie’s rating out of 10” tells the model the scale it would otherwise guess. Before switching models, check that the new one supports structured output. LangChain 1.1 added a capability profile per model, sourced from the open models.dev data; for the course’s default model it reports structured output and tool calling as supported and a 128,000-token input limit.

Check yourself

1. When should a structured-output schema be a Pydantic model rather than a typed dictionary?

When the data crosses a trust boundary. Pydantic returns an instance and raises if the provider sends text where you declared a number. A typed dictionary returns a plain dict with no validation and hands you the text.

2. A ticket schema has a required refund amount, and the model writes a number even for conversations that mention no refund. What schema change allows a missing amount, and what does it not guarantee?

Make the field optional with a default of none, so the model can leave the amount empty and zero stays distinct from no refund. It permits abstention only: a number the model does write still needs checking against the source.

3. You give a typed dictionary field a Pydantic-style default and description, yet the field stays required and the model never sees the description. What happened, and what fixes it?

Inside a typed dictionary the assignment is silently discarded, so the converter sees a required field with no description. Marking it not-required fails too, because the converter rejects that marker. Put the default and description in the annotation’s middle slot, or switch to a Pydantic model.

Middleware

Lesson 23.4: Middleware, including human-in-the-loop. Notebooks: 04a_middleware.ipynb

What you’ll learn

  • Explain where middleware hooks run in the agent loop, and how they show up in the compiled graph.
  • Compare message, token and context-fraction triggers for summarising history.
  • Trace an approval through approve, edit and reject, and what each leaves in the message list.
  • Diagnose the provider error that a new message on a paused thread causes.

Lesson 23.2 capped the loop with one middleware. This lesson opens the mechanism up and adds the guard every agent with a write tool needs: a person who can stop the call.

Larkspur’s support agent may look up an account on its own, but sending the customer an email or issuing a refund must wait for a support engineer. The loop from lesson 23.2 has no place to wait. Rebuilding it as hand-wired graph nodes for every guard would mean rewriting the agent each time a rule is added.

Middleware attaches hooks at fixed points of the agent loop: before the model call, after it, and around a model or tool call. Teams use it for observability (logging, timing), transformation (rewriting the prompt, filtering tools), control flow (retries, early exit) and guardrails (call limits, redaction, human approval).

Summarising history: three triggers

Summarisation needs a trigger, the point at which it fires, and a keep setting, how much recent history survives verbatim. Each can be counted in messages, tokens or a fraction of the model’s context window. Three recorded runs, with thresholds set deliberately low so they fire within a few turns:

Turn Messages trigger (10, keep 4): messages Tokens trigger (550, keep 200): tokens, messages Fraction trigger: share of window, messages
1 2 about 140, 4 0.05%, 4
2 4 about 281, 8 0.11%, 8
3 6 about 422, 12 0.16%, 12
4 8 about 446, 8 0.22%, 16
5 10 about 376, 5 0.28%, 20
6 6 about 465, 5 0.33%, 12

Table 3: History size per turn under each trigger. Token figures are a display estimate of characters divided by four.

  • A message count is predictable but a poor proxy for pressure: ten short arithmetic turns and ten long tool results count the same.
  • Tokens track what actually runs out. The token run’s history collapsed twice as long hotel listings piled up. The table’s estimate is rough and does not show the exact point where the middleware’s own counter crossed 550.
  • A fraction keeps its meaning when the model changes. Seven tenths of the window means the same on a 128,000-token model and on one with a million; a hard-coded token count does not. The demo’s tiny fractions only make it fire in six turns.

A checkpointer keeps history across invocations, which is what gives summarisation a long history to work on and what lets an approval pause survive. Within one run, summarisation works on whatever history the run has.

Planted failure: over-redaction

Email redaction ran on a user message and on a tool result. The recorded trail:

Message What the model saw
Human I’m [REDACTED_EMAIL]. Look up account 1029 and tell me the balance and the email on file.
Tool Account 1029: balance ₹42,500, status active, email [REDACTED_EMAIL]
AI The balance for account 1029 is ₹42,500, and the email on file is [REDACTED_EMAIL].

Table 4: Redaction before and after the model call.

The model never saw either address, which is the point. But the user asked for the email on file and received a placeholder. We call this over-redaction: a redaction rule that covers a field the user is entitled to see. Decide per field whether the model needs it, and return entitled data to the user through code that bypasses the model.

Writing your own

A custom middleware subclasses the agent middleware class and overrides the hook it needs. Two rules are easy to break, and both fail quietly or late:

  • Every hook takes the state and the runtime. A hook defined without the runtime argument raises a type error when the agent runs, not when it is built.
  • A hook returns a state update; it never edits the state it was given. To hand a value from before the model to after it, declare the key on a custom state schema and return it. The recorded timing logger did this and reported 1.15 s and 0.81 s for the two model calls of one run.

To end a run early, a hook declares that it may jump to the end and returns that jump with a final message, as the call-limit middleware does. The M23 lab’s off-topic guard uses the same shape.

Human approval

The approval middleware turns a consequential tool call into a decision. Gate writes, such as sending email or issuing a refund. Authorised reads can run freely, though a sensitive read may still need access control.

Planted failure: the orphaned tool call

When the middleware interrupts, the AI message carrying the tool call is already saved on the thread. If the app sends a new user message on that thread instead of resuming it, the history becomes:

Index Message State
0 Human: send an email to …
1 AI with a send-email tool call Never answered
2 Human: the new message Where a tool message was required

Table 5: The history after a new message on a paused thread.

The provider rejects the next model call (OpenAI, error 400): an assistant message with tool calls must be followed by tool messages responding to each call id, and the error points at index 2. We call this the orphaned tool call. The only valid next step on a paused thread is a resume with decisions. If the user wants a separate conversation, start a new thread.

In practice: Larkspur’s support agent

  1. Gate the email and refund tools with human approval; leave the account lookup ungated so approvals stay rare.
  2. Show pending interrupts per thread in the support console and block new messages on that thread until a reviewer decides.
  3. Trigger summarisation on a fraction of the context window, with a checkpointer for every conversation.
  4. Redact payment details before the model, and decide per field what a customer may see in answers.
  5. Keep the model-call limit from lesson 23.2, sized from the golden questions, on the same agent: it bounds whatever the other hooks let through.

Key Takeaways

  • Middleware hooks run before, after or around model and tool calls, appear as nodes in the compiled graph, and run in the order you list them. A custom hook takes the state and the runtime and returns a state update.
  • Trigger summarisation on tokens or a fraction of the context window rather than a message count, and redact only what the model does not need, or the user loses data they are entitled to.
  • Gate consequential writes with human approval and resume a paused thread with one decision per call. A new user message on that thread orphans the tool call, and the provider rejects the next request.

Check yourself

1. Why should human approval gate tools that write, such as sending email, but not every tool that reads?

The middleware turns an irreversible call into a decision, which is what consequential writes need. Authorised reads can run without a pause, which keeps approvals rare; sensitive reads still need an access policy. The pause is a real suspension checkpointed under the thread id, so approval needs a checkpointer.

2. With summarisation triggered at 10 messages and keeping 4, history grows by two messages a turn. On which turn does it shrink, to how many messages, and why is a token trigger usually better?

On the sixth turn: history grew 2, 4, 6, 8 and 10 and dropped to 6 when the summary replaced the older turns. A message count treats a short arithmetic turn and a long tool result the same, while tokens or a fraction of the window track what actually runs out.

3. An agent paused on a send-email approval is invoked again with a new user message, and OpenAI returns error 400. Why, and what should the app do?

The AI message with the tool call was saved on the thread when the middleware interrupted, and the new message leaves that call without a matching tool message, which the provider rejects. Resume the paused thread with one decision per gated call, or start a new thread for a separate conversation.

Design choices worth copying

Choice Why
Fail soft in every tool An exception ends the run; an error string such as “Timeout extracting from” a page lets the agent answer from the pages that did load
Cut each page to 1,500 characters Three full pages can fill the context window, and attractions usually sit near the top of a travel page (lesson 22.1’s context creep)
Fetch pages in parallel and stop waiting One slow site would otherwise stall the whole answer; stragglers are abandoned after 15 seconds
Cap model calls at 6 Bounds cost if the agent keeps searching on a thin result (lesson 23.2’s runaway loop)
No Thought and Action format in the prompt Native tool calls need none, and the format would leak into the answer (lesson 23.1)

Key Takeaways

  • A use-case system prompt, two well-described tools and the agent factory with a call cap are the whole agent; the work is in making the tools behave on the live web.
  • Tools over live sources must fail soft, cap what they return and stop waiting for slow pages, or one call can end the run or flood the context.

Check yourself

1. The user types only Kolkata. Why does the agent call both tools, and why usually in a single model turn?

The system prompt says that any destination needs attractions and the current weather, so the model knows what the word asks for. Neither tool needs the other’s result, so the model can request both in one reply and the tool node runs them before the model’s second call.

2. Three pages come back from a search: one loads, one times out after 15 seconds and one blocks the request. What does the agent receive, and why is that better than an exception?

It receives the first 1,500 characters of the page that loaded and two short error strings for the others. An exception would end the run; error strings let the model answer from the page it has. The cost is that monitoring which counts exceptions never sees those failures.

3. In the tool-selection check, the model asks only for the web search when the question names attractions and weather. Where do you look first?

At the weather tool’s description, because the model chooses tools from their names and descriptions. A description that does not say to use it whenever a destination, the weather or the temperature comes up leaves the model guessing. Fix it and repeat the one bound call before building the agent.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s support agent cost three times as much yesterday as the day before. Traces show some runs making a dozen search_handbook calls with reworded queries before giving up. What do you check, and what do you change?

What a strong answer covers:

  • Reads the ToolMessages in the long runs first: a loop that keeps rewording usually means the tool returns nothing useful, such as an index re-ingested without the answer text
  • Checks what changed that day (an index rebuild, a new document type, a prompt that says “never give up”) against the calls-per-run distribution
  • Fixes what the model sees (data, retrieval depth, result formatting, the tool description) before touching the cap; raising the cap only buys more attempts
  • Keeps a ModelCallLimitMiddleware with run_limit sized from the golden set’s call counts plus headroom, and alerts on the share of runs that hit it

2. Product wants a monthly account summary for every Larkspur customer: usage, invoices, open incidents. A teammate wants to reuse the ReAct support agent. What do you build instead, and why?

What a strong answer covers:

  • The steps are known in advance, so a planned pipeline (fetch usage, fetch invoices, fetch incidents, write) is cheaper, has a fixed cost per customer and runs the same way every time
  • ReAct pays off when the next step depends on what a result says; a batch report has no such step
  • Testing and debugging are easier when every run takes the same path; failures are recorded per step instead of steering the run
  • Keeps the agent for open support questions, and considers plan first, then react, if a summary section sometimes needs follow-up
  • Lesson 26.1 (M26, p07_advanced_agents/m26_coding_computer_use_and_deep_agents/) works through planned pipelines against the ReAct loop on applied agents

3. You replace the M10 baseline retriever with a ReAct agent that uses it as a tool. How do you show the change is worth it?

What a strong answer covers:

  • Runs the frozen golden set through both and reports evidence recall and answer quality per question, not only the mean (in the lab, mean recall goes from 0.50 to 1.00)
  • Reports what the loop costs: model calls per question (the lab’s questions need 2, 3 and 4), tokens read, latency at p50 and p95
  • Grades answers with a judge that is not the agent’s own model, since live search results and sampling make single runs noisy
  • Checks the questions the baseline already answered for regressions, such as a loop that over-searches easy questions

4. Larkspur’s agent can call issue_refund behind HumanInTheLoopMiddleware. A support engineer, tired of waiting, pastes the customer’s message into the same conversation again, and the next model call fails with a 400 about tool_call_ids. What happened, and how do you prevent it?

What a strong answer covers:

  • The interrupt saved the AIMessage with the issue_refund call on the thread; the new user message left that call without a ToolMessage, which the provider rejects
  • The only valid next step on a parked thread is Command(resume={"decisions": [...]}), with one decision per gated call
  • The UI shows pending interrupts per thread_id and blocks new messages until a reviewer approves, edits or rejects
  • Uses edit to fix a wrong amount instead of rejecting, and keeps reads such as an account lookup ungated so approval stays rare

5. The ticketing system needs {category, priority, refund_amount} from every Larkspur conversation. Some days the agent returns prose; on questions with no refund it writes refund_amount: 0. How do you make the output reliable?

What a strong answer covers:

  • Passes a Pydantic schema as response_format on create_agent and reads structured_response, so the provider constrains the reply
  • Makes refund_amount optional with a None default, so the model is not forced to invent a number; 0 and “no refund” stay distinct
  • Writes field descriptions as instructions (units, allowed categories), because they reach the model as part of the schema
  • Logs parse failures with include_raw=True where the model is called directly, and checks llm.profile for structured-output support before switching models

Key Takeaways

  • Use ReAct when the next step depends on what a tool returns; use a planned pipeline when the steps are known.
  • Read the ToolMessages before you blame the model. A loop that keeps searching usually has a tool that returns the wrong thing.
  • Give every loop a call cap sized from your golden set, and gate every irreversible tool with human approval.
  • When code consumes the answer, ask for a schema, validate it with Pydantic, and make fields optional when the source may not contain them.
