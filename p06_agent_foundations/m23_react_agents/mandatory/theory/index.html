The ReAct loop and its call cap
Open the lab

The running example is a support agent for the Larkspur Cloud handbook from M10 to M12. Its one tool, search_handbook, is the M10 lab’s TF-IDF retriever over twelve chunks, and its questions are the M10 golden set: Can I export my data after I cancel my plan?, How long does a refund take? and What happens if my server goes down? The interview questions add the tools a real support agent would have, such as an account lookup and a refund action.

TL;DR

  • ReAct interleaves reasoning and tool calls, and reads every observation before choosing the next step. The difference from a single-shot tool call is one edge, tools → model.
  • In the lab, the loop lifts mean evidence recall on the M10 golden set from 0.50 (one search, the M10 baseline) to 1.00 by rewording failed searches, for 9 model calls instead of 3. Every call rereads the whole message list, so cost grows each round.
  • create_agent(model, tools, system_prompt=...) returns that loop as a compiled LangGraph graph (model ⇄ tools) on native tool calls, so there is no text to parse.
  • response_format=Schema on an agent, or with_structured_output(Schema) on a model, returns structured data for the next system to validate; Pydantic is the style that validates it.
  • Middleware hooks run before and after each model call: ModelCallLimitMiddleware bounds the loop, HumanInTheLoopMiddleware pauses irreversible tool calls for approve, edit or reject, PIIMiddleware redacts, SummarizationMiddleware compresses history.

Mental model

The model is the only part that decides; the graph executes and the middleware guards. A run is as long as the model’s decisions make it, so every production agent pairs the loop with a cap, and every irreversible tool with a checkpoint where a person can stop it.

Reason–act–observe

Lesson 23.1: The ReAct loop in LangGraph; tool calling vs ReAct. Notebooks: 01a_react_agent_langgraph.ipynb, 01b_tool_calling_vs_react.ipynb

Larkspur’s first refund search returns a related passage but misses the timing rule. A single tool call cannot repair that result. You will trace how an agent rephrases the search after reading it, measure the extra calls, and test what happens when the call limit blocks the final answer.

Step 1: Read the growing message history

A ReAct agent does not plan its steps up front. It reasons about the next step only, acts by calling a tool, observes the result, and reasons again with that result in front of it. The loop ends when the model replies without asking for a tool (Yao et al., ReAct: Synergizing Reasoning and Acting in Language Models, ICLR 2023).

In LangGraph the whole run lives in one state key, a message list with the add_messages reducer, so every model call sees everything that came before:

HumanMessage   the question
AIMessage      tool_calls=[search_handbook(...)]     reason + act
ToolMessage    what the tool returned                observe
AIMessage      another tool call, or the answer

Step 2: Add the feedback edge

The model never runs a tool. bind_tools() lets it return a request for a tool call; ToolNode executes the request and appends the ToolMessage. The difference between a one-shot augmented LLM and an agent is one edge:

With tools → END, the last message is the ToolMessage itself: the user gets search snippets, and no search can build on another. With tools → agent, tools_condition sends the run back to the model after every observation and ends it when the model stops calling tools. The recorded comparison asks both graphs a question that needs a chain of searches (the company behind Dune, its CEO, its latest film, that film’s budget). The single-shot graph returned a ToolMessage. The loop wrote an answer from several searches, each naming something only an earlier result contained. The same loop costs nothing extra on a question that needs no tool: Explain AI in 2 bullets goes START → agent → END in one call.

Step 3: Compare evidence and completed answers

The interactive lab runs this loop over the twelve Larkspur handbook chunks from the M10 lab. The tool, search_handbook, returns the top two chunks by real TF-IDF. The model is scripted: it writes the queries a model might write and answers once the evidence is in the message list. The retrieval, the loop and the counts are computed. On the three M10 golden questions:

Question Single shot ReAct ReAct, run_limit=3
Can I export my data after I cancel my plan? evidence 1.00, raw tool output 1.00, 2 calls, answered answered
How long does a refund take? 0.50, raw tool output 1.00, 3 calls, answered answered
What happens if my server goes down? 0.00, raw tool output 1.00, 4 calls, answered stopped at the cap, evidence 1.00
Mean, total 0.50, 3 calls, 0 of 3 answered 1.00, 9 calls, 3 of 3 answered 8 calls, 2 of 3 answered

Read the evidence and completion columns separately:

  • Single shot equals the M10 baseline. One top-2 retrieval per question gives the same mean recall, 0.50, and the user receives chunks instead of an answer.
  • The loop recovers vocabulary mismatch by rewording. The refund question’s first search misses refund-timing (“Refunds” in the chunk, “refund” in the question). The second, written after reading the first result, finds it. The outage question needs three searches: the question’s own words and “server outage” both rank reboot and sizing first, and “what happens during an outage incident” returns incidents and sla.
  • Every call rereads the whole list. The outage run reads about 451 tokens of context over four calls, against 9 for the single search. Cost grows with every round, which is why a loop needs a cap (lesson 23.2).
  • A cap set too low cuts off the answer, not the search. At run_limit=3 the outage run already holds both evidence chunks when the middleware stops it. The call it blocks is the one that would have written the answer.

ReAct earns its extra calls on questions whose path depends on what the searches find. When you already know the fixed sequence of steps, a workflow is cheaper, more predictable and easier to test (M24, and lesson 26.1 in M26).

Native tool calls vs text-based ReAct

Step 1: Compare structured calls with parsed text

The ReAct paper predates tool-calling APIs. It drove the loop with text: the prompt listed the tools and asked the model to write Thought:, Action: and Action Input: lines. The framework stopped generation at Observation:, parsed the action with a regular expression, ran the tool and pasted the result back. Native tool calling moves the same loop onto structured tool_calls returned by the provider.

Native tool calling Text-based ReAct
How the call travels Structured tool_calls from the provider API Free text, parsed with a regex
Needs a tool-calling model Yes No, any instruction-following model
Parallel calls in one turn Yes No, one Action per turn
Visible reasoning Optional Always, the Thought: lines
Typical failure Wrong tool or bad arguments Format drift, or arguments polluted by quotes and whitespace

Step 2: Inspect a transport failure

The recorded comparison runs both on the same two stub tools. With gpt-4o-mini, the text agent often wrote Action Input: 'Tokyo' with the quotes, the tool looked up the city 'Tokyo' and found nothing, and the calculator received '0.25 * 80' as a quoted string. The model knew which tool it wanted. The transport failed. Text-driven tools need input cleaning, and handle_parsing_errors=True turns a format break into an observation the model can react to.

On What’s the weather in Tokyo and calculate 25% of 80? the native agent asked for both tools in one turn and needed 2 model calls. The text agent, one Action per turn, needed 3. LangChain 1.x create_agent uses native tool calls, so there is nothing to parse. The ReAct idea, read every observation before choosing the next step, is unchanged.

Key Takeaways

  • A ReAct agent reasons about one step, calls a tool, reads the result and repeats until it replies without a tool call. The tools → agent edge is what turns a single-shot graph into that loop.
  • Rewording after each observation recovers vocabulary mismatch, but every call rereads the whole message list. In the lab the outage run read about 451 tokens over four calls, against 9 for one search.
  • Prefer native tool calls to text-based ReAct. They need no regex parsing, allow parallel calls in one turn and avoid format drift such as quoted arguments. Use a fixed workflow when the steps are known.

create_agent

Lesson 23.2: ReAct with LangChain create_agent. Notebooks: 02a_react_with_create_agent.ipynb

You need a Larkspur agent that can inspect a tool result and decide whether another lookup is necessary. You will read the graph built by create_agent, distinguish dependent from independent calls, and diagnose a loop that repeatedly retrieves documents without the answer.

Step 1: Inspect the compiled loop

create_agent(model, tools, system_prompt=...) from langchain.agents builds the loop of lesson 23.1 for you and returns a compiled LangGraph graph (CompiledStateGraph). Its compiled structure exposes the loop:

nodes: __start__, model, tools, __end__
__start__ -> model
model -> tools      (conditional: the model asked for a tool)
tools -> model      (the ReAct feedback loop)
model -> __end__    (conditional: no tool call)

Because it is a graph, everything from M08 and M09 applies: .stream(..., stream_mode="values") replaces 0.x’s verbose=True, and a checkpointer plus a thread_id gives memory. Input and output are message lists: invoke({"messages": [...]}) returns the whole trail, and result["messages"][-1] is the answer.

Step 2: Separate dependent and independent calls

The model decides how much to do per turn:

  • Dependent calls take one turn each. Get Google’s price, then email it to an analyst needs get_stock_price, an observation, then send_email, because the email body needs the price.
  • Independent calls share a turn. Weather in Bangalore and Mumbai, and 25 * 4 came back as three tool calls in one AIMessage. The tools node ran all three before the model’s second and last call.

Step 3: Migrate the input and control settings

What changed from LangChain 0.x, in the migration comparison:

LangChain 0.x LangChain 1.x
initialize_agent(...), create_tool_calling_agent + AgentExecutor, or LangGraph’s create_react_agent(prompt=...) create_agent(llm, tools, system_prompt=...)
max_iterations=3 ModelCallLimitMiddleware(run_limit=3)
verbose=True .stream(..., stream_mode="values")
memory=ConversationBufferMemory(...) checkpointer= plus thread_id in the config
invoke({"input": ...}) returns {"output": ...} invoke({"messages": [...]}) returns {"messages": [...]}

Renaming only the function is not enough: the old prompt= argument raises TypeError on create_agent, which takes system_prompt=. create_react_agent in langgraph.prebuilt is deprecated since LangGraph v1.0.

Tools come in three weights. load_tools (now in langchain_community) gives ready-made ones such as llm-math; @tool turns a function into a tool. A BaseTool subclass carries configuration, such as which vector store to search. In every case the model chooses tools by their name and description, so the description is prompt text.

Call limits and runaway loops

Step 1: Reproduce an answerless retrieval

A loop that decides its own length can run long. The controlled failure uses a restaurant FAQ indexed badly, with only the questions stored and the answers lost. Asked When does the restaurant open?, the recorded plain-agent run searched once, saw four questions and no hours, and said it could not answer. An agent told to keep searching until it found the answer reworded its query again and again, getting the same answerless questions back each time, until ModelCallLimitMiddleware(run_limit=3, exit_behavior="end") ended the run and appended its notice. The cap bounded the bill. The user still had no opening hours.

Step 2: Fix the evidence before increasing the cap

Rank the fixes by how much they change what the model sees:

Fix Where
1. Fix the data: store each question with its answer ingestion
2. Retrieve more documents (search_kwargs={"k": 6}) the retriever
3. Format results clearly (“Restaurant Information:” headers) the tool’s return value
4. Say in the description what the tool returns the tool’s description
5. Raise the call cap create_agent(middleware=[...])

Fix 5 is the least effective: it buys more attempts at a retrieval problem. With fixes 1 to 4 the same question took one search and one answer, under the same cap.

Step 3: Budget the final answering call

ModelCallLimitMiddleware counts model calls per run (run_limit) and per thread across runs (thread_limit). It checks before each model call. At the limit, exit_behavior="end" jumps to the end with an AIMessage such as Model call limits exceeded: run limit (3/3), and "error" raises ModelCallLimitExceededError. In the M23.1 lab the golden questions need 2, 3 and 4 calls. At run_limit=2 only the export question is answered, even though the refund run already holds both evidence chunks. Set the cap from the call counts your golden set needs, with headroom, and alert when runs hit it.

Structured output

Lesson 23.3: Models, messages and structured output in LangChain 1.x. Notebooks: 03c_structured_output.ipynb, 03a_model_integration.ipynb (optional), 03b_messages.ipynb (optional)

A Larkspur ticket queue needs fields it can validate, such as category and an optional refund amount. Prose alone is hard to route reliably. You will choose where to attach an output schema, inspect what it returns, and distinguish a missing value from a fabricated one.

Step 1: Choose where the schema is applied

An agent’s last message is prose. When the next consumer is code (a ticket queue, a database row, a judge’s score), ask for a schema instead. A structured-output integration sends a machine-readable schema, using a provider-supported mechanism such as native structured output or tool calling. Confirm which mechanism your model supports and handle validation failures.

There are two places to attach a schema:

  • On a model. llm.with_structured_output(Movie) returns a new runnable; llm itself is unchanged. Its invoke() returns a Movie instead of an AIMessage. The judge in lesson 23.1 is built this way, so its scores are fields rather than sentences.
  • On an agent. create_agent(model=llm, response_format=ContactInfo) runs the agent as usual and adds structured_response to the result state, next to messages. It selects ProviderStrategy where the provider supports native structured output.

Step 2: Compare returned values and validation

The three schema styles differ in what they check:

Style Returns Validation Optional field
Pydantic BaseModel an instance yes, raises on a wrong type budget: float \| None = Field(None, description=...)
TypedDict a plain dict none Annotated[float \| None, None, "description"]
@dataclass an instance none

Choose Pydantic when the data crosses a trust boundary: if a provider returns a nonnumeric string where you declared an int, Pydantic raises and TypedDict hands you the string. In the tested schema conversion, there are two TypedDict traps: = Field(...) inside a TypedDict is silently discarded, so the field stays required and its description never reaches the model. NotRequired[...] is rejected by LangChain’s schema converter (TypeError: NotRequired accepts only a single type). Use the middle slot of Annotated for the default.

Step 3: Inspect descriptions and missing values

Three details matter in production:

  • Descriptions are prompt text. Field(description="The movie's rating out of 10") tells the model the scale. Without it the model guesses one.
  • Optional fields allow missing values. A field the source may not contain (a budget, a refund amount on a question that has none) should be optional with a None default, so the schema does not require a number when the source has none. This permits abstention. It does not guarantee factual correctness.
  • include_raw=True returns {"raw", "parsed", "parsing_error"}. You keep the AIMessage with its usage_metadata (119 input and 22 output tokens for the recorded four-field Movie), and a parse failure becomes a value you can branch on instead of an exception.

Test missing and invalid values locally. This Pydantic check needs no model and makes the optional-field behaviour observable.

from pydantic import BaseModel, ValidationError

class Ticket(BaseModel):
    refund_amount: float | None = None

print(Ticket().model_dump())
try:
    Ticket(refund_amount="unknown")
except ValidationError as error:
    print(error.errors()[0]["type"])

Expected output

{'refund_amount': None}
float_parsing

Pydantic permits the absent amount but rejects a nonnumeric string. Its default validation can coerce compatible values, such as a numeric string, unless strict types are requested.

Step 4: Check capability and raw parsing results

Not every model supports structured output. llm.profile (LangChain 1.1) reports capabilities from the open models.dev data. For gpt-4o-mini it lists structured_output: true, tool_calling: true and max_input_tokens: 128000. Branch on it rather than guessing.

The underlying model and message APIs explain what travels through this boundary. init_chat_model builds a model for any provider behind one interface, with streaming and batching. Messages are the unit of context: SystemMessage, HumanMessage, AIMessage and ToolMessage, and the list you pass is all the model sees. An AIMessage that asks for a tool usually has content="" and carries the call in .tool_calls, so print both when you debug a run.

Then send a nonnumeric string and confirm that Pydantic raises a validation error. A permitted missing value and a supported factual value are different checks.

Key Takeaways

  • Ask for a schema when code consumes the output. with_structured_output() makes a model return a schema instance, and response_format= adds structured_response to an agent’s result next to messages.
  • Use Pydantic when data crosses a trust boundary, because it validates types and TypedDict does not. Inside a TypedDict, = Field(...) is silently dropped.

Check yourself

1. When should a structured-output schema be a Pydantic model rather than a TypedDict?

When the data crosses a trust boundary. Pydantic returns an instance and raises if the provider sends a nonnumeric string where you declared an int. A TypedDict returns a plain dict with no validation and hands you the string.

2. A ticket schema has a required refund amount, and the model writes a number even for questions that mention no refund. What schema change allows a missing amount?

Make the field optional with a None default, for example refund_amount: float | None = Field(None, description=...). A required field forces the model to write a value, while an optional one lets it leave a missing fact empty.

3. You add a field description inside a TypedDict with an equals Field call, yet the field stays required and the model never sees the description. What happened?

= Field(...) inside a TypedDict is silently discarded. NotRequired[...] will not help either, because LangChain’s schema converter rejects it. Put the default and description in Annotated[float | None, None, "description"], or switch to Pydantic.

Middleware

Lesson 23.4: Middleware, including human-in-the-loop. Notebooks: 04a_middleware.ipynb

Larkspur’s agent may read account information automatically, but sending a message needs review. You will place hooks around the model and tool calls, inspect the saved approval request, and resume the same thread without leaving a tool call unanswered.

Step 1: Locate the hooks in the compiled graph

Middleware attaches hooks at fixed points of the create_agent loop: before the model call, after it, and around a model or tool call. You use it for observability (logging, timing), transformation (rewriting the prompt, filtering tools), control flow (retries, early exit) and guardrails (call limits, PII redaction, human approval), without rebuilding the loop as raw LangGraph nodes.

Inspect the graph to see how these middleware hooks are represented. The recorded node lists are:

SummarizationMiddleware              model, SummarizationMiddleware.before_model
HumanInTheLoopMiddleware             model, tools, HumanInTheLoopMiddleware.after_model
PIIMiddleware("email") + call limit  model, tools, PIIMiddleware[email].before_model, PIIMiddleware[email].after_model,
                                     ModelCallLimitMiddleware.before_model, ModelCallLimitMiddleware.after_model

The built-ins used in this comparison:

Middleware What it does Key arguments
SummarizationMiddleware Before the model call, replaces old history with a summary, keeps recent messages verbatim model (the summariser), trigger and keep in ("messages", n), ("tokens", n) or ("fraction", f)
HumanInTheLoopMiddleware After the model call, pauses before a gated tool call runs interrupt_on={tool: {"allowed_decisions": [...]}}, or False to let a tool run
PIIMiddleware Before and after the model call, redacts one PII type in inputs and tool results the type ("email", "credit_card", "ip", …), strategy="redact", apply_to_input, apply_to_tool_results
ModelCallLimitMiddleware Counts model calls after each call, checks them before the next, and ends the run at the cap run_limit, thread_limit, exit_behavior

Step 2: Observe summarisation and state updates

With trigger=("messages", 10) and keep=("messages", 4), the recorded history grew 2, 4, 6, 8, 10 over five turns and dropped to 6 on the sixth, when the summary replaced the older turns. A message count is predictable but a poor proxy for context pressure. Tokens track what runs out, and a fraction of the context window keeps its meaning when you change models. A checkpointer preserves history across invocations and is required to resume an approval interrupt. Summarisation can also operate on the history supplied within a run. It does not itself require persistence.

Middleware runs in the order you list it. A custom one subclasses AgentMiddleware and overrides the hook it needs, with two rules that are easy to break. Every hook takes (self, state, runtime). Leaving out runtime raises TypeError at run time. And a hook returns a state update instead of mutating state: to pass a value from before_model to after_model, declare it on a custom state_schema and return {"key": value}. To end a run early, follow ModelCallLimitMiddleware’s own before_model: it is decorated with @hook_config(can_jump_to=["end"]) and returns {"jump_to": "end", "messages": [AIMessage(...)]}. The M23 lab brief’s off-topic guard has the same shape.

Step 3: Pause before the tool executes

HumanInTheLoopMiddleware turns an irreversible tool call into a decision. In this example, gate writes such as sending email or issuing a refund and allow authorised reads. A sensitive read can also need approval or access control.

Step 4: Resume with one decision per call

The pause is a real suspension: the state is checkpointed under the thread_id and nothing runs until you resume with one decision per gated call. The three decisions, as the recorded message trails show them:

  • Approve. The tool runs with the model’s arguments.
  • Edit. {"type": "edit", "edited_action": {"name": ..., "args": {...}}} replaces the arguments, and the tool runs with yours. The ToolMessage tells the model a reviewer replaced its call, so it does not re-issue the original.
  • Reject. The tool never runs. The model receives a ToolMessage saying the user rejected the call and not to retry unless asked, and it explains to the user that it could not send.

Step 5: Diagnose an unanswered tool call

One pitfall breaks real deployments. When the middleware interrupts, the AIMessage with the tool call is already saved on the thread. Invoking that thread again with a new user message instead of Command(resume=...) leaves the call unanswered, and the provider rejects the next request: An assistant message with ‘tool_calls’ must be followed by tool messages responding to each ‘tool_call_id’ (OpenAI, error 400). Resume a parked thread, or start a new one.

Try it yourself

Check the trace for a matching tool result before another model request. If the user wants a separate conversation, start a new thread rather than overwriting the pending decision.

Key Takeaways

  • Middleware hooks run before, after or around model and tool calls, in the order you list them. A custom hook takes (self, state, runtime) and returns a state update instead of mutating state.
  • Trigger summarisation on tokens or a fraction of the context window rather than a message count. Use a checkpointer to preserve history across runs and to resume human approval. Summarisation itself can operate on history within a run.
  • Gate consequential writes and apply the appropriate access policy to reads. Resume a paused thread with Command(resume=...). A new user message on it leaves the tool call unanswered, and the provider rejects the next request.

Check yourself

1. Why should human approval gate tools that write, such as sending email, but not tools that only read?

The middleware turns an irreversible call into a decision, which makes it useful for consequential writes. Authorised reads can run without a pause in this example. Sensitive reads still need an access policy. The pause is a real suspension checkpointed under the thread_id, so approval needs a checkpointer.

2. With summarisation triggered at 10 messages and keeping 4, history grows by two messages a turn. On which turn does it shrink, and to how many messages?

On the sixth turn. The recorded history grew 2, 4, 6, 8 and 10 over five turns and dropped to 6 on the sixth, when the summary replaced the older turns. A message count is predictable but a poor proxy for context pressure. Tokens or a fraction of the window track what runs out.

3. An agent paused on a send_email approval is invoked again with a new user message, and OpenAI returns error 400. Why, and what should the app do?

The AIMessage with the tool call was saved on the thread when the middleware interrupted, and the new message leaves that call without a matching tool message, which the provider rejects. Resume the parked thread with Command(resume=...), one decision per gated call, or start a new thread.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s support agent cost three times as much yesterday as the day before. Traces show some runs making a dozen search_handbook calls with reworded queries before giving up. What do you check, and what do you change?

What a strong answer covers:

  • Reads the ToolMessages in the long runs first: a loop that keeps rewording usually means the tool returns nothing useful, such as an index re-ingested without the answer text
  • Checks what changed that day (an index rebuild, a new document type, a prompt that says “never give up”) against the calls-per-run distribution
  • Fixes what the model sees (data, retrieval depth, result formatting, the tool description) before touching the cap; raising the cap only buys more attempts
  • Keeps a ModelCallLimitMiddleware with run_limit sized from the golden set’s call counts plus headroom, and alerts on the share of runs that hit it

2. Product wants a monthly account summary for every Larkspur customer: usage, invoices, open incidents. A teammate wants to reuse the ReAct support agent. What do you build instead, and why?

What a strong answer covers:

  • The steps are known in advance, so a planned pipeline (fetch usage, fetch invoices, fetch incidents, write) is cheaper, has a fixed cost per customer and runs the same way every time
  • ReAct pays off when the next step depends on what a result says; a batch report has no such step
  • Testing and debugging are easier when every run takes the same path; failures are recorded per step instead of steering the run
  • Keeps the agent for open support questions, and considers plan first, then react, if a summary section sometimes needs follow-up
  • Lesson 26.1 (M26, p07_advanced_agents/m26_coding_computer_use_and_deep_agents/) works through planned pipelines against the ReAct loop on applied agents

3. You replace the M10 baseline retriever with a ReAct agent that uses it as a tool. How do you show the change is worth it?

What a strong answer covers:

  • Runs the frozen golden set through both and reports evidence recall and answer quality per question, not only the mean (in the lab, mean recall goes from 0.50 to 1.00)
  • Reports what the loop costs: model calls per question (the lab’s questions need 2, 3 and 4), tokens read, latency at p50 and p95
  • Grades answers with a judge that is not the agent’s own model, since live search results and sampling make single runs noisy
  • Checks the questions the baseline already answered for regressions, such as a loop that over-searches easy questions

4. Larkspur’s agent can call issue_refund behind HumanInTheLoopMiddleware. A support engineer, tired of waiting, pastes the customer’s message into the same conversation again, and the next model call fails with a 400 about tool_call_ids. What happened, and how do you prevent it?

What a strong answer covers:

  • The interrupt saved the AIMessage with the issue_refund call on the thread; the new user message left that call without a ToolMessage, which the provider rejects
  • The only valid next step on a parked thread is Command(resume={"decisions": [...]}), with one decision per gated call
  • The UI shows pending interrupts per thread_id and blocks new messages until a reviewer approves, edits or rejects
  • Uses edit to fix a wrong amount instead of rejecting, and keeps reads such as an account lookup ungated so approval stays rare

5. The ticketing system needs {category, priority, refund_amount} from every Larkspur conversation. Some days the agent returns prose; on questions with no refund it writes refund_amount: 0. How do you make the output reliable?

What a strong answer covers:

  • Passes a Pydantic schema as response_format on create_agent and reads structured_response, so the provider constrains the reply
  • Makes refund_amount optional with a None default, so the model is not forced to invent a number; 0 and “no refund” stay distinct
  • Writes field descriptions as instructions (units, allowed categories), because they reach the model as part of the schema
  • Logs parse failures with include_raw=True where the model is called directly, and checks llm.profile for structured-output support before switching models

Key Takeaways

  • Use ReAct when the next step depends on what a tool returns; use a planned pipeline when the steps are known.
  • Read the ToolMessages before you blame the model. A loop that keeps searching usually has a tool that returns the wrong thing.
  • Give every loop a call cap sized from your golden set, and gate every irreversible tool with human approval.
  • When code consumes the answer, ask for a schema, validate it with Pydantic, and make fields optional when the source may not contain them.
