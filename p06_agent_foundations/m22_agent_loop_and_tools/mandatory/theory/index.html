M22 The agent loop and tool calling

A language model on its own can only write text. It cannot check whether a server is running or look up a policy. Tool calling closes that gap: you describe a few functions to the model, the model replies with a request to call one of them, your code runs the function, and the result goes back to the model as part of the conversation. An agent is a loop around that exchange, repeated until the model has what it needs to answer. This module covers how the loop works, how a tool is described to the model, what happens when a tool fails, how to score whether the model used its tools well, and when to let the provider run a tool for you.

Where a tool error goes
Open the lab

The running example is a support agent for Larkspur Cloud, the fictional host from M10 to M12. It has two tools that run in your own code (client-side tools). search_handbook ranks the twelve handbook chunks from the M10 lab with TF-IDF and returns the best two. get_server_status looks up one of the customer’s servers. The agent is tested on a small fixed set of questions with known right answers (a golden set). One comes from M10 (Can I export my data after I cancel my plan?). One needs both tools (Is my server web-1 running, and does a reboot change its IP address?): the model has to request two calls, your code has to run them, and both results have to come back before it can answer. Two fail on purpose: one asks about a server that does not exist, and in the other the model names a tool argument wrongly.

TL;DR

  • The loop has one rule. While the model’s reply contains tool calls, run them, add the results to the conversation and call the model again. A reply with no tool calls is the answer. Because a confused model can keep calling tools indefinitely, the loop also needs a cap on the number of rounds and a fallback reply for when the cap is reached. Reaching the cap means the run stopped, not that the task was done.
  • The model never sees your function’s code. It sees only the tool’s schema: a name, a description and a list of typed parameters. If a parameter has no declared type or description, the schema says nothing about it and the model has to guess what to send.
  • Each tool call gets exactly one result message, linked to the call by an id, so the model knows which result answers which request. In the lab, the two-tool question ends with 5 messages in the conversation: the question, the model’s reply requesting both calls, two results and the answer. A call that fails once and is retried ends with 6.
  • A tool failure has to reach the model as a message it can read and react to. If the failure escapes as an exception instead, the whole run crashes. LangGraph’s ToolNode setting handle_tool_errors decides which failures become messages. Its default turns invalid arguments into messages but lets exceptions raised inside the tool through. In the lab, True answers 4 of the 4 questions, the default answers 3 and False answers 2.
  • Evaluate three things separately: did the model pick the right tool, did it send valid arguments, and did it write a correct answer from the results. For execution, run a tool in your own code when it touches customer data or anything you must check before it happens. A hosted tool, which the provider runs on its own servers, suits general-purpose work where you have nothing to enforce between the request and the result.

Mental model

The model never runs anything itself. It writes a structured request, and your code decides whether to run it, runs it, and writes the result into the conversation as a tool result message (a ToolMessage in LangChain). That division is where control sits. Your code can validate the arguments, refuse a call, redact the result or log it, and the model only learns what you send back. Every later agent in this course, from create_agent to a multi-agent graph, is this loop with more machinery around it.

Why the model cannot run the tool

An agent is a model inside a loop that can act on the world. This lesson builds the loop’s three classic shapes by hand, with no framework in between.

A Larkspur customer asks support How long does a refund take? The model does not know Larkspur’s policy; the answer sits in the support handbook. So the model replies with a request, search the handbook for “refund timeline”, and then nothing happens. The model only writes text.

The model decides. Your application acts.

That split leaves two jobs every agent has to do:

  • Running the tool: your code reads the request, executes the function and returns the result as an observation, a message telling the model what the tool returned.
  • Stopping: every loop needs a stopping rule, a condition that ends it.

All three patterns share one shape:

Figure 1: The shared skeleton. The model only writes text; your code decides whether to stop or feed something back.

Agent loop

An agentic pattern is a fixed shape for repeating model calls until a task is done. The three patterns differ in what repeats and what ends the repetition:

Pattern What repeats Stops when Model calls in our runs
Reflection Draft, critique, redraft The critic approves, or after a set number of rounds 2 to 7 with a three-round limit
Tool use Nothing: one round of calls, then the answer The model answers from the observation 2
ReAct Thought, tool call, observation The model writes its final response, or after a round cap (10 by default) 4 for the arithmetic task

Table 1: The three patterns compared by loop body and stopping rule.

The counts come from a re-implementation where a scripted policy stands in for the model. The parsing, checking and looping are real; the model’s choices are not.

Key distinction: every pattern has two kinds of exit. One belongs to the model (an approval, an answer, a final-response tag). The other belongs to you (a round limit). A loop with only the model’s exit is not finished.

Pattern 1: one round of tool use

Here tools are described in the system prompt and the model writes its calls as text, which shows what native tool calling (lesson 22.4) later automates.

The contract the model reads

A tool is a function plus a description the model can read: its name, its docstring, and each argument with its type. That description goes into the system prompt with one instruction: when you need a tool, reply with a call in a fixed tagged format. A vague docstring makes a vague tool, because the model never sees the function body.

The request is only a string

Asked What’s the current temperature in Madrid, in Celsius?, the model does not answer. It writes a tagged call naming the weather tool, with Madrid as the location and celsius as the unit. Nothing has run yet. The whole round looks like this:

Figure 2: One round of tool use. Two model calls; the tool runs between them, inside your code.

The gatekeeper

Between the reply and the tool sits a gatekeeper, the code that decides whether a call may run. It makes four checks in a fixed order, and turns every failure into an observation the model can read instead of an exception that ends the run:

Figure 3: Validate in this order. Each failure becomes a specific message the model can act on.

The last step converts each argument to its declared type, so “5” becomes the number 5 when the tool wants a number. For Madrid the observation is 25 celsius, and a second model call turns it into a sentence.

Planted failures

We planted five broken calls, each a mistake models really make, and one run with type conversion switched off:

Planted call What the gatekeeper returned
A reply with no call tags Error: no call tags found
A sum call whose JSON is cut off Error: the content is not valid JSON
A call to calculator, a tool that does not exist Error naming the unknown tool and listing the four valid ones
A multiply call with only one of its two numbers Error: missing argument b
A multiply call with “6912” and “5” as text 34,560, after conversion to numbers
The same call with conversion switched off “69126912691269126912…”, and no error

Table 2: Five planted calls and one unguarded run.

The first four never reach a tool; each comes back as an error the model can correct. The last row is the dangerous one: Python repeats the text five times and returns a wrong answer with no error. We call that a stringly-typed answer: the failure no exception reports.

Where one round breaks

Now a harder task: sum 1234 and 5678, multiply the result by 5, then take the natural log.

Each call needs the result of the one before it, but in one round the model must write every argument before any tool has run. It can fill in the sum; the multiplication needs 6,912 and the log needs 34,560, and neither exists yet.

We call this one-shot blindness: a single round can run independent calls side by side, but it cannot chain dependent ones.

Pattern 2: ReAct planning

ReAct (reason plus act) interleaves reasoning and acting: the model writes a thought, takes an action, reads the observation, and repeats. In the text protocol that is four kinds of message:

  • Thought: what the model plans to do next and why.
  • Tool call: one action, in the same format as before.
  • Observation: the tool result, written by your code, never by the model.
  • Final response: the answer, which ends the loop.

The loop and its two exits

On each round the model gets the whole history. A final response ends the loop. Otherwise your code runs every call through the same gatekeeper and appends one observation per call, so by round two 6,912 is in the model’s context.

Figure 4: The ReAct state machine with its two exits: the model’s final response and your round cap.

Tracing the arithmetic task

The reference task uses three tools (sum, multiply, natural log) and needs them in order:

Figure 5: ReAct on a three-step dependent task. Each tool argument comes from the previous observation.

Round The model wrote Observation sent back
1 Sum 1234 and 5678 6912
2 Multiply 6912 by 5 34560
3 Natural log of 34560 10.450452222917992
4 Final response: about 10.45 none, the loop returns

Table 3: The scripted ReAct run, four model calls.

Every argument after round one came from an observation.

Planted failure: the runaway loop

A model that never writes a final response never stops on its own. We planted a stubborn policy that calls the handbook search every round, capped at five rounds, and reran the arithmetic task with a cap of two, below the number of dependent steps:

Run Model calls How it ended
Arithmetic task, cap of 2 2 Stopped by the cap, no answer
Stubborn search, cap of 5 5 Stopped by the cap, no answer

Table 4: Two capped runs.

Without the cap, the stubborn run never ends. We call that a runaway loop, and it bills for every round. Reaching the cap means the run stopped, not that the task was done, so the loop needs a fallback reply that says so. The first row shows the opposite risk: a cap below the task’s depth stops the agent before it can finish.

What the loop costs

Each ReAct round resends the whole history, so round k pays again for everything in rounds 1 to k minus 1. Four rounds cost more than twice the input tokens of one round of tool use, and the gap widens every round. We call that context creep.

Interview tip: asked why not always use ReAct, answer with latency and cost. Each round is a full model call that waits for the last one, and the prompt grows every time. Use the smallest loop that solves the task.

ReAct fixes reach and chaining. A weak answer from good tools needs a different loop.

Pattern 3: reflection

Reflection improves an output by critiquing it and trying again. One persona writes a draft, a second persona reviews it against the task and returns either a list of fixes or an approval, and the writer revises.

Figure 6: The reflection loop. The critique becomes the next message to the writer.

It uses no tools but has the same two exits: the critic’s approval and your round limit. We ran it with three planted critics and a three-round limit:

Critic Rounds Model calls How it ended
Approves everything 1 2 Critic approved
Finds two real bugs, then approves 3 6 Critic approved
Never approves 3 7 Round limit reached

Table 5: Reflection with three planted critics.

The lenient critic ends the loop after one review, so reflection costs two calls and improves nothing. The never-satisfied critic is the reflection version of a runaway loop, and the limit stops it at 1 + 2 × 3 = 7 calls.

Pitfall: the lenient critic. If the reviewer prompt is soft, reflection quietly becomes a single generation that costs double. Tell the critic exactly what good means.

One guard worth copying: each side keeps only its system prompt plus the latest exchange, so earlier drafts are not resent. M25 covers reflection in full.

Choosing a pattern

Choosing is a short decision:

Figure 7: Pick the smallest loop that fits the task.

Reflection Tool use ReAct
Reaches outside data ✗ ✓ ✓
Chains dependent calls ✗ ✗ ✓
Model calls 1 + 2 × rounds 2 rounds + 1
Main risk Lenient critic One-shot blindness Runaway loop, context creep

Table 6: Trade-offs at a glance.

The patterns combine. A production support agent often runs ReAct to gather evidence, then a reflection pass to check the draft answer against that evidence.

In practice: the Larkspur refund question

Back to the customer. The loop is the one traced above; only the tool changes:

  1. The model writes a thought (“I need the refund policy”) and a call to the handbook search with the query “refund timeline”.
  2. The gatekeeper checks the call, runs the search and returns the top handbook chunks as an observation.
  3. The model writes its final response, quoting the chunks it was given.

That is retrieval as a tool: your code touched the handbook, and the observation carried the evidence back. The round cap stops a search that never satisfies the model.

Key distinction: native tool calling (lesson 22.4) moves the tool description into the API request and returns structured calls with ids, so most of the gatekeeper’s parsing failures disappear. The loop in Figure 4 stays the same, and so does your responsibility for the round cap.

Limits of this evidence

  • No live model. Every model reply in Tables 2 to 5 is scripted. The planted failures cover the common shapes, not how often they happen.
  • Text protocol only. Native tool calling changes the parsing, not the loop.

Left out on purpose, and when to add it:

  • Retries with backoff: when you call a real API, which returns rate limits and timeouts.
  • History trimming or summaries: once a task regularly needs more than a handful of rounds.
  • Parallel tool execution: when one round requests several slow, independent calls.
  • Tracing every round: before the first production user; a runaway loop is invisible without it.

Key Takeaways

  • The model never runs a tool. It writes a call as text; your code parses, checks, converts and runs it, and the result goes back as an observation.
  • One round of tool use cannot chain dependent calls. ReAct can, because every observation stays in the history for the next decision.
  • Give every loop two exits, the model’s own and a round cap you own. Reaching the cap is a stop with a fallback reply, not a completed task.

Check yourself

1. Why can the ReAct agent chain three dependent tool calls when the one-round tool-use agent cannot?

One round of tool use must write every argument before any tool has run, so it cannot use one result to choose the next call. ReAct loops, and every observation stays in the history, so the model sees 6912 before it asks to multiply it by 5.

2. The gatekeeper receives a multiply call with 6912 and 5 written as text. What comes back with type conversion, and what comes back without it?

With conversion the text becomes numbers and the tool returns 34,560. Without it, the language repeats the text “6912” five times and returns a long string with no error at all. That stringly-typed answer is more dangerous than a missing argument, which at least produces an error the model can read.

3. A hand-written ReAct agent keeps calling a search tool that returns nothing useful, and the bill keeps growing. Which exit was missing?

The round cap, the exit you own (10 rounds by default). The final-response exit only fires when the model decides it is done, and a model that keeps asking for tools never decides that. With the cap the run stops and says why, and the user should get a fallback reply rather than silence.

Tool schema

Lesson 22.3: Defining tools and binding them to a model. Notebooks: 03a_defining_tools.ipynb

What you’ll learn

  • Compare an untyped, a typed and a validated definition of the same tool by what the model learns from each.
  • Diagnose a wrapped built-in tool whose argument name changed under you.

Lesson 22.1 described tools in a hand-written prompt and parsed the model’s calls out of its text. This lesson replaces that prompt with the real thing: a schema the provider understands.

Larkspur’s support agent has two tools. One searches the policy handbook, the other checks a customer’s server. For every question it must pick one, both or neither, and fill in the arguments, and it makes that choice without ever seeing the code behind either tool.

What it sees instead is a short description of each tool. That description decides how often the agent calls the right tool with the right arguments.

A tool schema is the machine-readable description of a tool that travels with every model request. Binding tools to a model means attaching their schemas to each call. LangChain builds the schema from the function’s name, its docstring and its type hints:

Figure 1: From function to schema. Only the right-hand box reaches the model.

The schema has three parts, and each drives a different decision:

Part Comes from What the model uses it for
Name The function name, or one you set The call it writes; your code looks the tool up by this name when it runs the call (lesson 22.4)
Description The docstring, or one you set Deciding when to call this tool, out of all the tools it holds
Parameters Type hints, or a validation model Deciding what to pass: each argument’s type, its description, and which arguments are required

Table 1: The three parts of a tool schema.

The function body is the one part the model never sees. A vague description produces wrong or missing calls however good the code behind it is. We call that a blind tool: correct code behind a description that does not say when to use it.

Types do two jobs

Take a multiply tool with no type hints. Its schema lists two arguments, a and b, each with a title and no type at all. The model has nothing to go on, and the tool has nothing to check:

Call Untyped multiply Validated multiply (both arguments declared as numbers)
2 and 3 6 6
2 and “abc” “abcabc”, no error Rejected with a validation error before the function runs

Table 2: The same bad call against an untyped and a validated tool.

The untyped tool returns “abcabc” because Python repeats a string when you multiply it by a whole number. That is the stringly-typed answer from lesson 22.1 again: a wrong result that no exception reports.

The validated version declares its arguments through a validation model, a Pydantic class that states each field’s type and description. The schema now tells the model to send numbers, and the same bad call stops at the door.

Key distinction: a type in the schema does two jobs. It tells the model what to send, and it lets the framework refuse what the model sends wrongly, before your code runs.

Three versions of the handbook search

Here is Larkspur’s handbook search defined three ways, with what the parameters part of each schema tells the model about its one argument, the query:

Definition What the model learns about the query
A function with an untyped query argument It exists and is required. Nothing about its type or meaning
The same function with the query typed as a string It is a required string
A validation model with a field description It is a required string described as “Words to look up in the handbook, for example ‘refund window’”

Table 3: Three definitions of one tool, as the model sees them.

The full schema of the third version also carries a tool description: “Search the Larkspur Cloud handbook and return the two best-matching chunks. Use it for policy questions: billing, refunds, exports, outages, server sizing.” That sentence says what the tool returns and which questions it is for, so the model can tell it apart from the server-status tool. The argument description says what a good query looks like.

We planted one bad call against all three versions, the number 3 as the query:

Definition Query = 3
Untyped Accepted; the function runs with a number
Typed as a string Rejected: “Input should be a valid string”
Validation model Rejected: “Input should be a valid string”

Table 4: One planted call against three definitions.

The rejection happens before the function runs, which is where it belongs. Lesson 22.5 shows how that failure can come back to the model as a message it can read and correct.

Check a wrapped tool before you bind it

LangChain’s built-in tools carry their own schemas. The Wikipedia tool is named wikipedia and takes one string argument, query. Wrapping it in a generic tool with your own name and description changes that argument’s name to the generic tool_input:

Built-in Wikipedia tool Same tool, wrapped
Name wikipedia Your name
Description The built-in one Yours
Argument query tool_input

Table 5: What wrapping changes.

The model now sends tool_input, and any prompt or test that expects query silently stops matching. We call that argument drift: the right value under the wrong key, which is still an invalid call.

Pitfall: argument drift. Whatever the source of a tool, inspect its final name, description and argument list before you trust it in a loop. That is exactly what the model will read.

The from-scratch tools in lesson 22.1 described their arguments with Python type names inside a prompt. A native schema uses JSON Schema types (string, number) and travels in the API request itself, so the provider can return structured calls that match it.

In practice: Larkspur’s two tools

For Larkspur’s agent, the schemas should leave no overlap for the model to guess about:

  1. Handbook search: described as the tool for policy questions (billing, refunds, exports, outages, server sizing), with a typed, described query.
  2. Server status: described as the tool for one of the customer’s own servers, with a typed, required server id.
  3. Before binding: print each tool’s name, description and arguments, and read them as the model will.

A question such as Is my server web-1 running, and does a reboot change its IP address? then maps cleanly onto both tools, which lesson 22.4 traces message by message.

Key Takeaways

  • The model reads only the schema: name, description and parameters, never the function body. A vague description gives wrong or missing calls however good the code is.
  • Type every argument. An untyped tool accepts anything (multiply turns 2 and “abc” into “abcabc”), while a validated schema rejects bad input before the function runs.
  • Inspect a tool’s final name, description and arguments before binding it, especially a wrapped built-in, because that is exactly what the model sees.

Check yourself

1. The model never sees a tool's function body. Which three parts of the schema does it read, and what does each one decide?

The name, the description and the parameters. The name is the call it writes and your code dispatches on. The description decides when to call the tool out of all the tools it holds. The parameters decide what to pass, with each argument’s type, description and whether it is required.

2. The untyped multiply tool gets 2 and the string abc. What comes back, and what does the validated version do with the same call?

The untyped tool returns “abcabc”, because its schema has no types and Python repeats a string when it is multiplied by a whole number. The validated version declares both arguments as numbers, so the same call fails validation before the function runs.

3. You wrap the built-in Wikipedia tool with your own name and description, and the agent starts passing odd arguments. What should you check before binding it?

The argument name. Wrapping changes the built-in’s query argument to the generic tool_input. Inspect the tool’s final name, description and arguments before you trust it in a loop, because that is exactly what the model reads.

Native tool calls and the message trace

Lesson 22.4: The manual tool loop and the augmented LLM in LangGraph. Notebooks: 04a_tool_calling_manual_loop.ipynb, 05a_tool_loop_errors_and_evaluation.ipynb (Part 3.1)

What you’ll learn

Lesson 22.3 turned each tool into a schema. This lesson sends those schemas with a real request and follows what comes back.

A Larkspur customer asks Is my server web-1 running, and does a reboot change its IP address? Answering needs two lookups, a server status and a handbook search, and neither depends on the other. The model can ask for both in one reply, which means your code has to keep track of which result answers which request.

A reply that requests tools

With native tool calling, the tool schemas travel in the API request, and the provider returns tool requests as structured data instead of tagged text. A reply that requests tools is an AI message whose text content is often empty and whose list of tool calls holds one entry per request:

Field Example from the recorded weather run What it is for
Name The weather tool Which tool to run
Arguments City: Munich What to pass
Call id A unique id the provider generates Pairing the result with this request

Table 1: One entry in a reply’s tool calls.

Ask about the weather and outdoor seating together, and the same reply holds two calls, one per tool, with a finish reason that says the model stopped to request tools. The model asks for both at once because neither depends on the other, which saves a round trip.

One result for each call

The model still runs nothing. The loop from lesson 22.1 becomes four moves over typed messages:

Figure 1: The native loop. Each tool message carries the id of the call it answers.

  1. Send the user’s question as a human message, and append the model’s AI message with its tool calls.
  2. For each call, look the tool up by name and run it with the given arguments.
  3. Append one tool message per call, holding the result and the id of the call it answers.
  4. Call the model again with the whole list. It answers from the results.

The call id is what pairs a result with its request. With two parallel calls, the model would otherwise receive two unlabelled strings and no way to tell which tool produced which.

Pitfall: the orphaned call. OpenAI’s API rejects a history in which a tool call has no matching tool message. A loop that drops the result of a failed call breaks the next request, not only that answer.

Matching ids only records which request a result belongs to. It does not prove the tool ran correctly or that the server was actually checked.

Counting messages in a two-tool run

The M22 lab’s two-tool question shows the whole trace on Larkspur’s tools:

# Message Content
0 Human Is my server web-1 running, and does a reboot change its IP address?
1 AI Two calls: server status for web-1, and a handbook search for “reboot server IP address”
2 Tool web-1: running
3 Tool The reboot chunk (score 0.747): “You can reboot a server from the console. A reboot takes about a minute and does not change the server IP address.” The sizing chunk follows with a score of 0.156
4 AI The answer, with no tool calls

Table 2: The two-tool trace, five messages.

Five messages, two of them tool results. The scores are real TF-IDF scores over the M10 handbook chunks; the model’s turns are scripted. Message count is a cheap diagnostic: a single-tool question takes four messages, so six on the same question means an extra round, which lesson 22.5 traces to a malformed first call.

A model without native tool calling needs the text protocol from lesson 22.1 instead: tool descriptions in the system prompt and your code parsing the call out of the reply. Nothing guarantees valid JSON, a real tool name or every argument, so use it only when the model leaves no choice.

The augmented LLM

LangGraph can take over the dispatch. The graph has three pieces:

  • Model node: calls the model with the tools bound.
  • Router: checks the latest reply; tool calls send the run to the tool node, no tool calls end it.
  • Tool node: runs every requested call and writes one tool message per call into the graph’s state.

Figure 2: A one-shot tool graph. The solid edges stop after the tools; the dashed edge is the loop.

Follow the solid edges with two questions:

Question Path What the user gets
Explain tool calling in one sentence Model, router, end A direct answer; no tool needed
What’s the weather in Tokyo? Model, router, tool node, end The tool’s raw output and no sentence

Table 3: Two questions through the one-shot graph.

The second run ends on a tool message. Nobody reads the result, the user gets no sentence, and a second call that depends on the first is impossible. We call that stopping at the tool.

That graph is an augmented LLM: a model that can use tools once, but not a loop. One more edge, from the tool node back to the model node (the dashed line), makes it an agent. The model then reads each result and decides whether to call another tool or answer, which is the loop in the module’s mental model.

Key distinction: an augmented LLM ends on whatever the tools return; an agent ends when the model writes a reply with no tool calls. The difference is one edge, and it changes the final message from a tool result to an answer.

In practice: the web-1 question

Run the web-1 question through both graphs:

  1. Augmented LLM: the model requests both lookups, the tool node runs them, and the run ends on the handbook chunk. The customer sees raw tool output.
  2. Agent loop: the same two tool messages go back to the model, which answers that web-1 is running and that a reboot does not change its IP address. The final message is an AI message with no tool calls.

In both runs each tool message carries its call id, so the model can tell the status from the handbook chunk. Lesson 22.5 adds what happens when one of those calls fails.

Key Takeaways

  • A model with tools bound returns an AI message with tool calls and runs nothing. Independent calls arrive together in one reply, saving a round trip.
  • Answer every call with exactly one tool message carrying its call id. The id pairs results with requests, and OpenAI rejects a history with an unanswered call.
  • A graph that goes from the tool node to the end is an augmented LLM. One edge from the tool node back to the model turns it into an agent loop.

Check yourself

1. Why does every ToolMessage carry the id of the tool call it answers?

The call id pairs a result with its request. With two parallel calls the model would otherwise get two unlabelled strings and no way to tell which tool produced which. OpenAI’s API also rejects a history in which a tool call has no matching tool message, so dropping a failed call’s result breaks the next request.

2. A customer asks if web-1 is running and if a reboot changes its IP. How many messages does the trace hold, and why are both tools requested at once?

Five: the human message, one AI message with two calls (server status and handbook search), two tool messages and the final AI message. Neither call depends on the other, so the model asks for both at once and saves a round trip.

3. A graph answers a weather question with the tool's raw output and no sentence. What is missing, and which one change fixes it?

The tool node goes straight to the end, so nobody reads the result and no dependent call is possible. That graph is an augmented LLM. Adding an edge from the tool node back to the model makes it an agent loop, and the model then turns the result into an answer.

Lesson 22.4 closed the loop from the tool node back to the model. This lesson asks what travels along that edge when a call fails.

A Larkspur customer asks the support agent Is my server web-9 up? The customer has no server called web-9, so the status tool raises an error. With LangGraph’s default settings, that error escapes the graph and the customer gets no answer at all.

The loop and its trace

The agent loop has two nodes. The agent node calls the model. The tool node runs every tool call the model asked for and appends one tool message per call. An edge from the tool node back to the agent node lets the model read the results, and a router ends the run when the last model reply has no tool calls:

Figure 1: The agent loop. Every tool result goes back to the model before the run can end.

The message list is the run’s trace. For the Larkspur export question it holds four messages: the question, one model reply requesting the handbook search, its tool message, and the final answer. The status-and-reboot question holds five, because one reply requests two tools. Message count helps diagnose extra work, but it does not say whether the answer is correct.

Two places a call can fail

To isolate the tool node, we fed it a hand-written model reply with one call, so every result is deterministic. The tool checks a customer’s servers, web-1 and db-1, and raises an error naming the real servers when asked about any other:

Call What came back
Status of web-1 A tool message with status success: “web-1: running”
Status of web-9 No tool message. The error escaped: “Unknown server ‘web-9’; your servers: [‘db-1’, ‘web-1’]”

Table 1: A valid call and a controlled failure, default settings.

In the full loop the second row means the whole run raises and the model never sees the error. Yet the error text lists the customer’s real servers: a model that could read it could ask which one the customer meant.

A tool call can fail in two places:

  • Validation error: the model sends bad arguments, which fail the schema check before the tool runs (a call naming the argument id instead of server_id).
  • Execution error: the arguments are fine and the tool itself raises (web-9).

Figure 2: The two failure points. The error setting decides what each one becomes.

The three error settings

The tool node’s handle_tool_errors setting decides what happens at each failure point. We ran both planted failures under each of its three values, in the LangGraph version this course pins (1.2.18):

Setting Bad arguments from the model Error raised inside the tool
Default Error message: the missing field, then “Please fix the error and try again.” Re-raised: the run crashes
True Error message ending “Please fix your mistakes.” Error message with the exception text
False Re-raised Re-raised

Table 2: Two failures under three settings.

Of the three, only True turns both failures into messages the model can read. The default catches the model’s mistakes but not the tool’s, which is why the web-9 question crashes under it. This behaviour depends on the installed version, so check it again after an upgrade.

What the model does next

An error message lets the model recover, but it does not make it recover: the model still has to read the message and choose a sensible next step. Here is the web-9 run under True. The tool message is LangGraph’s real output; the model’s two turns are scripted:

# Message Content
0 Human Is my server web-9 up?
1 AI Calls the status tool for web-9
2 Tool, status error The unknown-server error listing db-1 and web-1, then “Please fix your mistakes.”
3 AI I can’t find a server called web-9 on your account. Your servers are db-1 and web-1. Which one did you mean?

Table 3: The web-9 run with errors returned to the model.

The scripted reply asks for clarification using the server names in the error. A live model could choose another action, including an unhelpful retry. Under the default or False, the same run raises after message 1, before another model turn.

Four golden questions, three settings

The interactive lab runs Larkspur’s four golden questions through the full loop under each setting. Its tool results and error texts match what LangGraph produces for the same calls byte for byte (12 runs, 0 mismatches); the model’s turns are scripted, as in Table 3.

Question Default True False
Can I export my data after I cancel my plan? Answered, 4 messages Answered, 4 Answered, 4

  • The unknown server is an execution error. Only True catches it, and the model can then name the customer’s real servers, because the error text lists them.
  • The wrong argument name is a validation error. The default and True both return it as a message, the model retries with query, and the run costs one extra round trip (6 messages instead of 4). False re-raises it.
  • The two questions with no failure behave the same under every setting. We call this the happy-path blind spot: a test suite of questions that never fail cannot tell the three settings apart.

Deciding where each error is handled

There are two ways to get a failure to the model:

Approach How it works Use it when Message status
The tool returns the error A divide tool checks for zero and returns “Error: Division by zero” as its result The tool knows the failure in advance: an unknown id, an empty result, an input out of range success
The tool raises and the tool node catches it True, or a custom handler that catches selected exception types Failures you cannot list in advance, such as a client library’s errors error

Table 5: Returning an error versus catching an exception.

The setting also accepts a custom message, an exception type or a group of types (catch only those), or a function that formats the message. Either way, write error messages the model can act on: what was wrong and what would work, as the web-9 message lists the valid servers. Return only information the customer is allowed to see.

Pitfall: the successful failure. A tool that returns an error string completes normally, so its tool message has status success. Only a caught exception produces status error. Monitoring that counts error statuses misses every failure a tool reports as text.

Letting an exception escape is also a choice, and it has a cost: your application code must then log the failed run and give the user a fallback reply.

Tool-call evaluation

A run can finish and still be wrong. The refund question in the lab answers correctly under the default setting, yet its first call was malformed and cost an extra round trip. An agent that picks the wrong tool, passes the wrong server id, or ignores what the tool returned can also produce a fluent answer. Each of those is a different failure, so score them separately, from the same trace.

Three dimensions

Dimension Question How to score it
Tool selection Did it pick the right tool or tools? Compare called names with the golden set’s expected calls
Tool input Were the arguments well formed and relevant? Check required arguments are present and pinned values match
Synthesis Did the answer use what the tools returned, and nothing else? An LLM judge or a reference answer

Table 6: The three scores and where each comes from.

Separate scores tell you what to fix: a selection drop after a description change points at the description, an input drop at the schema and the generated arguments. Confirm the cause from the failing calls before changing either.

Scoring selection and input from the trace

The first two dimensions need no model at all. Give each golden question its expected calls:

  • Is my server web-1 running, and does a reboot change its IP address? expects the status tool with server web-1, and the handbook search with any query.
  • How long does a refund take? expects the handbook search alone.

A small scorer reads every tool call from the model’s replies, compares the set of called names with the expected set, and flags any call that is missing a required argument or has the wrong value for a pinned one. On two runs from the lab:

Run Selection Calls Flagged for input
web-1 status and reboot Correct 2 None
Refund (first call passed q) Correct 2 The handbook search

Table 7: The trace scorer on two lab runs.

Both runs chose the right tools. The refund run’s first call is flagged because it passed q instead of query; the lab’s trace marks the same call “right tool, missing query”.

That scorer is deliberately small. It does not check types, query relevance, call order or duplicate calls, and it assumes it knows every tool name. A production scorer validates against the real tool schemas and flags unknown tool names before looking up their required fields.

Judging synthesis

Synthesis measures whether the final answer uses the returned facts correctly, and that needs judgement. An LLM judge is another model asked to grade the trace against explicit criteria: give it the question, the tool requests, the tool results and the final answer, and ask for a score from 1 to 5 on each of the three dimensions plus a short justification.

One recorded judgement shows the shape. The trace asks Calculate 15% of 250 and check weather in Paris; the agent calls a calculator (37.5) and a simulated weather tool (65°F, partly cloudy), and its answer includes both. The judge scored it 5, 5 and 5. That is one recorded judgement on a practice trace, not a Larkspur result, and a new judge call may disagree.

Pitfall: the self-grading judge. In that recording the judge is the agent’s own model, which tends to be lenient on its own work. Use a different, ideally stronger, model, and check its scores against a few human-graded runs before you trust a trend.

Two more cautions. The score fields there are plain whole numbers, so nothing rejects a 7 unless you add a range check. And a single trace scored 5 out of 5 proves little: scores mean something across a fixed golden set, compared before and after one change, as M10’s baseline-first method does for retrieval.

Counting what never finishes

Per-call scores miss the runs that never produce an answer. Log three counts per run as well:

  • Rounds per run: the refund question’s extra round shows as 6 messages instead of 4.
  • Error tool messages per tool: which tool fails, and how often.
  • Crashed runs: the web-9 question under the default has no answer to score at all.

Those counts are cheap and catch both of the lab’s failures. A web-9 run where the model asks for exactly what the customer said passes selection and input; its failure belongs to the tool’s error handling, and only the crashed-run count records it.

Limits of this evidence

  • Scripted model turns. Every model reply in Tables 3, 4 and 7 is scripted; only the tool messages and error texts are LangGraph’s real output.
  • One version. Table 2 is the behaviour of the pinned LangGraph version; the settings have changed between releases.
  • One judgement. The synthesis example is a single recorded score, so it shows the method, not the judge’s reliability.

Key Takeaways

  • Choose error routing explicitly. In the tested version, the default tool node returns the missing-argument error to the model but re-raises the tool’s own error; True returns both.
  • A tool that returns an error string produces a success-status message. Write error messages the model can act on, and remember that happy-path tests never show the difference between settings.
  • Score tool selection, tool input and synthesis separately. The first two come straight from the trace; judge synthesis with a different model, across a fixed golden set, and count crashed runs too.

Check yourself

1. With the default ToolNode settings, why does the web-9 question crash while the wrong-argument refund question still gets answered?

They fail in different places. The wrong argument name is a validation error, which the default turns into an error message the model can read and retry from. The unknown server is an exception raised inside the tool, which the default re-raises, so the run crashes before the model sees it.

2. In the lab, how many of the four golden questions does each handle_tool_errors setting answer, and which questions make the difference?

The default answers 3 of 4, True 4 of 4 and False 2 of 4. The web-9 question (the tool raises) crashes under the default and False, and the refund question (wrong argument name) crashes under False. The other two questions behave the same under every setting.

3. Your error dashboard counts tool messages with status error and shows almost none, yet customers report failed lookups. What is the likely cause?

The tools probably return their failures as strings, such as “Error: Division by zero”. A returned string completes the tool normally, so its message has status success. Count those failures another way, or let the tool raise and have the tool node catch it, which produces status error.

Hosted vs client-side tools

Lesson 22.6: Hosted vs client-side tools: code execution and image generation. Notebooks: 06a_hosted_vs_client_side_tools.ipynb, 06b_hosted_code_execution.ipynb (optional), 06c_agentic_image_generation.ipynb (optional)

What you’ll learn

  • Explain the difference between a client-side tool and a hosted tool, call by call.
  • Compare what each path lets you see, refuse, test and pay for.
  • Diagnose where a policy check can sit, and why a hosted tool has no place for it.
  • Choose where each of Larkspur’s tools should run.

Every tool in lessons 22.1 to 22.5 ran in your process. This lesson moves a tool to the provider’s side and looks at what you give up.

Larkspur has to confirm that a customer owns a server before showing its status. That check has to happen before the lookup runs, in code Larkspur controls. A public web search has nothing comparable to enforce. Where a tool runs decides whether such a check is even possible.

Two execution paths

A client-side tool is the kind built so far: the model returns a call, your code runs it, and you send the result back. A hosted tool runs on the provider’s infrastructure instead, and the reply arrives with the result already folded in. The change in the request is small. The change in what you can see and control is large.

The recorded comparison answers What is the current population of Lisbon? both ways with the same small model:

Who chose the search query Your code The provider (“current population of Lisbon 2023”)

One run proves little about latency, but it does show that one round trip is not automatically faster. The policy gap

The gap between “the model asked” and “the model sees the result” is where policy lives. We call it the policy gap. In the recorded example, a guarded version of the client-side lookup refuses any city outside an allow-list:

Question Guarded client-side lookup Hosted search
Population of Lisbon Runs; the model answers Runs; the model answers
Population of Pyongyang Refused with an error; the model says it cannot retrieve that population Would run; nothing of yours sits between the call and the result

Table 3: An allow-list in the policy gap.

Allow-lists, tenant scoping, redaction of personal data and spend caps all sit in that gap. Choosing a hosted tool means choosing not to have it.

Key distinction: a hosted tool can be well run and still impossible to govern. What decides the placement is whether anything must happen between the call and the result.

What each hosted tool shows you

Hosted tools expose different amounts of their execution:

Hosted tool What comes back besides the answer
Web search Roughly the query; no raw results
Code interpreter The code it ran, its output and any files, so you can audit the method
Image generation The revised prompt the model wrote for itself, and the image

Table 4: Visibility by hosted tool.

Code interpreter is also configurable: the recorded example sets a memory ceiling and turns network access off, so the sandbox works only on data you supplied. What you still cannot do is approve the code before it runs, veto one call, or replace it with a stub in a test.

Image generation adds a different caution. The agent describes what it meant to draw, and only showing the image to a vision model reveals what it actually drew. We call that narrated output: a description of the result that nobody checked against the result. The model also has to leave the tool alone when a turn asks for advice rather than an image, and the recorded example checks that it does.

Choosing where each tool runs

The decision follows the data the tool touches:

Figure 2: Three yes/no questions. Any yes keeps the tool in your process.

For Larkspur’s support agent, the split is:

  1. The handbook search and the server-status lookup stay client-side. They read the customer’s account and Larkspur’s own policy, need tenant scoping and logging, and must be replaceable with stubs in tests. The M22 lab runs them deterministically for this reason.
  2. A hosted web search fits questions the handbook cannot answer, about public software or third-party services, where there is nothing to enforce between the call and the result.
  3. Hosted code execution fits arithmetic on numbers the customer pasted into the chat. A model that runs three lines of code computes the answer; a model that answers directly produces plausible-looking digits.

In OpenAI’s API, hosted tools are offered through the Responses API, while Chat Completions carries client-side function calls. Check which API your integration and provider version support before choosing a wrapper. A third placement, a tool on a server you run that the model reaches over a protocol, is MCP (M38 to M40), and it gives back much of the control that hosted tools remove.

Limits of this evidence

  • One run per path. The latencies in Table 1 come from a single recorded run each; measure on your own traffic before deciding anything on speed.
  • One provider. The visibility in Table 4 is what OpenAI’s hosted tools returned in the recorded examples; other providers expose more or less.

Key Takeaways

  • A hosted tool runs on the provider’s side and returns the result folded into the reply. You lose the policy gap, where your code can log, refuse, redact or cache a call.
  • Hosted tools vary in visibility: web search shows roughly the query, code interpreter shows the code and output, image generation shows its revised prompt. None can be replaced with a stub in a test.
  • Keep tools that touch customer data or need tenant scoping client-side. Use hosted tools for public lookups and arithmetic on data the user supplied.

Check yourself

1. What do you give up when you move a tool from client-side to hosted?

The gap between the model asking and the model seeing the result, which is where policy lives: allow-lists, tenant scoping, redaction and spend caps. You also lose the chance to see arguments before execution, refuse a call, or replace the tool with a stub in a deterministic test, and a failure can only be handled by re-running the whole request.

2. Larkspur's support agent needs the customer's server status and an answer about a third-party service. Which should run client-side, and which suits a hosted tool?

The server-status lookup stays client-side: it reads the customer’s account, needs tenant scoping and logging, and must be stubbed in tests. A hosted web search fits the third-party question, which the handbook cannot answer and where there is nothing to enforce between the call and the result.

3. The hosted search took one round trip and 3.16 s, the client-side path two and 1.86 s. Is hosted the way to cut latency?

Not on this evidence. One round trip is not automatically faster: in that run the hosted path was the slower one. One run also proves little about latency, so measure on your own traffic, and remember that going hosted removes the gap where your code could log, refuse or redact the call.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s support agent returns a 500 whenever a customer mistypes a server name (“Is web-9 up?”). The logs show ValueError: Unknown server 'web-9'. The tool works for valid names. What is wrong, and what do you change?

What a strong answer covers:

  • The exception escapes the tool-running step. ToolNode’s default turns invalid arguments into messages but re-raises exceptions from inside the tool, so the whole run fails and the model never sees the error
  • Two fixes: set handle_tool_errors=True, or have the tool catch the failure and return a descriptive error string. Either way the model receives a tool result marked as an error and can respond to it
  • Makes the error text useful to the model by listing the customer’s real servers, so the model can ask “did you mean web-1?” instead of apologising
  • Adds the typo to the golden set and alerts on the share of error results per tool, so a new failure mode shows up before customers report it

2. A product manager wants to drop search_handbook and give the agent the provider’s hosted web search, since “the handbook is public anyway”. What do you weigh before agreeing?

What a strong answer covers:

  • Where a tool runs decides how much control you have. With a client-side tool you see the arguments before anything runs, can refuse or redact, and own the raw result. With hosted web search you see a status and the query only after the search has happened
  • Accuracy and scope: the handbook index returns Larkspur’s own current policy with chunk ids the answer can cite, while web search can return third-party pages or an old cached copy
  • Testing and cost: a client-side tool can be replaced by a stub that returns fixed results, which makes tests repeatable. A hosted call hits the live web and is billed per call on top of tokens
  • A reasonable split: client-side for anything that touches customer data or policy, hosted search only for questions the handbook cannot answer, and a log of which path produced each answer

3. You change the description of get_server_status and swap in a new model in the same release. How do you know the agent still calls the right tool with the right arguments?

What a strong answer covers:

  • A golden set of questions with the expected tool calls, run before and after. Change one thing at a time, so a regression points at its cause
  • Scores tool selection and tool arguments directly from the trace (the tool names match, the arguments validate against the schema). These checks are deterministic and need no judge
  • Uses an LLM judge only for the final answer, from a different and ideally stronger model than the agent, checked against a few traces graded by people, because a model grading its own run tends to be lenient
  • Watches production too: how often each tool is called, the share of error results, and rounds per run, split by question type

4. A trace shows the agent calling search_handbook eight times with slightly different queries for “How long does a refund take?” before it gives up. What is going on, and how do you stop it?

What a strong answer covers:

  • Checks the tool results first. TF-IDF matches exact tokens, so “refund” never matches “Refunds” in the refund-timing chunk. The tool returned the wrong chunk or nothing, and the model kept rephrasing in the hope of a better result
  • Fixes the retriever (embeddings or query rewriting, M13 and M17) rather than the loop, and makes an empty result say so plainly, so the model can stop searching and say it found nothing
  • Caps the loop anyway, with a round limit in a hand-written agent or LangGraph’s recursion_limit, and returns a fallback answer when the cap is hit
  • Monitors for repeated near-identical calls in traces, since each round costs a model call and adds latency

5. The model sometimes calls get_server_status with “my database server” instead of an id like db-1. The schema says server_id: string. How do you make wrong arguments rarer, and what catches the ones that remain?

What a strong answer covers:

  • The schema is all the model reads. Describe the argument in the schema with the id format and an example, and say in the tool description when to use the tool
  • Constrains the type where the values are known, for example an enum of the customer’s server ids, so a free-text value fails validation instead of reaching the lookup
  • Sends validation errors back as messages (the ToolNode default does this), so the model can retry with a valid id
  • Measures the tool-argument score on the golden set before and after the description change, and keeps the version that scores better

Key Takeaways

  • Write the loop’s exit conditions first: a reply with no tool calls is the answer, and reaching the round cap means stop with a fallback, not success.
  • Treat the tool schema as the interface. Give every argument a type and a description, because the model reads nothing else about your function.
  • Every tool failure must come back as a tool result the model can read. Set handle_tool_errors deliberately and test it with a tool that raises.
  • Run tools that touch customer data in your own code, where you can log, refuse and stub them. Hosted tools fit general-purpose capabilities where you have nothing to enforce.
