M24 Agentic workflow patterns

A Larkspur support request may need a sequence of policy checks, one specialist queue or several independent lookups. Those tasks need different control paths. You will build the fixed paths first, inspect where each model decision belongs, then test joins and retry limits. The tutorials cover workflow versus agent control, quality gates, fan-out and fan-in, and bounded feedback loops.

Open the lab

The running example is the Larkspur Cloud support assistant from M10 to M12, answering from the same handbook. Its golden question Can I export my data after I cancel my plan? needs two evidence chunks, export and retention, which makes it the natural case for orchestrator-worker decomposition. The notebooks run their own small demos (an email, a story, a joke, a code review), and every number on these pages is one they printed or one the lab computes.

TL;DR

  • In a workflow, code fixes the path through the LLM calls; in an agent (M23), the model picks its next step. Each M24 pattern hands the model one decision at most: a gate’s verdict, a route, a vote, a plan’s length or a grade.
  • A quality gate checks an intermediate result before the next step spends tokens on it. In lesson 24.1 a concrete topic passed on attempt 1 (four LLM calls); an abstract one was rejected three times and stopped before drafting (six calls, no email).
  • Routing by model tier sent 1 of 7 requests to o4-mini and scored 86%, against 71% for all-cheap and 100% for all-reasoning. The router’s costly mistake is sending a hard request to the cheap tier.
  • A fan-out lasts as long as its slowest branch: the 24.3 sections took 7.0 s in parallel against a 13.4 s sum. In the lab a cap of two concurrent branches costs nothing on that workload, until the slowest branch is submitted last.
  • Every loop gets a cap in code. LCEL cannot loop at all, so a generate, critique, refine cycle lives in LangGraph, a Python loop or agent middleware, and at MAX_ITERATIONS = 5 it makes at most ten LLM calls.

Mental model

Real systems nest these. CRAG (M29) is an evaluator-optimizer around retrieval, adaptive RAG (M30) is a router, and query decomposition (M17) is orchestrator-worker. Read an architecture by asking which of the five each node belongs to, and where the model, rather than your code, makes the call.

Workflow vs agent

Lesson 24.1: Prompt chaining with quality gates. Notebooks: 01a_prompt_chaining_langgraph.ipynb, 01b_prompt_chaining_structured_output.ipynb (optional), 01c_prompt_chaining_lcel.ipynb (optional)

What you’ll learn

  • Explain the difference between a workflow and an agent by who chooses the next step.
  • Map each of the five M24 patterns to the one decision it hands the model.
  • Trace a gated chain through its pass path and its retry-limit path, call by call.
  • Diagnose why a gate leaks, loops or lets an unusable result through.

M23 ended with an agent that picks its own tools. This module goes the other way: five patterns where your code draws the path and the model fills in one kind of decision.

A Larkspur customer writes I want my money back for last month. A useful reply needs the plan and the purchase date before it can apply the refund-window policy. A chain that drafts straight away turns those missing inputs into a polished guess. This lesson builds the guard against that, and first separates two kinds of system.

Who picks the next step

The distinction comes from Anthropic’s Building Effective Agents (December 2024). In a workflow, LLM calls and tools run along code paths you defined in advance. In an agent, the model directs its own process: it picks the next tool, reads the result and decides when to stop. The ReAct agent of M23 is an agent. All five M24 patterns are workflows.

The two differ in what you can know before a request runs:

Workflow (M24) Agent (M23)
Who picks the next step Your edges; the model at most chooses among edges you wrote The model, on every turn
LLM calls per request Known, or bounded by a cap in your code Known only when it stops; bounded by a step limit
Testing Each node and each router, like a function Whole trajectories, end to end
A failed run Ends at a node you named, with a reason Shows in the trajectory: a repeated tool call, an early stop
Fits Tasks you can draw before they run Tasks whose steps depend on what the model finds

Table 1: Workflow and agent, side by side.

A Larkspur refund reply has a shape you can draw: pull out the plan and the date, check them, draft, polish. Investigating why one customer’s servers keep rebooting has no such shape, and that is where an agent earns its extra calls.

One decision per pattern

Each workflow pattern hands the model exactly one kind of decision and keeps the rest in code:

Pattern Code fixes The model decides
Prompt chaining (24.1) the order of the steps each step’s content, and a gate’s verdict
Routing (24.2) the set of handlers which single handler runs
Parallelization (24.3) the branches and the merge each branch’s content, each vote
Orchestrator-worker (24.4) the worker’s job and the merge how many workers run, and what each one gets
Evaluator-optimizer (24.5) the criteria and the iteration cap the grade, and so whether to go round again

Table 2: The five patterns by who decides what.

The gated chain in this lesson shows how little the model controls. Its compiled graph has five nodes and eight edges, and only three edges are conditional:

From To Kind
start extract_points fixed
extract_points check_points fixed
check_points write_draft conditional (pass)
check_points extract_points conditional (reject, try again)
check_points fail_validation conditional (retries used up)
write_draft polish_final fixed
polish_final end fixed
fail_validation end fixed

Table 3: The recorded edge list of the gated chain. All three conditional edges leave the gate.

Everything the model decides happens inside a node. Where the run goes next is decided by code you can read, which is what the next section relies on.

Quality gates

Prompt chaining splits one task into a fixed sequence of focused calls, each reading the previous step’s output. The lesson’s chain turns a topic into an email in three steps: extract the key points, draft, polish. A quality gate sits between two steps and decides whether the intermediate result may go on.

Where the gate sits

The gate checks the cheapest artefact that can already be wrong. Failing after extraction costs one check. Failing at the end costs a draft and a polish written from nothing:

Figure 1: The gated chain. The gate can pass the key points on, send extraction round again, or stop the run with a reason.

We call the failure this prevents writing from nothing: later steps spend calls polishing a result whose input was never usable.

The three parts of a gate

A gate is three separate pieces, and keeping them apart is what makes each one testable:

Part In the reference chain Why it is built this way
The check A gpt-4o-mini judge at temperature 0 returns a structured verdict: actionable (yes or no) and a one-sentence reason A keyword rule leaks; a structured verdict cannot come back as free text
The router A pure function reads the stored verdict and the attempt count and returns write_draft, regenerate or fail No LLM call, so it is tested like any function
The bound Each extraction adds 1 to a counter; at MAX_VALIDATION_RETRIES = 3 the router takes the fail edge; a recursion limit of 12 steps backs it up A rejecting judge cannot keep the chain running

Table 4: Check, router and bound.

The counter uses a reducer, a rule for combining a node’s update with the value already in state. Here the rule is addition, so each extraction’s 1 accumulates into an attempt count.

Two recorded runs

The two recorded runs take the two exits of Figure 1:

Topic Attempts Gate verdicts Ended at LLM calls
Request for project deadline extension due to technical challenges 1 pass: the points outline a request, its reason and a new timeline the polished email 4 (extract, judge, draft, polish)
The meaning of life and happiness 3 reject three times: informative points with no request, decision or next step fail_validation, with a reason 6 (three extracts, three judges)

Table 5: Both exit paths, from the notebook’s recorded output.

The second run spent three judge calls to avoid writing and polishing an email with no purpose. It also ended with a message a caller can show or log, which a crash or an empty email would not give.

Planted failures

Each piece of the gate exists because something specific goes wrong without it:

Planted failure What happens The guard
A keyword gate (“mentions request, deadline, support”) Philosophical key points mention “support” and “progress”, so vague topics pass An LLM judge with a yes-or-no verdict and a reason
Extractor at temperature 0 A regenerated attempt can repeat the rejected key points, so all three tries fail the same way Extract at 0.7, judge at 0
A bug in the router that never returns fail The reject edge loops forever The recursion limit of 12 steps stops the run
Typed output with useless content Every field is present and the email still has no purpose A schema checks shape; the gate still checks content

Table 6: One planted case per guard.

Pitfall: the repeating regenerator. A retry only helps when the next attempt can differ. At temperature 0 the extractor may return the same points, and lower temperature does not guarantee identical output either. Check that retries actually change the result, and that the judge grades the same text consistently.

Gates in other frameworks

The same gate appears in the two alternative builds of this lesson:

  • LCEL (LangChain Expression Language, which composes runnable steps with |): the gate is a step that passes the payload through or raises a rejection error. A retry wrapper re-runs extraction and gate together, playing the reject edge, and a fallback plays fail_validation.
  • Structured output at every hop: each step returns a validated object, so shape errors are caught without an extra judge call. Shape is all it checks.

In practice: the Larkspur refund ticket

The refund reply follows the same chain:

  1. Extract the plan, the purchase date and the request from the ticket.
  2. Gate: check that the ticket names a plan and a purchase date. Without them the refund-window chunk cannot be applied.
  3. On pass, draft from the refund policy and polish.
  4. On the third reject, end at a terminal node whose reason asks the customer for the missing date.

I want my money back for last month fails the gate before any drafting, and the customer is asked one precise question. In lesson 24.2 the same ticket meets a different decision: which queue, and which model, should handle it.

Limits of this evidence

  • Two runs. Table 5 comes from one recorded run per topic; a new run can extract different points and the judge can word its reasons differently.
  • One judge. The gate’s verdicts were not compared against human labels, so its false-pass rate is unmeasured.
  • Left out: a gate per step. Add one after drafting when the draft itself can fail a check you can state, such as a missing policy citation.

Key Takeaways

  • In a workflow your code fixes the path and the model makes one kind of decision; in an agent the model picks every step. Use a workflow for any task you can draw before it runs.
  • Put the gate after the cheapest step that can already be wrong. Check with an LLM judge that returns a structured verdict, and route in a pure function you can test without a model.
  • Bound retries with a counter and a terminal node that records why the chain stopped. A schema checks shape, never usefulness, so typed output still needs a gate.

Check yourself

1. Why does the quality gate sit right after extraction instead of checking the finished email?

Failing after extraction costs one check, while failing at the end costs a draft and a polish written from nothing. The gate stops unusable key points before later steps spend calls on them, and the chain ends with a reason a caller can show or log.

2. The topic about the meaning of life is rejected three times. How many LLM calls does the run make, and where does it end?

Six: three extractions and three judge calls. At the third rejection the router takes the fail edge to fail_validation, which records why the chain stopped. No draft or polish call runs.

3. You set the extractor to temperature 0, and the gate rejects the same key points three times in a row. Why did regenerating not help?

At temperature 0 the extractor may repeat the points it already produced, so each retry fails the same way. The reference chain extracts at 0.7 so a new attempt can differ, and judges at 0 so the verdict stays as consistent as possible. Neither setting guarantees identical or different output, so check that retries really change the result.

Routing by handler

Lesson 24.2: Routing by handler and by model tier. Notebooks: 02a_routing_langgraph.ipynb, 02b_routing_by_model_tier.ipynb, 02c_routing_lcel_runnable_branch.ipynb (optional)

What you’ll learn

  • Explain why a router asks the model for one label from a closed set and dispatches in plain code.
  • Compare all-cheap, all-reasoning and routed strategies on accuracy and reasoning calls.
  • Diagnose a router from its confusion matrix, and say which of its two errors costs more.
  • Choose the direction a router should err, and when a cheap-first fallback is safe.

Lesson 24.1 sent every request down one chain. Larkspur’s tickets are not all the same kind: I want my money back belongs in billing, my server will not boot in technical support. Routing classifies the input once and sends it down exactly one specialist path.

This lesson routes on two axes. The first picks a handler. The second, in the next section, picks a model.

One label from a closed set

The content router in this lesson has the same two-part shape as the 24.1 gate: a model makes a small, constrained decision, and a pure function acts on it.

  • A constrained classifier. The model returns structured output whose only field is a content type limited to story, poem or joke. It cannot answer with a label the graph has no edge for.
  • A pure condition function. A dictionary maps the stored label to a node name, with story as the default, so even an unexpected label lands on a real node.

Each request then costs exactly two LLM calls, one to classify and one in the chosen handler, however many handlers exist. A fourth category is one more allowed label, one node and one edge.

For Larkspur the closed set is the ticket queue: billing, technical, sales. The test that matters is the routing decision itself, measured on labelled tickets, because a fluent answer from the wrong queue still reads well.

Routing by model tier

The second router picks a model, not a handler. A cheap model triages each request as easy or hard. Easy work stays on the cheap model; hard work goes to a reasoning model, so reasoning prices are paid only on the traffic that needs them:

Figure 1: Routing by model tier. The triage call is the only extra cost on every request.

Both answering nodes send the same prompt, so any difference in the answers belongs to the model. Two details matter on the first real call: o-series reasoning models accept only the default temperature, so the reasoning tier runs at 1, and the reasoning-effort setting only means something to a reasoning model.

The workload and the three strategies

A router means nothing without “cheaper than what”. The recorded comparison runs seven requests, mixed the way real traffic is, mostly easy:

Kind Requests
Easy (4) extract an order id from a shipping note; name the capital of Portugal; convert 2:45 pm to 24-hour time; reply with the word ok
Hard (3) a deploy-schedule puzzle with ordering constraints; which key an LRU cache evicts; the total wait under exponential backoff

Table 3: The labelled workload. Each request carries its true difficulty and an expected answer.

Each strategy answers all seven, and an answer counts as correct when the expected value appears as a whole word in it:

Strategy Correct Answering time, total Reasoning calls
All cheap 71% (5 of 7) 5.2 s 0 of 7
Routed 86% (6 of 7) 13.4 s 1 of 7
All reasoning 100% (7 of 7) 20.1 s 7 of 7

Table 4: The recorded payoff table.

Read the table for its shape. Routed accuracy should sit near all-reasoning while its reasoning-call count sits near all-cheap. The time column counts answering calls only; the routed strategy also pays one triage call per request, seven in all.

Pitfall: the nervous router. A router that sends everything to hard is worse than no router. It pays the full reasoning bill and adds a triage call on top of every request.

The router’s confusion matrix

The router predicts difficulty from the question text. It never observes it, so it makes mistakes, and they show up in a confusion matrix, a table of predicted against true labels:

Sent to reasoning Sent to cheap
Truly hard 1 (the deploy puzzle) 2 (LRU: wrong answer; backoff: right)
Truly easy 0 4

Table 5: Routing decisions against ground truth.

The two kinds of mistake cost different things:

  • Easy sent to reasoning: overspend. Bounded, and visible on the bill.
  • Hard sent to cheap: a confident wrong answer. Invisible until someone acts on it.

We call the second one the silent downgrade. In this run it happened twice and cost one wrong answer. Because it costs more than overspend, bias the triage prompt toward hard on borderline cases and accept some overspend as insurance.

Which way to fall back

The same asymmetry decides the fallback direction. “Answer on the cheap model, detect a bad answer, retry on reasoning” only works with a reliable wrong-answer detector, and that detector can miss exactly the confident errors a silent downgrade produces:

Figure 2: Escalate on uncertainty before answering, not after a bad answer.

A measured detector can support a cheap-first fallback. Without one, escalate before answering.

In practice: the 45-day refund question

On Larkspur, Can I get a refund after 45 days? is the case to watch:

  1. The handler router sends it to billing, correctly.
  2. The tier router sees what looks like a lookup and may label it easy.
  3. The answer needs proration arithmetic against the refund-window policy, so the cheap tier can return a confident wrong amount.
  4. Add questions like it to the labelled set the router is measured on, and re-read its confusion matrix after every triage-prompt change.

Lesson 24.3 keeps all the work but runs it at once: several branches in parallel, merged into one answer.

Limits of this evidence

  • Seven questions. One question moves accuracy by 14 points, so Table 4 shows a shape, not a ranking of models.
  • Token-match grading. An answer that states the right value in other words counts as wrong.
  • One run. Times and triage labels come from a single recorded run; a rerun can route differently.

Key Takeaways

  • A router asks the model for one label from a closed set and dispatches in plain code, with a default route. Each request costs two calls however many handlers exist.
  • Routing by model tier pays reasoning prices only on hard traffic: in the recorded run, 86% correct with 1 of 7 reasoning calls, against 71% all cheap and 100% all reasoning.
  • The silent downgrade, hard work sent to the cheap tier, costs more than overspend. Lean triage toward hard on borderline cases and escalate before answering, not after.

Check yourself

1. Why does the content router classify into a fixed set of labels instead of free text?

With the label limited to story, poem or joke, the model cannot return a value the graph has no edge for, which a free-text answer like “I think they want a poem” could. A pure function then maps the label to a node, with a default so even an unexpected label lands somewhere.

2. A Larkspur customer asks whether they can get a refund after 45 days. Why is this a risky question for the model-tier router?

It looks like a lookup but needs proration arithmetic, so triage may label it easy and send it to the cheap tier. That is a silent downgrade: the cheap model can return a confident wrong answer. Put questions like it in the labelled set the router is measured on.

3. A teammate proposes answering on the cheap model first and retrying on the reasoning model when the answer is bad. Why is this risky?

It needs a reliable wrong-answer detector, and the detector can miss the confident errors a cheap model makes on hard questions. A measured detector may support the fallback, but without one, escalate on uncertainty before answering and bias triage toward hard on borderline cases.

Fan-out / fan-in

Lesson 24.3: Parallelization: sectioning and voting. Notebooks: 03a_parallelization_langgraph.ipynb, 03b_parallelization_sectioning_and_voting.ipynb, 03c_parallelization_lcel.ipynb (optional)

What you’ll learn

  • Explain how a graph starts branches together, waits for all of them and merges their writes.
  • Calculate a fan-out’s wall time from its branch durations, with and without a concurrency cap.
  • Diagnose a lost or rejected write when two branches update the same state key.
  • Choose between sectioning and voting, and set a vote threshold knowingly.

Chaining runs steps one after another, and routing runs one of several. Parallelization runs all of a fixed set of branches at once and merges what they return.

A Larkspur reply about an outage needs three pieces of evidence: the handbook’s outage policy, the status page, and the customer’s account. None of the three lookups needs another’s result, yet a chain would run them back to back. Running them together cuts the wait to the slowest one, provided the merge is defined.

Fan-out, fan-in and the sync point

In LangGraph the graph and its state schema decide both the scheduling and the merging:

  • Fan-out: several edges leave one node, and their targets run in the same step, concurrently.
  • Fan-in: several edges enter one node, and it waits until every one of them has finished.
  • Sync point: when one path is longer (A to B to X, beside A to C), an edge from the list of both endpoints into the next node makes it wait for the longer path explicitly.

The lesson’s sectioning graph writes a story’s characters, setting and premise in parallel, then synthesizes an introduction:

Figure 1: The recorded sectioning run. Each branch is labelled with the time it finished.

Two branches, one key

The merge needs one more rule. A reducer says how to combine a node’s update with the value already in a state key. Branches that each own a key, as the three story sections do, need none. Branches that write the same key in the same step do.

We ran a model-free fan-out in which a handbook branch and an account branch each append their name to one shared list, in the LangGraph version this course pins (1.2.18):

Shared key declared as Both branches write in one step Result
a list with an addition reducer yes both names kept: account, handbook
a plain list, no reducer yes InvalidUpdateError: the key “can receive only one value per step”

Table 1: The same two-branch graph with and without a reducer.

We call this failure colliding writes. Here it fails loudly, which is the useful outcome; the fix is to declare the reducer on any key that more than one parallel branch writes.

The critical path

Wall time follows the longest path through the graph, not the sum of the steps. The recorded timing runs measure it first with nodes that sleep 0.5 s each, then with real LLM calls:

Graph Wall time Why
A, B, C, D in a line 2.01 s four steps, one after another
A, then B and C in parallel, then D 1.51 s B and C overlap: three steps’ worth
A, then B to X beside C, then D 2.02 s paced by the longer path A, B, X, D
Three story sections, then synthesis 10.6 s sections finished at 1.6, 4.7 and 7.0 s; in sequence they take about 13.4 s

Table 2: Recorded wall times.

The synthesis step overlaps nothing, because it needs every section. So a fan-out costs the step before, plus the slowest branch, plus the merge: 7.0 s for the slowest section plus 3.6 s of synthesis gives the 10.6 s total.

Concurrency caps and submission order

Production adds a limit the toy graphs lack. The API behind the branches is rate-limited, so you cap how many branches run at once. In LCEL the cap is a setting on the call: six 0.5 s branches took 0.51 s unbounded and 1.51 s two at a time, three rounds of two.

Under a cap, order starts to matter. The interactive lab schedules the recorded section durations the way a thread pool does: branches are submitted in order and each starts on the first free slot. On the story sections:

Cap Submitted Merge starts Wall time
3 (all at once) as written 7.0 s 10.6 s
2 as written 7.0 s 10.6 s
2 fastest first 8.6 s 12.2 s
1 any order 13.3 s 16.9 s

Table 3: The lab’s schedule of the recorded durations.

A cap of 2 costs nothing as written: the 7.0 s setting branch gets a slot at once, and the premise runs after the characters in the other slot, finishing at 6.3 s. Submit the fast branches first and the setting waits 1.6 s for a slot, which the whole request pays. We call that the queued straggler: the slowest branch held behind faster ones. Start long branches first when you know their durations. The lab adds the printed one-decimal times, so its sequential total shows 13.3 s where the recorded run printed 13.4 s.

Sectioning and voting

The same fan-out mechanics serve two different jobs, and they buy different things:

Sectioning Voting
Branches do different parts of one task the same kind of check, independently
Lesson example characters, setting and premise of a story three security reviews of one function
State one key per branch, no reducer one shared list of votes, reducer required
Fan-in an LLM call that weaves the parts together plain code that counts flags against a threshold
Buys you latency confidence

Table 4: Two uses of one mechanism.

The recorded security vote

The voting graph gives each reviewer one concern (injection, secrets handling, input validation), and no reviewer sees another’s vote. Each returns a structured vote, flagged or not, with a reason. The aggregator blocks the code when at least 2 of 3 reviewers flag it:

Snippet Injection Secrets Validation Verdict
SQL built from user input by string interpolation; hard-coded password written to the log flagged flagged flagged (SQL injection) BLOCK, 3 of 3
Parameterised query, validated username, password read from the environment clear clear clear APPROVE, 0 of 3

Table 5: The two recorded reviews.

Setting the threshold

The threshold trades false alarms against misses. On the two recorded snippets every setting gives the same verdict, because the votes were unanimous:

Threshold Blocks when Unsafe snippet Safe snippet Trade-off
1 of 3 any reviewer flags BLOCK APPROVE most false alarms, fewest misses
2 of 3 (reference) a majority flags BLOCK APPROVE balanced
3 of 3 every reviewer flags BLOCK APPROVE fewest false alarms, most misses

Table 6: Thresholds on the recorded votes. Only split votes would separate them.

The unsafe run also shows a planted weakness. The validation reviewer flagged the SQL injection, which is the injection reviewer’s concern, so the votes are not fully independent. We call this correlated reviewers: two flags can be one finding counted twice. Allow for it before lowering the threshold, and test thresholds on snippets where the reviewers disagree.

In practice: Larkspur’s outage reply

Both uses appear in one Larkspur reply:

  1. Sectioning for evidence. Fan out to the handbook index, the status page and the account. The answer waits for the slowest source, so each branch gets a timeout and a fallback value, and each result keeps its source label so the reply can cite it.
  2. Voting before sending. Three narrow reviewers check the draft: does it promise a refund the policy does not allow, does it quote the right refund window, does it commit to a support response time. A threshold over three narrow checks is easier to tune than one judge asked about everything.

Lesson 24.4 removes the last fixed piece: an orchestrator decides at run time how many branches there are.

Limits of this evidence

  • One run per graph. The LLM timings in Tables 2 and 3 come from one recorded run; another run will finish its branches at different times.
  • Unanimous votes only. Neither recorded snippet split the reviewers, so the threshold’s effect is reasoned, not measured.
  • Left out: per-branch timeouts and fallback values. Add them when a branch calls a service that can hang.

Key Takeaways

  • A fan-out costs the step before, plus the slowest branch, plus the merge. Declare a reducer on any state key that parallel branches share, or the writes collide.
  • Rate limits force a concurrency cap, and then submission order matters: a queued straggler delays the whole request, so start long branches first.
  • Sectioning splits one task to cut latency; voting repeats one check to raise confidence. The threshold trades false alarms against misses, and correlated reviewers can count one finding twice.

Check yourself

1. Why does a fan-out's wall time follow its slowest branch rather than the sum of its branches?

The targets of a fan-out run in the same step, concurrently, and the fan-in node waits until all of them finish. So the cost is the step before, plus the slowest branch, plus the merge: the three story sections took 10.6 s in all, against about 13.4 s for the same calls in sequence.

2. Under a concurrency cap of 2, the story sections take 1.6, 4.7 and 7.0 seconds. Should you submit the fastest or the slowest branch first?

The slowest first. Submitted as written, the 7.0 s setting branch gets a slot at once and the request takes 10.6 s, the same as with no cap. Submitted fastest first, it waits 1.6 s for a slot, the merge starts at 8.6 s and the request takes 12.2 s.

3. The security vote blocks code at 2 of 3 flags and raises too many false alarms. Which way do you move the threshold, and what does it cost?

Raise it to 3 of 3. The aggregator then blocks less often: fewer false alarms, but more misses. Allow for correlated reviewers too, since the validation reviewer flagged the SQL injection outside its own concern, and check the change on snippets where the reviewers disagree.

Lesson 24.3 ran branches you wrote into the graph. Larkspur questions do not all have the same number of parts. Can I export my data after I cancel my plan? needs two answers: how to export, and how long data stays after cancellation. How long does a refund take? needs one. A fixed set of branches either wastes calls on the second question or misses half of the first.

Orchestrator-worker lets an orchestrator LLM decide, per input, how many subtasks there are and what each one covers. A worker runs once per subtask, and a final step merges the results.

A plan instead of fixed branches

The pattern looks like parallelization from outside. The difference is who decides the branches, and when:

Parallelization (24.3) Orchestrator-worker (24.4)
Who decides the subtasks you, when you build the graph the orchestrator, at run time
Number of branches fixed follows the input
Branch identity known in advance (characters, setting, premise) generated (whatever sections this input needs)
Graph shape static fan-out edges one conditional edge returning a list of Send

Table 1: Fixed branches against a run-time plan.

The same graph is often called map-reduce: the plan is the list, the fan-out maps one worker over it, and the synthesizer reduces the results to one answer:

Figure 1: Orchestrator-worker. The dotted edge fires once per plan item, a number the graph learns only after the orchestrator runs.

From plan item to worker

Four pieces make the plan load-bearing:

Piece What it does Why it matters
A variable-length plan The orchestrator returns structured output: a list of sections, each with a name and a description The list length is the number of workers
Dispatch from the plan The conditional edge returns one Send per section, each naming the worker node and carrying its own payload A normal edge returns one node; this returns as many runs as the plan has items
A narrow worker state Each worker sees the topic and its one section, and writes from that section’s description The worker does what the plan asked, nothing else
A reducer for results The results key concatenates lists, so any number of workers can write it in the same step Without it the parallel writes collide, as in 24.3

Table 2: The four pieces of a Send fan-out.

A Send is an instruction to run a named node with a given input. The graph drawing shows the orchestrator-to-worker edge once, because the count is unknown until the plan exists.

Workers finish in whatever order their calls return, but the reducer does not merge them in that order. In the same model-free graph, an export worker took 0.3 s and a retention worker 0.05 s:

View Order

The merged list follows the order the Sends were created, which is the plan order, so the final report reads in the planned order whichever worker finishes first. The notebook’s own order check makes the same point.

In practice: decomposing the export question

This is the shape of query decomposition (M17) and of the module lab:

  1. The orchestrator splits Can I export my data after I cancel my plan? into “how do I export?” and “what happens to my data after I cancel?”.
  2. Two workers each retrieve and answer one sub-question. Their evidence is the export and retention chunks of the M10 golden set.
  3. The synthesizer writes one reply from both, in plan order.
  4. How long does a refund take? gets a plan of one item; a one-item plan can skip the fan-out and answer directly.
  5. An empty plan returns a fixed reply instead of ending silently, and the plan size has a cap.

Lesson 24.5 adds the last ingredient the patterns so far lack: a loop that goes back and tries again.

Limits of this evidence

  • Model-free traces. Tables 3 and 4 come from our own graph of the same shape with hand-written plans; the notebook’s live planner was not rerun.
  • Padded plans from one model. The five-section result is the notebook’s report for gpt-4o-mini with that prompt; other models pad differently.

Key Takeaways

  • In orchestrator-worker an LLM decides at run time how many subtasks there are, and a conditional edge returns one Send per plan item. A reducer merges the results in plan order.
  • Make the plan drive execution: each worker gets only its own section and writes from its description. Fixed workers that ignore the plan make it decorative.
  • Guard the plan in code: ban padding in the prompt, cap the number of Sends, and decide what an empty plan returns, because it otherwise ends with no answer and no error.

Check yourself

1. Both orchestrator-worker and parallelization run several LLM calls at once and merge them. What separates them?

Who decides the branches, and when. In parallelization you wrote them into the graph as fixed edges. In orchestrator-worker an LLM decides at run time how many subtasks there are and what each covers, and one conditional edge returns a list of Send, one per plan item.

2. The orchestrator returns an empty plan for a Larkspur question. What does the caller get, and what should you add?

No worker runs, the synthesizer is never reached, and the run ends with no answer and no error, so a caller that only checks for errors sees success. Decide in code what an empty plan returns, such as a direct answer or a fixed reply, and cap the plan size as well.

3. The orchestrator's plan changes with every topic, yet the same five workers run every time. What is wrong?

The plan drives nothing: five fixed workers wired with plain edges ignore the orchestrator’s output, so the graph is parallelization with a decorative LLM call in front. Dispatch one Send per section, and have each worker write from its section’s description.

Bounded loops

Lesson 24.5: Evaluator-optimizer loops, always bounded: LangGraph vs LCEL. Notebooks: 05a_evaluator_optimizer_langgraph.ipynb, 05b_evaluator_optimizer_lcel.ipynb

What you’ll learn

  • Explain how an evaluator-optimizer loop feeds a critique back into the next draft.
  • Design criteria an evaluator can pass, with the verdict computed in code.
  • Prove that a loop ends when the evaluator never approves, and count its worst-case calls.
  • Choose where the loop lives: LangGraph, a Python loop around LCEL, or agent middleware.

Lessons 24.1 to 24.4 all run forward: every step happens once, or a fixed number of times. The 24.1 gate could retry, but it only re-ran extraction blind. This lesson’s pattern sends the reason for a rejection back to the step that can fix it.

A Larkspur answer can cite the handbook and still promise a refund the policy does not allow. A reviewer that names that problem, and a generator that revises with the review in hand, can catch it. The risk is a reviewer that never says yes.

Generate, evaluate, revise

Evaluator-optimizer generates a draft, grades it against explicit criteria and feeds the critique into the next draft, until the grade passes or a cap is reached. The 24.1 gate decided whether a result may proceed; this loop sends feedback to the generator. It pays off when two things hold: the criteria are clear, and feedback measurably improves the next attempt.

The lesson’s loop writes a short joke about agentic AI:

Figure 1: The bounded loop. Approval ends it, and so does the fifth draft.

The generator runs at temperature 0.7, so a revision can differ from the draft before it. The evaluator runs at 0 to keep grading as consistent as possible, though the same draft can still get a different grade on another call. From the second pass on, the generator receives the previous draft and the feedback, so it revises instead of starting over.

Criteria an evaluator can pass

The evaluator is only as useful as its criteria. A first version of the notebook asked for one holistic grade against loose criteria such as “is it genuinely funny?”, and with gpt-4o-mini the loop almost never converged: the evaluator kept finding something that could be better. We call this the moving bar. The bounded version changes three things:

Change In the reference loop Why
One yes-or-no per criterion clear punchline; a punchline that depends on agentic AI specifically; no stock template; appropriate A met criterion passes even when the joke could be better
Code checks what code can check Length is a word count of at most 40, computed in code A model should not be asked to count
The verdict is computed approved only when every criterion and the length check pass; otherwise needs improvement, with one fix named per failed criterion The model never asserts the grade itself

Table 1: From a holistic grade to computed criteria.

Proving the loop stops

A structured verdict does not guarantee the evaluator will ever approve. So the router checks two things in order: approval first, then the iteration count against a cap of 5. We ran the reference stopping rule on four states:

Grade Iteration Router returns What happens
needs improvement 1 refine the generator revises with the feedback
needs improvement 5 cap reached the run ends with the last draft, marked needs improvement
approved 5 approved the run ends with the draft
approved 2 approved the run ends early

Table 2: The router’s decisions. Approval is checked first, and no state starts a sixth draft.

The notebook proves the cap on a live generator with a stub reviewer that rejects every draft and makes no LLM call. Without the cap branch, that cell would never finish. With it, the run ends after five drafts.

The cap also bounds cost. Each pass is one generator call and one evaluator call:

Outcome Passes LLM calls
Approved on the first draft 1 2
Approved on the third draft 3 6
Never approved 5 10, the worst case

Table 3: Calls per run under a cap of 5.

Each guard has a case that shows why it is there:

Planted failure What happens The guard
The moving bar: one holistic grade The loop almost never converges Yes-or-no criteria, verdict computed in code
A reviewer that rejects everything Without a cap, the loop never ends The router’s iteration cap
A model asked to count words Length checks drift A word count in code

Table 4: One planted case per guard.

Pitfall: the capped success. A run that ends at the cap returns a draft that did not pass. Count it as a failure, and watch the share of runs that end there: it rises when criteria drift or a new evaluator model is stricter than the old one.

Where the bound lives

The bound sits in a different place in each implementation:

Implementation The loop is The bound is
LangGraph a conditional edge back to the generator the iteration cap checked in the router
LCEL plus Python a for loop around two chains the loop’s range, 1 to the cap
Agent middleware a hook after each model call that jumps back to the model a model-call limit of 5 that ends the run

Table 5: Three homes for the same bound.

For Larkspur, an answer-quality check is the natural evaluator, written as yes-or-no criteria: does the reply cite a handbook chunk, does it state the refund window the chunk states, does it avoid promising anything the handbook does not say, and is it under a length limit counted in code. CRAG (M29) applies the same loop to retrieval: grade the documents, rewrite the query, try again, within a bound.

Where LCEL stops

LCEL, the LangChain Expression Language, composes runnable steps into a flow. Every earlier M24 pattern is a flow without cycles, so each maps onto an LCEL building block. This one has a cycle, and LCEL has no block for “go back and try again until a check passes”:

Pattern LangChain 1.x building block Full coverage
Prompt chaining the pipe, plus retry and fallback wrappers yes
Routing a branch runnable yes
Parallelization a parallel runnable yes
Orchestrator-worker mapping a runnable over a list the fan-out; shared state and per-worker durability need Send
Evaluator-optimizer a Python loop, or a middleware hook that jumps back to the model yes, outside LCEL itself

Table 6: The five patterns and their LCEL coverage.

Two tempting shortcuts fail:

  • Piping generator, evaluator, generator builds a three-step chain that runs the generator twice. It never loops.
  • A retry wrapper re-runs a step blind, with no memory of why the last attempt failed. Feeding the critique forward is the point of the pattern.

Choosing the runtime around the loop

The two LangChain loops differ in what surrounds them:

Python loop around LCEL Agent middleware
Reads as a plain for loop one agent run with every pass nested
State a dict you shape the full message history
Tracing each pass as separate chain runs one run
Streaming, persistence none inherited from the agent runtime
How the critique arrives passed into the next prompt appended to the conversation as a user message

Table 7: Two ways to loop without LangGraph.

In the middleware version the hook must declare that it may jump back to the model; that declaration is what creates the conditional edge. When the loop needs checkpoints, interrupts or a human in it, move it to LangGraph.

Limits of this evidence

  • No recorded convergence counts. The notebooks ship without outputs, so how many passes a real joke needed is not measured here; the “almost never converged” result is the notebook’s own report on its first version.
  • Model-free router trace. Table 2 runs the reference stopping rule on hand-set states, not a live loop.
  • One task. Jokes are a cheap stand-in; Larkspur criteria were not run.

Key Takeaways

  • Evaluator-optimizer feeds a critique into the next draft until the grade passes. Use it only when the criteria are clear and feedback measurably improves the next attempt.
  • Grade with one yes-or-no per criterion, check length in code and compute the verdict from the checks. A single holistic grade becomes a moving bar the loop rarely clears.
  • Cap every loop in your own code, count a run that hits the cap as a failure, and do not rely on the framework’s default limit. LCEL cannot express the cycle, so use a Python loop or middleware, and LangGraph when you need checkpoints or interrupts.

Check yourself

1. Why did replacing one holistic grade with one yes-or-no per criterion make the joke loop converge?

Against a loose holistic grade the evaluator kept finding something that could be better, a moving bar. With yes-or-no criteria, a met criterion passes even if the joke could improve, length is counted in code, and approval is computed only when every check passes, so the model never asserts the grade itself.

2. With a cap of 5 iterations, how many LLM calls can one run make at most, and how should you count a run that hits the cap?

Ten, because each pass makes one generator call and one evaluator call. A run that ends at the cap returns its last draft marked needs improvement, so count it as a failure and watch the share of runs that end there.

3. A teammate builds the loop in LCEL by piping generator, evaluator and generator again, or by adding a retry. Why does neither work?

Piping builds a three-step chain that runs the generator twice; it never loops. A retry re-runs a step blind, with no memory of why the last attempt failed, while feeding the critique forward is the point of the pattern. Use a Python loop or a middleware hook that jumps back to the model, and move to LangGraph when the loop needs checkpoints or interrupts.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s reply drafter is an evaluator-optimizer loop. After an evaluator model upgrade, p95 latency triples and cost per ticket doubles, but no request fails. What happened, and what do you change?

What a strong answer covers:

  • Suspects the loop first: the new evaluator approves less often, so more tickets run to the iteration cap, and the cap returns a draft instead of an error
  • Confirms it from logs: drafts per ticket, the share of runs ending at iteration_cap_reached, and which criterion fails most
  • Fixes the criteria, not the cap: one boolean per criterion, counts and lengths checked in code, and a re-check of the new evaluator on drafts already graded by hand
  • Alerts on the cap-hit rate as its own metric, and marks capped answers so they are not sent as approved

2. Larkspur routes support questions by model tier. “Can I get a refund after 45 days?” needs proration arithmetic, and the triage step sends it to the cheap tier, which answers it wrong with confidence. Which way should the router err, and how do you prove the router pays for itself?

What a strong answer covers:

  • Names the asymmetry: over-escalation costs money and shows on a bill; under-escalation returns a wrong answer nobody sees until a customer acts on it
  • Biases triage toward hard on borderline cases and escalates before answering, since detecting a confident wrong answer afterwards is the hard problem
  • Measures routed accuracy and reasoning-call share against all-cheap and all-reasoning baselines on a labelled, honestly mixed set
  • Reads the router’s own confusion matrix, counting hard-sent-cheap separately, and remembers that triage is one more call on every request

3. The assistant fans out to the handbook index, the status page and the account API, then merges. p95 latency is 9 s and nobody knows which branch is slow. How do you find out, and what can you change?

What a strong answer covers:

  • Times each node as it finishes (stream_mode="updates" in LangGraph, or per-run traces), since the fan-in waits for the slowest branch and the mean hides it
  • Gives each branch a timeout and a fallback value, so one slow source degrades the answer instead of stalling it
  • Checks the concurrency cap against the API rate limits and submits the slowest branch first when a cap applies
  • Checks whether the merge step itself dominates: it needs every branch, so no fan-out can shorten it

4. You rebuild query decomposition as orchestrator-worker. For “How long does a refund take?” the planner returns five sub-questions, including “Introduction” and “Conclusion”. What went wrong, and what guards do you add?

What a strong answer covers:

  • Spots padding: a prompt with numeric anchors (“simple topics need 2, broad topics 5+”) produced five sections for every topic in lesson 24.4
  • Rewrites the planner prompt to ask for one item per distinct question and forbids padding sections
  • Bounds the plan in code: a maximum number of Sends, a direct path for single-part questions, and a defined result for an empty plan
  • Checks that workers consume their item, by confirming the set of workers that ran changes with the plan

5. A product manager wants to replace the fixed refund workflow with a ReAct agent “so it can handle anything”. When do you agree, and what do you keep?

What a strong answer covers:

  • Keeps a workflow where the steps are known: its calls are countable, each node and router can be unit-tested, and it stops at a known node with a reason
  • Uses an agent where the steps depend on what the model finds, such as a multi-step account investigation, and accepts trajectory-level evaluation and a step limit as the bound
  • Proposes a hybrid: a router that sends known intents to workflows and only the rest to the agent
  • Compares both on the same golden questions for accuracy, LLM calls, p95 latency and the share of runs that hit a limit

Key Takeaways

  • Draw the graph first. If you can, it is a workflow; give the model one decision per node at most, and keep that decision in a closed set your edges cover.
  • Put a gate where a bad intermediate result would waste the steps after it, and give every gate a retry count and a terminal “stop with a reason” node.
  • Measure a router against both of its baselines, and bias it toward the error that costs money rather than the one that costs correctness.
  • Every loop has a cap in code, and hitting the cap is a metric. A fan-out costs its slowest branch, so time branches one by one before tuning any of them.
