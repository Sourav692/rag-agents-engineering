M29 Self-correcting RAG: CRAG and Self-RAG

A RAG pipeline that never checks its own work answers from whatever retrieval returns, relevant or not. This module adds the checks. Corrective RAG (CRAG) grades the retrieved chunks before generation and looks elsewhere when too few pass; Self-RAG also decides whether to retrieve at all and checks the answer after generation for support and usefulness. Every check is another model call, so the module ends by counting what each pipeline spends and where the spending buys nothing. The M29 notebooks build on four ideas: grading retrieval before generation, refining the context, the four reflection decisions, and checking that an answer is grounded.

What correction costs
Open the lab

The running example is the twelve-chunk Larkspur Cloud handbook from M10 and its three golden questions, plus two questions the handbook cannot answer: Does Larkspur offer GPU servers? and How much does the starter plan cost per month? The handbook is private, so a web search cannot answer for it. That makes it a fair stress test for a pipeline whose fallback is the web.

TL;DR

  • CRAG puts a retrieval evaluator between retrieval and generation. In notebook 01a it grades each chunk yes or no and searches the web when half or fewer pass; in 01b it scores each chunk from 0 to 1 and picks Correct (above 0.7), Incorrect (below 0.3) or Ambiguous.
  • Knowledge refinement cuts the context down to the parts that answer the question before generation. 01b does it with an LLM call that turns a document into bullet points.
  • Self-RAG makes four judgments, the reflection tokens of the paper: retrieve or not, is this chunk relevant, is the answer supported, is it useful. Notebook 02a asks an LLM for each one and caps the retry loops at max_iterations = 2.
  • The groundedness check is the hallucination guard, and in 02a it has two holes: it passes without a call when there are no documents, and its regenerate loop ignores the iteration cap.
  • Correction is paid in LLM calls. In the lab at k = 5, the baseline makes 1 call per question, CRAG 5.6 on average and Self-RAG 15.0, up to 20 on a question the handbook cannot answer.

Mental model

There are two places to catch a bad answer. CRAG checks the context before generation; Self-RAG also checks the answer after it. Each check is an LLM call, and each failed check sends the question round again, so the price of correction is set by how often the checks fail.

Retrieval evaluator

M28 graded each retrieved chunk and rewrote the question when none passed. Corrective RAG keeps that grader and adds a second exit: when too few chunks pass, it goes outside the index for evidence.

Take the Larkspur question What happens if my server goes down? The M10 baseline’s TF-IDF retrieval at k = 3 returns three chunks about reboots, server sizing and exports, and the model writes an answer from them. Nothing in that pipeline notices that none of the three is about outages. We call this blind generation: the generator answers from whatever retrieval returned, because nobody checked it first.

Corrective RAG (Yan et al., Corrective Retrieval Augmented Generation, 2024, arXiv:2401.15884) adds one component to the baseline. A retrieval evaluator is a check that judges the retrieved documents before the generator sees them, and its verdict picks the next step. The paper gives it three verdicts:

  • Correct: retrieval looks right, so generate from it.
  • Incorrect: retrieval looks wrong, so find other context.
  • Ambiguous: the evaluator is unsure, so use both.

The paper trains a small model (T5-large) as the evaluator. Both M29 implementations prompt an LLM instead, which costs one call per judgment.

The CRAG graph

The LangGraph implementation turns the evaluator into a node and a conditional edge. Here is the graph it builds:

Figure 1: The CRAG graph. Its nodes are retrieve, grade_documents, rewrite_query, web_search and generate_answer.

The grader keeps the chunks graded yes and drops the rest. When nothing is retrieved at all, the graph also takes the web branch. The graph runs once, with no loop back to retrieval.

The graph collapses the paper’s three verdicts into two, because a yes-or-no grade has no middle. The function variant keeps all three, because a score has room for a band between the thresholds.

Where the majority rule breaks

The graph’s rule is a fraction of the retrieved set, and that has consequences you can work out without calling a model. Hold the number of relevant chunks fixed and vary how many were retrieved:

3 2 0.67 generate
5 2 0.40 web search
1 1 1.00 generate

Every Larkspur golden question has two evidence chunks. A perfect grader keeps those two, and 2 of k is more than half only when k is 3 or less. Case Question, k Chunks kept Route LLM calls

Diluted majority Same question, 5 retention, export web search 7, plus the search
Thin pass Same question, 1 retention generate 2
Wrong fix What happens if my server goes down?, 3 none of reboot, sizing, export web search 5, plus the search

Table 3: Planted failures of the majority rule, from the M29 lab.

Each planted row names a failure mode:

  • Diluted majority: extra low-ranked chunks lower the fraction, so CRAG falls back with both evidence chunks in hand. The threshold moves with k.
  • Thin pass: one relevant chunk out of one passes the rule, and CRAG answers without the export chunk that says how to export. The evaluator grades chunks, not whether the set is complete.
  • Wrong fix: the grader rightly rejects all three outage chunks, and CRAG searches the web for a private handbook’s outage policy. The answer was in the corpus all along, under the words “outage” and “availability”.

Key distinction: the evaluator says whether the context is good enough. It says nothing about where better context lives, and the fallback is a separate design choice.

Where missing evidence may come from

A correct verdict of “not good enough” still needs a fix that can reach the evidence. The options differ by where they look:

  • Web search: suits a corpus of public facts that go stale, such as the research papers the CRAG graph indexes.
  • Rewrite and retry inside the index: suits a miss caused by wording, like the outage question (M17 rewriting, M28 retry loop).
  • Refusal: suits a question the corpus cannot answer, where any answer would be invented.

For a private handbook the web branch fits none of Larkspur’s misses. Replace it, or guard it so it runs only for questions about public facts: retry inside the index first, then refuse. Knowledge refinement is the other half of CRAG, and it works on the context the evaluator lets through.

Knowledge refinement

Retrieval returns whole chunks, and a chunk can mix the sentence that answers the question with sentences that do not. Knowledge refinement cuts the context down to the parts that answer the question before generation. The CRAG paper does it with decompose-then-recompose:

Figure 2: Decompose-then-recompose, the paper’s refinement step.

The function variant uses a simpler version. Its refinement step sends one document to the LLM with the prompt “Extract the key information from the following document in bullet points” and returns the bullets. Where it runs depends on the verdict:

Verdict Best score Context sent to the generator
Correct above 0.7 the best retrieved document, as is
Incorrect below 0.3 refined bullets from the web results
Ambiguous 0.3 to 0.7 refined bullets from the best document, plus refined web results

Table 4: Where the function variant refines its context.

The verdicts form a short chain of decisions on the best score:

Figure 3: The function variant’s three verdicts as a chain of thresholds.

The LangGraph graph has no refinement step. It filters at chunk level, keeping only chunks graded yes, and passes web pages as full text, so a fallback can put six whole pages into the prompt. We call that context flood: the evaluator removes bad chunks from the index, then the fallback adds pages nobody graded.

Strips on the export question

On the export question at k = 3, the retriever returns retention, export and cancel. Chunk-level filtering keeps the first two whole. Strip-level refinement would go one step further, as this hand-written illustration shows:

Strip Keep?
retention: After a plan is cancelled, its data is kept for 30 days and then permanently deleted. yes, it answers “after I cancel”
retention: Export it before that window closes. yes
export: Export your data at any time from Settings, then Data. yes, it says how
export: Exports include databases, object storage and server snapshots. borderline, it answers a different question
cancel: You can cancel any plan from the Billing page. no

Table 5: Strip-level refinement on the export question (illustrative, written by hand, not a measured output).

Refinement has two costs. It adds one LLM call per document it rewrites, and an LLM that rewrites evidence can also change it. We call the second one rewritten evidence: a bullet that reads well and no longer says what the chunk said. Keep the original chunk id beside each bullet so the answer can still cite its source, and so a reviewer can compare the bullet with the text.

In practice: CRAG on the Larkspur handbook

Run the support assistant’s questions through the graph and its weak points show up in order:

  1. Can I export my data after I cancel my plan? at k = 3 keeps both evidence chunks and answers in 4 calls. At k = 5 the same chunks trigger a diluted majority and a web search.
  2. What happens if my server goes down? gets a correct “not relevant” verdict and then the wrong fix: a web search that cannot see the handbook.
  3. Does Larkspur offer GPU servers? is not in the handbook. The web branch fires and can return another provider’s GPU plans, which the generator may present as Larkspur’s.

For Larkspur, the fallback becomes a rewrite against the index followed by a refusal, and every route is logged with the chunks graded, the chunks kept and the branch taken.

Interview tip: when a CRAG answer is wrong, read the route before the prompt. Which chunks came back, how each was graded and whether the web branch fired usually explain the answer.

Lesson 29.2 adds the check CRAG lacks: one that runs after generation and looks at the answer itself.

Key Takeaways

  • CRAG grades the retrieved chunks before generation and falls back to a rewritten web search when too few pass. It grades chunks, not answers, so a passing set can still miss the evidence, and a fraction-based rule moves with k.
  • A web fallback suits public facts that go stale. For a private handbook, replace it with a retry inside the index and then a refusal, because the web cannot see your documents.
  • Knowledge refinement cuts chunks down to the parts that answer the question before generation. An LLM that rewrites evidence can also change it, so carry the source chunk id with every bullet.

Its rule is a fraction: generate only when more than half of the retrieved chunks are graded relevant. Every golden question has two evidence chunks, and 2 of k is more than half only when k is 3 or less. At k = 5 the export question keeps both evidence chunks and still falls back, spending 7 calls plus a web search instead of 4.

2. On the outage question, retrieval returns the reboot, sizing and export chunks, and the grader rightly rejects all three. What does CRAG do next, and what should it have done?

It searches the web for a private handbook’s outage policy, which the web cannot see. The answer was in the corpus all along, under the words “outage” and “availability”. A rewrite and retry against the index (M17, M28) would have found it, so for a private handbook, retry inside the index and then refuse.

It costs one more LLM call per document it rewrites, and an LLM that rewrites evidence can also change it. Keep the original chunk id beside each bullet so the answer can still cite its source and a reviewer can check the bullet against the chunk.

Reflection tokens

Lesson 29.2: Self-RAG: retrieve-or-not, relevance, groundedness, utility. Notebooks: 02a_self_rag_langgraph.ipynb, 02b_self_rag_rag_techniques.ipynb (optional)

What you’ll learn

  • Explain the four reflection decisions of Self-RAG and the question each one answers.
  • Trace a question the handbook cannot answer through every loop, and count its LLM calls.
  • Diagnose a groundedness check that passes without running, and a retry cap that never bites.
  • Choose where a loop counter must be updated in a LangGraph graph.

Lesson 29.1 checked the context before generation and never looked at the answer. Self-RAG checks both, and it can also skip retrieval when a question does not need it.

A Larkspur answer can cite real policy and still miss the question. As an illustrative case, ask Can I export my data after I cancel my plan?, retrieve only the export chunk, and the model can write a well-supported paragraph on how to export that never mentions the 30-day retention window. Every sentence is grounded in the context, and the customer still loses their data. Relevance, support and usefulness are three separate properties, and a pipeline that checks one of them misses the other two.

Self-RAG (Asai et al., Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection, 2023, arXiv:2310.11511) trains one model to emit special tokens that judge its own pipeline. Reflection tokens are labels the model produces about its own retrieval and output: whether to retrieve, whether a passage is relevant, whether the answer is supported, and whether it is useful. The table lists the four kinds and how each implementation in this module represents them:

Token Question it answers Values in the paper Self-RAG graph (LangGraph) Self-RAG function variant (optional)
Retrieve Do I need documents for this? yes, no, continue need_retrieval: yes or no Yes or No
ISREL Is this passage relevant? relevant, irrelevant yes or no, per chunk Relevant or Irrelevant
ISSUP Is the answer supported by the passage? fully, partially, no support yes or no, plus feedback Fully supported, Partially supported or No support
ISUSE Is the answer useful for the question? a score from 1 to 5 yes or no, plus feedback an integer from 1 to 5

Table 1: The four reflection tokens in the paper and in the two implementations.

In the paper the tokens are part of the model’s vocabulary and come out of the same decoding pass as the answer. Neither implementation trains a model. Each judgment is a separate LLM call with a structured-output schema, so “reflection token” here means one more call that returns a label.

Key distinction: in the paper a reflection costs a few extra tokens. In these implementations it costs a full model round trip, and that changes which checks are worth running.

How the graph wires the four checks

The LangGraph implementation wires each judgment to its own conditional edge:

Figure 1: The Self-RAG graph. Two loops go back through a rewrite, one goes straight back to generation.

The three loops have different exits:

  • No relevant chunk: rewrite the question and retrieve again.
  • Answer not useful: rewrite the question and retrieve again, with the utility feedback as a hint.
  • Answer not grounded: generate again, with the groundedness feedback in the prompt.

max_iterations = 2 bounds the rewrite loops, because the rewrite node increments the counter each time it runs. After two rewrites the relevance router sends the question to generation even with no relevant chunk, and the utility router ends the run.

The first token is the one CRAG lacks. What is 9 plus 10? gets need_retrieval = no in the graph and skips the vector store. Every Larkspur question is about the handbook, so on this corpus the Retrieve token saves nothing and costs one call.

The expensive question is the one the handbook cannot answer, and the run ends with a generation that has nothing to be grounded in. The groundedness check is the next section, and it is where that generation should have been caught.

Groundedness check

A groundedness check asks whether every claim in the answer is supported by the context the answer was generated from. It is Self-RAG’s hallucination guard. In the graph, the groundedness node sends the context and the answer to a “strict fact-checker” prompt. The schema returns a yes only if every claim is supported, and a feedback string naming the unsupported claims.

On a no, the router sends the run back to generation, and the feedback goes into the prompt as “a previous attempt at this answer was rejected for this reason”. The regenerate loop is shown here as a sequence of calls:

Figure 2: One regeneration after an unsupported answer.

Groundedness and utility are separate checks because they fail separately. The export answer in the opening example is fully grounded and still not useful. An answer that quotes the retention window correctly and adds an invented export fee (again illustrative) sounds useful and is not grounded.

Planted failures in the hallucination guard

Two details in the graph decide what the check actually catches. Planting one failing case against each shows them:

Planted case What the graph does Why
No relevant chunk after the cap, starter-plan question Generates with no context; groundedness returns yes with no call The node treats “no documents” as grounded by default
A groundedness grader that always says no Regenerates until LangGraph raises a recursion error The regenerate loop’s counter update is discarded
The same question in the function variant Generates from “No relevant context found.” with a prompt that asks only for a response, and runs no support check No instruction to refuse, so the model answers from memory

Table 3: Three planted failures of the groundedness check.

The first row is the empty-context pass. On the starter-plan question, Self-RAG exhausts its rewrites, generates with no context, and the check waves the answer through. The only guard left is the generation prompt’s line “If the context does not contain enough information to answer confidently, say so plainly”. The function variant is weaker still: its own low-relevance test asks a climate-change corpus how did harry beat quirrell?, and nothing stops the model from answering.

Pitfall: the empty-context pass. A check that returns yes when it has nothing to check guards only the cases where it was least needed. Route “no documents after the cap” to a fixed refusal instead.

The counter that never moves

The second row is the stuck counter. The groundedness router writes iteration + 1 into the state inside the routing function. In LangGraph a conditional-edge router only returns the name of the next node. Only what nodes return is merged into the state, so a write inside a router is discarded:

Where the update happens Kept in state? Effect on the cap
The rewrite node returns the new iteration yes Rewrite loops stop after two rewrites
The groundedness router writes the iteration no The regenerate loop never moves the counter

Table 4: Why one loop is bounded and the other is not.

The cap still bites if earlier rewrites already pushed the counter to 2, because the router reads that value. On a question that passes relevance on the first pass, the counter starts at 0 and stays there. Run against the example’s own node and router code with a groundedness grader that always says no, the compiled graph (langgraph 1.2.18) regenerated until LangGraph raised GraphRecursionError. With recursion_limit = 200, that was 98 regenerations and 200 LLM calls. With the default config it ran to the limit that release reports, 10,007 steps.

The fix is to count in a node: have generation return the new iteration when it is regenerating, or add a small regenerate node before it. A test with a grader that always says no proves the fix, and a per-request call budget catches the next loop nobody bounded.

Keeping three support levels

The paper’s three support levels are worth keeping when you build this yourself. The function variant generates one candidate answer per relevant passage and ranks them by “fully supported” first and utility second. A yes-or-no grade cannot rank candidates that way, because a partially supported answer and an unsupported one both come back as no.

In practice: Self-RAG on the Larkspur handbook

Run the four checks on Larkspur’s questions and the cost and the gaps line up:

  1. Can I export my data after I cancel my plan? passes relevance, groundedness and utility on the first pass: 9 calls at k = 5 for the context the baseline read in 1.
  2. How much does the starter plan cost per month? runs three retrieval passes and 20 calls, then hits the empty-context pass: the answer that most needs checking is the one the check skips.
  3. A grader outage that returns no on every call turns any first-pass question into a stuck counter and runs to the recursion limit.

For Larkspur, the out-of-corpus route ends in a refusal and a handoff to support, the regenerate counter moves in a node, and every request carries a call budget. Lesson 29.3 puts these call counts next to CRAG’s and the baseline’s.

Key Takeaways

  • Self-RAG judges four things: whether to retrieve, whether each chunk is relevant, whether the answer is supported and whether it is useful. In these implementations each judgment is one more LLM call that returns a label.
  • The loops make cost depend on the question, from 9 calls on the export question to 20 on an out-of-corpus price question at k = 5. With no documents, the groundedness check passes without running.
  • Groundedness and utility fail separately, so check both, and make “no documents” a refusal rather than a pass.
  • Update loop counters in a node, because LangGraph discards state written inside a routing function, and back every loop with a per-request call budget.

Cost per question

Lesson 29.3: Trade-offs: when correction is worth the extra calls

What you’ll learn

  • Compare the three pipelines on the five Larkspur questions at two values of k.
  • Diagnose a correction loop that spends calls on evidence it can never reach.

Lessons 29.1 and 29.2 built two ways to catch a bad answer: CRAG grades the context before generation, and Self-RAG also checks the answer after it. Both are paid for in model calls, and neither was free on the questions we traced.

Larkspur’s product team wants Self-RAG on every support question “to stop hallucinations”. The assistant already handles most of Larkspur’s support traffic, and on the refund question Self-RAG spends 18 calls and still never sees the chunk that answers it. More calls bought nothing there. This page counts what each pipeline spends, finds where the spending goes, and turns that into a rule for when correction is worth it.

Calls by path

Every check in CRAG and Self-RAG is an LLM call, and every failed check sends the question round again. The calls can be counted from the graphs themselves:

The five questions, measured

Where the calls go

Three patterns hold across Table 2, and each is a failure mode worth naming:

  • Expensive dead end: correction costs most where it helps least. The two questions the handbook cannot answer cost Self-RAG 14 to 20 calls, and they end with a generation that has no context to be grounded in. CRAG sends both to the web, which cannot see a private handbook.
  • Unreachable evidence: some misses no check can repair. On the refund question, refund-timing shares no term with “How long does a refund take?”, so it is never retrieved and never graded. Self-RAG’s utility check sees the gap and spends 18 calls on three passes that return the same chunks. The fix is upstream, in retrieval (M13, M16) or in a rewrite that changes the words (M17).
  • Overhead on easy questions: at k = 3 the export question is answered from both evidence chunks by all three pipelines. CRAG pays 4 calls and Self-RAG 7 for the same context the baseline read in 1.

Pitfall: the expensive dead end. A loop that looks for evidence the corpus does not hold spends its whole budget and then answers anyway. The cheapest fix is a refusal path that ends the loop early.

Latency depends on how the calls are scheduled, and the reference implementations make them one after another: both graphs grade chunks in a Python loop, so k grades add k round trips of waiting. When correction pays

Correction earns its calls when a wrong answer costs more than the extra latency and tokens, and when the fix it reaches for can supply the missing evidence. Both halves matter: a check on a low-stakes question is overhead, and a check whose fix cannot reach the evidence is an expensive dead end. A short chain of questions settles most cases:

In practice: a correction policy for Larkspur

For the Larkspur assistant the decision chain gives one policy per question type:

  1. Billing and refund questions get a check, because a wrong refund window turns into a support ticket. A relevance grade per chunk and one groundedness check on the answer add k + 1 calls.
  2. The web fallback stays off. Every Larkspur fact lives in the handbook. A question the handbook cannot answer gets a refusal and a handoff to support, never a search.
  3. Retrieval misses are fixed in retrieval. The outage question fails on wording. One rewrite against the index is cheaper than three Self-RAG passes or a web search.
  4. Every loop gets a counter and a budget. max_iterations caps the rewrite loops in the Self-RAG graph; the regenerate loop needs a counter updated in a node (lesson 29.2), and a per-request limit on LLM calls catches the next loop nobody bounded.

Interview tip: answer “should we add Self-RAG everywhere?” with a count. Table 2 shows 15.0 calls per question against 1 at k = 5, and the refund row shows calls that changed nothing.

What the lab leaves out

The lab’s numbers are call counts under stand-in graders, so some questions stay open:

  • Answer quality. The lab does not judge whether any pipeline’s answer is right. The M29 lab notebook’s out-of-corpus run counts refusals and hallucinated answers; add it when you need accuracy next to cost.
  • Real grader errors. The stand-in relevance grader is perfect. A real one makes mistakes in both directions, which changes both routes and counts.
  • Rewrites that work. The lab’s rewrite repeats the question, so Self-RAG’s counts are a ceiling for questions a better rewrite could reach.
  • Tokens and price. A grading call over one chunk is far smaller than a generation over five chunks plus six web pages. Weight calls by tokens before quoting a cost in money.

Key Takeaways

  • Count the calls before adding correction. On the lab’s golden set at k = 3, the mean was 1 call for the baseline, 4.6 for CRAG and 13.4 for Self-RAG.
  • No check repairs a chunk that retrieval never returns, and questions the corpus cannot answer cost the most. Fix wording misses upstream, with better retrieval or a rewrite against the index.
  • Add correction where a wrong answer costs more than the extra latency, such as refund questions. Keep the web fallback off for a private corpus, and give every loop a counter and a per-request call budget.

Check yourself

1. Why does correction cost the most on the questions where it helps the least?

The two questions the handbook cannot answer are the most expensive for Self-RAG, 14 to 20 calls, and they still end with a generation that has no context to be grounded in. CRAG sends both to the web, which cannot see a private handbook. The checks spend their budget looking for evidence that does not exist, so a refusal path is the cheaper fix.

2. At k equal to 3, all three pipelines answer the export question from both evidence chunks. How many LLM calls does each one pay?

The baseline pays 1, CRAG 4 and Self-RAG 7, all for the same context. On an easy question the checks are pure overhead.

3. Self-RAG spends 18 calls on the refund question and never retrieves the refund-timing chunk. Where should the fix go?

Upstream, in retrieval. refund-timing shares no term with “How long does a refund take?”, so it is never retrieved and never graded, and three passes return the same chunks. Fix it with better retrieval (M13, M16) or a rewrite that changes the words (M17), not with more checks.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s support assistant runs CRAG with a web fallback. A customer asks what happens when their server goes down, and the assistant quotes another provider’s availability guarantee. The handbook has the right answer. What went wrong, and what do you change?

What a strong answer covers:

  • Reads the trace first: which chunks came back, how each was graded, and whether the web branch fired. In the lab, TF-IDF retrieves reboot, sizing and export for this question, the grader correctly rejects all three, and CRAG goes to the web
  • Names the two faults: a retrieval miss on wording (“server goes down” against “outage” and “availability”), and a fallback that searches a source which cannot know a private handbook
  • Fixes retrieval inside the corpus first: a rewrite-and-retry against the index (M28), hybrid or embedding search (M16, M13)
  • Restricts the web branch to questions about public facts, or replaces it with a refusal that says the handbook does not cover the question

2. Product wants Self-RAG on every Larkspur question “to stop hallucinations”. The assistant already carries most of Larkspur’s support traffic. How do you decide?

What a strong answer covers:

  • Counts calls before arguing: in the lab at k = 5 Self-RAG averages 15.0 LLM calls per question against 1 for the baseline, and the easy export question still costs 9
  • Notes that 02a grades chunks one at a time in a loop, so calls add latency in series unless they are batched
  • Proposes tiering: the baseline with a cheap check for most traffic, the full loop for high-stakes intents such as billing and refunds
  • Measures on the golden set whether the extra calls change answers, and keeps the loop only where they do

3. CRAG has been live for a month. How do you tell whether the retrieval evaluator is helping or just adding cost?

What a strong answer covers:

  • Logs the route for every request: chunks graded, chunks kept, relevant fraction, web fallback yes or no
  • Tracks the web fallback rate by question type; a rate that jumps after an index change points at retrieval, not at the questions
  • Samples cases where the grader kept everything and cases where it kept nothing, and grades them by hand to measure the grader’s own precision and recall
  • Watches for the threshold coupling with k: in the lab the export question falls back to the web at k = 4 and k = 5 with both evidence chunks kept

4. Someone asks the Self-RAG assistant “How much does the starter plan cost per month?” The handbook lists no prices. The groundedness check passed, yet the answer contains a price. How?

What a strong answer covers:

  • Traces the loop: no chunk is relevant, so 02a rewrites and retrieves until the cap, then generates with no documents
  • Points at grade_groundedness: with no documents it returns “yes” without calling the grader, so the check never ran
  • Notes the only remaining guard is the generation prompt’s instruction to say so when the context is missing; 02b drops even that and answers from the model’s memory
  • Fixes it by routing “no relevant documents after the cap” to a fixed refusal, and by adding out-of-corpus questions to the golden set

5. A cost dashboard shows one Self-RAG request that made about 200 LLM calls before it failed with a recursion error. The iteration cap is 2. Where do you look?

What a strong answer covers:

  • Suspects a loop that does not move the counter, and reads the routers
  • Finds it in 02a’s route_after_groundedness, which writes state["iteration"] inside a routing function; LangGraph keeps only what nodes return, so the counter never moves and the regenerate loop runs until the recursion limit
  • Moves the increment into a node (for example, generate returns the new iteration when it regenerates) and adds a test with a grader that always says “no”
  • Sets an explicit recursion_limit and a per-request call budget as a second guard

Key Takeaways

  • Grade the context before you generate from it, and log the grade: the route a request took is the first thing to read when an answer is wrong.
  • Pick the fallback by where the answer can live. A web search cannot answer for a private handbook; rewrite and retry against your own index first, and refuse when the corpus has nothing.
  • A groundedness check guards only the cases it runs on. Make “no documents” a refusal, never an automatic pass.
  • Count LLM calls per question on your golden set before you ship a correction loop, and bound every loop with a counter that a node, not a router, updates.
