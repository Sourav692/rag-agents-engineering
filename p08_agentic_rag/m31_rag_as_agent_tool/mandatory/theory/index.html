M31 RAG as an agent tool

Larkspur needs handbook evidence for a policy answer, but small talk should not trigger a search. This module lets the agent choose when to call a retriever tool, measures the description that drives that choice, and then moves the retriever behind a managed service and the agent behind a chat window.

Agentic RAG
Tool descriptions and routing
Open the lab

The running example is the Larkspur Cloud support agent. It has two tools: handbook_search, a retriever over the handbook from M10 to M12, and web_search for everything outside Larkspur. The lab routes twenty mixed questions between them, ten about the handbook (How long does a refund take?, Can I export my data after I cancel my plan?), six for the web (What does Hetzner charge for a 4 GB server?) and four that need no tool at all (What is 15% of 240?).

TL;DR

  • As a tool, retrieval runs inside a loop: the agent node calls the model, the model may reply with a tool call, ToolNode runs the retriever, and the chunks go back to the model as a ToolMessage. The loop ends when the model replies without a tool call. The default retriever tool drops each chunk’s source, so print it into the chunk text when the answer must cite.
  • All the model knows about a tool is its name, its description and its argument schema. In the lab, where TF-IDF stands in for the model, two tools both described as “Search tool.” route 4 of 20 questions correctly, and only the four that needed no tool; specific descriptions route 15 of 20.
  • Tune descriptions like any retrieval setting: on a golden set, then on questions held out from it. Fitted to the lab’s twenty questions they route 19 of 20 and 4 of 5 held-out questions, and they cost 133 tokens on every model call instead of 84.
  • A managed RAG platform (Contextual AI in lesson 31.2) runs the datastore, parser, reranker and grounded generator behind one API. The agent can call the whole platform as a single tool, so swapping it in leaves the agent loop unchanged.
  • A chat UI adds sessions, settings and visible tool steps. State such as the index and the agent belongs to the user’s session, not to module globals.

Mental model

Retrieval sits inside the loop, so the model decides whether it runs, how often, and with which query. A question that never triggers a tool call is answered from the model’s weights, with no handbook text in front of it. The quality of the retriever matters only for questions the model sends to it.

M22 built the agent loop, and M30 routed questions inside a fixed graph where code decided whether to retrieve. This lesson puts the retriever inside the loop and hands that decision to the model.

A Larkspur customer asks How long does a refund take? The support agent has a handbook_search tool, and the handbook says refunds take 5 to 10 business days. The agent gives a confident, generic answer with no citation. The trace shows one model call and no tool call.

Two things can cause it. Either the graph gave the model the decision and the model declined it, or the description gave the model no reason to pick the tool. This page takes them in that order.

Agent-decided retrieval

Two graphs over one retriever

The notebook builds two graphs over one retriever: four short documents about a fictional cafe in Chroma, searched with k = 2. In the first, the pipeline decides. A classifier node, topic_decision, asks the model a yes or no question with structured output. A conditional edge then sends the question either to retrieve and generate_answer or to a fixed off-topic reply:

Figure 1: The pipeline decides. Every on-topic question is retrieved exactly once, with the user’s words as the query.

The model decides

Agent-decided retrieval means the retriever is one of the model’s tools, and the model chooses whether to call it, how often and with which query. In the second graph the retriever becomes retriever_tool, beside an off_topic tool for unrelated questions. The agent node calls the model and ToolNode runs the tools it asked for. The run loops back to agent while the reply carries tool calls and ends when it carries none:

Figure 2: The model decides. The retriever runs only because the model’s reply asked for it.

Both graphs spend two model calls on a handbook question: classify then generate in the first, tool call then answer in the second. They differ in who decides and in what the retriever receives:

The model-decided graph handles small talk with no retrieval, rewrites a follow-up into a better query, and searches again when the first chunks miss. It pays with a decision you no longer control in code. Each graph has its own way to miss the handbook on the opening question:

Send the refund question through each graph and compare where the handbook can be missed. Scripted illustration on the Larkspur handbook.

Pipeline decides

  • The classifier answers yes, and retrieve searches with the user's exact words.
  • If it answers no, the handbook is never searched and the customer gets the fixed off-topic reply.

Failure: a classifier veto. Two model calls when it passes, one when it vetoes.

Model decides

  • The model reads the tool descriptions and may call handbook_search with a query it writes, such as "refund timing".
  • If nothing in the descriptions points at refunds, it answers from its training data.

Failure: a silent skip. One model call and nothing to cite, the trace from the opening.

We call the second failure a silent skip: the model answers a policy question without calling handbook_search, from its training data, with nothing to cite. Its mirror in the fixed graph is the classifier veto: a no from topic_decision, and the handbook is never searched.

What the tool hands back

A retriever tool turns a list of Documents into one message, and that step can lose the sources. The standard wrapper, create_retriever_tool, joins the chunk texts with a blank line and drops each Document’s metadata. We wrapped a fixed retriever that returns one chunk, Refunds take 5 to 10 business days., tagged refund-timing, three ways:

Wrapper setting What the model receives Source visible to
Default the chunk text only nobody
A document prompt that prints the source refund-timing: Refunds take 5 to 10 business days. the model
Content plus artifact the chunk text, with the full Documents kept beside it your code, not the model

Table 2: One chunk through three wrapper settings (run against the installed langchain_core 1.7.0).

We call the default row’s failure the lost source: the model quotes a correct policy and cannot say where it came from. Print the source into each chunk when the answer must cite, and keep the artifact when your code checks citations.

Getting the evidence back intact matters only once the model has chosen the tool, and that choice rests on the description.

Tool descriptions

A tool description is the short text the model reads to decide whether a tool fits the question. When the model picks a tool it sees three things per tool and nothing else:

Figure 3: The model’s whole view of a tool. It never sees the documents behind it.

In the notebook the description reads Information related to pricing, hours, or the founder of Cafe Lumiere, over one query string argument. That sentence now carries the scope the first graph kept in its classifier prompt. It also has to separate the retriever from every other tool the model can call.

Measuring routing with a stand-in router

The interactive lab gives the Larkspur agent handbook_search and web_search and routes twenty golden questions (ten for the handbook, six for the web, four for no tool) plus five held out. Its router stands in for the model: the M10 TF-IDF retriever scores each question against the two descriptions and picks the higher, or no tool when neither shares a word. On all 100 preset and question pairs its scores match scikit-learn’s TfidfVectorizer to within 2e-16:

Descriptions Golden set, of 20 Sent to the wrong tool Held out, of 5 Tokens per call
Names only: “Search tool.” for both 4 0 0 6
Vague: “Information related to Larkspur Cloud plans and pricing.” 5 0 0 20
Specific: the topics each tool covers 15 1 2 84
Tuned: Specific plus words taken from the golden questions 19 0 4 133

Table 3: Routing scores for the four description presets. Tokens are the lab’s estimate of four characters per token.

  • Names only gets right only the four questions that needed no tool. The other sixteen are silent skips.
  • Vague catches When are monthly plans billed? on “plans” and nothing else. Can I export my data after I cancel my plan? misses because TF-IDF treats “plan” and “plans” as different words.
  • Specific gets three handbook questions right for a thin reason: goes down, reboot and size match nothing, and the word “server” carries them.

Planted failures in the Specific preset

We reran the lab’s router against scikit-learn to see why Specific misses its five golden questions:

Question Routed to Why
How long does a refund take? no tool the description says “refunds”; the question says “refund”
Is there a major AWS outage right now? no tool the web description says “other cloud providers” and never names AWS or outages
What is the latest stable PostgreSQL release? no tool the description says “releases” and never names PostgreSQL
Who won the Champions League final this year? no tool “sports” is in the web description; no word of the question is
What does Hetzner charge for a 4 GB server? handbook_search “server” appears only in the handbook description

Table 4: Specific’s five golden misses, read from the router’s scores.

The first four are vocabulary misses: the description covers the topic in words the question does not use, and a model would catch most of them. The last is a scope gap: neither description says which tool owns other providers’ prices. The router guessed, and a model would have to guess too. It is the worst miss in the set, because a competitor’s price gets answered from Larkspur’s handbook. Adding “refund” to the handbook description takes Specific to 16 of 20 and leaves the Hetzner question wrong. More Larkspur words cannot draw a boundary neither description states.

Planted failure: the overfitted description

Tuned copies the golden questions’ own words (PostgreSQL, AWS, Hetzner, Docker, Ubuntu) into the descriptions and fixes every golden row but one. On the held-out five, What is the newest Node.js version? still gets no tool. We call this an overfitted description: it scores well on the questions it was written against and worse on the next one a user types, like a retriever tuned on its own test set.

From the stand-in to a real model

Descriptions also cost tokens, because each one is sent with every model call. Tuned carries 133 to Specific’s 84, which is 49 more per call. A handbook question takes two calls (Table 1), or 98 more tokens per question. A model forgives vocabulary misses but fails on a scope gap the same way the stand-in does. A description that earns its tokens states four things:

  • What it searches, and whose data: “the Larkspur Cloud handbook” against “the public web”.
  • The topics, in the words users type: refunds, cancelling, data export, outages, server sizing.
  • Where it stops: Larkspur’s own prices and policies belong to handbook_search; other providers’ prices belong to web_search.
  • What it returns: handbook passages as plain text, so the model knows what comes back and that it should quote it.

Treat the descriptions as a retrieval setting. Keep a routing golden set of questions with the tool each should use, a held-out set, and the misses from production traces added over time.

Key Takeaways

  • Retrieval as a tool lets the model skip it for small talk, rewrite the query and search again. The cost is a silent skip: a model that answers from memory has nothing to cite.
  • The default retriever tool drops each chunk’s source. Print the source into the chunk text, or keep the Documents beside the text, before you ask the model to cite.
  • Write each description to say what it searches, its topics in users’ words, where it stops and what it returns. Score every change on a routing golden set and on held-out questions, because a description copied from the golden set overfits.

Check yourself

1. What does letting the model decide when to retrieve gain over a fixed classifier, and what does it give up?

It handles small talk with no retrieval, rewrites a follow-up into a better query, and searches again when the first chunks miss. It gives up a decision you control in code. A model that answers a refund question without calling handbook_search makes a silent skip: the answer comes from its training data, with nothing to cite.

2. With the Specific descriptions, the question about Hetzner's price for a 4 GB server goes to the handbook tool. Why, and what fixes it?

“server” appears only in the handbook description, and neither description says which tool owns other providers’ prices, so the router guessed. That is a scope gap, and adding more Larkspur words does not close it. State where each tool stops: Larkspur’s own prices and policies belong to handbook_search, other providers’ prices to web_search.

3. The Tuned descriptions route 19 of 20 golden questions because they copy words from those questions. What else must you check before trusting them?

The held-out questions, where they reach 4 of 5 and still give the Node.js question no tool, which marks an overfitted description. Check the cost too: 133 tokens on every model call against 84. Score each description change against the golden set and the held-out set, and add misses from production traces.

Managed RAG

Managed RAG is retrieval run as a service. You upload documents to a datastore, create an agent over it, and send questions to one endpoint that parses, chunks, indexes, retrieves, reranks and generates. The notebook does this with Contextual AI’s Python SDK over four PDFs: two quarterly revenue slides and two spurious-correlation reports.

Planted case: two versions of one policy

After every policy change the Larkspur index can hold two versions of the same rule. We call the failure from the opening the stale-policy win: the archived version outranks the current one, and the answer quotes it with full confidence.

An instruction-following reranker takes a plain-language instruction alongside the query and orders passages by both. The notebook plants a conflict about enterprise GPU pricing, with the instruction Prioritize internal sales documents over market analysis reports. More recent documents should be weighted higher. Enterprise portal content supersedes distributor communications. It passes three passages, each with its date and source as metadata:

Passage Metadata Role in the test
Bulk orders run on a $2,899 baseline Enterprise sales portal, January 15, 2025, internal the current internal figure
Bulk orders cost $3,100 to $3,300 per unit Analyst report, November 30, 2023 the older, external figure
The GPU needs 450W and 20% cooling overhead Enterprise sales portal, January 25, 2025, internal recent and internal, but off topic

Table 2: The notebook’s planted conflict. The first two answer the question and disagree.

The third row makes the test honest. It matches the instruction on date and source. A reranker that only read the metadata would rank it first. The notebook ranks the passages with the instruction and without it, for comparing the two orders. For Larkspur the instruction would read Prefer the current handbook over archived handbook versions and community forum posts, with each chunk’s date and source passed as metadata.

Planted case: a question the handbook cannot answer

The grounded language model answers from the passages it is handed. It has a flag, avoid_commentary, that decides whether the answer may add context beyond those passages. The notebook runs three cases:

Question Passages given Flag What to check
Solar in rural Africa and its economic impact renewable-energy reports off which sentences go beyond the passages
The same question the same reports on that the extra commentary is gone
Latest quantum computing hardware the same renewable-energy reports off that the model says it has no relevant information

Table 3: The notebook’s three generation runs.

For a support agent the third row is the one to test first. A question the handbook does not answer should get “I don’t have that information”, never a plausible policy: an answer that sounds like Larkspur’s rules and is not in the handbook. The flag narrows the answer to the evidence. It does not prove the answer is correct, so read the retrieved passages beside it.

Unit tests for answers

LMUnit replaces a single quality score with natural-language tests. The notebook writes six, one per property (numerical accuracy, correlation versus causation, multi-document synthesis, stated limitations, evidence, no unnecessary information). It scores three sample answers against all six and plots each answer’s scores on a polar chart. One worked case asks Does the response avoid unnecessary information? of an answer that lists four quarters when the question asked for one. Larkspur would write its own tests, such as Does the answer give the refund time from the current handbook?

Keeping the tool contract

A managed platform fits behind the tool interface from lesson 31.1. The outer LangGraph agent keeps a handbook_search tool with the same name, description and one query argument. Only its body changes, from calling your own retriever to calling the platform agent:

Figure 3: The outer agent still decides when to search. The platform decides how.

Because the interface is fixed, the routing golden set from lesson 31.1 still applies unchanged. Swapping the platform in or out is a change to one tool’s implementation.

Pitfall: a grounded answer inside an ungrounded loop. The platform refuses when its datastore has no answer, but the outer agent can still skip the tool and answer from memory. The silent skip from lesson 31.1 does not go away; measure it on the routing golden set.

Key Takeaways

  • A managed RAG platform runs parsing, chunking, reranking and grounded generation behind one endpoint. Wrap its agent in the same tool, and your own agent still decides when to search.
  • You run fewer parts but control fewer settings, and your documents leave your infrastructure. Check data residency, access control on each datastore and how a deleted document leaves the index.

Check yourself

1. What do you trade when you replace your own retrieval pipeline with a managed RAG platform?

You run fewer parts, since parsing, chunking, reranking and grounded generation come configured. You control fewer settings, such as chunk size, the embedding model and k, and your documents leave your infrastructure, so check residency, access control and deletion. You measure it the same way, by running the M10 golden set through it.

2. After a Larkspur policy change, the index holds an old and a new version of the same rule. How would the instruction-following reranker handle it, and what planted passage keeps the test honest?

Pass each passage’s date and source as metadata with an instruction such as “Prefer the current handbook over archived handbook versions and community forum posts”, and the reranker orders passages by relevance and by that instruction. Include a recent, current-source passage that does not answer the question, as the notebook does with the GPU cooling spec. A reranker that reads only the metadata would rank it first.

3. Larkspur wraps the platform agent as its handbook_search tool, and a customer still gets a refund policy from the model's memory. Which part failed?

The outer agent’s routing, not the platform. The platform refuses when its datastore lacks an answer, but it only runs when the outer agent calls the tool. The model skipped the call, a silent skip from lesson 31.1, so the fix is in the tool description and the routing golden set.

The user saves new pages and asks at once the question reaches no agent, or the agent for the previous pages confirm in the chat only after indexing finishes
Each user indexes different pages a fixed description says nothing about this session’s index build the description from the session’s settings
A reviewer checks an answer the tool calls behind it are hidden show each tool call as a step in the chat

Table 3: Three planted cases and the guard for each.

The premature question. The index is built when settings are saved, not offline as in M10. A question sent before the first confirmation finds no agent. The scaffold sets index = None at module level but never agent. Its if agent: check raises a NameError instead of staying quiet until you add agent = None. On a later save, the question reaches the agent still holding the previous pages. That case is the dangerous one: the answer looks normal and comes from the wrong pages.

The generic description. The tool takes a name and a description through its metadata. When each user indexes different pages, write the description from their settings (“Wikipedia articles on London, Barcelona and Paris”). Then the agent knows what this session’s index holds. A fixed “Wikipedia pages” tells it nothing about which ones.

Hidden steps. Chainlit can show the agent’s intermediate steps in the chat. For Larkspur’s support chat, a visible step per handbook_search call lets a support lead check the answer against what was retrieved.

Design choices worth copying

Choice Why
Index on settings save, confirm when done The user knows when questions can be answered; a confirmation sent early would hide the premature question
Index and agent per session One process serves every user: globals leak one user’s data into another’s answers
Description built from settings The agent’s routing reads the description, as lesson 31.1 measured
Tool calls shown as steps A reviewer can compare the answer with its evidence, as lesson 31.2’s retrieval contents allow

The Larkspur support chat

The same three events host the Larkspur agent from lesson 31.1:

  1. On chat open, build the agent for this session with handbook_search and web_search, and store it in the session.
  2. On each message, read the session’s agent, run it, and send the reply.
  3. Show each handbook_search call as a step. A support lead then sees the chunks behind every refund answer.

The handbook index is built once, offline, as in M10. The premature question disappears. The shared-agent risk does not: the conversation history still belongs to one session.

Limits of this evidence

  • The scaffolds are incomplete on purpose. Both files have gaps to fill. The exercise has no expected output to quote. Test it by behaviour: open two sessions with different pages and check that each answers from its own.
  • Version drift in the scaffold. Its configuration file was generated by Chainlit 0.7.0 and switches visible steps on with hide_cot = false. Chainlit 2.x, which the course installs (2.12.0), reads .chainlit/config.toml and uses cot ("full", "tool_call" or "hidden", default "full") instead. The old setting does nothing. The folder’s README also notes that the legacy OpenAI program package does not support llama-index-core 0.14; its function-calling or text-completion programs replace it.
  • What it needs to run. An OpenAI API key and the course’s llamaindex dependency group. There is no notebook: the app runs with Chainlit from its own folder.

Key Takeaways

  • A chat UI calls one function per event. Build the index and agent when settings are saved, confirm only once indexing finishes, and run the agent on each message.
  • Keep the index and agent per session, not in module globals, because one Python process serves every connected user.
  • Build each session’s tool description from its settings so the agent knows what its index holds, and show tool calls as steps so a reviewer can check answers against retrieval.

Check yourself

1. Why does keeping the index and agent in module globals break the Chainlit app as soon as two people use it?

Chainlit serves every connected user from one Python process, so the second user to save settings replaces the first user’s index and agent. The first user’s next answer comes from the second user’s pages. Store both in the user session, which keeps one value per connection.

2. A user indexes the Wikipedia pages on London, Barcelona and Paris. What tool description should that session's agent get?

One built from the user’s settings, such as “Wikipedia articles on London, Barcelona and Paris”, passed in the tool’s metadata. A fixed description such as “Wikipedia pages” tells the agent nothing about what this session’s index holds, and the description is all the agent reads when it decides to call the tool.

3. A user who had indexed London saves Lagos instead and asks about Lagos straight away, and the answer comes from the London page. What went wrong, and what guards against it?

The question arrived before the new index was built, so it reached the agent that still held the previous pages. Build the new index and agent in the settings event, store them in the session, and send the confirmation only after both are ready, so the user knows when questions about the new pages can be answered.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur adds a web_search tool to the support agent. A week later a customer asks “Can I get a refund on my annual plan?” and the agent quotes another provider’s refund policy. How do you find out what happened?

What a strong answer covers:

  • Opens the trace for that conversation and reads the model’s tool_calls: which tool it called, with which query, and what came back
  • If it called web_search: a routing failure. Compares the two descriptions for overlap (“refund”, “plans”, “pricing” in both, or in neither)
  • If it called handbook_search and still answered wrongly: a retrieval or generation failure, debugged as in M10 by printing the returned chunks
  • Rewrites the descriptions to state the boundary (“Larkspur’s own policies” against “other providers”), adds the question to a routing golden set, and re-runs it

2. The Larkspur support bot today always retrieves before it answers. A teammate wants to replace it with an agent that calls handbook_search only when it decides to. What do you gain, what do you risk, and how do you decide?

What a strong answer covers:

  • Gains: no retrieval for small talk or arithmetic, a query the model rewrites from the conversation, and a second call when the first chunks miss
  • Risks: the model answers a policy question from memory without calling the tool, or loops on tool calls and adds latency
  • Counts the cost per question from the graph: two model calls either way for a handbook question, more when the agent loops
  • Decides on the golden set: answer quality, the share of handbook questions that triggered the tool, and p95 latency, against the always-retrieve baseline

3. The agent is live. How do you monitor tool selection in production, before customers notice a wrong answer?

What a strong answer covers:

  • Logs every tool call with its name, the model-written query, the number of chunks returned and their top score
  • Tracks per-tool call rates and the share of answers given with no tool call; a jump after a prompt, model or description change is the alert
  • Samples conversations for an LLM judge or a reviewer to label the right tool, and grows the routing golden set from the misses
  • Re-runs the routing golden set and a held-out set on every change to a description, a tool list or the model

4. A customer asks “Is a 4 GB server cheaper at Larkspur or at Hetzner?” What should the agent do, and how can it go wrong?

What a strong answer covers:

  • The question needs both tools: handbook_search for Larkspur’s price and web_search for the competitor’s, then a comparison
  • Failure modes: only one tool is called and the other price is filled in from memory, or a web result about Larkspur outranks the handbook
  • Guards: descriptions that say which tool owns Larkspur’s own facts, answers that cite each figure’s source, and a refusal when one side is missing
  • Adds multi-tool questions to the routing golden set, scored on whether both tools were called

5. The platform team proposes replacing the hand-built handbook retriever with a managed RAG platform. What do you evaluate before you agree?

What a strong answer covers:

  • Runs the same golden set through both and compares answer quality, refusals on out-of-scope questions, and latency, as M10 does for any change
  • Checks what the platform does with the handbook’s tables and policy versions: its parser output, and whether reranker instructions can prefer the current policy
  • Reviews data residency, access control on the datastore, per-query cost, and what leaving the platform would take
  • Keeps the agent’s tool interface fixed (handbook_search(query)), so the swap is one tool’s implementation and the routing golden set still applies

Key Takeaways

  • An agent retrieves only when the model calls the tool. Measure how often it does on questions that need the handbook, and how often it does not.
  • Write each tool description for the model: what it searches, the topics in users’ words, and where it stops and the neighbouring tool starts. Keep it short, because it is sent on every call.
  • Tune descriptions against a routing golden set and score them on held-out questions too, as you would any retrieval setting.
  • A managed platform or a chat UI changes what sits behind or in front of the tool, not the loop. Keep the tool’s name, description and arguments stable across both.
