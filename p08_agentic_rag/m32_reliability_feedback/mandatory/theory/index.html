M32 Reliability, Feedback Loops & Diversity

A RAG answer can read well and still be wrong in three separate ways. It can rest on a chunk that has nothing to do with the question, it can state something no chunk says, and it can keep failing after users have said so. This module adds a check for each: graders before and after generation, quoted sources the user can verify, a feedback loop that re-weights retrieval, and a selector that stops duplicate chunks from crowding out the evidence. The M32 notebooks build on four ideas: catching unsupported answers, proving each quote, learning from user signals, and choosing diverse chunks.

TL;DR

  • Lesson 32.1 wraps generation in two LLM graders. One answers yes or no for each retrieved chunk before generation, the other for whether the answer is grounded in the kept chunks. Grading removes noise but cannot add a chunk retrieval missed, and with source highlighting the three checks add 6 model calls per answer at k = 4.
  • Source highlighting asks the model for verbatim quotes of the chunks it used. The parser checks only their shape, so find every quote in its chunk in code and fall back to citing the whole chunk when it is missing.
  • The feedback re-ranker in lesson 32.2 multiplies each chunk’s score by its average rating over 3, which keeps it between 0.333 and 1.667. In the lab, 100 rated answers lift mean recall@2 on the golden set from 0.50 to 0.70, the order stops changing after event 8, and 40 of the 41 wrong answers go to two questions whose evidence the retriever never returns.
  • A rating on the whole answer lands on every chunk in it. In the lab an unrelated chunk rides a good answer up to 1.667, and an evidence chunk is pushed down to 0.333 next to the distractor it was served with.
  • With the handbook stored five times, plain top-3 for the export question returns the export chunk three times. Dartboard selection returns export, retention, export at its default oversampling of 3, and export, retention, cancel at 4, once the pool holds three distinct chunks.

Mental model

The checks in the top row act on one answer and can only remove: a grader drops a chunk or rejects an answer, and neither can add the chunk that was missing. The loop in the bottom row acts across many answers and can only reorder the chunks retrieval already returns. A missing chunk is a retrieval problem in both rows, and the fixes for it sit in M13 to M18.

M31 made the retriever a tool the agent calls when it decides to. This module asks what happens after the call returns: whether the chunks are on topic, whether the answer stays inside them, and whether the user can see where each claim came from.

A Larkspur customer asks How long does a refund take? The answer comes back fluent and confident, with a number of business days that differs from the handbook’s 5 to 10. That duration sits in the refund-timing chunk, and that chunk was never retrieved. The model found a related passage about refunds, saw no duration in it, and filled the gap from memory. Nothing in a plain RAG pipeline notices.

This lesson adds three checks around generation, each catching a different failure:

Figure 1: The reliable RAG pipeline. A grader filters chunks before generation, a second grader checks the answer after it, and highlighting ties each claim to a quote.

Relevance grading

A relevance grader is a small model call that reads one retrieved chunk together with the question and returns a structured verdict, yes or no. Chunks graded no are dropped; only the kept ones reach the generator.

The notebook indexes five posts on agentic design patterns from DeepLearning.AI’s The Batch (500-token chunks, no overlap, OpenAI’s text-embedding-3-small, Chroma) and retrieves 4 chunks per question. Every grader runs Llama 3.1 8B on Groq at temperature 0 with structured output, which makes the verdict a field the code can branch on.

The grading prompt sets a low bar on purpose: a chunk counts as relevant if it shares keywords or meaning with the question, because “The goal is to filter out erroneous retrievals.” A strict grader would drop borderline chunks that still help.

What grading can and cannot fix

Run the refund question against the M10 TF-IDF index of the Larkspur handbook. Only two chunks score above zero:

Rank Chunk Why it was retrieved What the grader should do
1 refund-window (0.227) Shares “refund” with the question Keep: it is about refunds
2 reboot (0.194) Both texts contain “does” Drop: it is about servers
none refund-timing Never retrieved Nothing: it never reaches the grader

Table 1: The refund question on the M10 index, and what a relevance grader sees.

Dropping reboot removes a distractor. But the chunk that holds the answer is absent, and no grader can add it. We call this the candidate ceiling: every check downstream of retrieval works on the candidates retrieval returned, and recall stays where retrieval left it. Fixing the missing chunk is retrieval work (M13 to M18).

Pitfall: the empty-context answer. The notebook passes the kept chunks to generation without checking whether any survived. If all four are graded no, the model gets no documents and answers anyway, from memory. Branch on the empty case: rewrite the query and retry a bounded number of times (M28), fall back to another source (M29), or say the handbook does not cover the question.

The grader cleans the input. The next check looks at the output.

Hallucination detection

Hallucination detection here means a second grader that reads the kept chunks and the finished answer, and returns yes when the answer is “grounded in / supported by the set of facts”. A no means the answer says something the chunks do not.

Three limits of one verdict

Three properties decide how far to trust it:

  • It checks support, not usefulness. The question is not in the grader’s input, and a grounded answer can still miss the question. Self-RAG (M29) adds a check for that.
  • It returns one verdict for the whole answer. One unsupported sentence fails the answer, and the grader does not say which one. Per-claim checks split the answer into statements and verify each against a cited chunk, giving the location as well as the verdict.
  • It is a model judgment. The same 8B model writes and grades here, and the two can share blind spots. Before relying on it, label a sample of answers by hand and measure how often the grader agrees, for yes and no separately, because a lenient grader fails in one direction.

What a no leads to

The notebook prints the verdict and stops. In production a no has to go somewhere: regenerate once with the stricter prompt, then retry retrieval with a rewritten query, then answer that the handbook does not say and offer a person. Cap the retries, because each one is another generation call and another grading call on top of these:

Those calls add latency as well as cost. The four chunk grades can run in parallel; the rest run one after another. Put the graders on the same dashboard as the answer time. Once an answer passes, the last check shows the user which words it rests on.

Source highlighting

Source highlighting asks the model which exact passages of the kept chunks the answer used, letting the reader check the answer against the handbook at a glance.

The notebook asks for the result as four parallel lists, one entry per highlighted passage:

Field What it holds

The prompt asks for segments that are “verbatim snippets from the documents, ensuring a word-for-word match”, and tells the model to leave out documents the answer did not use. For Can I export my data after I cancel my plan?, a correct highlight returns two exact sentences:

The parser checks shape, not truth

A structured-output parser checks that the response has the four lists with strings in them. It does not check that a segment appears in its chunk. A model can paraphrase, merge two sentences or quote a chunk it was never given, and the output still parses.

Check every segment in your own code with an exact substring search of the cited chunk. A hit returns the character offset where the quote starts, which is what the interface needs to draw the highlight. A miss returns nothing:

Segment checked against the export chunk Result
“Export your data at any time from Settings, then Data.” Found at offset 0
“You can always export in Settings.” (a paraphrase) Not found

Table 6: An exact quote and a paraphrase, checked against the source text.

This checks quotation, not whether the sentence answers the customer. That judgment stays with the hallucination grader.

A rising miss rate in that log means the highlighting prompt or the model has drifted. A chunk that is retrieved often and never highlighted is a candidate for the grader to drop or for retrieval to stop returning.

Limits of this evidence

  • Two corpora. The notebook runs on five blog posts with dense embeddings; the traces on this page use the Larkspur handbook with the M10 TF-IDF index. The retrieval scores come from that index, not from the notebook’s.
  • Illustrative answers. The answers in Table 2 and the walkthrough are written to show each verdict. No grader agreement rate was measured here; measure your own before trusting a no.
  • Call counts, not latency. Table 3 counts calls. Waiting time depends on which calls run in parallel and on token counts.

Key Takeaways

  • Grade each retrieved chunk before generation, at one call per chunk. Grading drops noise but cannot add a chunk retrieval missed (the candidate ceiling): branch on an empty kept set instead of answering anyway.
  • The hallucination grader checks support, not usefulness, and gives one verdict for the whole answer. Measure its agreement with hand labels, prompt the generator to answer only from the documents, and send a no to a capped retry or an abstention.
  • A parser checks only the shape of a highlight. Find every segment in its cited chunk, check the ids and list lengths, and fall back to citing the whole chunk when a check fails.

Check yourself

1. The relevance grader drops off-topic chunks before generation. Why can it not raise recall?

It only sees the chunks retrieval returned. On the refund question it should drop reboot, which ranked second only because both texts contain “does”, but it cannot add refund-timing, which was never retrieved. Grading removes noise and leaves recall where retrieval put it.

2. Only the refund-window chunk survives grading, and the answer states how many days a refund takes. What should the hallucination grader return, and what prevents such answers?

It should return no: that chunk states the 30-day window and nothing about how long a refund takes, so any duration is unsupported. The notebook’s prompt, “Answer the question based upon your knowledge”, invites the remembered number. A prompt that says to answer only from the documents, and to say when they do not cover the question, stops most of these answers before they are written.

3. A highlighted segment parses correctly but is not found in the chunk it cites. What should the app do?

The parser checks only the shape, so the model may have paraphrased or merged sentences. Fall back to citing the whole chunk and log the miss, because a rising miss rate means the highlighting prompt or model has drifted. Also compare the list lengths before pairing them, since pairing stops at the shorter list and silently drops a row.

Twenty askings later the answer is still incomplete, because the chunk with the answer, refund-timing, was never among the candidates the ratings could touch. The feedback re-ranker

The notebook builds a question-answering chain with gpt-4o over a climate-change PDF and stores one feedback record per answer, appended to a log file as a line of JSON:

Field What it holds
query The question asked
response The answer given
relevance The user’s 1 to 5 rating of how relevant the answer was
quality The user’s 1 to 5 rating of its quality
comments Free text, often empty

Table 1: One feedback record.

On the next query a feedback re-ranker re-weights the retrieved chunks. For each chunk and each stored record, it asks gpt-4o whether that record is relevant to the current query and that chunk. It averages the relevance of the records judged relevant, multiplies the chunk’s score by that average divided by 3 (3 is the neutral middle of the scale), and sorts by the new score:

Figure 1: The feedback loop. Ratings re-weight the next retrieval’s candidates; they never change which candidates come back.

Four properties of the rule

The arithmetic is short:

Average rating Multiplier Chunk score
1 (every rating a thumbs-down) 1/3 0.333
3 (neutral) 1 1.000
5 (every rating a thumbs-up) 5/3 1.667

Table 2: The multiplier at the ends and the middle of the scale.

  • Feedback sets the order on its own. Every chunk starts at a score of 1.0, and after the multiplication ratings alone decide the order. Similarity only breaks ties, because a stable sort keeps the retriever’s order for equal scores.
  • The multiplier is bounded. It uses the average, and a chunk sits between 0.333 and 1.667. The first rating moves a chunk as far as it will go; later ratings only move the average.
  • It reorders the candidates and nothing else. The retriever returns 4 chunks by default, and a chunk outside those 4 never receives a rating: the candidate ceiling from lesson 32.1 again.
  • It costs one model call per pair. Every retrieved chunk is checked against every stored record: 4 chunks and 1,000 records make 4,000 gpt-4o calls for one query.

Implicit vs explicit feedback

Explicit feedback is a judgment the user states: a thumbs-up, a star rating, the 1 to 5 relevance and quality fields above. Implicit feedback is inferred from what the user does next. The two differ on every axis that matters:

Explicit Implicit
Examples Thumbs up or down, a 1 to 5 rating, a comment Opening a cited source, copying the answer, asking the same question again in other words, opening a support ticket
Meaning Clear: the user said it Inferred: a rephrased question probably means the answer missed
Volume Only from users who choose to rate From every session
What it rates The whole answer Often one source, such as the one the user opened
Bias Raters choose themselves and may not be typical users Users click what is shown first, and top-ranked chunks collect more signal

Table 5: Explicit and implicit feedback compared.

Re-ranking leaves the index alone. The notebook’s second half changes the index itself.

Folding good answers into the index

The notebook’s second use of feedback is a periodic job, run “daily or weekly”. It keeps the records rated 4 or more on both relevance and quality, joins each question and answer into one text, appends that text to the original document, and re-encodes everything (1,000-character chunks, 200 overlap) into a new vector store.

Figure 4: The fold-back job. Only answers that were already good enter the new index.

This adds chunks worded the way users ask, which helps questions phrased like past ones. It has three limits:

  • Only answers that were already good get in. In the lab, the refund and outage questions never earn a thumbs-up, and nothing about them would be added. The questions that most need new text get none.
  • Past answers become retrievable facts. When Larkspur changes its refund rule, the stored answers still quote the old one, and they match refund questions better than the handbook because they were written as answers to them. We call this stale-answer echo. Tag each added chunk with its date and the handbook chunks it came from, drop it when those change, and rank feedback chunks below primary documents.
  • It rebuilds the whole index. Every run re-embeds the full corpus plus the feedback text. Incremental upserts (M14) avoid that.

Limits of this evidence

  • A scripted user. The lab’s user rates 5 exactly when the answer holds every evidence chunk. Real users rate mood, length and speed too, and many never rate.
  • A rule in place of gpt-4o. The lab decides which records count for a chunk with a fixed rule. The notebook’s model call can match records across differently worded questions, and can also miss.
  • Five questions, twelve chunks. The totals in Table 3 come from one small handbook and TF-IDF retrieval; the notebook itself prints no ranking figures.

Key Takeaways

  • The feedback re-ranker multiplies each chunk’s score by its average rating over 3: a chunk stays between 0.333 and 1.667 and ratings alone set the order. It costs one model call per chunk and stored record.
  • Feedback only reorders the candidates retrieval returns. In the lab, mean recall@2 rose from 0.50 to 0.70, but 40 of the 41 wrong answers came from chunks that were never candidates.
  • Combine implicit and explicit feedback, and rate sources rather than whole answers where you can, so credit does not ride along to the chunk beside the evidence. Each thumbs-down is a golden-set candidate.

Lesson 32.2 showed that feedback can only reorder the candidates retrieval returns. This lesson stays inside that limit: a better way to choose among the candidates, when many of them say the same thing.

Larkspur ingests its handbook from three places: the help centre, the PDF export and the internal wiki. Every rule is now stored several times. A customer asks Can I export my data after I cancel my plan? The answer needs two chunks, export (how to export) and retention (how long data is kept after cancelling). Plain top-3 retrieval returns export, export, export, and the answer never mentions the 30-day deadline. The runs below store each chunk five times, which makes the effect easy to see.

Diversity-aware selection

Top-k scores each chunk against the query on its own and keeps the best k. Copies of one passage score identically, and whichever passage scores best takes every slot. We call this duplicate crowding. The notebook creates it on purpose: it loads its climate-change PDF five times over, splits it into 1,000-character chunks with 200 overlap, and shows that the top 3 results for What is the main cause of climate change? are repetitions of one chunk.

The fix is to score the set rather than each chunk. Diversity-aware selection picks chunks so that the set, taken together, covers the query well: a chunk adds value only when it brings something the chosen ones do not.

The dartboard picture

The notebook’s method comes from Better RAG using Relevant Information Gain, the dartboard method. Picture the query as the centre of a dartboard and darts thrown around it, landing more often near the centre. A set of chunks scores by how close its nearest member lies to where each dart lands.

A second copy of a chunk already in the set lies exactly where the first one does. It brings no landing place any closer and adds nothing. A chunk that covers ground nearby, close to the query but away from the chosen chunks, adds the most.

The greedy rule

Finding the best set exactly is expensive. The method builds it one chunk at a time from a candidate pool of num_results × oversampling_factor nearest chunks (the factor is 3 by default):

  1. Turn distances (1 minus cosine similarity) into log probabilities with a normal curve of width SIGMA = 0.1, for query to chunk and for chunk to chunk.
  2. Pick the chunk most probable under the query.
  3. Treat every candidate as a place a dart can land, weighted by how close it is to the query (RELEVANCE_WEIGHT). For each remaining candidate, measure how close the set would come to each landing place if that candidate joined (DIVERSITY_WEIGHT), and sum over the landing places. Both weights are 1.0.
  4. Add the highest scorer and repeat until num_results are picked.

Figure 1: Greedy dartboard selection. Every pick after the first is scored on the coverage it adds to the set so far.

SIGMA sets how quickly closeness stops counting: a small width means only near neighbours of a landing place matter, and two chunks a little apart already count as covering different ground.

The same run at four pool sizes shows both the gain and its limit:

Oversampling factor Pool Distinct chunks in pool Plain top-3 Dartboard top-3
1 3 1 export × 3 export, export, export
2 6 2 export × 3 export, retention, export
3 (default) 9 2 export × 3 export, retention, export
4 12 3 export × 3 export, retention, cancel

Table 1: Dartboard against plain top-3 on the handbook stored five times, export question.

Plain top-3 has recall 0.50 on this question at every pool size. Dartboard reaches 1.00 once the pool holds retention, from an oversampling factor of 2. At the default of 3 its third pick is still a copy of export, because a pool of 9 drawn from five copies of each chunk holds only two distinct chunks.

That is the pool ceiling, the candidate ceiling of lessons 32.1 and 32.2 in a new form: a selector can only choose among the candidates it is given. The arithmetic for sizing the pool is direct when copies rank side by side:

Copies per chunk Distinct chunks wanted Smallest pool that holds them
5 2 6
5 3 11
3 3 7

Table 2: Pool size needed when every chunk has the same number of copies, (copies × (wanted − 1)) + 1.

The default pool of 9 sits between the first two rows, which is exactly why Table 1 shows two distinct picks at factor 3 and three at factor 4 (pool 12). Real duplication is uneven. The reliable fix is to remove the copies before retrieval and keep oversampling for the overlap that remains.

Dartboard or MMR

Dartboard and MMR, maximal marginal relevance (lesson 16.4), solve the same problem the same greedy way and differ in the score each candidate gets.

MMR scores a candidate by its similarity to the query, minus a penalty for its similarity to the closest chunk already chosen. One weight, λ, sets the balance:

Figure 2: The MMR score. A copy of a chosen chunk has similarity 1 to it and takes the full penalty.

Dartboard adds instead of subtracting: the log probability of covering each landing place, summed over the pool, with the query’s pull counted in:

Figure 3: The dartboard score. A copy changes no landing place’s closeness and adds nothing over the set without it.

MMR Dartboard
Score for the next pick Relevance minus a redundancy penalty Log probability of covering the landing places
Balance control One linear weight, λ SIGMA, plus a relevance weight and a diversity weight
Usually run on Embedding similarities Any distance: dense, hybrid or cross-encoder scores

Table 3: Two greedy selectors compared.

Because Dartboard needs only distances, the notebook’s notes point out that it works the same on dense, hybrid or cross-encoder scores. Neither selector replaces deduplication: a content hash at indexing time catches exact copies cheaply, and every later step then works on fewer, distinct chunks.

Limits of this evidence

  • The first score is a placeholder. The notebook records the first pick with a fixed score of 1.0, not a computed one. It cannot be compared with the scores after it.
  • The last example call fails. It passes the result count under the name k, while the function names that parameter num_results. Python raises a type error until the name is corrected.
  • One question, one corpus. Table 1 is one question on a twelve-chunk handbook with uniform copies and TF-IDF vectors. Uneven duplication, near-duplicates in other words and dense embeddings were not tested.

Key Takeaways

  • Top-k fills every slot with copies of the best match when the corpus holds duplicates. Dartboard selection scores a set by how close its nearest member lies to each landing place, and a copy adds nothing.
  • The selector only chooses among its num_results × oversampling_factor candidates. With five copies per chunk the default pool of 9 holds two distinct chunks: enlarge the pool past the copy count or deduplicate at indexing.
  • Dartboard and MMR both select greedily and differ in the score. MMR subtracts a linear redundancy penalty, while Dartboard adds log probabilities and needs only distances, which lets it run on dense, hybrid or cross-encoder scores.

Check yourself

1. Why does a second copy of a chunk already in the set add nothing to the dartboard score?

A set scores by how close its nearest member lies to where the darts land. The copy lies exactly where the first one does, so it brings no landing place any closer. A chunk that covers ground nearby adds the most.

2. With the Larkspur chunks stored five times and the default oversampling factor of 3, what does dartboard return for the export question, and why?

export, retention, export. Recall reaches 1.00 against 0.50 for plain top-3, but the pool of 9 drawn from five copies of each chunk holds only two distinct chunks, so the third pick is a copy. At a factor of 4 the pool holds three and the picks become export, retention, cancel.

3. Your retriever scores with a cross-encoder rather than embeddings. Can you still use dartboard selection, and how does it differ from MMR?

Yes: the method needs only distances, so it works the same on dense, hybrid or cross-encoder scores. Both pick greedily; MMR subtracts a redundancy penalty with a linear λ, while Dartboard adds log probabilities, with SIGMA setting how quickly closeness stops counting.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. A Larkspur customer asks how long a refund takes. The assistant answers with a number of business days that differs from the handbook, and the hallucination grader marked the answer grounded. How do you work out what failed?

What a strong answer covers:

  • Pulls the trace: the retrieved chunks, the grader’s verdict on each, the kept set, the answer and the hallucination grader’s input
  • Checks retrieval first: on the M10 TF-IDF index refund-timing scores 0 for this question, so the kept set may hold only refund-window, which gives no duration at all
  • Checks the generation prompt: the lesson’s example tells the model to answer “based upon your knowledge”, which invites a remembered number; a grounded system says “only from the documents”
  • Treats the grader as a model with an error rate: labels a sample of answers by hand, measures how often the grader agrees, and adds this case to that set

2. Product wants a thumbs-up and thumbs-down on every answer, feeding a re-ranker like the one in lesson 32.2. What do you tell them it will and will not fix?

What a strong answer covers:

  • It reorders the candidates retrieval returns, so it fixes questions whose evidence is retrieved but ranked low (the lab’s credit question goes from recall@2 0.00 to 1.00 after one thumbs-down)
  • It cannot reach a chunk retrieval never returns: in the lab 40 of the 41 wrong answers in 100 events go to the refund and outage questions, and no rating changes that
  • A rating on the answer credits every chunk in it, so unrelated chunks ride along on good answers; per-source signals or a reranker trained on graded pairs are sharper
  • Ships it with a holdout: re-runs the golden set before and after, and watches per-question recall so one popular question cannot hide a regression elsewhere

3. The relevance grader and the hallucination grader have been live for a month. How do you know they are working, and what do you alert on?

What a strong answer covers:

  • Logs every verdict with the question, chunk ids and answer, so rates can be tracked per question type and per document
  • Watches the share of questions where every chunk is graded irrelevant, and the share of answers graded not grounded; a jump after an index or prompt change points at the change
  • Samples graded traffic for human labels each week and tracks the graders’ agreement with them, separately for “yes” and “no”, since a lenient grader fails in one direction
  • Counts the cost: five grader calls per answer (one per chunk at k = 4, plus one grounding call) and a sixth for highlighting, and the latency they add belongs on the same dashboard

4. A weekly job has been folding highly rated question and answer pairs into the index. Larkspur then changes its refund rule. What goes wrong, and how do you guard against it?

What a strong answer covers:

  • Old answers that quote the old rule are now chunks in the index, and they match refund questions better than the handbook does because they were written as answers to those questions
  • The new handbook chunk competes with every highly rated answer that repeats the old rule
  • Tags every feedback-derived chunk with its source, date and the handbook chunks it was answered from, and removes it when any of those chunks changes
  • Keeps feedback chunks out of the citation path, or ranks them below primary documents, so the assistant never cites a past answer as policy

5. Larkspur ingests the handbook from the help centre, the PDF export and the internal wiki, so the export rule is stored three times. Top-3 retrieval returns it three times. Do you add Dartboard, MMR or deduplication?

What a strong answer covers:

  • Deduplicates at indexing time first: exact or near-duplicate chunks waste storage and every later step, and a content hash catches the exact copies
  • Uses Dartboard or MMR for the overlap that survives deduplication, such as two documents that state one rule in different words
  • Sizes the candidate pool to the duplication: in the dartboard run, a pool of 9 drawn from five copies of each chunk holds only two distinct chunks, so the third pick is a copy again
  • Measures on golden questions that need two or more distinct chunks, and checks that single-fact questions do not lose their second supporting chunk

Key Takeaways

  • Graders filter and verify; they never add evidence. When every chunk is graded irrelevant or the answer is not grounded, rewrite the query or abstain instead of answering anyway.
  • Check source highlights in code: every segment must be found in the chunk it claims to come from.
  • Feedback re-ranking moves only chunks that were shown. Read its result per question, and send questions it cannot fix to retrieval work.
  • Remove duplicate chunks at indexing time, then use a diversity-aware selector with a candidate pool larger than the number of copies.
