M28 Grading and query rewriting

Open the lab

The notebooks run on a research paper (lesson 28.1, and lesson 28.2, which moves the same graph onto a managed Databricks index) and a fictional company’s support documents (lesson 28.3). These pages put the same graphs on the Larkspur Cloud handbook from M10: its twelve chunks, and five golden questions that each take a different path through the loop. Can I export my data after I cancel my plan? is answered on the first retrieval, How long does a refund take? after one rewrite, What happens if my server goes down? after two, Do you offer a student discount? has no answer in the handbook, and What’s the weather like today? is off topic.

TL;DR

  • A document grader is an LLM call with structured output that reads retrieved text next to the question and says whether it helps answer it. A conditional edge turns that verdict into the next node: generate, or rewrite and retrieve again.
  • A retriever returns k chunks for every query. In the lab, the student-discount question retrieves two chunks at 0.000, and a rewrite of it retrieves support at 0.503; neither says anything about discounts, and only the grader keeps them from the model.
  • A rewrite loop without a counter runs until the grader says yes or LangGraph stops it. At the default recursion limit of the pinned langgraph 1.2.18 (10,007 steps), a grader that always says no costs 3,336 retrievals.
  • Lesson 28.3’s graph allows 2 rewrites per question. On the five golden questions, that bound answers 3 at 31 LLM calls; a bound of 3 answers the same 3 at 34.
  • A topic check before retrieval costs one call per question and stops off-topic ones early: the weather question costs 1 call instead of 8, and gets an off-topic reply instead of “not found”.

Mental model

Every self-correcting design in Part IX is this loop with more branches. The grader decides whether the loop runs again, and the counter decides when it must stop. Without the grader the model answers from whatever came back; without the counter an unanswerable question never ends.

Conditional edges

Lesson 28.1: Retriever as a tool; grade then rewrite in LangGraph. Notebooks: 01a_simple_agentic_rag.ipynb

What you’ll learn

  • Explain how a retriever becomes a tool the model chooses to call, and what the model sees of it.
  • Trace a question through the two conditional edges that decide between retrieving, answering and rewriting.
  • Compare a grader on the edge with a grader that is a node, and say what each leaves in the state.
  • Diagnose a grader that passes related text which does not answer the question.

M22 built the loop where a model asks for a tool and your code runs it; M10 built a RAG chain that retrieves once and answers from whatever came back. This lesson joins them: retrieval becomes a tool in a LangGraph graph that checks what the tool returned before the model answers.

A Larkspur customer asks How long does a refund take? The handbook’s first hit is the refund-window chunk. It is about refunds, and it says an annual plan can get a full refund within 30 days. It never says how long the money takes to arrive. A plain RAG chain hands that chunk to the model, and the model writes a confident answer about the wrong thing. We call this answering from a near miss: the retrieval looked fine by every number the chain had.

The fix has three jobs: let the model decide when to search (the retriever tool), read the retrieved text against the question (the grader, next section), and route elsewhere when the text fails (the conditional edge).

The retriever as a tool

The graph wraps the vector store’s retriever as a tool with a name and a description, the only things the model knows about it. The agent node binds the tool to the model, which decides whether to call it and with what query. For Larkspur the description says the tool searches the handbook, so a customer who writes hello gets a greeting with no search. The notebook does the same over a research paper.

Fixed and conditional edges

A conditional edge is an edge whose destination is chosen at run time: after its source node runs, LangGraph calls a routing function on the state, and the value it returns names the next node. A fixed edge always goes the same way, as the edge from rewrite back to agent does. The graph has two conditional edges:

After node Routing function Returns Goes to
agent tools_condition, prebuilt in LangGraph "tools" if the model’s last reply has a tool call, otherwise the end marker retrieve through a path map that translates "tools", or the end
retrieve grade_documents "generate" or "rewrite" The node with that name, with no path map, because the function returns node names

Table 1: The two routing decisions and how each return value becomes a node.

The first search misses refund-timing for a reason worth knowing. TF-IDF matches exact words, and the question says “refund” while the chunk says “Refunds”. The reworded question uses “refunds” and “business days”, the chunk’s own words, and scores 0.720.

The rewrite goes back to agent, not straight to retrieve, so the model reads the reworded question and decides again whether and how to search. That keeps the model in charge of the search, at one more model call per round.

Where the verdict lives

Here the grader is the routing function itself, not a node, so it writes nothing to the state. The history shows a rewrite but not the verdict behind it; the only record is a printed line. We call this the invisible verdict. Lesson 28.3 splits the job: a grading node writes the passing chunks and a should-generate flag to the state, and a small router reads them. That costs one graph step per retrieval and makes every decision visible in the state, a checkpointer and a trace.

Pitfall: the unbounded rewrite loop. Nothing on the rewrite path counts the trips. The loop ends only when the grader says yes. For a question the handbook cannot answer, that never happens, and lesson 28.3 adds the counter that stops it.

The routing is only as good as the verdict it reads, so the next section looks at the call that produces it.

Document grader

A document grader is one LLM call that reads retrieved text next to the question and says whether the text helps answer it. It uses structured output: the reply must match a declared schema, so the router compares a typed field instead of parsing free text. This module has two graders:

Edge grader (this lesson) Node grader (lesson 28.3)
Place in the graph Routing function on the edge after retrieve Node, followed by a separate router
What it reads Everything the tool returned, as one message One chunk per call
Output schema A score field described as 'yes' or 'no' A relevance label (RELEVANT or IRRELEVANT) and a reasoning field
Decision Exact match with "yes" Match with "RELEVANT" after trimming and upper-casing
What reaches the answer Every retrieved chunk, relevant or not Only the chunks that pass
Grader calls per retrieval 1 k, the number of chunks retrieved (2 in lesson 28.3)

Table 2: The two graders side by side.

Grading the block is cheap, but one relevant chunk carries the irrelevant ones into the prompt. Grading each chunk costs k calls per retrieval and filters what the model reads.

The label contract

The schema decides what the router can trust. In this lesson’s grader the score is a plain string and the router compares it exactly with "yes". Here is what each label does under three ways of reading it:

Model’s label Exact match with "yes" Trimmed and lower-cased first Field typed as a fixed set of values
yes generate generate accepted
Yes rewrite generate rejected by validation
yes (leading space) rewrite generate rejected by validation
maybe rewrite rewrite rejected by validation

Table 3: Planted labels under three contracts. The bold rows are relevant retrievals sent to rewrite.

We call the bold rows the capital-Y rewrite: the grader agreed, and the graph still discarded the evidence. Normalising fixes those rows. Typing the field as a fixed set of values (a Literal in Pydantic) goes further: any other label fails loudly as a validation error instead of quietly choosing a branch, as in lesson 28.3’s topic check.

Related text or an answer

The prompt sets the bar. This lesson’s grader calls a document relevant if it “contains keyword(s) or semantic meaning related to the user question”; lesson 28.3’s also accepts “context that helps understand the topic”. Both pass refund-window for How long does a refund take?, because it is about refunds: the near miss, now approved by the grader. A grader that asks “does this text answer the question?” fails it and sends the query to rewrite. “Related” maximises recall into the prompt; “answers” protects what the model reads.

Why a score cannot do the grader’s job

A retriever returns k chunks for every query, whatever they score. The lab’s TF-IDF scores over the M10 handbook chunks show that no score threshold can replace the grader:

Query Top chunk and score Answers the question?
How long does a refund take? refund-window, 0.227 No
Its rewrite refund-timing, 0.720 Yes
Do you offer a student discount? billing and cancel, both 0.000 No
Its rewrite Student discount pricing for plans support 0.503, then billing 0.461 No
Larkspur outage availability guarantee and incident updates sla 0.470, then incidents 0.253 Yes

Table 4: Retrieval scores from the M28 lab. A non-answer at 0.503 outscores a real answer at 0.470.

The discount question shares no word with the handbook and still retrieves two chunks, and its rewrite scores 0.503 without either chunk mentioning a discount. A threshold above 0.503 would reject the outage answer at 0.470; one below it lets the discount non-answer through. Only reading the chunk next to the question separates them.

In practice: the refund question at Larkspur

Put the graph on the Larkspur support assistant and follow the refund question once more:

  1. The model reads the handbook tool’s description, sees a policy question and calls the tool.
  2. The tool returns refund-window first. An “answers the question” grader says no.
  3. The conditional edge sends the run to rewrite, which rewords the question and hands it back to the model.
  4. The model searches again, the tool returns refund-timing at 0.720, the grader says yes and generate answers from it.

Key distinction: this graph corrects a bad retrieval but cannot give up, and its verdicts leave no record. Lesson 28.3 adds the counter that ends the loop, a node that records each verdict, and a topic check before retrieval.

Limits of this evidence

  • Notebook corpus. The notebook runs on a research paper; the Larkspur paths and scores come from the M28 lab.
  • TF-IDF scores. Table 4 uses exact-word TF-IDF. Embedding scores differ, though an embedding retriever still returns k chunks for every query.
  • Planted labels. Table 3 tests the comparison, not how often a model writes Yes.

Key Takeaways

  • Wrap the retriever as a tool whose name and description tell the model when to call it, then put a conditional edge after retrieval that sends the run to generate or rewrite on the grader’s verdict.
  • Make the verdict a typed field with a fixed set of values, and prefer a grading node that writes it to the state, so a wrong label fails loudly and every decision can be traced.
  • Ask the grader whether a chunk answers the question, not whether it is related. A similarity score cannot do this, because the retriever returns k chunks for every query whatever they score.

Check yourself

1. Why does the rewrite node send the new question back to the agent instead of straight to the retriever?

The model reads the reworded question as the newest message and decides again whether to call the tool and with what query, so it stays in charge of the search. Nothing on this path counts the trips, so the loop ends only when the grader says yes, which lesson 28.3 fixes with a counter in the state.

2. The refund-duration question retrieves the refund-window chunk first. Does a grader that accepts related text pass it, and what follows?

Yes. The chunk is about refunds, but it only says an annual plan can get a full refund within 30 days, not how long a refund takes, so the model answers from a near miss. A grader that asks whether the text answers the question fails it and sends the query to rewrite, which finds refund-timing at 0.720.

3. The grader sends a clearly relevant retrieval to rewrite, and its label was Yes with a capital letter. Why, and what are two fixes?

The score is a plain string compared exactly with "yes", so "Yes" takes the rewrite branch: the capital-Y rewrite. Trim and lower-case the label before comparing, or type the field as a fixed set of values so any other label fails validation instead of silently choosing a branch.

The project: the same agent on Databricks Vector Search

Lesson 28.2: The same agent on Databricks Vector Search. Notebooks: 02a_simple_agentic_rag_databricks.ipynb (optional)

What you’ll build

  • A Delta table of chunks with a primary key, the source the index is built from.
  • A Vector Search endpoint and index that embed the table’s text for you and stay in sync with it.
  • A retriever tool over that index that returns two chunks per call.
  • Lesson 28.1’s graph, unchanged: agent, retrieve, grade, rewrite, generate, with models served on Databricks.

Lesson 28.1 kept its chunks in an in-memory vector store that the notebook rebuilt on every run. This project moves the retriever behind a managed index on Databricks. The graph, grader, rewrite and generate nodes stay the same; only the tool points somewhere new.

What changes is who owns the index. The chunks live in a governed table, the platform computes the embeddings and serves the search, and the agent sees only a tool. That suits a Larkspur team: the support writers update a table, and the assistant searches the latest handbook without anyone rebuilding a vector store.

Architecture

Databricks offers three kinds of index, and the notebook uses the first:

  • Managed embeddings: the platform embeds a text column and keeps the index in sync with the table.
  • Self-managed embeddings: you compute the vectors, store them in the table, and the platform syncs them.
  • Direct access: no table; you write vectors to the index yourself.

Design choices worth copying

Choice Why
A table as the source of truth Chunks are rows with ids, so an edit to one policy updates one row, and the index follows on the next sync
Change data feed on the table The sync reads only the rows that changed instead of re-embedding the whole corpus
Managed embeddings The same embedding model indexes the chunks and the queries, so they cannot drift apart. Lesson 28.1’s notebook used the same model, computed by the notebook
Create only if missing, then wait The setup waits until the endpoint and index report online, and a rerun neither fails nor duplicates them
A small, fixed result count Two chunks per call keeps the grader’s block small (lesson 28.1’s block-grade risk)

Table 2: Five choices and what each protects against.

The graph code did not change, which is the point of the tool boundary from M22: the model sees a name and a description, so the backend behind them can move.

Limits

  • A misleading tool name. The description talks about the paper, but the name refers to a company policy document. A name that contradicts the description can make the model skip the tool or call it for the wrong questions.
  • Lesson 28.1’s flaws come along. The grader still compares its label exactly with "yes" (the capital-Y rewrite), still grades the block, and nothing counts rewrites.
  • Mixed providers. The rewrite node calls an OpenAI model while every other node uses a model served on Databricks, so one run needs two providers’ credentials.
  • A triggered sync. A table edit is invisible to the agent until a sync runs, so whatever writes the table must also trigger the sync.
  • Standing cost. The endpoint is billed while it exists, whether or not anyone asks a question.

The notebook runs only inside a Databricks workspace, with permission to create a catalog, a schema and a Vector Search endpoint. The rewrite node also needs an OpenAI key, and the generate node pulls a public RAG prompt from LangSmith.

Key Takeaways

  • Behind the tool boundary the retriever can move from an in-memory store to a managed index without touching the graph: the model sees only the tool’s name and description.
  • A managed index makes the chunk table the source of truth. Turn on change data feed and trigger a sync after every write, or the agent searches yesterday’s handbook.
  • Moving platforms carries the graph’s flaws with it. The exact-match label, the block grade and the missing rewrite counter need the same fixes as in lessons 28.1 and 28.3.

Check yourself

1. The project swaps an in-memory vector store for Databricks Vector Search. Which parts of lesson 28.1's graph had to change, and why so few?

Only the retriever tool: the agent, grader, rewrite and generate nodes are the same. The model knows the retriever only through the tool’s name and description, so the store behind the tool can change without the graph noticing.

2. A Larkspur writer fixes the refund-timing row in the chunk table, but the assistant keeps quoting the old text an hour later. What is the likely cause?

The index uses a triggered sync, so it refreshes only when a sync is started. Until then it serves the embeddings of the old row. The pipeline that writes the table should trigger the sync, and change data feed lets that sync re-embed only the changed row.

3. The retriever tool is named for a policy document but described as a search over a research paper. What can go wrong, and what is the fix?

The model reads both strings to decide when to call the tool, so a contradiction can make it skip the search for paper questions or call it for policy questions it cannot answer. Name the tool for what it actually searches, and make the description agree.

Topic guardrails

Lesson 28.3: Guardrails, query optimisation and a retry loop. Notebooks: 03a_advanced_rag_agent.ipynb

What you’ll learn

  • Distinguish an off-topic question from one the handbook cannot answer, and the check that catches each.
  • Calculate what a question costs in LLM calls for any rewrite bound.
  • Choose a rewrite bound from the golden set.

Lesson 28.1’s graph rewrites when the grade fails, but it cannot stop. Two Larkspur questions show the cost. Do you offer a student discount? is about pricing, but the handbook has no discount policy. What’s the weather like today? has nothing to do with Larkspur. In lesson 28.1’s graph both rewrite again and again and never get a reply. Even with a counter, both would end in the same “I couldn’t find that” message, which is wrong for the weather question.

The eight-node support agent

The notebook builds this agent for a fictional company’s support documents; these pages run it on the Larkspur handbook. Before retrieving, it asks whether the question belongs to the assistant at all:

Figure 1: The support agent. Three nodes end the turn; the two handlers reply with fixed text and make no LLM call.

A topic guardrail is a classification step before retrieval that decides whether a question is in scope. Here it is one structured-output call whose schema has a classification (RELEVANT or IRRELEVANT) and a confidence (HIGH, MEDIUM or LOW), both typed as fixed sets of values. Its prompt lists what is on topic (services, pricing, support procedures, company information) and what is not (general technology, other companies, weather and news). RELEVANT goes to retrieval; anything else goes to the off-topic handler, which lists what the assistant can help with.

Off topic or unanswered

The check comes before retrieval because the grader cannot tell “off topic” from “not in the handbook”: both look like a retrieval where nothing passes. The lab shows the difference with two rewrites allowed:

Question Topic check Grader Ends in LLM calls
Can I export my data after I cancel my plan? on topic 2 of 2 pass on the first retrieval answer 4
Do you offer a student discount? on topic 0 of 2 on each of 3 retrievals no-results reply 9
What’s the weather like today? off topic not reached off-topic reply 1
What’s the weather like today?, check off none 0 of 2 on each of 3 retrievals no-results reply 8

Table 1: Three golden questions, two rewrites allowed. The guardrail and the grader catch different failures.

The student-discount question passes the topic check, so only the grader and the bound stop it. The weather question stops for 1 call instead of 8, and the customer reads “I can help with pricing, refunds and servers” instead of “I couldn’t find that in the handbook”.

What the check costs

The check costs one call on every question, so it does not always pay. Over the lab’s five golden questions it costs 3 calls at zero rewrites (14 with the check, 11 without), breaks even at one (24 and 24) and saves 3 at two (31 and 34). The check pays when the off-topic share of traffic times the cost of a full retry loop exceeds one call per question, and it pays in reply quality at any bound.

The classification boundary

Three details matter in production:

  • It classifies the enhanced query. The enhancement node first folds the conversation history into a standalone question, so a follow-up such as What about annual plans? carries the refund question it follows.
  • Confidence is computed and ignored. The router reads only the classification. Asking a clarifying question on LOW confidence needs a third branch.
  • A false rejection is silent. An on-topic question classified IRRELEVANT never reaches retrieval or its logs. We call this the silent rejection: track the off-topic rate and sample those replies.

The guardrail keeps one kind of question out of the loop; the next section bounds the loop for the rest.

Bounded retries

Bounded retries means the graph counts its rewrites in the state and takes a different exit when the count reaches a limit. Lesson 28.1’s graph has no counter, so when the handbook has no answer, LangGraph’s recursion limit (a cap on graph steps per run) is the only stop.

The runaway rewrite loop

In the pinned langgraph 1.2.18 the default recursion limit is 10,007 steps. Lesson 28.1’s graph, run with stub nodes and a grader that always says no:

Recursion limit Retrievals LLM calls How it ended
Default, 10,007 3,336 10,007 GraphRecursionError
25, set in the run’s config 8 25 GraphRecursionError

Table 2: Lesson 28.1’s graph on a question nothing can answer, with stub nodes.

We call this the runaway rewrite loop. Each round costs three LLM calls (agent, grader, rewrite) and three graph steps, so calls track the step limit, and the run still ends in an error, not a reply.

A counter in the state

This lesson’s graph bounds the loop in the state:

  • The count: a rewrite counter that the enhancement node resets to 0 at the start of every turn, so the bound is per question, not per conversation.
  • The router: after grading, it picks one of three exits in a fixed order, shown in Figure 2.
  • The guard: the rewrite node repeats the limit check and does nothing if it is reached, in case a later edge reaches it directly.

Figure 2: The router’s check order. Evidence is checked before the budget, so a hit on the last retrieval is still answered.

With a limit of 2 rewrites, a turn makes at most 3 retrievals. Swapping the two checks would discard a passing chunk on the third retrieval and reply “not found” to a question the graph had just answered.

The cost of each attempt

The bound also caps the cost. With k = 2 chunks per retrieval, a question costs one call for the topic check, two grader calls per retrieval, one per rewrite and one for the answer if there is one; the handlers and a first-turn enhancement make none. Answered on the first retrieval, a question costs 1 + 2 + 1 = 4. Never answered with a bound of m, it costs 1 + 2(m + 1) + m: 9 at a bound of 2. The interactive lab runs the loop on the five golden questions with real TF-IDF retrieval over the M10 handbook chunks and the bound as its slider:

Choosing the bound

Each step up the bound reaches one more question until 2, where the outage question is answered on its second rewrite. Going to 3 answers nothing new: the extra retrieval and three calls all go to the student-discount question, which no bound can answer. Unanswerable questions always pay the full bound, so set it where the answered count stops rising.

Pitfall: the counter as the only stop. Keep the recursion limit as a backstop under the counter. The counter bounds the loop you designed; the recursion limit bounds the one a later edit creates by accident.

The counter decides how many rewrites a question gets; what they say decides whether they help.

Two rewrites, two jobs

The graph rewrites the query in two places, for different reasons:

enhance_query optimize_query
Runs Once per turn, before the topic check After a retrieval where no chunk passed
Reads The conversation history and the new question The current query
Job Make a follow-up standalone Find words that retrieve better
On the first turn Passes the question through, no LLM call Same as any turn

Table 4: Enhancement repairs the conversation; optimisation repairs the retrieval.

When a rewrite helps

A rewrite helps only if it moves toward the documents’ words. The outage question shows both cases:

Attempt Query Top two chunks Passes?
Original What happens if my server goes down? reboot 0.416, sizing 0.389 No
Rewrite 1 What happens when my server is unavailable? reboot 0.416, sizing 0.389 No
Rewrite 2 Larkspur outage availability guarantee and incident updates sla 0.470, incidents 0.253 Yes

Table 5: The outage question’s three retrievals. The rewrites are the lab’s hand-written ones.

TF-IDF matches exact words, and “unavailable” is not in the handbook (only “availability” is), so the first rewrite retrieves the same chunks at the same scores. We call this the synonym swap: new wording that never reaches the documents’ vocabulary. The second rewrite uses the handbook’s words, “outage” and “availability”.

Drift across rewrites

Each optimisation reads the current query and writes back to the same field, so the second rewrite rewrites the first, and two rounds can drift from what the customer asked. Lesson 28.1’s rewrite node rewords the original question every time instead, at the cost of never building on a near miss. M17 covers rewriting before retrieval as a stage of its own, including HyDE and multi-query.

In practice: the student-discount question at Larkspur

Follow Do you offer a student discount? with a bound of 2:

  1. The topic check says RELEVANT: 1 call.
  2. Three retrievals, the first scoring 0.000 on both chunks, and all six chunks fail: 6 calls.
  3. Two rewrites between them, then the fixed no-results reply: 2 calls, 9 in all.

This question needs new handbook content, which no rewrite can supply. The no-results rate lists the handbook’s gaps, and a jump after a change points at the index or the grader.

Key distinction: this graph knows when to stop, but it never checks its own answer. M29 adds a web-search fallback when grading fails and a check on the generated answer.

Limits of this evidence

  • Stand-ins in the lab. Retrieval is real TF-IDF, but the grader passes only the golden set’s answer chunks, the topic check reads the golden label and the rewrites are hand-written. Real LLMs make mistakes these do not.
  • Five questions. A larger golden set may keep gaining answers past a bound of 2.
  • Stub nodes. Table 2 measures graph steps, not a model’s behaviour.

Key Takeaways

  • A topic check before retrieval costs one call per question and keeps off-topic questions out of the retry loop. Track the off-topic rate, because a silent rejection leaves no retrieval log.
  • Bound rewrites with a per-question counter in the state, check evidence before the budget, and keep the recursion limit as a backstop. Unanswerable questions always pay the full bound, so set it where the golden set’s answered count stops rising.
  • Enhancement makes a follow-up standalone; optimisation looks for words that retrieve better. A rewrite helps only when it reaches the documents’ vocabulary, and rewriting a rewrite can drift from the question.

Check yourself

1. Why does the topic check run before retrieval instead of leaving off-topic questions to the document grader?

The grader cannot tell “off topic” from “not in the handbook”: both look like a retrieval where nothing passes, spend the retry budget and end in the same no-results reply. In the lab the weather question costs 1 call with the check and 8 without.

2. With two rewrites allowed and two chunks per retrieval, how many LLM calls does a question the handbook cannot answer cost?

Nine: 1 for the topic check, 6 grader calls (2 per retrieval over 3 retrievals) and 2 rewrites, with no answer call. In general it is 1 + 2(m + 1) + m for a bound of m, because unanswerable questions always pay the full bound.

3. The outage question's first rewrite retrieves exactly the same two chunks as the original. What went wrong, and should you raise the bound to compensate?

It is a synonym swap: “unavailable” is no more a handbook word than “goes down”, so TF-IDF returns the same chunks at the same scores. A higher bound only buys more attempts; the fix is a rewriter that reaches the documents’ vocabulary, as the second rewrite does with “outage” and “availability”.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. A week after the Larkspur handbook moved to a new document system, the support assistant’s LLM bill doubled while traffic stayed flat. Traces show most questions now making three retrievals. What happened, and what do you check first?

What a strong answer covers:

  • Reads the path log: the share of questions that use rewrites and end in the no-results reply rose, so retrieval or grading changed, not traffic
  • Re-runs the golden set and prints retrieved chunks for a failing question: if the right chunk is missing, the migration broke loading, chunking or the index; if it is present and graded no, the grader or its prompt changed
  • Explains why cost doubled: with a bound of 2 and k = 2, every failed question pays 9 calls instead of 4
  • Adds an alert on the no-results rate and rewrites per question, so the next regression shows up the same day

2. Your retriever moves to k = 8 for better recall. The grader currently reads all eight chunks as one block and answers yes or no. Do you switch to grading each chunk?

What a strong answer covers:

  • One block grade lets a single relevant chunk carry seven irrelevant ones into the prompt; per-chunk grading filters them out
  • Per-chunk grading costs k calls per retrieval, 8 instead of 1, and multiplies with every retry
  • Mitigations: run the grades in parallel, put the grader on a small fast model, or ask for a list of per-chunk verdicts in one structured-output call
  • Measures both on the golden set: answer faithfulness, tokens sent to the model, latency and cost per question

3. How do you know the grader is grading correctly in production?

What a strong answer covers:

  • Labels a sample of (question, chunk) pairs by hand and measures the grader’s precision and recall against them
  • Names both errors: a false yes sends a non-answer to the model (refund-window for “how long does a refund take?”); a false no burns a rewrite and can end in “not found” for a question the handbook answers
  • Logs the verdict and its reasoning field per chunk, since a grader on a routing edge leaves no trace in the state
  • Re-checks after every change to the grader’s model or prompt, and when a new document type enters the index

4. A customer asks about refunds, then sends “What about annual plans?” and gets the off-topic reply. What went wrong?

What a strong answer covers:

  • The topic check saw the follow-up alone; it should classify the enhanced query, after the history is folded in
  • Checks that the history was there: the conversation is checkpointed per thread_id, and a new thread starts empty
  • Uses the confidence field the classifier already returns: route low confidence to a clarifying question instead of a refusal
  • Adds follow-up questions to the golden set and tracks the off-topic rate, since a false rejection never reaches retrieval logs

5. A product manager asks to raise the retry bound from 2 to 5 “so more questions get answered”. How do you respond?

What a strong answer covers:

  • Plots answered questions against the bound on the golden set: in the lab, going from 2 to 3 answers nothing new and adds 3 calls
  • Points out who pays: questions with no answer in the handbook always use the full bound, 1 + 2(m + 1) + m calls at k = 2
  • Looks at the questions still unanswered: a rewrite cannot find content that is not indexed, so the fix is the handbook, or better rewriting toward its vocabulary
  • Keeps LangGraph’s recursion_limit as a backstop under the counter, since a later edit can add a loop the counter does not see

Key Takeaways

  • Grade retrieved text against the question before the model reads it. A similarity score measures shared words; only reading the chunk tells you whether it answers.
  • Put the verdict in the state and route on it with a conditional edge, so every path the graph takes can be logged and explained.
  • Bound every retry loop with a counter in the state that resets each turn, and set the bound where the golden set stops gaining answers.
  • Check the topic before retrieval when off-topic traffic is real, and watch the no-results rate it leaves behind: those questions are gaps in the handbook.
