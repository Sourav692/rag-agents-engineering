M30 Adaptive RAG and query routing

A fixed RAG pipeline does the same work for every question. A support desk cannot afford that: one Larkspur ticket needs billing policy, another a technical guide, a third a person, and a fourth something the handbook does not hold. A router reads the question first and decides where it goes, and every step after it can only work with what that route returns. This module covers how a router classifies a question into a closed set of labels, how a label becomes a knowledge-base filter, when a ticket should go to a person instead, how to choose between the vector store and the web and then check the evidence and the answer, and how to pick a retrieval method per kind of question.

Open the lab

The running example is the Larkspur Cloud support desk. The lab routes eighteen support tickets, each labelled with the knowledge base that holds its answer, such as Why was I billed twice this month? (billing) and How long do you keep my data after I cancel? (general).

TL;DR

  • A router is a classifier in front of retrieval. In the notebooks it is one LLM call with structured output that must return a label from a fixed set (Literal['Technical', 'Billing', 'General']), and the label becomes a metadata filter or a branch in a LangGraph graph.
  • A misroute hides the answer: the filter restricts retrieval to a knowledge base that does not hold it. In the lab, a router that always picks sends 15 of 18 tickets to the right knowledge base at one search each. A score floor of 0.42 removes all 3 misroutes, but 11 tickets then fall back to searching all three knowledge bases, 2.22 searches per ticket.
  • Escalation is checked before the category. A negative ticket goes to a person whatever it is about; the healthcare notebook adds a fourth sentiment, Distress, that goes to an on-call team.
  • Adaptive RAG routes between the vector store and the web, then checks twice: a document grader sends the question to the web when half or fewer chunks pass, and a hallucination grader sends an unsupported answer back for regeneration.
  • A strategy per query type spends LLM calls where the question needs them. In the 04a notebook a factual or contextual question costs up to 11 LLM calls and an analytical or opinion question 4.

Mental model

The router decides what retrieval is allowed to see. Sentiment is checked first, so an unhappy customer reaches a person whatever the topic; the rest go by category to one knowledge base, which retrieves, and the model answers from what came back. Grading and generation work only with what the chosen path returns, so a misroute surfaces as a confident wrong answer or an apology, never as an error. Lesson 30.1 calls that a silent misroute, and every lesson in the module has a version of it.

Query classification

A router is a classifier whose output decides where a question goes. In the 01a notebook it is one LLM call with structured output: the model must fill a schema whose only field is the category, and the field’s type lists the three allowed values, Technical, Billing and General.

That type is what makes the label set closed. The parser accepts only those three strings, and the routing function downstream can compare against them with no defensive parsing:

Model output What the schema does What reaches the router
Billing Accepts it Billing
billing Rejects it with a literal error Nothing; the call fails before routing

Table 1: A closed label set rejects a near-miss before the router sees it.

The prompt gives each label a one-line definition, such as “Billing queries will focus more on payment and purchase related aspects”. Those definitions are the router’s whole specification. A ticket that fits two of them gets whichever label the model leans toward that day.

Six routers, one shape

Every M30 lesson puts a classifier of this kind in front of something:

Router Labels Field type What the label decides

General support (30.1) Positive, Neutral, Negative Closed Escalate to a human or answer
Clinic (30.2) Billing, Appointments, Records, Insurance Closed Which department’s documents to search
Clinic (30.2) Positive, Neutral, Negative, Distress Closed Human support, on-call team or answer
Source (30.3) vectordb, web_search Closed Vector store or web search
Strategy (30.4) Factual, Analytical, Opinion, Contextual Free text Which retrieval strategy runs

Table 2: The M30 routers. Five close their label set; one does not.

The last row breaks. The strategy router’s value is a key into a table of four strategies, and factual or Factual query fails the lookup with a key error. We call this an open label set: the classifier may say something the code has no branch for. A closed field turns the same mistake into a rejected parse, which you can retry or default.

The 01a notebook classifies category and sentiment in two sequential LLM calls. One call with a two-field schema, as in the lab solution, halves the classification cost; two prompts are easier to test separately. Either way, keep the labels you route on in the schema, never in free text you parse afterwards.

An LLM classifier is logical routing in M17’s terms. Semantic routing instead compares the question with example text for each route and takes the closest; this page’s lab uses it with TF-IDF, because its scores can be checked exactly.

Multi-KB routing

Multi-KB routing means each label selects a different knowledge base, and retrieval sees only that one. In the notebook, the three knowledge bases are not three stores. They are one Chroma collection, compared by cosine distance, where every document carries a category field in its metadata. A response node sets a metadata filter on that field, and the retriever returns at most three chunks scoring 0.2 or more. The clinic notebook in lesson 30.2 notes the other design, one vector store per category. Both trust the label equally.

The label must match the stored value

Chroma compares metadata values exactly. The classifier returns Technical and the documents store technical, and each response node lowercases the label first. The notebook runs the refund question under three filters:

Filter value What the search can return Why
general The refund chunks Matches the stored value
General Nothing Capital G matches no document
technical Whatever clears 0.2 among technical chunks, or nothing This is what a misroute retrieves

Table 3: The refund question under three filters.

Lowercasing works only while labels and stored values differ by case alone; lesson 30.2 needs an explicit mapping.

Planted failure: the silent misroute

Filtered to the wrong knowledge base, the retriever behaves correctly: it returns whatever clears the threshold there, or nothing, and with no chunks the prompt makes the model apologise. Nothing records that the route was wrong. We call this a silent misroute, the default failure of every router in this module. It shows up only downstream: empty retrievals, apology answers, reopened tickets.

Planted failure: the shared-filter race

The notebook writes the filter onto the retriever object itself, which every request shares. Two requests served at the same time can overwrite each other’s filter, and a billing ticket can retrieve technical chunks. We call this the shared-filter race. The fix is to pass the filter with each search call, which the LangChain retriever merges over its defaults, and leave the shared object unchanged.

The optional modular notebook binds one response function to all three response nodes, turning three prompts into one template. A fourth knowledge base then needs one prompt entry, one node and one routing branch.

Giving an uncertain route a fallback

The notebook’s schema has no “unsure” label, and its classifier must always answer, as in Figure 1. A router that can abstain needs a confidence score and a rule for what happens below it:

Figure 2: The confidence floor. Below it, the ticket searches every knowledge base.

A fallback always includes the right knowledge base but costs three searches instead of one. The lab’s four presets show the trade:

The three misroutes at floor 0.00 fail for three different reasons:

Ticket Routed to, score Why it misroutes Smallest floor that catches it
The dashboard keeps logging me out. Billing, 0.000 Shares no term with any chunk; billing is first in the list Any floor above zero

Table 4: Three misroutes, three causes.

The first row is a no-signal route, and its score says so. The third is a confident misroute: it scores as high as a correct route, and the router’s own confidence cannot find it.

Key distinction: a floor removes no-signal routes cheaply. Confident misroutes need a better classifier (embeddings, an LLM, or several example tickets per route) and a labelled routing set to find them.

Choosing a router and a floor

The decisions on this page reduce to a short sequence:

The two combine: a low floor such as 0.01 catches tickets that match nothing, and the labelled set shows which confident routes need a better classifier.

Limits of this evidence

  • TF-IDF stands in for the LLM. The lab routes by TF-IDF similarity so its scores can be checked against scikit-learn. The notebook’s LLM classifier will misroute different tickets.
  • Eighteen hand-written tickets. The floor numbers describe this set, not a production ticket mix.
  • No recorded notebook run. Notebooks ship without outputs; Table 3 follows from Chroma’s exact-match filter, not from a logged run.

Key Takeaways

  • Close the router’s label set in its output schema, and code never meets a value it cannot handle. The prompt’s one-line label definitions are the router’s whole specification.
  • Map each label to its exact stored metadata value and pass the filter per call, not onto a shared retriever. A silent misroute leaves no trace, because the wrong knowledge base just returns weaker chunks or none.
  • A confidence floor with an all-KB fallback catches no-signal routes, in the lab for 0.11 extra searches per ticket. Confident misroutes need a better classifier and a labelled routing set.

Check yourself

1. Why can the query-type classifier crash on a label such as factual, while the knowledge-base classifier never returns a label the code cannot handle?

The knowledge-base classifier’s field lists the three allowed values, so the parsed output can only be Technical, Billing or General. The query-type classifier’s field is free text used as a key into a table of strategies, so factual or Factual query fails the lookup and crashes the request. A closed field turns the same mistake into a rejected parse instead.

2. The outage-compensation ticket scores 0.416 for technical, the same as a genuine restart ticket. Can a confidence floor catch this misroute?

Not without heavy cost. Once stop words are removed both tickets reduce to “server”, so they score the same and no floor separates them; catching it at 0.42 sends 8 correct tickets to the fallback too. It is a confident misroute, so it needs a better classifier and a labelled routing set, since the router’s own score cannot find it.

3. Under load, two requests sometimes retrieve from each other's knowledge base. What in the notebook causes this, and what is the fix?

The notebook writes the category filter onto the shared retriever object, so concurrent requests overwrite each other’s filter: the shared-filter race. Pass the filter with each search call instead, which the retriever merges over its defaults, and leave the shared object unchanged.

Lesson 30.1 sent every ticket to a knowledge base. That assumes the right reply is always a retrieved answer.

Two Larkspur tickets break the assumption. One customer writes, angrily, that they were billed twice; the billing knowledge base explains double charges perfectly, and the customer wants a person. Another writes, calmly, that their production server has been down for an hour. The technical knowledge base has a restart guide, and the customer needs the on-call engineer now.

A topic router sends both to retrieval and both get a polite handbook answer. The topic was right each time. The question of who should reply was never asked. This lesson adds four jobs in front of the topic route:

  • Detect: decide whether a person should handle the ticket.
  • Direct: pick which person, since an unhappy customer and an emergency need different teams.
  • Hand off: pass what the person needs to start without asking again.
  • Wait: pause the graph until the person or the customer responds, without tying anything up.

Human-in-the-loop escalation

Human-in-the-loop escalation means the graph hands a ticket to a person instead of answering it, based on a check that runs before retrieval. Both routers in this module classify sentiment as well as topic, and the routing function reads sentiment first: a Negative ticket goes to escalation, and only the rest are routed by category.

The order is the policy. A negative billing ticket never reaches the billing knowledge base, however well the router would have classified it. In the 01a notebook the escalation node returns a fixed apology and notifies nobody; it marks where a real handoff goes.

The optional clinic notebook builds that handoff for a clinic’s support desk. It routes four departments (Billing, Appointments, Records, Insurance) and four sentiments, with a rule in the sentiment prompt that Distress applies “only when the customer is facing a health emergency”:

Waiting for a person

The form is where the graph waits, and the notebook’s way of waiting does not survive a service.

Planted failure: the blocking form

The clinic notebook’s form node displays Jupyter widgets and then loops, polling UI events with a 0.3-second sleep, until the Submit button sets a flag. The node holds the graph open the whole time:

Figure 2: The polling form. The worker stays inside the form node until Submit.

That works in a notebook. In a service it ties up a worker per waiting customer, and a restart loses every form in progress. We call this the blocking form.

The interrupt pattern

Both notebooks already compile their graphs with a MemorySaver checkpointer and run each conversation under a thread_id. That is what LangGraph’s interrupt() needs (M09). The node calls it with the form it wants filled, the graph saves its state and returns, and a later call on the same thread resumes with the form values:

Figure 3: The interrupt pattern. Nothing waits in memory between the two calls.

Compare the two ways of waiting on one angry ticket while the customer takes ten minutes to fill the form.

Polling loop

  • Worker: held for the whole ten minutes, waking every 0.3 seconds.
  • Restart during the wait: the form and the ticket's state are lost.
  • Outside a notebook: the widgets have nowhere to render.
  • Needs a thread_id: no.

Interrupt and resume

  • Worker: free as soon as the form is sent.
  • Restart during the wait: the ticket resumes, with a persistent checkpointer in place of the in-memory one.
  • Outside a notebook: the form is just data in the response.
  • Needs a thread_id: yes, to find the saved state.

Counting missed and needless escalations

Sentiment is a proxy for “a person should handle this”. It misses a calm customer with an urgent problem and catches a sarcastic one with a simple question. Count both errors on labelled tickets before trusting it:

Error What it costs at Larkspur How to see it
Missed escalation A customer with a production outage gets a handbook answer Tickets reopened or escalated by the customer after an automated answer
Needless escalation An agent’s time on a question the handbook answers Escalated tickets an agent closes with a handbook link

Table 4: The two escalation errors and where each shows up.

The two errors pull in opposite directions. A looser trigger cuts missed escalations and raises needless ones, making the threshold a staffing decision as much as a model decision.

Triggers beside sentiment

Sentiment is one signal among several the graph already has:

  • Sentiment: Negative or an emergency label, as in both notebooks.
  • Fallback search: the router fell back to searching every knowledge base (lesson 30.1), a sign it was unsure of the topic.
  • Rejected answer: the hallucination grader rejected the answer (lesson 30.3).
  • Repeat: the same customer asked the same question twice.

Each extra trigger reduces missed escalations and adds some needless ones, which Table 4’s counts will show.

Key Takeaways

  • Check escalation before topic, and an angry or distressed customer reaches a person, not the knowledge base. Give each kind of escalation its own target, such as support for unhappy customers and on-call for live outages.
  • Map each label to its filter value explicitly, and pass the query, both labels and anything retrieved with the handoff. Wait for the person with interrupt() and a checkpointer, not a blocking form.
  • Sentiment is only a proxy for needing a person. Count missed and needless escalations on labelled tickets, and add triggers such as a fallback search, a rejected answer or a repeated question.

Check yourself

1. Why does the router check sentiment before it checks the topic?

The order is the policy. Checked first, a negative ticket goes to a person and never reaches the knowledge base, however well the router would have classified its topic. An angry customer wants a person, not a retrieved answer.

2. A calm Larkspur customer writes that their production server is down right now. Where should it go, and what risk does sentiment-only routing carry?

To the on-call engineer, the Larkspur equivalent of the clinic’s Distress route. Sentiment misses a calm customer with an urgent problem, so this ticket may get a handbook answer: a missed escalation. 3. The clinic notebook's form node polls widgets in a loop until Submit is pressed. Why does that fail in a service, and what replaces it?

Lessons 30.1 and 30.2 chose a knowledge base or a person. This lesson chooses between two sources, the vector store and the web, and then adds the two checks from M28 and M29 behind that choice.

A Larkspur customer asks how to tune Postgres memory on a Larkspur server. The handbook covers server sizing and memory, and a fixed pipeline retrieves those chunks and answers from them. The chunks say how much memory each plan has, and nothing about Postgres settings. The answer sounds grounded and does not help.

A fixed pipeline does the same work for every question. It has no way to say that the evidence is weak, or to look somewhere else. The graph in this lesson does four jobs a fixed pipeline cannot:

  • Choose a source before retrieving.
  • Check the evidence and fall back to the web when it is weak.
  • Check the answer against the evidence and regenerate when it is unsupported.
  • Stop, which the notebook’s graph leaves out.

Vector store or web

Adaptive-RAG (Jeong et al., NAACL 2024, arXiv:2403.14403) starts from the observation that a fixed pipeline does the same work for an easy question and a hard one. The paper routes by question complexity: no retrieval, one retrieval step or several, chosen by a small classifier trained for the job. The 03a notebook keeps the idea of deciding up front and routes by source instead.

A source router is a classifier whose labels are data sources. Here it is one LLM call with a closed schema whose only field allows vectordb or web_search, the same closed-label pattern as lesson 30.1.

What the router knows about the index

The router’s system prompt lists what the vector store holds: chain-of-thought prompting, transformers and attention, the DINO vision model, diffusion models and parameter-efficient fine-tuning. It asks the model to choose vectordb when the question relates to any of them.

That list is the router’s only knowledge of the index. Add documents on a new topic and the router keeps sending those questions to the web until someone edits the prompt. We call this the stale topic list. For Larkspur, the list would be the handbook’s sections: pricing, refunds, exports, outages and server sizing.

Each route rewrites for its own engine

Each route rewrites the question before searching. The vector-store rewriter makes it concise for semantic search; the web rewriter makes it a search-engine query. The two paths are set up differently:

Path How the notebook configures it
Vector store Research-paper PDFs split at 4,000 characters with 300 overlap; Chroma with cosine distance; up to 5 chunks scoring 0.35 or more
Web Tavily search returning up to 6 pages with their full text, at its advanced depth; pages with no content are dropped

Table 1: The two retrieval paths in the 03a notebook.

The whole graph puts the router first and the two graders after retrieval:

Figure 1: The adaptive RAG graph. A failed document grade joins the web path; a failed answer check loops back to generation.

The router can be wrong in both directions, and the document grader is what catches the vector-store side of that.

Grading documents and answers

The graph checks its work twice, once on the evidence and once on the answer. M28 and M29 teach each check on its own; here they sit behind a router.

The relevant-fraction rule

The document grader asks the LLM, once per retrieved chunk, whether the chunk is relevant, and gets a yes or no. The grading node keeps the chunks graded yes and computes the share that passed. If that share is 0.5 or less, the graph sets a web-search flag:

Chunks retrieved Graded relevant Fraction Next step
5 3 0.60 Generate from the 3
4 2 0.50 Web search, keeping the 2
5 2 0.40 Web search, keeping the 2
0 0 none Web search

Table 2: The relevant-fraction rule with a threshold of 0.5.

Exactly half counts as failure. On the web route, the search node appends the pages to the chunks that passed, and the answer can draw on both sources.

Planted failure: the inverted grade

The hallucination grader reads the answer and the documents and returns a score and a line of feedback. The score is inverted from what most graders use: yes means the answer may contain unsupported or contradicting content, and no means it is grounded.

Grader returns Meaning in this notebook What the graph does
no Grounded in the documents Ends with the answer
yes May be unsupported Returns to generation with the feedback added to the prompt

Table 3: The hallucination grader’s two outcomes.

We call this the inverted grade. Reuse this grader in a graph that expects yes to mean “pass” and every good answer loops while every bad one ships.

Planted failure: the unbounded regeneration loop

Nothing counts the retries in Figure 1. The regeneration edge has no limit, and a grader that keeps saying yes loops until LangGraph’s recursion limit stops the graph. In the version this repo locks (langgraph 1.2.18) that limit is 10,007 steps by default. Each round costs two LLM calls, a generation and a check. We call this the unbounded regeneration loop.

The fix is a counter in the graph state and a terminal branch:

Unbounded

  • Rounds: until the recursion limit, 10,007 steps by default.
  • Cost: two LLM calls a round, with nothing to stop the bill.
  • Result: a recursion error, and the customer gets no answer at all.

Bounded

  • Rounds: the first answer plus two retries.
  • Cost: four extra LLM calls beyond the first generation and check.
  • Result: the best answer with a warning, or lesson 30.2's handoff, triggered by a rejected answer.

The notebook tests the loop by uncommenting a hard-coded wrong answer in the generation node. That line sits in the first-attempt branch only, and the retry, which takes the feedback branch, runs the real chain. The test exercises one rejection and one retry with feedback, never a second rejection.

Each regeneration adds 2 more. A question the router sends to the vector store and the grader then rejects is the most expensive path. We call that the store-then-web detour. If many questions take it, the router’s topic list is wrong or the index is missing content, and both are cheaper to fix than to grade around.

Check yourself

1. You index documents on a new topic, but the source router keeps sending questions about it to the web. Why?

The topic list in the router’s system prompt is its only knowledge of the index: a stale topic list. Until someone edits that prompt, questions on the new topic do not match the list and go to web search. For Larkspur, the list would be the handbook’s sections.

2. Four chunks are retrieved and two are graded relevant. Does the graph generate from them or search the web?

It searches the web, keeping the 2 chunks that passed. The fraction is 0.50 and the rule sends anything at or below 0.5 to the web, so exactly half counts as failure. The web pages are appended to those 2 chunks, so the answer can draw on both sources.

3. The hallucination grader keeps returning yes for one question. What happens, and what should you add?

In this grader yes means the answer may contain unsupported content, so the graph returns to generation every time. Nothing counts the retries, so it loops until the recursion limit (10,007 steps by default), at two LLM calls a round. Add a counter to the graph state, stop after one or two retries, and return the best answer with a warning or escalate it.

Per-query strategy

A per-query strategy router labels each question Factual, Analytical, Opinion or Contextual, and runs a different retrieval strategy for each label over the same index. The idea is to spend retrieval work where the question needs it: precision for a fact, coverage for an analysis, spread for an opinion, the user’s situation for a contextual question.

The router is one classifier call in front of four strategies:

Figure 1: The type router. Every branch searches the same index; only the method changes.

Each strategy turns the question into searches differently:

Type What the question wants How the strategy retrieves
Factual One verifiable fact Rewrites the query, retrieves 8 chunks, has the LLM score each from 1 to 10, keeps the top 4
Analytical An explanation that covers several aspects Generates 4 sub-questions, retrieves 2 chunks for each, has the LLM pick the 4 most diverse and relevant
Opinion Several viewpoints Has the LLM name 3 viewpoints, retrieves 2 chunks for each, has the LLM pick 3 representative ones
Contextual An answer for this user Rewrites the query with the user’s context, retrieves 8 chunks, scores each against query and context, keeps the top 4

Table 1: The four strategies in the 04a notebook.

What each strategy costs

The strategies differ most in how they spend LLM calls. Counting from the code, with the classifier and the final answer included:

Type Classify Plan or rewrite Per-chunk scores Select Answer Total
Factual 1 1 up to 8 0 1 Up to 11
Analytical 1 1 0 1 1 4
Opinion 1 1 0 1 1 4
Contextual 1 1 up to 8 0 1 Up to 11

Table 2: LLM calls per question by type.

The factual and contextual strategies score chunks one call at a time, and their cost grows with the number retrieved. The analytical and opinion strategies spend one call to plan the searches and one to select, whatever the number of chunks. We call the first pattern per-chunk scoring: it is the most precise and the most expensive, and it is the line to cut first when cost matters.

Four faults to fix before reuse

The notebook’s code runs the idea, but four faults stop it working as written. Each is a planted failure worth knowing:

Fault What happens Fix
Open label set The classifier’s label is free text used as a key into the table of strategies; any other spelling raises a key error A closed field, as in lesson 30.1
The split crash The opinion selection call already returns a list of integers, and the code then splits it as if it were text, which raises an attribute error Iterate over the list
Dropped context The contextual strategy accepts the user’s context, but the wrapper calls every strategy with the query alone, and it always runs with “No specific context provided” Pass the context through the wrapper
Four indexes Each strategy splits the texts at 800 characters with no overlap, embeds them and builds its own FAISS index, embedding the corpus four times at start-up Build one index and share it

Table 4: The four faults in the 04a code.

The opinion strategy has one more quirk. It splits the LLM’s viewpoint reply on line breaks, and the number of searches follows the number of lines the model writes, not the 3 it was asked for.

Dropped context is the quietest of the four. The contextual path runs, returns chunks and answers, and nothing looks broken; it has simply stopped being contextual.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s support assistant started answering “Apologies, I was not able to answer your question” to customers who ask how long their data is kept after they cancel. The retention chunk is in the general knowledge base. How do you find the fault?

What a strong answer covers:

  • Pulls the logged category for those tickets first: a ticket routed to technical or billing never searches the general knowledge base, whatever the retriever does
  • Checks that the label matches the stored metadata exactly (General against general), since a filter that matches nothing returns no chunks and triggers the apology
  • Replays retrieval with the correct filter to separate a routing failure from a retrieval failure (score below the 0.2 threshold, chunk missing from the index)
  • Adds the failing tickets to a labelled routing set, and adds a fallback that searches without the filter when the filtered search returns nothing

2. The team is splitting the handbook into billing, technical and general knowledge bases. One Chroma collection with a category filter, or one collection per department?

What a strong answer covers:

  • One collection with a filter (the 01a design) keeps one embedding model and one index to run, and a fallback is the same search with the filter removed
  • Separate collections let each department choose its own chunking, embedding model and re-indexing schedule, at the cost of a fan-out query for the fallback
  • A misroute costs the same in both designs, because both trust the label
  • Access control never rests on a classifier’s label: if some documents are restricted, enforce it with collections or filters derived from the user’s identity

3. The router has been live for a month. How do you know whether it is still routing well?

What a strong answer covers:

  • Keeps a labelled routing set (the lab’s eighteen tickets are a small version) and reports accuracy per category and a confusion matrix on every prompt or model change
  • Logs the label, its score or confidence, the fallback rate and the escalation rate per day, and watches the label mix: a launch can create a kind of question no knowledge base covers
  • Tracks downstream signals per route, such as empty retrievals and apology answers, since a silent misroute shows up there first
  • Samples routed tickets for human review, weighted toward low-confidence and fallback cases

4. A ticket reads: “I was charged twice and my server has been down all morning. This is ridiculous.” What should the router do?

What a strong answer covers:

  • Sentiment runs first in determine_route, so a negative reading sends it to a person; the handoff should carry both topics, the contact details and anything already retrieved
  • A single-label classifier must drop one of the two problems; a schema that allows several labels, or decomposition into sub-questions (M17), keeps both
  • An outage in progress may deserve the on-call path, the way the healthcare notebook separates Distress from Negative
  • Measures both error costs: a missed escalation loses a customer, and a needless one costs an agent’s time

5. The adaptive RAG graph from lesson 30.3 is much slower and costlier than the plain pipeline it replaced. Where do the calls go, and what do you cut?

What a strong answer covers:

  • Counts LLM calls per path from the graph: on the vector route, one for routing, one rewrite, one grade per retrieved chunk (up to five), one answer and one hallucination check, plus a rewrite and a web search when grading fails
  • Grades all chunks in one call, or skips grading when the top retrieval score is high
  • Puts a retry counter in the graph state: the regeneration loop has none, so only LangGraph’s recursion limit stops it, and that limit is 10,007 steps by default in the version this repo locks (langgraph 1.2.18)
  • Moves routing and grading to a smaller model, traces latency per node, and re-checks answer quality against the baseline after each cut

Key Takeaways

  • Give the router a closed label set in its output schema, and normalise the label before it becomes a filter.
  • Plan for the silent misroute. A score floor with an unfiltered fallback catches no-signal routes cheaply; confident misroutes only show up on a labelled routing set.
  • Check escalation before the category, and make the handoff a pause with saved state rather than a node that blocks while it waits.
  • Every grader loop needs a counter, and every query type should spend only the LLM calls its question needs.
