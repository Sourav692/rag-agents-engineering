M26 Coding, computer-use and deep agents

Agents that write code, drive a browser or run for hours need a harness: sub-agents, a file system, skills and a tester that checks the work. This module moves the ReAct loop from web search into files, browsers and screens, pairs a developer agent with a tester agent, and then configures a deep agent instead of wiring a graph node by node. The M26 notebooks build on two ideas: the same agent loop running in new environments, and a deep-agent harness around one orchestrator.

  • Moving the loop to code, browsers or screens keeps the agent ⇄ tools graph and changes the tools, the observation and the success signal. On pixels, gpt-4o-mini missed 53 of 53 clicks, and gpt-4o missed 15 of 26 and met the goal in 2 of 3 runs.

Stub nodes show the developer runs r + 1 times and the tester r times, with zero model calls. A tester without a Python tool only estimates its pass rate.

Mental model

Every lesson keeps this loop and changes one part of it. Lesson 26.1 swaps the environment: search results, a test run, a mock browser, a screenshot. Lesson 26.2 adds a tester whose critique becomes the next observation, and a counter in state ends the loop. Planned pipeline vs ReAct loop

Lesson 26.1: Applied ReAct: web research, SWE and computer-use agents. Notebooks: 01a_web_research_agent.ipynb, 01b_swe_agent_applied.ipynb (optional), 01c_browser_agent_computer_use.ipynb (optional), 01d_vision_driven_computer_use.ipynb (optional)

What you’ll learn

  • Compare a planned research pipeline with a ReAct researcher on the same topic.
  • Choose between predictable cost and adaptive search for a given report.
  • Explain what changes when the loop moves to files, a browser and a screen.
  • Diagnose a coding, browser or vision agent from what the environment shows, not what the agent says.

M23 built the ReAct loop with create_agent, and M25 weighed plan-and-execute against it. This lesson puts both to work, first on research and then in three environments where the agent’s actions change things.

Larkspur Cloud’s support team wants a researcher that drafts a weekly outage summary. The first version plans three searches up front. One week the status page moved, the first search returns nothing, and the summary goes out with an empty “Root cause” section. Nothing in the run noticed, because the plan was fixed before any result came back.

The notebook builds both designs on one topic, Artificial Intelligence in Healthcare. A planned pipeline writes every search before running any of them. A ReAct researcher chooses its next search after reading the last result:

Figure 1: The two research paths. The pipeline runs straight through. The loop goes back to the model after every search.

The pipeline’s state carries more than messages: the topic, the planned questions, a dictionary of results per question merged by a custom reducer, the report, and a log that appends one line per node. Each node returns only the keys it changes. No edge goes back to planning. The pipeline cannot notice an empty search or follow a lead, and a failed search simply becomes an empty result.

The ReAct researcher is create_agent with one web_search tool and a prompt that asks for one search per turn, 3 to 5 in all. ModelCallLimitMiddleware from M23’s call limits bounds the loop in code.

One recorded live run produced these counts:

Planned pipeline ReAct agent
Web searches 3 4
LLM calls 2 5
Report characters 7,229 4,298

Table 1: One recorded run on the same topic. Search results and model choices change between runs. These are observations, not a benchmark.

The pipeline’s three questions were written together and came out broad and parallel. The agent started broad, then searched for things its results had named: AI models in surgery at Duke University, and physician adoption statistics.

Choosing a research shape

The two designs trade predictability for adaptivity:

Planned pipeline ReAct agent
Who chooses the searches The plan, up front The model, after each observation
Cost Fixed and predictable Varies, bound it with a call cap
Reacts to empty or surprising results ✗ ✓
Same steps every run, testable with one fixed input ✓ ✗
Good for Known-shape reports, batch jobs Open questions, multi-hop facts

Table 2: What each research shape gives you.

The decision comes down to whether the report’s shape is known before the first search:

Figure 2: Choosing a research shape. The hybrid keeps the plan’s sections and lets each step search adaptively.

Many production researchers sit in the middle: plan the sections first, then let each section’s step react to what it finds. M24 treats the pipeline side as workflow patterns. Larkspur’s weekly summary keeps its plan because the sections are fixed. Each section still needs a check for an empty result and a retry, or the empty “Root cause” section ships again.

Coding agent: tests as the reward signal

A SWE agent is a ReAct agent whose tools are a developer’s workflow: list, read and write files, and run the tests. The test output is its bug report.

The notebook writes a small project into a fresh temporary folder: two modules with planted bugs and a six-test suite. Running that suite before the agent starts gives this:

Test Result Why
test_add pass
test_subtract fail subtract(10, 4) returns 14
test_average pass
test_reverse_string fail reverse_string returns its input unchanged
test_is_palindrome_true pass “racecar” equals itself, reversed or not
test_is_palindrome_false fail “python” also equals its unreversed self

Table 4: The suite before the agent runs, from running the notebook’s scratch project: 3 failed, 3 passed.

The tool surface is deliberately narrow. Every path is reduced to a filename inside the scratch folder, and a hallucinated absolute path cannot reach the repository. The test tool runs one fixed pytest command with a 30-second timeout. The model chooses when tests run, never what command runs. That constrains the tools. It does not isolate hostile code, which needs a container or a hosted sandbox.

A green suite is still not proof of a good change. A common deviation with the small model is an extra edit, such as is_palindrome rewritten to stop calling reverse_string. The tests pass and the agent changed code no failing test pointed at. We call this a silent extra edit. Only a diff of the files before and after shows it, and only re-running the tests outside the loop confirms the agent did not just claim success.

Browser agent: grade the cart

The browser notebook turns screenshot_text, click, type_text and navigate into ordinary tools over a deterministic mock shop. The agent never sees the shop’s code, only the page text each action returns. Driving the shop by hand first shows the path the agent has to find:

Action Page after it Cart
type_text(search_box, "wireless mouse") Home 0
click(search_button) Search results, two mice 0
click(result_0) Logitech M185, $14.99 0
click(add_to_cart) Same product page 1

Table 5: The manual drive, from running the notebook’s mock browser. Four actions put one item in the cart.

Two things change once actions change state. The turn cap becomes a safety bound, because each extra click mutates the shop. And success is graded on browser.cart, never on the agent’s reply. A wrong element id returns an ERROR: line plus the current page, which lets the agent correct itself on the next turn.

Vision agent: when the observation is pixels

The vision notebook removes the text description. The agent gets a real PNG of a checkout page and must click by coordinates. Recognising a control and locating it turn out to be different abilities. Every run made while writing the notebook is in the table:

Model Screenshot Runs Clicks Missed Goal met
gpt-4o-mini raw 5 53 53 0
gpt-4o-mini with ruler, 2× 4 27 25 0
gpt-4o raw 3 26 15 2
gpt-4o with ruler, 2× 3 22 9 2

Table 6: Vision runs recorded in the notebook. Single-digit run counts on one synthetic screen: indicative only.

The small model knew it wanted the + button and kept clicking the wrong row, even though every miss was fed back to it. A miss raises no error and changes nothing on screen, and the loop just repeats. We call this the no-op loop, and the step cap in code is the only thing that ends it.

A coordinate ruler drawn over the screenshot fixed the vertical axis and broke the horizontal one. The miss count improved, but the error had moved rather than gone. Only the per-click log showed that. One ruled run also ended with “quantity set and coupon applied” when neither had happened, which is why the notebook asserts on the screen’s state.

Cost runs against intuition here. In the notebook’s measurement a raw screenshot cost gpt-4o-mini 14,175 prompt tokens ($0.0021) and gpt-4o 433 tokens ($0.0011). The stronger model was half the price per screenshot as well as more accurate.

Used as a frontend tester, the click log gives three outcomes rather than two:

Click log Verdict Whose problem
Hit the control, state changed pass nobody
Hit the control, state unchanged fail, the UI is broken frontend
Never hit the control errored, the UI is unverified the agent’s owner

Table 7: Three test outcomes from the click log. Reporting the third as a failure sends someone hunting a bug that may not exist.

If a selector or an accessibility tree is available, use it. Coordinates are the fallback when nothing else is exposed.

In practice: Larkspur’s control-panel agent

Larkspur wants an agent that resizes a customer’s server from the control panel after a support ticket approves it.

  1. Prefer selectors. The panel has an accessibility tree. The agent acts on named elements, as the browser agent does, and pixels stay out of the loop.
  2. Grade on the panel. Success is the server’s new size read back from the API, the equivalent of reading the cart, never the agent’s confirmation.
  3. Cap the loop in code. Each click changes a live account. The cap is a safety bound sized just above a clean run.
  4. Log every action. The action log separates “the resize button is broken” from “the agent never found it”.

Lesson 26.2 adds a second agent that checks the first one’s work.

Limits of this evidence

  • One live research run. Table 1 is a single recorded run, and a rerun will give different counts.
  • A few vision runs on one screen. Table 6 separates 100% from 41% misses clearly, but three runs cannot separate the two gpt-4o rows.
  • Mock environments. The shop and the checkout page are simulations. A real browser adds scrolling, overlays and timing, which these notebooks do not test.

Key Takeaways

  • A planned pipeline fixes its searches up front. Its cost is predictable and one fixed test covers it, but it cannot react to an empty result. A ReAct researcher picks each search after reading the last one and needs a call cap.
  • Moving the loop to code, browsers or screens changes the tools, the observation and the success signal. Grade success on the environment (the test suite, the cart, the screen) and verify with a diff, never with the agent’s final message.
  • On pixels a miss raises no error, and the step cap is the only bound. Prefer selectors to coordinates, and report “never reached the control” as errored, not failed.

Check yourself

1. Why can the planned research pipeline not follow a lead that one of its searches turns up?

Its questions are fixed before any result comes back, and no edge goes back to planning. It cannot notice an empty search or add one. The ReAct researcher chooses each search after reading the last observation, which is how it went on to search for things its results had named.

2. You need a weekly report with the same sections on a fixed topic, at a predictable cost. Planned pipeline or ReAct agent?

The planned pipeline. It suits known-shape reports and batch jobs, its cost is fixed, and it runs the same steps every time, so one fixed test covers it. A ReAct agent suits open questions and multi-hop facts, and its cost varies and needs a call cap. Each step still needs a check for an empty result.

3. A vision-driven computer-use agent keeps clicking, never reaches its goal and raises no error. What is going on, and what stops it?

It cannot locate the controls from pixels: in the notebook’s runs gpt-4o-mini missed 53 of 53 clicks even with every miss fed back. A miss changes nothing and raises no error. This is a no-op loop, and the step cap in code is the only bound. Prefer selectors to coordinates.

The project: a developer and tester pair

Lesson 26.2: Developer vs tester agents. Notebooks: 02a_developer_vs_tester_agents.ipynb (optional)

What you’ll build

  • A developer agent that writes Python and can run it with a timed Python tool.
  • A tester agent that reviews the code, writes unit tests in its report, scores it and lists fixes.
  • A two-node graph that loops developer, tester, developer until a reflection counter reaches its cap.
  • Two small games, FLAMES and Tic-Tac-Toe, built by the pair and checked against hand-written references.

Lesson 26.1 graded a coding agent on a test suite someone had already written. This project asks a second agent to supply the critique. It is the critique-and-revise (reflection) pattern from M25, with a generator (the developer) and a reflector (the tester) taking turns on one shared conversation.

The project adds no new pattern. It shows what two agents in one loop need: a stop rule no model can talk its way past, a safe-enough way to run model-written code, and a line between a test that ran and a test the tester only imagined.

Architecture

The graph has two nodes and one decision:

Figure 1: The critique-and-revise loop. The router reads a counter in state. Code decides the stop.

Piece What it does Built on
Developer A create_agent agent with one Python tool, its own tool loop capped at 12 steps, which sees the whole conversation on every turn M23’s create_agent
Tester A prompt piped into the model, no tools. Its report enters the conversation as a user message, because to the developer it is feedback M25’s reflector
Python tool Runs each snippet as a script in a new isolated Python process, in an empty folder, with no environment variables, closed standard input and a 10-second timeout
State The conversation, the cap and a reflection_count that each tester turn adds 1 to M08 reducers
Router A pure function that ends the run once the count reaches the cap M37’s capped quality loop

Table 1: The project’s five pieces.

The notebook checks the Python tool’s guards without a model. Keyboard input fails at once with EOFError, and an endless loop is killed at its timeout (2.0 s with a 2-second limit in our run).

Following one FLAMES request

The task is Write a Python program for the FLAMES game, plus a short example that calls it with two fixed names, with a cap of one reflection:

Figure 2: One reflection round. The developer speaks twice, the tester once.

The loop’s arithmetic holds for any cap. Stub nodes that only append a message, with zero model calls, give these counts:

Cap r Developer turns Tester turns Graph steps used recursion_limit (2r + 4)
0 1 0 1 4
1 2 1 3 6
3 4 3 7 10

Table 2: Stub runs from the notebook’s own graph builder. The developer runs r + 1 times, the tester r times, and the recursion limit leaves 3 spare steps as a second guard.

After the run, code checks how many times each agent spoke and whether the last answer holds a Python block that parses. Parsing does not prove the game is right.

A hand-written reference does. For John and Jane it finds 4 letters left, crosses out M, L, F, A and S in turn, and lands on Enemy. The notebook records two mistakes one model run made: it restarted counting from the start of FLAMES after each removal, and read S as “Sister” rather than “Sibling”. The Tic-Tac-Toe reference plays three scripted games (a win, a draw, a move onto an occupied square) and all three end as expected.

Design choices worth copying

Choice Why
Counter in state, pure router The loop ends by a rule in code, not when a model decides it is happy
recursion_limit as a second guard If the router were ever broken, the run still stops after 2r + 4 steps
Prove the cap with stubs Zero model calls make the termination test free and repeatable
Ask for code driven by fixed inputs The tool closes standard input. An interactive game would only raise EOFError
Check against a reference The tester’s verdict is a model’s opinion. A hand-written implementation is a fact

Table 3: Six choices and what each protects against.

Limits

  • The tester estimates. It has no tools. Its pass percentage and score are the model’s estimates, not executed results. We call this an estimated pass rate. Giving it the Python tool makes the results real, at roughly twice the cost.
  • Fixed rounds, not “until the tests pass”. The loop stops at the cap even if the tester still lists failures. The module’s lab brief asks for iteration until tests pass, which needs a router that also reads an executed test result.
  • A guard, not a sandbox. The Python tool runs model-written code with your user’s permissions. It can still read your files and reach the network, and anything beyond a demo needs a container or a hosted sandbox (lesson 26.3).
  • No recorded model run. The notebook ships without outputs and the drafts change each run. This page quotes only the deterministic checks.

The notebook needs an OpenAI key for the two agents. The stub runs, the tool guards and both references run without one.

Key Takeaways

  • Stop a two-agent loop with a counter in state and a pure router, back it with a recursion_limit, and prove the counts with stub nodes before spending a model call.
  • A tester without a way to run code only estimates its pass rate. Run the tests, or check against a reference, before trusting the verdict.
  • Running model-written code in a fresh process with a timeout, no environment and closed input keeps a demo from hanging or leaking keys, but it is not a sandbox.

Check yourself

1. With a cap of three reflections, how many times does each agent run, and what stops the loop?

The developer runs four times (a first draft plus one revision per critique) and the tester three times. The router stops the loop once the reflection counter in state reaches the cap, and a recursion limit of 2r + 4, here 10 steps, stops it even if the router were broken.

2. After one round the tester reports 100% of its tests passing and a score of 9 out of 10. How much does that tell you?

Little. The tester has no tools. It wrote the tests in its report and reasoned about them. The pass rate and score are the model’s estimates. Run the tests, give the tester the Python tool at roughly twice the cost, or compare against a hand-written reference.

3. Why does the Tic-Tac-Toe task ask for a function that plays a fixed list of moves?

The developer’s Python tool closes standard input and kills a snippet after a timeout. A game that waits for a player would raise an error at once or be stopped. The task asks for a version the tool can run and check without a keyboard.

Deep-agent harness

Lesson 26.3: Deep agents: orchestrator, sub-agents, skills and long-term memory. Notebooks: 03a_simple_coding_agent.py, 03b_long_term_memory_agent.py (optional), 03c_skills (optional)

What you’ll learn

  • Explain what a deep-agent harness gives one orchestrator model: files, sub-agents, skills, a backend and memory.
  • Trace why a sub-agent’s work stays out of the orchestrator’s context.
  • Diagnose a backend setting that sounds safer than it is.
  • Separate conversation state from long-term memory, and spot a memory shared by every user.

Lesson 26.2 wired two agents into a graph node by node. This lesson starts from the other end, with a ready-made harness you configure instead of a graph you draw. The examples are two command-line scripts, 03a_simple_coding_agent.py and its long-term-memory variant 03b_long_term_memory_agent.py, plus the eight skill folders in 03c_skills.

Larkspur Cloud wants one assistant for its support engineers. It should research an outage on the web, draft a fix to a billing script, and remember that one engineer wants refund answers as a checklist. Built as a graph, that is a node per specialist, a router, a file store, a memory store and the edges between them. A deep agent is the shortcut: one orchestrator model inside a harness, a prebuilt set of tools and middleware that gives it files, sub-agents, skills, an execution backend and memory.

The scripts use the deepagents library’s create_deep_agent. The tool and backend behaviour below is that of deepagents 0.7.32, the version in this course’s lock file:

Figure 1: The harness around one orchestrator. You configure each box instead of drawing edges between them.

The scripts configure each part as follows:

Part What it gives the orchestrator In the scripts
Built-in tools File operations (ls, read_file, write_file, edit_file, glob, grep), execute for shell commands, and task to call a sub-agent Added by create_deep_agent. execute returns an error unless the backend can run commands
Custom tools Domain actions 03a: name_project, internet_search (Tavily, 5 results by default) and four Databricks Genie tools for an insurer’s customer, distribution, policy and claims data. 03b adds save_memory, recall_memories, forget_memory

Because the harness is a configuration, you audit it by reading the configuration. The next three sections take its parts one at a time.

Sub-agents keep context small

A call to task runs the named sub-agent with its own messages and tools, and only its final message returns to the orchestrator:

Figure 2: Delegation through task. The searches and the sub-agent’s notes stay in its own context.

The research agent’s search calls and its notes never enter the orchestrator’s transcript. After a dozen searches the orchestrator holds the task it sent and one report. That is what lets a deep agent run long jobs without context creep, the slow growth of a transcript until the model loses the thread.

The trade is visibility. The orchestrator cannot check a claim against raw results it never saw. A sub-agent’s report should name its sources.

Skills load only when a task needs them

A SKILL.md starts with YAML frontmatter holding a name and a description (the library caps the description at 1,024 characters). The harness puts only those two fields in the system prompt and tells the model to read_file the full instructions when a task matches the description. This is progressive disclosure: eight skills cost eight short lines until one is needed.

The memory-manager skill shows what the full body holds once read:

Section What it tells the sub-agent
Workflow Assess the request, then save, recall or forget
Recall Search broadly first with an empty query, then narrow by category or keyword
Categories Five labels: preference, fact, decision, project, feedback
Forgetting Confirm with the user before deleting, unless the request is unambiguous

Table 2: The memory-manager skill body, read only when a memory task comes up.

Because the model matches a task against the description alone, a description that does not say when the skill applies is a skill that never loads. We call this a silent skill. Adding eight more skills is cheap in tokens, but each new description has to be distinct enough that the model picks the right one.

The backend decides what can run

The backend is where files live and whether a command can run at all. Two settings in the scripts look safer than they are:

Setting What it sounds like What it does
FilesystemBackend(virtual_mode=True) A sandbox Anchors paths under the root folder and blocks traversal such as ... The library’s docstring says it provides no sandboxing or process isolation
USE_SANDBOX=true A LangSmith cloud sandbox, as the script’s comment says Selects LocalShellBackend, which the library documents as unrestricted shell execution on the host
Neither, and execute called A shell An error, because the backend cannot run commands

Table 3: Three backend settings and what they really do.

We call the middle row sandbox by name: a flag whose name promises isolation the code does not provide. The library does ship a separate LangSmithSandbox backend, but the script never selects it.

The choice of backend follows from what the agent needs to run:

Figure 3: Choosing a backend. Code execution needs both a real sandbox and a person approving commands.

create_deep_agent takes interrupt_on to pause before chosen tools, which is how a person approves each execute call. Lesson 26.2’s Python tool gives the same advice for its own runner, and M27 builds the approval step.

Three layers of memory

The memory variant keeps three layers apart:

Layer Scope Store in 03b Store in the deployed version
Conversation One thread MemorySaver checkpointer, lost on restart The same
Long-term Every thread, every session A JSON file, long_term_memories.json, under the key memories:<user id> A Delta table, agent_memories, with user_id, content, category and saved_at

The orchestrator’s prompt tells it to recall memories at the start of each conversation and to save preferences, facts, decisions, project context and feedback as they come up. Running the script’s own memory functions against a scratch file shows two limits the code carries:

Call Returned Why
Engineer A saves “Prefers refund answers as a bulleted checklist” Saved
Engineer B recalls everything Found 2 memories, A’s included CURRENT_USER_ID is fixed to default-user. Every user shares one namespace

The second row is a shared namespace, and in a multi-user deployment it leaks one engineer’s notes into another’s session. The user key has to come from authentication. The fourth row is the cost of substring search, and the script’s comment names PostgresStore as the production replacement.

The module’s deployed design, described in the deep agent overview, runs the same harness behind a FastAPI backend with Server-Sent Events, eight sub-agents and a recursion limit of 100.

In practice: Larkspur’s support deep agent

  1. Delegate research. A research-agent sub-agent searches outage reports, and the orchestrator reads one report per task.
  2. Write a skill per specialist. A billing-fixes skill’s description says when it applies (changes to refund or proration scripts). The model loads it only for those tasks.
  3. Pick the backend on purpose. The default is virtual-mode files with no execution. Running a billing test needs a real sandbox backend and interrupt_on approval for every command.
  4. Key memory on the user. Each engineer’s preferences live under their authenticated id, and recall uses search that tolerates a paraphrase.

Limits

  • No recorded run. The scripts need a model-serving endpoint and a Tavily key. This page describes their configuration and the library’s behaviour rather than a measured run.
  • One library version. Tool names and backend behaviour are those of deepagents 0.7.32. Check them again after an upgrade.

Key Takeaways

  • A deep agent is one orchestrator configured with file tools, sub-agents through task, skills and a backend. Only a sub-agent’s final message returns, which keeps the orchestrator’s context small.
  • Skills put only their name and description in the prompt and are read in full when a task matches, so each description must say when its skill applies.
  • Audit the harness by its configuration. FilesystemBackend(virtual_mode=True) blocks traversal without isolating anything, LocalShellBackend runs unrestricted shell on the host, and memory keyed to one fixed user id is shared by everyone.

Check yourself

1. How does a call to the task tool keep the research agent's searches out of the orchestrator's context?

The task tool runs the sub-agent with its own messages and tools, and only its final message returns to the orchestrator. The search calls and notes stay in the sub-agent’s context, and the orchestrator reads only the report.

2. The harness loads eight skills from 03c_skills. What does the orchestrator's system prompt hold for them before any is needed?

Only each skill’s name and description from the SKILL.md frontmatter, eight short lines in all. When a task matches a description, the model calls read_file for the full instructions. This is progressive disclosure.

3. A teammate sets USE_SANDBOX=true, believing the agent's commands now run in a cloud sandbox. Are they safe?

No. Despite the script’s comment, the code selects LocalShellBackend, which the library documents as unrestricted shell execution on the host with no isolation. Code execution belongs in a real sandbox backend, with a person approving each command through interrupt_on.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. You ship a deep agent to Larkspur’s support engineers, built like 03b_long_term_memory_agent.py. Someone sets USE_SANDBOX=true expecting cloud isolation, and the memory panel shows one engineer’s notes in another’s session. What is wrong?

What a strong answer covers:

  • The script’s comment promises a LangSmith sandbox, but the flag selects LocalShellBackend, which the library documents as unrestricted shell execution on the host
  • FilesystemBackend(virtual_mode=True) blocks path traversal and is not a sandbox either. Code execution needs a real sandbox backend and approval on each command through interrupt_on
  • Long-term memory is keyed by CURRENT_USER_ID, fixed to default-user, and every engineer reads and writes one namespace. The key must come from the authenticated user
  • recall_memories matches a substring of the stored text, and a paraphrase finds nothing. The script names PostgresStore as the production replacement

2. Larkspur wants two research agents: one writes the weekly outage summary with the same sections every week, the other answers open questions from support engineers. Which gets a planned pipeline and which a ReAct loop?

What a strong answer covers:

  • The weekly summary is a known-shape report. A planned pipeline has a fixed, predictable cost and runs the same steps every time, so one fixed test covers it
  • The open questions are multi-hop. A ReAct agent picks each search after reading the last result and can follow a lead the plan could not foresee
  • The ReAct agent’s cost varies. It needs a call cap such as ModelCallLimitMiddleware and an observable goal, such as evidence for each section, instead of trusting its claim that research is complete
  • The pipeline still needs a check for an empty search result per section. Many production researchers combine the two: plan first, then let each step react

3. A developer and tester pair writes a refund-proration helper for Larkspur’s billing code. After one round the tester reports 100% of its tests passing and a score of 9 out of 10. How do you know the code works?

What a strong answer covers:

  • A tester without a Python tool writes tests in its report and reasons about them. Its pass rate and score are the model’s estimates, not executed results
  • Giving the tester the Python tool makes the results real, at roughly twice the cost. Otherwise run the tests yourself, diff the changes and re-run them rather than trusting the final message
  • Log per run the reflection count against the cap, the developer and tester turn counts (r + 1 and r), and whether the last code block parses
  • Run model-written code in a fresh process with a timeout, closed standard input and an empty environment, and remember that this is a guard, not a sandbox

4. A vision-driven computer-use agent for Larkspur’s control panel keeps clicking, never reaches its goal and raises no error. What is going on, and how do you stop it?

What a strong answer covers:

  • When the observation is pixels, locating a control is the hard part. In the module’s runs gpt-4o-mini missed 53 of 53 clicks even with every miss fed back
  • A miss raises no error and changes nothing. The step cap is the only bound on the loop and has to be set in code
  • Success is graded on the environment, as the browser agent is graded on the cart’s contents, and a run that never touched the control is reported as errored, not failed
  • Prefer selectors to coordinates. Where pixels are unavoidable, the stronger model in the same runs (gpt-4o, 15 misses in 26 clicks, goal met in 2 of 3 runs) costs half as much per screenshot

5. Larkspur’s deep agent delegates web research to a sub-agent, and an engineer asks why the orchestrator’s context stays small even after dozens of searches. Then they ask to give it eight more skills. What do you tell them?

What a strong answer covers:

  • A call to task runs the sub-agent with its own messages and tools, and only its final message returns. The searches and notes stay in the sub-agent’s context
  • Skills use progressive disclosure: only each SKILL.md’s name and description sit in the system prompt, and the model calls read_file for the full instructions when a task matches
  • Eight more skills add eight more short lines to the prompt until one is needed, and each description has to say when its skill applies, because that is what the model matches a task against
  • Before adding skills that run code, check the backend: execute returns an error unless the backend can run commands, and LocalShellBackend runs them on the host

Key Takeaways

  • Keep the agent loop and change the tools: when the loop moves to code, browsers or screens, decide the observation, the success signal and the cap for each new environment.
  • Grade success on the environment (tests, the cart, the files written) and stop the loop with a counter or cap in code, never with the agent’s own claim that it is done.
  • A tester that only reads code estimates. A tester that runs code measures. Pay for the measurement when the result matters.
  • A deep agent’s safety comes from its harness: check which backend actually runs, which tools each sub-agent has, and which user key its memory uses.
