M26 Coding, computer-use and deep agents

Agents that write code, drive a browser or run for hours need a harness: sub-agents, a file system, skills and a tester that checks the work. You will move the ReAct loop from web search into files, browsers and screens, see where the success signal and the stop condition have to live, and then configure a deep agent instead of wiring a graph node by node. The M26 notebooks build on two ideas: the same agent loop running in new environments, and a deep-agent harness around one orchestrator.

The lessons keep the notebooks’ own examples, because their numbers come from those runs: a research report on Artificial Intelligence in Healthcare, a coding agent in a temporary folder, a mock browser with a shopping cart, a screen read from pixels, two small games for the developer and tester pair, and an insurer’s analytics agents in the deep-agent scripts. TL;DR

  • A planned research pipeline fixes its searches before any result comes back; a ReAct researcher picks each search after reading the last one. In one recorded run the pipeline made 3 searches and 2 LLM calls, the agent 4 searches and 5 LLM calls. Those are observations, not a benchmark.
  • Moving the loop to code, browsers or screens keeps the agent ⇄ tools graph and changes the tools, the observation and the success signal: tests grade the coding agent, the cart’s contents grade the browser agent. On pixels, gpt-4o-mini missed 53 of 53 clicks; gpt-4o missed 15 of 26 and met the goal in 2 of 3 runs.
  • A developer and tester pair is a critique-and-revise loop that ends by a rule in code: a reflection_count in state, a pure router and a recursion_limit of 2r + 4. Stub nodes show the developer runs r + 1 times and the tester r times, with zero model calls. A tester without a Python tool only estimates its pass rate.
  • A deep agent is one orchestrator inside a harness: file tools, a task tool that runs each sub-agent in its own context, skills whose name and description alone sit in the prompt, a backend and memory. 03a_simple_coding_agent.py configures 7 sub-agents and 8 skills.
  • The backend decides what code can do. FilesystemBackend(virtual_mode=True) blocks path traversal without isolating anything, and USE_SANDBOX=true selects LocalShellBackend, unrestricted shell on the host.

Mental model

Every lesson keeps this loop and changes one part of it. Lesson 26.1 swaps the environment: search results, a test run, a mock browser, a screenshot. Lesson 26.2 adds a tester whose critique becomes the next observation, and a counter in state ends the loop. In each case the success check and the stop belong to code or to the environment, never to the agent’s final message.

Planned pipeline vs ReAct loop

Lesson 26.1: Applied ReAct: web research, SWE and computer-use agents. Notebooks: 01a_web_research_agent.ipynb, 01b_swe_agent_applied.ipynb (optional), 01c_browser_agent_computer_use.ipynb (optional), 01d_vision_driven_computer_use.ipynb (optional)

You need a research report, but must decide whether its searches can be planned before seeing any results. You will compare a fixed research pipeline with a ReAct researcher on the same topic, then transfer the distinction to file edits and browser actions.

Step 1: Draw the two research paths

A planned researcher writes every search up front and runs them in a fixed sequence. A ReAct researcher chooses the next search after reading the results. The comparison builds both on the same topic, Artificial Intelligence in Healthcare:

The pipeline’s state carries more than messages: the topic, the planned questions, a {question: results} dict merged by a custom reducer, the report, and a log appended with operator.add. Each node returns only the keys it changes. The plan is fixed before any result comes back, and no edge goes back, so the pipeline cannot notice an empty search or follow a lead. The ReAct researcher is create_agent with one web_search tool, a prompt asking for one search per turn and 3 to 5 in all, and ModelCallLimitMiddleware as the bound.

Step 2: Compare a recorded run without treating it as a benchmark

One recorded live run has the following results. Search results and model choices change, so these counts and report lengths are observations rather than repeatable performance guarantees:

Planned pipeline ReAct agent
Web searches 3 4
LLM calls 2 5
Report characters 7,229 4,298

Step 3: Choose predictability or adaptive search

The pipeline’s three questions were written together and are broad and parallel. The agent started broad, then searched for things its results had named (AI models in surgery at Duke University, physician adoption statistics). The trade-off:

Planned pipeline ReAct agent
Who chooses the searches The plan, up front The model, after each observation
Cost Fixed and predictable Varies; bound it with a call cap
Reacts to empty or surprising results No Yes
Easy to test and debug Yes, same steps every run Harder, the path changes run to run
Good for Known-shape reports, batch jobs Open questions, multi-hop facts

Step 4: Combine planning with bounded exploration

Many production researchers combine them: plan first, then let each step react. M24 treats the pipeline side as workflow patterns.

The same loop in other environments

Step 1: Inspect actions and success signals

The applied examples keep the agent ⇄ tools graph and change only the tools and the environment.

  • SWE agent. The actions are file edits and the observation is a test run. Every file sits in a tempfile.mkdtemp() sandbox, paths are reduced to a filename inside it, and run_tests() runs one fixed pytest command, which constrains those tool interfaces. This is a teaching sandbox, not a security boundary against arbitrary adversarial code. Production execution needs isolation and resource limits. Tests are the reward signal. Diff the changes and re-run the tests yourself instead of trusting the final message.
  • Browser agent. screenshot_text, click, type_text and navigate are ordinary tools over a deterministic mock browser. Actions now change state, so the turn cap becomes a safety bound, and success is graded on the environment (the cart’s contents), not the agent’s words.
  • Vision-driven computer use. When the observation is pixels, locating a control is the hard part. In the example’s runs gpt-4o-mini missed 53 of 53 clicks, even with every miss fed back; gpt-4o missed 15 of 26 and met the goal in 2 of 3 runs, at half the cost per screenshot. A miss raises no error, so the step cap is the only bound on the loop. Prefer selectors to coordinates.

Key Takeaways

  • A planned pipeline fixes its searches up front. Its cost is predictable and it is easy to test, but it cannot react to an empty result or follow a lead.
  • A ReAct researcher picks each search after reading the last result, so it suits open and multi-hop questions at a variable cost that needs a call cap. Many production researchers plan first, then let each step react.
  • Moving the loop to code, browsers or screens changes only the tools. Sandbox the actions, grade success on the environment rather than the agent’s words, and prefer selectors to coordinates.

Check yourself

1. Why can the planned research pipeline not follow a lead that one of its searches turns up?

Its questions are fixed before any result comes back, and no edge goes back to planning, so it cannot notice an empty search or add one. The ReAct researcher chooses each search after reading the last observation, which is how it went on to search for things its results had named.

2. You need a weekly report with the same sections on a fixed topic, at a predictable cost. Planned pipeline or ReAct agent?

The planned pipeline. It suits known-shape reports and batch jobs, its cost is fixed, and it runs the same steps every time, so it is easy to test. A ReAct agent suits open questions and multi-hop facts, and its cost varies and needs a call cap.

3. A vision-driven computer-use agent keeps clicking, never reaches its goal and raises no error. What is going on, and what stops it?

It cannot locate the controls from pixels: in the reported experiment gpt-4o-mini missed 53 of 53 clicks even with every miss fed back. A miss raises no error, so the step cap is the only bound on the loop. Prefer selectors to coordinates.

Deep-agent harness

Lesson 26.3: Deep agents: orchestrator, sub-agents, skills and long-term memory. Notebooks: 03a_simple_coding_agent.py, 03b_long_term_memory_agent.py (optional), 03c_skills (optional)

A Larkspur deep agent may delegate research and save preferences through a prebuilt harness. You will inspect which tools and instructions the harness exposes, distinguish path restrictions from execution isolation and trace which memory survives a new conversation.

Step 1: Inspect the configured harness rather than its name

The planned research pipeline of lesson 26.1 is a graph you wire node by node. A deep agent starts from the other end: one orchestrator model inside a ready-made harness that gives it files, sub-agents, skills, an execution backend and memory, and you configure the harness instead of drawing the graph. Lesson 26.3 uses the deepagents library’s create_deep_agent, in two command-line scripts. The tool and backend behaviour below is that of deepagents 0.7.32, the version in this course’s lock file.

The parts, as the scripts configure them:

Part What it gives the orchestrator In 03a and 03b
Built-in tools File operations (ls, read_file, write_file, edit_file, glob, grep), execute for shell commands, and task to call a sub-agent Added by create_deep_agent; execute returns an error unless the backend can run commands
Custom tools Domain actions 03a: name_project, internet_search (Tavily) and four Databricks Genie tools for an insurer’s customer, distribution, policy and claims data. 03b adds save_memory, recall_memories, forget_memory
Sub-agents Specialists, each a dict of name, description, system_prompt, skills and tools 03a: 7 (senior-developer, code-reviewer, research-agent and four insurer analytics agents). 03b adds memory-manager
Skills Instructions in SKILL.md files, loaded from /skills/ 8 skills in 03c_skills, one per sub-agent; each sub-agent’s prompt is “Follow the … skill instructions”
Backend Where files live and whether commands run FilesystemBackend(root_dir=..., virtual_mode=True) by default; LocalShellBackend when USE_SANDBOX=true
Checkpointer Memory within one thread MemorySaver, one thread_id per task
Model The orchestrator’s model databricks-claude-opus-4-6, temperature 0.1

Step 2: Keep delegated context out of the parent transcript

A call to task runs the sub-agent with its own messages and tools, and only its final message returns to the orchestrator. The research agent’s search calls (up to 5 results each by default) and its notes stay in its own context; the orchestrator reads its report.

Step 3: Read instructions only when the task needs them

A SKILL.md starts with YAML frontmatter, a name and a description. The harness puts only those two fields in the system prompt and tells the model to read_file the full instructions when a task matches the description. This is progressive disclosure: eight skills cost eight short lines until one is needed. The memory-manager skill, for example, sets a workflow (assess, then save, recall or forget), five categories, and a rule to confirm before deleting unless the request is unambiguous.

Step 4: Inspect the actual execution backend

Two settings in the scripts look safer than they are:

  • FilesystemBackend(virtual_mode=True) anchors paths under root_dir and blocks traversal such as ... The library’s own docstring says it provides no sandboxing or process isolation.
  • The script’s comment says USE_SANDBOX=true selects a LangSmith cloud sandbox. The code selects LocalShellBackend, which the library documents as unrestricted shell execution on the host, with no isolation.

Code execution belongs in a real sandbox backend, with a person approving each command; create_deep_agent takes interrupt_on for that. The reference implementation gives the same advice for its Python tool.

Step 5: Separate thread state from durable memory

The implementation keeps three layers apart:

Layer Scope Store in 03b Store in the deployed version
Conversation One thread MemorySaver checkpointer, lost on restart The same
Long-term Every thread, every session A JSON file, long_term_memories.json, under the key memories:<user id> A Delta table, agent_memories, with user_id, content, category and saved_at
Artifacts Project files the developer agent writes projects/ beside the script A Unity Catalog volume

The orchestrator’s prompt tells it to recall memories at the start of each conversation and to save preferences, facts, decisions, project context and feedback as they come up. Two limits are visible in the code: CURRENT_USER_ID is fixed to default-user, so every user shares one namespace until it comes from authentication, and recall_memories matches a substring of the stored text, so a paraphrase finds nothing. The script’s comment names PostgresStore as the production replacement.

The module’s deployed design, in deep_agent_overview.md, runs the same harness behind a FastAPI backend with Server-Sent Events, eight sub-agents and a recursion limit of 100.

Key Takeaways

  • A deep agent is one orchestrator configured with file tools, sub-agents through task, skills and a backend, instead of a graph wired node by node. Only a sub-agent’s final message returns, so the orchestrator’s context stays small.
  • Skills put only their name and description in the prompt and are read in full when a task matches. Eight skills cost eight short lines until one is needed.
  • Check what the backend really allows. FilesystemBackend(virtual_mode=True) blocks traversal without isolating anything, and LocalShellBackend runs unrestricted shell on the host, so use a real sandbox with interrupt_on approval.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. You ship a deep agent to Larkspur’s support engineers, built like 03b_long_term_memory_agent.py. Someone sets USE_SANDBOX=true expecting cloud isolation, and the memory panel shows one engineer’s notes in another’s session. What is wrong?

What a strong answer covers:

  • The script’s comment promises a LangSmith sandbox, but the flag selects LocalShellBackend, which the library documents as unrestricted shell execution on the host
  • FilesystemBackend(virtual_mode=True) blocks path traversal and is not a sandbox either, so code execution needs a real sandbox backend and approval on each command through interrupt_on
  • Long-term memory is keyed by CURRENT_USER_ID, fixed to default-user, so every engineer reads and writes one namespace; the key must come from the authenticated user
  • recall_memories matches a substring of the stored text, so a paraphrase finds nothing; the script names PostgresStore as the production replacement

2. Larkspur wants two research agents: one writes the weekly outage summary with the same sections every week, the other answers open questions from support engineers. Which gets a planned pipeline and which a ReAct loop?

What a strong answer covers:

  • The weekly summary is a known-shape report: a planned pipeline has a fixed, predictable cost and runs the same steps every time, so it is easy to test
  • The open questions are multi-hop: a ReAct agent picks each search after reading the last result and can follow a lead the plan could not foresee
  • The ReAct agent’s cost varies, so it needs a call cap such as ModelCallLimitMiddleware and an observable goal, such as evidence for each section, instead of trusting its claim that research is complete
  • Many production researchers combine the two: plan first, then let each step react

3. A developer and tester pair writes a refund-proration helper for Larkspur’s billing code. After one round the tester reports 100% of its tests passing and a score of 9 out of 10. How do you know the code works?

What a strong answer covers:

  • A tester without a Python tool writes tests in its report and reasons about them, so its pass rate and score are the model’s estimates, not executed results
  • Giving the tester the Python tool makes the results real, at roughly twice the cost; otherwise run the tests yourself, diff the changes and re-run them rather than trusting the final message
  • Log per run the reflection count against the cap, the developer and tester turn counts (r + 1 and r), and whether the last code block parses
  • Run model-written code in a fresh process with a timeout, closed standard input and an empty environment, and remember that this is a guard, not a sandbox

4. A vision-driven computer-use agent for Larkspur’s control panel keeps clicking, never reaches its goal and raises no error. What is going on, and how do you stop it?

What a strong answer covers:

  • When the observation is pixels, locating a control is the hard part; in the module’s runs gpt-4o-mini missed 53 of 53 clicks even with every miss fed back
  • A miss raises no error, so the step cap is the only bound on the loop and has to be set in code
  • Success is graded on the environment, as the browser agent is graded on the cart’s contents, not on the agent’s words
  • Prefer selectors to coordinates; where pixels are unavoidable, the stronger model in the same runs (gpt-4o, 15 misses in 26 clicks, goal met in 2 of 3 runs) costs half as much per screenshot

5. Larkspur’s deep agent delegates web research to a sub-agent, and an engineer asks why the orchestrator’s context stays small even after dozens of searches. Then they ask to give it eight more skills. What do you tell them?

What a strong answer covers:

  • A call to task runs the sub-agent with its own messages and tools, and only its final message returns, so the searches and notes stay in the sub-agent’s context
  • Skills use progressive disclosure: only each SKILL.md’s name and description sit in the system prompt, and the model calls read_file for the full instructions when a task matches
  • Eight more skills add eight more short lines to the prompt until one is needed, and each description has to say when its skill applies, because that is what the model matches a task against
  • Before adding skills that run code, check the backend: execute returns an error unless the backend can run commands, and LocalShellBackend runs them on the host

Key Takeaways

  • Keep the agent loop and change the tools: when the loop moves to code, browsers or screens, decide the observation, the success signal and the cap for each new environment.
  • Grade success on the environment (tests, the cart, the files written) and stop the loop with a counter or cap in code, never with the agent’s own claim that it is done.
  • A tester that only reads code estimates; a tester that runs code measures. Pay for the measurement when the result matters.
  • A deep agent’s safety comes from its harness: check which backend actually runs, which tools each sub-agent has, and which user key its memory uses.
