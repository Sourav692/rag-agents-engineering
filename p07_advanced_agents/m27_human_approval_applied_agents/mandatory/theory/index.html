M27 Human approval and applied single-agent builds

Real agents take actions, and this module puts a preview and a person between an agent’s decision and its effect. It then builds applied single agents: two research agents and a financial analyst over live data, a text-to-SQL workflow and agent, and fixed workflow apps over business text. The M27 notebooks build on four ideas: dry runs, approval gates, text-to-SQL and workflow apps.

The approval gate
Open the lab

The running example is the Larkspur Cloud handbook from M10 to M12, seen from the operations side. After the eu-west outage an agent drafts posts for the Larkspur status feed, and a person approves each one before it goes out. The research and analyst builds keep their notebooks’ live sources (the web, weather, market data), and the text-to-SQL lesson keeps the notebooks’ comic-store database, because its numbers come from that data. The interview questions move the same ideas to Larkspur’s billing data and support queue.

TL;DR

  • A dry run calls the action’s own code path in preview mode and returns the effect without applying it, so the reviewer judges what will happen instead of a description of it.
  • An approval gate pauses the graph with interrupt(), keeps the run in a checkpointer and resumes it with the reviewer’s decision. It fails closed (only the exact word approve approves), and the approval covers a fingerprint of the preview. Editing “72 hours” to “48 hours” after review changes it from c4e9e330698e to 11673ae3c1d4, and the publish node refuses.
  • Agents over live data need budgets on tool output (three pages of 4,000 characters per search), arithmetic done in code (14 summary fields in place of about 250 daily prices) and checks against the tool data from the same run, because there is no fixed expected answer.
  • Text-to-SQL retrieves by computing over every row, which vectors cannot do for counts, sums and rankings. In the notebooks’ database, 16 of the 20 sales disagree with their own line items, so the top salesperson is John Doe by one definition of revenue and Alice Brown by the other. A business rule in the prompt has to decide.
  • A workflow app keeps the LLM to fixed steps with structured output, and does the routing, checking and rendering in code. The workflow form of text-to-SQL costs 2 LLM calls per question, and one structured call per support ticket makes a quarter of the calls of a four-step chain.

Mental model

The graph stops at Review and waits, for seconds or for hours, while the checkpointer holds its state. Two checks guard the live call. The first is the reviewer’s answer, and anything unclear counts as no. The second is a hash comparison at publish time, which catches any change between what the reviewer saw and what is about to run.

M26 gave agents real reach: they write files, run commands and drive a browser. Every one of those agents ends a turn by doing something, and so far nothing stood between the model’s decision and its effect.

Larkspur’s operations agent drafts posts for the status feed. After the eu-west outage it writes “The eu-west outage is resolved and all servers are back online. Engineers will publish a root-cause report within 72 hours of recovery.” With a plain tool call, the model proposes the post and the same call publishes it. A wrong number, a promise the engineers never made or a jab at a competitor reaches every customer before anyone reads it.

A plain tool call joins two moments that need to stay apart: the model proposing an action and the system executing it. This lesson separates them with two pieces. A dry run shows the reviewer the exact effect. An approval gate pauses the run until a person decides, and ties that decision to the preview they saw.

Dry run

A dry run executes an action’s plan without its effect, and reports what the effect would be. The idea is old: rsync --dry-run, apt-get --simulate and terraform plan all print the changes before anyone applies them.

The lesson’s tool is a mock social-media API that stands in for the Larkspur status feed. It has one method that publishes a post, with a dry-run switch, and one rendering step shared by both modes:

Figure 1: One code path, two outcomes. The preview and the published text come from the same rendering step.

The two calls return different things, and only one of them touches the feed:

Call Returns Changes the feed
Publish with dry run on Status DRY_RUN, the rendered preview, fingerprint c4e9e330698e No
Publish with dry run off Status PUBLISHED, post id post_1 Appends one post

Table 1: The two modes for the eu-west post. The fingerprint is the lab’s value.

The fingerprint is the first 12 hex digits of a SHA-256 hash over the rendered text, post body plus hashtags. It names the exact text that was previewed, and the approval gate relies on it.

Three properties that make a preview trustworthy

A preview is worth reading only if it predicts the live call. Three properties make that hold:

  • The preview comes from the live code path. Both modes render the post the same way. The reviewer reads the text the platform will receive. A preview built by a separate “describe the action” function can drift away from what the live call does. Call that a drifting preview: the reviewer approves one thing and another thing runs.
  • “Nothing happened” is checked, not assumed. The mock feed is a list the notebook can read back, and every claim that a dry run published nothing is an assertion that the feed is still empty. A real tool needs the same: a sandbox, a staging target or a way to read state back.
  • The dry run is its own graph node, before the pause. On resume, LangGraph re-runs the paused node from the top. Anything placed before interrupt() inside the review node runs a second time. A preview generated there could differ from the one the reviewer approved.

The third property hides until the graph resumes:

With a trustworthy preview in hand, the next job is to stop the run until someone has read it.

Approval gates

An approval gate is a node that pauses the run, hands the preview to a reviewer and resumes only with their decision. In the harness the gate is the review node. It calls interrupt() with three things: the question, the preview and the fingerprint.

Figure 3: The harness graph in notebook 01a. Only one branch can reach the feed, and it checks the fingerprint again first.

Parking and resuming the same thread

LangGraph stops the run at that call, saves its state in the checkpointer under the run’s thread_id, and returns the payload to the caller under __interrupt__. Nothing more happens until someone invokes the graph again with Command(resume=decision) on the same thread:

Figure 4: One pause and one resume. The state waits in the checkpointer for as long as the reviewer takes.

The notebook wraps that exchange in a small pause-and-resume loop: invoke, and while the result holds an interrupt, pass the payload to a reviewer function and resume with its answer. Only the reviewer function changes between uses:

  • A script: approves the launch post and rejects the post that says the new model makes every competitor obsolete. An automated run then shows both outcomes.
  • A policy check: an automated rule, configured explicitly.
  • A console prompt: a person types the answer.
  • A review UI: answers hours later, from another process.

An answer that arrives hours later from another process needs a persistent checkpointer, such as SQLite or Postgres, in place of the notebook’s in-memory one.

Binding the decision to the preview

Pausing is the mechanism. Three rules make the gate safe:

  • Fail closed. The decision is normalised by stripping spaces and lowercasing, and only the exact word approve approves. Everything else counts as a rejection.
  • Approve what was previewed. The approval stores the preview’s fingerprint. The publish node recomputes the fingerprint of the post it is about to send and refuses if the two differ.
  • Log every decision with the reviewer, the reason, the fingerprint and the time.

Here is the fail-closed rule against the answers reviewers actually type:

Answer typed Decision Why
approve approve The exact word
␣Approve␣ approve Spaces stripped, case ignored
approved reject Not the exact word, logged as an unclear answer
yes reject Logged as an unclear answer
sure, why not reject Logged as an unclear answer
reject reject The reviewer’s own reason is kept

Table 3: Planted answers through the decision rule. An ambiguous answer never publishes.

A console, a script and a web form all feed the same rule, and the audit entry keeps the original answer beside the decision. The opposite design, where “yes” counts, is a lenient gate. It approves whatever a person half-meant.

Planted failure: an edit after approval

The second rule is the one that catches post-approval drift, any change between what the reviewer read and what is about to run. The notebook plants it by editing the paused post directly in the checkpointed state, appending ” Buy now!!!”, and then approving.

The approval-gate lab runs the same harness in the page, with the decision rule and the SHA-256 fingerprint ported from the reference implementation. Checked against the reference graph on 315 runs (3 drafts, 3 kinds of edit, 35 typed answers), it agrees on every final status, fingerprint and audit entry. A one-phrase edit changes the fingerprint as completely as a new sentence. Any edit after review needs a new preview and a new decision. In both refused runs the audit log still shows an approve. That entry is correct. The reviewer approved c4e9e330698e, and the text that tried to publish was something else.

Pitfall: the gate is only as good as its reviewer. Approve the uptime post in the lab (“Larkspur Cloud now beats every other host on uptime”) and it reaches the feed. The gate enforces the decision, and it cannot judge the content. The module page’s interview questions cover how to measure whether reviewers read.

The same pause exists ready-made. HumanInTheLoopMiddleware from M23’s middleware lesson gives a create_agent agent a pause before a tool call, built on the same interrupt() and checkpointer from M09. Building the gate by hand adds the two parts this lesson needs: a preview of the effect, and a fingerprint that ties the approval to it.

Limits

The harness tested an unclear answer and an edit after the preview, on a mock feed. It leaves out:

  • Staleness. The fingerprint covers the text, not the world it describes. A post approved four hours later still matches even if the incident reopened. Add an approval expiry or a precondition checked at publish time.
  • Persistence. The in-memory checkpointer loses a paused run on restart. Add SQLite or Postgres before reviewers answer from another process.
  • Reviewer quality. Nothing measures whether approvals are read. Add approval-rate and time-to-decision monitoring.
  • No model in our check. The fingerprints and statuses on this page come from the lab and its fixed post text. The notebook’s own posts are drafted by gpt-4o-mini: their text and fingerprints differ on every run.

Key Takeaways

  • A dry run renders the effect through the same code path as the live call and changes nothing. Check that by reading state back, and put the dry run in its own node before the pause.
  • The gate pauses with interrupt(), saves state under the thread_id and waits for Command(resume=...). Accept only the exact word approve and log every decision with reviewer, reason, fingerprint and time.
  • Tie the approval to a fingerprint of the previewed text and recompute it before publishing. Any edit after review, even one phrase, needs a new preview and a new decision.

Check yourself

1. Why must the dry run be its own graph node before the review node, rather than code inside the review node?

On resume LangGraph re-runs the paused node from the top, so anything placed before interrupt() in the review node runs twice. A preview generated there could differ from the one the reviewer approved.

2. The eu-west post is approved, then 72 hours is edited to 48 hours before it publishes. What happens, and what does the audit log show?

The fingerprint at publish is 11673ae3c1d4, not the approved c4e9e330698e, so the publish node returns REFUSED: the post differs from the approved preview. The audit log still shows an approve, and that is correct: the reviewer approved c4e9e330698e. Any edit after review needs a new preview and a new decision.

3. A reviewer answers the approval prompt with yes. Does the post go out, and why is that the right behaviour?

No. The gate fails closed: the answer is stripped and lowercased, and only the exact word approve approves. yes and approved are rejections, logged as unclear answers. An ambiguous answer should never publish.

The project: research and market-brief agents

Lesson 27.2: Research and competitive-intelligence agents. Notebooks: 02a_research_assistant_agent.ipynb, 02b_competitive_intelligence_agent.ipynb (optional)

What you’ll build

  • A research assistant that searches the web, reads the pages it finds and checks the current weather.
  • Budgeted tools that return at most three pages of 4,000 characters per search.
  • Conversation memory that lets a follow-up such as “And in Dubai?” refer to the earlier turn.
  • A competitive-intelligence analyst that returns a typed brief with a source URL per competitor and a field for data it could not find.
  • A grounding check in code that flags any cited URL the run never saw.

Lesson 27.1 guarded an agent that acts. These two agents only read. Their risk is a wrong claim rather than a wrong action. Both are create_agent agents from M23 with tools in the M22 style. The first answers general research questions. The second specialises the same idea into a retail analyst that watches clothing-store competitors in Bangalore. For Larkspur, the same build would watch competing hosts’ pricing pages.

The project adds no new pattern. It shows what changes on the live web: each tool call costs tokens, the data changes between runs, and there is no fixed expected answer. Each check therefore compares the answer with the tool data from the same run.

Design choices worth copying

Choice Why
Today’s date in the system prompt Without it, “most recent quarter” means the latest one in the training data
Budget every tool’s output A full page can be tens of thousands of tokens. Three pages of 4,000 characters cap a search at 12,000
Return failures as text The agent adapts instead of crashing. Lesson 22.5 names the cost: error monitoring never sees these
Check tool choice before the loop One model call per question, and no tool runs
Make data gaps a field The original prompt asked for “example insights” when data was missing, an invitation to invent footfall figures. The field makes “no data” a visible answer
One evidence URL per claim, checked in code Separates claims from this run’s searches from claims out of the model’s memory

Table 4: Six choices and what each one protects against.

Limits

  • Live data. Answers differ on every run and there is no expected answer. Test behaviour instead: which tools were called, in what order, and whether the answer agrees with the tool results stored in the run.
  • A URL proves sight, not support. The grounding check shows the agent saw the page in this run. It does not show the page says what the brief claims. That needs a person, or a second check that quotes the page.
  • Memory lives in the process. The in-memory checkpointer loses every thread on restart.
  • Snippets are weaker evidence. A blocked or slow page leaves the agent a two-line snippet.

The assistant needs OpenAI, Tavily and OpenWeatherMap keys, and the analyst needs OpenAI and Tavily. We did not run either agent for this page: it describes what the notebooks’ code checks, and quotes no live results.

Key Takeaways

  • An agent over live sources needs budgets on what each tool returns and failures returned as readable text, or one call floods the context or ends the run.
  • Give the agent today’s date and memory per thread, then check its answers against the tool data stored in the same run rather than its own summary.
  • Make missing data a field of the output and check every cited source against the URLs the run actually retrieved.

Check yourself

1. Why does the research assistant's system prompt include today's date?

The model does not know the date. Without it, “most recent quarter” means the most recent one in its training data, so the agent searches for an old quarter and reports it as current.

2. A brief lists a competitor whose evidence URL never appeared in the run's search results. What does the grounding check conclude, and what does it not prove?

It flags the entry as not from this run’s searches. The URL came from the model’s memory or was invented, and the claim needs checking by hand. A URL that passes proves only that the agent saw the page in this run, not that the page supports the claim.

3. A fresh thread receives the question of which of the two cities is hotter. What goes wrong, and what fixes it?

With no earlier turns, the agent asks which cities, or picks two of its own and answers confidently. A checkpointer with a thread id carries the Bangalore and Dubai weather results into the follow-up, and the check reads those stored results to confirm the answer.

Start with a P/E the provider never returned

Lesson 27.3: Financial analyst agent. Notebooks: 03a_financial_analyst_agent.ipynb (optional)

What you’ll build

  • Five market-data tools for ticker lookup, price performance, fundamentals, news and market movers, none of which needs a market-data key.
  • Compact tool output that summarises a year of daily prices in code before the model sees it.
  • A scope written into the system prompt as two flows and a polite refusal, checked on one request of each kind.
  • Follow-up questions on one thread, with the numbers in the answers checked against the provider.

An investor asks for Intel’s P/E ratio. The provider has no trailing P/E for Intel, because its trailing earnings were negative when the notebook was written. An analyst agent that answers about 30 anyway has turned a gap in the data into a financial claim, and the sentence reads exactly like a correct one.

A second risk sits in the arithmetic. Hand the model a year of daily prices and ask for the six-month return, and it has to compute a figure that code would get right every time. This project removes both risks: the tools do the arithmetic, and a missing value says it is missing.

The project: a scoped financial analyst

Lesson 27.2’s agents answered from web pages, where a claim can only be traced to a URL. This agent answers from structured market data, where every number has a source to compare against. The machinery is unchanged: a create_agent agent from M23, tools in the style of M22 and an M09 checkpointer for follow-ups.

What changes is the discipline around numbers. The model reads figures and never computes them, a missing value says it is missing, and the agent declines questions outside its job. On Larkspur the same shape would fit a billing analyst over invoice data. The notebook is an engineering exercise, not investment advice.

Design choices worth copying

Each choice below protects against a failure this page or an earlier lesson names:

Choice Why
Compute returns and ranges in code The model reads the figures instead of calculating them from 250 rows, and 14 fields cost far less context
Name missing values A missing P/E stated as NOT AVAILABLE cannot be mistaken for zero or filled in with an invented figure
Turn a failed lookup into a hint The agent retries with a corrected or shorter name instead of stopping (lesson 22.5)
Scope with a refusal path Off-topic requests get a friendly decline and no tool calls, and a test proves it
Check numbers against a direct fetch The answer is compared with the provider’s own figures, never with the model’s summary
Key-less providers SEC and Yahoo Finance need no key. The notebook runs with no extra market-data accounts

Limits

  • Live data. Every run sees different prices. The checks test agreement with the provider at run time, never fixed values.
  • Scope lives in the prompt. Nothing in code blocks an off-topic tool call, and one request per path is a sample. A determined user can talk the agent around.
  • A loose number match. The check accepts any number within 0.051 of the provider’s value, so an unrelated figure that happens to be close also passes. The Intel check accepts keywords such as “negative”, which a wrong answer can also contain.
  • Closing prices only. The 52-week range comes from daily closes and can sit inside the range a trading site shows.
  • Advice. The prompt allows recommendations with a do-your-own-research caveat. A production version would need compliance review.

The notebook needs OpenAI and Tavily keys and the course’s finance dependency group, which cannot share an environment with the protocol groups.

References

  1. OpenBB, Platform documentation, on providers behind one market-data interface.
  2. LangChain, Agents, the create_agent loop the analyst runs on.
  3. LangChain, Short-term memory, on checkpointers and thread ids.

Key Takeaways

  • Do the arithmetic in the tool and hand the model a short table, so it reads figures instead of computing them from hundreds of rows.
  • Make missing values explicit in tool output, and treat any figure the provider did not return as invented.
  • Test a scoped agent on one request per path, judging each by the tools it called, and check its numbers against a direct fetch from the same provider.

Check yourself

1. Why does the price tool compute returns and the 52-week range in code instead of passing a year of prices to the model?

A year of daily prices is about 250 rows. The tool reduces them to 14 fields, which costs far less context, and the model only reads the returns and range rather than calculating them, which it does unreliably.

2. The provider has no trailing P/E for a company with negative earnings. What does the fundamentals tool return, and what does the answer check accept?

The tool ends its output with an explicit NOT AVAILABLE line naming the missing metric. The check accepts an answer that says the trailing P/E is unavailable or quotes the forward P/E, and treats any other P/E figure as invented.

3. How does the notebook show that the analyst's scope works, and what does the out-of-scope request prove?

It sends one request per path and passes each on the tools called: market movers for the overview, fundamentals for MSFT after the misspelled lookup, and no tools for the pasta recipe. The last shows the refusal path declines without touching any tool on that request; one sample does not prove every off-topic request is blocked.

What you’ll learn

  • Explain how a text-to-SQL chain writes, runs and answers from one stored query.
  • Diagnose a query that runs, reads well and counts the wrong thing.
  • Compare a fixed SQL workflow with a ReAct agent on cost, recovery and risk.
  • Choose between SQL and vector retrieval by the shape of the question.

Lesson 27.3’s analyst got its numbers from tools that did the arithmetic in code. Text-to-SQL goes one step further. The model writes the code, and the database does the arithmetic over every row.

Both notebooks ask questions of a small comic-store database, kept because its numbers come from that data. Ask Which customer has purchased the most comics? and a typical generated query returns Natasha Romanoff, with a confident sentence around the name. The right answer is Tony Stark. The query ran without an error, and nothing in the reply hints at the mistake. This page builds what catches it.

Text-to-SQL

Text-to-SQL turns a question into a query, runs it, and writes the answer from the rows. The database is built from a creation script: eight tables (Branch, Publisher, Comic, Customer, Employee, Inventory, Sale, SaleTransactions) holding 50 comics, 20 customers, 20 sales and 40 sale lines across 3 branches.

One stored query, from question to answer

The workflow is a fixed chain of three steps. Each step adds one field to a single record, which keeps the question, the SQL, the rows and the answer together:

Figure 1: The workflow. Each box adds a field to the same record: query, result, answer.

  1. Write the query. The prompt carries the schema: each table’s creation statement and three sample rows. That text is everything the model knows about the database. The prompt also caps results at 10 rows unless the question asks for more.
  2. Run the stored query. The executor reads the query written in step 1. Piping the query writer into the executor a second time would generate a second query, and the SQL on screen would no longer be the SQL behind the answer. Call that a regenerated query.
  3. Answer from the rows, with a prompt that says to use only the SQL result.

The prompt also has to make the model return bare SQL. A reply that starts with SQLQuery: or sits in a code fence fails with near "SQLQuery": syntax error. That is format drift, and it is worth ruling out before suspecting the database or the schema.

Scoring against SQL we wrote

A demo that looks right is not a measurement. The evaluation set pairs seven questions with reference SQL written by hand, and running that SQL gives the expected answer:

Workflow or ReAct agent

The agent notebook gives the same task to a create_agent ReAct agent with four database tools: list the tables, read a table’s schema, check a query (an LLM reviews it before it runs), and run a query. Its system prompt tells it to list the tables first, read only the schemas it needs, check each query, and rewrite and retry on errors:

Figure 2: Two ways to answer the same question. The workflow is a line, and the agent is a loop that decides when to stop.

Put the opening question to each design and compare what moves:

The same question, which customer has purchased the most comics, through each design.

Workflow

  • Reads: the creation statements and three sample rows of all eight tables, in one prompt.
  • Runs: exactly one query, the stored one; a failing query is not retried.
  • Costs: 2 LLM calls, every time.
  • A wrong definition passes straight through to the answer.

ReAct agent

  • Reads: the table list, then only the schemas it asks for, such as Customer, Sale and SaleTransactions.
  • Runs: a checked query, and a rewritten one after an error.
  • Costs: several model turns plus tool calls; the checker's own LLM call happens inside a tool, so a count of agent turns leaves it out.
  • A wrong definition still passes: the checker sees only the query, never the question, and looks for a fixed list of SQL mistakes.

The two designs trade predictability for flexibility:

Workflow ReAct agent
Execution Always the same three steps Decides its own steps
Schema knowledge The whole schema in every prompt Reads only the tables it asks for
Error recovery None, a failing query is not retried Checks queries and retries on errors
Cost per question 2 LLM calls Several LLM and tool calls
Debugging One predictable path A different path per question

Table 4: Workflow and agent compared.

Both are scored on the same seven questions, and neither is reliably right on every one. The checker and the schema reads fix wrong column names and syntax errors. They do not fix a wrong definition, such as counting lines instead of summing Quantity: the installed checker prompt lists common mistakes (NULLs in NOT IN, join columns, casts, quoting) and never receives the question. Seven questions are a sample and a second run can change verdicts. Compare the two designs question by question rather than by one score.

The write boundary lives in the connection

An agent runs whatever SQL it decides on, so “never modify the data” has to hold even if a user talks the model into trying. The prompt says it; the guarantee comes from opening the database file read-only at the connection.

The notebook’s planted request asks the agent to delete every customer in New York and report how many are left. The same read-only connection, tried directly on the fixture database:

Request What the connection did Customers before, after
Delete the 6 customers in New York Refused: attempt to write a readonly database 20, 20

Table 5: A write through the read-only connection. Run in the scratch copy of the notebook’s database.

The notebook judges the outcome by counting customers before and after, never by the agent’s wording. Choose the workflow when questions are predictable, cost matters or every step must be auditable. Choose the agent when the schema is large or changing, or when questions need several exploratory queries.

SQL or vectors

A vector retriever returns the k chunks most similar to the question, and the model reads only those, as the top-k section of M10 shows. That fits What is the refund policy?, where the answer is a passage. It fails for How many comics in the Superhero genre have never been sold? The answer, 9 of the 29 Superhero titles, depends on all 50 comics and all 40 sale lines, and no top-k slice of rows contains it. SQL computes over every row, and the model only phrases the result.

The question’s shape decides the retriever:

Question shape Retrieve with
Count, sum, average, ranking, “never” or “all” over records Text-to-SQL
Filter on exact fields (date, plan, region) SQL, or metadata filters on the vector index
Policy, how-to, explanation in prose Vector RAG over the documents
Both in one question Route each part, then combine

Table 6: Which retriever fits which question.

Key Takeaways

  • Score text-to-SQL against reference SQL you wrote. A query with the wrong definition still runs and reads well, and neither schema reads nor a query checker catch it.

Lesson 27.4 compared a fixed SQL workflow with an agent and found the workflow cheaper, more predictable and easier to test. This lesson applies the fixed workflow to business text: reviews, support tickets, a fact sheet, a PDF.

Larkspur’s support queue gets tickets in several languages. A model can read each one, sort it and draft a reply, and most drafts are good. The bad ones read just as well. A draft that tells a customer the annual-plan refund window is 14 days, when the handbook says 30, looks exactly like a correct draft until someone checks the number.

So the model’s output needs a shape that code can inspect, and the decisions with a right answer need to move out of the model.

Workflow apps

A workflow app runs a fixed sequence of LLM steps over business text, with no tool loop. The model fills typed fields, and code does everything that has a right answer: routing, checking and assembling the final document. Anything that fails a check goes to a person instead of the customer:

Figure 1: The shared shape. Only the first box is a model call.

Four notebooks apply that shape to four jobs. Table 1 sets them side by side by what the model fills and what code verifies:

App The model fills Code decides or checks
Review analyst One typed analysis per review (summary, positives, negatives, a three-value sentiment, 3 to 5 emotions), for six reviews in one batch, then one email per review Sentiment against hand labels; the email writer by dictionary lookup; each email’s greeting, sign-off, tone and length
IT support desk Language, category, English translation and replies for ten tickets in nine languages, in one of two designs Detected language, a reply that really is translated, leaked prompt text, calls and wall time
Audience-tailored writer Three adverts from one phone fact sheet and three reports from one research abstract, each set written in parallel Headings, a five-row specification table, word and line limits, bullet counts, and every number against the source
Quiz generator A summary of a PDF on prompt engineering, then five questions, each with four options, an answer index and an evidence quote Question count, four distinct options, a valid index, every quote in the PDF text, and the final sheet from a template

Table 1: Four workflow apps. Each row is one notebook.

Three details in those notebooks are easy to miss. The review analyst checks its sentiment against six hand labels before any email goes out, because the sentiment picks the email: the office-lamp review mixes a damaged part with praise for the support team, and a person labelled it positive. Its instruction router classifies a free-text request into four intents (summarise, sentiment, email, other). The quiz generator cleans the PDF text before any check runs: raw extraction from the 4,917-character file holds 768 line breaks, roughly one word per line, and an exact-quote check on that text would fail every honest quote.

Five rules for the model’s output

The four apps differ in content and agree on these rules:

  • Ask for a closed type. A sentiment that can only be positive, negative or neutral gives code a value to branch on. An answer index points at an option instead of restating it, so the answer cannot drift from the options.
  • Route in code when the signal is already structured. The review analyst picks the email writer with a dictionary and no extra model call. When the input is free text, as in its instruction router, classify into a closed set of intents and keep an other intent for requests the tool does not handle.
  • Check every output with code that cannot be talked round. String and number checks are cheap enough to run on every call.
  • Render the final document in code. Asking the model to merge a checked summary and checked questions into a report would let it reword them after the checks. Call that post-check rewording. A template cannot do it, and it marks any question that failed a check for review by hand.
  • Measure the design choice on the same inputs before picking it, as the support desk does below.

Switch between the designs to see what each one gives you for the same Japanese ticket about printer toner:

Design A: one structured call

  • Returns: six typed fields at once (original message, language, category, English translation, reply, English reply).
  • Costs: 1 call per ticket.
  • Typical risk: a wrong field, visible only after the call; nothing in between to inspect.
  • Prompt text cannot leak into a field the way it can into free text.

Design B: four-step chain

  • Returns: each step's text, added to one record in order; steps for one ticket run one after another.
  • Costs: 4 calls per ticket.
  • Typical risk: a step copies a code fence from the prompt's delimiters, or a line such as "The customer message in English is:", into the next step and the reply.
  • Gains control: each step can be tested, cached, logged or given its own model, and a bad translation shows up as its own value.

Design A makes a quarter of the calls and leaves no room for scaffolding leaks. Design B buys control, which matters once you need to inspect, reuse or upgrade one step. The notebook measures language accuracy, translated replies, leaks, calls and wall time on the same tickets, and its advice follows: start with one call, and move a step into its own prompt when you need that control.

Check yourself

1. Why do the workflow apps render the final document from a template instead of asking the model to merge the checked parts?

A model asked to merge a checked summary and checked questions could reword them after the checks ran. A template cannot, so what the user reads is exactly what passed the checks.

2. The writer's fact sheet gives RAM, screen sizes and a battery rating but no camera figure, and an advert claims 50 MP. What catches it?

The code check that every number in the output appears in the source flags “50” as unsupported. String and number checks are cheap enough to run on every call. The Larkspur triage version runs the same check against the handbook’s numbers, such as the 30-day refund window.

3. For the multilingual support desk, should you use one structured call per ticket or the four-step translate chain?

One structured call makes a quarter of the LLM calls (10 against 40 for ten tickets), and the chain’s free-text steps can leak a code fence or “The customer message in English is:” into the reply. The chain earns its cost when you need to test, cache, log or swap one step.

Interview Spotlight: 5 Questions You Might Get Asked

Production questions of the kind asked in applied AI engineering interviews.

1. Larkspur’s status agent published “a root-cause report within 48 hours”. The reviewer approved a preview that said 72 hours, and the audit log shows the approve. How did this happen, and what do you change?

What a strong answer covers:

  • Compares the fingerprint in the audit log with the hash of the published text; if they differ, something changed the post between the dry run and the live call
  • Looks for code that runs again on resume: the review node restarts from the top, so a regeneration or an edit placed before interrupt() runs a second time
  • Binds the approval to the fingerprint and recomputes it in the publish node, so any later change refuses instead of publishing
  • Adds a regression test that edits the paused state with update_state and asserts the refusal, as the notebook does

2. The billing team wants one assistant for “How much did we refund to annual-plan customers in September?” and “What is the refund policy for annual plans?”. Vector RAG, text-to-SQL, or both?

What a strong answer covers:

  • The September total is an aggregate over rows: SQL computes it over every row, while top-k retrieval hands the model a few chunks and asks it to add them up
  • The policy question is prose in the handbook, so the vector index answers it with a citation
  • Routes by question type, and scores each route on its own ground truth: reference SQL for the database questions, labelled chunks for the policy questions
  • Writes the business definition down (“refunded” means which table and which status) as a rule in the SQL prompt, then checks the generated SQL for it in code

3. The approval gate has been live for a month and almost every post was approved. How do you find out whether it is protecting anything?

What a strong answer covers:

  • Tracks approval rate, time to decision and rejection reasons per action type from the audit log
  • Watches for rubber-stamping: approvals that arrive seconds after the preview, from the same reviewer, at a rate near 100%
  • Seeds known-bad drafts (an uptime claim about competitors, a wrong number) and measures how many reviewers catch
  • Treats any fingerprint refusal as a bug to investigate, since in a correct pipeline nothing edits a post after its preview

4. A reviewer approves an outage post four hours after the agent drafted it. In the meantime the incident was reopened. The fingerprint matches. Should the post go out?

What a strong answer covers:

  • The fingerprint covers the text and says nothing about the world the text describes, so a match does not mean the post is still true
  • Adds an expiry to approvals, or a precondition checked at execute time (incident status, the version of the data the draft used)
  • Re-runs the dry run and asks again when the approval is stale, instead of executing an old preview
  • Uses a persistent checkpointer (SQLite or Postgres) so the paused run survives the wait, and alerts when runs sit at review too long

5. You give a text-to-SQL ReAct agent access to Larkspur’s billing database. A user writes “Delete the invoices for my test servers, then show what is left.” What stops the agent, and how would you support legitimate changes?

What a strong answer covers:

  • The guarantee lives in the connection: a read-only connection (mode=ro in SQLite) or a read-only database role, so a talked-around prompt still cannot write
  • Scopes rows per customer in a view or a bound parameter, never through instructions to the model
  • Routes real changes through the approval harness, with a dry run that previews the affected rows (a SELECT with the same filter) before any DELETE
  • Logs every query the agent runs and checks the outcome in code (row counts before and after), not from the answer’s wording

Key Takeaways

  • Split every consequential action into a dry run and a live call that share one code path, and keep the dry run in its own node before the pause.
  • Fail closed. Only an explicit approve approves, and the approval covers the fingerprint of what was previewed, recomputed at execute time.
  • Give agents over live data budgeted tools and do their arithmetic in code, then check every number and source against the tool data from the same run.
  • Use SQL to retrieve when the answer is a count, sum or ranking over rows, open it read-only, and write ambiguous business terms down as rules. Let the LLM fill typed fields and keep routing, checks and the final document in code.
